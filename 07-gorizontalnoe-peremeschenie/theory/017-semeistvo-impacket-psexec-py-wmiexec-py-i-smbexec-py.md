# Семейство Impacket: psexec.py, wmiexec.py и smbexec.py в контексте горизонтального перемещения

## Контекст и базовые понятия: Impacket как инструмент двойного назначения

Impacket — это набор модулей на языке Python для работы с сетевыми протоколами, изначально разработанный для нужд пентестинга и форензики, но ставший стандартом де-факто для злоумышленников при горизонтальном перемещении (Lateral Movement). Инструментарий позволяет манипулировать пакетами на низком уровне, что дает возможность реализовывать легитимные административные функции (удаленное выполнение команд, сбор учетных данных, релей-атаки) без необходимости установки дополнительных агентов на целевую систему.

Ключевая особенность Impacket заключается в его способности имитировать легитимный сетевой трафик. В отличие от классических эксплойтов, эксплуатирующих уязвимости в коде, скрипты семейства Exec используют встроенные механизмы Windows (SMB, WMI, RPC) для выполнения задач. Это делает их «Living off the Land» (LotL) инструментами, которые сложно отличить от действий системных администраторов или легитимного программного обеспечения без глубокого анализа контекста и артефактов.

В контексте горизонтального перемещения три основных скрипта — `psexec.py`, `wmiexec.py` и `smbexec.py` — решают одну задачу: получение удаленной оболочки (shell) на целевой машине. Однако они используют принципиально разные механизмы взаимодействия с операционной системой, что влияет на их обнаруживаемость, требования к привилегиям и следы в логах.

Для понимания различий необходимо разграничить три сущности, которые часто путают из-за схожести функционала:

| Скрипт | Основной протокол/механизм | Метод выполнения кода | Требует загрузки бинарника? | Типичный порт/интерфейс |
| :--- | :--- | :--- | :--- | :--- |
| **psexec.py** | SMB + RPC (svcctl) | Запуск сервиса с исполняемым файлом | Да (загружает `psexesvc.exe` в ADMIN$) | TCP 445 (SMB), RPC Pipe `svcctl` |
| **wmiexec.py** | DCOM + RPC (WMI) | Создание процесса через WMI | Нет (использует встроенные механизмы) | TCP 135 (RPC), динамические порты |
| **smbexec.py** | SMB + RPC (svcctl) | Запуск сервиса с временным BAT-файлом | Нет (генерирует BAT on-the-fly) | TCP 445 (SMB), RPC Pipe `svcctl` |

**Разграничение понятий:**
*   **PsExec (Sysinternals)** vs **psexec.py (Impacket)**: Классический PsExec от Microsoft загружает бинарный файл `psexesvc.exe` на целевую машину. Скрипт `psexec.py` из Impacket делает то же самое, но реализует протокол вручную через Python. Оба оставляют следы в виде создания сервиса и загрузки файла.
*   **WMI (Windows Management Instrumentation)** vs **DCOM (Distributed Component Object Model)**: `wmiexec.py` использует WMI как интерфейс управления, но для передачи данных по сети применяет протокол DCOM. Именно DCOM-вызовы являются ключевым индикатором компрометации при использовании этого скрипта.
*   **SMBExec vs PsExec**: Оба используют создание сервиса. Разница в том, что `smbexec.py` не требует загрузки внешнего исполняемого файла. Вместо этого он генерирует временный BAT-файл, который запускает `cmd.exe`, перенаправляет вывод в файл, а затем читает этот файл через SMB. Это делает `smbexec.py` менее заметным для антивирусов, но более заметным для SIEM-систем, анализирующих создание сервисов.

Использование Impacket стало массовым благодаря его доступности и простоте. Злоумышленники часто компилируют эти скрипты в исполняемые файлы (например, через PyInstaller), чтобы избежать детектирования по имени процесса `python.exe`. Кроме того, современные версии Impacket по умолчанию используют SMB3 с шифрованием, что затрудняет анализ трафика на уровне сети (NDR), перекладывая нагрузку на анализ конечных точек (EDR/XDR).

## Внутреннее устройство: Архитектура и механизмы работы скриптов

Каждый из трех скриптов имеет уникальную внутреннюю архитектуру, определяющую его поведение в сети и на целевой системе. Понимание этих механизмов критично для создания эффективных правил детектирования.

### 1. psexec.py: Классический сервисный подход

Скрипт `psexec.py` реализует протокол, аналогичный оригинальному PsExec. Процесс взаимодействия выглядит следующим образом:

1.  **Аутентификация:** Устанавливается SMB-сессия к целевой машине с использованием предоставленных учетных данных (пароль, хеш NTLM или Kerberos-билет).
2.  **Загрузка полезной нагрузки:** Скрипт загружает скомпилированный бинарный файл `psexesvc.exe` (или аналогичный) в административный шар `ADMIN$` на целевой машине.
3.  **Создание сервиса:** Через RPC-вызов к pipe `svcctl` создается новый сервис (обычно с именем `PSEXESVC`). В качестве пути к исполняемому файлу указывается путь к загруженному бинарнику.
4.  **Запуск сервиса:** Сервис запускается, что приводит к выполнению `psexesvc.exe` в контексте SYSTEM (если используются административные учетные данные).
5.  **Установка соединения:** `psexesvc.exe` открывает named pipe (обычно `\\.\pipe\psexesvc`) и ожидает подключения.
6.  **Обмен данными:** Атакующий подключается к этому pipe, отправляет команды, получает вывод и закрывает соединение.
7.  **Очистка:** Сервис останавливается и удаляется, бинарный файл может быть удален (хотя часто остается как артефакт).

Ключевой особенностью является использование named pipe для коммуникации. Это создает четкий след в логах файлового сервера и событийной модели Windows (Event ID 4656, 4663 для доступа к pipe).

### 2. wmiexec.py: DCOM и WMI без загрузки файлов

`wmiexec.py` использует совершенно другой подход, не требующий загрузки внешних бинарных файлов на целевую машину.

1.  **Инициализация DCOM:** Скрипт устанавливает соединение с целевой машиной через порт 135 (RPC Endpoint Mapper) и запрашивает интерфейс `IWbemServices` через протокол DCOM.
2.  **Создание процесса:** Через WMI инициируется создание нового процесса (`Win32_Process.Create`). В качестве команды передается `cmd.exe /Q /c <command>`.
    *   Флаг `/Q` отключает отображение приглашения командной строки.
    *   Флаг `/c` указывает выполнить команду и завершить работу.
3.  **Перенаправление вывода:** Чтобы получить вывод команды, `wmiexec.py` использует трюк с временным файлом. Команда модифицируется так, чтобы перенаправить `stdout` и `stderr` во временный файл в папке `ADMIN$` (например, `\\127.0.0.1\ADMIN$\__12345678.90`).
4.  **Чтение результата:** После выполнения команды скрипт подключается по SMB к этому временному файлу, читает его содержимое и удаляет.
5.  **Завершение:** Процесс `cmd.exe` завершается, временный файл удаляется.

Важно отметить, что родительским процессом для `cmd.exe` будет `wmiprvse.exe` (WMI Provider Host). Это критический индикатор. Кроме того, коммуникация происходит через зашифрованные RPC-пакеты, что делает анализ трафика сложным без ключей шифрования.

### 3. smbexec.py: Сервис с BAT-файлом

`smbexec.py` находится между двумя предыдущими вариантами. Он использует создание сервиса (как PsExec), но не загружает бинарный файл.

1.  **Генерация BAT-файла:** Скрипт генерирует временный BAT-файл на лету. Содержимое файла выглядит примерно так:
    ```bat
    @echo off
    set output_file=C:\Windows\Temp\__output.tmp
    cmd.exe /c <command> > %output_file% 2>&1
    ```
2.  **Создание сервиса:** Через RPC `svcctl` создается сервис (часто с именем `RemComSvc` или случайным), который запускает этот BAT-файл.
3.  **Выполнение:** Сервис запускает `cmd.exe`, который выполняет команду и записывает результат во временный файл.
4.  **Получение результата:** Скрипт подключается по SMB к временному файлу, читает его и удаляет.
5.  **Удаление сервиса:** Сервис удаляется.

В отличие от `wmiexec.py`, здесь нет DCOM-вызовов, но есть создание сервиса и запись/чтение файлов через SMB. В некоторых реализациях `smbexec.py` может использовать обратное SMB-соединение (reverse SMB) для получения вывода, что еще больше усложняет детектирование.

### Сравнительный анализ механизмов

| Характеристика | psexec.py | wmiexec.py | smbexec.py |
| :--- | :--- | :--- | :--- |
| **Механизм запуска** | Загрузка бинарника + Сервис | WMI `Win32_Process.Create` | Сервис + BAT-файл |
| **Родительский процесс** | `services.exe` | `wmiprvse.exe` | `services.exe` |
| **Следы на диске** | Файл `psexesvc.exe` в ADMIN$ | Временный файл вывода (кратковременно) | Временный BAT-файл (кратковременно) |
| **Сетевой порт** | 445 (SMB) | 135 (RPC) + динамические | 445 (SMB) |
| **Протокол коммуникации** | Named Pipe (`psexesvc`) | DCOM/RPC | SMB (чтение файла) |
| **Шифрование** | SMB3 (по умолчанию) | DCOM (по умолчанию) | SMB3 (по умолчанию) |
| **Сложность детектирования** | Средняя (известные сигнатуры) | Высокая (легитимный WMI) | Средняя (создание сервисов) |

## Применение и работа с предметом: Практическое использование и детектирование

На практике выбор между скриптами зависит от контекста: наличия антивируса, настроек EDR, доступных привилегий и требований к скрытности.

### Типовые сценарии использования

1.  **psexec.py:** Используется, когда требуется стабильная, полнофункциональная оболочка с поддержкой перенаправления ввода/вывода. Часто применяется в начальных этапах атаки, когда есть уверенность в наличии административных прав. Риск обнаружения выше из-за загрузки бинарного файла и создания сервиса с известным именем.
2.  **wmiexec.py:** Предпочтителен для скрытности. Не требует загрузки файлов, что обходит многие сигнатурные антивирусы. Широко используется в автоматизированных инструментах (например, в Cobalt Strike через модуль `wmi`). Однако может быть заблокирован политиками WMI или брандмауэрами, блокирующими исходящие RPC-соединения.
3.  **smbexec.py:** Используется как альтернатива `psexec.py` при блокировке загрузки файлов. Менее заметен для EDR, так как не загружает бинарники, но более заметен для SIEM из-за частого создания и удаления сервисов.

### Паттерны детектирования

Детектирование Impacket требует корреляции данных из нескольких источников:

1.  **EDR/XDR (Process Tree):**
    *   **wmiexec.py:** Поиск процессов `cmd.exe` или `powershell.exe`, запущенных от имени `wmiprvse.exe`.
    *   **psexec.py/smbexec.py:** Поиск процессов `cmd.exe`, запущенных от имени `services.exe`, с аргументами, указывающими на временные файлы или BAT-скрипты.
    *   **Python:** Обнаружение процессов `python.exe`, запускающих скрипты с аргументами, содержащими IP-адреса или имена хостов.

2.  **Сетевые логи (NDR/NetFlow):**
    *   **wmiexec.py:** Подозрительная активность на порту 135 (RPC) с последующим подключением к динамическим портам.
    *   **psexec.py/smbexec.py:** Подключения к SMB (порт 445) с последующим доступом к ADMIN$ или другим административным шарам.

3.  **Логи Windows (Sysmon/Event Logs):**
    *   **Event ID 4688 (Process Creation):** Анализ командных строк.
    *   **Event ID 7045 (Service Creation):** Создание сервисов с именами, похожими на `PSEXESVC`, `RemComSvc`, или с путями к временным файлам.
    *   **Event ID 5140/5145 (Network Share Connection):** Подключения к ADMIN$ с необычных источников.

### Типичные ошибки и подводные камни

*   **Игнорирование SMB3 шифрования:** Современные версии Impacket шифруют SMB-трафик. Детектирование только по сетевому трафику без расшифровки будет неэффективным.
*   **Фальшивые срабатывания:** Легитимные администраторы также используют PsExec и WMI. Ключевым фактором является контекст: время выполнения, источник подключения, частота создания сервисов.
*   **Компиляция в EXE:** Злоумышленники часто компилируют скрипты в исполняемые файлы, чтобы избежать детектирования по имени процесса `python.exe`. Необходимо мониторить хеши файлов и поведение процессов, а не только их имена.

## Сквозной практический пример: Имитация атаки и детектирование

**Исходные условия:**
*   **Среда:** Домашняя лаборатория с двумя машинами: Атакующий (Kali Linux, IP: 192.168.1.100) и Цель (Windows 10, IP: 192.168.1.101).
*   **Инструменты:** Impacket (установлен на Kali), Sysmon (установлен на Windows с конфигурацией по умолчанию).
*   **Роль:** Пентестер, имеющий учетные данные локального администратора на целевой машине.
*   **Сценарий:** Выполнение горизонтального перемещения с использованием всех трех скриптов и анализ артефактов.

### Шаг 1: Использование psexec.py

**Действие:** Запуск `psexec.py` для получения оболочки на целевой машине.

```bash
# Команда на машине атакующего
python3 psexec.py administrator@192.168.1.101
```

**Ожидаемый вывод:**
```text
[*] Requesting shares on 192.168.1.101.....
[!] Share 'ADMIN$' is not writable.
[!] Share 'C$' is not writable.
[!] Share 'IPC$' is writable.
[*] Uploading file...
[*] Opening Service...
[+] Service PSEXESVC started!
[+] Connecting to \\192.168.1.101\pipe\PSEXESVC...
C:\Windows\system32> whoami
nt authority\system
```

**Артефакты на цели (Sysmon Event ID 4688 и 7045):**
*   Создание сервиса `PSEXESVC` (Event ID 7045).
*   Загрузка файла `psexesvc.exe` в `C:\Windows\System32\` (Event ID 11 - FileCreate).
*   Запуск `cmd.exe` от имени `services.exe` (Event ID 4688).

### Шаг 2: Использование wmiexec.py

**Действие:** Запуск `wmiexec.py` для выполнения команды через WMI.

```bash
# Команда на машине атакующего
python3 wmiexec.py administrator@192.168.1.101 "whoami"
```

**Ожидаемый вывод:**
```text
Impacket v0.10.0 - Copyright 2022 SecureAuth Corporation

[*] SMBv3.0 dialect
[*] PID: 1234
[*] Hostname: TARGET-PC
[*] Domain: WORKGROUP
[*] OS: Windows 10 Pro 19041
[*] Architecture: x64
[*] System time: 2023-10-27 10:00:00 UTC+0
[*] Username: administrator
[*] Domain: WORKGROUP
[*] Session: 1
[*] Connecting to \\192.168.1.101\ADMIN$\__12345678.90
[*] Reading output...
[*] Deleting output file...
nt authority\system
```

**Артефакты на цели (Sysmon Event ID 4688 и 10):**
*   Создание процесса `cmd.exe` с аргументами `/Q /c whoami > C:\Windows\Temp\__output.tmp 2>&1` (Event ID 4688).
*   Родительский процесс: `wmiprvse.exe` (Event ID 4688).
*   Сетевое подключение к порту 135 и динамическим портам (Event ID 3 - Network Connection).

### Шаг 3: Использование smbexec.py

**Действие:** Запуск `smbexec.py` для выполнения команды через временный сервис.

```bash
# Команда на машине атакующего
python3 smbexec.py administrator@192.168.1.101 "whoami"
```

**Ожидаемый вывод:**
```text

[*] PID: 1234
[*] Hostname: TARGET-PC
[*] Domain: WORKGROUP
[*] OS: Windows 10 Pro 19041

[*] System time: 2023-10-27 10:00:00 UTC+0

[*] Session: 1
[*] Connecting to \\192.168.1.101\ADMIN$\__12345678.90
[*] Reading output...
[*] Deleting output file...
nt authority\system
```

**Артефакты на цели (Sysmon Event ID 4688 и 7045):**
*   Создание сервиса `RemComSvc` (Event ID 7045).
*   Создание временного BAT-файла (Event ID 11 - FileCreate).
*   Запуск `cmd.exe` от имени `services.exe` (Event ID 4688).

### Ожидаемый вывод примера

Пример демонстрирует, что все три скрипта позволяют получить доступ `SYSTEM`, но оставляют разные артефакты:
*   `psexec.py` оставляет бинарный файл и сервис с известным именем.
*   `wmiexec.py` оставляет следы в WMI и создает процессы через `wmiprvse.exe`.
*   `smbexec.py` оставляет следы создания сервисов и временных файлов, но без загрузки бинарников.

## Аналитический вывод

Семейство Impacket представляет собой мощный инструмент для горизонтального перемещения, который активно используется как в легитимных целях, так и злоумышленниками. Ключевое различие между `psexec.py`, `wmiexec.py` и `smbexec.py` заключается в механизме выполнения кода: загрузка бинарника, использование WMI/DCOM и создание сервиса с BAT-файлом соответственно. Это определяет их обнаруживаемость: `psexec.py` наиболее заметен из-за загрузки файлов, `wmiexec.py` сложнее обнаружить из-за использования легитимных механизмов WMI, а `smbexec.py` занимает промежуточное положение.

Для эффективного детектирования необходимо использовать корреляцию данных из EDR, сетевых логов и событий Windows. Особое внимание следует уделять процессам, запущенным от имени `wmiprvse.exe`, созданию сервисов с подозрительными именами, и подключениям к административным шарам. Учитывая использование SMB3 шифрования, детектирование должно фокусироваться на поведении конечных точек, а не только на сетевом трафике.
