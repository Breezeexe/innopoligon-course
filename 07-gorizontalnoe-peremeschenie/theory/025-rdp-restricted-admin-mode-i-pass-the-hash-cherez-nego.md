# RDP Restricted Admin Mode и Pass-the-Hash через него

## Контекст и базовые понятия

Restricted Admin Mode (RAM) — это функция безопасности в протоколе удаленного рабочего стола (RDP) для операционных систем Windows, начиная с версии 8.1 и Windows Server 2012 R2. Функция предназначена для защиты учетных данных администраторов при подключении к потенциально скомпрометированным или недоверенным хостам. В стандартном режиме RDP-клиент передает целевому серверу учетные данные пользователя для создания интерактивной сессии. Эти данные кэшируются в памяти процесса Local Security Authority Subsystem Service (LSASS) на целевой машине. Если целевой хост заражен вредоносным ПО, способным извлекать данные из памяти (например, Mimikatz), злоумышленник может получить хеши паролей администратора и использовать их для дальнейшего горизонтального перемещения.

Restricted Admin Mode изменяет механизм аутентификации: вместо передачи пароля или интерактивного входа система использует сетевой вход (network logon). Клиент отправляет NT-хеш или Kerberos-билет, но целевой сервер не сохраняет учетные данные пользователя в памяти LSASS. Вместо этого создается сессия, привязанная к компьютерному аккаунту целевого хоста. Это предотвращает кражу учетных данных администратора, но создает новую уязвимость: поскольку для аутентификации требуется только NT-хеш, злоумышленник, обладающий хешем учетной записи с правами локального администратора на целевой машине, может выполнить атаку Pass-the-Hash (PtH) непосредственно через протокол RDP.

Ключевое разграничение заключается в типе входа, который инициирует RDP-сервер. В стандартном режиме используется Interactive Logon, что приводит к кэшированию учетных данных. В режиме Restricted Admin используется Network Domain Logon, что исключает кэширование паролей, но делает возможным использование хешей.

| Характеристика | Стандартный RDP (Interactive Logon) | RDP Restricted Admin Mode (Network Logon) |
| :--- | :--- | :--- |
| **Механизм аутентификации** | Интерактивный вход пользователя (Interactive Logon) | Сетевой вход (Network Logon) |
| **Хранение учетных данных** | Пароль/хеш кэшируется в LSASS на целевом хосте | Учетные данные не кэшируются в LSASS |
| **Идентификатор сессии** | Идентичность пользователя (User Identity) | Идентичность компьютерного аккаунта ($Computer$) |
| **Делегирование (Delegation)** | Поддерживается (Double Hop) | Не поддерживается (Credentials не доступны для делегирования) |
| **Уязвимость к краже** | Высокая (LSASS Dump) | Низкая (для паролей), но высокая для PtH |
| **Требование к клиенту** | Любой RDP-клиент | Клиент, поддерживающий `/restrictedadmin` или модифицированный (xfreerdp) |
| **Применение в атаках** | Кража паролей для последующих атак | Прямое горизонтальное перемещение (Lateral Movement) через RDP |

Restricted Admin Mode был изначально разработан для защиты администраторов, работающих с терминальными серверами, где вероятность присутствия вредоносного ПО выше. Однако, как показали исследования, эта функция стала вектором атак, так как позволяет обходить некоторые механизмы защиты, ориентированные на блокировку интерактивных входов, и использовать хеши для аутентификации.

## Внутреннее устройство предмета

Restricted Admin Mode и Pass-the-Hash через RDP представляют собой пересечение протокольных особенностей Windows и механизмов аутентификации. Для понимания механизма необходимо рассмотреть архитектуру аутентификации RDP, структуру реестра Windows и процесс передачи хешей.

### Механизм аутентификации RDP и Restricted Admin

Протокол RDP использует протокол CredSSP (Credential Security Support Provider) для безопасной передачи учетных данных. В стандартном режиме CredSSP шифрует учетные данные клиента и передает их серверу. Сервер, получив данные, выполняет интерактивный вход (Interactive Logon) для пользователя. Это приводит к созданию токена доступа и кэшированию учетных данных в LSASS.

В режиме Restricted Admin механизм меняется. Клиент RDP запрашивает у сервера аутентификацию в режиме «ограниченного администратора». Сервер проверяет наличие ключа реестра `DisableRestrictedAdmin` в ветке `HKLM\SYSTEM\CurrentControlSet\Control\Lsa`. Если ключ равен `0` (или отсутствует, в зависимости от версии ОС, но по умолчанию в новых системах он может быть установлен в `1` для отключения), сервер разрешает вход.

Вместо интерактивного входа сервер выполняет сетевой вход (Network Logon). Это означает, что аутентификация происходит на уровне протокола (NTLM или Kerberos), но сессия не привязывается к учетной записи пользователя в контексте безопасности целевой машины. Вместо этого сессия выполняется от имени компьютерного аккаунта целевого хоста. Это предотвращает кэширование пароля, но оставляет возможность использования NT-хеша для аутентификации.

### Реестр и конфигурация Restricted Admin

Управление режимом Restricted Admin осуществляется через ключи реестра Windows. Основные ключи находятся в `HKLM\SYSTEM\CurrentControlSet\Control\Lsa`.

| Ключ реестра | Значение | Описание |
| :--- | :--- | :--- |
| `DisableRestrictedAdmin` | `0` | Включает Restricted Admin Mode. Позволяет использовать хеши для входа через RDP. |
| `DisableRestrictedAdmin` | `1` | Отключает Restricted Admin Mode. Стандартное поведение для новых ОС. |
| `CredentialGuard` | `1` | Включает Credential Guard. Изолирует хеши в виртуализированной среде безопасности (VBS). |
| `LsaCfgFlags` | `1` | Устанавливает режим Credential Guard. |

Для включения Restricted Admin Mode на целевой машине необходимо установить `DisableRestrictedAdmin` в `0`. Это можно сделать локально или удаленно через WMI, PowerShell или инструменты вроде NetExec.

### Pass-the-Hash через RDP

Pass-the-Hash (PtH) — это техника атаки, при которой злоумышленник использует NT-хеш пароля вместо самого пароля для аутентификации. В контексте RDP и Restricted Admin Mode, атака работает следующим образом:

1.  Злоумышленник получает NT-хеш учетной записи с правами локального администратора на целевой машине.
2.  Злоумышленник обеспечивает наличие на целевой машине включенного Restricted Admin Mode (`DisableRestrictedAdmin = 0`).
3.  Злоумышленник использует RDP-клиент, поддерживающий передачу хеша (например, `xfreerdp` с флагом `/pth` или `mstsc.exe` через инъекцию хеша в память процесса).
4.  Клиент отправляет NT-хеш серверу. Сервер, находящийся в режиме Restricted Admin, принимает хеш для аутентификации, так как он не требует интерактивного входа, а использует сетевой.
5.  Устанавливается сессия RDP, позволяющая злоумышленнику выполнять действия от имени учетной записи, чей хеш был использован.

Важно отметить, что для работы PtH через RDP в некоторых случаях требуется также отключение проверки шифрования Oracle (CredSSP Encryption Oracle Remediation). В Windows 10 и Server 2016+ по умолчанию включена защита от уязвимости CredSSP. Для успешной атаки может потребоваться установка значения `AllowEncryptionOracle` в `2` или `0` в реестре клиента или сервера, в зависимости от конфигурации.

### Архитектура атаки и потоки данных

```text
[Атакующий] ──(NT Hash)──▶ [RDP Client] ──(CredSSP/NTLM)──▶ [RDP Server (Target)]
                              │                                   │
                              │   (Restricted Admin Mode)         │   (Network Logon)
                              │                                   │
                              └───(Инъекция хеша)─────────────────┘
```

В этой схеме RDP Server не сохраняет учетные данные пользователя. Вместо этого он проверяет хеш против локальной базы SAM или домена. Если хеш валиден, сессия создается. Однако, поскольку сессия не интерактивная, учетные данные не кэшируются в LSASS, что делает невозможным их последующее извлечение для атак на другие системы.

## Применение и работа с предметом

На практике работа с Restricted Admin Mode и Pass-the-Hash через RDP включает как защитные меры, так и исследовательские/пентестинговые операции. Пентестеры используют эти техники для горизонтального перемещения, когда стандартные методы (SMB, WMI) заблокированы или неэффективны.

### Инструментарий и методы

Для работы с PtH через RDP используются следующие инструменты:

1.  **xfreerdp (FreeRDP)**: Кроссплатформенный RDP-клиент, поддерживающий флаг `/pth` для передачи NT-хеша.
    ```bash
    xfreerdp /v:<target_ip> /u:<username> /pth:<nt_hash>
    ```
    Этот инструмент наиболее популярен в среде Kali Linux и других дистрибутивах для пентестинга.

2.  **mstsc.exe (Native RDP Client)**: Нативный клиент Windows. Для использования PtH требуется инъекция хеша в память процесса LSASS или использование утилит вроде Mimikatz для создания процесса с внедренным хешем.
    ```powershell
    sekurlsa::pth /user:<username> /domain:<domain> /ntlm:<nt_hash> /run:"mstsc.exe /restrictedadmin"
    ```
    Этот метод позволяет использовать стандартный интерфейс RDP, что может быть менее заметно для систем мониторинга.

3.  **NetExec (nxc)**: Инструмент для автоматизации атак, включающий поддержку PtH через различные протоколы, включая RDP.
    ```bash
    nxc rdp <target_ip> -u <username> -H <nt_hash>
    ```

4.  **Remmina**: Графический RDP-клиент для Linux, который также поддерживает передачу хешей через плагины или конфигурацию.

### Типичные ошибки и подводные камни

1.  **Отсутствие поддержки Restricted Admin Mode на сервере**: Если на целевой машине не установлен ключ `DisableRestrictedAdmin = 0`, атака не сработает. Пентестер должен сначала включить эту функцию, используя другие векторы атаки (например, WMI или SMB).
2.  **Проблемы с CredSSP**: В новых версиях Windows по умолчанию включена защита от уязвимости CredSSP. Для успешной атаки может потребоваться отключение этой защиты на клиенте или сервере.
3.  **Ограничения делегирования**: Поскольку Restricted Admin Mode не кэширует учетные данные, злоумышленник не может использовать двойной прыжок (Double Hop) для доступа к другим ресурсам сети от имени пользователя. Это ограничивает возможности горизонтального перемещения после установки сессии RDP.
4.  **Мониторинг и детекция**: Атаки через RDP могут быть обнаружены через мониторинг событий Windows (Event ID 4624 с типом входа 10 для интерактивного входа и 11 для сетевого входа). Изменение ключей реестра также оставляет следы в журналах аудита.

### Защитные меры

Для защиты от атак через Restricted Admin Mode и PtH через RDP рекомендуется:

1.  **Отключение Restricted Admin Mode**: Установка `DisableRestrictedAdmin = 1` в реестре всех хостов.
2.  **Блокировка NTLM**: Отключение NTLM аутентификации через групповые политики (GPO) и использование Kerberos.
3.  **Credential Guard**: Включение Credential Guard для изоляции хешей в виртуализированной среде.
4.  **Мониторинг**: Настройка детекции аномальной активности RDP, особенно входа с использованием сетевого типа (Type 11) и изменений ключей реестра.

## Сквозной практический пример: Горизонтальное перемещение через RDP с использованием Restricted Admin Mode

**Исходные условия**:
*   **Среда**: Домашняя лаборатория с двумя хостами: `Attacker` (Kali Linux с установленным FreeRDP и Mimikatz) и `Target` (Windows 10/11 или Windows Server 2019).
*   **Роль**: Пентестер, имеющий доступ к `Attacker` и получивший NT-хеш учетной записи `Administrator` на `Target` через предыдущую стадию атаки (например, через SMB или WMI).
*   **Сценарий**: Выполнение горизонтального перемещения с использованием Pass-the-Hash через RDP, включая включение Restricted Admin Mode на целевой машине.

**Шаг 1: Проверка и включение Restricted Admin Mode на целевой машине**

Перед попыткой подключения необходимо убедиться, что на `Target` включен Restricted Admin Mode. Если ключ `DisableRestrictedAdmin` отсутствует или равен `1`, его необходимо установить в `0`. Это можно сделать удаленно через WMI или PowerShell, используя полученные учетные данные.

```powershell
# Пример команды для включения Restricted Admin Mode через PowerShell
Invoke-Command -ComputerName Target -Credential (Get-Credential) -ScriptBlock {
    New-ItemProperty -Path "HKLM:\System\CurrentControlSet\Control\Lsa" -Name "DisableRestrictedAdmin" -Value "0" -PropertyType DWORD -Force
}
```

**Ожидаемый вывод**: Команда выполняется успешно, ключ реестра создается или обновляется. Это подтверждает, что `Target` теперь принимает подключения в режиме Restricted Admin.

**Шаг 2: Получение NT-хеша учетной записи**

Предположим, что пентестер уже получил NT-хеш учетной записи `Administrator` с `Target` с помощью инструмента вроде Mimikatz или Impacket. Хеш имеет формат 32-символьной шестнадцатеричной строки.

```text
# Иллюстративный вывод из Mimikatz
user : Administrator
hash : 30B3783CE2ABF1AF70F77D0660CF3453
```

**Ожидаемый вывод**: Хеш получен и готов к использованию. Важно убедиться, что хеш соответствует учетной записи `Administrator`.

**Шаг 3: Подключение через RDP с использованием Pass-the-Hash**

Используется инструмент `xfreerdp` для подключения к `Target` с передачей NT-хеша.

```bash
xfreerdp /v:192.168.1.100 /u:Administrator /pth:30B3783CE2ABF1AF70F77D0660CF3453 /dynamic-resolution
```

**Ожидаемый вывод**: Устанавливается сессия RDP. Пентестер получает доступ к рабочему столу `Target` от имени учетной записи `Administrator`. В логах `Target` будет зафиксирован вход с типом 11 (Network Logon).

**Шаг 4: Верификация и дальнейшие действия**

После подключения пентестер может выполнить команды для верификации прав и сбора информации.

```powershell
# Пример команды для проверки текущей учетной записи
whoami
```

**Ожидаемый вывод**: Вывод `target\administrator`, подтверждающий успешную аутентификацию и выполнение действий от имени администратора.

## Аналитический вывод

Restricted Admin Mode представляет собой классический пример компромисса между безопасностью и функциональностью. Изначально разработанный для защиты учетных данных администраторов от кражи через LSASS, он создал новый вектор атак — Pass-the-Hash через RDP. Это подчеркивает важность комплексного подхода к безопасности, где отдельные функции не должны рассматриваться изолированно. Для защиты от таких атак необходимо не только отключать Restricted Admin Mode, но и внедрять механизмы блокировки NTLM, такие как Credential Guard и аудит групповых политик. Пентестерам важно понимать, что даже защищенные механизмы могут быть использованы для обхода, если конфигурация системы не соответствует лучшим практикам безопасности.
