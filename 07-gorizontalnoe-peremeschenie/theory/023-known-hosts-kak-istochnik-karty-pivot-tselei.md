# known_hosts как источник карты pivot-целей при горизонтальном перемещении

## Контекст и базовые понятия

Файл `known_hosts` является критическим артефактом аутентификации хоста в протоколе SSH (Secure Shell), стандартизированном в RFC 4255 и RFC 8731. В контексте тестирования на проникновение и реагирования на инциденты (IR) этот файл представляет собой не просто список доверенных серверов, а **структурированную карту сетевой инфраструктуры**, доступную локально на скомпрометированной системе. Понимание механики работы `known_hosts` необходимо для разграничения понятий «аутентификация хоста» и «аутентификация пользователя», а также для понимания того, как атакующие используют легитимные механизмы доверия для обхода сетевых сегментаций.

SSH-протокол использует двухуровневую модель доверия. Первый уровень — доверие к хосту (host key verification). Когда клиент подключается к серверу в первый раз, сервер отправляет свой публичный ключ (хост-ключ). Клиент сохраняет этот ключ в файле `~/.ssh/known_hosts` (для конкретного пользователя) или `/etc/ssh/ssh_known_hosts` (глобально). При последующих подключениях клиент проверяет соответствие текущего ключа сохраненному. Если ключи не совпадают, соединение разрается с предупреждением о возможной атаке типа «человек посередине» (MITM). Второй уровень — аутентификация пользователя (user authentication), которая может происходить по паролю, публичному ключу или другим методам. Файл `known_hosts` не содержит пользовательских данных, но он косвенно раскрывает архитектуру сети, так как каждый записанный хост — это точка, к которой ранее обращался пользователь или сервис.

Ключевое разграничение, которое часто упускается в учебных материалах, заключается в различии между `known_hosts` и `authorized_keys`. Файл `authorized_keys` (`~/.ssh/authorized_keys`) определяет, **кто может войти** на локальную машину (список разрешенных публичных ключей пользователей). Файл `known_hosts` определяет, **на какие машины можно выйти** без интерактивного подтверждения отпечатка (fingerprint) (список доверенных удаленных хостов). Для атакующего, имеющего доступ к `authorized_keys`, задача горизонтального перемещения решается кражей приватного ключа. Для атакующего, имеющего доступ только к `known_hosts`, задача заключается в реконструкции топологии сети и поиске других векторов атаки (например, повторного использования ключей, если они скомпрометированы на целевых хостах, или выявления сервисных аккаунтов с слабыми паролями).

| Характеристика | `~/.ssh/known_hosts` | `~/.ssh/authorized_keys` |
| :--- | :--- | :--- |
| **Назначение** | Хранение доверенных публичных ключей **удаленных хостов** | Хранение доверенных публичных ключей **пользователей** для входа на локальный хост |
| **Уровень доверия** | Доверие к серверу (Host Key) | Доверие к субъекту (User Key) |
| **Содержимое** | Имена хостов/IP + хэш или открытый ключ хоста | Публичный ключ пользователя + опции (если есть) |
| **Роль в Lateral Movement** | Раскрывает **направления** движения (куда ходили) | Раскрывает **возможность** входа (кто может зайти) |
| **Формат хранения** | Часто хэшируется (`HashKnownHosts`) | Обычно в открытом виде (Base64) |
| **Влияние на аудит** | Позволяет восстановить историю посещений | Позволяет выявить избыточные привилегии |

В современных корпоративных средах `known_hosts` часто используется в автоматизированных сценариях (CI/CD пайплайны, скрипты мониторинга, сервисные аккаунты). Это делает файл особенно ценным, так как он может содержать ключи хостов критической инфраструктуры (базы данных, контроллеры домена, внутренние API), к которым у атакующего нет прямого доступа, но к которым есть доступ у скомпрометированного сервера. Важно отметить, что наличие записи в `known_hosts` не гарантирует успешного входа, если на целевом хосте не настроена аутентификация по ключу или если ключ был изменен. Однако это указывает на наличие **предыдущего успешного взаимодействия**, что является сильным индикатором потенциальной уязвимости для повторной эксплуатации.

## Внутреннее устройство файла known_hosts и методы извлечения

Файл `known_hosts` представляет собой текстовый файл, состоящий из строк, где каждая строка соответствует одному хосту. Структура строки определяется конфигурацией клиента SSH и политикой безопасности организации. Понимание форматов записи критично для эффективного извлечения информации, так как современные системы по умолчанию используют хэширование имен хостов для защиты от утечки топологии сети в случае компрометации файла.

### Структура записи и хэширование

По умолчанию в OpenSSH (начиная с версии 7.3) включена опция `HashKnownHosts yes`. Это означает, что имена хостов (доменные имена или IP-адреса) не хранятся в открытом виде. Вместо них записывается хэш, вычисленный по алгоритму SHA-256 с использованием случайной соли (salt).

Структура строки в хэшированном файле выглядит следующим образом:
```text
<hash1> <hash2> <public_key>
```
Где:
*   `<hash1>` — хэш имени хоста (hostname/IP).
*   `<hash2>` — хэш публичного ключа хоста (используется для быстрого поиска, если имя неизвестно, но ключ известен).
*   `<public_key>` — открытый ключ хоста в формате OpenSSH (например, `ssh-ed25519 AAAAC3Nza...`).

Если опция `HashKnownHosts` отключена, строка имеет вид:
```text
<hostname> <public_key>
```
Или для нескольких имен:
```text
<hostname1>,<hostname2>,<ip_address> <public_key>
```

### Механизм хэширования и его уязвимость

Алгоритм хэширования имен хостов использует функцию `HMAC-SHA256`. Соль генерируется случайно при создании файла или при первом добавлении хоста. Без знания соли восстановить исходное имя хоста из хэша невозможно. Однако на практике соль часто доступна или может быть извлечена из других артефактов, либо атакующие используют методы перебора (brute-force), если имена хостов предсказуемы (например, `db01`, `web02`, `192.168.1.10`).

Для извлечения информации из `known_hosts` используются следующие подходы:

1.  **Прямое чтение (если хэширование отключено):**
    Простой просмотр файла дает полный список целевых хостов.
2.  **Извлечение соли и дешифровка:**
    Если файл был создан старыми версиями SSH или с отключенным хэшированием, данные открыты. В новых системах соль может быть найдена в других файлах конфигурации или в памяти процесса `sshd`/`ssh`, если он активен.
3.  **Перебор (Brute-force):**
    Инструменты, такие как `ssh2john` (из пакета John the Ripper) или специализированные скрипты на Python, могут преобразовать хэши в формат, удобный для перебора. Если атакующий знает диапазон IP-адресов или стандартную систему именования, он может попытаться подобрать исходные значения.
4.  **Анализ публичных ключей:**
    Даже без расшифровки имен, публичные ключи хостов могут быть сопоставлены с известными ключами из других источников (например, из публичных репозиториев, если ключи скомпрометированы ранее, или из других скомпрометированных хостов).

### Сравнительная таблица форматов known_hosts

| Формат записи | Включен ли HashKnownHosts? | Читаемость для человека | Устойчивость к извлечению топологии | Типичное применение |
| :--- | :--- | :--- | :--- | :--- |
| `hostname ssh-rsa AAAA...` | Нет | Высокая | Низкая (имена открыты) | Старые системы, тестовые среды, отключенная политика |
| `* ssh-rsa AAAA...` | Нет (wildcard) | Средняя | Низкая (домен открыт) | Групповые политики, доверие к целым доменам |
| `HxYz... HwQr... ssh-ed25519 AAAA...` | Да | Низкая (требует расшифровки) | Высокая (требует соли или перебора) | Современные корпоративные стандарты (RHEL 8+, Ubuntu 20.04+) |
| `192.168.1.10 ssh-rsa AAAA...` | Нет | Высокая | Низкая (IP открыт) | Внутренние сети с жестко заданными IP |

### Артефакты и индикаторы

При анализе `known_hosts` на предмет горизонтального перемещения атакующий или аналитик SOC ищет следующие индикаторы:
*   **Наличие ключей хостов критической инфраструктуры:** Ключи, принадлежащие контроллерам домена (AD), базам данных (PostgreSQL, MySQL), или внутренним API-шлюзам.
*   **Дублирование ключей:** Если один и тот же публичный ключ хоста встречается в `known_hosts` разных пользователей, это указывает на использование сервисных аккаунтов или общих административных практик.
*   **Аномальные имена/IP:** Записи, не соответствующие стандартной системе именования компании, могут указывать на использование облачных сервисов, VPN-туннелей или скомпрометированных внешних узлов.
*   **Отсутствие хэширования:** Если в современной системе обнаружен файл с открытыми именами, это является индикатором слабого конфигурирования безопасности.

## Применение и работа с файлом known_hosts в пентесте и IR

На практике работа с `known_hosts` является этапом разведки (reconnaissance) и планирования горизонтального перемещения. Атакующий, получивший доступ к файловой системе скомпрометированного хоста, использует этот файл для построения графа достижимости. Аналитики IR используют его для восстановления цепочки атаки и определения масштаба компрометации.

### Этапы работы с known_hosts в пентесте

1.  **Локализация файла:**
    Файл может находиться в нескольких местах в зависимости от контекста доступа:
    *   `~/.ssh/known_hosts` — для текущего пользователя.
    *   `/etc/ssh/ssh_known_hosts` — глобальный файл, применяется ко всем пользователям.
    *   `~/.ssh/known_hosts2` — альтернативный файл (устаревший, но иногда используется).
    *   В конфигурации SSH (`~/.ssh/config` или `/etc/ssh/ssh_config`) могут быть указаны альтернативные пути через директиву `UserKnownHostsFile`.

2.  **Анализ содержимого:**
    Если файл не хэширован, атакующий сразу получает список целей. Если хэширован, необходимо определить, можно ли его расшифровать.
    *   *Проверка на хэширование:* Поиск паттерна `*` в начале строки или использование инструментов для определения типа хэша.
    *   *Поиск соли:* Соль может быть записана в файл, если используется специфическая конфигурация, или извлечена из памяти процесса `ssh` с помощью `gdb` или `procfs`.

3.  **Реконструкция целей:**
    *   Если хэширование отключено: список IP/доменов готов.
    *   Если хэширование включено: использование инструментов перебора. Например, если известно, что в сети используются имена вида `server01`, `server02`, можно сгенерировать wordlist и попробовать подобрать исходные значения.
    *   *Альтернативный подход:* Если атакующий не может расшифровать имена, он может попытаться использовать публичные ключи. Если ключи хостов стандартные (например, сгенерированные при установке ОС и не измененные), они могут быть известны из других источников или уязвимы к атакам на генератор случайных чисел (хотя это маловероятно для современных систем).

4.  **Планирование атаки:**
    На основе списка целей атакующий выбирает вектор:
    *   Если на целевом хосте есть публичный ключ атакующего в `authorized_keys`, вход возможен без пароля.
    *   Если ключей нет, но есть сервисный аккаунт с известным паролем (из других артефактов), используется брутфорс или перебор.
    *   Если есть доступ к `ssh-agent` скомпрометированного пользователя, можно использовать пересылку агента (agent forwarding) для подключения к целевым хостам, если они доверяют этому пользователю.

### Инструментарий и команды

Для работы с `known_hosts` используются следующие инструменты:

*   **cat/grep:** Для базового просмотра.
    ```bash
    cat ~/.ssh/known_hosts | grep -v "^#" | cut -d' ' -f1
    ```
*   **ssh2john (John the Ripper):** Для преобразования хэшированного `known_hosts` в формат, удобный для перебора.
    ```bash
    python3 /usr/share/john/ssh2john.py ~/.ssh/known_hosts > known_hosts.hash
    ```
*   **hashcat:** Для перебора хэшированных имен хостов, если известна соль или если хэширование слабое.
    ```bash
    hashcat -m 160 -a 3 known_hosts.hash '<wordlist>'
    ```
    *Примечание:* Режим 160 в Hashcat предназначен для SSH private keys, а не для known_hosts. Для known_hosts используется специализированный скрипт или режим для HMAC-SHA256, если соль известна. На практике чаще используется перебор с помощью `john` с использованием специфического формата `ssh` или кастомных скриптов.

*   **nmap/ssh-keyscan:** Для проверки доступности целей, если имена известны.
    ```bash
    ssh-keyscan -t rsa,ecdsa,ed25519 <target_ip> 2>/dev/null
    ```

### Типичные ошибки и подводные камни

*   **Игнорирование глобального файла:** Атакующий часто проверяет только домашнюю директорию пользователя, но забывает `/etc/ssh/ssh_known_hosts`, который может содержать ключи хостов, доверенные всей системой.
*   **Неверная оценка хэширования:** Попытка прочитать хэшированный файл как открытый текст приводит к ложным выводам об отсутствии целей.
*   **Отсутствие контекста:** Сам по себе `known_hosts` не дает доступа. Он только указывает направления. Без дополнительных учетных данных (паролей, ключей) или уязвимостей на целевых хостах горизонтальное перемещение невозможно.
*   **Изменение ключей:** Если на целевом хосте был изменен хост-ключ, запись в `known_hosts` станет невалидной, и подключение будет прервано. Это может быть индикатором того, что хост был переустановлен или скомпрометирован ранее.

## Сквозной практический пример: Реконструкция топологии через known_hosts

**Исходные условия:**
*   **Среда:** Внутренняя сеть предприятия. Скомпрометирован рабочий узел Linux (Ubuntu 22.04) с правами пользователя `dev_user`.
*   **Инструменты:** `cat`, `grep`, `ssh2john` (из пакета `john`), `hashcat` (опционально), `nmap`.
*   **Роль:** Пентестер, выполняющий этап горизонтального перемещения.
*   **Сценарий:** Необходимо выявить другие хосты, к которым имеет доступ `dev_user` через SSH, для последующей атаки.

### Шаг 1: Локализация и первичный анализ файла

Пентестер ищет файл `known_hosts` в домашней директории пользователя.

```bash
# Проверка существования файла
ls -la ~/.ssh/known_hosts

# Просмотр содержимого
cat ~/.ssh/known_hosts
```

**Ожидаемый вывод:**
```text
# This is a ssh known_hosts file
# hashes appear in hex, base64, or decimal
* ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
192.168.1.10 ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABgQC...
```
В данном примере видно, что хэширование отключено для IP-адреса, но включено (или используется wildcard) для доменных имен. Запись `*` означает, что доверие распространяется на все хосты в определенном домене или что ключ был добавлен с использованием wildcards.

### Шаг 2: Извлечение и анализ хэшированных записей

Если бы файл содержал только хэши, пентестер попытался бы их расшифровать. Предположим, что в файле есть хэшированные записи, и мы хотим проверить, можно ли их подобрать.

```bash
# Преобразование в формат для John the Ripper
python3 /usr/share/john/ssh2john.py ~/.ssh/known_hosts > known_hosts.hash

# Проверка формата файла
file known_hosts.hash
```

**Ожидаемый вывод:**
```text
known_hosts.hash: ASCII text
```
Если хэширование включено, пентестер генерирует wordlist с возможными именами хостов (например, из подсети `192.168.1.0/24` или из стандартной системы именования компании).

### Шаг 3: Перебор имен хостов (если хэширование включено)

Предположим, что пентестер знает, что в сети используются имена вида `db01`, `db02`, `web01`.

```bash
# Создание wordlist
echo -e "db01\ndb02\nweb01\n192.168.1.10\n192.168.1.11" > hostnames.txt

# Попытка перебора (если известен алгоритм и соль)
# В реальности для known_hosts используется специализированный скрипт, так как ssh2john не всегда корректно обрабатывает HMAC-SHA256 с солью
# Пример использования khashcat или аналогичного инструмента
khashcat -m known_hosts.hash -w hostnames.txt
```

**Ожидаемый вывод:**
```text
db01: <matched_hash>
192.168.1.10: <matched_hash>
```
Это подтверждает, что `dev_user` ранее подключался к `db01` и `192.168.1.10`.

### Шаг 4: Проверка доступности и аутентификации

На основе полученного списка пентестер проверяет, можно ли подключиться к целевым хостам.

```bash
# Проверка подключения к db01
ssh -o BatchMode=yes -o ConnectTimeout=5 dev_user@db01 'echo "Connected"'

# Проверка подключения к 192.168.1.10
ssh -o BatchMode=yes -o ConnectTimeout=5 dev_user@192.168.1.10 'echo "Connected"'
```

**Ожидаемый вывод:**
```text
# Для db01
Permission denied (publickey,password).

# Для 192.168.1.10
Connected
```
Результат показывает, что на `192.168.1.10` аутентификация по ключу работает (вероятно, публичный ключ `dev_user` есть в `authorized_keys`), а на `db01` требуется пароль или ключ отсутствует.

### Шаг 5: Построение графа и планирование следующей атаки

Пентестер фиксирует, что `192.168.1.10` является следующей целью для горизонтального перемещения.

```bash
# Сохранение результатов
echo "192.168.1.10" >> pivoting_targets.txt
```

**Ожидаемый вывод:**
Файл `pivoting_targets.txt` содержит список хостов, к которым можно получить доступ с текущими учетными данными. Это позволяет пентестеру сосредоточиться на эксплуатации уязвимостей на `192.168.1.10` или краже дополнительных учетных данных для доступа к `db01`.

## Аналитический вывод

Файл `known_hosts` является мощным источником разведывательной информации при тестировании на проникновение и расследовании инцидентов. Он позволяет восстановить историю сетевых взаимодействий и выявить скрытые связи между хостами, которые могут не быть видны в сетевых журналах из-за шифрования или ограничений доступа. Использование хэширования имен хостов в современных системах усложняет прямое извлечение данных, но не делает его невозможным, особенно если атакующий имеет доступ к соли или может использовать методы перебора. Для защитников важно регулярно аудировать файлы `known_hosts` на наличие неавторизованных записей и отключать хэширование только в строго контролируемых средах. Для пентестеров анализ `known_hosts` должен быть частью комплексного подхода к разведке, сочетающегося с поиском приватных ключей и анализом истории команд.
