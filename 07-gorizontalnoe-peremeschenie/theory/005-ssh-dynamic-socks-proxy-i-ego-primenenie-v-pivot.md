# SSH Dynamic SOCKS Proxy и его применение в pivot

## Контекст и базовые понятия

Динамическое проброс портов (Dynamic Port Forwarding) в протоколе SSH — это механизм, позволяющий клиенту SSH создавать локальный сокет (обычно TCP), который функционирует как SOCKS-прокси (версии 4 или 5). В отличие от статического проброса портов (Local/Remote Port Forwarding), где маршрут соединения жестко задается администратором на момент запуска туннеля (например, `localhost:8080` -> `remote:80`), динамический туннель делегирует решение о маршрутизации самому приложению-клиенту. При подключении к локальному порту туннеля клиент отправляет запрос SOCKS-серверу (в данном случае — процессу SSH на стороне атакующего), который затем устанавливает новое соединение через зашифрованный канал SSH к удаленному серверу, а тот, в свою очередь, инициирует исходящее соединение к запрашиваемому адресу.

В контексте тестирования на проникновение (Penetration Testing) и Red Teaming этот механизм является фундаментальным инструментом для горизонтального перемещения (Lateral Movement) и обхода сегментации сети. Термин «pivot» (от англ. *pivot* — ось, точка опоры) описывает процесс использования скомпрометированной хост-системы (pivot host) в качестве промежуточного узла для доступа к ресурсам внутренней сети, которые недоступны напрямую из внешней сети или сети атакующего.

Ключевое разграничение необходимо проводить между тремя основными типами проброса портов в SSH, так как их функциональное назначение и архитектурные последствия различны:

| Характеристика | Local Port Forwarding (`-L`) | Remote Port Forwarding (`-R`) | Dynamic Port Forwarding (`-D`) |
| :--- | :--- | :--- | :--- |
| **Направление трафика** | От локального клиента к удаленному серверу, затем к цели. | От удаленного сервера к локальному клиенту, затем к цели. | От локального клиента через удаленный сервер к любому адресу. |
| **Роль SSH-сервера** | Пассивный ретранслятор (forwarder). | Активный инициатор исходящего соединения. | SOCKS-прокси сервер (решает маршрут динамически). |
| **Где открывается порт** | На машине атакующего (клиента). | На машине жертвы (сервера). | На машине атакующего (клиента). |
| **Типичное применение** | Доступ к внутренней базе данных через DMZ-сервер. | Доступ к локальному веб-серверу атакующего из внутренней сети. | Создание SOCKS-прокси для сканирования всей подсети (pivot). |
| **Гибкость маршрутизации** | Низкая (фиксированная пара адресов). | Низкая (фиксированная пара адресов). | Высокая (любой TCP-хост, доступный с сервера). |
| **Риск обнаружения** | Средний (аномальный трафик к конкретному порту). | Высокий (исходящие соединения от жертвы к C2). | Средний/Низкий (трафик выглядит как обычный SSH). |

Динамический туннель часто сравнивают с легковесным VPN, однако между ними есть принципиальная архитектурная разница. VPN (например, OpenVPN или WireGuard) работает на канальном (Layer 2) или сетевом (Layer 3) уровнях модели OSI, перенаправляя весь IP-трафик или его часть через туннель, что требует настройки сетевых интерфейсов и маршрутизации на стороне клиента. SSH Dynamic Forwarding работает на транспортном (Layer 4) уровне. Оно не подменяет сетевой стек ОС, а предоставляет прикладному уровню (Layer 7) интерфейс прокси-сервера. Это означает, что только те приложения, которые умеют работать с протоколом SOCKS (или HTTP-прокси, если используется конвертация), будут использовать туннель. Остальной трафик ОС (например, обновления системы, фоновые службы) продолжит идти напрямую, что является как преимуществом (меньше шума в сети), так и ограничением (невозможность сканирования ICMP или UDP-сканирования через стандартные средства, если они не поддерживают SOCKS).

Понятие «pivot» в данном контексте подразумевает использование привилегий на скомпрометированной машине. Если на жертве запущен SSH-демон, а атакующий имеет учетные данные (или смог выполнить код с помощью SSH-клиента, например, через `plink` на Windows или `ssh` на Linux), он может инициировать туннель. Важно отметить, что сам по себе факт создания туннеля не является атакой; это легитимная функция администрирования. Однако в контексте инцидента безопасности (Incident Response) создание динамического туннеля с внутренней машины на внешний IP или даже на локальный порт с последующим использованием его для сканирования внутренней сети является сильным индикатором компрометации (IoC).

## Внутреннее устройство предмета

Динамическое проброс портов реализуется на уровне протокола SSH (RFC 4251, RFC 4253). Механизм основан на расширении протокола, позволяющем клиенту запрашивать у сервера создание SOCKS-сервера. Ниже описаны ключевые компоненты и этапы работы механизма.

### Архитектура взаимодействия

Процесс создания и использования динамического туннеля состоит из трех фаз: инициализации туннеля, установления SOCKS-сессии и ретрансляции данных.

1.  **Инициализация туннеля:** Клиент SSH отправляет серверу запрос на открытие локального сокета. Сервер подтверждает создание и начинает прослушивать указанный порт.
2.  **SOCKS Handshake:** Когда приложение (например, `nmap` или браузер) подключается к локальному порту, происходит рукопожатие по протоколу SOCKS. Клиент отправляет версию протокола (обычно 5), методы аутентификации (чаще всего «No Authentication Required» для локальных туннелей) и желаемый тип соединения (TCP).
3.  **Динамическая маршрутизация:** После успешного рукопожатия SOCKS-сервер (SSH-клиент) извлекает целевой адрес и порт из запроса. Затем он устанавливает новое SSH-соединение (или использует существующее канальное соединение, в зависимости от реализации) к SSH-серверу, передавая запрос на установку соединения с целевым хостом.
4.  **Ретрансляция:** SSH-сервер, получив запрос, инициирует исходящее TCP-соединение к целевому хосту. После установления соединения сервер начинает двунаправленную передачу данных между локальным клиентом и удаленной целью через зашифрованный канал SSH.

### Структура SOCKS5 запроса в контексте туннеля

При использовании динамического туннеля ключевым элементом является формат запроса SOCKS5. В отличие от статического проброса, где адрес назначения жестко закодирован в команде SSH, здесь он передается динамически.

```text
+----+------+------+----------+----------+----------+
|VER | NMETHODS | METHODS |   ATYPE  |   DST.ADDR    | DST.PORT |
+----+------+------+----------+----------+----------+
| 5  |   1    |   0    |   0x00   |   0x03     |  IP.ADDR | 0x0000   |
+----+------+------+----------+----------+----------+
```

*   `VER`: Версия протокола SOCKS (5).
*   `NMETHODS`: Количество предлагаемых методов аутентификации.
*   `METHODS`: Список методов (обычно `0x00` — без аутентификации).
*   `ATYPE`: Тип адреса назначения. `0x01` — IPv4, `0x03` — доменное имя, `0x04` — IPv6.
*   `DST.ADDR`: Целевой IP-адрес или домен.
*   `DST.PORT`: Целевой порт.

Именно поле `ATYPE` и `DST.ADDR` делает туннель «динамическим». SSH-сервер не знает заранее, куда будет направлено соединение, и выполняет роль ретранслятора на основе этих данных.

### Сравнительный анализ типов проброса портов

Для понимания места динамического туннеля в экосистеме сетевых технологий необходимо сопоставить его с альтернативами.

| Критерий | Local Forward (`-L`) | Remote Forward (`-R`) | Dynamic Forward (`-D`) |
| :--- | :--- | :--- | :--- |
| **Сложность настройки** | Низкая | Средняя | Низкая |
| **Гибкость** | Низкая (1 порт -> 1 цель) | Низкая (1 порт -> 1 цель) | Высокая (любой порт/хост) |
| **Нагрузка на CPU** | Низкая | Низкая | Средняя (обработка SOCKS-запросов) |
| **Видимость в логах** | Четкие связи `src:port -> dst:port` | Четкие связи `src:port -> dst:port` | Запросы к произвольным портам |
| **Поддержка UDP** | Нет (только TCP) | Нет (только TCP) | Нет (только TCP) |
| **Интеграция с инструментами** | Требует настройки каждого инструмента | Требует настройки каждого инструмента | Требует SOCKS-клиента (ProxyChains, настройки браузера) |

### Ограничения и особенности реализации

1.  **Только TCP:** Протокол SOCKS5, используемый в SSH, поддерживает только TCP-соединения. Это означает, что такие протоколы, как DNS (по умолчанию UDP), ICMP (ping) или NetBIOS, не могут быть напрямую туннелированы через стандартный `ssh -D`. Для обхода этого ограничения используются специализированные инструменты, такие как `dnscat2` (DNS over SSH) или `chisel` (поддержка UDP через HTTP/2).
2.  **Аутентификация:** По умолчанию динамический туннель не требует дополнительной аутентификации на уровне SOCKS, так как аутентификация уже пройдена на уровне SSH. Однако, если SSH-сервер настроен на использование `GatewayPorts` или других расширений, могут применяться дополнительные проверки.
3.  **Безопасность:** Трафик внутри туннеля зашифрован алгоритмами, согласованными в ходе SSH-рукопожатия (например, AES-256-GCM). Однако сам факт туннелирования может быть обнаружен системами мониторинга трафика (NDR) по аномалиям в длительности сессий или объему переданных данных.

## Применение и работа с предметом

На практике применение SSH Dynamic SOCKS Proxy в тестировании на проникновение сводится к трем основным сценариям: сканирование внутренней сети, доступ к веб-приложениям и обход ограничений доступа.

### Сценарий 1: Сканирование внутренней сети с помощью ProxyChains

Наиболее распространенный метод использования динамического туннеля — интеграция с утилитой `proxychains`. ProxyChains перехватывает системные вызовы сетевых библиотек (например, `connect()`) и перенаправляет их через указанный SOCKS-прокси. Это позволяет использовать любые инструменты, поддерживающие SOCKS, без необходимости их перекомпиляции или настройки.

**Типовая процедура:**
1.  Создание туннеля на локальном порту (например, 1080).
2.  Редактирование файла `/etc/proxychains.conf` для указания локального прокси.
3.  Запуск целевого инструмента с префиксом `proxychains`.

```bash
# Шаг 1: Создание динамического туннеля
# -D 1080: открывает SOCKS5 прокси на порту 1080
# -N: не выполнять удаленную команду (только туннель)
# -f: перейти в фоновый режим
# -o StrictHostKeyChecking=no: отключить проверку хоста (для автоматизации)
ssh -D 1080 -N -f -o StrictHostKeyChecking=no user@compromised_host

# Шаг 2: Проверка работы туннеля
netstat -an | grep 1080
# Ожидаемый вывод:
# tcp        0      0 127.0.0.1:1080          0.0.0.0:*               LISTEN
```

### Сценарий 2: Доступ к веб-приложениям и базам данных

Для доступа к внутренним веб-интерфейсам (например, админ-панелям, CRM, базам данных) можно настроить браузер или специализированные инструменты (Burp Suite, sqlmap) на использование SOCKS-прокси.

**Настройка Burp Suite:**
1.  Перейти в `Proxy` -> `Proxy Settings`.
2.  В разделе `SOCKS Proxy` установить `Enable SOCKS proxy`.
3.  Указать `SOCKS server` как `127.0.0.1` и порт `1080`.
4.  Выбрать `SOCKS version 5`.

**Настройка sqlmap:**
```bash
sqlmap -u "http://internal-app/admin" --proxy="socks5://127.0.0.1:1080"
```

### Сценарий 3: Обход ограничений доступа (Bypass)

Если внутренняя сеть имеет правила файрвола, запрещающие прямой доступ извне, но разрешающий доступ с pivot-хоста, динамический туннель позволяет обойти эти ограничения. Важно отметить, что если pivot-хост находится в DMZ, а внутренняя сеть защищена строгими правилами, то доступ будет возможен только к тем ресурсам, к которым имеет доступ сам pivot-хост.

**Типичные ошибки и подводные камни:**
1.  **Отсутствие поддержки SOCKS в инструменте:** Многие старые или специализированные инструменты не поддерживают SOCKS. В таких случаях требуется использование альтернатив, таких как `chisel` (который может работать как HTTP-прокси) или `ligolo-ng` (который создает виртуальный сетевой интерфейс).
2.  **DNS-leak:** При использовании браузеров через SOCKS-прокси важно убедиться, что DNS-запросы также направляются через прокси. В некоторых конфигурациях DNS-запросы могут уходить напрямую, раскрывая локальную сеть.
3.  **Блокировка портов:** Если на pivot-хосте заблокирован исходящий трафик на порт 22 (SSH), создать туннель не удастся. В таких случаях используются обходные пути, такие как `chisel` на порту 443 (HTTPS) или `ngrok`.

## Сквозной практический пример: Сканирование внутренней сети через SSH Dynamic Proxy

**Исходные условия:**
*   **Атакующий (Attacker):** Kali Linux (IP: `10.10.14.5`), инструмент `nmap`, `proxychains4`.
*   **Pivot Host (Жертва):** Ubuntu Server 22.04 (IP: `192.168.1.100`), скомпрометирован через RCE, имеет SSH-демон.
*   **Target Host (Цель):** Windows Server 2019 (IP: `192.168.1.50`), находится в той же подсети, что и Pivot Host, но недоступен из внешней сети.
*   **Цель:** Выполнить сканирование портов на Target Host, используя Pivot Host как прокси.

**Шаг 1: Создание динамического туннеля на Pivot Host**

Атакующий подключается к скомпрометированному серверу и создает SOCKS-прокси на локальном порту 9050.

```bash
# На машине атакующего (Kali)
ssh -D 9050 -N -f user@192.168.1.100
```

**Шаг 2: Проверка активности туннеля**

Убедимся, что порт прослушивается.

```bash
netstat -tuln | grep 9050
```

*Ожидаемый вывод:*
```text
tcp        0      0 127.0.0.1:9050          0.0.0.0:*               LISTEN
```

**Шаг 3: Настройка ProxyChains**

Редактируем конфигурационный файл `/etc/proxychains4.conf`, добавляя в конец:

```text
[ProxyList]
socks5 127.0.0.1 9050
```

**Шаг 4: Выполнение сканирования через туннель**

Запускаем `nmap` через `proxychains`, направляя трафик на целевой IP.

```bash
proxychains4 nmap -sT -p 80,443,3389,445 192.168.1.50
```

*Ожидаемый вывод (фрагмент):*
```text
[proxychains] DLL init: proxychains-ng 4.16
[proxychains] Strict chain  ...  127.0.0.1:9050  ...  192.168.1.50:80  ...  OPEN
[proxychains] Strict chain  ...  127.0.0.1:9050  ...  192.168.1.50:443  ...  OPEN
[proxychains] Strict chain  ...  127.0.0.1:9050  ...  192.168.1.50:3389  ...  OPEN
[proxychains] Strict chain  ...  127.0.0.1:9050  ...  192.168.1.50:445  ...  OPEN
```

**Шаг 5: Анализ результатов**

Результаты сканирования показывают открытые порты на целевой машине. Важно отметить, что в логах Pivot Host будут видны только SSH-соединения, а в логах Target Host — соединения, исходящие с IP Pivot Host (`192.168.1.100`), что маскирует источник атаки.

**Ожидаемый вывод:**
Пример демонстрирует, как динамический туннель позволяет обойти сетевые сегменты, предоставляя атакующему доступ к внутренним ресурсам через скомпрометированный хост. Это классический пример горизонтального перемещения.

## Аналитический вывод

SSH Dynamic SOCKS Proxy представляет собой мощный инструмент для горизонтального перемещения в сетях, позволяющий обходить сегментацию и маскировать источник атак. Его ключевое преимущество заключается в гибкости маршрутизации и использовании легитимного протокола SSH, что затрудняет обнаружение средствами мониторинга трафика. Однако, в отличие от VPN-туннелей, он работает только с TCP-трафиком и требует поддержки SOCKS на стороне клиента. Для эффективного использования в тестировании на проникновение рекомендуется комбинировать его с инструментами вроде `proxychains` или `chisel`, а также учитывать ограничения, связанные с аутентификацией и поддержкой UDP. В контексте защиты, мониторинг создания динамических туннелей и аномального поведения SSH-клиентов является критически важным для выявления инцидентов компрометации.
