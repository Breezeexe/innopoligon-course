# Политики и шаблоны сканирования в Nessus: архитектура, классификация и применение

## Контекст и базовые понятия

Vulnerability Assessment (VA) — это систематический процесс выявления, классификации и оценки уязвимостей в информационных системах. В отличие от пентеста, который имитирует атаку для подтверждения эксплуатационной возможности, VA фокусируется на полноте обнаружения и точности индикаторов. Nessus, разработанный компанией Tenable, является индустриальным стандартом в этой области благодаря архитектуре на основе плагинов (Nessus Plugins) и гибкой системе политик.

Ключевое понятие в работе с Nessus — **Политика сканирования (Scan Policy)**. Это набор конфигурационных параметров, определяющих *как* сканер взаимодействует с целевой инфраструктурой. Политика не содержит логики обнаружения сама по себе; она управляет поведением движка сканера: какие порты сканировать, какие плагины включать/исключать, как часто повторять проверки, как обрабатывать таймауты и какие учетные данные использовать.

**Шаблон сканирования (Scan Template)** — это предопределенная, неизменяемая (в части базовой структуры) конфигурация, предоставляемая Tenable. Шаблон служит отправной точкой для создания пользовательской политики. При выборе шаблона пользователь не может изменить его внутренние параметры напрямую; он может только скопировать его в пользовательскую политику и затем модифицировать. Это обеспечивает стандартизацию: все сканирования в организации базируются на проверенных Tenable профилях.

Разграничение понятий критически важно для понимания архитектуры инструмента:

| Сущность | Уровень абстракции | Назначение | Изменяемость | Пример использования |
| :--- | :--- | :--- | :--- | :--- |
| **Scan Template** | Конфигурационный профиль | Базовая настройка поведения сканера (глубина, скорость, тип проверки) | Только для копирования в Policy. Внутренние поля шаблона фиксированы вендором. | Выбор "Basic Network Scan" для быстрого аудита. |
| **Scan Policy** | Пользовательская конфигурация | Индивидуализированный набор параметров на основе шаблона. Содержит ссылки на плагины, порты, учетные данные. | Полностью редактируема пользователем. | Настройка "Internal Prod Policy" с учетными данными администратора. |
| **Scan** | Инстанс выполнения | Запуск конкретной политики против конкретного набора целей (Targets) в определенное время. | Неизменяем после запуска (архивируется). | Еженедельное сканирование подсети 10.0.0.0/24. |
| **Plugin** | Логика обнаружения | Скрипт (NASL, Python, C), содержащий код проверки уязвимости или настройки. | Обновляется через Tenable Network Update Service (NU). | Плагин `apache_2_4_49.nasl` для проверки Heartbleed. |

Путаница между "шаблоном" и "политикой" часто приводит к ошибкам: администраторы пытаются изменить параметры встроенного шаблона, что невозможно, или создают политику с нуля, игнорируя рекомендации Tenable по базовым настройкам сетевого стека.

Архитектурно Nessus разделяет задачи на три категории, что отражается в классификации шаблонов:
1.  **Discovery (Обнаружение):** Определение живых хостов, открытых портов, ОС и сервисов. Не ищет уязвимости, но формирует инвентарь.
2.  **Vulnerability (Уязвимости):** Активное сканирование открытых портов и сервисов с использованием базы плагинов для поиска известных дефектов.
3.  **Compliance (Соответствие):** Проверка конфигураций ОС и приложений на соответствие стандартам (CIS, DISA STIG, PCI DSS) через аутентифицированные запросы.

## Внутреннее устройство предмета

Архитектура политик и шаблонов Nessus базируется на модульной структуре, где каждый элемент отвечает за определенный аспект взаимодействия с целью. Понимание внутреннего устройства необходимо для настройки баланса между полнотой обнаружения и производительностью сети.

### Структура шаблонов сканирования (Scanner Templates)

В Tenable Nessus (и Tenable Vulnerability Management) шаблоны разделены на три основные категории. Каждая категория имеет специфические технические ограничения и области применения.

**1. Discovery Templates (Шаблоны обнаружения)**
Эти шаблоны не используют базу плагинов уязвимостей. Они работают на уровне сетевого стека и протоколов идентификации.
*   **Host Discovery:** Использует комбинацию ARP (для локальных сетей), ICMP Echo Request, TCP SYN к портам 135, 139, 445, 3389 и UDP сканирование. Позволяет определить живые хосты без отправки вредоносного трафика.
*   **Ping-Only Discovery:** Минималистичный сканер, использующий только ICMP. Эффективен для обхода базовых файрволов, блокирующих TCP-соединения, но не определяет ОС или порты.
*   **Attack Surface Discovery (Tenable Nessus Expert):** Использует API Tenable Attack Surface Management для сбора данных о внешних доменах, поддоменах и DNS-записях. Не сканирует сеть напрямую, а агрегирует внешние индикаторы.

**2. Vulnerability Scanning Templates (Шаблоны сканирования уязвимостей)**
Самая обширная категория. Содержит настройки для инициализации плагин-движка.
*   **Basic Network Scan:** Базовый профиль. Включает все стандартные плагины, сканирует все TCP-порты, использует эвристику для определения ОС. Оптимизирован для баланса между скоростью и полнотой.
*   **Advanced Network Scan:** Расширенный профиль. Позволяет тонко настраивать:
    *   *Port Range:* Выбор конкретных диапазонов (например, только 80, 443, 8080).
    *   *Plugin Families:* Включение/исключение групп плагинов (например, отключить "Brute Force" для предотвращения блокировок).
    *   *Performance:* Настройка параллельных соединений, таймаутов, скорости отправки пакетов.
    *   *Credentialed Checks:* Настройка типов аутентификации (SSH, SMB, SNMP, WinRM).
*   **Tactical Scans:** Легковесные шаблоны, активируемые только при появлении критических уязвимостей (например, Log4Shell, PrintNightmare). Содержат только плагины, проверяющие конкретную CVE или группу CVE. Позволяют быстро проверить масштаб инцидента без полного сканирования.

**3. Compliance Scanning Templates (Шаблоны соответствия)**
Требуют аутентификации. Проверяют состояние системы против базы знаний (SCAP/CIS).
*   **CIS Benchmarks:** Проверка настроек ОС и приложений по стандартам Center for Internet Security.
*   **DISA STIG:** Security Technical Implementation Guide от DISA (для военных и государственных структур США).
*   **PCI DSS:** Проверка соответствия стандарту безопасности индустрии платежных карт.
*   **HIPAA:** Проверка соответствия закону о переносимости и подотчетности медицинского страхования.

### Внутренняя структура Политики (Policy Structure)

Пользовательская политика Nessus представляет собой иерархическую конфигурацию. Ниже приведена иллюстративная схема структуры данных политики (на основе JSON-подобной логики внутренней базы данных Nessus):

```json
{
  "policy_id": "uuid-12345",
  "name": "Custom Internal Audit",
  "template_source": "Advanced Network Scan",
  "settings": {
    "network": {
      "port_range": "1-65535",
      "max_checks": 10,
      "max_retransmissions": 2,
      "timeout": 30,
      "host_discovery": true,
      "scan_hosts": ["192.168.1.0/24"]
    },
    "plugins": {
      "enabled_families": [
        "general",
        "service_detection",
        "os_detection",
        "vuln",
        "exploit"
      ],
      "excluded_families": [
        "brute_force",
        "denial_of_service"
      ],
      "custom_plugins": [
        "path/to/custom_plugin.nasl"
      ]
    },
    "credentials": {
      "ssh": {
        "enabled": true,
        "username": "admin",
        "password": "encrypted_blob",
        "key_file": "id_rsa"
      },
      "smb": {
        "enabled": true,
        "domain": "CORP.LOCAL",
        "username": "svc_scan",
        "password": "encrypted_blob"
      }
    },
    "reporting": {
      "format": "html",
      "include_cvss": true,
      "include_epss": true,
      "include_vpr": true
    }
  }
}
```

Ключевые компоненты внутренней структуры:
1.  **Network Settings:** Определяют сетевое поведение. `max_checks` — максимальное количество одновременных проверок на один хост. Высокое значение ускоряет сканирование, но может вызвать перегрузку сети или срабатывание IDS/IPS.
2.  **Plugin Families:** Группы плагинов. Исключение семейств `brute_force` критично для production-сред, так как такие плагины могут заблокировать учетные записи.
3.  **Credentials:** Хранят зашифрованные учетные данные. Nessus поддерживает множество протоколов: SSH (Linux), SMB (Windows), SNMP (Network Devices), WinRM (Remote Windows), VMware (Virtualization).
4.  **Reporting:** Настройки вывода. Включают выбор метрик риска: CVSS v3.1/v4.0, EPSS (Exploit Prediction Scoring System), VPR (Vulnerability Priority Rating — проприетарная метрика Tenable).

### Взаимодействие шаблонов и политик

Процесс создания сканирования выглядит следующим образом:
1.  Пользователь выбирает шаблон (например, "Advanced Network Scan").
2.  Nessus создает копию конфигурации шаблона в пользовательском хранилище.
3.  Пользователь модифицирует копию: добавляет цели, настраивает учетные данные, исключает плагины.
4.  При запуске сканирования движок Nessus читает политику, загружает необходимые плагины из локального кэша (или обновляет их через NU), инициализирует сетевые сокеты согласно настройкам `network` и начинает проверку.

Важно: Шаблоны обновляются вендором автоматически. При обновлении Nessus новые шаблоны могут появиться, но существующие пользовательские политики не меняются автоматически, чтобы избежать непредвиденных изменений в процессах аудита.

## Применение и работа с предметом

Практическая работа с политиками и шаблонами Nessus требует понимания не только интерфейса, но и сетевых и системных особенностей целевой среды. Неправильная настройка политики может привести к ложным срабатываниям, пропуску уязвимостей или отказу в обслуживании (DoS) целевых систем.

### Типовые операции с политиками

**1. Создание пользовательской политики на основе шаблона**
Это стандартная процедура. Пользователь никогда не должен использовать встроенные шаблоны напрямую для долгосрочного аудита, так как они не сохраняют пользовательские настройки (цели, расписание, отчеты).

*   *Шаг 1:* Перейти в раздел "Scans" -> "New Scan".
*   *Шаг 2:* Выбрать категорию (например, "Advanced Network Scan").
*   *Шаг 3:* Ввести имя политики и описание.
*   *Шаг 4:* Настроить вкладку "Settings".

**2. Настройка учетных данных (Credentials)**
Аутентифицированные сканирования (Credentialed Scans) дают значительно более точные результаты, так как позволяют проверять состояние реестра, установленных обновлений и конфигурационных файлов, что невозможно при сетевом сканировании.

*   *SSH:* Для Linux/Unix. Требуется пользователь с правами `sudo` или доступ к файлам конфигурации.
*   *SMB:* Для Windows. Требуется пользователь с правами локального администратора или доступ к реестру.
*   *SNMP:* Для сетевого оборудования. Требуется правильный Community String (v2c) или User/Password (v3).

**3. Управление плагинами (Plugin Management)**
Пользователь может исключать целые семейства плагинов или отдельные плагины. Это полезно для:
*   Обхода блокировок IDS/IPS.
*   Снижения нагрузки на сеть.
*   Избежания срабатывания бизнес-логики (например, блокировки учетных записей при brute-force проверках паролей).

### Типичные ошибки и подводные камни

**Ошибка 1: Игнорирование настроек производительности**
По умолчанию Nessus может использовать агрессивные настройки. В production-средах это приводит к перегрузке серверов.
*   *Решение:* В настройках политики уменьшить `max_checks` (например, до 5-10), увеличить `timeout`, отключить `host_discovery` если хосты уже известны.

**Ошибка 2: Неправильная настройка аутентификации**
Использование учетных данных с недостаточными правами приводит к ложным отрицаниям (False Negatives). Nessus не сможет проверить состояние системы и сообщит, что проверка не выполнена, а не что уязвимость отсутствует.
*   *Решение:* Тестировать учетные данные в разделе "Credentials" перед запуском сканирования.

**Ошибка 3: Отсутствие исключения семейств плагинов**
Семейство `brute_force` может заблокировать учетные записи пользователей. Семейство `denial_of_service` может вызвать сбой служб.
*   *Решение:* Всегда исключать `brute_force` и `denial_of_service` в production-средах, если это не специально запланированное тестирование на устойчивость.

### Пример конфигурации политики для Production-среды

Ниже приведен пример фрагмента конфигурации политики (в формате, близком к внутреннему представлению Nessus) для безопасного сканирования production-сети.

```yaml
# Пример фрагмента политики Nessus для Production
policy:
  name: "Prod_Safe_Audit"
  template: "Advanced Network Scan"
  
  network:
    # Ограничиваем параллельные проверки для снижения нагрузки
    max_checks: 5
    # Увеличиваем таймаут для медленных систем
    timeout: 60
    # Исключаем агрессивные методы обнаружения хостов
    host_discovery: false
    # Сканируем только важные порты
    port_range: "22,80,443,3389,8080,8443"
    
  plugins:
    # Включаем только необходимые семейства
    enabled_families:
      - "os_detection"
      - "service_detection"
      - "vuln"
      - "config"
    # Исключаем опасные семейства
    excluded_families:
      - "brute_force"
      - "denial_of_service"
      - "exploit"
      
  credentials:
    ssh:
      enabled: true
      username: "scanner_user"
      # Пароль хранится в зашифрованном виде в базе данных Nessus
      password: "AES256_ENCRYPTED_BLOB"
      sudo: true
    smb:
      enabled: true
      domain: "CORP.LOCAL"
      username: "svc_nessus"
      password: "AES256_ENCRYPTED_BLOB"
      
  reporting:
    # Включаем EPSS для приоритизации
    include_epss: true
    # Включаем VPR для оценки риска эксплуатации
    include_vpr: true
```

## Сквозной практический пример: Аудит уязвимостей в гибридной среде

**Исходные условия:**
*   **Среда:** Корпоративная сеть с Windows Server 2019 (DC) и Ubuntu 22.04 (Web Server).
*   **Инструмент:** Tenable Nessus Professional (веб-интерфейс).
*   **Роль:** Системный администратор безопасности.
*   **Сценарий:** Проведение планового аудита уязвимостей с аутентификацией для обоих типов ОС.

### Шаг 1: Создание политики на основе шаблона

Пользователь создает новую политику, выбирая шаблон "Advanced Network Scan". Это дает максимальную гибкость.

```bash
# В веб-интерфейсе Nessus:
# 1. Scans -> New Scan -> Advanced Network Scan
# 2. Name: "Hybrid_Audit_Q4"
# 3. Description: "Quarterly audit for Windows and Linux assets"
```

### Шаг 2: Настройка целей и учетных данных

Добавляем цели и настраиваем учетные данные для каждой ОС.

```json
// Фрагмент настройки целей и учетных данных в интерфейсе
{
  "targets": [
    "192.168.1.10",  // Windows DC
    "192.168.1.20"   // Linux Web Server
  ],
  "credentials": {
    "windows": {
      "type": "SMB",
      "username": "admin@corp.local",
      "password": "SecureP@ss123",
      "domain": "CORP.LOCAL"
    },
    "linux": {
      "type": "SSH",
      "username": "sysadmin",
      "password": "LinuxP@ss456",
      "sudo_password": "SudoP@ss789"
    }
  }
}
```

### Шаг 3: Настройка плагина и производительности

Исключаем агрессивные плагины и настраиваем порты.

```yaml
# Настройка в разделе "Settings" -> "Plugins"
excluded_families:
  - "brute_force"
  - "denial_of_service"
  
# Настройка в разделе "Settings" -> "Network"
port_range: "1-1024, 3389, 80, 443, 8080"
max_checks: 10
```

### Шаг 4: Запуск сканирования и мониторинг

Запускаем сканирование и наблюдаем за прогрессом.

```bash
# В веб-интерфейсе:
# 1. Нажать "Launch"
# 2. Перейти в раздел "Scans" -> "Hybrid_Audit_Q4"
# 3. Смотреть статус: "Running" -> "Finished"
```

### Шаг 5: Анализ результатов

После завершения сканирования открываем отчет.

```json
// Пример фрагмента отчета Nessus (JSON-структура алерта)
{
  "report_id": "scan_12345",
  "vulnerabilities": [
    {
      "plugin_id": "101234",
      "name": "Microsoft Security Update for Windows Server 2019",
      "severity": "Critical",
      "cvss_v3": 9.8,
      "epss": 0.45,
      "description": "A critical vulnerability exists in the SMB protocol...",
      "solution": "Apply KB5001234",
      "port": 445,
      "host": "192.168.1.10"
    },
    {
      "plugin_id": "202345",
      "name": "Ubuntu Security Notice USN-1234-1",
      "severity": "High",
      "cvss_v3": 7.5,
      "epss": 0.12,
      "description": "A vulnerability exists in the OpenSSL library...",
      "solution": "Run 'sudo apt update && sudo apt upgrade'",
      "port": 22,
      "host": "192.168.1.20"
    }
  ]
}
```

**Ожидаемый вывод:**
Пример демонстрирует полный цикл: от выбора шаблона до анализа результатов. Использование аутентифицированных данных позволило получить точные данные об отсутствующих обновлениях (KB5001234) и конфигурациях OpenSSL. Исключение агрессивных плагинов обеспечило безопасность процесса.

## Аналитический вывод

Политики и шаблоны сканирования в Nessus представляют собой не просто набор настроек, а архитектурный механизм балансировки между полнотой обнаружения и безопасностью целевой среды. Шаблоны обеспечивают стандартизацию и соответствие лучшим практикам вендора, в то время как политики позволяют адаптировать сканирование под специфические требования инфраструктуры. Ключевым фактором эффективности является правильная настройка учетных данных и управление семействами плагинов. Аутентифицированные сканирования критически важны для обнаружения конфигурационных уязвимостей и отсутствующих обновлений, которые невозможно выявить сетевым сканированием. Игнорирование настроек производительности и безопасности (таких как исключение brute-force плагинов) может привести к негативным последствиям для бизнес-процессов. Таким образом, мастерство работы с Nessus заключается не в запуске сканирования, а в тонкой настройке политик под конкретную среду, обеспечивая точность данных при минимизации рисков для инфраструктуры.
