# Установка и первичная настройка Greenbone Vulnerability Manager (GVM)

## Контекст и базовые понятия: Эволюция, архитектура и компоненты экосистемы

Greenbone Vulnerability Manager (GVM) — это комплексная платформа управления уязвимостями с открытым исходным кодом, предназначенная для обнаружения, классификации и управления рисками в сетевой инфраструктуре. Исторически проект берет начало в 2002 году как OpenVAS (Open Vulnerability Assessment System), который был форком проприетарного сканера Nessus после того, как компания Tenable изменила лицензию на закрытую. В 2019 году проект был официально переименован в Greenbone Vulnerability Manager для отражения его перехода от простого сканера к полноценной платформе управления жизненным циклом уязвимостей. GVM является отраслевым стандартом для open-source решений в области vulnerability management, конкурируя с коммерческими продуктами, такими как Tenable Nessus, Qualys и Rapid7 InsightVM.

Ключевое различие между терминами «OpenVAS» и «GVM» заключается в масштабе. OpenVAS традиционно ассоциировался с самим движком сканирования (сканером), в то время как GVM описывает всю экосистему: сканер, менеджер уязвимостей (базу данных), веб-интерфейс и вспомогательные сервисы. В современной терминологии «OpenVAS» часто используется как синоним компонента `ospd-openvas` (OpenVAS Scanner Daemon), но в контексте установки и настройки речь всегда идет о полном стеке GVM.

Архитектура GVM построена на микросервисном подходе, что обеспечивает модульность и масштабируемость. Система не является монолитным приложением; она состоит из нескольких независимых процессов, взаимодействующих через сокеты (Unix domain sockets) и сетевые протоколы. Понимание этой архитектуры критически важно для успешной установки и отладки, так как ошибки часто возникают на стыке компонентов, а не внутри них.

Ниже представлена сравнительная таблица ключевых компонентов GVM, их функций и уровней взаимодействия.

| Компонент | Основная функция | Уровень взаимодействия | Зависимости и технологии |
| :--- | :--- | :--- | :--- |
| **gvmd** (Greenbone Vulnerability Manager Daemon) | Центральный менеджер. Хранит конфигурации, цели, задачи, результаты сканирования и отчеты. Обрабатывает запросы от веб-интерфейса и API. | Прикладной уровень (Application Layer) | PostgreSQL (хранилище данных), REST API, XML-RPC. |
| **ospd-openvas** (OpenVAS Scanner Daemon) | Движок сканирования. Выполняет непосредственную проверку хостов на наличие уязвимостей, используя NVT (Network Vulnerability Tests). | Прикладной уровень (Application Layer) | Сокет `/run/ospd/ospd.sock`, NASL (скрипты), C-библиотеки. |
| **gsad** (Greenbone Security Assistant Daemon) | Веб-сервер и бэкенд для веб-интерфейса. Отвечает за рендеринг UI, аутентификацию пользователей и проксирование запросов к `gvmd`. | Прикладной уровень (Application Layer) | HTTPS (порт 9392), GnuTLS, HTML/JS фронтенд. |
| **PostgreSQL** | Система управления реляционными базами данных. Хранит метаданные GVM, учетные записи, результаты сканирований и настройки. | Уровень данных (Data Layer) | Версия 14+ (зависит от дистрибутива), collation UTF-8. |
| **Redis** | In-memory структура данных. Используется для кэширования, очередей задач и межпроцессного взаимодействия между компонентами. | Уровень данных (Data Layer) | Порт 6379 (локальный), аутентификация по токену. |
| **Notus Scanner** | Сканер уязвимостей на стороне хоста (Host-based). Проверяет установленное ПО на локальной машине, где запущен агент, а не всю сеть. | Агентовый уровень (Agent-based) | Локальный доступ к файловой системе, JSON-формат отчетов. |
| **Feed (NVT/SCAP/CERT)** | Потоки данных с уязвимостями. Содержат скрипты NASL для проверки, данные SCAP для соответствия стандартам и сертификаты. | Внешний источник | HTTPS, синхронизация через `greenbone-feed-sync`. |

Разграничение понятий также важно в контексте ролей. `gvmd` не выполняет сканирование сам; он лишь оркестрирует процесс, передавая задачи `ospd-openvas`. `ospd-openvas` не хранит результаты; он возвращает сырые данные в `gvmd`. `gsad` не имеет доступа к базе данных напрямую; он делегирует все операции к `gvmd`. Эта строгая сегрегация ответственности означает, что при установке необходимо настраивать права доступа и сетевые правила для каждого компонента отдельно.

Особое внимание следует уделять концепции «Feed» (поток данных). GVM бесполезен без актуальных данных об уязвимостях. NVT (Network Vulnerability Tests) — это скрипты на языке NASL (Nessus Attack Scripting Language), которые реализуют логику проверки. Без регулярной синхронизации с Greenbone Community Feed или Enterprise Feed сканер будет выдавать ложноотрицательные результаты, так как не будет знать о новых CVE. Установка GVM без настройки автоматического обновления фидов является критической ошибкой конфигурации.

## Внутреннее устройство: Архитектура стека, потоки данных и зависимости

Архитектура GVM представляет собой распределенную систему, где каждый компонент может быть развернут на отдельном хосте, хотя в типовых установках (особенно в Kali Linux или на выделенном сервере) все сервисы размещаются на одной машине. Понимание внутренних зависимостей и потоков данных необходимо для диагностики проблем, таких как «висение» сканирования, ошибки аутентификации или несовместимость вер баз данных.

Центральным элементом является `gvmd`. Он работает как демон systemd, запускается от имени специального пользователя `_gvm` (с минимальными привилегиями) и взаимодействует с PostgreSQL. База данных `gvmd` содержит сложную схему: таблицы для пользователей, ролей, целей (targets), конфигураций (configurations), задач (tasks) и результатов (results). `gvmd` использует ORM (Object-Relational Mapping) для взаимодействия с PostgreSQL, что требует строгого соответствия версий драйверов и самой СУБД.

Сканер `ospd-openvas` является реализацией протокола OSPD (Open Scanner Protocol). OSPD — это простой протокол на основе Unix domain sockets, который позволяет различным сканерам (не только OpenVAS, но и, например, GVM-21/22/23 совместимым сканерам) общаться с `gvmd`. `ospd-openvas` загружает скрипты NASL в память, компилирует их и выполняет. Он не имеет собственного сетевого стека для внешних соединений; все сетевые запросы (HTTP, SMB, SSH) он выполняет от имени процесса `ospd-openvas`, что требует настройки файервола на уровне ОС, а не внутри самого сканера.

Поток данных при запуске сканирования выглядит следующим образом:
1.  Пользователь через `gsad` (веб-интерфейс) создает задачу сканирования.
2.  `gsad` отправляет запрос `create_task` в `gvmd` через API.
3.  `gvmd` сохраняет задачу в PostgreSQL и ставит ее в очередь Redis.
4.  `ospd-openvas`, подписанный на очередь Redis, забирает задачу.
5.  `ospd-openvas` инициализирует сканирование, обращаясь к целевым хостам.
6.  Результаты сканирования возвращаются в `gvmd` через тот же сокет OSPD.
7.  `gvmd` сохраняет результаты в PostgreSQL и обновляет статус в Redis.
8.  `gsad` опрашивает `gvmd` о статусе и отображает данные пользователю.

Нарушение любого из этих звеньев приводит к сбою. Например, если PostgreSQL не отвечает, `gvmd` не сможет сохранить задачу. Если Redis недоступен, `ospd-openvas` не узнает о новой задаче. Если сокет `/run/ospd/ospd.sock` заблокирован или имеет неверные права, `gvmd` не сможет передать управление сканеру.

Важным аспектом внутренней структуры является управление версиями. GVM прошел через несколько крупных версионных веток (GVM-21, GVM-22, GVM-23). Каждая новая версия может требовать обновления схемы базы данных. `gvmd` автоматически применяет миграции при запуске, но если база данных была создана старой версией, а компоненты обновлены, могут возникнуть конфликты. Особенно это касается PostgreSQL: обновление версии PostgreSQL (например, с 16 на 17) требует ручного обновления collation (сортировки) в базе данных, иначе `gvmd` откажется запускаться с ошибкой несовместимости.

Ниже представлена ASCII-диаграмма взаимодействия компонентов в типовой установке.

```text
[Пользователь] ──HTTPS──▶ [gsad :9392] ──REST API──▶ [gvmd]
                              │                         │
                              │                         ├──▶ [PostgreSQL :5432]
                              │                         │    (Хранение данных)
                              │                         │
                              │                         └──▶ [Redis :6379]
                              │                              (Очереди задач)
                              │
                              │                         [gvmd] ──OSPD Socket──▶ [ospd-openvas]
                              │                                              │
                              │                                              ├──▶ [NASL Scripts]
                              │                                              │    (Логика проверки)
                              │                                              │
                              │                                              └──▶ [Сеть]
                                                       (Сканирование целей)
```

Компонент `notusd` (Notus Daemon) добавляет еще один слой. Он работает как локальный агент, сканируя установленное ПО на хосте, где установлен GVM. `notusd` отправляет данные о версиях пакетов в `gvmd`, который затем сопоставляет их с базой уязвимостей. Это позволяет выявлять уязвимости в локальном ПО, даже если хост не доступен извне сети.

Безопасность самого стека GVM также является частью его внутренней структуры. `gvmd` использует токены аутентификации и сертификаты TLS. `gsad` генерирует самоподписанный сертификат при первой настройке, который должен быть принят пользователем. `ospd-openvas` не имеет встроенной аутентификации для входящих соединений, полагаясь на изоляцию Unix domain sockets. Это означает, что только процессы с правами на чтение/запись этого сокета могут управлять сканером. Обычно это только `gvmd` и пользователь `_gvm`.

## Применение и работа с предметом: Установка, инициализация и первичная конфигурация

Процесс установки GVM на Debian-подобных системах (включая Kali Linux, Ubuntu, Debian) стандартизирован и использует пакетный менеджер `apt`. Установка из исходных кодов возможна, но не рекомендуется для большинства сценариев, так как требует ручной настройки зависимостей, компиляции NASL-компилятора и управления версиями библиотек.

Первым шагом всегда является обновление системы. Это критически важно, так как GVM зависит от актуальных версий PostgreSQL, Redis и библиотек OpenSSL. Устаревшие библиотеки могут привести к ошибкам компиляции или运行时 (runtime) ошибкам.

```bash
sudo apt update && sudo apt dist-upgrade -y
```

Установка самого пакета `gvm` является мета-пакетом, который тянет за собой все необходимые компоненты: `gvmd`, `gsad`, `ospd-openvas`, `notusd`, а также зависимости.

```bash
sudo apt install gvm postgresql nsis -y
```

После установки пакета необходимо выполнить скрипт инициализации `gvm-setup`. Этот скрипт выполняет ряд критических операций:
1.  Инициализирует базу данных PostgreSQL.
2.  Создает пользователя `_gvm` и настраивает права доступа.
3.  Генерирует SSL-сертификаты для `gsad`.
4.  Запускает первоначальную синхронизацию фидов (NVT, SCAP, CERT).
5.  Создает административного пользователя `admin` и выводит его пароль.

```bash
sudo gvm-setup
```

Этот процесс может занять от 30 минут до нескольких часов в зависимости от скорости интернета и мощности процессора, так как скачивается и парсится огромный объем данных об уязвимостях. Пароль администратора выводится в конце выполнения скрипта и должен быть сохранен.

После завершения `gvm-setup` необходимо проверить состояние установки с помощью утилиты `gvm-check-setup`. Эта утилита проверяет наличие всех необходимых сервисов, правильность конфигурации PostgreSQL, наличие фидов и работоспособность API.

```bash
sudo gvm-check-setup
```

Если проверка проходит успешно, вывод будет содержать сообщение: `It seems like your GVM-<version> installation is OK.`. Если есть ошибки, скрипт предоставит детальные инструкции по их исправлению.

Первичная конфигурация включает в себя настройку прав доступа. По умолчанию пользователь `admin` может только просматривать отчеты, но не создавать задачи. Для предоставления прав на создание задач необходимо выполнить следующую команду:

```bash
sudo gvmd --modify-setting 78eceaec-3385-11ea-b237-28d24461215b --value admin
```

UUID `78eceaec-3385-11ea-b237-28d24461215b` соответствует настройке `create_task` в GVM.

Также необходимо убедиться, что сервисы запущены. В современных системах они управляются через systemd.

```bash
sudo systemctl start gvmd.service gsad.service ospd-openvas.service notusd.service
sudo systemctl enable gvmd.service gsad.service ospd-openvas.service notusd.service
```

Проверка статуса сервисов:

```bash
sudo systemctl status gvmd.service
sudo systemctl status gsad.service
sudo systemctl status ospd-openvas.service
```

Доступ к веб-интерфейсу осуществляется по адресу `https://localhost:9392`. При первом подключении браузер выдаст предупреждение о самоподписанном сертификате, что является нормальным для локальных установок.

## Сквозной практический пример: Развертывание и верификация GVM на Kali Linux

**Исходные условия:**
*   **Среда:** Виртуальная машина с Kali Linux 2025.3 (или Ubuntu 24.04 LTS).
*   **Роль:** Администратор безопасности (Penetration Tester / SOC Analyst).
*   **Цель:** Установить GVM, инициализировать базу данных, синхронизировать фиды, создать пользователя и проверить работоспособность веб-интерфейса.
*   **Инструменты:** Терминал, веб-браузер, утилиты `apt`, `systemctl`, `gvmd`.

### Шаг 1: Обновление системы и установка пакета GVM

Действие: Обновление списков пакетов и установка мета-пакета `gvm` вместе с зависимостями.

```bash
kali@kali:~$ sudo apt update && sudo apt dist-upgrade -y
kali@kali:~$ sudo apt install gvm postgresql nsis -y
```

Ожидаемый вывод/результат:
Система обновляется. Пакет `gvm` и все его зависимости (включая `gvmd`, `gsad`, `ospd-openvas`, `redis-server`, `postgresql`) устанавливаются. Процесс завершается без ошибок.

### Шаг 2: Инициализация и первичная настройка

Действие: Запуск скрипта `gvm-setup` для создания базы данных, пользователей и загрузки фидов.

```bash
kali@kali:~$ sudo gvm-setup
```

Ожидаемый вывод/результат:
Скрипт выводит прогресс-бары. В конце выводит сообщение:
```text
[+] Please note the password for the admin user
[*] User created with password 'a1b2c3d4-e5f6-7890-abcd-ef1234567890'.
[+] You can now run gvm-check-setup to make sure everything is correctly configured
```
Пароль `a1b2c3d4-e5f6-7890-abcd-ef1234567890` записывается в файл `/var/lib/gvm/CA/clientcert.pem` (или выводится в консоль, в зависимости от версии).

### Шаг 3: Проверка состояния установки

Действие: Запуск утилиты диагностики.

```bash
kali@kali:~$ sudo gvm-check-setup
```

Ожидаемый вывод/результат:
Если все правильно:
```text
It seems like your GVM-23.11.0 installation is OK.
```
Если есть ошибки (например, несовпадение версий PostgreSQL), скрипт укажет на них и предложит команды для исправления.

### Шаг 4: Настройка прав администратора

Действие: Предоставление прав на создание задач пользователю `admin`.

```bash
kali@kali:~$ sudo gvmd --modify-setting 78eceaec-3385-11ea-b237-28d24461215b --value admin
```

Ожидаемый вывод/результат:
Команда выполняется молча (exit code 0). Теперь пользователь `admin` может создавать задачи сканирования через веб-интерфейс.

### Шаг 5: Запуск сервисов и проверка доступа

Действие: Запуск сервисов и проверка прослушиваемых портов.

```bash
kali@kali:~$ sudo systemctl start gvmd.service gsad.service ospd-openvas.service
kali@kali:~$ sudo ss -ltn4p | grep 9392
```

Ожидаемый вывод/результат:
```text
LISTEN  0  4096  127.0.0.1:9392  0.0.0.0:*  users:(("gsad",pid=1234,fd=10))
```
Порт 9392 прослушивается. Открытие `https://127.0.0.1:9392` в браузере показывает форму входа. Ввод логина `admin` и пароля из шага 2 обеспечивает доступ к веб-интерфейсу.

**Ожидаемый вывод:**
Пример демонстрирует полный цикл от чистой установки до рабочего состояния GVM. Ключевыми моментами являются корректное выполнение `gvm-setup` (которое автоматически настраивает PostgreSQL и Redis) и предоставление прав на создание задач, без которых веб-интерфейс будет функционально ограничен.

## Аналитический вывод

Установка и первичная настройка Greenbone Vulnerability Manager представляет собой не просто инсталляцию программного обеспечения, а развертывание сложной микросервисной архитектуры. Успех зависит от строгого соблюдения последовательности действий: обновление системы, установка мета-пакета, инициализация через `gvm-setup` и верификация через `gvm-check-setup`. Критическими точками отказа являются совместимость версий PostgreSQL, права доступа к Unix domain сокетам OSPD и актуальность фидов уязвимостей. GVM требует значительных ресурсов (CPU, RAM, Disk I/O), особенно на этапе синхронизации фидов и выполнения сканирований, что необходимо учитывать при планировании инфраструктуры. Понимание разделения ролей между `gvmd`, `ospd-openvas` и `gsad` позволяет эффективно диагностировать проблемы и масштабировать систему в будущем.
