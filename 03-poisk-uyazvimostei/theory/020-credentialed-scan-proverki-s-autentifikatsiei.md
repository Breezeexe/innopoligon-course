# Credentialed Scan в Nessus: архитектура, риски и практика применения

## Контекст и базовые понятия

Аутентифицированное сканирование (Credentialed Scan) в контексте инструментов оценки уязвимостей, таких как Tenable Nessus, представляет собой метод проверки безопасности, при котором сканер получает локальный доступ к целевой системе с использованием предоставленных учетных данных. В отличие от неаутентифицированного (unauthenticated) сканирования, которое ограничивается анализом сетевых ответов (баннеров, заголовков, открытых портов), аутентифицированное сканирование позволяет сканеру выполнять локальные проверки (local checks). Это включает чтение реестра операционной системы, проверку установленных файлов (например, версий DLL), анализ журналов событий и проверку конфигураций служб.

Ключевое различие между типами сканирования заключается в глубине получаемой информации. Неаутентифицированное сканирование подвержено высокому уровню ложноположительных (false positives) и ложноотрицательных (false negatives) результатов, так как оно основывается на эвристическом анализе внешних ответов. Аутентифицированное сканирование обеспечивает точность, сопоставимую с локальным аудитом, так как сканер видит систему изнутри, как легитимный администратор. Однако этот метод вводит критический риск: передача привилегированных учетных данных в сеть создает поверхность атаки. Если учетные данные перехвачены злоумышленником, они могут быть использованы для полного компрометации инфраструктуры.

В экосистеме Tenable различают несколько уровней аутентификации:
1.  **Системные учетные данные:** Локальные администраторы (Windows) или root/sudo (Linux/Unix) для проверки ОС и установленных патчей.
2.  **Сетевые протоколы:** SNMP (для сетевого оборудования), SMB (для файловых серверов).
3.  **Веб-приложения:** HTTP Basic/Digest, формы входа, cookies.
4.  **Агенты:** Tenable Agent, который устанавливается на хост и устраняет необходимость передачи учетных данных по сети, так как проверка происходит локально.

Путаница часто возникает между понятиями "Credentialed Scan" и "Agent-based Scan". Хотя оба метода обеспечивают локальный доступ, первый требует передачи учетных данных по сети (SSH, SMB, WMI), что создает риск перехвата, тогда как второй исключает этот вектор атаки, но требует установки ПО на каждый хост.

| Характеристика | Unauthenticated Scan (Без аутентификации) | Credentialed Scan (С аутентификацией) | Agent-based Scan (С агентом) |
| :--- | :--- | :--- | :--- |
| **Метод доступа** | Сетевой анализ (banner grabbing, port probing) | Локальный вход (SSH, SMB, WMI, SNMP) | Локальный процесс на хосте |
| **Глубина проверки** | Низкая (только открытые сервисы) | Высокая (реестр, файлы, логи, патчи) | Максимальная (полный доступ к ОС) |
| **Точность результатов** | Низкая (много ложных срабатываний) | Высокая (минимум ложных срабатываний) | Максимальная |
| **Риск безопасности** | Низкий (нет передачи паролей) | **Высокий** (риск перехвата учетных данных) | Низкий (нет передачи паролей по сети) |
| **Требования к инфраструктуре** | Доступ к портам (TCP/UDP) | Настройка учетных записей, правил брандмауэра | Установка и поддержка агента |
| **Применимость** | Внешние периметры, сетевое оборудование | Внутренние сети, серверы, рабочие станции | Гибридные среды, облака, конечные точки |

Аутентифицированное сканирование является стандартом де-факто для внутренних аудитов безопасности. Оно позволяет выявить конфигурационные ошибки, отсутствующие патчи и локальные уязвимости, которые невозможно обнаружить извне. Однако, как отмечается в исследованиях по безопасности, неправильная конфигурация механизмов аутентификации (например, использование SSH с паролем вместо ключей или передача учетных данных по незащищенным каналам) может превратить инструмент аудита в вектор атаки.

## Внутреннее устройство предмета

Аутентифицированное сканирование в Nessus базируется на нескольких ключевых механизмах взаимодействия с целевыми системами. Архитектура сканера позволяет использовать различные протоколы в зависимости от операционной системы и требуемых проверок.

### Механизмы аутентификации и протоколы

Для Windows-систем Nessus использует комбинацию протоколов SMB (Server Message Block) и WMI (Windows Management Instrumentation). SMB используется для доступа к файловым системам и реестру, а WMI — для получения информации о службах, процессах и установленных программах. Критическим аспектом конфигурации Windows является политика "Network access: Sharing and security model for local accounts". По умолчанию в некоторых версиях Windows эта политика установлена в "Guest only", что блокирует удаленный доступ для локальных учетных записей. Для работы аутентифицированного сканирования необходимо установить значение "Classic - local users authenticate as themselves". Это позволяет сканеру аутентифицироваться как локальный администратор, а не как гость.

Для Unix/Linux-систем основным протоколом является SSH (Secure Shell). Nessus поддерживает аутентификацию по паролю и по открытым ключам. Использование ключей предпочтительнее с точки зрения безопасности, так как исключает риск перехвата пароля. Однако, если используется аутентификация по паролю, возникает риск, описанный в исследовании Shorebreak Security: учетные данные отправляются всем хостам в подсети, которые отвечают на порт 22. Если злоумышленник контролирует хост в этой подсети, он может перехватить учетные данные сканера.

Для сетевого оборудования (роутеры, коммутаторы, фаерволы) Nessus использует SNMP (Simple Network Management Protocol). Версии SNMPv1 и SNMPv2c передают community string в открытом виде, что делает их уязвимыми к перехвату. SNMPv3 обеспечивает шифрование и аутентификацию, что является рекомендуемым подходом.

### Архитектура передачи учетных данных

Учетные данные в Nessus хранятся в зашифрованном виде в базе данных `global.db` на сервере Tenable. При запуске скана сканер извлекает учетные данные и пытается установить соединение с целевыми хостами. Nessus открывает несколько параллельных аутентифицированных соединений к каждому хосту. Это может привести к блокировке учетной записи (account lockout), если на целевой системе настроена строгая политика блокировки после нескольких неудачных попыток входа.

Процесс аутентифицированного сканирования включает следующие этапы:
1.  **Инициализация соединения:** Сканер пытается установить соединение с целевым хостом через выбранный протокол (SSH, SMB, WMI).
2.  **Аутентификация:** Предоставление учетных данных. Для SMB/WMI это может включать использование NTLM-хэшей или паролей. Для SSH — пароль или закрытый ключ.
3.  **Выполнение локальных проверок:** После успешной аутентификации сканер выполняет набор плагинов (plugins), которые запрашивают локальные данные (версию реестра, список файлов, конфигурацию службы).
4.  **Обработка результатов:** Данные анализируются, и если обнаруживается несоответствие известным уязвимостям, формируется отчет.

### Риски и уязвимости конфигурации

Основной риск аутентифицированного сканирования связан с утечкой учетных данных. Если учетные данные передаются по незащищенному каналу или если они используются для аутентификации на всех хостах в подсети, злоумышленник может перехватить их. В случае с SSH, если используется аутентификация по паролю, сканер отправляет пароль всем хостам, которые отвечают на порт 22. Это означает, что любой хост в сети, который не является целью сканирования, но имеет открытый порт 22, может получить учетные данные.

Другой риск связан с избыточными привилегиями. Использование учетной записи Domain Administrator для сканирования всех хостов в домене создает риск компрометации всей инфраструктуры в случае утечки этих учетных данных. Рекомендуется использовать специализированные учетные записи с минимально необходимыми привилегиями.

### Сравнительная таблица механизмов аутентификации

| Протокол | Платформа | Механизм аутентификации | Требования к конфигурации | Риски |
| :--- | :--- | :--- | :--- | :--- |
| **SSH** | Linux/Unix | Пароль / SSH Key | Открытый порт 22, доступ к пользователю | Перехват пароля при использовании пароля; необходимость настройки ключей |
| **SMB/WMI** | Windows | NTLM / Kerberos / Пароль | Открытые порты 139/445, политика "Classic" | Перехват NTLM-хэшей; необходимость настройки политик безопасности |
| **SNMP** | Network Devices | Community String (v1/v2c) / Auth/Priv (v3) | Открытый порт 161/162 | Перехват community string; необходимость настройки SNMPv3 |
| **HTTP** | Web Applications | Basic/Digest / Form / Cookies | Доступ к веб-приложению | Перехват учетных данных; необходимость настройки regex для проверки успешности входа |

## Применение и работа с предметом

Практическое применение аутентифицированного сканирования требует тщательной подготовки инфраструктуры и настройки учетных данных. Процесс включает создание специализированных учетных записей, настройку политик безопасности и конфигурацию сканера.

### Подготовка инфраструктуры для Windows

Для успешного аутентифицированного сканирования Windows-хостов необходимо выполнить следующие шаги:

1.  **Создание учетной записи:** Создать локальную или доменную учетную запись с правами администратора. Рекомендуется использовать отдельную учетную запись для сканирования, а не использовать существующие учетные записи администраторов.
2.  **Настройка политики безопасности:** Изменить политику "Network access: Sharing and security model for local accounts" на "Classic - local users authenticate as themselves". Это можно сделать через `gpedit.msc` или через Group Policy Management Console (GPMC) в домене.
3.  **Настройка реестра:** Создать или изменить параметр `LocalAccountTokenFilterPolicy` в реестре (`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System`) со значением `1`. Это позволяет локальным учетным записям аутентифицироваться удаленно без ограничений.
4.  **Настройка брандмауэра:** Разрешить доступ к портам 135 (RPC), 139 (NetBIOS), 445 (SMB) и 49152-65535 (динамические порты RPC). Также необходимо разрешить доступ к службе Remote Registry.

### Подготовка инфраструктуры для Linux

Для Linux-хостов необходимо:

1.  **Создание учетной записи:** Создать пользователя с правами sudo или root.
2.  **Настройка SSH:** Убедиться, что SSH-сервер разрешает вход для этого пользователя. Рекомендуется использовать аутентификацию по ключам.
3.  **Настройка брандмауэра:** Разрешить доступ к порту 22.

### Конфигурация сканера Nessus

В веб-интерфейсе Nessus при создании нового скана необходимо перейти на вкладку "Credentials" и добавить учетные данные для каждой платформы.

Для Windows:
-   Тип: Windows
-   Имя пользователя: `DOMAIN\Username` или `.\Username`
-   Пароль: Ввести пароль или указать путь к файлу с NTLM-хэшем.

Для Linux:
-   Тип: SSH
-   Имя пользователя: `username`
-   Пароль: Ввести пароль или указать путь к приватному ключу.

Для сетевого оборудования:
-   Тип: SNMP
-   Community String: Ввести community string.

### Типичные ошибки и подводные камни

1.  **Использование учетных записей с избыточными привилегиями:** Использование Domain Administrator создает риск компрометации всего домена. Рекомендуется использовать учетные записи с минимально необходимыми привилегиями.
2.  **Неправильная настройка политик безопасности:** Неизмененная политика "Guest only" в Windows приводит к неудачным попыткам аутентификации.
3.  **Блокировка учетных записей:** Слишком частые попытки аутентификации могут привести к блокировке учетных записей на целевых системах. Необходимо настроить задержки между попытками.
4.  **Перехват учетных данных:** Использование аутентификации по паролю в SSH создает риск перехвата. Рекомендуется использовать аутентификацию по ключам.

Ниже приведен пример JSON-структуры, описывающей учетные данные для сканирования (иллюстративная схема, так как реальный формат зависит от версии API):

## Сквозной практический пример: Настройка и запуск аутентифицированного скана

**Исходные условия:**
Среда: Корпоративная сеть с доменом Active Directory.
Цель: Провести аутентифицированное сканирование группы Windows-серверов и Linux-рабочих станций.
Роль: Администратор безопасности.
Инструменты: Tenable Nessus Professional, Active Directory, Group Policy Management Console.

### Шаг 1: Создание специализированной учетной записи в Active Directory

Создаем учетную запись, которая будет использоваться для сканирования. Эта учетная запись должна иметь права локального администратора на всех целевых хостах.

```powershell
# PowerShell на Domain Controller
New-ADUser -Name "NessusScanner" -SamAccountName "nessus_scan" -AccountPassword (ConvertTo-SecureString "P@ssw0rd!123" -AsPlainText -Force) -Enabled $true -PasswordNeverExpires $true
# Добавляем пользователя в группу локальных администраторов на целевых хостах
# (Пример для одного хоста, в реальности используется GPO)
net localgroup Administrators /add CORP\nessus_scan
```

### Шаг 2: Настройка групповой политики для Windows-хостов

Настройка политик безопасности для обеспечения возможности удаленного входа.

```powershell
# Настройка политики "Network access: Sharing and security model for local accounts"
# Через GPMC или локально на каждом хосте
gpupdate /force

# Настройка реестра для отключения фильтрации токенов
reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" /v LocalAccountTokenFilterPolicy /t REG_DWORD /d 1 /f
```

### Шаг 3: Конфигурация сканера Nessus

В веб-интерфейсе Nessus создаем новый скан. На вкладке "Credentials" добавляем учетные данные.

```json
{
  "scan": {
    "name": "Credentialed Scan - Q4 Audit",
    "credentials": {
      "windows": [
        {
          "username": "nessus_scan",
          "password": "P@ssw0rd!123",
          "scope": "domain",
          "domain": "CORP"
        }
      ],
      "ssh": [
        {
          "username": "nessus_scan",
          "password": "P@ssw0rd!123",
          "scope": "subnet",
          "subnet": "192.168.1.0/24"
        }
      ]
    },
    "targets": ["192.168.1.0/24"],
    "policy": "Internal Network Scan"
  }
}
```

### Шаг 4: Запуск сканирования и мониторинг

Запускаем скан и наблюдаем за процессом. Nessus будет пытаться аутентифицироваться на каждом хосте в указанной подсети.

```bash

```

### Шаг 5: Анализ результатов

После завершения скана анализируем отчет. Аутентифицированные проверки позволяют выявить отсутствующие патчи и конфигурационные ошибки.

```json

Успешная аутентификация на всех целевых хостах позволяет Nessus получить доступ к локальным данным и выявить уязвимости, которые невозможно обнаружить при неаутентифицированном сканировании. Однако, использование учетных данных с паролем в SSH создает риск перехвата, что требует дополнительных мер защиты.

## Аналитический вывод

Аутентифицированное сканирование в Nessus является мощным инструментом для выявления уязвимостей, но оно требует тщательного управления учетными данными и конфигурацией инфраструктуры. Использование специализированных учетных записей с минимально необходимыми привилегиями, настройка политик безопасности и использование защищенных протоколов (таких как SSH с ключами или SNMPv3) критически важны для минимизации рисков. Перехват учетных данных при аутентифицированном сканировании может привести к компрометации всей инфраструктуры, поэтому необходимо применять дополнительные меры защиты, такие как сегментация сети и мониторинг активности сканера. Альтернативой аутентифицированному сканированию является использование агентов Tenable, которые устраняют риск перехвата учетных данных, но требуют установки ПО на каждый хост. Выбор между этими методами зависит от требований безопасности и инфраструктуры организации.
