# Анализ отчётов Tenable Nessus и работа с метриками оценки уязвимостей (CVSS, VPR, EPSS)

## Контекст и базовые понятия: Эволюция систем оценки уязвимостей и архитектура данных отчёта

Тестирование на проникновение и управление уязвимостями (Vulnerability Management) опираются на стандартизированные методы количественной оценки рисков. Без единой системы метрик специалист по безопасности не может эффективно сортировать тысячи обнаруженных дефектов. Tenable Nessus, являясь индустриальным стандартом для сканирования уязвимостей, использует сложную многоуровневую систему оценки, которая эволюционировала от статических оценок к динамическим, контекстно-зависимым рейтингам.

Ключевым понятием здесь является **CVSS (Common Vulnerability Scoring System)** — открытый стандарт оценки технической тяжести уязвимости, поддерживаемый FIRST (Forum of Incident Response and Security Teams). CVSS присваивает балл от 0.0 до 10.0, основываясь на характеристиках самой уязвимости (Base Metrics), её текущем состоянии (Temporal Metrics) и специфике окружения (Environmental Metrics). Однако CVSS имеет фундаментальное ограничение: он не учитывает наличие эксплойтов в дикой природе, ценность актива или контекст инфраструктуры.

Для преодоления этого ограничения Tenable внедрила собственную метрику **VPR (Vulnerability Priority Rating)**. VPR — это проприетарная система оценки риска, разработанная Tenable Research. Она объединяет данные CVSS с проприетарными данными об угрозах, активностью в даркнете, социальной сети и историей эксплуатации. В отличие от CVSS, который статичен после публикации, VPR динамически обновляется по мере поступления новых разведданных.

Также в современных версиях Nessus (начиная с 10.x) активно используется **EPSS (Exploit Prediction Scoring System)** — метрика, предсказывающая вероятность того, что уязвимость будет эксплуатироваться в течение следующих 30 дней. EPSS использует машинное обучение на основе данных о прошлых эксплойтах.

Разбор отчёта Nessus требует понимания структуры данных. Отчёт Nessus (в формате CSV или XML) содержит не только факт наличия уязвимости, но и набор метаданных, необходимых для фильтрации и приоритизации. Понимание разницы между версиями Nessus (Essentials, Professional, Expert) критично, так как только версии Professional и Expert предоставляют доступ к расширенным метрикам (VPR, EPSS, CVSS v4) и аудитам конфигураций.

| Характеристика | CVSS (Base Score) | VPR (Tenable) | EPSS (Exploit Prediction) |
| :--- | :--- | :--- | :--- |
| **Источник данных** | NVD / Вендор продукта | Tenable Research + внешние угрозы | FIRST / Data-driven ML модель |
| **Диапазон значений** | 0.0 – 10.0 | 0.1 – 10.0 | 0.0 – 1.0 (вероятность) |
| **Динамичность** | Статичен (после публикации CVE) | Динамичен (обновляется ежедневно) | Динамичен (обновляется еженедельно) |
| **Учет контекста среды** | Нет (только технические метрики) | Да (интеграция с данными Tenable) | Нет (фокус на вероятности эксплойта) |
| **Основное применение** | Сравнение тяжести уязвимости | Приоритизация исправлений в SOC | Оценка вероятности атаки в ближайшие дни |
| **Версии Nessus** | Все версии | Professional / Expert | Professional / Expert |

*Таблица 1. Сравнительный анализ систем оценки уязвимостей в экосистеме Tenable.*

Важно разграничивать понятия **Severity** (Тяжесть) и **Risk** (Риск). В отчёте Nessus Severity часто отображается как цветовой индикатор (Critical, High, Medium, Low, Info), который может быть настроен на основе CVSS или VPR. Risk — это итоговая оценка необходимости действия, которая формируется на пересечении Severity, ценности актива и контекста. Студенты часто путают высокий CVSS с высоким риском для конкретной организации, что является типичной ошибкой: уязвимость с CVSS 9.8 на изолированном сервере без сетевого доступа может иметь меньший практический риск, чем уязвимость с CVSS 5.0 на публичном веб-сервере.

## Внутреннее устройство: Структура отчёта Nessus и метрики оценки

Отчёт Nessus представляет собой структурированный набор данных, где каждая строка соответствует обнаруженной уязвимости на конкретном узле. Понимание внутренней структуры колонок CSV-отчёта необходимо для автоматизации обработки данных и написания правил детекции.

### Структура CSV-отчёта Nessus

Отчёт Nessus содержит от 20 до 25 колонок. Ключевые поля, необходимые для анализа:

1.  **Plugin ID**: Уникальный идентификатор плагина Tenable. Это внутренний ключ, по которому сканер связывает данные с базой знаний.
2.  **Plugin Name**: Название проверки (например, `Apache HTTP Server Multiple Vulnerabilities`).
3.  **Family**: Категория уязвимости (например, `Web Servers`, `SSL`, `Windows`).
4.  **Host IP / Host Name**: Целевой узел.
5.  **Port**: Порт, на котором обнаружена уязвимость (например, `80`, `443`, `8009`).
6.  **CVE ID**: Идентификатор Common Vulnerabilities and Exposures.
7.  **CVSS Base Score**: Базовый балл CVSS.
8.  **CVSS Vector**: Векторная строка, позволяющая пересчитать балл.
9.  **VPR Score**: Рейтинг приоритетности уязвимости (если включен в лицензии).
10. **EPSS Score**: Вероятность эксплуатации.
11. **Risk Factor**: Категоризация (Critical, High, Medium, Low, Info).
12. **Solution**: Рекомендация по устранению (часто содержит ссылки на патчи).
13. **See Also**: Ссылки на дополнительные материалы.
14. **Plugin Publication Date**: Дата публикации плагина.
15. **Vuln Publication Date**: Дата публикации CVE.

*Иллюстративная схема полей CSV-отчёта Nessus:*

```json
{
  "scan_metadata": {
    "scan_name": "Basic Network Scan",
    "start_time": "2024-05-20T10:00:00Z",
    "scanner_version": "Nessus 10.x"
  },
  "vulnerability_record": {
    "plugin_id": "123456",
    "plugin_name": "Example Vulnerability Check",
    "family": "Web Servers",
    "host_ip": "192.168.1.100",
    "port": 80,
    "protocol": "tcp",
    "cve_ids": ["CVE-2024-XXXXX"],
    "cvss_v3_base_score": 9.8,
    "cvss_v3_vector": "AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H",
    "vpr_score": 8.5,

  }
}
```

*Примечание: Конкретные значения полей зависят от среды сканирования и версии плагина.*

### Архитектура метрик CVSS v3.1 и v4.0

CVSS v3.1 и v4.0 имеют различную структуру метрик. В Nessus Professional и Expert поддерживается обе версии, но по умолчанию часто используется v3.1, хотя переход на v4.0 становится стандартом индустрии.

**CVSS v3.1 Base Metrics:**
*   **Attack Vector (AV):** Network, Adjacent, Local, Physical.
*   **Attack Complexity (AC):** Low, High.
*   **Privileges Required (PR):** None, Low, High.
*   **User Interaction (UI):** None, Required.
*   **Scope (S):** Unchanged, Changed.
*   **Confidentiality (C), Integrity (I), Availability (A):** None, Low, High.

**CVSS v4.0 отличия:**
Введена новая метрика **Safety** (безопасность для жизни/здоровья), **Automatable** (возможность автоматизации атаки), **Technical Impact** (раздельно от Availability). Это делает оценку более точной для современных облачных и IoT-сред.

### Внутренняя логика VPR (Vulnerability Priority Rating)

VPR не является публичным алгоритмом, но его логика описана в документации Tenable. VPR рассчитывается на основе:
1.  **Threat Intelligence:** Наличие эксплойтов в даркнете, GitHub, социальных сетях.
2.  **Exploit Availability:** Активность в репозиториях эксплойтов.
3.  **Asset Context:** Интеграция с данными о критичности активов (если настроено).
4.  **Historical Data:** Статистика успешности эксплуатации подобных уязвимостей.

VPR позволяет группировать уязвимости не по технической тяжести, а по вероятности наступления инцидента. Это критически важно для SOC-аналитиков, которые не могут исправить все уязвимости с CVSS 9.8, если на них нет активных атак.

## Применение и работа с предметом: Анализ отчёта и приоритизация

Работа с отчётом Nessus на практике сводится не к просмотру списка уязвимостей, а к фильтрации и приоритизации. Типичный пайплайн специалиста по уязвимостям:

1.  **Экспорт данных:** Выгрузка отчёта в CSV или интеграция через API с SIEM/SOAR.
2.  **Фильтрация по контексту:** Удаление ложных срабатываний (False Positives) и уязвимостей на незначимых активах.
3.  **Приоритизация:** Сортировка по VPR или EPSS, а не только по CVSS.
4.  **Корреляция:** Сопоставление с данными о патчах и конфигурациях.
5.  **Отчетность:** Формирование отчёта для руководства с фокусом на бизнес-риске.

### Практическая работа с CSV-данными

Для анализа отчёта часто используются инструменты командной строки (awk, grep, python-pandas) или Excel. Ниже приведен пример фильтрации уязвимостей с высоким риском.

**Задача:** Выбрать все уязвимости с CVSS >= 9.0 и VPR >= 7.0 для дальнейшей обработки.

```python
import pandas as pd

# Загрузка отчёта Nessus (иллюстративный путь)
df = pd.read_csv('nessus_scan_report.csv')

# Фильтрация по CVSS и VPR
# Примечание: названия колонок могут варьироваться в зависимости от версии экспорта
critical_vulns = df[
    (df['CVSS Base Score'] >= 9.0) & 
    (df['VPR Score'] >= 7.0)
]

# Группировка по Plugin ID для оценки масштаба проблемы
summary = critical_vulns.groupby('Plugin Name').agg({
    'Host IP': 'count',
    'CVSS Base Score': 'first',
    'VPR Score': 'first'
}).reset_index()

# Вывод топ-5 наиболее критичных уязвимостей
print(summary.nlargest(5, 'Host IP'))
```

*Код 1. Скрипт на Python для фильтрации и агрегации данных из отчёта Nessus.*

### Интерпретация вектора CVSS

Вектор CVSS позволяет специалисту понять *почему* уязвимость имеет такой балл. Например, вектор `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` означает:
*   **AV:N:** Атака возможна удаленно по сети (Network).
*   **AC:L:** Сложность атаки низкая (Low).
*   **PR:N:** Права не требуются (None).
*   **UI:N:** Взаимодействие с пользователем не требуется.
*   **S:U:** Scope unchanged (влияние только на целевую систему).
*   **C/I/A:H:** Высокое влияние на конфиденциальность, целостность и доступность.

Такой вектор автоматически дает высокий балл. Если же в векторе есть `PR:H` (требуются права администратора) или `AV:L` (локальная атака), балл будет значительно ниже, даже если влияние на систему максимальное.

### Работа с EPSS в Nessus

EPSS Score от 0.0 до 1.0 показывает вероятность эксплуатации. Например, EPSS 0.85 означает 85% вероятность того, что уязвимость будет эксплуатироваться в ближайшие 30 дней. В Nessus Professional/Expert это поле доступно в отчёте.

**Рекомендация Tenable:** Использовать комбинацию CVSS и EPSS.
*   Высокий CVSS + Высокий EPSS = Немедленное исправление.
*   Высокий CVSS + Низкий EPSS = Исправление в плановом порядке (если нет других факторов риска).
*   Низкий CVSS + Высокий EPSS = Внимание (возможно, активная эксплуатация в дикой природе).

## Сквозной практический пример: Анализ инцидента на основе отчёта Nessus

**Исходные условия:**
Среда: Корпоративная сеть с веб-сервером Apache на Linux.
Инструмент: Tenable Nessus Professional.
Роль: Специалист по управлению уязвимостями.
Сценарий: Получен отчёт сканирования, необходимо определить приоритет устранения критической уязвимости Ghostcat (CVE-2020-1938).

**Шаг 1: Идентификация уязвимости в отчёте**

Экспортируем отчёт в CSV и ищем строку с Plugin ID, соответствующим Ghostcat. В отчёте находим следующую запись (иллюстративные данные):

```csv
Plugin ID,Plugin Name,Host IP,Port,CVE ID,CVSS Base Score,VPR Score,EPSS Score,Risk Factor
138062,Ghostcat (CVE-2020-1938) Vulnerability Check,10.0.0.50,8009,CVE-2020-1938,9.8,8.2,0.92,Critical
```

*Артефакт 1. Фрагмент CSV-отчёта Nessus с данными об уязвимости Ghostcat.*

**Шаг 2: Анализ вектора CVSS и контекста**

Проверяем детали уязвимости в базе знаний Nessus.
*   **Synopsis:** Apache Tomcat AJP Connector allows remote attackers to read files.
*   **CVSS Vector:** `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`
*   **Affected Port:** 8009 (AJP protocol).

Анализ показывает, что уязвимость позволяет читать произвольные файлы на сервере. Порт 8009 часто открыт только во внутренней сети, но в данном случае сканер обнаружил его доступность.

**Шаг 3: Оценка риска с помощью VPR и EPSS**

*   **VPR Score:** 8.2 (High). Это указывает на то, что уязвимость активно эксплуатируется или широко распространена в дикой природе.
*   **EPSS Score:** 0.92. Это экстремально высокая вероятность эксплуатации в ближайшие 30 дней.

Сравнение: Если бы мы ориентировались только на CVSS (9.8), мы бы поняли тяжесть, но не скорость угрозы. EPSS 0.92 требует немедленного действия.

**Шаг 4: Проверка конфигурации и ложных срабатываний**

Перед исправлением необходимо убедиться, что порт 8009 действительно доступен из недоверенных сетей. Выполняем проверку вручную:

```bash
# Проверка открытости порта AJP
nmap -p 8009 --script ajp-auth 10.0.0.50

# Вывод (иллюстративный):
# PORT     STATE SERVICE
# 8009/tcp open  ajp13
# | ajp-auth: 
# |   Status: Vulnerable
# |   Can read /etc/passwd
# |_  Can read /WEB-INF/web.xml
```

*Артефакт 2. Результат ручной проверки уязвимости через nmap.*

**Шаг 5: Принятие решения и устранение**

На основе данных:
1.  CVSS 9.8 (Тяжесть: Critical).
2.  EPSS 0.92 (Вероятность атаки: Очень высокая).
3.  VPR 8.2 (Риск: Высокий).
4.  Подтвержденный доступ к файловой системе (через nmap).

**Решение:** Уязвимость классифицируется как **P0 (Priority 0)**. Требуется немедленное применение патча или закрытие порта 8009 в фаерволе.

**Ожидаемый вывод:**
Пример демонстрирует, что анализ отчёта Nessus выходит за рамки чтения CVSS-балла. Комбинация VPR и EPSS позволяет выявить уязвимости, которые технически могут иметь среднюю тяжесть, но представляют критическую угрозу из-за высокой вероятности эксплуатации. В данном случае, даже если бы порт 8009 был закрыт для публичного доступа, высокий EPSS потребовал бы проверки внутренней сегментации сети.

## Аналитический вывод

Анализ отчётов Tenable Nessus и работа с метриками оценки уязвимостей требуют перехода от реактивного подхода (исправление всех уязвимостей с высоким CVSS) к проактивному приоритизированному управлению рисками. CVSS остается фундаментальной метрикой технической тяжести, но её статичность делает её недостаточной для определения приоритетов в условиях современных угроз. Интеграция динамических метрик, таких как VPR (от Tenable) и EPSS (от FIRST), позволяет специалистам по безопасности фокусироваться на уязвимостях, которые действительно эксплуатируются в дикой природе.

Ключевым навыком для специалиста по тестированию на проникновение и управлению уязвимостями является умение интерпретировать векторы CVSS, понимать контекст работы плагинов Nessus и использовать многомерные данные (CVSS + VPR + EPSS + Asset Criticality) для обоснования решений перед руководством. Игнорирование контекста среды и полагание исключительно на CVSS-баллы приводит к "усталости от алертов" и неэффективному распределению ресурсов. Современные версии Nessus (Professional/Expert) предоставляют необходимый инструментарий для такого анализа, но эффективность зависит от компетенции аналитика в интерпретации этих данных.
