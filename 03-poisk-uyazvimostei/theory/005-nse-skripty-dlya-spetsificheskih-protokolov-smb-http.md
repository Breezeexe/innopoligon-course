# NSE-скрипты для специфических протоколов: SMB и HTTP в контексте тестирования на проникновение

## Контекст и базовые понятия

Протоколы Server Message Block (SMB) и Hypertext Transfer Protocol (HTTP) являются фундаментальными строительными блоками современных корпоративных и публичных сетей. SMB, разработанный в 1980-х годах для обмена файлами и ресурсами, эволюционировал в сложный протокол удаленного вызова процедур (RPC) и аутентификации, став основным вектором атак внутри периметра (lateral movement). HTTP, будучи прикладным протоколом веб-коммуникации, расширил свою роль от простой передачи документов до платформы для выполнения произвольного кода, управления инфраструктурой и обхода межсетевых экранов.

Nmap Scripting Engine (NSE) представляет собой фреймворк, интегрированный в сканер Nmap, который позволяет использовать скрипты на языке Lua для автоматизации сложных задач: от простого обнаружения служб до эксплуатации уязвимостей. Ключевое отличие NSE от специализированных сканеров уязвимостей (например, Nessus или OpenVAS) заключается в его ориентации на сетевую разведку и быструю проверку конкретных векторов атак в рамках единого рабочего процесса. NSE не заменяет глубокий статический анализ, но предоставляет оперативный доступ к базе знаний сообщества (более 600 скриптов) для выявления известных проблем конфигурации и уязвимостей.

Для понимания роли NSE-скриптов необходимо разграничить понятия «обнаружение службы» (service discovery) и «обнаружение уязвимости» (vulnerability detection). Стандартный скан портов (`nmap -sV`) определяет версию ПО, но не проверяет её безопасность. NSE-скрипты категорий `vuln`, `auth` и `exploit` выполняют именно проверку безопасности, взаимодействуя со службой по протоколу и анализируя ответы на предмет отклонений от безопасного состояния.

| Характеристика | SMB (Server Message Block) | HTTP (Hypertext Transfer Protocol) |
| :--- | :--- | :--- |
| **Основное назначение** | Доступ к файлам, принтерам, IPC$-ресурсам, RPC. | Передача веб-контента, API-вызовы, управление веб-приложениями. |
| **Типичные порты** | TCP 445 (Direct TCP/IP), TCP 139 (NetBIOS over TCP). | TCP 80 (HTTP), TCP 443 (HTTPS), альтернативные (8080, 8443). |
| **Ключевые риски** | EternalBlue, Responder (NTLM relay), Null Sessions, weak signing. | XSS, SQLi, RCE через заголовки/методы, misconfiguration, outdated CMS. |
| **Категории NSE** | `smb`, `smb-vuln`, `smb-enum`, `auth`. | `http`, `http-enum`, `http-vuln`, `http-methods`, `http-headers`. |
| **Сложность протокола** | Высокая (бинарный формат, состояния сессий, сложные Negotiate/NTLM). | Относительно низкая (текстовый формат, stateless, но сложная логика приложения). |
| **Зрелость защиты** | Улучшена в SMBv2/v3 (подписание сообщений, шифрование), но SMBv1 всё ещё массово. | Зависит от реализации сервера и конфигурации приложения; часто уязвим из-за бизнес-логики. |

Сравнение показывает, что SMB требует глубокого понимания состояния сессии и криптографии аутентификации, тогда как HTTP-скрипты чаще фокусируются на анализе заголовков, методов и путей (URL), что отражает природу веб-приложений.

## Внутреннее устройство NSE-скриптов для SMB

Скрипты NSE для SMB (категория `smb`) работают на уровне протокольных диалогов. Они не просто сканируют порт, но инициируют полноценные SMB-сессии. Архитектура взаимодействия строится на этапе Negotiation Protocol, где клиент и сервер согласовывают версию протокола (dialect), после чего следует этап Session Setup для аутентификации и Tree Connect для доступа к ресурсам.

Ключевые скрипты для SMB можно разделить на три функциональные группы:
1.  **Обнаружение ОС и конфигурации (`smb-os-discovery`, `smb-protocols`):** Эти скрипты анализируют ответы на этапе Negotiation и Session Setup. `smb-os-discovery` извлекает информацию об ОС, имени компьютера, домене и рабочую группу, используя поля структуры `SMB_HEADER` и ответов `NEGOTIATE_PROTOCOL_RESPONSE`. `smb-protocols` проверяет поддержку диалектов, особенно критично выявляя наличие SMBv1, который помечается как уязвимый из-за известных эксплойтов (например, EternalBlue).
2.  **Перечисление ресурсов (`smb-enum-shares`, `smb-enum-users`):** После установки сессии скрипты отправляют запросы `SMB_COM_TREE_CONNECT` и `SMB_COM_QUERY_INFO` для получения списка общих папок (shares) и пользователей. Важно различать публичные шары и шары, требующие аутентификации. Скрипты могут использовать Null Session (анонимный доступ) или переданные учетные данные.
3.  **Проверка безопасности (`smb-security-mode`, `smb2-security-mode`):** Эти скрипты проверяют флаг `SMB_FLAGS2` на предмет требования подписи сообщений (message signing). Отсутствие подписи позволяет атакующим использовать инструменты вроде Responder для перехвата NTLM-хешей.

Структура данных, возвращаемая скриптами `smb-protocols`, иллюстрирует иерархию диалектов. Ниже представлена схема полей, характерных для ответа сервера:

```json
{
  "protocol_negotiation": {
    "dialects": [
      {
        "name": "NT LM 0.12",
        "version": "SMBv1",
        "status": "insecure",
        "notes": "Default on legacy systems, vulnerable to EternalBlue"
      },
      {
        "name": "2.0.2",
        "version": "SMBv2",
        "status": "acceptable"
      },
      {
        "name": "3.1.1",
        "version": "SMBv3",
        "status": "secure",
        "features": ["encryption", "multichannel"]
      }
    ],
    "security_mode": {
      "signing_required": true,
      "null_session_allowed": false
    }
  }
}
```

Скрипты `smb-vuln-*` (например, `smb-vuln-ms17-010`) используют специфические паттерны в ответах протокола для идентификации уязвимостей. Они не эксплуатируют уязвимость, а проверяют наличие определенных флагов или ответов на специально сформированные запросы, которые отличаются от стандартных. Например, скрипт `ms17-010` отправляет запрос с нулевым размером буфера и проверяет код ошибки или структуру ответа, которая возникает только в уязвимых реализациях SMBv1.

## Внутреннее устройство NSE-скриптов для HTTP

HTTP-скрипты NSE работают на уровне текстовых запросов и ответов. В отличие от бинарного SMB, HTTP-протокол позволяет легко парсить заголовки и тело ответа. NSE предоставляет библиотеку `http`, которая абстрагирует работу с сокетами и парсинг HTTP-сообщений.

Ключевые категории HTTP-скриптов:
1.  **Анализ методов (`http-methods`):** Скрипт отправляет запрос `OPTIONS` для получения списка поддерживаемых методов (поле `Allow`). Затем он проверяет, работают ли методы, не указанные в `Allow` (например, `TRACE`, `DELETE`, `PUT`), отправляя их индивидуально. Это выявляет несоответствия в конфигурации веб-сервера (например, Apache или Nginx), когда сервер отвечает 200 OK на метод, который должен быть запрещен.
2.  **Перечисление контента (`http-enum`):** Использует базу данных путей (wordlist) для поиска скрытых директорий, файлов конфигурации, бэкапов и админ-панелей. Скрипт анализирует коды ответов: 200 (OK), 301/302 (Redirect), 403 (Forbidden), 404 (Not Found). Наличие 200 OK на нестандартном пути указывает на потенциальную точку входа.
3.  **Проверка заголовков и безопасности (`http-headers`, `http-ssl-cert`):** Скрипт анализирует заголовки ответа на наличие строгих политик безопасности (HSTS, X-Frame-Options, CSP). Также проверяется наличие сертификатов SSL/TLS, их срок действия и алгоритмы шифрования.
4.  **Проверка уязвимостей (`http-vuln-*`):** Эти скрипты содержат специфические проверки для известных уязвимостей веб-серверов (Apache Struts, Log4j, IIS) и приложений (WordPress, Joomla). Они формируют payload, отправляют его и анализируют ответ на наличие специфических строк или изменений в поведении.

Сравнительная таблица основных HTTP-скриптов NSE:

| Скрипт | Категория | Функция | Ключевой индикатор проблемы |
| :--- | :--- | :--- | :--- |
| `http-methods` | safe | Проверка HTTP-методов | Поддержка TRACE, PUT, DELETE без необходимости аутентификации. |
| `http-enum` | discovery | Поиск скрытых путей | Код ответа 200 OK на пути из wordlist (например, `/admin`, `/backup`). |
| `http-headers` | safe | Анализ заголовков | Отсутствие `X-Frame-Options`, `Content-Security-Policy`, `Strict-Transport-Security`. |
| `http-ssl-cert` | safe | Проверка SSL-сертификатов | Истекший сертификат, самоподписанный сертификат, слабые алгоритмы подписи. |
| `http-vuln-cve2017-5638` | vuln | Проверка Apache Struts | Ответ содержит специфическую ошибку парсинга multipart/form-data. |
| `http-wordpress-users` | brute | Перебор пользователей WP | Код ответа 200 OK с указанием имени пользователя в redirect или заголовке. |

Скрипты `http-vuln` часто используют библиотеку `httpsploit` или `http` для отправки запросов с измененными заголовками или телом. Они сравнивают ответ с эталонным (baseline) или ищут специфические строки (signatures). Например, скрипт для проверки Log4Shell отправляет запрос с payload `${jndi:ldap://...}` и проверяет, не инициирует ли сервер исходящее DNS-запрос (что невозможно проверить напрямую из NSE, но можно проверить по косвенным признакам, таким как время отклика или специфические ошибки).

## Применение и работа с предметом

На практике применение NSE-скриптов для SMB и HTTP требует понимания контекста сканирования. Слепое выполнение всех скриптов (`--script all`) может привести к отказу в обслуживании (DoS) для целевых систем, особенно для устаревших или embedded-устройств. Поэтому рекомендуется использовать категории скриптов (`--script safe`, `--script vuln`) или конкретные имена скриптов.

Для SMB-скриптов критически важно учитывать аутентификацию. Многие скрипты (например, `smb-enum-shares`) могут работать с Null Session, но для получения полного списка ресурсов или проверки прав записи может потребоваться передача учетных данных. Аргументы `smbusername`, `smbpassword`, `smbhash` позволяют передать данные аутентификации. Также важно использовать аргумент `smbnoguest` для ускорения сканирования, если известно, что гостевой доступ отключен.

Для HTTP-скриптов важным аспектом является настройка пользовательского агента (User-Agent) и обработка редиректов. Некоторые скрипты могут не работать корректно, если веб-сервер требует специфический User-Agent или блокирует запросы от Nmap. Аргумент `http.useragent` позволяет изменить этот параметр. Также стоит учитывать, что HTTP-скрипты могут быть медленными из-за необходимости ожидания полных ответов сервера.

Примеры команд для применения:

```bash
# Проверка SMB на наличие уязвимостей и перечисление ресурсов
# Использует категории safe и vuln, проверяет порты 445 и 139
nmap -p 445,139 --script smb-protocols,smb-security-mode,smb-os-discovery,smb-vuln-ms17-010 <target>

# Проверка HTTP на поддержку опасных методов и перечисление путей
# Использует категорию safe и discovery, проверяет порт 80
nmap -p 80 --script http-methods,http-enum,http-headers <target>

# Проверка SMB с передачей учетных данных (если известны)
nmap -p 445 --script smb-enum-shares,smb-enum-users --script-args smbusername=admin,smbpassword=pass <target>
```

Типичные ошибки при использовании NSE-скриптов:
1.  **Игнорирование времени выполнения:** Некоторые скрипты (например, `http-enum` с большим wordlist) могут выполняться часами. Необходимо использовать аргумент `--max-retries` и `--min-rate` для контроля скорости.
2.  **Неправильная интерпретация результатов:** Код ответа 200 OK не всегда означает уязвимость. Например, `http-methods` может показать поддержку PUT, но если сервер требует аутентификации, это не критично.
3.  **Пропуск SMBv1:** Не все скрипты автоматически проверяют SMBv1. Необходимо явно запускать `smb-protocols` для выявления этого диалекта.
4.  **Неучет контекста сети:** SMB-скрипты могут не работать за NAT или межсетевыми экранами, которые блокируют SMB-трафик. HTTP-скрипты могут не работать, если целевой сервер использует WAF (Web Application Firewall), который блокирует запросы от Nmap.

## Сквозной практический пример: Аудит уязвимостей SMB и HTTP на тестовом стенде

**Исходные условия:**
*   **Среда:** Локальная виртуальная машина с Windows Server 2012 R2 (уязвимый к EternalBlue, SMBv1 включен) и веб-сервером Apache Tomcat 8.5 (открытые методы, устаревший сертификат).
*   **Инструменты:** Nmap 7.94, скрипты NSE из стандартной поставки.
*   **Роль:** Пентестер, выполняющий начальную разведку.
*   **Цель:** Выявить уязвимости SMB и HTTP для последующей эксплуатации.

**Шаг 1: Сканирование SMB на наличие уязвимости MS17-010 и определение версии протокола**

Действие: Запуск скриптов `smb-protocols` и `smb-vuln-ms17-010` на порт 445.

```bash
nmap -p 445 --script smb-protocols,smb-vuln-ms17-010 192.168.1.100
```

Эти данные могут быть использованы для дальнейшей эксплуатации: например, использование EternalBlue для получения RCE или использование открытой шары `Public` для загрузки вредоносного файла.

## Аналитический вывод

NSE-скрипты для SMB и HTTP представляют собой мощный инструмент для начального этапа тестирования на проникновение, позволяющий автоматизировать обнаружение известных уязвимостей и ошибок конфигурации. Ключевое преимущество NSE заключается в интеграции с процессом сканирования: один инструмент может выполнить как обнаружение служб, так и проверку уязвимостей, что экономит время и упрощает рабочий процесс. Однако, скрипты NSE не являются заменой глубокого анализа уязвимостей или ручного тестирования. Они выявляют только известные паттерны и не могут обнаружить уязвимости нулевого дня или сложные логические ошибки в веб-приложениях.

Для SMB-скриптов критически важно учитывать версию протокола и настройку подписи сообщений. Наличие SMBv1 и отсутствие подписи являются критическими рисками, позволяющими атакующим использовать инструменты вроде Responder и EternalBlue. Для HTTP-скриптов важно понимать, что они проверяют конфигурацию веб-сервера, а не самого приложения. Уязвимости уровня приложения (SQLi, XSS) требуют использования специализированных инструментов (Burp Suite, SQLmap) и ручного тестирования.

Рекомендуется использовать NSE-скрипты как часть комплексного подхода: сначала выполнить сканирование портов и служб, затем применить NSE-скрипты для быстрой проверки известных уязвимостей, и наконец, использовать специализированные инструменты для глубокого анализа выявленных сервисов. Важно также учитывать контекст сети и политику безопасности организации, чтобы избежать непреднамеренного отказа в обслуживании или нарушения политик доступа.
