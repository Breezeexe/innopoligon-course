# Анализ отчёта GVM и приоритизация находок по CVSS

## Контекст и базовые понятия

Vulnerability Management (VM) — это непрерывный процесс выявления, оценки, обработки и мониторинга уязвимостей в ИТ-инфраструктуре. В отличие от разового аудита безопасности, VM интегрируется в жизненный цикл разработки и эксплуатации, обеспечивая постоянное снижение поверхности атаки. Ключевым инструментом в этом процессе выступают сканеры уязвимостей, среди которых Greenbone Vulnerability Management (GVM, ранее известный как OpenVAS) занимает особое место благодаря открытой архитектуре, обширной базе знаний (Greenbone Community Feed) и гибкой системе отчётности.

Основой для приоритизации находок в GVM служит система CVSS (Common Vulnerability Scoring System). CVSS — это отраслевой стандарт, разработанный Forum of Incident Response and Security Teams (FIRST), позволяющий количественно оценивать серьезность уязвимостей. Оценка базируется на трех группах метрик: базовых (inherent characteristics), временных (characteristics that change over time) и окружения (characteristics relevant to a specific user’s environment). В контексте GVM первичную роль играют базовые метрики, которые формируют базовый балл (Base Score) от 0.0 до 10.0.

Важно разграничивать понятия «уязвимость», «CVE» и «CVSS». CVE (Common Vulnerabilities and Exposures) — это уникальный идентификатор, предоставляемый организацией MITRE, который служит справочным номером. Сам по себе CVE не содержит информации о степени опасности. CVSS — это система оценки, которая присваивает этому идентификатору числовое значение. GVM сопоставляет обнаруженные несоответствия конфигурации или версий ПО с записями в своей базе NVT (Greenbone Network Vulnerability Tests), извлекая соответствующие CVSS-оценки из внешних источников (NVD, Red Hat, SUSE и др.).

Путаница часто возникает между понятиями «Severity» (Серьезность) и «Threat» (Угроза). В отчетах GVM эти термины могут использоваться в разных контекстах. Severity обычно ссылается на CVSS-балл, определенный стандартом. Threat (или Risk) в контексте GVM может учитывать дополнительные факторы, такие как доступность эксплойта в дикой природе (Exploitability), наличие патча или критичность самого актива. Однако в базовом PDF-отчете GVM приоритизация чаще всего опирается именно на CVSS-баллы, разделенные на категории: Critical (9.0–10.0), High (7.0–8.9), Medium (4.0–6.9), Low (0.1–3.9).

Для эффективного анализа отчета необходимо понимать структуру данных, генерируемых GVM. Отчет не является статичным текстом; это результат трансформации XML-данных, хранящихся в базе данных gvmd, с помощью XSLT-шаблонов. Понимание этой архитектуры позволяет не только читать отчет, но и автоматизировать его обработку через API или скрипты.

| Понятие | Определение | Роль в GVM | Источник данных |
| :--- | :--- | :--- | :--- |
| **CVE** | Уникальный идентификатор уязвимости. | Связующее звено между находкой сканера и базой знаний. | MITRE / NVD |
| **CVSS** | Система оценки серьезности (0.0–10.0). | Ключевой параметр для сортировки и фильтрации в отчете. | FIRST / NVD |
| **NVT** | Greenbone Network Vulnerability Test. | Скрипт (NASL/PB), который проверяет наличие уязвимости. | Greenbone Feed |
| **Severity** | Категория серьезности (Critical/High/Medium/Low). | Визуальная группировка в отчетах и интерфейсе GSAD. | Вычисляется из CVSS Base Score |
| **Threat** | Оценка вероятности эксплуатации. | Дополнительный индикатор в детальных отчетах. | Exploit-DB, CISA KEV, данные GVM |

Структура отчета GVM включает несколько уровней детализации:
1.  **Резюме (Summary):** Общие статистические данные по сканированию (количество хостов, общее число уязвимостей, распределение по категориям).
2.  **Обзор результатов (Results Overview):** Сводная таблица по каждому хосту или сервису с указанием количества уязвимостей каждой категории.
3.  **Детальные отчеты:** Информация по каждой конкретной уязвимости, включая описание, решение (Solution), ссылки на CVE/CVSS, а также контекст (какой порт, какая версия ПО затронута).

Понимание того, как формируются эти данные, критично для аудитора. Ошибка в интерпретации CVSS-балла может привести к неверной приоритизации: например, игнорирование уязвимости с баллом 7.5 (High) на публичном веб-сервере против уязвимости с баллом 9.8 (Critical) на внутреннем сервере домена требует не просто сравнения цифр, а понимания контекста, который должен быть извлечен из полного отчета.

## Внутреннее устройство предмета

Внутреннее устройство процесса анализа отчета GVM и работы с CVSS требует понимания архитектуры данных, механизмов вычисления оценок и структуры самого отчета. GVM состоит из нескольких компонентов: `openvas-scanner` (выполняет проверки), `gvmd` (менеджер данных, хранит результаты в PostgreSQL) и `gsad` (веб-сервер, предоставляющий интерфейс GSAD). Отчет генерируется компонентом `gvmd` на основе XML-представления данных.

### Архитектура данных и генерация отчета

Данные в GVM хранятся в реляционной базе PostgreSQL. При завершении сканирования результаты сохраняются в виде дерева объектов: `Host` → `Port` → `Vulnerability` (NVT). Каждое событие уязвимости содержит метаданные, включая `severity`, `cvss_v2`, `cvss_v3`, `cve`, `bid`, `xref` и другие.

Генерация PDF-отчета происходит через процесс `generate`, который является скриптом (обычно на Python или Perl), вызывающим XSLT-преобразование. Исходным файлом является `report.xml` (или `report-start.xml` для агрегированных данных). XSLT-файлы, такие как `latex.xsl`, определяют, как поля XML транслируются в LaTeX-код, который затем компилируется в PDF.

```xml
<!-- Иллюстративная структура XML-элемента уязвимости в gvmd -->
<vulnerability id="nvts/CVE-2023-XXXX" severity="7.5" type="vuln">
    <name>CVE-2023-XXXX</name>
    <description>...</description>
    <solution>...</solution>
    <cvss_v3_vector>CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H</cvss_v3_vector>
    <cve>CVE-2023-XXXX</cve>
    <refs>
        <ref href="https://nvd.nist.gov/vuln/detail/CVE-2023-XXXX" type="cve"/>
    </refs>
    <detection>
        <detail>
            <name>installed_software</name>
            <value>Apache httpd 2.4.49</value>
        </detail>
    </detection>
</vulnerability>
```

### Механизм вычисления CVSS в GVM

GVM не вычисляет CVSS самостоятельно в реальном времени для каждой находки. Вместо этого он извлекает готовые метрики из Greenbone Feed. Feed обновляется ежедневно и содержит NVT-скрипты, которые при обнаружении несоответствия (например, неверной версии ПО) возвращают метаданные, включая CVSS-вектор.

CVSS v3.1 (и v3.0) использует три группы метрик:

1.  **Base Metrics (Базовые):** Оценивают ингерентные свойства уязвимости.
    *   *Attack Vector (AV):* Network (N), Adjacent (A), Local (L), Physical (P).
    *   *Attack Complexity (AC):* Low (L), High (H).
    *   *Privileges Required (PR):* None (N), Low (L), High (H).
    *   *User Interaction (UI):* None (N), Required (R).
    *   *Scope (S):* Unchanged (U), Changed (C).
    *   *Confidentiality (C), Integrity (I), Availability (A):* None (N), Low (L), High (H).
2.  **Temporal Metrics (Временные):** Учитывают факторы, меняющиеся со временем (например, наличие эксплойта, доступность патча). В GVM эти метрики часто не заполняются полностью, так как зависят от внешних источников, которые не всегда актуальны в момент сканирования.
3.  **Environmental Metrics (Окружения):** Позволяют адаптеру (пользователю) скорректировать оценку под свою инфраструктуру. В стандартном отчете GVM эти метрики обычно игнорируются, если пользователь не настроил их вручную в GSAD.

Базовый балл вычисляется по сложной формуле, учитывающей влияние Scope (S). Если Scope меняется (S:C), влияние на Confidentiality, Integrity и Availability усиливается.

| Метрика CVSS v3.1 | Значения | Влияние на балл |
| :--- | :--- | :--- |
| **AV** | N, A, L, P | N (наибольшее) → P (наименьшее) |
| **AC** | L, H | L > H |
| **PR** | N, L, H | N > L > H |
| **UI** | N, R | N > R |
| **S** | U, C | C усиливает Impact |
| **C/I/A** | N, L, H | H > L > N |

### Структура отчета GVM и интерпретация полей

Отчет GVM состоит из нескольких разделов. Ключевым для приоритизации является раздел **Results Overview**. Он содержит таблицу, где строки — это хосты или сервисы, а столбцы — количество уязвимостей по категориям (Critical, High, Medium, Low, Log, Info).

Важно отметить, что GVM также использует понятие **Threat Level** (Уровень угрозы), который может отличаться от CVSS Severity. Threat Level учитывает:
*   Наличие активного эксплойта (Exploit Available).
*   Статус уязвимости в CISA KEV (Known Exploited Vulnerabilities).
*   Критичность актива (если настроено).

В детальных отчетах каждая уязвимость имеет поле **Solution** (Решение). Качество решения критично для аудита. Решения могут быть:
*   *Vendor Fix:* Официальный патч.
*   *Workaround:* Временное обходное решение.
*   *No Fix:* Уязвимость не может быть устранена, требуется компенсация.
*   *Will Not Fix:* Разработчик не планирует исправление.

Анализ отчета должен включать проверку на дубликаты. Один и тот же CVE может быть обнаружен через разные NVT (например, через проверку версии ПО и через проверку заголовков HTTP). GVM группирует их, но аудитор должен убедиться, что устранение одной причины устраняет все связанные находки.

## Применение и работа с предметом

На практике анализ отчета GVM и приоритизация находок требуют не только чтения PDF, но и работы с данными через API или командную строку `gvmd`. Это позволяет автоматизировать процесс, интегрировать результаты в системы тикетинга (Jira, ServiceNow) и проводить глубокий анализ.

### Работа с данными через GVM CLI и API

Для анализа отчета в программистском контексте используется `gvmd`. Команды позволяют экспортировать данные в XML или JSON, что удобнее для обработки скриптами.

```bash
# Экспорт отчета в XML для конкретного ID отчета (например, 1)
gvmd --get-report=1 --format=xml > report.xml

# Получение списка уязвимостей с высоким баллом (пример логики фильтрации)
# В реальном сценарии используется парсинг XML через Python или XSLT
```

Для автоматизации часто используется REST API GVM. Это позволяет получать данные в формате JSON, который легче обрабатывать в современных пайплайнах DevSecOps.

```json
{
  "report": {
    "id": "1",
    "name": "Weekly Scan Report",
    "results": [
      {
        "id": "00000000-0000-0000-0000-000000000001",
        "host": "192.168.1.10",
        "port": "443/tcp",
        "severity": "7.5",
        "cvss_v3": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N",
        "name": "CVE-2023-1234",
        "solution": "Update to version 1.2.3",
        "refs": [
          {
            "href": "https://nvd.nist.gov/vuln/detail/CVE-2023-1234",
            "type": "cve"
          }
        ]
      }
    ]
  }
}
```

### Приоритизация находок: за пределами CVSS

Хотя CVSS является стандартом, он имеет ограничения. Он не учитывает контекст инфраструктуры. Аудитор должен применять методологию **Risk-Based Prioritization**.

1.  **Контекст актива:** Уязвимость с баллом 5.0 (Medium) на сервере, хранящем персональные данные (PII), может быть приоритетнее уязвимости с баллом 7.5 (High) на тестовом стенде, отключенном от сети.
2.  **Эксплуатируемость:** Если уязвимость есть в CISA KEV или имеет публичный эксплойт (EPSS > 0.5), её приоритет резко возрастает, даже если CVSS средний.
3.  **Сложность устранения:** Уязвимости, требующие перезагрузки сервиса или сложного изменения конфигурации, могут откладываться, если они не критичны, чтобы избежать простоев.

### Типичные ошибки при анализе

*   **Игнорирование False Positives:** GVM может ошибочно определить версию ПО. Необходимо верифицировать находки вручную или через дополнительные проверки.
*   **Слепое доверие CVSS:** Балл 9.8 не гарантирует успешной эксплуатации. Если уязвимость требует локального доступа, а вектор атаки — удаленный, её реальная опасность ниже.
*   **Отсутствие приоритизации по времени:** Уязвимости, появившиеся недавно, могут быть менее приоритетными, чем старые, но давно известные, если для последних уже есть массовые атаки.

### Инструментарий и интеграция

Для анализа отчета GVM используются следующие инструменты:
*   **Greenbone Security Assistant (GSAD):** Веб-интерфейс для визуального анализа.
*   **gvmd:** CLI-инструмент для управления данными.
*   **Faraday:** Платформа для управления результатами сканирования, поддерживает импорт GVM.
*   **Custom Scripts (Python/Bash):** Для парсинга XML/JSON и создания кастомных отчетов.

```bash
# Пример команды для экспорта в формат, совместимый с Faraday
gvmd --get-report=1 --format=xml | faraday-manager import --format=gvm
```

## Сквозной практический пример: Приоритизация находок в отчете GVM

**Исходные условия:**
*   **Среда:** Корпоративная сеть с веб-сервером Apache на Ubuntu 20.04.
*   **Инструменты:** Greenbone Vulnerability Management (GVM) 22.4, gsad, gvmd.
*   **Роль:** Аудитор информационной безопасности.
*   **Сценарий:** Проведено сканирование веб-сервера. Получен отчет. Необходимо определить приоритет устранения находок.

**Шаг 1: Получение и анализ структуры отчета**

Аудитор загружает отчет в формате XML для программной обработки.

```bash
# Получение ID отчета (например, 5) и экспорт в XML
gvmd --get-report=5 --format=xml > scan_report.xml
```

**Шаг 2: Извлечение критических уязвимостей**

Аудитор использует `xsltproc` или Python-скрипт для извлечения уязвимостей с CVSS >= 7.0.

```xml
<!-- Фрагмент scan_report.xml, иллюстративная схема -->
<vulnerability id="nvts/CVE-2021-41773" severity="9.8" type="vuln">
    <name>CVE-2021-41773</name>
    <description>Path Traversal in Apache HTTP Server</description>
    <cvss_v3_vector>CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H</cvss_v3_vector>
    <detection>
        <detail>
            <name>installed_software</name>
            <value>Apache httpd 2.4.49</value>
        </detail>
    </detection>
    <solution>Update to version 2.4.50 or later.</solution>
</vulnerability>
```

**Шаг 3: Оценка контекста и эксплойта**

Аудитор проверяет наличие эксплойта для CVE-2021-41773.

```bash
# Проверка через API NVD или локальную базу (иллюстративная команда)
curl -s "https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2021-41773" | jq '.vulnerabilities[0].metrics.cvssMetricV31[0].cvssData.baseScore'
# Вывод: 9.8
```

**Шаг 4: Сравнение с другими находками**

На сервере также найдена уязвимость CVE-2023-XXXX с CVSS 5.3.

```xml
<!-- Иллюстративная схема сравнения -->
| CVE | CVSS Base | Vector | Context | Priority |
| :--- | :--- | :--- | :--- | :--- |
| CVE-2021-41773 | 9.8 | AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H | Публичный веб-сервер, есть эксплойт | **Critical** |
| CVE-2023-XXXX | 5.3 | AV:L/AC:H/PR:L/UI:N/S:U/C:L/I:N/A:N | Локальная, высокая сложность | **Low** |
```

**Шаг 5: Формирование рекомендации**

На основе анализа аудитор формирует тикет для ИТ-отдела.

```json
{
  "ticket_priority": "P1",
  "vulnerability": "CVE-2021-41773",
  "reason": "High CVSS (9.8) + Public Exploit + Web-Facing Service",
  "action": "Upgrade Apache to 2.4.50+",
  "deadline": "24 hours"
}
```

**Ожидаемый вывод:**
Пример демонстрирует, что анализ отчета GVM выходит за рамки простого чтения баллов. Ключевым является сопоставление CVSS-вектора с контекстом (публичный доступ, наличие эксплойта). В данном случае уязвимость с CVSS 9.8 требует немедленного устранения, в то время как уязвимость с CVSS 5.3 может быть отложена.

## Аналитический вывод

Анализ отчета GVM и приоритизация находок по CVSS требуют глубокого понимания как технической структуры данных сканера, так и методологии оценки рисков. CVSS v3.1 предоставляет стандартизированный и объективный базис для оценки серьезности уязвимостей, однако его ограничения (игнорирование контекста инфраструктуры) делают его недостаточным для принятия окончательных решений. Эффективный аудит безопасности интегрирует данные GVM с внешними источниками (CISA KEV, Exploit-DB) и внутренними политиками (критичность активов).

Ключевым аспектом работы с GVM является понимание архитектуры генерации отчетов (XML → XSLT → PDF), что позволяет автоматизировать обработку данных через API и CLI. Это критично для масштабирования процессов управления уязвимостями в крупных организациях. Приоритизация должна быть риск-ориентированной: уязвимости с высоким CVSS, но низким риском эксплуатации (например, требующие физического доступа) могут уступать по приоритету уязвимостям со средним CVSS, но наличием активных эксплойтов в дикой природе.

Студентам и практикам следует избегать механического подхода к чтению отчетов. Необходимо верифицировать false positives, анализировать векторы атаки (AV, AC, PR) и учитывать сложность устранения. Интеграция результатов GVM в системы тикетинга и мониторинга обеспечивает непрерывность процесса управления уязвимостями, превращая разовые сканирования в часть стратегии кибербезопасности.
