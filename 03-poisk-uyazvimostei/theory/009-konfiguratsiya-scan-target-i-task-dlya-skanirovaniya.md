# Конфигурация scan target и task в Greenbone Vulnerability Manager (OpenVAS)

## Контекст и базовые понятия

Greenbone Vulnerability Manager (GVM), исторически известный как OpenVAS, представляет собой комплексную платформу для управления уязвимостями (Vulnerability Management), а не просто одиночный сканер. Платформа состоит из нескольких взаимодействующих компонентов: Greenbone Security Assistant (GSA) — веб-интерфейс, Greenbone Vulnerability Manager Daemon (gvmd) — центральный сервис управления, ospd-openvas — движок сканирования, и базы данных (PostgreSQL, Redis). В контексте тестирования на проникновение и аудита безопасности ключевыми сущностями для запуска проверки являются **Scan Target** (Цель сканирования) и **Task** (Задача).

**Scan Target** — это логическая сущность, определяющая, *что* именно будет сканироваться. Она содержит сетевые адреса (IP-диапазоны, подсети CIDR, отдельные хосты), параметры аутентификации (для проверки конфигураций и локальных уязвимостей) и настройки сети (порты, протоколы). Target не содержит информации о том, *как* сканировать (какие скрипты использовать, с какой интенсивностью).

**Task** — это исполняемая единица работы. Она связывает конкретный Target с конкретной **Scan Config** (Конфигурацией сканирования). Task определяет параметры выполнения: расписание, приоритет, уведомления, а также технические параметры самого процесса (таймауты, количество параллельных потоков, политика сканирования). Запуск Task инициирует процесс: gvmd делегирует работу ospd-openvas, который обращается к целевым хостам.

Частая ошибка студентов и начинающих специалистов — путаница между Target и Config. Target отвечает за геометрию сети и доступ, Config — за методологию проверки (например, «Полное сканирование», «Только критические CVE», «Сканирование портов»). Одна и та же цель может быть проверена разными задачами с разными конфигурациями.

Разграничение сущностей в архитектуре GVM:

| Сущность | Назначение | Ключевые параметры | Аналогия в CI/CD |
|---|---|---|---|
| **Scan Target** | Определение объекта воздействия | IP/CIDR, имя хоста, порты, аутентификация, настройки сети (NAT, сканирование хоста) | Инфраструктура / Серверная группа |
| **Scan Config** | Определение методологии проверки | ID конфигурации (Full and fast, Deep Analysis, и т.д.), приоритет скриптов, таймауты | Pipeline / Job Definition |
| **Task** | Исполнение проверки | Связка Target + Config, расписание, статус, уведомления, параметры выполнения (max_checks, max_hosts) | Запуск пайплайна (Build Run) |
| **Report** | Результат выполнения | Список уязвимостей, severity, CVSS, доказательства (proof), рекомендации | Отчет о тестировании |

Понимание этого разделения критично: изменение Target не влияет на уже созданные Tasks (если они не привязаны динамически, что в GVM по умолчанию не является стандартным поведением без внешних скриптов), но изменение Config может кардинально изменить результаты всех связанных Tasks.

## Внутреннее устройство Scan Target

Scan Target в GVM — это структурированный объект, описывающий сетевую зону или конкретный хост. Его внутреннее устройство включает несколько слоев: сетевую спецификацию, параметры аутентификации и параметры сетевого взаимодействия.

### 1. Сетевая спецификация (Hosts)

Ядро Target — это список хостов. GVM поддерживает несколько форматов указания хостов:
*   **Single Host:** `192.168.1.10`
*   **CIDR Notation:** `192.168.1.0/24` (поддержка IPv4 и IPv6)
*   **Hostname:** `example.com` (разрешается в IP на момент создания Target или в момент сканирования, в зависимости от версии и настроек DNS)
*   **Port Ranges:** `192.168.1.0/24:80,443` (сканирование только указанных портов)
*   **Exclude Hosts:** `192.168.1.0/24!192.168.1.254` (исключение конкретного хоста из диапазона)

Важно: GVM не проверяет доступность хоста при создании Target. Ошибки в CIDR (например, `192.168.1.0/33`) или недоступные хосты обнаруживаются только на этапе выполнения Task, что может привести к длительным таймаутам или ошибкам.

### 2. Аутентификация (Authentications)

Для выявления конфигурационных уязвимостей, проверки паролей и локальных проверок (через агенты или SSH) Target требует указания учетных данных. В GVM аутентификация хранится отдельно и привязывается к Target через ссылку.

Типы аутентификации:
*   **SSH Key/Password:** Для Linux/Unix систем.
*   **SNMP Community String:** Для сетевого оборудования (роутеры, коммутаторы, принтеры).
*   **VMware vCenter Credentials:** Для сканирования виртуальных машин через API vSphere.
*   **SSL Certificate:** Для проверки конфигурации TLS.
*   **Local Agent (Greenbone Agent):** Для глубокого сканирования Windows/Linux без необходимости открытия портов.

### 3. Параметры сети (Network Settings)

Этот раздел определяет, *как* сканер взаимодействует с целью. Ключевые поля:
*   **Port Range:** Диапазон сканируемых портов (по умолчанию `1-65535`). Сужение диапазона ускоряет сканирование.
*   **Reverse Lookup:** Выполнять обратное DNS-разрешение IP-адресов. Отключение ускоряет сканирование в сетях с медленным или недоступным DNS.
*   **Hosts Reachable Via:** Выбор метода обнаружения хостов (ARP, ICMP, TCP SYN, None).
*   **Scan Hosts Alive:** Метод определения живых хостов (ICMP Ping, ARP Ping, TCP SYN Ping на порт 80/443).
*   **NAT Gateway:** Если сканирование идет через NAT, здесь указывается шлюз для корректной маршрутизации ответов.

### Структурная визуализация Target

Ниже представлена логическая структура объекта Target в базе данных gvmd (упрощенная схема связей):

```text
[Target ID: uuid]
├── Name: "Test Network Segment"
├── Comment: "Для аудита веб-серверов"
├── Hosts:
│   ├── "10.0.0.0/24"
│   └── "10.0.1.50"
├── Ports: "22,80,443,8080"
├── Authentications:
│   ├── [Auth ID: uuid] -> Type: SSH
│   │   ├── Host: "10.0.0.0/24"
│   │   ├── Port: 22
│   │   ├── Username: "admin"
│   │   └── Password/Key: <ref>
│   └── [Auth ID: uuid] -> Type: SNMP
│       ├── Host: "10.0.0.1"
│       ├── Community: "public"
│       └── Version: v2c
├── Settings:
│   ├── Reverse Lookup: "on"
│   ├── Hosts Reachable Via: "arp"
│   └── Port Range: "1-65535"
```

### Типичные ошибки конфигурации Target

1.  **Неверная маска подсети:** Использование `/24` вместо `/16` или наоборот. Это приводит к сканированию нецелевых сетей или пропуску хостов.
2.  **Отсутствие аутентификации для нужных хостов:** Попытка сканировать Windows-хосты без указания SMB-аутентификации или SSH для Linux без ключей.
3.  **Конфликт портов:** Указание портов, которые не соответствуют реально открытым сервисам, может привести к ложноотрицательным результатам (False Negatives), если скрипты GVM не могут установить соединение.
4.  **Игнорирование NAT:** При сканировании из внешней сети во внутреннюю без указания NAT-шлюза ответы могут не дойти до сканера.

## Внутреннее устройство Task

Task — это исполнительный механизм. Он не хранит данные о целях или методах напрямую, а ссылается на них. Task определяет *когда*, *как долго* и *с какими ресурсами* будет выполняться сканирование.

### 1. Связи (References)

Task содержит ссылки на:
*   **Target:** UUID цели.
*   **Config:** UUID конфигурации сканирования (например, `085569ce-73ed-11df-a475-002264764cea` — Full and fast).
*   **Observer:** Пользователь, ответственный за задачу.
*   **Alerts:** Настройки уведомлений (email, SNMP trap) при завершении или обнаружении критических уязвимостей.

### 2. Параметры выполнения (Settings)

Внутри Task настраиваются параметры, влияющие на производительность и точность:
*   **Max Concurrent Scans:** Количество одновременных сканируемых целей.
*   **Max Checks:** Количество параллельных проверок на один хост.
*   **Max Scans:** Общее количество параллельных задач.
*   **Scan Priority:** Приоритет задачи (от -128 до 127). Влияет на распределение ресурсов CPU/RAM.
*   **In Progress:** Статус задачи (New, Running, Stopped, Done, Failed).
*   **Schedule:** Расписание (Cron-подобное или одноразовое).

### 3. Жизненный цикл Task

1.  **New:** Задача создана, но не запущена.
2.  **Running:** Сканер активно взаимодействует с целями.
3.  **Stopped:** Задача остановлена вручную или из-за ошибки.
4.  **Done:** Сканирование завершено успешно.
5.  **Failed:** Сканирование завершилось с ошибкой (сетевая ошибка, таймаут, ошибка конфигурации).

### Сравнительная таблица параметров Task

| Параметр | Описание | Влияние на результат |
|---|---|---|
| **Config ID** | Методология проверки | Определяет, какие уязвимости будут найдены (например, Deep Analysis найдет больше, но медленнее) |
| **Target ID** | Объект сканирования | Определяет, какие хосты и порты будут проверены |
| **Max Checks** | Параллельность проверок | Высокое значение ускоряет сканирование, но может вызвать перегрузку цели или сканера |
| **Max Hosts** | Параллельность хостов | Высокое значение увеличивает нагрузку на сеть и сканер |
| **Schedule** | Время выполнения | Позволяет проводить сканирование в нерабочие часы для минимизации влияния на бизнес-процессы |
| **Alerts** | Уведомления | Не влияет на сканирование, но обеспечивает оперативное реагирование на результаты |

## Применение и работа с предметом

На практике работа с Target и Task в GVM осуществляется через веб-интерфейс GSA или через командную строку с помощью утилиты `omp` (OpenVAS Management Protocol). Для студентов и специалистов по безопасности важно уметь работать с обоими методами, так как автоматизация пентеста часто требует CLI.

### 1. Создание Target через CLI (omp)

Команда `omp` позволяет создавать Target программно. Это критично для интеграции GVM в CI/CD пайплайны или скрипты автоматизации.

Пример создания Target с аутентификацией SSH:

```bash
# Создаем Target с именем "Web Servers" и диапазоном 192.168.1.0/24
# Примечание: В реальном сценарии ID аутентификации нужно получить заранее через 'omp --get-authentications'
omp -u admin -w password -h 127.0.0.1 -p 9390 \
  --create-target="Web Servers" \
  "hosts=192.168.1.0/24; port=22,80,443; auth=ssh_auth_id_here"
```

### 2. Создание Task через CLI

После создания Target и выбора Config, создается Task.

```bash
# Создаем Task, связывающую Target и Config
# ID Target и Config должны быть известны
omp -u admin -w password -h 127.0.0.1 -p 9390 \
  --create-task="Initial Scan" \
  "target=target_id_here; config=config_id_here; max_checks=10; max_hosts=5"
```

### 3. Запуск и мониторинг Task

Задача запускается командой `start-task`. Мониторинг осуществляется через `get-tasks`.

```bash
# Запуск задачи
omp -u admin -w password -h 127.0.0.1 -p 9390 \
  --start-task=task_id_here

# Проверка статуса
omp -u admin -w password -h 127.0.0.1 -p 9390 \
  --get-tasks=task_id_here
```

### 4. Типичные ошибки и подводные камни

*   **Устаревшие NVT:** Если Feed не обновлен, Task будет выполняться, но результаты будут неактуальны. Всегда проверяйте статус Feed в GSA.
*   **Недостаток ресурсов:** Запуск Task с высоким `max_checks` на слабом сервере приведет к зависанию `gvmd` или `ospd-openvas`.
*   **Блокировка фаерволом:** Если Target указывает на хост, который блокирует ICMP или порты сканирования, Task может завершиться с ошибкой или вернуть 0 результатов.
*   **Конфликт аутентификации:** Если Target содержит хосты с разными ОС, аутентификация должна быть настроена для каждого типа ОС отдельно.

## Сквозной практический пример: Сканирование тестовой сети с аутентификацией

**Исходные условия:**
*   **Среда:** Kali Linux с установленным GVM (через Docker или пакет).
*   **Цель:** Сканирование подсети `192.168.50.0/24` на наличие уязвимостей.
*   **Инструменты:** GSA (веб-интерфейс), `omp` (CLI).
*   **Роль:** Специалист по аудиту безопасности.
*   **Сценарий:** Создание Target с SSH-аутентификацией для Linux-хостов, создание Task с конфигурацией "Full and fast", запуск и проверка статуса.

### Шаг 1: Подготовка аутентификации

Перед созданием Target необходимо создать учетные данные для SSH. В GSA это делается в разделе Configuration -> Authentications. Для CLI используем `omp`.

```bash
# Создаем аутентификацию SSH для пользователя 'admin' с паролем 'password123'
# ID аутентификации будет возвращен в ответе
omp -u admin -w admin_password -h 127.0.0.1 -p 9390 \
  --create-auth="SSH Auth" \
  "auth_type=ssh; host=192.168.50.0/24; port=22; username=admin; password=password123"
```

**Ожидаемый вывод:**
```xml
<create_auth_response status="201" status_text="Created">
  <auth id="a1b2c3d4-e5f6-7890-abcd-ef1234567890">
    ...
  </auth>
</create_auth_response>
```
*Сохраните ID аутентификации `a1b2c3d4-e5f6-7890-abcd-ef1234567890`.*

### Шаг 2: Создание Scan Target

Создаем Target, привязывая к нему аутентификацию и указывая диапазон хостов.

```bash
# Создаем Target с именем "Test Network"
# Используем сохраненный ID аутентификации
omp -u admin -w admin_password -h 127.0.0.1 -p 9390 \
  --create-target="Test Network" \
  "hosts=192.168.50.0/24; port=22,80,443,8080; auth=a1b2c3d4-e5f6-7890-abcd-ef1234567890"
```

**Ожидаемый вывод:**
```xml
<create_target_response status="201" status_text="Created">
  <target id="b2c3d4e5-f6a7-8901-bcde-f12345678901">
    ...
  </target>
</create_target_response>
```
*Сохраните ID Target `b2c3d4e5-f6a7-8901-bcde-f12345678901`.*

### Шаг 3: Создание Scan Task

Создаем Task, связывающую Target с конфигурацией сканирования. Используем стандартную конфигурацию "Full and fast" (ID: `085569ce-73ed-11df-a475-002264764cea`).

```bash
# Создаем Task с именем "Initial Scan"
# Устанавливаем max_checks=10 для предотвращения перегрузки
omp -u admin -w admin_password -h 127.0.0.1 -p 9390 \
  --create-task="Initial Scan" \
  "target=b2c3d4e5-f6a7-8901-bcde-f12345678901; config=085569ce-73ed-11df-a475-002264764cea; max_checks=10"
```

**Ожидаемый вывод:**
```xml
<create_task_response status="201" status_text="Created">
  <task id="c3d4e5f6-a7b8-9012-cdef-123456789012">
    ...
  </task>
</create_task_response>
```
*Сохраните ID Task `c3d4e5f6-a7b8-9012-cdef-123456789012`.*

### Шаг 4: Запуск Task и мониторинг

Запускаем задачу и проверяем ее статус.

```bash
# Запуск задачи
omp -u admin -w admin_password -h 127.0.0.1 -p 9390 \
  --start-task=c3d4e5f6-a7b8-9012-cdef-123456789012

# Проверка статуса (повторять до получения статуса "Done")
omp -u admin -w admin_password -h 127.0.0.1 -p 9390 \
  --get-tasks=c3d4e5f6-a7b8-9012-cdef-123456789012
```

**Ожидаемый вывод (статус "Running"):**
```xml
<get_tasks_response>
  <task id="c3d4e5f6-a7b8-9012-cdef-123456789012">
    <status>Running</status>
    <progress>45</progress>
    ...
  </task>
</get_tasks_response>
```

**Ожидаемый вывод (статус "Done"):**
```xml
<get_tasks_response>
  <task id="c3d4e5f6-a7b8-9012-cdef-123456789012">
    <status>Done</status>
    <progress>100</progress>
    ...
  </task>
</get_tasks_response>
```

### Ожидаемый вывод

Пример демонстрирует полный цикл создания и запуска сканирования в GVM через CLI. Ключевые моменты:
1.  **Разделение сущностей:** Аутентификация, Target и Task создаются отдельно, что позволяет переиспользовать учетные данные и цели.
2.  **Параметризация:** Использование `max_checks` позволяет контролировать нагрузку на сканер.
3.  **Автоматизация:** CLI-интерфейс `omp` позволяет интегрировать сканирование в скрипты, что невозможно при работе только через веб-интерфейс.

## Аналитический вывод

Конфигурация Scan Target и Task в Greenbone Vulnerability Manager является фундаментальным аспектом профессионального аудита уязвимостей. Правильное разделение этих сущностей позволяет гибко управлять процессом сканирования, переиспользовать учетные данные и настраивать методологию проверки независимо от целевой инфраструктуры. Ключевыми факторами успешного сканирования являются корректная настройка сетевой спецификации Target (включая маски подсети и NAT), наличие необходимых аутентификаций для глубокой проверки и оптимизация параметров Task (max_checks, max_hosts) под ресурсы сканера. Использование CLI-инструмента `omp` для создания и управления задачами обеспечивает возможность автоматизации процессов сканирования, что критично для интеграции в CI/CD пайплайны и регулярного мониторинга безопасности. Ошибки в конфигурации Target (неверные IP, отсутствие аутентификации) и Task (недостаток ресурсов, устаревшие NVT) приводят к ложноотрицательным результатам или сбоям в работе сканера, что подчеркивает важность тщательной предварительной настройки и мониторинга.
