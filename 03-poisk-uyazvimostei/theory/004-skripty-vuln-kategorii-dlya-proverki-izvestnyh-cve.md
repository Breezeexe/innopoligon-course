# Скрипты уязвимостей NSE для проверки известных CVE: архитектура, применение и анализ

## Контекст и базовые понятия

Nmap Scripting Engine (NSE) представляет собой встроенный в сканер Nmap фреймворк, позволяющий расширить функциональность инструмента от простого обнаружения портов до глубокого анализа безопасности сервисов. Ключевым элементом этого расширения является категория скриптов `vuln`. В отличие от стандартных скриптов категории `default` или `safe`, которые собирают информацию о версиях ПО (banner grabbing) и базовых конфигурациях, скрипты `vuln` предназначены для прямой проверки наличия известных уязвимостей (CVE) или критических ошибок конфигурации.

Понимание разницы между категориями скриптов критически важно для специалиста по тестированию на проникновение. Ошибка в выборе категории может привести либо к пропуску уязвимости (если использовать только `safe` скрипты), либо к отказу в обслуживании (DoS) целевой системы (если использовать `intrusive` или `exploit` скрипты без необходимости).

Категория `vuln` объединяет скрипты, которые выполняют проверку на наличие конкретной уязвимости. Эти скрипты обычно не пытаются эксплуатировать уязвимость для получения доступа, а лишь констатируют факт её наличия, возвращая информацию о CVE, описании и ссылке на источник. Это делает их безопасными для использования в большинстве сред, хотя некоторые проверки могут быть ресурсоемкими.

Для наглядного разграничения сущностей в экосистеме NSE ниже приведена сравнительная таблица, фиксирующая ключевые различия между категориями скриптов, наиболее релевантными для задачи поиска уязвимостей.

| Категория | Уровень риска | Основная функция | Поведение при обнаружении уязвимости | Примеры использования |
| :--- | :--- | :--- | :--- | :--- |
| **default** | Низкий | Базовая эnumерация сервисов. | Не проверяет уязвимости. Возвращает версии ПО. | `http-default-accounts`, `ssl-enum-ciphers` |
| **safe** | Низкий | Неинтрузивные проверки. | Игнорирует потенциально опасные проверки. | `http-headers`, `dns-zone-transfer` |
| **vuln** | Низкий-Средний | Проверка на известные CVE и ошибки конфигурации. | Сообщает о наличии уязвимости, но не эксплуатирует её. | `http-vuln-cve-2021-41773`, `ssl-heartbleed` |
| **intrusive** | Высокий | Агрессивные проверки, способные повлиять на стабильность сервиса. | Может вызвать сбой сервиса или генерировать много логов. | `ftp-vsftpd-backdoor`, `smb-vuln-ms17-010` |
| **exploit** | Критический | Активная эксплуатация уязвимостей. | Пытается получить доступ или выполнить код. | `http-shellshock`, `smb-double-pulsar` |

Скрипты категории `vuln` часто являются гибридными: они могут иметь метки `safe` (если проверка не влияет на сервис) или `intrusive` (если проверка требует отправки большого объема данных). Понимание этой двойственной природы позволяет специалисту выбирать скрипты, балансируя между полнотой покрытия и риском для целевой инфраструктуры.

## Внутреннее устройство скриптов уязвимостей

NSE использует язык программирования Lua для написания скриптов. Каждый скрипт уязвимости (`vuln`) состоит из нескольких обязательных секций: `prerule`, `prerule_output`, `portrule`, `portoutput`, `action` и `hostrule`. Для скриптов проверки уязвимостей наиболее важными являются `portrule` и `action`.

`portrule` определяет, к каким портам и сервисам должен применяться скрипт. Обычно он проверяет результат службы (service name) и версию, полученные на этапе `version detection` (`-sV`). Если условия `portrule` не выполняются, скрипт пропускает этот порт, что экономит ресурсы.

`action` содержит основную логику проверки. В скриптах категории `vuln` эта функция обычно возвращает таблицу с полями `state` (обычно `VULNERABLE` или `NOT_VULNERABLE`), `desc` (описание уязвимости) и `extra` (дополнительные данные, такие как CVE ID).

Скрипты уязвимостей можно разделить на три подкласса по механизму действия:
1.  **Direct CVE Checkers:** Скрипты, которые содержат жестко закодированные проверки для конкретных CVE (например, `http-vuln-cve-2021-41773`). Они работают быстро, но требуют обновления при появлении новых уязвимостей.
2.  **Version-based Matchers:** Скрипты, которые сравнивают обнаруженную версию сервиса с базой данных уязвимых версий. Пример: `ssl-heartbleed`.
3.  **Database-driven Scanners:** Скрипты, которые загружают внешние базы данных (например, Vulscan или Nmap-vulners) и сопоставляют их с обнаруженными версиями. Эти скрипты более гибкие, но требуют больше времени на выполнение.

Ниже представлена структура данных, возвращаемая скриптом уязвимости в результатах сканирования Nmap.

```json
{
  "script_id": "http-vuln-cve-2021-41773",
  "output": {
    "state": "VULNERABLE",
    "description": "Apache HTTP Server 2.4.49 through 2.4.50 is vulnerable to path traversal and remote code execution.",
    "cve_ids": [
      "CVE-2021-41773",
      "CVE-2021-42013"
    ],
    "references": [
      "https://nvd.nist.gov/vuln/detail/CVE-2021-41773"
    ],
    "extra": {
      "path": "/cgi-bin/..%2f..%2f..%2f..%2fetc%2fpasswd",
      "method": "GET"
    }
  }
}
```

Важно отметить, что скрипты `vuln` не являются изолированными. Они часто зависят от результатов других скриптов. Например, скрипт `ssl-heartbleed` требует, чтобы скрипт `ssl-cert` уже выполнился и определил, что на порту запущен OpenSSL. Если `ssl-cert` не сработал, `ssl-heartbleed` может не выполниться или выдать ложноположительный результат. Это создает цепочку зависимостей, которую специалист должен учитывать при построении пайплайна сканирования.

## Применение и работа с предметом

На практике использование скриптов `vuln` требует понимания процесса обновления базы данных скриптов и управления параметрами выполнения. Nmap хранит метаданные всех скриптов в файле `script.db`. При добавлении новых скриптов или обновлении существующих необходимо синхронизировать эту базу данных.

Основная команда для обновления скриптов:
```bash
nmap --script-updatedb
```
Эта команда загружает последние версии скриптов из официального репозитория Nmap. Однако для сторонних скриптов (например, `vulscan` или `nmap-vulners`) обновление происходит вручную путем замены файлов `.nse` в директории `/usr/share/nmap/scripts/`.

При запуске сканирования уязвимостей критически важно использовать флаг `-sV` (version detection). Без него Nmap не сможет определить точную версию сервиса, что сделает невозможным выполнение большинства скриптов `vuln`, которые полагаются на сопоставление версий. Также рекомендуется использовать флаг `-p-` для сканирования всех портов, так как уязвимости могут находиться на нестандартных портах.

Фильтрация скриптов осуществляется через операторы Lua. Например, можно запустить только безопасные скрипты из категории `vuln`, чтобы минимизировать риск:
```bash
nmap -sV --script "vuln and safe" <TARGET_IP>
```
Или, наоборот, запустить все скрипты, включая агрессивные:
```bash
nmap -sV --script "vuln or intrusive" <TARGET_IP>
```

Типичная ошибка при работе со скриптами `vuln` — игнорирование контекста. Скрипт может сообщить об уязвимости, но не указать, является ли она критической в данной конкретной конфигурации. Например, уязвимость может требовать специфического заголовка HTTP или наличия определенного модуля, который не активирован. Поэтому результаты скриптов `vuln` всегда требуют верификации вручную или с помощью дополнительных инструментов.

## Сквозной практический пример: Проверка уязвимости Apache Log4j (CVE-2021-44228)

**Исходные условия:**
*   **Цель:** Виртуальная машина с установленным Apache Tomcat 9.0.50, слушающим порт 8080.
*   **Инструмент:** Nmap 7.92+ с установленными скриптами NSE.
*   **Роль:** Специалист по тестированию на проникновение.
*   **Сценарий:** Проверка наличия уязвимости Log4Shell в целевом сервисе.

**Шаг 1: Определение сервиса и версии**
Перед запуском скриптов уязвимостей необходимо убедиться, что Nmap правильно определил сервис.
```bash
nmap -sV -p 8080 192.168.1.105
```
*Ожидаемый вывод:*
```text
PORT     STATE SERVICE VERSION
8080/tcp open  http    Apache Tomcat 9.0.50
```

**Шаг 2: Запуск специализированного скрипта CVE**
Для проверки Log4Shell используется скрипт `http-vuln-cve-2021-44228`.
```bash
nmap -sV -p 8080 --script http-vuln-cve-2021-44228 192.168.1.105
```
*Ожидаемый вывод (при наличии уязвимости):*
```text
PORT     STATE SERVICE VERSION
8080/tcp open  http    Apache Tomcat 9.0.50
| http-vuln-cve-2021-44228:
|   VULNERABLE:
|   Apache Log4j2 JNDI in JARs allows Remote Code Execution.
|     State: VULNERABLE
|     IDs:  CVE:CVE-2021-44228
|     Description:
|       Apache Log4j2 versions 2.0-beta9 through 2.15.0 (excluding
|       2.12.3 and 2.16.0) are vulnerable to Remote Code Execution.
|     References:
|       https://nvd.nist.gov/vuln/detail/CVE-2021-44228
|       https://www.rapid7.com/blog/post/2021/12/10/cve-2021-44228-apache-log4j2-jndi-in-jar-rce/
|_
```

**Шаг 3: Использование скрипта Vulscan для расширенного поиска**
Если специализированный скрипт отсутствует, можно использовать `vulscan` с базой данных CVE.
```bash
nmap -sV -p 8080 --script vulscan/vulscan.nse --script-args vulscandb=cve.csv 192.168.1.105
```
*Ожидаемый вывод (фрагмент):*
```text
| vulscan:
|   CVE-2021-44228:
|     Description: Apache Log4j2 JNDI in JARs allows Remote Code Execution.
|     CVSS: 10.0
|     URL: https://nvd.nist.gov/vuln/detail/CVE-2021-44228
|_
```

**Ожидаемый вывод:**
Пример демонстрирует, как Nmap интегрирует информацию о версиях с базой данных уязвимостей. Скрипт `http-vuln-cve-2021-44228` предоставляет точную информацию о CVE, в то время как `vulscan` дает более общий обзор, включая оценку CVSS. Оба метода подтверждают наличие уязвимости, но первый более специфичен и быстрее.

## Аналитический вывод

Скрипты категории `vuln` в Nmap представляют собой мощный инструмент для автоматизированного обнаружения известных уязвимостей, однако их эффективность напрямую зависит от качества определения версий сервисов и актуальности базы данных скриптов. Использование встроенных скриптов обеспечивает высокую скорость и надежность для критических уязвимостей, таких как Log4Shell или Heartbleed, но оставляет пробелы для менее известных или новых CVE. Сторонние скрипты, такие как `vulscan` и `nmap-vulners`, расширяют покрытие за счет внешних баз данных, но требуют дополнительных ресурсов на выполнение и обновление.

Специалисту по тестированию на проникновение следует использовать скрипты `vuln` как первый этап в процессе оценки уязвимостей, а не как единственный источник истины. Результаты сканирования NSE должны всегда верифицироваться вручную или с помощью специализированных сканеров уязвимостей (например, Nessus или OpenVAS), которые могут проводить более глубокий анализ, включая аутентифицированное сканирование. Кроме того, важно учитывать контекст выполнения: скрипты `vuln` могут быть ложноположительными, если сервис использует нестандартные конфигурации или обфускацию версий.
