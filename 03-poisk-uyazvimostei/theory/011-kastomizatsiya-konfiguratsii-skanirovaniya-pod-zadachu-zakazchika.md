# Кастомизация конфигураций сканирования в Greenbone Vulnerability Manager (GVM)

## Контекст и базовые понятия

Greenbone Vulnerability Manager (GVM), ранее известный как OpenVAS, представляет собой полнофункциональный фреймворк для управления уязвимостями (Vulnerability Management). В отличие от простых сканеров портов (например, Nmap), которые определяют только открытые сервисы, GVM выполняет глубокую проверку на наличие известных уязвимостей (CVE), ошибок конфигурации и отсутствующих патчей, сопоставляя результаты с базой данных Network Vulnerability Tests (NVT). Исторически GVM является форком Nessus, что обуславливает схожесть архитектуры и логики работы, однако GVM полностью открыт и использует собственную экосистему обновлений (Greenbone Feed Services).

Ключевой проблемой при внедрении GVM в корпоративную среду является то, что «сканирование по умолчанию» редко соответствует требованиям заказчика. Стандартные профили (например, «Full and fast» или «Full and deep») либо генерируют избыточный объем ложноположительных срабатываний (False Positives), либо, наоборот, пропускают специфичные для бизнеса риски из-за ограничения времени выполнения или блокировок фаерволами. Кастомизация конфигурации сканирования — это процесс адаптации параметров задачи (Task) под конкретные технические и бизнес-ограничения заказчика.

Важно разграничивать три уровня кастомизации, которые часто путают:
1.  **Кастомизация списка портов (Port List):** Определение того, *куда* сканер будет подключаться. Это влияет на скорость и охват сетевой поверхности.
2.  **Кастомизация конфигурации сканирования (Scan Config):** Определение того, *какие проверки* (NVT) будут выполняться. Это влияет на глубину обнаружения уязвимостей.
3.  **Кастомизация целевой инфраструктуры (Target):** Определение того, *как* сканер взаимодействует с хостом (аутентификация, использование агентов, обход IDS/IPS).

Путаница между этими уровнями приводит к некорректным результатам: например, настройка агрессивных NVT на целевой системе, не поддерживающей соответствующие проверки, может вызвать отказ в обслуживании (DoS).

| Параметр кастомизации | Уровень воздействия | Влияние на результат сканирования | Типичные сценарии использования |
| :--- | :--- | :--- | :--- |
| **Port List** | Сетевой уровень (L3/L4) | Определяет время выполнения и вероятность обнаружения сервисов. Узкие списки ускоряют сканирование, но могут пропустить нестандартные сервисы. | Сканирование DMZ (только публичные порты), сканирование внутренних баз данных (только специфичные порты). |
| **Scan Config (NVT Selection)** | Уровень приложения/ОС | Определяет полноту отчета по уязвимостям. Включение всех NVT увеличивает риск нестабильности систем; исключение снижает полноту. | Соответствие стандартам (CIS, PCI DSS), сканирование критической инфраструктуры с ограничениями на нагрузку. |
| **Scan Config (Settings)** | Уровень взаимодействия | Влияет на надежность обнаружения и безопасность сканируемой системы. Агрессивные таймауты и интервалы могут быть восприняты как атака. | Сканирование через интернет (нужны большие таймауты), сканирование устаревшего оборудования (нужны малые интервалы). |
| **Target Auth/Agents** | Уровень хоста | Определяет точность проверки конфигурации и наличия патчей. Без аутентификации сканирование ограничивается внешним анализом. | Аудит Windows AD (SMB-аутентификация), аудит Linux (SSH-аутентификация), использование GMP-агентов для обхода файрволов. |

Разграничение между *конфигурацией сканирования* и *списком уязвимостей* также критично. В GVM нет возможности «добавить» новую уязвимость в базу данных без написания собственного плагина (NVT). Однако можно создать *кастомный список уязвимостей* (Custom Vulnerability List) внутри конфигурации сканирования, исключив из него известные ложноположительные проверки или проверки для несуществующих в данной среде сервисов. Это позволяет «очистить» отчет от шума, не меняя саму базу данных NVT.

## Внутреннее устройство конфигураций сканирования

Архитектура GVM построена на разделении ответственности между компонентами: `gvmd` (база данных и управление задачами), `openvas` (сам сканер, выполняющий проверки), `gsad` (веб-интерфейс) и `pgdg` (PostgreSQL). Конфигурация сканирования хранится в базе данных PostgreSQL в виде иерархической структуры объектов. Понимание этой структуры необходимо для программной или скриптовой кастомизации.

### Структура объекта Scan Config

Конфигурация сканирования в GVM — это не просто набор флагов, а сложный граф зависимостей. Базовая конфигурация (например, `Full and fast`) является родительской для других профилей. При создании кастомной конфигурации пользователь фактически создает новый объект, который наследует свойства родителя, но переопределяет ключевые параметры.

Структура конфигурации включает следующие обязательные компоненты:

1.  **NVT Selection (Список проверок):**
    *   Определяет, какие скрипты NASL (Nessus Attack Scripting Language) будут загружены в память сканера.
    *   Может быть задан как полный список (All NVTs), так и подмножество (Custom List).
    *   Подмножество формируется через создание нового «Vulnerability List» в интерфейсе, который содержит whitelist/blacklist OID'ов (Object Identifiers) скриптов.

2.  **Port List (Список портов):**
    *   Связан с конфигурацией на уровне задачи, но может быть привязан к профилю.
    *   Поддерживает форматы: `all_tcp`, `all_udp`, `nmap_top_100`, `custom`.
    *   Влияет на инициализацию сокетов сканера.

3.  **Performance and Throttling (Производительность и ограничение):**
    *   **Max Checks:** Максимальное количество параллельных проверок на один хост. По умолчанию часто равно 10. Увеличение этого значения ускоряет сканирование, но может вызвать перегрузку CPU целевой системы или сетевого оборудования.
    *   **Max Hosts:** Максимальное количество параллельно сканируемых хостов.
    *   **Port Range:** Диапазон портов для сканирования.
    *   **Hosts Alive Test:** Метод определения живости хоста (ICMP, TCP SYN на порт 445/139, ARP).

4.  **Scan Settings (Параметры взаимодействия):**
    *   **Timeout:** Время ожидания ответа от хоста перед повторной попыткой или переходом к следующему хосту.
    *   **Interval:** Задержка между отправкой пакетов. Критично для обхода IDS/IPS.
    *   **Do ARP Discovery:** Использовать ли ARP-сканирование для локальных сетей.
    *   **Reverse Address Lookup:** Выполнять ли обратное DNS-разрешение IP-адресов (часто отключается для ускорения).

### Механизм наследования и переопределения

GVM использует механизм прототипирования. Стандартные конфигурации (`Full and fast`, `Full and deep`, `Host Discovery`) являются шаблонами. При создании кастомной конфигурации через API или CLI (`gvmd`) создается новый объект с уникальным UUID.

Процесс кастомизации включает следующие шаги на уровне данных:
1.  Клонирование UUID родительской конфигурации.
2.  Создание нового объекта `vulnerability_list` (если требуется фильтрация NVT).
3.  Назначение нового `vulnerability_list` клонированной конфигурации.
4.  Обновление параметров `settings` (таймауты, порты) в объекте конфигурации.

Важно отметить, что изменения в конфигурации сканирования не влияют на уже запущенные задачи. Для применения кастомизации к существующей задаче необходимо либо создать новую задачу с новой конфигурацией, либо изменить конфигурацию задачи (если она не привязана к жесткому профилю).

### Взаимодействие с базой данных NVT

База данных NVT обновляется через Greenbone Feed Services (GFS). Каждый скрипт имеет уникальный OID (например, `1.3.6.1.4.1.25623.1.0.101734`). При кастомизации списка уязвимостей специалист работает именно с этими OID'ами.

| Элемент конфигурации | Тип данных | Описание | Влияние на сканирование |
| :--- | :--- | :--- | :--- |
| **NVT OID** | Строка (OID) | Уникальный идентификатор скрипта проверки. | Определяет конкретную проверяемую уязвимость. |
| **Vulnerability List** | Список OID | Whitelist/Blacklist OID'ов. | Фильтрует, какие проверки будут загружены в сканер. |
| **Port List UUID** | UUID | Идентификатор списка портов. | Определяет целевые конечные точки для подключения. |
| **Max Checks** | Integer | Количество параллельных потоков проверок. | Баланс между скоростью и стабильностью системы. |
| **Interval** | Integer (мс) | Задержка между пакетами. | Влияет на обнаружение IDS/IPS и нагрузку на сеть. |
| **Timeout** | Integer (сек) | Время ожидания ответа. | Влияет на полноту сканирования в нестабильных сетях. |

Для глубокой кастомизации, когда стандартные NVT не покрывают специфичные риски (например, внутренние проприетарные приложения), требуется создание собственных скриптов NASL. Однако это выходит за рамки простой кастомизации конфигурации и требует разработки плагина. В рамках кастомизации под задачу заказчика основной фокус делается на фильтрацию существующих NVT и настройку параметров производительности.

## Применение и работа с предметом

На практике кастомизация конфигураций GVM осуществляется через три основных интерфейса: Web UI (Greenbone Security Assistant), CLI (`gvmd`) и API (GMP — Greenbone Management Protocol). Для студентов и специалистов по тестированию на проникновение наиболее эффективен подход, сочетающий CLI для создания базовой структуры и Web UI для детальной настройки списков уязвимостей, либо полное использование GMP для автоматизации.

### Создание кастомной конфигурации через CLI

Команда `gvmd` является основным инструментом управления. Для создания кастомной конфигурации необходимо:
1.  Получить UUID существующей конфигурации (например, `Full and fast`).
2.  Создать новую конфигурацию на основе этого UUID.
3.  Создать новый список уязвимостей (если требуется фильтрация).
4.  Назначить список уязвимостей новой конфигурации.
5.  Обновить параметры конфигурации (таймауты, порты).

Пример создания кастомной конфигурации с использованием `gvmd`:

```bash
# 1. Получение UUID существующей конфигурации "Full and fast"
gvmd --getConfigs

# 2. Создание новой конфигурации на основе существующей
# Заменяем <UUID_FULL_AND_FAST> на реальный UUID из шага 1
gvmd --create-config --name="Custom Low Impact Scan" --copy=<UUID_FULL_AND_FAST>

# 3. Создание нового списка уязвимостей (пустой или с фильтрами)
# Сначала создаем список, затем добавляем в него NVT
gvmd --create-vulnerability-list --name="Custom NVT List"

# 4. Назначение списка уязвимостей конфигурации
# Заменяем <UUID_NEW_CONFIG> и <UUID_NEW_VULN_LIST> на реальные UUID
gvmd --modify-config --config=<UUID_NEW_CONFIG> --vulnerability-list=<UUID_NEW_VULN_LIST>

# 5. Настройка параметров производительности (через XML-структуру settings)
# Пример: установка max_checks=5, interval=1000ms
gvmd --modify-config --config=<UUID_NEW_CONFIG> --setting=0a06f2c0-0d36-11ea-9f22-28d24461215b=5
gvmd --modify-config --config=<UUID_NEW_CONFIG> --setting=0a06f2c0-0d36-11ea-9f22-28d24461215b=1000
```

*Примечание:* UUID настроек (`setting`) зависят от версии GVM. В GVM 22.04+ структура настроек может отличаться. Рекомендуется использовать `gvmd --get-settings` для получения актуальных UUID параметров.

### Кастомизация через Web UI

Web UI предоставляет более интуитивный интерфейс для работы со списками уязвимостей. Процесс включает:
1.  Переход в раздел **Scans > Configs**.
2.  Создание новой конфигурации через кнопку **New Config**.
3.  Выбор родительской конфигурации (например, `Full and fast`).
4.  Вкладка **NVT Selection**: здесь можно вручную выбрать или исключить конкретные NVT. Это полезно для исключения проверок, которые могут вызвать нестабильность (например, проверки на переполнение буфера в устаревших сервисах).
5.  Вкладка **Settings**: настройка таймаутов, интервалов, списков портов.

### Типичные ошибки и подводные камни

1.  **Игнорирование влияния на IDS/IPS:** Агрессивные настройки (высокий `max_checks`, низкий `interval`) часто триггерят IDS. Рекомендуется начинать с `interval=1000-5000` мс и постепенно снижать его, если время выполнения критично.
2.  **Неправильный выбор Port List:** Использование `All TCP` для сканирования через интернет может занять недели времени и привлечь внимание провайдера. Для внешних сканирований следует использовать `Nmap top 100` или кастомный список, основанный на данных `nmap` или `masscan`.
3.  **Отключение проверок живости хоста:** Отключение `Host Alive Test` может привести к сканированию недоступных хостов, что искусственно завышает время выполнения задачи. Рекомендуется использовать `TCP SYN` на порт 445 или 139 для обхода ICMP-блоков.
4.  **Некорректная аутентификация:** Настройка аутентификации в конфигурации сканирования не заменяет настройку аутентификации в цели (Target). Конфигурация определяет *как* сканировать, Target определяет *с какими правами* сканировать.

### Автоматизация через GMP API

Для интеграции с CI/CD пайплайнами или системами управления уязвимостями (VMS) используется GMP API. Пример создания задачи с кастомной конфигурацией через Python-библиотеку `gvm-tools`:

```python
from gvm.connections import TLSConnection
from gvm.protocols.gmp import Gmp

# Подключение к GVM
connection = TLSConnection(hostname="127.0.0.1", port=9390)
with Gmp(connection=connection) as gmp:
    # Аутентификация
    gmp.authenticate('admin', 'password')
    
    # Получение UUID кастомной конфигурации
    configs = gmp.get_configs()
    custom_config_id = None
    for config in configs.get_configs():
        if config.get('name') == 'Custom Low Impact Scan':
            custom_config_id = config.get('id')
            break
            
    # Создание задачи
    task_id = gmp.create_task(
        name='Automated Scan',
        config_id=custom_config_id,
        targets='192.168.1.0/24'
    )
    
    # Запуск задачи
    gmp.start_task(task_id)
```

Этот подход позволяет динамически создавать конфигурации под каждую задачу, что особенно важно при проведении регулярных аудитов.

## Сквозной практический пример: Кастомизация сканирования для PCI DSS

### Исходные условия
*   **Среда:** Greenbone Vulnerability Manager 22.04 (на базе Kali Linux).
*   **Роль:** Специалист по тестированию на проникновение.
*   **Задача:** Провести сканирование на соответствие требованиям PCI DSS (платежные карты) для веб-приложения, размещенного в DMZ.
*   **Ограничения:**
    *   Целевая система критична к нагрузке: нельзя превышать 5 параллельных проверок.
    *   Интервал между пакетами должен быть не менее 2 секунд для обхода WAF.
    *   Требуется исключить проверки, связанные с SMB (так как система Linux и SMB не используется), чтобы уменьшить шум.
    *   Требуется включить проверки на соответствие CIS Benchmarks.

### Шаги

#### Шаг 1: Создание кастомного списка уязвимостей (исключение SMB)

Сначала создаем список уязвимостей, который исключит все NVT, связанные с SMB. Это уменьшит объем данных и время сканирования.

```bash
# 1. Создаем новый список уязвимостей
gvmd --create-vulnerability-list --name="PCI DSS Excluded SMB"

# 2. Получаем OID'ы всех SMB-скриптов (иллюстративный запрос, в реальности используется grep по базе NVT)
# Предположим, мы нашли OID для SMB-скриптов: 1.3.6.1.4.1.25623.1.0.100001, 1.3.6.1.4.1.25623.1.0.100002
# Добавляем их в blacklist (в GVM 22.04+ используется структура XML для списков)

# 3. Создаем XML-файл для blacklist (smb_blacklist.xml)
cat > smb_blacklist.xml << EOF
<vulnerability_list>
  <vulnerability>
    <oid>1.3.6.1.4.1.25623.1.0.100001</oid>
    <action>exclude</action>
  </vulnerability>
  <vulnerability>
    <oid>1.3.6.1.4.1.25623.1.0.100002</oid>
    <action>exclude</action>
  </vulnerability>
</vulnerability_list>
EOF

# 4. Применяем список к конфигурации (предварительно создав конфигурацию на базе "Full and fast")
gvmd --create-config --name="PCI DSS Custom" --copy=$(gvmd --getConfigs | grep "Full and fast" | awk '{print $2}')
gvmd --modify-config --config=$(gvmd --getConfigs | grep "PCI DSS Custom" | awk '{print $2}') --vulnerability-list=$(gvmd --getVulnerabilityLists | grep "PCI DSS Excluded SMB" | awk '{print $2}')
```

#### Шаг 2: Настройка параметров производительности

Настройка таймаутов и интервалов для обхода WAF и снижения нагрузки.

```bash
# Получаем UUID новой конфигурации
CONFIG_UUID=$(gvmd --getConfigs | grep "PCI DSS Custom" | awk '{print $2}')

# Настройка max_checks=5
gvmd --modify-config --config=$CONFIG_UUID --setting=0a06f2c0-0d36-11ea-9f22-28d24461215b=5

# Настройка interval=2000ms (2 секунды)
# Примечание: UUID настройки interval может отличаться в разных версиях, проверяем через gvmd --get-settings
INTERVAL_UUID=$(gvmd --get-settings | grep "Interval" | awk '{print $2}')
gvmd --modify-config --config=$CONFIG_UUID --setting=$INTERVAL_UUID=2000

# Настройка timeout=30s
TIMEOUT_UUID=$(gvmd --get-settings | grep "Timeout" | awk '{print $2}')
gvmd --modify-config --config=$CONFIG_UUID --setting=$TIMEOUT_UUID=30
```

#### Шаг 3: Создание цели (Target) с аутентификацией

Для проверки CIS Benchmarks требуется аутентификация. Создаем цель с SSH-аутентификацией.

```bash
# Создание цели с SSH-аутентификацией
gvmd --create-target --name="PCI DSS Target" \
  --hosts="192.168.1.100" \
  --port-list=$(gvmd --getPortLists | grep "All IANA assigned TCP" | awk '{print $2}') \
  --ssh-credential="admin:password:22"
```

#### Шаг 4: Создание и запуск задачи

Создаем задачу, связывающую кастомную конфигурацию и цель.

```bash
# Создание задачи
TASK_UUID=$(gvmd --create-task --name="PCI DSS Scan" --config=$CONFIG_UUID --target=$TARGET_UUID)

# Запуск задачи
gvmd --start-task=$TASK_UUID
```

### Ожидаемый вывод

1.  **Созданная конфигурация** `PCI DSS Custom` содержит только NVT, исключая SMB-проверки.
2.  **Параметры сканирования** настроены на низкую нагрузку: 5 параллельных проверок, 2 секунды между пакетами.
3.  **Задача** запущена и использует SSH-аутентификацию для проверки CIS Benchmarks.
4.  **Результат:** Сканирование займет больше времени, чем стандартное, но не вызовет срабатывания WAF и не перегрузит целевую систему. Отчет будет содержать только релевантные для PCI DSS уязвимости.

## Аналитический вывод

Кастомизация конфигураций сканирования в Greenbone Vulnerability Manager является критическим этапом профессионального тестирования на проникновение. Стандартные профили, такие как `Full and fast`, оптимизированы для скорости и полноты, но не учитывают специфику корпоративных сред, таких как наличие IDS/IPS, критичность систем к нагрузке и специфичные требования соответствия (PCI DSS, HIPAA, GDPR).

Эффективная кастомизация требует понимания внутренней архитектуры GVM: разделения на NVT, Port Lists и Scan Settings. Ключевыми инструментами здесь являются CLI `gvmd` и API GMP, позволяющие программно создавать конфигурации, фильтровать уязвимости по OID и настраивать параметры производительности. Игнорирование этих параметров приводит к ложноположительным срабатываниям, пропуску уязвимостей или, что хуже, к отказу в обслуживании целевой системы.

Для студентов и специалистов важно помнить, что кастомизация — это не просто «отключение» проверок, а балансировка между глубиной обнаружения и безопасностью сканируемой инфраструктуры. Правильно настроенная конфигурация должна быть воспроизводимой, документированной и адаптированной под конкретную цель аудита.
