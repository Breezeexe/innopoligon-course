# Шаблоны Nuclei: структура и язык описания

## Контекст и базовые понятия

Nuclei представляет собой сканер уязвимостей следующего поколения, основанный на принципе «send-and-match» (отправь-совпадение). В отличие от классических сканеров, которые полагаются на статические сигнатуры или эвристические алгоритмы, Nuclei использует шаблоны, описывающие логику эксплуатации уязвимости. Это позволяет адаптировать сканирование под конкретные CVE, конфигурации и даже бизнес-логику приложений.

Ключевое понятие темы — **шаблон Nuclei**. Это файл конфигурации в формате YAML, который определяет:
1.  Какой запрос отправить (метод, путь, заголовки, тело).
2.  Как интерпретировать ответ (статус-код, наличие текста, регулярные выражения).
3.  Какую информацию извлечь (извлечение токенов, версий, путей).
4.  Метаданные о шаблоне (автор, серьезность, ссылки на уязвимость).

Язык описания шаблонов состоит из двух основных компонентов:
1.  **YAML (YAML Ain't Markup Language)** — язык разметки данных, обеспечивающий читаемую структуру файла.
2.  **DSL (Domain Specific Language)** — встроенный язык выражений, используемый для динамической генерации запросов, условной логики и обработки ответов.

Разграничение понятий:
*   **Шаблон (Template)** — файл `.yaml`, описывающий сценарий проверки.
*   **Работфлоу (Workflow)** — набор шаблонов, выполняемых последовательно или параллельно (например, сначала фаззинг, затем проверка найденных путей).
*   **Сканер (Scanner)** — сам исполняемый файл `nuclei`, который парсит шаблоны и выполняет сетевые операции.

| Сущность | Формат | Назначение | Уровень абстракции |
|---|---|---|---|
| Шаблон (Template) | YAML | Описание одной проверки (CVE, misconfig) | Высокий (декларативный) |
| Работфлоу (Workflow) | YAML | Оркестрация нескольких шаблонов | Высокий (процессный) |
| DSL-выражение | Текст внутри YAML | Динамическая логика (переменные, условия) | Средний (императивный) |
| Запрос (Request) | HTTP-фрагмент в YAML | Физическая отправка данных | Низкий (сетевой) |

## Внутреннее устройство шаблона

Шаблон Nuclei имеет строгую иерархическую структуру. Понимание внутренних компонентов необходимо для создания точных детекторов с низким уровнем ложных срабатываний.

### 1. Блок `id` и `info`
Каждый шаблон должен иметь уникальный идентификатор `id`. Он используется для ссылки на шаблон в командной строке и для предотвращения дублирования при загрузке. Поле `info` содержит метаданные:
*   `name`: Человеко-читаемое название.
*   `severity`: Уровень серьезности (critical, high, medium, low, info).
*   `author`: Автор шаблона.
*   `description`: Описание уязвимости.
*   `reference`: Ссылки на CVE, advisory, статьи.
*   `classification`: Метрики CVSS, CWE, CVE-ID.
*   `tags`: Теги для фильтрации (например, `cve`, `sqli`, `apache`).

### 2. Блок `metadata`
Содержит служебную информацию для движка:
*   `max-request`: Максимальное количество запросов (по умолчанию вычисляется автоматически, но может быть ограничено).
*   `verified`: Флаг, указывающий, проверен ли шаблон на реальных целях.
*   `shodan-query`, `fofa-query`: Запросы к OSINT-базам для предварительной фильтрации целей.

### 3. Блок `http` (или другие протоколы)
Описывает сетевые запросы. Для HTTP-шаблонов это массив объектов, каждый из которых представляет один запрос.
*   `method`: GET, POST, PUT, DELETE и др.
*   `path`: Массив путей. Поддерживает переменные `{{BaseURL}}`, `{{Hostname}}`.
*   `headers`: Заголовки HTTP.
*   `body`: Тело запроса (поддерживает YAML-литералы `|` и `>`).
*   `redirects`: Управление перенаправлениями.

### 4. Блок `matchers`
Самый критичный элемент. Определяет условия, при которых шаблон считается успешным (уязвимость найдена).
*   `type`: Тип проверки (`word`, `regex`, `status`, `dsl`, `size`).
*   `words`: Список строк для поиска.
*   `regex`: Регулярные выражения.
*   `part`: Где искать (`body`, `header`, `all`).
*   `condition`: Логическое условие (`and`, `or`). По умолчанию `and`.

### 5. Блок `extractors`
Извлекает данные из ответа для последующего использования или вывода.
*   `type`: `regex`, `kval`, `json`, `xpath`.
*   `group`: Номер группы захвата в regex.
*   `internal`: Флаг для внутреннего использования в DSL.

### 6. DSL и переменные
DSL позволяет использовать функции и переменные.
*   Переменные: `{{BaseURL}}`, `{{Hostname}}`, `{{Host}}`, `{{Port}}`.
*   Функции: `rand_base(n)`, `rand_text_alpha(n)`, `hex_decode()`, `urlencode()`.
*   Условия: `len(body) > 100`, `status_code == 200`.

```text
[Шаблон YAML]
   │
   ├── [id] ── Уникальный ID
   ├── [info] ── Метаданные (name, severity, author)
   ├── [metadata] ── Настройки движка (max-request, verified)
   ├── [http] ── Массив запросов
   │      ├── [method] ── HTTP-метод
   │      ├── [path] ── Пути с переменными
   │      ├── [headers] ── Заголовки
   │      └── [body] ── Тело запроса
   ├── [matchers] ── Условия успеха
   │      ├── [type] ── word/regex/status/dsl
   │      ├── [words/regex] ── Паттерны
   │      └── [condition] ── and/or
   └── [extractors] ── Извлечение данных
          ├── [type] ── regex/kval/json
          └── [group] ── Группа захвата
```

## Применение и работа с шаблонами

Работа с шаблонами Nuclei включает три основных аспекта: использование готовых, создание кастомных и отладка.

### Использование готовых шаблонов
Nuclei поставляется с обширной базой шаблонов. Для обновления базы используется команда `nuclei -update-templates`.
Фильтрация шаблонов осуществляется по тегам, severity или ID.
```bash
# Сканирование с использованием только шаблонов критической серьезности
nuclei -u https://target.com -s critical

# Сканирование по тегу
nuclei -u https://target.com -tags cve
```

### Создание кастомных шаблонов
При создании шаблона важно следовать принципам:
1.  **Специфичность**: Избегать общих слов, которые могут присутствовать на легитимных страницах.
2.  **Минимизация запросов**: Использовать `matchers-condition: and` для объединения нескольких условий в одном ответе.
3.  **Безопасность**: Не использовать шаблоны, которые могут вызвать отказ в обслуживании (DoS) на продакшене, без явного разрешения.

### Отладка шаблонов
Для отладки используется флаг `-v` (verbose) и `-d` (debug).
```bash
nuclei -u https://target.com -t my-template.yaml -v -d
```
В режиме отладки видны отправленные запросы и полученные ответы, что позволяет корректировать `matchers` и `extractors`.

### Типичные ошибки
*   **Неправильный YAML**: Использование табов вместо пробелов.
*   **Ошибки в regex**: Неправильная экранизация специальных символов.
*   **Игнорирование контекста**: Использование `matchers-condition: or` без учета того, что одно из условий может быть ложноположительным.

## Сквозной практический пример: Создание шаблона для обнаружения уязвимости XSS

### Исходные условия
*   **Среда**: Локальная тестовая машина с установленным Nuclei.
*   **Цель**: Веб-приложение с параметром `?name=`, подверженным рефлексивной XSS.
*   **Инструменты**: Nuclei, текстовый редактор.
*   **Роль**: Пентестер, создающий кастомный шаблон.

### Шаг 1: Анализ уязвимости и определение индикаторов
Перед написанием шаблона необходимо понять, как приложение реагирует на XSS-попадание.
Действие: Отправка тестового запроса с payload `<script>alert(1)</script>`.
Ожидаемый результат: В ответе сервера возвращается HTML-код, содержащий введенный payload.

```bash
curl -s "http://testphp.vulnweb.com/listproducts.php?cat=1<script>alert(1)</script>" | grep -i "script"
```
*Примечание: В реальном пентесте используется интерактивный анализ в браузере или Burp Suite.*

### Шаг 2: Определение структуры шаблона
Создаем файл `xss-reflected.yaml`.
Действие: Заполняем обязательные поля `id`, `info`, `http`.

```yaml
id: reflected-xss-test

info:
  name: Reflected XSS in Query Parameter
  author: pentester
  severity: high
  description: Detects reflected XSS in the 'cat' parameter.
  reference:
    - https://owasp.org/www-community/attacks/xss/
  tags: xss,reflected

http:
  - method: GET
    path:
      - "{{BaseURL}}/listproducts.php?cat={{rand_text_alpha(5)}}"
    matchers-condition: and
    matchers:
      - type: dsl
        dsl:
          - 'contains(body, "{{rand_text_alpha(5)}}")'
          - 'contains(header, "text/html")'
```

### Шаг 3: Настройка matchers для точного совпадения
Используем DSL для проверки того, что введенный случайный текст вернулся в ответе. Это гарантирует, что уязвимость существует, и исключает ложные срабатывания на случайное совпадение текста.

```yaml
# Продолжение файла xss-reflected.yaml
    matchers:
      - type: dsl
        dsl:
          - 'contains(body, "{{rand_text_alpha(5)}}")'
          - 'contains(header, "text/html")'
```

### Шаг 4: Запуск и проверка
Действие: Запуск шаблона на тестовой цели.

```bash
nuclei -u http://testphp.vulnweb.com -t xss-reflected.yaml -v
```

Ожидаемый вывод:
```text
[INF] Found result: http://testphp.vulnweb.com/listproducts.php?cat=abcde
```

### Шаг 5: Извлечение контекста (опционально)
Если нужно извлечь позицию вхождения или контекст, можно добавить `extractors`.

```yaml
extractors:
  - type: regex
    part: body
    regex:
      - '.*cat=([a-zA-Z0-9]+).*'
```

### Ожидаемый вывод
Пример демонстрирует, как создать специфичный детектор, используя динамические переменные для исключения ложных срабатываний. Шаблон отправляет уникальный случайный текст и проверяет его возврат в ответе, что является надежным индикатором рефлексивной XSS.

## Аналитический вывод

Шаблоны Nuclei представляют собой мощный инструмент для автоматизации поиска уязвимостей благодаря своей гибкости и читаемости. YAML обеспечивает понятную структуру, а DSL позволяет реализовывать сложную логику без написания кода на языках программирования. Ключевым преимуществом является возможность быстрой адаптации под новые уязвимости: при появлении нового CVE специалист может создать шаблон за минуты, используя публичные данные об эксплуатации.

Однако создание качественных шаблонов требует глубокого понимания сетевых протоколов, HTTP-семантики и особенностей целевых приложений. Основные вызовы включают минимизацию ложных срабатываний через использование специфичных индикаторов и оптимизацию производительности за счет эффективного использования `matchers-condition` и `extractors`. Для студентов важно не только уметь использовать готовые шаблоны, но и понимать их внутреннее устройство, чтобы критически оценивать результаты сканирования и разрабатывать собственные детекторы для специфических сценариев тестирования.
