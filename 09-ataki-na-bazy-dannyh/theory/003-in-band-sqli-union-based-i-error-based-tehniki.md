# In-band SQLi: Union-based и Error-based техники

## Контекст и базовые понятия: природа, классификация и разграничение In-band атак

SQL Injection (SQLi) представляет собой класс уязвимостей веб-приложений и баз данных, возникающий при некорректной обработке пользовательского ввода, который напрямую включается в SQL-запрос без должной санитизации или параметризации. В рамках классификации по каналу передачи данных (data channel) SQLi делятся на три основные категории: In-band (или Classic), Blind (включая Boolean-based и Time-based) и Out-of-band. Разделение обусловлено тем, как атакующий получает результат выполнения вредоносного запроса. In-band SQLi является наиболее прямым и эффективным методом, так как канал атаки и канал получения данных совпадают. Это означает, что результат выполнения внедренного SQL-кода выводится непосредственно в ответе веб-сервера или отображается в интерфейсе базы данных.

Ключевая особенность In-band атак заключается в их простоте и скорости. В отличие от Blind-атак, требующих длительного времени для посимвольного перебора или определения состояния через задержки, In-band позволяет получить данные практически мгновенно после успешной эксплуатации уязвимости. Однако этот метод требует, чтобы целевая СУБД (СУБД) поддерживала вывод результатов запроса в HTTP-ответе или генерировала ошибки, содержащие данные. Если веб-приложение скрывает ошибки и не выводит результаты запросов на страницу, In-band атака становится невозможной, и атакующему приходится переключаться на более сложные методы.

Внутри класса In-band SQLi выделяются две основные техники: Union-based и Error-based. Их разграничение критически важно для понимания механизма эксплуатации и выбора инструментария.

**Union-based SQLi** использует SQL-оператор `UNION`, который позволяет объединять результаты двух или более SELECT-запросов в один результат. Для успешной эксплуатации атакующий должен знать количество столбцов в оригинальном запросе и типы данных этих столбцов. Если эти параметры совпадают, данные из произвольной таблицы базы данных могут быть извлечены и отображены в том же месте интерфейса, где изначально выводился результат легитимного запроса. Эта техника требует высокой точности и понимания структуры базы данных.

**Error-based SQLi** эксплуатирует уязвимость приложения в обработке ошибок. Когда внедренный SQL-код вызывает синтаксическую или логическую ошибку, веб-сервер или СУБД возвращает сообщение об ошибке, которое отображается пользователю. В некоторых конфигурациях (особенно в старых версиях MySQL, PostgreSQL или при включенном режиме отладки) эти сообщения содержат фрагменты выполненного SQL-запроса или даже сами данные, которые вызвали ошибку. Атакующий использует специальные функции генерации ошибок (например, `CAST`, `CONVERT`, `GROUP BY` с `COUNT` и `RAND`), чтобы принудительно вызвать ошибку и извлечь данные через тело ошибки.

Разграничение между этими техниками и другими типами SQLi представлено в следующей таблице.

| Характеристика | In-band (Union-based) | In-band (Error-based) | Blind SQLi (Boolean/Time) | Out-of-band SQLi |
| :--- | :--- | :--- | :--- | :--- |
| **Канал получения данных** | HTTP-ответ (интерфейс) | HTTP-ответ (тело ошибки) | HTTP-ответ (косвенно) | DNS, HTTP, SMTP |
| **Механизм извлечения** | Оператор `UNION SELECT` | Функции генерации ошибок (`CAST`, `GROUP BY`) | Логические условия (`AND 1=1`) или задержки (`SLEEP`) | Внешние протоколы (`LOAD_FILE`, `UTL_HTTP`) |
| **Требования к СУБД** | Поддержка `UNION`, знание кол-ва столбцов | Поддержка функций генерации ошибок, режим отладки | Любая, поддерживающая SQL | Поддержка внешних вызовов (XSS, DBMS extensions) |
| **Скорость эксплуатации** | Высокая (мгновенно) | Средняя (зависит от кол-ва запросов) | Низкая (тысячи запросов) | Зависит от канала |
| **Сложность обнаружения** | Низкая (легко детектируется WAF) | Средняя (зависит от логирования ошибок) | Высокая (похоже на легитимный трафик) | Высокая (аномальный исходящий трафик) |
| **Типичные СУБД** | MySQL, PostgreSQL, MSSQL, Oracle | MySQL, PostgreSQL, MSSQL | Все | MySQL (LOAD_FILE), MSSQL (CLR), Oracle (UTL_HTTP) |

Путаница между Union-based и Error-based часто возникает из-за того, что обе техники относятся к In-band. Однако их природа различна: Union-based полагается на легитимный вывод данных, тогда как Error-based полагается на некорректный вывод (ошибки). Понимание этого различия определяет стратегию тестирования: сначала проверяется наличие вывода данных (Union), затем — наличие детальных сообщений об ошибках (Error). Если ни один из методов не работает, атака переходит в категорию Blind.

Важно отметить, что In-band SQLi требует, чтобы атакующий мог видеть результат выполнения запроса. В современных веб-приложениях это ограничение часто обходится через использование AJAX, где данные загружаются динамически, или через скрытые поля формы. Тем не менее, если уязвимый параметр влияет на любой вывод на странице (даже скрытый), атака остается возможной.

## Внутреннее устройство: архитектура Union-based и Error-based атак

### Union-based SQLi: механизм объединения запросов

Union-based SQLi базируется на возможности СУБД выполнять несколько SELECT-запросов и объединять их результаты в одну таблицу. Оператор `UNION` требует, чтобы количество столбцов и их типы данных в обоих запросах (оригинальном и внедренном) совпадали. Если эти условия не выполняются, СУБД возвращает ошибку, что может быть использовано для определения структуры базы данных (как в Error-based), но сам метод Union не сработает.

Процесс эксплуатации Union-based SQLi состоит из нескольких этапов:

1.  **Определение количества столбцов.** Атакующий использует оператор `ORDER BY` или `UNION SELECT NULL`, увеличивая количество значений до тех пор, пока не возникнет ошибка. Например, `UNION SELECT NULL` (1 столбец), `UNION SELECT NULL, NULL` (2 столбца) и т.д.
2.  **Определение типов данных столбцов.** После определения количества столбцов атакующий пытается подставить значения разных типов (строки, числа, даты) в каждый столбец, чтобы найти те, которые принимают строковые значения (обычно это столбцы, отображаемые на странице).
3.  **Извлечение данных.** Используя найденные столбцы, атакующий формирует запрос, который извлекает данные из системных таблиц (например, `information_schema.tables` в MySQL или `sys.tables` в MSSQL) и объединяет их с оригинальным запросом.

Структура запроса выглядит следующим образом:

```sql
-- Оригинальный запрос приложения
SELECT column_list FROM table_name WHERE id = 1

-- Внедренный запрос (после эксплуатации)
SELECT column_list FROM table_name WHERE id = 1 UNION SELECT table_name, column_name FROM information_schema.columns --
```

Ключевым аспектом Union-based атаки является необходимость точного совпадения типов данных. Если оригинальный запрос возвращает целые числа, а атакующий пытается вернуть строки, СУБД может выдать ошибку преобразования типов. В этом случае атакующий должен использовать функции приведения типов (например, `CAST` или `CONVERT`), чтобы привести данные к нужному типу.

### Error-based SQLi: механизм генерации ошибок

Error-based SQLi эксплуатирует уязвимость в обработке ошибок СУБД. Когда внедренный SQL-код вызывает ошибку, СУБД возвращает сообщение, которое может содержать данные, вызвавшие ошибку. Это возможно благодаря тому, что некоторые функции генерируют ошибки, содержащие значения аргументов.

Основные функции, используемые в Error-based атаках:

1.  **MySQL:**
    *   `CAST(value AS type)`: пытается привести значение к типу, который не поддерживается, вызывая ошибку.
    *   `EXTRACTVALUE(xml, xpath)`: извлекает значение из XML-документа по XPath. Если XPath невалиден, возвращается ошибка, содержащая значение.
    *   `UPDATEXML(xml, xpath, new_value)`: аналогично `EXTRACTVALUE`.

2.  **PostgreSQL:**
    *   `CAST(value AS type)`: аналогично MySQL.
    *   `array_agg()`: может использоваться для генерации ошибок при работе с массивами.

3.  **MSSQL:**
    *   `CONVERT(type, value)`: пытается привести значение к типу, вызывая ошибку.
    *   `sys.fn_helphelp`: может использоваться для получения информации о базах данных.

Механизм работы Error-based атаки заключается в следующем:

1.  Атакующий формирует запрос, который вызывает ошибку. Например, в MySQL:
    ```sql
    SELECT * FROM users WHERE id = 1 AND (SELECT 1 FROM (SELECT COUNT(*), CONCAT((SELECT database()), FLOOR(RAND(0)*2)) x FROM information_schema.tables GROUP BY x) a)
    ```
    Этот запрос использует `GROUP BY` и `RAND()` для генерации ошибки `Duplicate entry`. В сообщении об ошибке будет содержаться значение базы данных.

2.  Атакующий анализирует сообщение об ошибке и извлекает данные.

3.  Повторяет процесс для извлечения всех необходимых данных.

Ключевым ограничением Error-based атаки является то, что она работает только в том случае, если веб-приложение отображает сообщения об ошибках. В современных приложениях ошибки часто скрываются, и атакующий получает только общую страницу ошибки (например, "500 Internal Server Error"). В этом случае Error-based атака невозможна.

### Сравнительный анализ механизмов

| Аспект | Union-based | Error-based |
| :--- | :--- | :--- |
| **Основной принцип** | Объединение результатов запросов | Использование сообщений об ошибках |
| **Требования к СУБД** | Поддержка `UNION`, точное совпадение типов | Поддержка функций генерации ошибок, режим отладки |
| **Сложность эксплуатации** | Высокая (требует знания структуры) | Средняя (требует знания функций) |
| **Скорость извлечения** | Высокая (много данных за один запрос) | Низкая (много запросов для посимвольного перебора) |
| **Зависимость от вывода** | Требует вывода данных на страницу | Требует вывода ошибок на страницу |
| **Типичные инструменты** | SQLmap, manual exploitation | SQLmap, manual exploitation |

## Применение и работа с предметом: инструменты, методы детекции и контрмеры

### Детекция In-band SQLi

Детекция In-band SQLi начинается с выявления потенциально уязвимых параметров. Атакующий или тестировщик на проникновение использует следующие методы:

1.  **Проверка на Union-based SQLi:**
    *   Добавление одинарной кавычки (`'`) для проверки на синтаксическую ошибку.
    *   Использование `ORDER BY` для определения количества столбцов.
    *   Использование `UNION SELECT NULL` для проверки возможности объединения запросов.

2.  **Проверка на Error-based SQLi:**
    *   Использование функций генерации ошибок, таких как `CAST`, `EXTRACTVALUE`, `CONVERT`.
    *   Анализ сообщений об ошибках на наличие данных.

### Инструментарий

Для автоматизации обнаружения и эксплуатации In-band SQLi используются следующие инструменты:

1.  **SQLmap:** Наиболее популярный инструмент для автоматизации SQLi. Поддерживает как Union-based, так и Error-based техники.
    ```bash
    sqlmap -u "http://example.com/page?id=1" --dbs
    ```
    Эта команда автоматически определяет тип SQLi и извлекает список баз данных.

2.  **Burp Suite:** Инструмент для ручного тестирования. Позволяет перехватывать и модифицировать запросы, а также использовать инструмент Intruder для автоматизации атак.

3.  **Havij:** Платный инструмент для автоматизации SQLi.

### Контрмеры

Для предотвращения In-band SQLi необходимо использовать следующие контрмеры:

1.  **Параметризованные запросы (Prepared Statements):** Самый эффективный метод защиты. Данные пользователя никогда не включаются напрямую в SQL-запрос.
    ```python
    # Пример на Python с использованием psycopg2
    cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
    ```

2.  **Хранение процедур (Stored Procedures):** Использование хранимых процедур может снизить риск SQLi, но не устраняет его полностью, если процедуры формируют запросы динамически.

3.  **Валидация ввода:** Проверка входных данных на соответствие ожидаемому формату. Однако это не должно быть единственным методом защиты.

4.  **Минимальные привилегии:** Использование учетных записей с минимальными привилегиями для подключения к базе данных.

5.  **Скрытие ошибок:** Настройка веб-сервера и СУБД на скрытие детальных сообщений об ошибках в production-среде.

## Сквозной практический пример: эксплуатация Union-based SQLi в учебной среде

### Исходные условия
*   **Среда:** Учебный веб-приложение DVWA (Damn Vulnerable Web Application) с уровнем безопасности "Low".
*   **СУБД:** MySQL 5.7.
*   **Инструменты:** Burp Suite, SQLmap.
*   **Роль:** Тестировщик на проникновение.
*   **Сценарий:** Обнаружение и эксплуатация Union-based SQLi для извлечения данных из таблицы `users`.

### Шаг 1: Определение количества столбцов

Атакующий начинает с определения количества столбцов в оригинальном запросе. Для этого используется оператор `ORDER BY`.

```bash
# Пример запроса с увеличением номера столбца
http://dvwa/page.php?id=1 ORDER BY 1--
http://dvwa/page.php?id=1 ORDER BY 2--
http://dvwa/page.php?id=1 ORDER BY 3--
http://dvwa/page.php?id=1 ORDER BY 4--
```

Ожидаемый вывод: Запросы с `ORDER BY 1` и `ORDER BY 2` возвращают данные. Запрос с `ORDER BY 3` возвращает ошибку `Unknown column '3' in 'order clause'`. Это указывает на то, что в оригинальном запросе 2 столбца.

### Шаг 2: Проверка возможности Union-based атаки

Проверяется, может ли СУБД объединить результаты запросов.

```bash
# Пример запроса с UNION SELECT
http://dvwa/page.php?id=1 UNION SELECT 1,2--
```

Ожидаемый вывод: Если запрос возвращает данные без ошибок, значит, Union-based атака возможна. В данном случае, на странице отображаются числа `1` и `2`, которые являются результатами `UNION SELECT 1,2`.

### Шаг 3: Извлечение данных

Используя номера столбцов, атакующий извлекает данные из таблицы `users`.

```bash
# Пример запроса с извлечением данных
http://dvwa/page.php?id=1 UNION SELECT username, password FROM users--
```

Ожидаемый вывод: На странице отображаются имена пользователей и их хэши паролей.

### Шаг 4: Автоматизация с помощью SQLmap

Для автоматизации процесса используется SQLmap.

```bash
sqlmap -u "http://dvwa/page.php?id=1" --dbs --batch
```

Ожидаемый вывод: SQLmap автоматически определяет тип SQLi, извлекает список баз данных и таблиц.

### Ожидаемый вывод
Этот пример демонстрирует, как Union-based SQLi позволяет извлечь данные из базы данных без необходимости знания структуры базы данных заранее. Использование SQLmap упрощает процесс, но понимание механизма эксплуатации критически важно для обхода современных средств защиты.

## Аналитический вывод

In-band SQLi, включая Union-based и Error-based техники, представляет собой критическую угрозу для веб-приложений, эксплуатирующих уязвимости в обработке пользовательского ввода. Union-based атака эффективна благодаря возможности извлечения данных через легитимный вывод, но требует точного знания структуры базы данных. Error-based атака использует сообщения об ошибках для извлечения данных, что делает ее менее зависимой от структуры, но более зависимой от конфигурации СУБД. Обе техники требуют, чтобы веб-приложение отображало результаты запросов или ошибки, что в современных приложениях часто ограничивается. Тем не менее, In-band SQLi остается важным инструментом в арсенале тестировщиков на проникновение и злоумышленников. Защита от этих атак требует комплексного подхода, включающего параметризованные запросы, валидацию ввода и минимальные привилегии. Понимание механизмов In-band SQLi необходимо для разработки эффективных стратегий защиты и тестирования на проникновение.
