# SSH Port Forwarding как канал pivot

## Контекст и базовые понятия

SSH Port Forwarding (перенаправление портов SSH) — это механизм протокола SSH, позволяющий туннелировать произвольные сетевые соединения через зашифрованный канал SSH. В контексте тестирования на проникновение и расследования инцидентов (IR) эта функция является ключевым инструментом для обхода сетевых ограничений (firewall, ACL) и перемещения внутри изолированной среды (pivot).

Основное назначение SSH Port Forwarding в легитимной эксплуатации — обеспечение безопасного доступа к внутренним сервисам из ненадежных сетей (например, доступ к базе данных через туннель SSH вместо прямого подключения по TCP). В атаках этот же механизм используется для создания «моста» между внешней сетью и внутренней инфраструктурой, недоступной напрямую из-за правил маршрутизации или межсетевых экранов.

Критически важно разграничивать три типа перенаправления, так как их функциональное назначение и сетевая семантика различны:

1.  **Local Forwarding (`-L`)**: Клиент слушает порт на локальной машине и перенаправляет трафик через сервер SSH к указанному хосту и порту. Используется для доступа к внутренним сервисам извне.
2.  **Remote Forwarding (`-R`)**: Сервер SSH слушает порт и перенаправляет трафик от этого порта обратно через туннель к клиенту, который затем маршрутизирует его к указанному хосту. Используется для экспорта внутренних сервисов наружу (reverse tunnel).
3.  **Dynamic Forwarding (`-D`)**: Клиент действует как SOCKS-прокси. Приложения, настроенные на использование этого прокси, могут устанавливать соединения через туннель SSH к любому адресу. Используется для полного обхода сетевых ограничений на стороне клиента.

Различие между этими типами определяется направлением потока данных относительно точки входа в туннель (клиента или сервера) и тем, кто инициирует новое соединение внутри туннеля.

| Тип форвардинга | Флаг SSH | Направление потока | Роль SSH-сервера | Роль SSH-клиента | Типичное применение в пентесте |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Local Forwarding** | `-L` | Клиент → Сервер → Целевой хост | Шлюз (Gateway) | Слушатель (Listener) | Доступ к БД/админ-панелям извне |
| **Remote Forwarding** | `-R` | Целевой хост → Сервер → Клиент | Слушатель (Listener) | Шлюз (Gateway) | Обход NAT, экспорт локального сервиса |
| **Dynamic Forwarding** | `-D` | Любой → Клиент (SOCKS) → Сервер → Целевой хост | Шлюз (Gateway) | SOCKS-прокси | Масштабное сканирование, обход ACL |

Путаница часто возникает между понятиями «SSH Tunnel» и «SSH Proxy». Технически динамический форвардинг (`-D`) создает SOCKS-прокси, который *использует* SSH-туннель как транспорт. Однако локальный и удаленный форвардинг создают статические порты, не являясь прокси в полном смысле этого слова (они не пересылают произвольные DNS-запросы или протоколы, отличные от TCP, без дополнительной настройки).

## Внутреннее устройство предмета

SSH Port Forwarding реализуется на уровне протокола SSH-2.0 через специализированные сообщения `SSH_MSG_GLOBAL_REQUEST` и `SSH_MSG_CHANNEL_OPEN`. Механизм работает поверх уже установленного защищенного канала (session channel), который обеспечивает шифрование и аутентификацию.

### Механизм работы Local Forwarding (`-L`)

При инициации команды `ssh -L local_port:remote_host:remote_port user@ssh_server` происходит следующее:
1.  SSH-клиент открывает сокет на `local_port` и начинает прослушивание.
2.  После успешной аутентификации клиент отправляет серверу запрос `SSH_MSG_GLOBAL_REQUEST` с именем `tcpip-forward` и параметрами `address`, `port`.
3.  Сервер, если разрешено конфигурацией (`AllowTcpForwarding yes` в `sshd_config`), отвечает подтверждением и начинает слушать указанный порт.
4.  Когда внешний клиент подключается к `local_port` на машине атакующего, SSH-клиент создает новый канал (`SSH_MSG_CHANNEL_OPEN` типа `direct-tcpip`) через существующее SSH-соединение к серверу.
5.  SSH-сервер, получив запрос `direct-tcpip`, устанавливает новое TCP-соединение к `remote_host:remote_port` и связывает его с каналом.
6.  Данные пересыкаются в обе стороны: `Client <-> Tunnel <-> Server <-> Target`.

Ключевой аспект безопасности: SSH-сервер выступает как доверенный посредник. Для целевой системы (`remote_host`) источником соединения является SSH-сервер, а не атакующий. Это позволяет обходить IP-фильтрацию, но не скрывает факт подключения от логов SSH-сервера.

### Механизм работы Remote Forwarding (`-R`)

При инициации `ssh -R remote_port:local_host:local_port user@ssh_server`:
1.  Клиент отправляет серверу запрос `tcpip-forward` с указанием порта для прослушивания.
2.  Сервер открывает сокет на `remote_port`.
3.  При подключении к этому порту на сервере, SSH-сервер создает канал `direct-tcpip` обратно к клиенту.
4.  Клиент, получив запрос, устанавливает соединение к `local_host:local_port` на своей машине.
5.  Трафик от внешнего мира проходит: `External <-> Server <-> Tunnel <-> Client <-> Local Service`.

Ограничения: По умолчанию современные версии OpenSSH требуют явного разрешения `GatewayPorts` в `sshd_config` для того, чтобы сервер слушал порт на всех интерфейсах (`0.0.0.0`), а не только на localhost (`127.0.0.1`). Без этого параметра туннель доступен только локально на сервере, что ограничивает его полезность для внешнего пивота.

### Механизм работы Dynamic Forwarding (`-D`)

Динамический форвардинг (`-D`) не создает статического сопоставления портов. Вместо этого SSH-клиент запускает локальный SOCKS-сервер (по умолчанию на `127.0.0.1:1080`).
1.  Приложения, настроенные на использование SOCKS-прокси, отправляют запросы на этот локальный порт.
2.  SSH-клиент извлекает целевой адрес и порт из SOCKS-запроса (SOCKS4/SOCKS5).
3.  Клиент отправляет серверу запрос `tcpip-forward` (или использует внутренний механизм динамического туннелирования, зависящий от реализации, но в OpenSSH это часто реализуется через создание временных каналов `direct-tcpip` для каждого соединения).
4.  Сервер устанавливает соединение с целевым хостом.

Важно: Динамический форвардинг работает только на уровне TCP. Он не пересылает UDP-трафик (DNS, VoIP, некоторые игры) без дополнительных инструментов (например, `socat` или `iptables` с UDP-over-TCP).

### Архитектура компонентов туннеля

## Применение и работа с предметом

На практике SSH Port Forwarding используется в пентестах для расширения зоны поражения. После получения доступа к серверу в DMZ или периметре, атакующий использует форвардинг для доступа к внутренним сервисам (базы данных, админ-панели, внутренние API), которые не имеют публичных IP-адресов.

### Типовые операции и команды

**1. Local Forwarding для доступа к внутренней БД**
Частая ошибка новичков — попытка сканировать внутреннюю сеть напрямую с атакующей машины. Правильный подход — использовать SSH-сервер как мост.

```bash
# Синтаксис: ssh -L [bind_address:]port:host:hostport user@ssh_server
# Пример: Слушать порт 3307 на локальной машине и перенаправлять его на 192.168.1.100:3306 через SSH-сервер
ssh -L 3307:192.168.1.100:3307 user@10.0.0.5

# Проверка работы туннеля
nc -zv 127.0.0.1 3307
```

**2. Remote Forwarding для обхода NAT (Reverse Tunnel)**
Используется, когда атакующий находится за NAT, а цель доступна извне, но не может инициировать соединение к атакующему. Или наоборот: экспортировать локальный сервис (например, веб-сервер для демо) через внешний сервер.

```bash
# Синтаксис: ssh -R [bind_address:]port:host:hostport user@ssh_server
# Пример: Слушать порт 8080 на SSH-сервере и перенаправлять на локальный порт 80
ssh -R 8080:localhost:80 user@10.0.0.5

# На SSH-сервере нужно убедиться, что:
# 1. GatewayPorts yes (в /etc/ssh/sshd_config)
# 2. AllowTcpForwarding yes
```

**3. Dynamic Forwarding для SOCKS-прокси**
Позволяет использовать любые инструменты (nmap, burp suite, metasploit) через туннель.

```bash
# Синтаксис: ssh -D [bind_address:]port user@ssh_server
# Пример: Создать SOCKS5 прокси на порту 1080
ssh -D 1080 user@10.0.0.5

# Использование с nmap
nmap --socks5 127.0.0.1:1080 -sT 192.168.1.0/24
```

### Конфигурация сервера и ограничения

Безопасность туннелей зависит от конфигурации `sshd_config`. Ключевые параметры:

*   `AllowTcpForwarding`: Управляет разрешением на создание туннелей. Значения: `yes` (все), `no` (запрещено), `local` (только `-L`), `remote` (только `-R`).
*   `GatewayPorts`: Позволяет удаленным хостам подключаться к портам удаленного форвардинга. По умолчанию `no` (только localhost).
*   `PermitOpen`: Ограничивает, к каким хостам и портам можно подключаться через локальный форвардинг. Например, `PermitOpen 192.168.1.100:3306` разрешает доступ только к этой БД.
*   `PermitListen`: Ограничивает, на каких адресах и портах можно слушать при удаленном форвардинге.

### Типичные ошибки и подводные камни

1.  **DNS Rebinding**: При использовании динамического форвардинга DNS-запросы могут уходить напрямую от клиента, а не через туннель, если приложение не поддерживает SOCKS5 с DNS-over-SOCKS. Это может привести к утечке информации или невозможности разрешения внутренних имен.
2.  **MTU Issues**: Туннелирование добавляет заголовки SSH и TCP, что может привести к фрагментации пакетов или потере данных, если MTU сети не настроен корректно.
3.  **Persistence**: SSH-сессии могут разрываться. Для стабильности используются инструменты вроде `autossh` или `tmux`/`screen`.
4.  **Detection**: Туннели легко обнаруживаются по аномальному трафику (постоянные длинные соединения, специфичные паттерны шифрования) и по логам `sshd` (запросы `tcpip-forward`).

## Сквозной практический пример: Pivoting к внутренней БД

**Исходные условия**:
*   **Атакующий (Attacker)**: Kali Linux, IP `10.10.14.50`.
*   **Цель 1 (SSH Server)**: Сервер в DMZ, IP `192.168.1.10`, порт 22. Доступ получен через SSH.
*   **Цель 2 (Internal DB)**: База данных PostgreSQL, IP `192.168.1.20`, порт 5432. Недоступна извне, доступна только из внутренней сети `192.168.1.0/24`.
*   **Задача**: Подключиться к PostgreSQL с машины атакующего, используя SSH-сервер как мост.

**Шаг 1: Инициализация локального форвардинга**

Атакующий создает туннель, связывая локальный порт 5432 с внутренним хостом `192.168.1.20:5432` через SSH-сервер.

```bash
# Команда на машине атакующего
ssh -L 5432:192.168.1.20:5432 user@192.168.1.10 -N -f

# Пояснение:
# -L 5432:192.168.1.20:5432 : Локальный порт 5432 -> Целевой хост 192.168.1.20:5432
# -N : Не выполнять удаленную команду (только туннель)
# -f : Перейти в фон после аутентификации
```

**Шаг 2: Проверка доступности туннеля**

Проверка, что туннель работает и SSH-сервер может достучаться до базы данных.

```bash
# Проверка локального порта
nc -zv 127.0.0.1 5432

# Ожидаемый вывод (если туннель работает и БД доступна):
# Connection to 127.0.0.1 5432 port [tcp/postgresql] succeeded!
```

**Шаг 3: Подключение к базе данных**

Использование клиента psql для подключения к локальному порту, который теперь перенаправлен на внутреннюю БД.

```bash
# Подключение через tуннель
psql -h 127.0.0.1 -p 5432 -U admin -d production_db

# Вывод (иллюстративный):
# Password for user admin: 
# psql (14.5)
# SSL connection (protocol: TLSv1.3, cipher: TLS_AES_256_GCM_SHA384)
# Type "help" for help.
#
# production_db=> SELECT version();
#                version                 
# ----------------------------------------
#  PostgreSQL 14.5 on x86_64-pc-linux-gnu
# (1 row)
```

**Шаг 4: Анализ логов на SSH-сервере**

Проверка того, что действие было зафиксировано в логах SSH-сервера.

```bash
# На SSH-сервере (192.168.1.10)
grep "tcpip-forward" /var/log/auth.log

# Ожидаемый вывод:
# Oct 10 12:00:01 ssh-server sshd[12345]: user1: session opened for user user1
# Oct 10 12:00:02 ssh-server sshd[12345]: user1: request tcpip-forward from 10.10.14.50 port 5432
# Oct 10 12:00:02 ssh-server sshd[12345]: user1: forwarded tcp connection from 10.10.14.50:5432 to 192.168.1.20:5432
```

**Ожидаемый вывод**:
Пример демонстрирует успешный pivot через SSH. Атакующий получил доступ к внутренней БД, не имея прямого сетевого пути к ней. Для защиты от такой атаки необходимо использовать `PermitOpen` в `sshd_config` для ограничения направлений туннелей и мониторинг логов на предмет запросов `tcpip-forward`.

## Аналитический вывод

SSH Port Forwarding является мощным инструментом как для легитимного администрирования, так и для атакующих. Его основная угроза заключается в способности обходить сетевые сегментации и IP-фильтрацию, используя доверенное SSH-соединение как транспорт. Локальный форвардинг позволяет получить доступ к внутренним сервисам извне, удаленный — экспортировать сервисы наружу или обходить NAT, а динамический — действовать как SOCKS-прокси для масштабного сканирования.

Для специалистов по безопасности критически важно не только блокировать несанкционированные туннели, но и мониторить легитимные. Наличие запросов `tcpip-forward` в логах SSH-сервера должно быть предметом анализа: кто инициировал туннель, на какие порты и хосты он направлен. Использование параметров `PermitOpen` и `PermitListen` в `sshd_config` является лучшей практикой для минимизации поверхности атаки. В пентестах игнорирование возможности использования SSH-туннелей для пивота приводит к неполной оценке уязвимости внутренней сети.
