# Брутфорс учётных данных SMTP через VRFY и AUTH

## Контекст и базовые понятия

Протокол SMTP (Simple Mail Transfer Protocol), описанный в RFC 5321, является стандартом де-факто для передачи электронной почты в интернете. Его основная функция — «push» (отправка) сообщений от клиента к серверу и от сервера к серверу. Однако исторически SMTP обладал существенным недостатком: он не требовал аутентификации для выполнения базовых команд, таких как `VRFY` (проверка существования пользователя) или `EXPN` (расширение списка рассылки). Это позволяло злоумышленникам валидировать списки email-адресов без предоставления учётных данных, что облегчало последующие атаки на основе социальной инженерии или брутфорс.

В контексте тестирования на проникновение (pentest) и оценки уязвимостей SMTP-серверов ключевым понятием является **аутентификация SMTP**. Современная инфраструктура требует, чтобы отправители доказывали свою легитимность перед отправкой почты, особенно через внешние шлюзы. Это достигается либо через механизм **SMTP AUTH** (RFC 4954), либо через **IP-аутентификацию** (доверие к IP-адресу отправителя).

Разграничение понятий:
1.  **SMTP AUTH**: Механизм, встроенный в протокол SMTP, позволяющий клиенту передать учётные данные (логин/пароль) серверу в процессе рукопожатия. Поддерживает механизмы `PLAIN`, `LOGIN`, `CRAM-MD5`, `XOAUTH2`.
2.  **VRFY/EXPN**: Команды проверки существования пользователя. Не являются механизмом аутентификации, но часто используются как вектор для сбора информации (enumeration) перед атакой.
3.  **IP Whitelisting**: Метод аутентификации, при котором сервер доверяет отправителю на основе его IP-адреса, а не учётных данных. Часто используется для серверов приложений (SMTP Relay).

Путаница между **SMTP** и **IMAP/POP3** в контексте аутентификации:
*   **SMTP** используется для *отправки* почты. Атака на SMTP направлена на получение права отправлять почту от имени жертвы (spoofing) или на использование сервера как открытого ретранслятора (open relay).
*   **IMAP/POP3** используются для *получения* почты. Атака на эти протоколы направлена на чтение входящих сообщений.
*   **Критическое различие**: Учётные данные, полученные через брутфорс SMTP AUTH, позволяют *отправлять* письма, но не обязательно позволяют *читать* входящие (если не настроено перенаправление или если IMAP не использует те же учётные данные). Однако в современных системах (Gmail, Exchange) учётные данные часто универсальны для всех сервисов.

| Характеристика | SMTP AUTH | VRFY / EXPN | IP Whitelisting |
| :--- | :--- | :--- | :--- |
| **Назначение** | Аутентификация отправителя | Проверка существования адреса | Доверие к источнику |
| **Требует учётных данных** | Да (логин/пароль или токен) | Нет | Нет |
| **Риск при брутфорсе** | Высокий (получение доступа) | Низкий (только информация) | Неприменимо |
| **Статус в современных системах** | Основной метод | Отключён по умолчанию | Для внутренних сервисов |
| **RFC** | RFC 4954 | RFC 5321 (Section 4.1.1.10) | Практика администрирования |

## Внутреннее устройство предмета

Атака на SMTP через брутфорс опирается на два основных вектора: эксплуатацию уязвимости проверки пользователей (VRFY) и прямую атаку на механизм аутентификации (AUTH).

### 1. Механизм VRFY и его эволюция

Команда `VRFY` предназначена для того, чтобы клиент мог убедиться, что адресат существует на данном сервере. Сервер должен ответить кодом `250` (OK) или `251` (Forwarding), если пользователь найден, или `550` (User not found), если нет.

**Исторический контекст:**
В ранних реализациях SMTP (до 2000-х) `VRFY` был критически важен для отладки. Однако он стал инструментом для сбора баз (email harvesting). Злоумышленники использовали скрипты для перебора тысяч адресов, формируя списки для спам-рассылок или фишинга.

**Современное состояние:**
Большинство современных MTA (Mail Transfer Agents), таких как Postfix, Exim, Sendmail и коммерческие решения (Exchange, Gmail), **отключают** `VRFY` по умолчанию. Вместо этого они возвращают общий ответ `550 5.1.1 <address>: Recipient address rejected: User unknown in virtual mailbox table` для *любого* адреса, чтобы не раскрывать информацию.

**Обходные пути (Side-Channel):**
Даже если `VRFY` отключён, атакующий может использовать косвенные признаки:
*   **Различия во времени ответа (Timing Attack)**: Если сервер обрабатывает несуществующих пользователей быстрее (или медленнее) из-за особенностей базы данных или кэширования.
*   **Команда RCPT TO**: При попытке отправить письмо несуществующему пользователю сервер может вернуть ошибку сразу (`550 User unknown`) или принять письмо и отклонить его позже (`451 Temporary failure`). Разница в статусе ответа может указывать на существование адреса.
*   **EXPN**: Расширение списка рассылки (например, mailing list). Если список существует, сервер может вернуть список адресов.

### 2. Механизм SMTP AUTH

SMTP AUTH (RFC 4954) вводит команду `AUTH`, которая позволяет клиенту инициировать процесс аутентификации. Процесс происходит *после* команды `EHLO/HELO` и *до* команды `MAIL FROM`.

**Основные механизмы аутентификации:**

1.  **PLAIN**:
    *   Отправляет логин и пароль в открытом виде (или в base64, что легко декодируется).
    *   Формат: `0<username>0<password>` (где `0` — null-байт).
    *   Требует шифрования канала (STARTTLS), иначе пароль перехватывается.
    *   *Применимость*: Часто используется во внутренних сетях или при обязательном TLS.

2.  **LOGIN**:
    *   Более старый механизм, поддерживаемый для обратной совместимости (Microsoft, Exchange).
    *   Работает в два этапа: сервер запрашивает `Username:`, клиент отвечает; затем `Password:`, клиент отвечает.
    *   Данные также кодируются в Base64.

3.  **CRAM-MD5**:
    *   Механизм challenge-response. Сервер отправляет случайный вызов (challenge), клиент вычисляет HMAC-MD5 от пароля и вызова.
    *   Пароль никогда не передаётся по сети.
    *   *Уязвимость*: Уязвим к offline-брутфорсу, если перехвачен challenge/response.

4.  **XOAUTH2 / OAuth2**:
    *   Используется в современных облачных сервисах (Gmail, Outlook).
    *   Вместо пароля передаётся access token.
    *   Брутфорс в классическом понимании (подбор пароля) не применим; требуется кража токена или фишинг авторизации.

**Структура рукопожатия AUTH:**

```text
Client: EHLO attacker.com
Server: 250-mail.example.com
        250-AUTH PLAIN LOGIN
Client: AUTH PLAIN
Server: 334 
Client: <base64(0user@example.com0password123)>
Server: 235 2.7.0 Authentication successful
```

**Особенности реализации:**
*   **Rate Limiting**: Современные серверы ограничивают количество попыток аутентификации с одного IP (например, 5 попыток в минуту).
*   **Account Lockout**: После N неудачных попыток аккаунт блокируется.
*   **MFA (Multi-Factor Authentication)**: Для облачных сервисов простой брутфорс пароля бесполезен без второго фактора. Однако, если атакующий уже получил токен приложения (app password), он может обойти MFA.

## Применение и работа с предметом

На практике тестировщик использует специализированные инструменты для автоматизации перебора. Ручное выполнение команд SMTP неэффективно из-за необходимости обработки ответов и управления состоянием соединения.

### Инструментарий

1.  **Hydra (THC-Hydra)**:
    *   Самый популярный инструмент для брутфорса протоколов.
    *   Поддерживает модуль `smtp-plain` и `smtp-login`.
    *   Позволяет параллельно перебирать словари.

2.  **Nmap (NSE Scripts)**:
    *   Скрипт `smtp-enum-users` может использоваться для проверки уязвимости VRFY/EXPN.
    *   Скрипт `smtp-open-relay` проверяет, является ли сервер открытым ретранслятором.

3.  **Swaks (Swiss Army Knife for SMTP)**:
    *   Утилита для тестирования SMTP. Позволяет вручную эмулировать команды `AUTH`, `VRFY`, `RCPT TO`.
    *   Полезен для отладки и проверки конкретных ответов сервера.

4.  **Metasploit**:
    *   Модуль `auxiliary/scanner/smtp/smtp_enum` для автоматизированного перебора.

### Типовые операции и процедуры

**Шаг 1: Разведка (Reconnaissance)**
Перед атакой необходимо определить, какие механизмы поддерживает сервер.
*   Команда `EHLO` возвращает список поддерживаемых команд и механизмов аутентификации.
*   Если в ответе нет `AUTH`, брутфорс учётных данных через SMTP невозможен (требуется другой вектор, например, веб-интерфейс).
*   Если есть `VRFY`, проверяется его работа.

**Шаг 2: Подготовка словаря**
*   Словари должны быть релевантными. Для SMTP AUTH часто используются стандартные списки (rockyou.txt), но для облачных сервисов требуются специфичные форматы (email@domain.com).
*   Важно учитывать ограничения длины пароля и символов.

**Шаг 3: Выполнение атаки**
*   Использование Hydra с параметром `-t` (threads) для скорости, но с осторожностью, чтобы не вызвать блокировку.
*   Мониторинг ответов сервера на предмет блокировок (HTTP 429, SMTP 550/421).

**Шаг 4: Анализ результатов**
*   Успешная аутентификация подтверждается кодом `235` или `250`.
*   Необходимо проверить, можно ли использовать полученные данные для отправки почты (`MAIL FROM`, `RCPT TO`).

### Пример команды Hydra

```bash
hydra -L users.txt -P passwords.txt smtp://mail.target.com -s 25 -V -f
```

*   `-L users.txt`: Файл с именами пользователей.
*   `-P passwords.txt`: Файл с паролями.
*   `-s 25`: Порт SMTP.
*   `-V`: Подробный вывод (verbose).
*   `-f`: Остановить после первой найденной пары.

### Подводные камни

1.  **TLS-обязательность**: Если сервер требует STARTTLS, Hydra должен быть скомпилирован с поддержкой OpenSSL. Без этого подключение будет сброшено.
2.  **Блокировки IP**: Cloudflare, AWS SES, Google Workspace могут блокировать IP-адреса сканеров. Использование прокси-пула обязательно.
3.  **Ложные срабатывания**: Некоторые серверы возвращают `250 OK` для всех адресов в домене, даже если их нет, чтобы запутать атакующих.
4.  **OAuth2**: Для Gmail и Outlook брутфорс пароля через SMTP AUTH не работает, если включён 2FA. Требуется использование App Passwords или кража OAuth-токена.

## Сквозной практический пример: Исследование уязвимости SMTP-сервера на наличие VRFY и подбор паролей

**Исходные условия:**
*   **Цель**: Тестовый SMTP-сервер `smtp.testlab.local` (IP: `192.168.1.100`), работающий на порту 25.
*   **Инструменты**: `nmap`, `swaks`, `hydra`.
*   **Роль**: Пентестер, выполняющий оценку безопасности почтовой инфраструктуры.
*   **Сценарий**: Проверка возможности валидации пользователей через VRFY и последующий подбор учётных данных для авторизованной отправки почты.

### Шаг 1: Определение поддерживаемых механизмов

Действие: Отправка команды `EHLO` для получения списка возможностей сервера.

```bash
swaks --server 192.168.1.100 --ehlo testlab.local --tls --server-output
```

Ожидаемый вывод/результат:
```text
=== Trying 192.168.1.100:25/tcp ...
=== Connected to 192.168.1.100.
<- 220 mail.testlab.local ESMTP Postfix
-> EHLO testlab.local
<- 250-mail.testlab.local
<- 250-PIPELINING
<- 250-SIZE 10240000
<- 250-VRFY
<- 250-ETRN
<- 250-AUTH PLAIN LOGIN
<- 250-AUTH=PLAIN LOGIN
<- 250-ENHANCEDSTATUSCODES
<- 250-8BITMIME
<- 250 DSN
```
*Анализ*: Сервер поддерживает `VRFY` и механизмы аутентификации `PLAIN` и `LOGIN`. Это указывает на потенциальную возможность сбора пользователей и последующего брутфорса.

### Шаг 2: Проверка работы VRFY

Действие: Попытка проверить существование пользователя `admin` и несуществующего пользователя `nonexistent`.

```bash
swaks --server 192.168.1.100 --to admin@testlab.local --body "VRFY admin" --header "HELO testlab.local" --server-output
```

Ожидаемый вывод/результат (если VRFY активен):
```text
<- 250 2.1.5 admin@testlab.local
```

```bash
swaks --server 192.168.1.100 --to nonexistent@testlab.local --body "VRFY nonexistent" --header "HELO testlab.local" --server-output
```

Ожидаемый вывод/результат:
```text
<- 550 5.1.1 <nonexistent@testlab.local>: Recipient address rejected: User unknown
```
*Анализ*: Различие в ответах (`250` vs `550`) подтверждает, что VRFY работает и может быть использован для валидации списка пользователей.

### Шаг 3: Подготовка словаря пользователей

Действие: Генерация списка пользователей на основе публичной информации или стандартных имён.

```bash
echo -e "admin\npostmaster\nwebmaster\ninfo\nsupport" > users.txt
```

### Шаг 4: Брутфорс учётных данных через SMTP AUTH

Действие: Использование Hydra для перебора паролей для пользователя `admin`.

```bash
hydra -l admin -P /usr/share/wordlists/rockyou.txt smtp://192.168.1.100 -s 25 -V -f
```

Ожидаемый вывод/результат (при успешном подборе):
```text
[25][smtp] host: 192.168.1.100   login: admin   password: password123
1 of 1 target successfully completed, 1 valid password found
```

### Шаг 5: Проверка доступа и отправка тестового письма

Действие: Подключение с полученными учётными данными и отправка письма.

```bash
swaks --server 192.168.1.100 --auth --auth-user admin --auth-pass password123 --to victim@testlab.local --body "Test message from pentest" --header "Subject: Pentest Validation" --server-output
```

Ожидаемый вывод/результат:
```text
<- 235 2.7.0 Authentication successful
-> MAIL FROM:<admin@testlab.local>
<- 250 2.1.0 Ok
-> RCPT TO:<victim@testlab.local>
<- 250 2.1.5 Ok
-> DATA
<- 354 End data with <CR><LF>.<CR><LF>
-> .
<- 250 2.0.0 Ok: queued as 12345ABC
```
*Анализ*: Успешная аутентификация и отправка подтверждают компрометацию учётной записи. Атакующий может отправлять письма от имени `admin`.

**Ожидаемый вывод**: Пример демонстрирует полный цикл атаки: от разведки (EHLO) и валидации пользователей (VRFY) до подбора паролей (Hydra) и эксплуатации (отправка письма). В современных системах VRFY обычно отключён, но SMTP AUTH остаётся основным вектором для получения доступа к сервису отправки почты.

## Аналитический вывод

Атака на SMTP через брутфорс учётных данных и эксплуатацию VRFY представляет собой классический вектор компрометации почтовой инфраструктуры. Ключевой вывод заключается в том, что **VRFY** является устаревшим механизмом, который должен быть отключён на всех современных серверах, так как он позволяет злоумышленникам валидировать списки email-адресов без аутентификации. Отключение VRFY и EXPN является первой линией защиты.

Второй важный аспект — **SMTP AUTH**. Несмотря на то, что современные серверы поддерживают безопасные механизмы аутентификации, брутфорс остаётся эффективным против слабых паролей, особенно если не настроены ограничения скорости (rate limiting) и блокировка аккаунтов (account lockout). В облачных средах (Gmail, Office 365) классический брутфорс пароля часто блокируется политикой MFA, однако использование **App Passwords** или кража **OAuth-токенов** обходит эту защиту.

Для защиты от таких атак необходимо:
1.  Отключить VRFY/EXPN.
2.  Требовать шифрования (STARTTLS/TLS) для всех соединений.
3.  Использовать сложные политики паролей и обязательный MFA.
4.  Настроить rate limiting и мониторинг неудачных попыток аутентификации.
5.  Для внутренних сервисов использовать IP-whitelisting вместо паролей, где это возможно.
