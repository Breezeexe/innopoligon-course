# Banner Grabbing: Механизмы, методы и инструменты активной разведки

## Контекст и базовые понятия

Banner grabbing (захват баннера) — это техника активной разведки, заключающаяся в установлении соединения с открытым портом целевой системы и анализе приветственного сообщения (баннера), которое сервис отправляет в ответ на инициализацию взаимодействия. Баннер содержит метаданные о службе: имя программного обеспечения, версию, операционную систему, конфигурационные параметры или криптографические сертификаты. Эта информация критически важна на этапе сбора данных (Reconnaissance) в тестировании на проникновение, так как позволяет идентифицировать потенциальные векторы атаки, основанные на известных уязвимостях (CVE) конкретных версий ПО.

Разведка делится на пассивную и активную. Banner grabbing относится к **активной разведке**, поскольку требует от атакующего (или аудитора) отправки сетевых пакетов целевой системе и ожидания ответа. В отличие от пассивных методов (например, анализа данных Shodan или Censys, которые являются результатом сканирования третьих лиц), активный grabbing генерирует трафик, видимый в лог-файлах целевого хоста и IDS/IPS системах.

Ключевое разграничение терминологии часто вызывает путаницу среди студентов. Необходимо четко разделять **Banner Grabbing** и **Fingerprinting**.

| Характеристика | Banner Grabbing | Fingerprinting (Отпечаток) |
| :--- | :--- | :--- |
| **Суть метода** | Получение текстового ответа сервиса на стандартный запрос. | Анализ множества параметров (таймауты, флаги TCP, TTL, ответы на невалидные запросы) для определения ОС или ПО. |
| **Уровень взаимодействия** | Прикладной (Application Layer) или сеансовый. Часто требует протокольной корректности. | Сетевой (Network Layer) и Транспортный (Transport Layer). Может использовать нестандартные пакеты. |
| **Объем данных** | Узконаправленный: только приветственное сообщение. | Широкий: набор характеристик, формирующих уникальный профиль. |
| **Инструменты** | `telnet`, `nc`, `curl`, `nmap -sV`, `nmap --script banner`. | `nmap -O`, `p0f`, `telnet` (для анализа ответов на ошибки). |
| **Цель** | Узнать *что именно* запущено (версия Apache, OpenSSH). | Узнать *как* работает система (OS, брандмауэр, тип стека TCP). |
| **Риски обнаружения** | Высокие при неправильной настройке (генерирует много логов). | Зависит от метода; SYN-сканирование менее заметно, чем полносессионное. |

Banner grabbing является подмножеством технологии **Service Fingerprinting**. Если fingerprinting отвечает на вопрос «Какая операционная система и какой стек TCP/IP используется?», то banner grabbing отвечает на вопрос «Какая версия веб-сервера или почтового демона запущена?».

В современной инфраструктуре значение banner grabbing трансформировалось. Раньше баннеры содержали полные пути к файлам, имена хостов и точные версии. Сегодня, в рамках лучших практик безопасности (Hardening), администраторы часто скрывают или маскируют эту информацию (например, `Server: nginx` вместо `Server: nginx/1.18.0`). Однако даже скрытые или обрезанные баннеры предоставляют информацию для **OSINT** (Open Source Intelligence) и могут быть использованы для косвенного определения типа ПО по поведению протокола (например, по порядку заголовков HTTP или специфическим кодам ошибок).

## Внутреннее устройство предмета

Banner grabbing работает на основе принципа клиент-серверного взаимодействия. Большинство сетевых сервисов (SMTP, FTP, SSH, HTTP, DNS) при установлении соединения или получении первого запроса отправляют приветственное сообщение. Это сообщение является частью протокола и предназначено для информирования клиента о состоянии сервера и поддерживаемых функциях.

### Механизм формирования и передачи баннера

Процесс захвата баннера состоит из трех фаз:
1.  **Инициализация соединения:** Атакующий устанавливает TCP-соединение (или UDP-пакет) с целевым портом.
2.  **Протокольная инициация:** Для некоторых сервисов (FTP, SMTP, SSH) баннер отправляется сервером автоматически сразу после установки соединения (Handshake). Для других (HTTP) требуется отправить валидный запрос (например, `HEAD` или `GET`).
3.  **Анализ ответа:** Полученный текст парсится для извлечения ключевых полей.

Различные протоколы имеют разные форматы баннеров. Ниже приведена структура типичных ответов для основных сервисов.

#### Структура баннеров по протоколам

| Протокол | Порт (стандартный) | Механизм получения | Формат баннера / Ответа | Пример данных |
| :--- | :--- | :--- | :--- | :--- |
| **SSH** | 22 | Автоматически при подключении | `SSH-<version>-<software> <version>` | `SSH-2.0-OpenSSH_8.2p1 Ubuntu-4ubuntu0.5` |
| **FTP** | 21 | Автоматически при подключении | `<code> <message>` | `220 (vsFTPd 3.0.3)` |
| **SMTP** | 25 | Автоматически при подключении | `220 <hostname> ESMTP <software>` | `220 mail.example.com ESMTP Postfix` |
| **HTTP** | 80, 443 | Требуется запрос (`HEAD`/`GET`) | Заголовок `Server` в ответе | `Server: Apache/2.4.41 (Ubuntu)` |
| **DNS** | 53 | UDP/TCP запрос к корневому серверу | Ответ с информацией о версии (если разрешено) | `version.bind. CH TXT "9.11.5"` |
| **Telnet** | 23 | Автоматически при подключении | Строка приветствия или запрос логина | `Microsoft Telnet Server` |

### Типы баннеров и их информативность

Баннеры можно классифицировать по уровню детализации и типу передаваемой информации:

1.  **Версионные баннеры:** Содержат точную версию ПО. Наиболее ценны для атакующих, так как позволяют искать эксплойты в базах данных (Exploit-DB, CVE Details).
    *   *Пример:* `Apache/2.4.49` (уязвимость CVE-2021-41773).
2.  **Конфигурационные баннеры:** Содержат имена хостов, пути к директориям, имена баз данных.
    *   *Пример:* `220 ftp.company.local FTP server ready`.
3.  **Криптографические баннеры:** Содержат параметры шифрования, используемые сервисом.
    *   *Пример:* В SSL/TLS handshake — список поддерживаемых шифров (Cipher Suites) и версий протокола.
4.  **Скрытые/Маскированные баннеры:** Измененные администратором для сокрытия информации.
    *   *Пример:* `Server: Microsoft-IIS/10.0` (заменено на `Server: WebServer`).
    *   *Пример:* `Server: nginx` (без версии).

### Ограничения и методы обхода

Современные системы защиты используют несколько методов противодействия banner grabbing:

*   **Обфускация заголовков:** Изменение значения поля `Server` на нейтральное или ложное (например, `Server: Apache` на реальном Nginx).
*   **Удаление заголовков:** Полное отсутствие заголовка `Server` в HTTP-ответе.
*   **Rate Limiting:** Блокировка IP-адреса после нескольких неудачных попыток подключения.
*   **Honeypots (Tarpits):** Имитация сервиса с искусственной задержкой ответа, чтобы выявить автоматизированные сканеры.
*   **Протокольные шлюзы:** Использование WAF (Web Application Firewall), который возвращает стандартные ошибки, скрывая реальную информацию о бэкенде.

Для обхода маскировки применяются методы **HTTP Fingerprinting**: анализ порядка заголовков, специфических ошибок (например, код 404 с уникальной структурой HTML), заголовков `X-Powered-By`, `X-AspNet-Version` и других косвенных признаков.

## Применение и работа с предметом

На практике banner grabbing реализуется через ручные инструменты для глубокого анализа или автоматизированные сканеры для массового сбора данных. Выбор инструмента зависит от цели: верификация конкретной уязвимости или обзор инфраструктуры.

### Ручной сбор баннеров

Ручные инструменты позволяют контролировать процесс, видеть сырой трафик и избегать эвристик автоматических сканеров.

#### 1. Netcat (nc)
Netcat является универсальным инструментом для работы с сетевыми соединениями. Он позволяет подключаться к любому порту и отправлять произвольные данные.

*   **Для SSH/FTP/SMTP:** Просто подключиться к порту. Сервер сам отправит баннер.
    ```bash
    nc -v -w 3 <target_ip> <port>
    ```
*   **Для HTTP:** Необходимо отправить корректный HTTP-запрос. Команда `HEAD` предпочтительнее `GET`, так как она запрашивает только заголовки, не загружая тело страницы, что быстрее и менее заметно.
    ```bash
    echo -e "HEAD / HTTP/1.1\r\nHost: <target_domain>\r\n\r\n" | nc -v -w 5 <target_ip> 80
    ```
    *Примечание:* `\r\n` (CR/LF) критически важен для корректности HTTP-запроса.

#### 2. Telnet
Классический инструмент, хотя в современных ОС может быть отключен по умолчанию. Полезен для протоколов, требующих текстового ввода после подключения (например, SMTP для проверки `EHLO`).

```bash
telnet <target_ip> 25
# После подключения:
EHLO test.com
```

#### 3. Curl
Удобен для HTTP/HTTPS сервисов. Флаг `-I` запрашивает только заголовки.

```bash
curl -I http://<target_ip>
```

### Автоматизированный сбор (Nmap)

Nmap — стандарт де-факто для сетевой разведки. Он использует базу данных скриптов (NSE) для автоматического захвата баннеров.

#### 1. Встроенный сканер версий (`-sV`)
Nmap отправляет множество специфичных запросов к каждому открытому порту и сравнивает ответы с базой данных.

```bash
nmap -sV --version-intensity 9 -p 22,80,443,3306 <target_ip>
```
*   `-sV`: Включает определение версий.
*   `--version-intensity`: От 0 (только базовая проверка) до 9 (максимальное количество тестов). 9 рекомендуется для точности, но замедляет сканирование.

#### 2. NSE-скрипты
Скрипты Nmap предоставляют более детализированную информацию, чем `-sV`.

*   `banner.nse`: Стандартный скрипт для захвата баннеров всех сервисов.
*   `http-headers.nse`: Специализированный скрипт для HTTP, возвращает все заголовки ответа.
*   `ssl-cert.nse`: Извлекает информацию из SSL-сертификатов (CN, O, Issuer, Dates).

```bash
nmap --script banner.nse -p 21,22,25,80,443 <target_ip>
nmap --script http-headers.nse -p 80,8080 <target_ip>
nmap --script ssl-cert.nse -p 443 <target_ip>
```

### Анализ трафика (Wireshark)

Для понимания того, как выглядит banner grabbing «в воздухе», используется анализатор пакетов. Это позволяет выявить, какие именно пакеты отправляются и какие ответы приходят, а также обнаружить признаки маскировки или WAF.

```bash
# Захват трафика на интерфейсе eth0
sudo wireshark -i eth0 -f "host <target_ip>"
```
В Wireshark следует фильтровать по TCP-потоку (Follow TCP Stream), чтобы увидеть полный контекст рукопожатия и обмена данными.

### Типичные ошибки и подводные камни

1.  **Игнорирование TLS/SSL:** Для HTTPS-сервисов простой HTTP-запрос не сработает. Необходимо использовать инструменты, поддерживающие TLS (например, `openssl s_client` или `nmap --script ssl-cert`).
2.  **Неверный формат запроса:** Отправка HTTP/1.1 запроса без заголовка `Host` может привести к ошибке 400 Bad Request или возврату страницы по умолчанию, а не баннеру сервера.
3.  **Блокировка по IP:** Частые подключения с одного IP могут привести к бану. Использование рандомизации задержек (`--randomize-hosts` в Nmap) или прокси помогает избежать этого.
4.  **Ложные срабатывания:** Некоторые сервисы (например, балансировщики нагрузки) могут возвращать баннер, не соответствующий реальному бэкенду. Всегда требуется верификация.

## Сквозной практический пример: Комплексная разведка веб-сервиса

**Исходные условия:**
*   **Цель:** Веб-сервер с IP-адресом `192.168.1.100` (локальная лабораторная среда).
*   **Роль:** Тестировщик на проникновение (Red Team).
*   **Инструменты:** `nmap`, `curl`, `nc`, `openssl`.
*   **Задача:** Определить тип и версию веб-сервера, проверить наличие HTTPS, собрать метаданные для поиска уязвимостей.

### Шаг 1: Быстрая проверка открытых портов и версий с помощью Nmap

Первым делом необходимо определить, какие порты открыты и какие сервисы на них работают. Используем `nmap` с флагом определения версий.

```bash
nmap -sV --version-intensity 8 -p 80,443,8080 192.168.1.100
```

**Ожидаемый вывод:**
```text
PORT     STATE SERVICE     VERSION
80/tcp   open  http        Apache httpd 2.4.49
443/tcp  open  https       Apache httpd 2.4.49
8080/tcp open  http-proxy  nginx 1.18.0
```
*Анализ:* Nmap определил Apache 2.4.49 на портах 80/443 и nginx на 8080. Версия Apache 2.4.49 известна критической уязвимостью (CVE-2021-41773).

### Шаг 2: Ручная верификация HTTP-заголовков через Curl

Для подтверждения данных Nmap и получения дополнительных заголовков (например, `X-Powered-By`, `Server`), используем `curl`.

```bash
curl -I http://192.168.1.100
```

**Ожидаемый вывод:**
```http
HTTP/1.1 200 OK
Date: Mon, 01 Jan 2024 12:00:00 GMT
Server: Apache/2.4.49 (Ubuntu)
X-Powered-By: PHP/7.4.3
Content-Type: text/html; charset=UTF-8
```
*Анализ:* Заголовок `Server` подтверждает Apache 2.4.49. Заголовок `X-Powered-By` раскрывает версию PHP (7.4.3), что также является ценной информацией для поиска эксплойтов.

### Шаг 3: Анализ SSL/TLS сертификата через OpenSSL

Проверяем безопасность HTTPS-соединения и детали сертификата.

```bash
echo | openssl s_client -connect 192.168.1.100:443 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

**Ожидаемый вывод:**
```text
subject=CN = example.com
issuer=CN = Let's Encrypt Authority X3
notBefore=Jan  1 00:00:00 2024 GMT
notAfter=Apr  1 00:00:00 2024 GMT
```
*Анализ:* Сертификат валиден, выдан Let's Encrypt. Дата истечения (`notAfter`) важна для планирования атак, связанных с истечением срока действия сертификата (если сервис не обновлен).

### Шаг 4: Проверка скрытых сервисов через Netcat

Проверяем порт 8080, который Nmap определил как nginx. Поскольку это не стандартный порт для веб-сервера, возможно, это прокси или админ-панель.

```bash
echo -e "HEAD / HTTP/1.1\r\nHost: 192.168.1.100\r\n\r\n" | nc -v -w 3 192.168.1.100 8080
```

**Ожидаемый вывод:**
```text
Connection to 192.168.1.100 8080 port [tcp/*] succeeded!
HTTP/1.1 200 OK
Server: nginx/1.18.0
Content-Type: text/html
Content-Length: 612
...
```
*Анализ:* Подтверждено, что на 8080 работает nginx 1.18.0. Это может быть бэкенд-сервис, не доступный через основной домен.

### Шаг 5: Поиск уязвимостей через NSE-скрипты

Используем специализированные скрипты Nmap для поиска известных уязвимостей, связанных с баннерами.

```bash
nmap --script http-vuln-cve2021-41773 -p 80 192.168.1.100
```

**Ожидаемый вывод:**
```text
PORT   STATE SERVICE VERSION
80/tcp open  http    Apache httpd 2.4.49
| http-vuln-cve2021-41773:
|   VULNERABLE:
|   Apache HTTP Server 2.4.49 Path Traversal
|     State: VULNERABLE (Exploitable)
|     IDs:  CVE:CVE-2021-41773
|     Risk factor: HIGH
|     Description:
|     Apache HTTP Server 2.4.49 and 2.4.50 allow path traversal...
|_    https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2021-41773
```
*Анализ:* Скрипт подтвердил наличие критической уязвимости. Это результат точного совпадения баннера, полученного на шагах 1 и 2, с базой данных уязвимостей.

**Ожидаемый вывод:**
Пример демонстрирует полный цикл активной разведки: от сканирования до верификации и поиска уязвимостей. Banner grabbing позволил идентифицировать Apache 2.4.49 и PHP 7.4.3, что напрямую привело к обнаружению критической уязвимости. Без точного определения версии (fingerprinting) эта уязвимость могла бы остаться незамеченной.

## Аналитический вывод

Banner grabbing остается фундаментальным методом активной разведки в тестировании на проникновение, несмотря на развитие технологий маскировки. Его ценность заключается в прямой связи между полученными метаданными и базой знаний об уязвимостях. Точное определение версии ПО позволяет атакующим переходить от общего сканирования к целенаправленному поиску эксплойтов, экономя время и снижая шум в сети.

Ключевым аспектом современного применения banner grabbing является понимание ограничений. Администраторы активно используют обфускацию заголовков, WAF и honeypots, что делает простой анализ баннеров недостаточным. Поэтому техника должна применяться в комплексе с другими методами fingerprinting (анализ заголовков, ошибок, TLS-параметров) и верифицироваться вручную. Для защитников (Blue Team) мониторинг баннеров и их аномалий является важным индикатором компрометации (IoC), так как злоумышленники часто оставляют следы в логах при попытках захвата баннеров.
