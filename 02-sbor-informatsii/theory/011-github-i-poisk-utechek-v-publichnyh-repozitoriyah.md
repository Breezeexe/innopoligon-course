# Пассивная разведка через GitHub: поиск утечек в публичных репозиториях

## Контекст и базовые понятия

Публичный GitHub представляет собой крупнейший в мире агрегатор исходного кода, конфигураций и документации, что делает его одновременно ключевым инструментом для разработчиков и ценным источником разведывательной информации (OSINT) для специалистов по информационной безопасности. В контексте тестирования на проникновение (pentest) и пассивной разведки (passive reconnaissance) GitHub используется для сбора индикаторов компрометации (IoC), выявления уязвимых зависимостей, анализа архитектуры целевой системы и поиска скомпрометированных учетных данных. Понятие «утечка» (secret leak) в данном контексте означает несанкционированное попадание конфиденциальных данных (секретов) в публичное пространство, где они становятся доступны любому пользователю, включая злоумышленников.

Ключевое разграничение в данной теме проводится между **активной** и **пассивной** разведкой. Активная разведка предполагает прямое взаимодействие с целевой инфраструктурой (сканирование портов, обход WAF, взаимодействие с API с целью получения информации), что оставляет следы в логах и может быть заблокировано средствами защиты. Пассивная разведка через GitHub не требует взаимодействия с целевой системой в момент поиска; информация извлекается из уже существующих, публично доступных артефактов. Это делает метод безопасным для аудитора с точки зрения обнаружения и не влияющим на работоспособность цели.

Важно различать понятия **hardcoded secrets** (жестко закодированные секреты) и **configuration drift** (дрейф конфигурации). Hardcoded secrets — это непосредственно учетные данные (API keys, пароли, токены), встроенные в код. Configuration drift — это расхождение между конфигурацией в репозитории и реальной средой, которое может привести к утечке, но само по себе не является секретом. Также следует отличать **public repositories** (полностью открытые) от **private repositories** (закрытых), доступ к которым может быть получен только через инсайдерскую угрозу или компрометацию аккаунта разработчика. В рамках пассивной разведки фокус строго на публичных данных.

Существует путаница между терминами **Secret Scanning** (функция GitHub) и **Secret Sprawl** (проблема безопасности). Secret Scanning — это встроенный механизм платформы GitHub, который автоматически сканирует публичные репозитории на наличие известных паттернов секретов. Secret Sprawl — это явление неконтролируемого распространения секретов по множеству репозиториев, систем и команд, что усложняет их обнаружение и управление жизненным циклом. Для аудитора понимание этой разницы критично: он использует методы, аналогичные Secret Scanning, но вне платформы, чтобы найти то, что пропустили встроенные средства или что было удалено из истории коммитов.

| Сущность | Определение | Область применения в разведке | Роль в безопасности |
| :--- | :--- | :--- | :--- |
| **Public Repository** | Репозиторий с режимом доступа `public`, доступный для чтения любому пользователю интернета. | Основной источник данных для OSINT. Содержит код, конфиги, логи, документацию. | Уязвимая поверхность (Attack Surface). Источник IoC. |
| **Hardcoded Secret** | Учетные данные (ключ, пароль, токен), зашитые непосредственно в исходный код или файл конфигурации. | Цель поиска. Позволяет получить доступ к внешним сервисам (AWS, GCP, SaaS). | Критическая уязвимость. Прямой вектор компрометации. |
| **Git History** | Полная история изменений коммитов в репозитории, включая удаленные файлы и строки. | Источник «затертых» секретов. Секреты остаются доступны даже после удаления из текущей версии. | Ложное чувство безопасности у разработчиков. |
| **Secret Scanning** | Автоматизированный процесс GitHub по поиску известных паттернов секретов в публичных репозиториях. | Механизм защиты, который можно обойти или который может быть отключен/не настроен. | Инструмент обнаружения утечек со стороны платформы. |
| **Secret Sprawl** | Феномен массового распространения секретов по множеству репозиториев, систем и команд без централизованного контроля. | Контекст проблемы. Объясняет, почему ручная проверка недостаточна и почему нужны автоматизированные сканеры. | Фактор риска, увеличивающий вероятность успешной атаки. |

Понимание этих базовых концепций позволяет аудитору не просто искать «ключи», а анализировать контекст их использования, оценивать риск компрометации и строить гипотезы о внутренней архитектуре организации на основе публичных артефактов.

## Внутреннее устройство предмета

Внутреннее устройство процесса поиска утечек на GitHub базируется на нескольких технологических слоях: структуре системы контроля версий Git, механизмах индексации платформы, форматах секретов и методах их обнаружения.

### Структура Git и персистентность данных

Фундаментальной особенностью, делающей GitHub привлекательным для разведки, является архитектура Git. Git хранит данные в виде снимков состояния (snapshots) каждого коммита. Когда разработчик удаляет файл или строку с секретом и отправляет новый коммит, старый секрет не стирается физически из репозитория. Он остается в объектной базе данных (object database) до тех пор, пока не будет выполнен `git gc` (garbage collection) с принудительным удалением ссылок, что на публичных репозиториях происходит редко и не мгновенно. Более того, если репозиторий был форкнут (forked) или клонирован кем-либо до удаления секрета, копия с секретом сохраняется в сети форков. Это создает «хвост» уязвимости, который невозможно устранить простым удалением файла из текущей ветки.

### Форматы и классификация секретов

Секреты делятся на несколько классов в зависимости от их назначения и формата. Для эффективного поиска необходимо понимать структуру этих форматов.

1.  **API Keys/Tokens**: Обычно представляют собой строки символов с определенной длиной и префиксом. Примеры:
    *   AWS Access Key ID: `AKIAIOSFODNN7EXAMPLE` (префикс `AKIA`, длина 20 символов).
    *   GitHub Personal Access Token (classic): `ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx` (префикс `ghp`, длина 40 символов).
    *   Slack Token: `xoxb-xxxxxxxxxxxx-xxxxxxxxxxxx-xxxxxxxxxxxxxxx` (формат `xoxb-`).
2.  **Cloud Credentials**:
    *   AWS Secret Access Key: 40 символов, base64-like.
    *   Google Cloud Service Account Key: JSON-объект с полями `type`, `project_id`, `private_key`, `client_email`.
3.  **Database Connection Strings**:
    *   PostgreSQL: `postgresql://user:password@host:port/dbname`.
    *   MongoDB: `mongodb+srv://username:password@cluster.mongodb.net/db`.
4.  **Cryptographic Keys**:
    *   RSA Private Key: Начинается с `-----BEGIN RSA PRIVATE KEY-----`.
    *   SSH Private Key: Начинается с `-----BEGIN OPENSSH PRIVATE KEY-----`.

### Механизмы обнаружения (Detection Mechanisms)

Существует два основных подхода к поиску утечек: **Pattern Matching** (поиск по шаблонам) и **Entropy Analysis** (анализ энтропии).

*   **Pattern Matching**: Использует регулярные выражения (Regex) для поиска известных форматов. Например, поиск паттерна `AKIA[0-9A-Z]{16}` для AWS ключей. Этот метод высокоточен, но требует постоянного обновления базы паттернов.
*   **Entropy Analysis**: Основан на том, что случайные строки (секреты) имеют высокую энтропию (непредсказуемость), в отличие от обычного кода. Алгоритмы (например, в TruffleHog) вычисляют энтропию Шеннона для каждой строки. Если энтропия превышает порог (например, 4.5), строка помечается как потенциальный секрет. Этот метод позволяет находить неизвестные ранее форматы секретов, но дает высокий уровень ложных срабатываний (false positives).

### Архитектура сканирования

Процесс пассивной разведки через GitHub можно представить как конвейер данных:

```text
[Источник: GitHub API / Git Clone] 
       │
       ▼
[Индексатор / Парсер] ──(извлечение коммитов, файлов, истории)──▶ [База данных артефактов]
       │
       ▼
[Детектор Секретов] 
       ├──▶ [Regex Engine] (поиск известных паттернов)
       └──▶ [Entropy Analyzer] (поиск высокоэнтропийных строк)
       │
       ▼
[Фильтр / Верификатор] ──(проверка на ложные срабатывания, валидация ключей)──▶ [Результат: IoC / Утечка]
```

Инструменты вроде `TruffleHog`, `Gitleaks` и `GitGuardian` реализуют именно эту архитектуру. Они не просто ищут текст, а анализируют всю историю репозитория, включая удаленные коммиты, и применяют множественные детекторы.

### Сравнительная таблица методов обнаружения

| Метод обнаружения | Принцип работы | Преимущества | Недостатки | Типичные инструменты |
| :--- | :--- | :--- | :--- | :--- |
| **Regex Matching** | Поиск строк, соответствующих регулярному выражению. | Высокая точность для известных форматов. Низкая нагрузка. | Не находит новые/кастомные форматы. Требует обновления правил. | Gitleaks, TruffleHog (по умолчанию) |
| **Entropy Analysis** | Вычисление энтропии Шеннона для каждой строки. | Находит неизвестные форматы секретов. | Высокий уровень ложных срабатываний. Требует верификации. | TruffleHog (режим `--entropy`) |
| **Semantic Analysis** | Анализ контекста переменной (имя, тип). | Снижает ложные срабатывания. | Сложность реализации. Зависит от языка программирования. | GitGuardian, CodeQL |
| **Token Validation** | Попытка использования найденного ключа для аутентификации. | Подтверждает работоспособность секрета. | Риск обнаружения атакующим. Требует доступа к интернету. | `keyhacks`, `nuclei` templates |

Понимание этих внутренних механизмов позволяет аудитору выбирать правильные инструменты и настраивать их под конкретную цель, избегая избыточных запросов к API и ложных срабатываний.

## Применение и работа с предметом

На практике пассивная разведка через GitHub требует использования специализированных инструментов и соблюдения этических и технических ограничений. Аудитор должен уметь не только находить секреты, но и верифицировать их, оценивать контекст и документировать находки.

### Инструментарий и его функции

1.  **TruffleHog**: Мощный инструмент для поиска секретов в Git-репозиториях. Поддерживает поиск по истории коммитов, анализ энтропии и интеграцию с CI/CD. Используется для глубокого анализа локальных или клонированных репозиториев.
2.  **Gitleaks**: Инструмент, ориентированный на скорость и интеграцию в пайплайны. Использует конфигурационные файлы для определения правил поиска. Хорош для быстрого сканирования больших объемов кода.
3.  **GitGuardian CLI (`ggshield`)**: Командная строка от GitGuardian, предоставляющая доступ к их базе данных известных утечек. Позволяет проверять секреты на наличие в публичных утечках без их раскрытия (zero-knowledge).
4.  **GitHub Search API**: Официальный API для поиска по репозиториям. Позволяет выполнять сложные запросы с использованием операторов `in:file`, `in:commit`, `language:`, `extension:`.
5.  **HasMySecretLeaked**: Веб-инструмент от GitGuardian для проверки, был ли конкретный секрет публично скомпрометирован.

### Типовые операции и процедуры

#### 1. Поиск по конкретным доменам или именам разработчиков

Часто известно имя компании или домен электронной почты разработчика. Аудитор может использовать GitHub Search API для поиска всех публичных репозиториев, связанных с этим доменом.

```bash
# Пример запроса через GitHub Search API (URL-encoded)
# Поиск публичных репозиториев, содержащих домен "example.com" в коде
curl -s "https://api.github.com/search/repositories?q=example.com+in:code+language:python&per_page=100"
```

Этот запрос возвращает список репозиториев, где разработчики с доменом `example.com` оставляли комментарии или код, содержащий этот домен. Это может указать на внутренние сервисы, API эндпоинты или конфигурации.

#### 2. Сканирование локального репозитория на наличие секретов

Если у аудитора есть доступ к исходному коду (например, через публичный репозиторий или утечку), он запускает сканер локально.

```bash
# Использование TruffleHog для сканирования репозитория
trufflehog git https://github.com/target-org/target-repo.git --json | jq '.[0]'
```

Вывод будет содержать информацию о найденном секрете, типе, файле и коммите, где он был обнаружен.

#### 3. Верификация найденного секрета

Найденный секрет нужно проверить на работоспособность. Для этого используются специализированные скрипты или инструменты вроде `nuclei`.

```bash
# Пример проверки AWS ключа через nuclei template
nuclei -t aws-creds.yaml -var key="AKIAIOSFODNN7EXAMPLE" -var secret="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
```

Если template возвращает успешный ответ, секрет валиден.

### Типичные ошибки и подводные камни

*   **Игнорирование истории коммитов**: Многие аудиторы ищут секреты только в текущей версии файлов. Однако 80% утечек находятся в истории коммитов. Инструменты должны поддерживать `--all-history` или аналогичные флаги.
*   **Ложные срабатывания**: Тестовые ключи, примеры из документации и публичные ключи (public keys) часто маскируются под секреты. Важно настраивать фильтры для исключения известных публичных ключей (например, GitHub public keys).
*   **Обход сканеров**: Разработчики могут использовать обфускацию, разделение секретов на части или хранение в переменных окружения, которые не сканируются. Аудитор должен искать не только прямые совпадения, но и косвенные признаки.
*   **Нарушение Rate Limits**: GitHub API имеет строгие ограничения на количество запросов. Аудитор должен использовать кэширование, пагинацию и, при необходимости, аутентификацию для увеличения лимитов.

### Паттерны использования в пайплайне разведки

1.  **Сбор**: Использование GitHub Search API для сбора списка репозиториев по ключевым словам, доменам, именам.
2.  **Клонирование**: Скачивание репозиториев с сохранением истории (`git clone --mirror`).
3.  **Сканирование**: Запуск TruffleHog/Gitleaks на клонированных репозиториях.
4.  **Фильтрация**: Удаление ложных срабатываний (публичные ключи, тестовые данные).
5.  **Верификация**: Проверка оставшихся секретов на работоспособность.
6.  **Документирование**: Фиксация найденных IoC, оценка риска и рекомендации по устранению.

Этот подход обеспечивает систематический и воспроизводимый процесс пассивной разведки через GitHub.

## Сквозной практический пример: Поиск и верификация AWS IAM Credentials в публичном репозитории

**Исходные условия**:
*   **Среда**: Linux (Ubuntu 22.04), Kali Linux.
*   **Инструменты**: `git`, `trufflehog`, `aws-cli` (для верификации), `jq`.
*   **Роль**: Аудитор информационной безопасности, проводящий пассивную разведку для целевой организации `TargetCorp`.
*   **Сценарий**: Известно, что разработчики `TargetCorp` используют публичные репозитории для open-source проектов. Необходимо найти потенциальные утечки AWS IAM credentials.

### Шаг 1: Поиск репозиториев, связанных с целевой организацией

Используем GitHub Search API для поиска публичных репозиториев, содержащих домен `targetcorp.com` в коде или комментариях.

```bash
# Запрос к GitHub Search API
curl -s "https://api.github.com/search/repositories?q=targetcorp.com+in:code+language:python&per_page=10" | jq '.items[] | {name: .name, url: .html_url}'
```

**Ожидаемый вывод**:
Список репозиториев, где разработчики с доменом `targetcorp.com` оставляли код. Например:
```json
{
  "name": "targetcorp-data-pipeline",
  "url": "https://github.com/dev-user/targetcorp-data-pipeline"
}
```
Этот шаг позволяет сузить круг поиска до релевантных репозиториев.

### Шаг 2: Клонирование репозитория с сохранением истории

Клонируем найденный репозиторий с полным сохранением истории коммитов, чтобы найти удаленные секреты.

```bash
git clone --mirror https://github.com/dev-user/targetcorp-data-pipeline.git targetcorp-mirror.git
```

**Ожидаемый вывод**:
Локальная директория `targetcorp-mirror.git`, содержащая полную объектную базу Git.

### Шаг 3: Сканирование репозитория на наличие AWS IAM Credentials

Используем TruffleHog для сканирования клонированного репозитория на наличие AWS Access Key ID.

```bash
trufflehog git file://./targetcorp-mirror.git --json | jq 'select(.DetectorType == "AWS")'
```

**Ожидаемый вывод**:
JSON-объект, содержащий информацию о найденном секрете:
```json
{
  "Type": "AWS Access Key ID",
  "Value": "AKIAIOSFODNN7EXAMPLE",
  "File": "src/config/aws.py",
  "Commit": "a1b2c3d4e5f6",
  "Message": "Initial commit",
  "Timestamp": "2023-01-15T10:00:00Z"
}
```
Этот вывод указывает на то, что AWS ключ был закоммичен в прошлом и, возможно, удален в более поздних коммитах, но остался в истории.

### Шаг 4: Верификация найденного секрета

Проверяем, является ли найденный ключ рабочим, используя AWS CLI.

```bash
aws sts get-caller-identity --access-key-id AKIAIOSFODNN7EXAMPLE --secret-access-key wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
```

**Ожидаемый вывод**:
*   **Вариант А (Секрет невалиден)**: `An error occurred (InvalidClientTokenId) ...` — ключ был отозван или никогда не существовал.
*   **Вариант Б (Секрет валиден)**: `{"UserId": "AIDAI23X...", "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/dev-user"}` — ключ активен и принадлежит пользователю `dev-user`.

В данном примере предположим, что ключ валиден, что подтверждает успешную утечку.

### Шаг 5: Анализ контекста и документирование

Анализируем коммит, в котором был найден ключ, чтобы понять контекст.

```bash
git show a1b2c3d4e5f6 -- src/config/aws.py
```

**Ожидаемый вывод**:
Показывает, что ключ был добавлен как часть конфигурации для доступа к S3. Это указывает на то, что разработчик использовал жестко закодированные учетные данные вместо IAM Roles или Secrets Manager.

**Ожидаемый вывод примера**:
Пример демонстрирует полный цикл пассивной разведки: от поиска релевантных репозиториев до верификации найденных утечек. Найденный AWS IAM Access Key ID является критической уязвимостью, позволяющей злоумышленнику получить доступ к облачной инфраструктуре `TargetCorp`. Аудитор должен немедленно сообщить об этом владельцам репозитория и организации, рекомендуя отозвать ключ и использовать IAM Roles.

## Аналитический вывод

Пассивная разведка через GitHub является мощным инструментом в арсенале специалиста по информационной безопасности, позволяющим выявлять критические уязвимости до того, как ими воспользуются злоумышленники. Ключевым фактором эффективности этого метода является понимание архитектуры Git и персистентности данных: секреты, удаленные из текущей версии кода, остаются доступными в истории коммитов и форках, создавая долгосрочные риски. Использование комбинированного подхода, включающего поиск по паттернам (Regex) и анализ энтропии, позволяет обнаруживать как известные, так и неизвестные форматы секретов. Однако высокий уровень ложных срабатываний требует обязательного этапа верификации найденных данных с использованием специализированных инструментов. Интеграция таких практик в процесс разработки (Shift Left Security) и использование встроенных механизмов GitHub Secret Scanning являются наиболее эффективными способами предотвращения утечек. Для аудиторов важно соблюдать этические нормы и ограничения API, фокусируясь на анализе публично доступных данных без активного взаимодействия с целевой инфраструктурой.
