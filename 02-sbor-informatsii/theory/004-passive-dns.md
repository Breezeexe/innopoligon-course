# Passive DNS: сбор данных о доменных именах без активных запросов

## 1. Пассивный DNS как инструмент пассивной разведки: суть, цели и границы метода

Пассивный DNS (Passive DNS, pDNS) — это система сбора и архивирования ответов DNS-серверов, получаемых в результате реальных запросов пользователей, а не путём целенаправленного опроса авторитативных серверов исследуемого домена. В отличие от активного DNS-запроса, когда пентестер напрямую обращается к резолверу или авторитативному серверу, пассивный DNS извлекает информацию из сторонних хранилищ, фиксировавших фактические сопоставления «домен–IP» в прошлом. Такой подход обеспечивает полную скрытность — целевая система не получает ни одного пакета и не регистрирует активность в логах.

Пассивный DNS занимает особое место в цепочке пассивного сбора информации (OSINT). С помощью него решаются задачи, недоступные другим бесконтактным методам: восстановление исторической картины инфраструктуры, выявление «засветившихся» поддоменов, связывание доменов через общие IP-адреса, обнаружение быстрых миграций (fast-flux) и атрибуция атакующей инфраструктуры. Если WHOIS раскрывает момент регистрации и статические реквизиты владельца, а Certificate Transparency — факт выдачи сертификата, то пассивный DNS показывает динамику реального использования имён: когда и на какой IP указывал домен, какие ещё имена жили на том же сервере, как менялись NS-записи.

Основное различие методов сбора DNS-данных отражено в таблице ниже.

| Метод                                 | Характер взаимодействия                             | Источник данных                                                                 | Видимый временной срез            | Примеры инструментов / API                  |
|---------------------------------------|-----------------------------------------------------|---------------------------------------------------------------------------------|-----------------------------------|---------------------------------------------|
| Активный DNS-запрос                    | Прямой опрос резолвера или авторитативного сервера  | Текущее состояние зоны (A, AAAA, MX и т.д.)                                     | Только настоящий момент           | `dig`, `nslookup`, императивные API         |
| Пассивный DNS (Passive DNS)           | Запрос к сторонней БД, собранной из пассивных датчиков | Записи, извлечённые из трафика рекурсивных резолверов, сенсоров, вредоносного ПО | История: first_seen – last_seen   | SecurityTrails, VirusTotal, DNSDB, PassiveTotal |
| WHOIS                                  | Опрос регистратора / WHOIS-сервера                  | Регистрационные данные: registrar, даты, контакты                                | Текущий и исторический (при наличии) | `whois`, whois API                          |
| Certificate Transparency Logs (crt.sh) | Запрос к публичным логам центров сертификации        | Записи о выданных TLS/SSL-сертификатах, включая список поддоменов                | Момент выдачи сертификата         | crt.sh, Merkle, API Censys                  |

Почему же пассивный DNS относят именно к пассивной разведке, несмотря на то что пакет к базе данных всё равно отправляется? Ключевой критерий здесь — отсутствие взаимодействия с целевой системой. Запрос, отправленный к серверу SecurityTrails с целью узнать историю резолвинга домена `example.com`, видит `example.com` не в реальном времени, а как запись о наблюдении, сделанном кем-то другим в прошлом. Цель не получает ни DNS-запроса, ни пакетов к своему авторитативному серверу, ни каких-либо иных индикаторов сканирования. Именно этот признак отделяет pDNS от методов активной разведки, таких как AXFR-трансфер зон (когда повезёт) или подбор поддоменов по словарю, генерирующий разрешения через открытые резолверы.

Практическая ценность пассивного DNS в пентесте обусловлена несколькими факторами:
- **Историческая глубина.** Базы данных pDNS хранят записи месяцами и годами. Специалист может увидеть, на каком хостинге располагался корпоративный портал до миграции в облако, и проверить, не остались ли там забытые поддомены, по-прежнему ведущие к актуальным ресурсам.
- **Связывание инфраструктуры.** Один IP-адрес может обслуживать несколько доменов. Найдя IP, к которому привязан изучаемый домен, и запросив обратный поиск по этому IP в пассивном DNS, можно обнаружить десятки других доменов — часть из них может относиться к тому же владельцу или раскрывать служебные хосты.
- **Обход ограничений.** Некоторые DNS-серверы не отвечают на запросы ANY или блокируют подозрительно частые обращения. Пассивный DNS не зависит от текущего поведения серверов цели, потому что опирается на данные, записанные нейтральными наблюдателями.
- **Обнаружение аномалий.** Быстрое переключения IP (fast-flux), внезапное появление поддоменов, смена NS-серверов — все эти события фиксируются временными метками pDNS и могут служить индикаторами компрометации или подготовки фишинговой кампании.

Таким образом, пассивный DNS — не просто ещё один источник данных, а метод, позволяющий заглянуть в «тень» DNS-трафика, восстановить картину эволюции внешнего периметра и найти точки входа, невидимые для активного сканирования.

## 2. Архитектура и внутреннее устройство систем Passive DNS

Любая система пассивного DNS состоит из трёх логических слоёв: **датчики сбора**, **хранилище и нормализация**, **интерфейс доступа**. Понимание того, как формируются записи, какие поля они содержат и с какими ограничениями сталкивается аналитик, позволяет грамотно интерпретировать получаемые данные и избегать ложных выводов.

### 2.1 Датчики и источники данных

Записи в pDNS-базах появляются благодаря множеству распределённых сенсоров, которые фиксируют DNS-трафик на разных уровнях интернета. Основные категории сенсоров:

1. **Рекурсивные DNS-резолверы крупных провайдеров и публичных сервисов.** Сервисы типа [Google Public DNS](https://developers.google.com/speed/public-dns), [Cloudflare Resolver](https://www.cloudflare.com/dns/), [Cisco Umbrella](https://umbrella.cisco.com/) ежедневно обрабатывают колоссальные объёмы запросов от конечных пользователей. Часть этой информации — пары «запрашиваемое доменное имя → IP-адрес, отданный в ответе» — деперсонализируется и передаётся в pDNS-агрегаторы. Такие данные охватывают широчайший спектр доменов и отражают картину, близкую к реальному использованию интернета.

2. **Исследовательские сенсоры и ханипоты.** Компании, специализирующиеся на threat intelligence (например, [Farsight Security (DNSDB)](https://www.farsightsecurity.com/solutions/dnsdb/), [VirusTotal](https://www.virustotal.com), консорциум [PassiveTotal](https://www.riskiq.com/products/passivetotal/)), разворачивают собственные сети пассивного наблюдения. Они могут включать:
   - Специализированные резолверы, размещённые в разных географических регионах.
   - Ханипоты, эмулирующие уязвимые сервисы, которые при атаке генерируют DNS-запросы к C2-серверам.
   - Зонды для сбора и анализа спам-писем, где домены извлекаются из ссылок и проверяются.

3. **Анализ вредоносного ПО.** Песочницы (sandbox) антивирусных лабораторий и сервисов вроде VirusTotal выполняют динамический анализ образцов вредоносного кода. Во время исполнения образец часто обращается к DNS для разрешения имён командных центров или путей загрузки компонентов. Все эти запросы и полученные ответы попадают в pDNS-базу VirusTotal, обогащая её данными о вредоносной инфраструктуре.

4. **Пассивные зонды в сетях организаций.** Некоторые крупные предприятия передают обезличенные данные со своих корпоративных резолверов в pDNS-системы для улучшения качества threat intelligence и обнаружения скрытых утечек. Это закрытые источники, но они увеличивают полноту агрегированных коммерческих баз.

Схема движения данных от источников к конечному пользователю представлена ниже.

```text
[Клиенты Интернета]
   │ DNS-запросы
   ▼
[Рекурсивный резолвер провайдера] ──(деперсонализация)──▶ [Агрегатор pDNS]
                                                             ┌──────┴──────────────┐
                                                             ▼                      ▼
                                               [База данных pDNS]       [API / веб-интерфейс]
                                                      │
[Honeypot] ──(DNS-трафик атаки)──▶ [Сенсорная сеть] ──┘
[Песочница ВПО] ──(DNS-запросы образца)──▶ [Антивирусная лаборатория] ──┘
```

Все датчики работают в пассивном режиме: они лишь копируют ответы, уже прошедшие через них, не инициируя новых запросов к авторитативным серверам. Таким образом сохраняется главное свойство — отсутствие любого воздействия на целевую DNS-инфраструктуру.

### 2.2 Структура записи Passive DNS

Каждая запись в pDNS отражает факт наблюдения конкретной DNS-ресурсной записи (Resource Record, RR). Типовой набор полей включает:

| Поле             | Описание                                                                                   | Пример (иллюстративная схема)             |
|------------------|--------------------------------------------------------------------------------------------|-------------------------------------------|
| `domain`         | Доменное имя, для которого было зафиксировано наблюдение (FQDN)                            | `portal.example.com`                      |
| `rrtype`         | Тип ресурсной записи: A, AAAA, MX, NS, CNAME, SOA, TXT, PTR, SRV и др.                     | `A`                                       |
| `rdata`          | Данные ответа — IP-адрес для A, домен для MX/CNAME/NS, текстовый массив для TXT и т. д.      | `203.0.113.45`                            |
| `first_seen`     | Временная метка первого наблюдения этой связки                                              | `2023-08-15T02:11:33Z`                    |
| `last_seen`      | Временная метка последнего наблюдения                                                       | `2024-11-01T15:40:02Z`                    |
| `count`          | Количество наблюдений (опционально)                                                        | `147`                                     |
| `source`         | Идентификатор источника (например, `virustotal`, `securitytrails`)                          | `securitytrails`                          |
| `ttl`            | Значение TTL, с которым запись была получена                                               | `600`                                     |

Важнейшими для пентестера являются `first_seen` и `last_seen`. Они позволяют построить хронологию изменений: когда домен сменил IP, как долго существовал временный поддомен и т. д. Совокупная таблица записей одного домена по этим полям даёт «ленту времени» его DNS-истории.

Типы записей, доступные в pDNS, охватывают практически весь спектр RR, и каждый несёт свою разведывательную ценность:

- **A, AAAA** — IP-адреса, на которые указывает домен. Это основа для поиска связанных доменов по IP и анализа хостинг-провайдеров.
- **MX** — почтовые серверы домена. Могут раскрыть используемый почтовый хостинг (Google Workspace, Microsoft 365) или собственные серверы, что помогает при построении карты внешнего периметра и подготовке фишинговых симуляций.
- **NS** — DNS-серверы, обслуживающие зону. Изменение NS часто сопровождает захват домена или смену регистратора. Группировка доменов по общим NS-серверам — один из ключевых методов атрибуции инфраструктуры.
- **CNAME** — канонические имена. Раскрывают скрытые зависимости: например, поддомен `vpn.example.com` может быть алиасом для `vpn.thirdpartycloud.com`, что указывает на использование внешнего сервиса.
- **SOA** — запись о начале полномочий, содержит основной DNS-сервер и контактный e-mail, зачастую в устаревшем формате, который можно извлечь и проверить.
- **TXT** — текстовые записи, включая SPF, DKIM, DMARC, записи верификации владельца домена для сторонних сервисов (например, Google Site Verification). Эти строки могут выдать используемые облачные платформы и даже внутренние идентификаторы.
- **PTR** — обратные зоны; характерны для почтовых серверов, но могут быть использованы для сопоставления IP с доменными именами (reverse pDNS lookup).
- **SRV** — определяет хосты для конкретных служб (LDAP, SIP, XMPP), что прямо указывает на внутренние сервисы, вынесенные наружу.

### 2.3 Нормализация и ограничения

Данные, поступающие из разных источников, проходят нормализацию: приводятся к нижнему регистру, удаляются дубликаты, агрегируются по временным окнам. Качество данных варьируется: резолверы крупных провайдеров дают полную картину популярных доменов, но могут пропускать редкие внутренние имена или домены, используемые исключительно в узких сегментах сети. Вредоносные домены часто попадают в базы только после попадания образца в песочницу, что создаёт задержку в несколько часов или дней.

Необходимо учитывать следующие ограничения pDNS:

- **Задержка индексации.** Свежезарегистрированный домен может отсутствовать в базах от нескольких минут до суток, пока его не запросит хотя бы один клиент сенсорной сети.
- **Влияние шифрования DNS.** Распространение DNS-over-HTTPS (DoH) и DNS-over-TLS (DoT) в браузерах сокращает объём трафика, видимого классическими датчиками провайдеров. Системы pDNS, опирающиеся исключительно на провайдерские резолверы, могут потерять часть данных. Вендоры компенсируют это собственными резолверами и соглашениями с DoH-провайдерами, но полнота всё же снижается.
- **Отсутствие авторитативности.** Запись в pDNS — это лишь констатация того, что такой ответ был зафиксирован. Он мог быть результатом кэширования с ошибкой, подмены в локальной сети (ARP-spoofing) или ошибки конфигурации сервера. Поэтому pDNS-данные всегда следует перепроверять через другие источники.
- **Правовые ограничения.** Некоторые юрисдикции ограничивают сбор DNS-данных без согласия пользователей; поставщики pDNS обходят это обезличиванием и агрегацией, но объём данных может различаться по регионам.

## 3. Применение Passive DNS в пентесте: типовые сценарии и инструментарий

Пассивный DNS — не просто любопытный источник сведений, а полноценный инструмент для решения конкретных задач на этапе разведки. Рассмотрим основные сценарии использования в рамках тестирования на проникновение и соответствующий им инструментарий.

### 3.1 Обнаружение поддоменов и скрытых активов

Любой пентест начинается с составления карты внешнего периметра. Активные методы перебора поддоменов (brute-force по словарю) генерируют много запросов к публичным резолверам, что может привести к блокировке, а кроме того, нередко дают ложные срабатывания из-за wildcard-записей. Пассивный DNS позволяет получить список поддоменов, которые **уже видели** в реальном трафике, без единого запроса к целевой сети.

Для этого используются сервисы, предоставляющие поиск по домену и возврат всех известных поддоменов. Например, [SecurityTrails](https://securitytrails.com/) через [API](https://docs.securitytrails.com/reference) отвечает на запрос `https://api.securitytrails.com/v1/domain/example.com` JSON-объектом, содержащим поле `subdomains` с массивом FQDN. Иллюстративная команда:

```bash
curl -s "https://api.securitytrails.com/v1/domain/example.com?apikey=API_KEY" \
  | jq '.subdomains[]' \
  | head -n 10
```

Ожидаемый фрагмент ответа:

```
"www.example.com"
"mail.example.com"
"dev.example.com"
"staging.example.com"
"vpn.example.com"
...
```

Подобный запрос к VirusTotal через доменную разведку (endpoint `https://www.virustotal.com/api/v3/domains/example.com/subdomains`) при наличии API-ключа также возвращает список наблюдаемых поддоменов.

Полученный список, обогащённый pDNS-историей, позволяет обнаружить «забытые» поддомены, которые давно не используются, но всё ещё резолвятся или указывают на старые IP, что может стать точкой входа.

### 3.2 Исторический анализ и связывание IP-адресов

Для каждого обнаруженного IP-адреса пентестер может выполнить обратный поиск: «какие ещё домены когда-либо разрешались в этот IP». Большинство pDNS-провайдеров предлагают поиск по `rdata` (значению ответа). Типовой запрос к SecurityTrails:

```bash
curl -s "https://api.securitytrails.com/v1/ips/nearby/203.0.113.45?apikey=API_KEY" \
  | jq '.records[] | {hostname: .hostname, last_seen: .last_seen}'
```

Это вернёт список доменов, когда-либо указывавших на `203.0.113.45`, с указанием времени последнего обнаружения. Найденный среди них домен `internal-api.example.org` может не фигурировать в списке поддоменов, полученном на первом шаге, но указывает на существование внутреннего API, выходящего наружу. Такой подход особенно эффективен для поиска связанных между собой доменных имён в рамках одной кампании: фишинговый домен и его управляющий сервер часто живут на одном IP или перемещаются вместе.

Также pDNS помогает отслеживать миграцию инфраструктуры. Если домен `login.examplebank.com` в прошлом году указывал на IP, принадлежащий старому хостингу, а теперь — на облачный IP, но старый IP всё ещё принимает соединения и отвечает копией страницы, это серьёзная утечка, которую можно выявить, сопоставив исторические данные с текущим состоянием.

### 3.3 Выявление вредоносной инфраструктуры и фишинговых сетей

Злоумышленники часто регистрируют множество доменов, похожих на легитимные, и размещают их на одних и тех же серверах. Пассивный DNS позволяет связать такие домены через общие IP, NS-серверы или даже почтовые серверы (MX). Предположим, во время пентеста обнаружен подозрительный домен `micr0soft-update.com`. Запросив NS-записи для этого домена:

```bash
curl -s "https://api.securitytrails.com/v1/domain/micr0soft-update.com?apikey=API_KEY" \
  | jq '.current_dns.ns.values[]'
```

Вывод может показать серверы имён `ns1.badns.ru`, `ns2.badns.ru`. Поиск по этим NS через pDNS или специальные сервисы покажет все домены, которые используют те же серверы имён. Так можно быстро выявить десятки фишинговых доменов, принадлежащих той же группе, даже если они зарегистрированы в разных зонах и на разных аккаунтах.

Инструмент [PassiveTotal](https://www.riskiq.com/products/passivetotal/) предоставляет GUI и API для построения графа связей, где домены и IP объединяются в кластеры по общим атрибутам. Аналогично, [DNSDB](https://www.farsightsecurity.com/solutions/dnsdb/) от Farsight позволяет выполнять сложные запросы с фильтрацией по типу записи и времени.

### 3.4 Использование VirusTotal и открытых источников

VirusTotal предоставляет пассивный DNS через вкладку "Relations" для любого домена или IP. С помощью скрипта можно извлечь историю разрешений:

```bash
curl --request GET \
  --url "https://www.virustotal.com/api/v3/domains/micr0soft-update.com/resolutions" \
  --header "x-apikey: VT_API_KEY" \
  | jq '.data[] | {ip: .attributes.ip_address, date: .attributes.date}'
```

Ожидаемый пример ответа:

```json
{
  "ip": "198.51.100.77",
  "date": "2025-01-15"
}
{
  "ip": "203.0.113.99",
  "date": "2025-02-03"
}
```

Эта информация позволяет отследить миграцию инфраструктуры и привязать вредоносный домен к конкретному пулу IP-адресов, используемых злоумышленником.

### 3.5 Подводные камни и ограничения при практическом использовании

- **Платные API и квоты.** Бесплатные уровни доступа часто ограничены количеством запросов в месяц и не включают исторические данные за длительный период. Для полноценного пентеста требуется коммерческая подписка хотя бы на один pDNS-сервис.
- **Неполнота данных.** Ни одна база pDNS не хранит все DNS-ответы интернета. Домен, используемый исключительно внутри корпоративной сети, может вообще не попасть в pDNS, если его никогда не запрашивали через сенсорные резолверы.
- **Зашумлённость.** Среди найденных по обратному поиску доменов могут оказаться чужие, не относящиеся к цели. Например, на одном IP хостинга могут размещаться сотни клиентских сайтов, и простой перебор приведёт к шуму. Здесь помогает фильтрация по времени первого появления или совпадению регистраторов.
- **Юридическая осторожность.** Хотя pDNS считается пассивным методом, автоматический сбор поддоменов и связывание с угрозами без надлежащего соглашения может нарушать условия использования сервиса. Всегда следует проверять допустимые политики API.

## 4. Сквозной практический пример: расследование фишинговой инфраструктуры через Passive DNS

**Исходные условия:** В ходе мониторинга или фишинговой симуляции тестировщику стал известен подозрительный домен `secure-paypa1.com`, используемый для кражи учётных данных. Требуется, не отправляя ни одного пакета на сам домен и его сервер, выявить все связанные домены, IP-адреса и управляющую инфраструктуру. Используются следующие инструменты: SecurityTrails API (условный ключ `sTrlz-xxxxxxxx`), VirusTotal API (`vt-xxxxxxxx`), jq для обработки JSON, общие сетевые знания.

**Шаг 1. Получение истории A-записей домена.**  
Запрашиваем у SecurityTrails историю разрешений:

```bash
curl -s "https://api.securitytrails.com/v1/history/secure-paypa1.com/dns/a?apikey=sTrlz-xxxxxxxx" \
  | jq '.records[] | {first_seen, last_seen, ip: .values[].ip}'
```

Иллюстративный вывод:

```
{
  "first_seen": "2025-03-10T08:12:44Z",
  "last_seen": "2025-03-12T14:23:01Z",
  "ip": "198.51.100.88"
}
{
  "first_seen": "2025-03-12T14:25:11Z",
  "last_seen": "2025-03-15T18:00:00Z",
  "ip": "203.0.113.99"
}
```

Домен за несколько дней сменил IP-адрес. Оба IP интересны: первый мог быть временным, второй — постоянным. Действуем дальше.

**Шаг 2. Обратный поиск по IP-адресам.**  
Для каждого IP получаем все домены, которые когда-либо на него указывали:

```bash
curl -s "https://api.securitytrails.com/v1/ips/nearby/198.51.100.88?apikey=sTrlz-xxxxxxxx" \
  | jq '.records[] | {hostname, last_seen}' \
  | head -20
```

Часть вывода:

```
{"hostname":"secure-paypa1.com","last_seen":"2025-03-12T14:23:01Z"}
{"hostname":"login-paypa1.com","last_seen":"2025-03-12T13:55:01Z"}
{"hostname":"update-payment.online","last_seen":"2025-03-11T09:44:01Z"}
```

Мы видим два других домена, которые выглядели как фишинговые. Проводим аналогичный поиск по второму IP `203.0.113.99` — там могут быть ещё домены.

```bash
curl -s "https://api.securitytrails.com/v1/ips/nearby/203.0.113.99?apikey=sTrlz-xxxxxxxx" \
  | jq '.records[] | {hostname, last_seen}'
```

Результат:

```
{"hostname":"secure-paypa1.com","last_seen":"2025-03-15T18:00:00Z"}
{"hostname":"portal-verify.su","last_seen":"2025-03-15T17:45:00Z"}
{"hostname":"cdn-billing.net","last_seen":"2025-03-15T18:10:00Z"}
```

Полученные домены пополняют список целей, но не все обязательно связаны; фильтруем по времени — все они активны в один период, что подозрительно.

**Шаг 3. Анализ NS-серверов для группировки.**  
Выясним, какие NS-серверы использует наш исходный домен:

```bash
curl -s "https://api.securitytrails.com/v1/domain/secure-paypa1.com?apikey=sTrlz-xxxxxxxx" \
  | jq '.current_dns.ns.values[]'
```

Ответ:

```
"ns1.shadyhost.biz"
"ns2.shadyhost.biz"
```

Теперь проверим, какие ещё домены зарегистрированы на тех же NS, используя, например, сервис поиска по NS (может быть реализован через другой API, но для иллюстрации предположим, что мы получаем список доменов с теми же NS через SecurityTrails):

```bash
curl -s "https://api.securitytrails.com/v1/domains/list?ns=ns1.shadyhost.biz&apikey=sTrlz-xxxxxxxx" \
  | jq '.domains[]'
```

Примерный вывод:

```
"login-paypa1.com"
"update-payment.online"
"portal-verify.su"
"cdn-billing.net"
"legitbank-secure.com"
```

Все найденные ранее домены подтверждаются как имеющие общую управляющую инфраструктуру. Таким образом, мы связали пять доменов в одну кампанию, не отправив ни одного пакета к их серверам.

**Шаг 4. Верификация через VirusTotal Passive DNS.**  
Для каждого домена можно запросить историю разрешений VirusTotal, чтобы подтвердить IP и получить дополнительные временные метки, а также проверить, не засветились ли эти домены в отчётах антивирусов:

```bash
curl --request GET \
  --url "https://www.virustotal.com/api/v3/domains/login-paypa1.com/resolutions" \
  --header "x-apikey: vt-xxxxxxxx" \
  | jq '.data[] | {ip: .attributes.ip_address, date: .attributes.date}'
```

Вывод показывает, что `login-paypa1.com` также использовал IP `198.51.100.88` в тот же период, что подтверждает связь.

**Шаг 5. Построение карты связей и формулирование выводов.**  
Мы вручную или с помощью скрипта визуализации объединяем все сведения в граф: домены — прямоугольники, IP — овалы, направленные рёбра соответствуют A-записям, группировка по NS — общему родителю. Полученная картина выглядит так (текстовая схема):

```text
        ┌───────────────────────┐
        │ ns1/ns2.shadyhost.biz │ (NS серверы)
        └──────────┬────────────┘
   ┌───────────────┼─────────────────────────────┐
   ▼               ▼               ▼             ▼
secure-paypa1  login-paypa1  update-payment  cdn-billing.net
   │               │               │             │
   ▼ 198.51.100.88 ▼               │             │
   └───────┬──────┘   ┌────────────┘             │
           └──────────┼──────────────────────────┘
                      │              ▲
                      ▼              │
                   203.0.113.99 ─────┘ (portal-verify.su)
```

**Ожидаемый вывод:** Не произведя ни одного активного DNS-запроса к фишинговой инфраструктуре, мы смогли выявить пять доменов, два IP-адреса и общие NS-серверы, обслуживающие кампанию. Эта информация может быть передана команде реагирования, использована для блокировки на уровне прокси или DNS-фильтрации, а также для дальнейшего активного этапа пентеста (например, безопасного сбора контента с этих доменов через изолированную среду). Пассивный DNS позволил восстановить всю видимую инфраструктуру исключительно по следам, оставленным в сторонних хранилищах.
