# SpiderFoot: Архитектура и применение в автоматизированной OSINT-разведке

## Контекст и базовые понятия

Open Source Intelligence (OSINT) представляет собой процесс сбора и анализа информации из общедоступных источников для получения разведывательных данных. В контексте кибербезопасности и тестирования на проникновение OSINT является критически важным этапом разведки (Reconnaissance), соответствующим фазе сбора информации в моделях Kill Chain и MITRE ATT&CK (техники T1592, T1593). Традиционный ручной сбор данных (whois-запросы, перебор DNS, поиск в социальных сетях) не масштабируется при работе с крупными объектами из-за высокой скорости устаревания данных и необходимости агрегации разрозненных источников.

SpiderFoot (далее — SF) — это автоматизированная платформа для OSINT, написанная на Python, которая решает проблему масштабируемости за счет модульной архитектуры и механизма корреляции данных. Инструмент позволяет собирать информацию о целевых объектах (IP, домены, email, имена, телефоны) из более чем 200 источников, автоматически выявляя связи между ними.

Ключевое разграничение в терминологии OSINT-инструментов часто сводится к различию между **пассивной** и **активной** разведкой, а также между **графовыми** и **агрегирующими** платформами.

| Характеристика | SpiderFoot (Агрегатор/Коррелятор) | Maltego (Графовая платформа) | theHarvester / Subfinder (Специализированные сканеры) |
| :--- | :--- | :--- | :--- |
| **Основной принцип** | Publisher/Subscriber модель: данные из одного источника автоматически передаются в другие модули для расширения охвата. | Визуальное построение графа связей пользователем; трансформы запускаются вручную или по триггерам. | Линейный сбор данных по заданному списку индикаторов (IOC) без глубокой корреляции. |
| **Тип разведки** | Смешанная (Passive + Active). Может выполнять DNS-зонды, HTTP-запросы, но приоритет отдается API и пассивным базам. | Преимущественно активная (требует взаимодействия с целевой инфраструктурой для получения данных). | Преимущественно пассивная (поиск в поисковых системах, публичных сертификатах, DNS-базах). |
| **Вывод данных** | Структурированная база данных (SQLite/PostgreSQL), CSV, JSON, граф связей. | Интерактивный граф, отчеты в PDF. | Текстовые списки (CSV, TXT). |
| **Масштабируемость** | Высокая (параллельные запросы, обработка миллионов записей). | Средняя (зависит от мощности API и ручной настройки трансформов). | Низкая/Средняя (зависит от скорости перебора). |
| **Основная задача** | Автоматизация полного цикла разведки и выявление скрытых связей. | Визуализация сложных связей и ручное исследование. | Быстрый первичный сбор индикаторов. |

SpiderFoot позиционируется как инструмент для **автоматизации рутинных операций** и **корреляции данных**. В отличие от специализированных утилит (например, `dig` или `nslookup`), SF не просто выполняет запрос, а интерпретирует результат, извлекает новые индикаторы (например, из DNS-записи TXT извлекает email) и передает их в очередь на обработку. Это превращает линейный процесс в сетевой, где каждый найденный элемент становится новым «семенем» (seed) для дальнейшей разведки.

Понятие **Seed Target** (целевой объект) в SF является фундаментальным. Это начальный индикатор, с которого начинается сканирование. SF поддерживает широкий спектр типов seed-объектов: IPv4/IPv6, доменное имя, поддомен, сеть (CIDR), ASN, email, телефон, имя человека, username, Bitcoin-адрес. Выбор типа seed определяет стартовый набор модулей, которые будут активированы.

## Внутреннее устройство предмета

SpiderFoot представляет собой модульное веб-приложение с архитектурой клиент-сервер, где ядро работает на Python, а интерфейс — на JavaScript (React/Vue в зависимости от версии). Архитектура SF базируется на паттерне **Publisher/Subscriber** (Издатель/Подписчик), что обеспечивает динамическое расширение функциональности без изменения ядра.

### Модульная архитектура и механизм корреляции

Ядро SF (`sflib.py`, `sfscan.py`) управляет жизненным циклом сканирования. Каждый модуль в SF — это отдельный класс Python, наследующий базовый класс модуля. Модули классифицируются по типам данных, которые они собирают или обрабатывают.

**Ключевые категории модулей:**
1.  **Data Sources (Источники данных):** Модули, которые опрашивают внешние сервисы (Shodan, VirusTotal, Have I Been Pwned, WHOIS, DNS).
2.  **Data Consumers (Потребители данных):** Модули, которые анализируют уже собранные данные (например, модуль проверки email на валидность, модуль геолокации IP).
3.  **Correlators (Корреляторы):** Модули, которые ищут связи между различными типами данных (например, поиск доменов, зарегистрированных на тот же email, что и целевой).

Механизм работы основан на очереди задач (task queue). Когда сканирование начинается, SF создает список задач на основе seed-цели. Каждый модуль, подписанный на определенный тип данных (например, `IP_ADDRESS`), получает этот индикатор. После выполнения модуль возвращает новые данные (например, список доменов, связанных с IP). Эти новые данные добавляются в очередь как новые seed-объекты, что запускает каскадный эффект сбора информации.

### Структура данных и хранение

Результаты сканирования хранятся в реляционной базе данных (по умолчанию SQLite, поддерживается PostgreSQL). Структура данных оптимизирована для быстрого поиска связей.

**Иллюстративная схема структуры записи в БД SF:**

```json
{
  "id": "<уникальный идентификатор записи>",
  "data": "<значение индикатора, например, '192.0.2.1'>",
  "type": "<тип индикатора, например, 'IP_ADDRESS'>",
  "module": "<имя модуля, собравшего данные, например, 'shodan_internetdb'>",
  "confidence": "<уровень достоверности (0-100)>",
  "comments": "<пользовательские комментарии>",
  "source": "<первичный источник данных>",
  "url": "<URL, откуда получены данные>",
  "relevant_to": "<список ID других записей, с которыми связана данная>"
}
```

### Интерфейсы и управление

SF предоставляет два основных интерфейса:
1.  **Web UI:** Веб-интерфейс для визуализации графов, управления сканированиями и экспорта данных.
2.  **CLI (Command Line Interface):** Скрипт `sf.py` или `sfcli.py` для автоматизации и работы на серверах без GUI.

**Сравнительная таблица компонентов архитектуры:**

| Компонент | Функция | Технологический стек |
| :--- | :--- | :--- |
| **Core Engine** | Управление жизненным циклом сканирования, планировщик задач, логирование. | Python 3 |
| **Module Library** | Набор из 200+ модулей для сбора данных из различных источников. | Python 3 (классы) |
| **Database Layer** | Хранение результатов, корреляция данных, поиск связей. | SQLite / PostgreSQL |
| **Web UI** | Визуализация графов, управление сканированиями, экспорт отчетов. | JavaScript, HTML/CSS |
| **API** | Взаимодействие с внешними сервисами (Shodan, VT, MISP и др.). | HTTP/HTTPS, REST |
| **CLI** | Автоматизация сканирования, интеграция в CI/CD пайплайны. | Python 3 |

### Ограничения и инварианты

*   **Rate Limiting:** Многие модули зависят от внешних API, которые имеют ограничения на количество запросов. SF пытается балансировать нагрузку, но при интенсивном использовании могут возникать ошибки 429 (Too Many Requests).
*   **False Positives:** Автоматическая корреляция может генерировать ложные связи. Например, общий IP-адрес у разных компаний не означает их принадлежность к одной группе.
*   **Resource Intensive:** Полное сканирование домена с активацией всех модулей может потребовать значительных ресурсов CPU и RAM, особенно при работе с большими сетями (CIDR).

## Применение и работа с предметом

Работа с SpiderFoot в профессиональной среде требует понимания не только интерфейса, но и настройки окружения, управления API-ключами и интерпретации результатов. Ниже описаны типовые операции и процедуры.

### Установка и конфигурация

Для развертывания SF требуется Python 3.7+ и зависимости из `requirements.txt`. Установка из исходного кода является предпочтительной для получения последних версий модулей.

```bash
# Клонирование репозитория
git clone https://github.com/smicallef/spiderfoot.git
cd spiderfoot

# Установка зависимостей
python3 -m pip install -r requirements.txt
```

После установки необходимо настроить API-ключи для модулей, требующих аутентификации. Без ключей функциональность модулей ограничена или отключена. Ключи настраиваются через Web UI в разделе "Configuration" -> "Modules".

### Запуск сканирования и выбор профилей

При создании нового сканирования (New Scan) пользователь выбирает тип цели (Seed Target) и профиль сканирования. Профили определяют набор модулей, которые будут активированы.

**Типичные профили:**
*   **All:** Запускает все доступные модули. Максимальный охват, но высокое время выполнения и риск обнаружения.
*   **Footprint:** Фокусируется на публичной информации о домене/IP (DNS, WHOIS, SSL).
*   **Investigate:** Добавляет проверку на утечки данных, репутацию IP, данные из соцсетей.
*   **Passive:** Использует только пассивные источники (без прямого взаимодействия с целевой инфраструктурой).

### Анализ результатов и экспорт

Результаты сканирования доступны в нескольких представлениях:
1.  **Graph View:** Визуализация связей между индикаторами. Позволяет выявлять скрытые группы (например, несколько доменов, зарегистрированных на один email).
2.  **Table View:** Табличное представление всех найденных данных с фильтрацией по типу, модулю и достоверности.
3.  **Export:** Экспорт данных в CSV, JSON или XML для дальнейшего анализа в других инструментах (например, в SIEM или Threat Intelligence платформах).

**Типичные ошибки и подводные камни:**
*   **Игнорирование API-ключей:** Запуск сканирования без ключей приводит к получению только 20-30% данных.
*   **Перегрузка интерфейса:** При большом количестве связей граф может стать нечитаемым. Рекомендуется использовать фильтры или экспортировать данные для анализа.
*   **Неверная интерпретация связей:** Связь "домен -> IP" не означает, что все домены на этом IP принадлежат одной организации (возможны shared hosting).

### Интеграция в процессы безопасности

SpiderFoot может быть интегрирован в процессы Threat Intelligence и Incident Response. Результаты сканирования могут импортироваться в MISP (Malware Information Sharing Platform) для обмена данными с сообществом. Также возможно использование CLI для автоматизации регулярных сканирований собственных активов (Attack Surface Management).

## Сквозной практический пример: Разведка домена для пентеста

**Исходные условия:**
*   **Роль:** Пентестер, проводящий предварительную разведку перед тестированием на проникновение.
*   **Цель:** Домен `example.com` (используется как иллюстративная схема).
*   **Инструменты:** SpiderFoot 4.0+, Kali Linux.
*   **Сценарий:** Сбор публичной информации, выявление субдоменов, проверка утечек данных и поиск связанных активов.

### Шаг 1: Инициализация сканирования

Запуск сканирования через Web UI. Выбор типа цели "Domain" и ввод `example.com`. Выбор профиля "Footprint" для быстрого получения базовой сетевой информации.

```json
{
  "scan_name": "ExampleCorp_Footprint",
  "target": "example.com",
  "target_type": "DOMAIN",
  "profile": "Footprint",
  "modules": [
    "whois",
    "dns_records",
    "subdomain_enum",
    "ssl_cert"
  ]
}
```

**Ожидаемый результат:** Запуск сканирования, создание задачи в очереди, начало сбора данных из модулей WHOIS, DNS и SSL.

### Шаг 2: Сбор DNS-данных и субдоменов

Модуль `dns_records` собирает A, AAAA, MX, TXT, NS записи. Модуль `subdomain_enum` использует пассивные источники и словари для поиска субдоменов.

```bash
# Пример вывода модуля subdomain_enum (иллюстративная схема)
# Module: subdomain_enum
# Target: example.com
# Results:
# mail.example.com
# api.example.com
# dev.example.com
# staging.example.com
# admin.example.com
```

**Ожидаемый результат:** Список субдоменов, которые могут представлять интерес для дальнейшего тестирования (например, `dev` и `staging` часто имеют менее строгие настройки безопасности).

### Шаг 3: Проверка утечек данных и репутации

Активация модулей `haveibeenpwned` и `virustotal_com`. Проверка email-адресов, связанных с доменом, на наличие в базах утечек. Проверка IP-адресов на репутацию.

```json
{
  "module": "haveibeenpwned",
  "target": "admin@example.com",
  "results": [
    {
      "breach_name": "DataLeak2023",
      "breach_date": "2023-05-15",
      "data_types": [
        "email_address",
        "password_hash"
      ]
    }
  ]
}
```

**Ожидаемый результат:** Выявление факта утечки данных, что может указывать на компрометацию учетных записей и необходимость проверки доступа к внутренним системам.

### Шаг 4: Корреляция и визуализация связей

Просмотр графа связей в Web UI. Выявление доменов, зарегистрированных на тот же email, что и `example.com`.

```text
[example.com] --(WHOIS)--> [admin@example.com]
      |
      +--(DNS)--> [192.0.2.1]
      |
      +--(Subdomain)--> [mail.example.com]
      
[192.0.2.1] --(Reverse DNS)--> [mail.example.com]
[192.0.2.1] --(Whois)--> [other_company.com]
```

**Ожидаемый результат:** Выявление связи `example.com` с `other_company.com` через общий IP-адрес. Это может указывать на общую инфраструктуру или ошибку конфигурации, что расширяет поверхность атаки.

### Шаг 5: Экспорт данных для дальнейшего анализа

Экспорт результатов в CSV для импорта в другие инструменты или для создания отчета.

```bash
# Команда экспорта через CLI (иллюстративная схема)
sfcli.py export --scan_id 12345 --format csv --output example_footprint.csv
```

**Ожидаемый результат:** Файл `example_footprint.csv`, содержащий все собранные индикаторы, типы данных и источники, готовый для анализа.

Пример демонстрирует полный цикл OSINT-разведки с использованием SpiderFoot: от инициализации сканирования до корреляции данных и экспорта. Выявление субдоменов, утечек данных и скрытых связей позволяет пентестеру сформировать гипотезы о потенциальных векторах атаки и расширить цель тестирования.

## Аналитический вывод

SpiderFoot представляет собой мощный инструмент для автоматизации OSINT-разведки, который существенно снижает порог входа в сбор и корреляцию данных. Его модульная архитектура и механизм Publisher/Subscriber позволяют гибко настраивать процесс разведки под конкретные задачи, от пассивного сбора информации до активного сканирования. Однако, эффективность инструмента напрямую зависит от качества настройки API-ключей и понимания контекста собранных данных.

Ключевым преимуществом SF является способность выявлять скрытые связи между индикаторами, что недоступно линейным сканерам. Это делает его незаменимым для анализа поверхности атаки и Threat Intelligence. Тем не менее, инструмент требует осторожного использования из-за риска обнаружения при активной разведке и необходимости интерпретации результатов для исключения ложных связей. Интеграция SF в процессы безопасности позволяет автоматизировать рутинные задачи и повысить эффективность расследований инцидентов.
