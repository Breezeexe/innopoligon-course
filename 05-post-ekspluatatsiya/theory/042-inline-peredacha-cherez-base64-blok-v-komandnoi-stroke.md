# Inline-передача через Base64-блок в командной строке: механизмы, применение и детекция в пост-эксплуатации

## Контекст и базовые понятия

Передача файлов на скомпрометированный хост является критическим этапом пост-эксплуатации (post-exploitation), позволяющим злоумышленникам доставлять полезную нагрузку (payload), инструменты разведки или скрипты автоматизации. В условиях ограниченного канала связи или отсутствия возможности использовать стандартные сетевые протоколы (HTTP, FTP, SMB) из-за настроек межсетевых экранов (Firewall) или политик безопасности, применяется техника **inline-передачи через кодирование данных**.

Основой данного метода выступает алгоритм **Base64** — бинарно-текстовый кодировщик, преобразующий произвольные двоичные данные в строку, состоящую из символов ASCII (A-Z, a-z, 0-9, +, /). Это позволяет передавать бинарные файлы (исполняемые файлы, скрипты, дампы памяти) через текстовые каналы: командную строку (CLI), буфер обмена, HTTP-заголовки или тело запроса, не нарушая синтаксиса принимающей системы.

В контексте тестирования на проникновение и анализа угроз важно разграничивать два смежных понятия, которые часто путают:
1.  **Кодирование (Encoding)** — процесс преобразования данных для совместимости с каналом передачи. Не обеспечивает конфиденциальность. Цель — обойти фильтрацию по содержимому (content filtering) или ограничения на ввод бинарных данных в текстовые поля.
2.  **Шифрование (Encryption)** — процесс преобразования данных для обеспечения конфиденциальности с использованием криптографического ключа.

В рамках темы рассматривается именно кодирование Base64, классифицируемое в матрице MITRE ATT&CK как техника **T1132: Data Encoding** (Стандартное кодирование).

| Характеристика | Кодирование (Encoding) | Шифрование (Encryption) |
| :--- | :--- | :--- |
| **Цель** | Представление данных в текстовом формате для передачи. | Сокрытие смысла данных от несанкционированных лиц. |
| **Обратимость** | Определена алгоритмически, без ключа. | Требует наличия секретного ключа. |
| **Пример алгоритма** | Base64, Hex, Unicode, URL-encoding. | AES, RSA, ChaCha20. |
| **Индикатор компрометации (IoC)** | Высокая энтропия строки, наличие символов `=`, регулярные паттерны `A-Za-z0-9+/`. | Высокая энтропия, отсутствие видимых паттернов, специфичные заголовки пакетов. |
| **Применение в T1132** | Обход WAF, передача payload в CLI, скрытие в HTTP-заголовках. | Не является основной функцией T1132 (используется в T1024/T1048). |

Техника inline-передачи подразумевает, что закодированная строка вводится непосредственно в командную оболочку (PowerShell, CMD, Bash) или передается как аргумент функции, которая затем декодирует её и выполняет или сохраняет на диск. Это устраняет необходимость в создании временных файлов на промежуточных узлах или использовании внешних HTTP-серверов, что снижает сетевой шум, но увеличивает нагрузку на процессор целевой системы и оставляет следы в истории команд.

## Внутреннее устройство предмета

Inline-передача через Base64 базируется на взаимодействии трех компонентов: источника данных (payload), механизма кодирования (encoder) и механизма декодирования/исполнения (decoder/executor). В операционных системах Windows и Linux этот процесс реализуется через встроенные утилиты или классы библиотек.

### Механизм кодирования и структура данных

Base64 работает, разбивая входной поток байтов на группы по 3 байта (24 бита) и преобразуя их в 4 символа из набора из 64 возможных. Если количество байтов не кратно 3, добавляются символы заполнения (`=`).

Для файла размером $N$ байт, длина закодированной строки $L$ рассчитывается как:
$$ L = \lceil \frac{N}{3} \rceil \times 4 $$

Это означает, что размер данных увеличивается примерно на 33%. Для больших файлов (например, полных образов дисков или тяжелых бинарников) inline-передача через командную строку становится неэффективной из-за ограничений на длину аргумента командной строки (ARG_MAX в Linux, лимиты буфера в Windows).

### Реализация в Windows (PowerShell и CMD)

В экосистеме Windows наиболее распространенным инструментом для inline-передачи является PowerShell, использующий класс `System.Text.Encoding` и `System.Convert`.

**Структура команды PowerShell:**
1.  Чтение строки Base64.
2.  Декодирование в массив байтов (`byte[]`).
3.  Преобразование в исполняемый формат (например, запись в память или на диск).

```powershell
# Структура логики декодирования в PowerShell
[System.Text.Encoding]::ASCII.GetString([System.Convert]::FromBase64String("<Base64String>"))
```

Альтернативно, для бинарных данных используется:
```powershell
[System.Convert]::FromBase64String("<Base64String>")
```

В командной оболочке CMD (Command Prompt) встроенного декодера Base64 нет. Однако утилита `certutil`, входящая в состав Windows, поддерживает операцию `-decode`. Это позволяет использовать inline-передачу через перенаправление ввода:
```cmd
echo <Base64String> | certutil -decode - > output.exe
```
Здесь `certutil` выступает как декодер, а пайплайн (`|`) передает строку из буфера вывода `echo` во входной буфер `certutil`.

### Реализация в Linux (Bash и Python)

В Linux подход более гибок благодаря наличию утилиты `base64` и интерпретаторов.

**Утилита `base64`:**
```bash
echo "<Base64String>" | base64 -d > output.bin
```
Флаг `-d` указывает на декодирование.

**Python (inline-скрипт):**
```python
python3 -c "import base64; open('output.bin', 'wb').write(base64.b64decode('<Base64String>'))"
```

### Сравнение методов доставки

| Метод | Платформа | Преимущества | Недостатки | Типичный индикатор |
| :--- | :--- | :--- | :--- | :--- |
| **PowerShell + Base64** | Windows | Встроенный, гибкий, обходит базовые скрипт-бейслайны (если отключены). | Long-running process, логи PowerShell (Event ID 4104). | Длинная строка аргументов `powershell.exe -enc ...` |
| **Certutil -decode** | Windows | Встроенный системный инструмент, легитимный процесс. | Ограничение длины строки в CMD, запись на диск. | Процесс `certutil.exe` с аргументом `-decode` |
| **Base64 -d (Bash)** | Linux | Стандартная утилита, высокая скорость. | Ограничение ARG_MAX (~128KB+ в зависимости от ядра). | Процесс `base64` с флагом `-d` |
| **Python -c** | Linux/Windows | Мощный синтаксис, работа с сетью. | Требует установки Python, медленнее C-утилит. | Процесс `python3` с коротким кодом `-c` |

## Применение и работа с предметом

На практике специалист по тестированию на проникновение или аналитик SOC использует понимание механизма inline-передачи для двух противоположных целей: эмуляции атаки (Red Teaming) и детекции инцидентов (Blue Teaming).

### Эмуляция атаки: Доставка полезной нагрузки

При проведении тестирования на проникновение, если целевая система имеет ограниченный доступ к сети (air-gapped или строгий egress-фильтр) или если атака осуществляется через локальную оболочку (например, через RCE-уязвимость в веб-приложении), прямая загрузка файла невозможна.

**Типовой паттерн использования:**
1.  Подготовка payload (например, reverse shell или инструмент разведки).
2.  Кодирование payload в Base64.
3.  Формирование команды для выполнения на целевой системе.

**Пример формирования команды для PowerShell:**
```powershell
# Генерация Base64 строки из файла payload.exe
$payload = [Convert]::ToBase64String([IO.File]::ReadAllBytes("payload.exe"))

# Формирование команды для выполнения (пример: запись в файл)
$command = "IEX ([System.Text.Encoding]::ASCII.GetString([System.Convert]::FromBase64String('$payload')))"
```
В данном случае переменная `$command` содержит строку, которую можно передать через уязвимость командной инъекции.

**Ограничения и подводные камни:**
*   **Длина строки:** В Windows длина аргументов командной строки ограничена 8191 символами (для `cmd.exe`) и 32767 символами (для `powershell.exe` в некоторых версиях). Для больших файлов необходимо использовать фрагментацию (chunking) или внешние источники.
*   **Специальные символы:** Base64 использует символы `+`, `/`, `=`. В некоторых контекстах (например, URL или HTML-атрибуты) эти символы требуют дополнительного экранирования (URL-encoding), что усложняет inline-передачу.
*   **Обход скрипт-бейслайнов:** PowerShell по умолчанию блокирует выполнение необработанных скриптов. Inline-передача через `IEX` (Invoke-Expression) или `Invoke-Item` часто используется для обхода этого ограничения, так как код выполняется в памяти, не записываясь на диск в виде `.ps1` файла.

### Детекция и анализ: Поиск индикаторов компрометации

Для аналитиков безопасности ключевой задачей является выявление аномальной активности, связанной с декодированием Base64.

**Индикаторы в логах:**
1.  **Длинные строки в аргументах процессов:** Процесс `powershell.exe` с аргументом длиной более 1000 символов, начинающимся с `-enc` или `-encodedcommand`.
2.  **Активность `certutil.exe`:** Запуск `certutil` с флагом `-decode` или `-decodehex` является сильным индикатором компрометации (IoC), так как легитимное использование этой утилиты связано с управлением сертификатами, а не декодированием произвольных данных.
3.  **Высокая энтропия в сетевых пакетах:** Если Base64-строка передается по сети (например, в HTTP POST-запросе), анализ энтропии может выявить аномалии, хотя сам Base64 имеет предсказуемую энтропию (~4.5 бит/символ).

**Правило детекции (Sigma-формат):**
```yaml
title: Suspicious PowerShell Base64 Execution
id: 12345678-1234-1234-1234-123456789012
status: experimental
logsource:
  category: process_creation
  product: windows
detection:
  selection:
    Image|endswith: '\powershell.exe'
    CommandLine|contains:
      - '-enc'
      - '-encodedcommand'
      - 'FromBase64String'
  condition: selection
level: high
```

## Сквозной практический пример: Доставка и выполнение скрипта через PowerShell

**Исходные условия:**
*   **Среда:** Windows 10/11, PowerShell 5.1.
*   **Роль:** Пентестер, имеющий доступ к командной строке на скомпрометированном хосте (через веб-уязвимость или удаленное выполнение).
*   **Цель:** Передать и выполнить скрипт `rev_shell.ps1` (reverse shell), закодированный в Base64, без создания временных файлов на диске.
*   **Инструменты:** Генератор Base64 (локальный), целевой PowerShell.

### Шаг 1: Подготовка и кодирование payload

На машине атакующего генерируется Base64-строка из файла `rev_shell.ps1`. Для примера возьмем минимальный скрипт, выводящий текущий контекст пользователя.

```powershell
# Локальная генерация Base64 (иллюстративная схема)
$script_content = @"
Write-Host "Current User: $(whoami)"
Write-Host "Hostname: $(hostname)"
"@

$encoded_script = [Convert]::ToBase64String([System.Text.Encoding]::Unicode.GetBytes($script_content))
```

*Примечание: PowerShell по умолчанию использует Unicode (UTF-16LE) для строк. При декодировании важно учитывать кодировку.*

### Шаг 2: Формирование команды для выполнения

Формируется команда, которая декодирует строку и выполняет её через `IEX` (Invoke-Expression).

```powershell
# Команда для ввода в целевую систему (иллюстративная схема)
powershell.exe -NoProfile -NonInteractive -EncodedCommand <Base64String>
```

Или, используя явное декодирование внутри команды:

```powershell
# Явное декодирование ASCII (иллюстративная схема)
powershell.exe -Command "IEX ([System.Text.Encoding]::ASCII.GetString([System.Convert]::FromBase64String('<Base64String>')))"
```

### Шаг 3: Выполнение и верификация

Ввод команды в целевую систему. PowerShell декодирует строку, преобразует её в текст и выполняет как скрипт.

```powershell
# Ожидаемый вывод на экране целевой системы (иллюстративная схема)
Current User: NT AUTHORITY\SYSTEM
Hostname: WORKSTATION01
```

### Шаг 4: Анализ следов в логах

После выполнения команды в журнале событий Windows (Security Log) регистрируется создание процесса.

```json
{
  "EventID": 4688,
  "ProcessName": "C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe",
  "CommandLine": "powershell.exe -Command IEX ([System.Text.Encoding]::ASCII.GetString([System.Convert]::FromBase64String('V3JpdGUtSG9zdCAiQ3VycmVudCBVc2VyOiAkKHdob2FtaSkiICIK')))",
  "ParentProcessName": "C:\\Windows\\explorer.exe"
}
```

**Ожидаемый вывод:**
Пример демонстрирует, что файл не записывается на диск, что затрудняет обнаружение антивирусами, сканирующими файлы. Однако длинная строка в `CommandLine` и использование `IEX` являются четкими индикаторами компрометации для систем мониторинга.

## Аналитический вывод

Inline-передача через Base64 представляет собой фундаментальную технику пост-эксплуатации, позволяющую обходить ограничения на ввод бинарных данных и сетевые фильтры. В контексте Windows она наиболее часто реализуется через PowerShell (`System.Convert::FromBase64String`) и утилиту `certutil`, а в Linux — через стандартные утилиты `base64` и интерпретаторы. Ключевой особенностью метода является увеличение объема данных на 33% и зависимость от длины аргументов командной строки, что ограничивает применимость для крупных файлов.

Для специалистов по защите информации техника T1132 требует мониторинга не только самого факта кодирования, но и контекста его использования. Легитимные административные задачи редко используют inline-Base64 для выполнения кода, поэтому аномальная активность процессов `powershell.exe`, `certutil.exe` или `python.exe` с длинными закодированными аргументами должна рассматриваться как высокий риск. Эффективная детекция требует комбинации поведенческого анализа (вызов `IEX`, запись в память) и сигнатурного анализа (паттерны Base64 в логах событий).
