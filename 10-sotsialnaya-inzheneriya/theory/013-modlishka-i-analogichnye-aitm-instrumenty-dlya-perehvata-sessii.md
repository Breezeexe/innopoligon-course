# Моделирование AiTM-атак: Архитектура, Инструментарий и Детекция

## Контекст и базовые понятия: Эволюция фишинга и природа AiTM

Adversary-in-the-Middle (AiTM) — это класс атак социальной инженерии, использующий технологию обратного прокси (reverse proxy) для перехвата аутентификационных данных и сессионных токенов в реальном времени. В отличие от традиционного фишинга, где злоумышленник собирает статические учетные данные (логин/пароль), AiTM-инструменты функционируют как активный посредник между браузером жертвы и легитимным провайдером идентификации (Identity Provider, IdP).

Ключевое отличие AiTM от классического фишинга заключается в механизме обхода многофакторной аутентификации (MFA). При традиционной атаке, даже если жертва вводит код из SMS или TOTP-приложения, злоумышленник получает только временный одноразовый пароль, который истекает через минуту. При AiTM-атаке прокси-сервер перенаправляет введенные данные легитимному IdP, получает в ответ валидный сессионный cookie (например, `X-MS-RefreshToken` или `SPOIDCRL`) и передает его жертве для завершения визуального процесса входа. Злоумышленник сохраняет копию этого cookie. Поскольку cookie является доказательством успешной аутентификации, он позволяет обойти MFA полностью, так как сервер воспринимает запрос с этим cookie как запрос от уже аутентифицированного пользователя.

Эволюция AiTM-инструментов прошла путь от простых скриптов до сложных фреймворков, способных динамически адаптироваться к современным веб-приложениям (SPA, Single Page Applications). Современные платформы, такие как Tycoon 2FA или EvilProxy, коммерциализировали этот процесс, предоставляя функционал «фишинг как услуга» (Phishing-as-a-Service), что снизило порог входа для киберпреступников.

Для понимания архитектуры AiTM необходимо разграничить три ключевых понятия, которые часто путают в контексте перехвата сессий:

| Понятие | Механизм действия | Цель перехвата | Уязвимость к MFA |
| :--- | :--- | :--- | :--- |
| **Классический фишинг** | Статическая страница-подделка. Данные вводятся в форму, отправляющуюся на сервер атакующего. | Логин, пароль, код MFA (вводимый вручную). | **Уязвима.** Атакующий получает код, но не может завершить вход без него. |
| **AiTM (Reverse Proxy)** | Динамический прокси. Трафик жертвы ретранслируется в реальном времени на легитимный сайт. | Логин, пароль, код MFA, **сессионный cookie / refresh token**. | **Не уязвима.** MFA выполняется легитимно, но токен доступа перехватывается. |
| **Credential Stuffing / Brute Force** | Автоматизированная попытка входа с использованием утечек баз данных. | Попытка угадать пароль. | **Уязвима** (если нет MFA) или **блокируется** (при активном MFA и отсутствии токена). |

AiTM-атаки представляют собой критическую угрозу для инфраструктуры, использующей облачные сервисы (Microsoft 365, Google Workspace, Okta). Успешная атака приводит к полному компрометированию учетной записи, так как сессионный cookie предоставляет доступ ко всем ресурсам, связанным с этой учетной записью, без необходимости повторной аутентификации.

## Внутреннее устройство: Архитектура и инструменты AiTM

AiTM-инструменты строятся на базе обратного прокси, который перехватывает HTTP/HTTPS-трафик. Архитектура любого такого инструмента включает три основных компонента:
1.  **Веб-сервер прокси:** Принимает соединения от жертвы, обслуживает фишинговый контент.
2.  **Модуль ретрансляции:** Перенаправляет запросы жертвы на целевой легитимный домен и возвращает ответы.
3.  **Модуль парсинга:** Извлекает критические данные (cookies, токены) из ответов легитимного сервера.

Рассмотрим три основных открытых фреймворка, определяющих стандарты в этой области: **Evilginx2**, **Modlishka** и **Muraena**.

### Сравнительный анализ AiTM-фреймворков

| Характеристика | Evilginx2 | Modlishka | Muraena |
| :--- | :--- | :--- | :--- |
| **Архитектура** | Go-сервер с модульной системой «phishlets». | Go-сервер с автоматическим генерированием конфигураций. | Go-сервер с JSON-конфигурацией и динамическим парсингом. |
| **Механизм обхода CSP** | Подмена доменов в HTTP-ответах (content substitution). | Использование `iframe` и динамической загрузки ресурсов. | Динамическая замена URL в контенте и заголовках. |
| **Работа с Cookie** | Перехватывает `Set-Cookie` и модифицирует домен/путь для обхода ограничений SameSite. | Автоматический перехват всех cookies, связанных с целевым доменом. | Парсинг cookies через анализ HTTP-заголовков ответа. |
| **Сложность настройки** | Высокая. Требует ручного написания phishlet для каждого нового сервиса. | Низкая. Автоматическое определение структуры сайта. | Средняя. Требует настройки JSON-правил для сложных SPA. |
| **Поддержка SPA** | Хорошая (благодаря детальной настройке phishlet). | Умеренная (проблемы с динамической загрузкой ресурсов). | Умеренная (зависит от корректности правил замены). |
| **Индикаторы компрометации (IoC)** | Заголовки `X-Phish`, специфичные User-Agent, домены в phishlet. | Динамические поддомены, специфичные паттерны в HTTP-запросах. | JSON-конфигурации, специфичные паттерны ретрансляции. |

### Механизм обхода ограничений безопасности

Современные браузеры и IdP внедряют механизмы защиты, такие как `SameSite` cookies, Content Security Policy (CSP) и CORS. AiTM-инструменты используют следующие техники для их обхода:

1.  **Подмена доменов (Domain Substitution):** Когда легитимный сервер возвращает cookie с атрибутом `Domain=login.microsoftonline.com`, прокси изменяет этот атрибут на свой домен (например, `Domain=auth.attacker.com`), чтобы браузер жертвы отправлял cookie обратно атакующему.
2.  **Динамическая загрузка ресурсов:** Для обхода CSP, запрещающего загрузку скриптов с посторонних доменов, прокси загружает ресурсы (CSS, JS, изображения) с легитимного сервера, но подменяет URL в HTML-коде на свои. Это требует высокой точности парсинга HTML.
3.  **Обработка WebSocket и API-запросов:** Современные SPA активно используют WebSocket для обмена данными. Evilginx2 и Muraena перехватывают не только HTTP-запросы, но и WebSocket-соединения, ретранслируя их через прокси.

### Эволюция: Service Workers и EvilWorker

Новым направлением является использование Service Workers (EvilWorker). В отличие от традиционных прокси, работающих на уровне сервера, Service Workers регистрируются в браузере жертвы и перехватывают все сетевые запросы на клиенте. Это позволяет обойти ограничения CSP и CORS на стороне сервера, так как запросы исходят от домена жертвы, но перенаправляются на сервер атакующего. Этот метод требует меньше конфигурации, но зависит от поддержки Service Workers в браузере жертвы.

## Применение и работа с предметом: Развертывание и детекция

На практике тестирование на проникновение с использованием AiTM-инструментов требует тщательной подготовки инфраструктуры. Основные этапы включают: развертывание прокси, настройку доменов, конфигурацию phishlet и запуск кампании.

### Развертывание Modlishka

Modlishka отличается автоматизацией процесса настройки. Для развертывания целевого сервиса используется команда:

```bash
./modlishka -d target-domain.com -p 443 -c config.json
```

Где `config.json` может быть сгенерирован автоматически или задан вручную. Modlishka создает временные поддомены для обхода блокировок.

### Детекция AiTM-атак

Детекция AiTM-атак сложна, так как трафик выглядит легитимным. Основные методы детекции включают:

1.  **Анализ IP-адресов:** Использование IP-адресов, известных как прокси или VPN.
2.  **Анализ User-Agent:** Обнаружение нетипичных User-Agent для легитимных сервисов.
3.  **Корреляция сессий:** Обнаружение использования одного сессионного cookie с разных IP-адресов или устройств.
4.  **Анализ заголовков:** Обнаружение специфичных заголовков, добавленных прокси (например, `X-Phish` в Evilginx2).

### Пример правила детекции (Sigma)

```yaml
title: Detect Evilginx2 Proxy Headers
id: 12345678-1234-1234-1234-123456789012
status: experimental
logsource:
  category: web_proxy
  product: nginx
detection:
  selection:
    http_header_X_Phish: 'true'
  condition: selection
falsepositives:
  - False positive
level: high
```

## Сквозной практический пример: Моделирование AiTM-атаки на Okta

### Исходные условия
*   **Среда:** Локальная лаборатория с сервером Okta (имитация IdP) и клиентом (браузер).
*   **Инструменты:** Evilginx2, DNS-сервер, веб-сервер для фишинга.
*   **Роль:** Пентестер, моделирующий атаку на облачную инфраструктуру.
*   **Сценарий:** Перехват сессионного cookie Okta через фишинговую ссылку.

### Шаг 1: Подготовка инфраструктуры и DNS
Атакующий регистрирует домен, похожий на легитимный (например, `okta-auth.com` вместо `okta.com`). На DNS-сервере создается запись A, указывающая на IP-адрес сервера с Evilginx2.

```bash
# Настройка DNS (иллюстративная схема)
okta-auth.com.    IN    A    192.168.1.100
*.okta-auth.com.  IN    A    192.168.1.100
```

### Шаг 2: Запуск Evilginx2 и загрузка phishlet
Запускается Evilginx2 и загружается phishlet для Okta. Phishlet описывает структуру запросов Okta и правила перехвата cookies.

```bash
# Запуск Evilginx2
./evilginx -p ./lures -w ./phishlets

# Загрузка phishlet для Okta
lure create 1
```

### Шаг 3: Генерация фишинговой ссылки
Создается lure с фишинговой ссылкой, которая перенаправляет жертву на прокси.

```bash
# Генерация ссылки (иллюстративная схема)
lure link 1
# Результат: https://okta-auth.com/1/abc123
```

### Шаг 4: Перехват сессии
Жертва переходит по ссылке, вводит учетные данные и проходит MFA. Evilginx2 перехватывает сессионный cookie.

```json
// Иллюстративный вывод Evilginx2 (перехваченный cookie)
{
  "cookie_name": "SSO",
  "cookie_value": "00.abc123def456...",
  "domain": "okta-auth.com",
  "path": "/",
  "expiry": 1672531200
}
```

### Шаг 5: Использование перехваченного cookie
Атакующий использует перехваченный cookie для доступа к учетной записи жертвы.

```bash
# Использование cookie в curl (иллюстративная схема)
curl -H "Cookie: SSO=00.abc123def456..." https://okta-auth.com/admin
```

### Ожидаемый вывод
Пример демонстрирует, как AiTM-инструменты позволяют обойти MFA, перехватывая сессионный cookie. Это подчеркивает важность детекции нетипичного использования сессий и анализа IP-адресов.

## Аналитический вывод

AiTM-атаки представляют собой критическую угрозу для современной инфраструктуры, поскольку они обходят традиционные механизмы защиты, такие как MFA. Инструменты, такие как Evilginx2, Modlishka и Muraena, предоставляют злоумышленникам мощные средства для перехвата сессионных токенов. Детекция таких атак требует комплексного подхода, включающего анализ трафика, корреляцию событий и мониторинг нетипичного поведения сессий. Понимание архитектуры AiTM-инструментов и их механизмов обхода ограничений безопасности является ключевым для разработки эффективных стратегий защиты.
