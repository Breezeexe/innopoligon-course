# Упаковщики типа UPX как базовая обфускация исполняемого файла

## Контекст и базовые понятия упаковки исполняемых файлов

Упаковка исполняемых файлов (executable packing) — процесс преобразования PE-, ELF- или Mach-O-образа в форму, при которой оригинальный код и данные сжимаются или шифруются, а в начало файла добавляется код-распаковщик (stub), восстанавливающий рабочее состояние программы в памяти перед передачей управления на оригинальную точку входа (Original Entry Point, OEP). В контексте действий злоумышленников и пентестеров эта техника относится к тактике «Stealth» по MITRE ATT&CK и зафиксирована как подтехника [T1027.002 Software Packing](https://attack.mitre.org/techniques/T1027/002). Основная цель — изменение статической сигнатуры файла для обхода сигнатурных антивирусных сканеров, а также замедление ручного и автоматизированного анализа. По данным [Roundy и Miller (2013)](https://www.paradyn.org/papers/Roundy12-Packers.pdf) более 80% вредоносных семплов используют те или иные формы упаковки.

Упаковщики принято разделять на две большие категории, хотя граница нечёткая:

- **Компрессоры (compression packers)** — уменьшают размер файла без применения криптографических преобразований; код-распаковщик относительно прост и легко идентифицируется. Типичный представитель — UPX.
- **Протекторы / криптеры (encrypting packers / protectors)** — выполняют шифрование, виртуализацию кода, встраивают антиотладочные приёмы, модифицируют таблицу импортов, противодействуют снятию дампов памяти. Примеры: Themida, VMProtect, Enigma Protector.

Для пентестера UPX — доступный, воспроизводимый способ быстро изменить внешний вид исполняемого файла без привлечения сложных криптосредств. При этом важно понимать ограничения: UPX-артефакты широко известны и детектируются статическими анализаторами, а сам упаковщик не устойчив к обратному преобразованию штатной утилитой `upx -d`.

Сравнительная характеристика типичных представителей упаковщиков:

| Характеристика | UPX (UPX Team) | Themida (Oreans Technologies) | ASPack (ASPack Software) |
|----------------|----------------|-------------------------------|--------------------------|
| **Тип обфускации** | Сжатие (UCL/NRV/LZMA) | Шифрование + виртуализация + антиотладка | Сжатие + лёгкое шифрование |
| **Стойкость к статическому детекту** | Низкая (секции `UPX0`/`UPX1`, строка `UPX!`) | Высокая (кастомные stub, полиморфные варианты) | Средняя (известны сигнатуры) |
| **Сложность ручной распаковки** | Низкая – средняя (прямой jmp на OEP после цикла) | Высокая (виртуальная машина, антидамп) | Средняя (многослойная распаковка) |
| **Восстановление импортов** | Частично восстанавливаются stub’ом, но может потребоваться восстановление IAT | IAT запутана, часто требует скриптов и восстановления API-вызовов | Часто не требует доработки IAT после дампа |
| **Применение в пентестах** | Быстрое снижение детекта, PoC обхода AV | Используется для защиты коммерческих имплантов, но требует лицензии | Применяется редко из-за устаревшего кода и известных детектов |

В пентесте выбор в пользу UPX часто диктуется скоростью и доступностью инструмента, а не высокой стойкостью. Эта техника даёт эффект «обфускации первого порядка», снимая базовые сигнатуры и усложняя статический анализ жертве без продвинутых средств EDR.

## Внутреннее устройство упаковщика UPX и упакованного файла

UPX (Ultimate Packer for eXecutables) реализует архитектуру «stub – сжатые данные». Для формата PE/COFF оригинальный исполняемый файл целиком сжимается одним из поддерживаемых алгоритмов (по умолчанию — UCL, опционально — LZMA), а заголовки PE перестраиваются так, чтобы секции выглядели следующим образом (характерные имена секций, присваиваемые UPX):

- **`UPX0`** — секция с флагами `MEM_READ | MEM_WRITE | MEM_EXECUTE`, но в файле на диске её RawSize = 0 (или близок к 0); VirtualSize большой. Она служит приёмником для распакованных данных в памяти.
- **`UPX1`** — содержит сжатые данные и исполняемый код stub (распаковщика). Флаги обычно `MEM_READ | MEM_EXECUTE`.
- Иногда присутствует секция `.rsrc` (ресурсы), обрабатываемая отдельно.

Точка входа (EntryPoint) после упаковки указывает внутрь `UPX1` на начало кода распаковщика. Алгоритм работы stub выглядит так:

1. На стеке или в регистре сохраняется адрес OEP, извлечённый из структуры, внедрённой в конец сжатых данных.
2. Организуется цикл распаковки, который побайтово распаковывает содержимое из `UPX1` в адресное пространство, начинающееся с базы `UPX0`.
3. После завершения распаковки stub восстанавливает таблицу импортов, вызывая `LoadLibrary`/`GetProcAddress` для каждого требуемого API, и фиксирует IAT.
4. Выполняется инструкция перехода (часто `jmp` или `push`/`ret` в регистр) на оригинальную точку входа, после чего управление получает оригинальный код.

Структуру упакованного PE-файла можно визуализировать схематично:

```text
[ PE Header (изменённый) ]
[ Section Headers: UPX0, UPX1, .rsrc ]
[ UPX1 raw data (stub + compressed data) ]
(на диске UPX0 занимает 0 байт, но в памяти резервируется большой регион)
```

Типичный дамп заголовков секций запакованного UPX файла, полученный с помощью `dumpbin /headers`, показывает аномалию характеристик:

```bash
dumpbin /headers sample_upx.exe
```
Вывод (фрагмент, иллюстрирующий секции UPX0/UPX1):
```
SECTION HEADER #1
  UPX0 name
   10000 virtual size
   1000 virtual address (00401000 to 00410FFF)
       0 size of raw data
       0 file pointer to raw data
       0 file pointer to relocation table
       0 file pointer to line numbers
       0 number of relocations
       0 number of line numbers
E0000080 flags
         Code
         Execute Read Write

SECTION HEADER #2
  UPX1 name
   8000 virtual size
   2000 virtual address (00402000 to 00409FFF)
   4000 size of raw data
    200 file pointer to raw data (00000200 to 000041FF)
       0 file pointer to relocation table
       0 file pointer to line numbers
       0 number of relocations
       0 number of line numbers
E0000040 flags
         Initialized Data
         Execute Read
```
Отметим нулевой `size of raw data` у `UPX0` и флаг `Write` у исполняемой секции — характерные индикаторы UPX (для обычных исполняемых файлов секции кода редко доступны на запись). В `UPX1` размер сырых данных на диске значительно меньше виртуального размера, что обусловлено высокой степенью сжатия.

В процессе динамической распаковки регион `UPX0` заполняется оригинальными секциями программы (`.text`, `.data`, `.rdata` и т.д.), после чего stub восстанавливает IAT. Исходная точка входа обычно находится внутри скопированного `.text`. Для анализатора ключевым моментом является обнаружение операции передачи управления по завершении распаковки — хвостового `jmp` на OEP или эквивалентного перехода.

## Применение UPX в пентесте и практическая работа с упакованным файлом

Пентестеры применяют UPX к скомпилированному импланту или сгенерированному шелл-коду в формате PE для снижения вероятности срабатывания статических антивирусных движков. Типичная последовательность работы:

1. Генерация исполняемого файла (например, через `msfvenom` или компиляцию custom-агента на C/C++).
2. Упаковка с использованием актуальной версии UPX (стабильный релиз 4.0.2, но распространена также 3.96) с флагами максимального сжатия.
3. Тестирование детекта на VirusTotal, анализ выживаемости; при необходимости — изменение параметров сжатия или модификация флагов секций вручную (например, снятие подозрительного флага `WRITE` через редактирование PE-заголовка).
4. Доставка жертве.

Команда упаковки с максимальным сжатием и алгоритмом LZMA выглядит так:

```bash
upx --best --lzma payload.exe -o packed.exe
```
Вывод команды отображает степени сжатия и информацию о формате:
```
                       Ultimate Packer for eXecutables
                          Copyright (C) 1996 - 2024
UPX 4.0.2       Markus Oberhumer, Laszlo Molnar & John Reiser    Jan 12th 2024

        File size         Ratio      Format      Name
   --------------------   ------   -----------   -----------
     45056 ->     20480   45.45%    win64/pe     packed.exe

Packed 1 file.
```
Ключевые параметры UPX:
- `-1`...`-9`, `--best` — уровни сжатия.
- `--brute` — перебор параметров сжатия для достижения минимального размера (только совместно с `--lzma` в некоторых версиях).
- `--lzma` — использование алгоритма LZMA (более медленный, но лучшее сжатие).
- `--nrv2b`/`--nrv2d`/`--nrv2e` — методы NRV (по умолчанию).
- `-k` / `--keep` — не удалять оригинальный файл.
- `-d` — распаковка файла обратно.

Нестандартный флаг `--ultra-brute`, упоминаемый в некоторых публикациях, отсутствует в официальных сборках UPX и, вероятно, относится к кастомным модификациям упаковщика, создаваемым сообществом пентестеров для усиления обфускации (например, изменение структуры stub, добавление мусорных инструкций). В учебных целях его использование нецелесообразно; стандартные флаги достаточны для демонстрации.

После упаковки статические сигнатурные сканеры могут всё ещё детектировать UPX-артефакты. Для быстрой идентификации упаковщика применяются утилиты типа Detect It Easy (DiE), PEiD или Exeinfo PE.

```bash
die packed.exe
```
Вывод покажет информацию об упаковщике:
```
    packed.exe: PE32+ executable (GUI) x86-64, for MS Windows
        UPX(3.96)[NRV,best]
```
Дополнительно пентестер может проанализировать энтропию секций: у запакованных файлов секция, содержащая сжатые данные (`UPX1`), демонстрирует высокую энтропию, близкую к случайной (обычно >7.5 бит на байт). Это можно проверить с помощью Python-скрипта с модулем `pefile` или утилитой `binwalk`:

```python
import pefile
import math
pe = pefile.PE("packed.exe")
for section in pe.sections:
    name = section.Name.decode().rstrip('\x00')
    data = section.get_data()
    if not data: continue
    freq = [0]*256
    for b in data: freq[b]+=1
    n = len(data)
    entropy = -sum((f/n)*math.log2(f/n) for f in freq if f>0)
    print(f"{name}: entropy = {entropy:.2f}")
```
Пример вывода:
```
UPX0: entropy = 0.00
UPX1: entropy = 7.94
.rsrc: entropy = 3.45
```
Высокая энтропия `UPX1` — дополнительный индикатор упаковки/шифрования, используемый EDR.

Типичные ошибки начинающих пентестеров:
- Пренебрежение проверкой детекта на VirusTotal после упаковки (часть вендоров детектит сам UPX, а не полезную нагрузку).
- Использование стандартной сборки UPX без модификации заголовков, из-за чего файл маркируется как "packed by UPX" и может блокироваться политиками AppLocker/WDAC.
- Неправильная работа импланта после ручной модификации секций (например, удаление флага `WRITE` у `UPX0` ломает распаковку).

## Сквозной практический пример: упаковка, анализ и ручная распаковка UPX-семпла

**Исходные условия:** лаборантская среда Windows 10 21H2, установлены утилиты UPX 3.96, x32dbg, Scylla 0.9.8, Detect It Easy. Цель — продемонстрировать полный цикл: создание вредоносного кейлоггера на C, упаковка UPX, статический анализ, ручная распаковка из памяти с помощью отладчика.

**Шаг 1. Генерация тестового импланта.** Создадим простейший исполняемый файл, эмулирующий вредоносный агент (в реальном пентесте это может быть reverse shell, дампер учётных данных или троян). Используем файл `agent.cpp`, компилируем в 64-битном режиме:

```bash
x86_64-w64-mingw32-g++ -static -o agent.exe agent.cpp -lws2_32
```

Контролируем размер: порядка 50 КБ. Файл `agent.exe` не имеет обфускации.

**Шаг 2. Упаковка UPX.** Применяем максимальное сжатие и сохраняем результат:

```bash
upx --best --lzma agent.exe -o agent_packed.exe
```
Вывод подтверждает сжатие до 45% от исходного размера.

**Шаг 3. Статический анализ упакованного файла.** С помощью DiE уточняем факт упаковки и параметры:

```bash
die agent_packed.exe
```
Вывод (содержит UPX-сигнатуру):
```
UPX(3.96)[NRV,best]
```
Затем извлекаем список секций и энтропию через Python:

```python
import pefile, math
pe = pefile.PE("agent_packed.exe")
for sec in pe.sections:
    data = sec.get_data()
    entropy = 0.0
    if data:
        counts = [0]*256
        for b in data: counts[b] += 1
        n = len(data)
        entropy = -sum((c/n)*math.log2(c/n) for c in counts if c)
    print(sec.Name.decode(), hex(sec.VirtualAddress), hex(sec.VirtualSize), entropy)
```
Фрагмент вывода показывает нулевую энтропию `UPX0` и высокую у `UPX1`, что характерно.

**Шаг 4. Ручная распаковка в x32dbg.**
- Открываем `agent_packed.exe` в x32dbg. Отладчик останавливается на точке входа внутри `UPX1`.
- Наблюдаем типовой код UPX: сохранение регистров (`pushad` в 32-битном варианте), цикл распаковки. Устанавливаем аппаратную точку останова на исполнение инструкции после `popad` или на характерный безусловный переход.
- В 64-битном UPX используется другой stub, но принцип похож: ищем инструкцию `jmp rax` или `jmp` на регистр, которому предшествует восстановление контекста. Ориентир — адрес из пространства `UPX0`, куда уже записаны распакованные данные. Например:

```asm
; Фрагмент дизассемблера x64-версии UPX stub
00007FF7A0001E3  | 48 8B 45 F0        | mov rax,qword ptr ss:[rbp-10] ; OEP
00007FF7A0001E7  | 48 83 C4 20        | add rsp,20
00007FF7A0001EB  | 5D                 | pop rbp
00007FF7A0001EC  | C3                 | ret
```
После прохождения данной последовательности управление передаётся на OEP.

- В точке остановки снимаем дамп процесса с помощью плагина Scylla: «Dump memory» → «PE rebuild» с автоматическим восстановлением IAT. Сохраняем файл `unpacked.exe`.

**Шаг 5. Проверка работоспособности.** Запускаем `unpacked.exe`; он выполняет ту же функциональность, что и оригинал. Статический анализ показывает восстановленные секции и отсутствие UPX-артефактов. Дополнительно проводим сканирование на VirusTotal: количество детектов обычно снижается.

**Ожидаемый вывод:** пример демонстрирует, что UPX обеспечивает лишь базовую обфускацию, неспособную противостоять целенаправленному анализу, и что пентестер должен осознавать быстроту обратной операции. При модификации stub или комбинировании с другими техниками (например, подмена секций, разреженный код) UPX может служить элементом многослойной обфускации, но сам по себе не является стойкой защитой.
